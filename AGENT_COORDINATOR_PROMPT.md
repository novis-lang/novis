# Agent coordinator loop

MWL is built by a long series of unattended work sessions. This file describes how that loop is driven and
why it is shaped the way it is.

## The rule that determines the design

**A loop that lives inside one conversation cannot run hundreds of iterations.** Every iteration appends
permanently to that conversation — the subagent prompt, its report, the re-read handoff file — at roughly
3k tokens each. That caps a single coordinator session at ~30 iterations before it is either stopped or
auto-summarized, and a summarized coordinator quietly loses the standing instructions it exists to enforce.
No prompt wording fixes this; a conversation cannot forget.

So **the loop does not live in a conversation.** It lives in a driver process that starts one *fresh*
`claude` session per iteration. Context resets to zero every time, so session 400 costs exactly what
session 1 did. The loop's memory lives where it already lived: git history, `NEXT_SESSION_PROMPT.md`,
`docs/implementation-plan.md`.

Three things follow, and they are the whole design:

1. **The per-session prompt is fixed.** `.claude/SESSION_PROMPT.md` never changes between iterations. It is
   not regenerated by a coordinator, so it cannot drift.
2. **Stop conditions are script, not judgment.** The driver decides when to stop, from observable facts —
   an acceptance command's exit code, whether `HEAD` advanced, a status line the session wrote to disk.
   Nothing on the stop path depends on a model's self-assessment.
3. **The handoff file is bounded.** `NEXT_SESSION_PROMPT.md` is read in full by every future session, so it
   is capped at 80 lines and overwritten in place. Its contract is in `.claude/SESSION_PROMPT.md`.

## Files

| File | Role |
|---|---|
| `.claude/SESSION_PROMPT.md` | The fixed prompt handed to every session. Also holds the `NEXT_SESSION_PROMPT.md` handoff contract. |
| `.claude/loop-goal.md` | The loop's target and its machine-checkable acceptance command, plus the decisions pre-authorized on the way there. |
| `.claude/loop.ps1` | The driver. |
| `NEXT_SESSION_PROMPT.md` | Live state, rewritten by each session under the 80-line contract. |
| `.claude/loop-status.txt` | One line written by each session: `CONTINUE …`, `DONE …`, or `BLOCKED …`. |
| `.claude/loop-log.md` | Append-only ledger, one line per session: index, commit count, status. The human-readable run history. |
| `.claude/loop-logs/NNNN.log` | Full transcript of session NNNN as `stream-json` NDJSON, for when the ledger line is not enough. Replay it with `Get-Content …\0001.log \| ConvertFrom-Json`. |
| `.claude/loop-stop` | Create this file to halt the loop cleanly before the next session starts. |

## What the driver does, per iteration

    if .claude/loop-stop exists            -> stop
    record HEAD
    run: claude -p <SESSION_PROMPT.md> --model opus --permission-mode <mode>
              --output-format stream-json --verbose
         (each NDJSON event is appended to .claude/loop-logs/NNNN.log and rendered live to the console
          by Show-Event -- text, tool calls, tool errors, and the final turn/cost summary)
    if the CLI exited non-zero             -> exponential backoff, retry; give up after 3 in a row
    read .claude/loop-status.txt, diff HEAD, append one ledger line
    run the acceptance command from loop-goal.md
      -> passes                            -> stop, GOAL REACHED
    if status is DONE but acceptance fails -> stop and say so (the session was wrong)
    if status is BLOCKED                   -> stop, surface the decision
    if HEAD did not move                   -> stall++; stop after 3 consecutive stalls
    otherwise                              -> next iteration

The acceptance check running *before* the `DONE` check is deliberate: the machine outranks the claim.

## Running it

    powershell -ExecutionPolicy Bypass -File .claude\loop.ps1 -MaxSessions 300

Parameters worth knowing: `-MaxSessions`, `-Model`, `-PermissionMode`, `-MaxStalls`, `-MaxRetries`,
`-DelaySeconds`.

`-PermissionMode` defaults to `bypassPermissions`, and that is not an incidental default. A `claude -p`
session auto-denies any tool call that would otherwise prompt, so under `default` an unattended session
cannot run `cargo`, cannot commit, and cannot write its own handoff file — the run would halt on three
consecutive no-commit stalls having done nothing. Every session in the loop therefore runs unreviewed
against this working tree; that is the cost of the design, and the reason `.claude/loop-stop` and Ctrl-C
are both documented above.

Watch it with `Get-Content .claude\loop-log.md -Wait`. Stop it with `New-Item .claude\loop-stop` (finishes
the current session first) or Ctrl-C (kills it immediately; the repo is still consistent, because every
session commits before it exits).

## Setting a new goal

Rewrite `.claude/loop-goal.md`. It must contain a command whose exit code and stdout decide "done" — if the
goal cannot be expressed that way, the loop has no reliable stop condition and should not be run unattended.
Put every tradeoff the road to it will hit into that file's *Standing decisions* section, pre-authorized;
anything left out will eventually surface as a `BLOCKED` line and halt the run.

## Why not a coordinator conversation at all?

One is still fine for a **short** run — a dozen sessions, where you want to watch and intervene. Use the
same `.claude/SESSION_PROMPT.md` as the subagent prompt, one subagent at a time (they share one working
tree and one handoff file; concurrent sessions race). Keep the coordinator's own context small: never
re-read a diff, never re-derive the plan, never second-guess verified work. But stop at ~100k and restart —
and understand that restarting is not a workaround for the context problem, it *is* the driver design,
just done by hand.
