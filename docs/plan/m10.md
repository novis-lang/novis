# M10 — Developer tooling and IDE integration (~14 weeks; scope shifted by `rule:ide/every-feature-is-staged-behind-its-dependency`, net change undetermined)

M10 is the tooling a developer works in every day: the formatter, the editor, the test runner, the
profiler, the debugger, the debug service and its viewer, and the website pages that show them. The
goals below carry it, in the chain's order. Each goal file under `docs/goals/` holds its decisions and
its stages, and each rule it builds names it as its owner. The PhpStorm client is the one planned item
no goal carries: once these goals are reached, M10 keeps only the PhpStorm client and returns to the
backlog.

**`diagnostic-records`.** A compiler diagnostic and a `#[Test]` result become producers of the one
diagnostic record (`rule:errors/record-producers`), so `nvs check`'s text and `--json`, and the test
runner's JSON and JUnit reports, each render from one record. A `secret` literal in a diagnostic's
snippet is redacted, and an `inout` argument drops a `readonly` path's narrowing.

**`formatter-complete`.** `nvs fmt` closes every gap record it has, exits `2` for a file that does not
parse, leaves `vendor/` alone, and accepts `--check` with `--stdin`
(`rule:tooling/fmt-is-one-canonical-style`).

**`cli-housekeeping`.** `nvs cache gc` and `nvs cache clear`
(`rule:packaging/nvs-cache-gc-and-clear-are-the-deterministic-escape`), `nvs update-check` against the
public repository's latest release, and `nvs telemetry`, which records locally and uploads nothing until a
collector exists (`rule:tooling/telemetry-is-two-opt-ins`).

**`editor-refactors`.** Workspace rename with `require` paths updated on a file rename, workspace symbol
search, organize imports, extract to variable and to method, and the three generators
(`rule:ide/no-refactoring-introduces-an-alias`,
`rule:ide/a-code-action-writes-only-what-is-already-determined`).

**`editor-fixes`.** The five quick fixes whose diagnostics carry no suggestion yet, the narrowing action
and its one `nvs-types` function (`rule:ide/narrow-an-annotation-to-its-literal`), parameter hints on
every call, clickable lenses, settings applied without a restart, `semanticTokenScopes`, *Paste as doc
comment*, and the older `Core` reference cards in the plain voice.

**`api-document`.** A security scheme declared in code and checked, a class response and a request body
with real schemas, and a strict OpenAPI 3.1 validator over a fixture's document
(`rule:routing/api-document-is-generated-from-the-route-table`).

**`test-surface`.** Tests absent from `nvs run` and `nvs build` (`rule:testing/tests-never-reach-a-build`),
`private` members reachable from a test in the same file, `#[Property]`, `nvs test --list` over `.nvst`
trees, and the runner's time limit, tags, shards, fail-fast, rerun-failed, shuffle and watch.

**`mutation-testing`.** `nvs test --mutate` makes type-valid mutants from the checked program and runs
each only against the tests whose coverage reached its line (`rule:testing/mutation-testing`).

**`trace-timeline`.** Every trace event has a start and an end on one clock, the unbounded half of a
trace streams to a sink `Core\Debug` names, and the one profiler writes `--profile=callgrind` and
`--profile=speedscope` under `nvs run` and `nvs test` (`rule:testing/debug-surface`). VS Code's *View
Profile* opens the speedscope file in the extension's embedded speedscope.

**`bench-counters`.** `#[Bench]` and `nvs test --bench` report statements, calls, allocations, bytes and
GC cycles that are the same on every machine (`rule:testing/bench-counters`), and CI runs the
conformance suite with the probes on and at each optimisation level
(`rule:testing/probes-on-is-a-tested-configuration`).

**`debugger-core`.** The debug compile switch, a stop at a statement, the task tree paused with its
deadlines, frames and variables read, and breakpoints kept across a recompile, driven from Rust
(`rule:testing/a-debugged-program-is-compiled-with-a-debug-switch`,
`rule:testing/a-stop-pauses-the-whole-task-tree`).

**`debugger-adapter`.** `nvs dap` over stdio launches `nvs run`, `nvs test` or a development `nvs serve`,
steps over, into and out, and reports every capability the editor's debugger UI shows
(`rule:ide/the-debugger-ui-is-as-deep-as-the-adapter`). VS Code reaches it through a descriptor factory
and a `launch.json` schema, with no debugger UI of Novis's own.

**`debug-service`.** `[trace] response_header` can turn off the `traceresponse` header, and
`[debug] store` gates a per-writer spool of each request's outcome, input, response, events, dumps and
logs (`rule:testing/the-debug-stream-reaches-the-service-through-the-disk`). `nvs debug` ingests it into
a SQLite index that holds everything the viewer reads, and a development `nvs serve` starts it
(`rule:testing/the-ingester-runs-whether-or-not-anyone-is-looking`).

**`debug-viewer`.** The browser viewer `nvs debug` serves from the binary, on a listener only its own
page can use: the live request list and each request's timeline, the stream and the log with full-text
search and saved filters, grouped exceptions, open in editor, and compare and replay
(`rule:testing/the-viewer-shows-the-stream-and-hands-off-every-artifact`).

**`request-aware-editor`.** A method's lens counts the routes that reach it and the tests the last
coverage run saw reach it, and runs those tests. Call hierarchy walks the same call graph. A route's
hover shows the program's grants, a `tainted` or `secret` value's hover shows its path, each query
call shows what a recorded request ran there, and `nvs debug to-test` turns a recorded request into a
test that asserts its response.

**`tools-website`.** The website's Tools area: an overview and a page for each tool, every picture made
from a real run and checked, and the pages about running a tool moved there with no trace left behind.

**Not carried by a goal: the PhpStorm client.** `editors/phpstorm` is a Kotlin and Gradle plugin that
registers `.nvs` as its own file type, so PhpStorm's bundled PHP support never claims it
(`rule:ide/nvs-is-its-own-file-type`). It bridges to the same `nvs lsp` and `nvs fmt` binaries through
JetBrains' LSP client support, ships a baseline grammar, and conceals `secret` literals as VS Code does
(`rule:ide/phpstorm-bridges-to-the-same-server`). PSI-level refactoring, structural search, a native
code style page, a test explorer and debugger UI wiring stay out of scope for it
(`rule:ide/one-server-two-thin-clients`).

**Verify:** the PhpStorm plugin registers `.nvs` as its own file type, and opening one does not invoke
PhpStorm's bundled PHP support. It gets the same completion, hover, diagnostics, rename and formatting
round trip through the identical `nvs lsp` and `nvs fmt` binaries as VS Code: both editors agree byte
for byte on the same file's formatted output and its diagnostics, and neither client contains
formatting logic of its own. Breakpoints are verified through `nvs dap` directly, since PhpStorm has no
debugger UI wiring.
