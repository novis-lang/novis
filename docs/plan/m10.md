# M10 — Developer tooling and IDE integration (~14 weeks; scope shifted by `rule:ide/every-feature-is-staged-behind-its-dependency`, net change undetermined)

**Backlog 2.**

`nvs fmt` (canonical, idempotent — the **only** formatting implementation; neither editor client below gets
its own; its PER-based, unconfigurable, no-reflow style and `--check`/`--diff` surface are
`rule:tooling/fmt-is-one-canonical-style`) — reading **M4B's lossless entry point, not the strict
parse**, because `Lexer::skip_trivia` discards `//`, `#` and `/* */` without emitting a token, so a
formatter walking the strict tree would delete every comment in the file and `rule:tooling/fmt-quotes` promises the
opposite. `rule:ide/the-tree-survives-a-syntax-error` already schedules that tree
at M4B and already names `nvs fmt` as its second consumer, so nothing new is owed here beyond the
comment-attachment rule `rule:tooling/fmt-base-style-is-per`'s blank-line rules need. Then `nvs-lsp` grows past M4B's minimal slice
into full
workspace-wide symbol search, incremental reparse, rename, and code actions — **incremental reparse being
the one M4B deliberately did not buy**, since
`rule:ide/one-grammar-one-tree` traded `rowan`'s red/green design
away and the first move here is item-level caching over M4B's offset index rather than adopting it; that
ADR also settles the server's stack as `lsp-server`/`lsp-types` rather than the `tower-lsp` earlier drafts
named, so nothing in this milestone introduces an async runtime either. **Parameter inlay hints widen with
that slice**: M4B's walk annotates a call the checker recorded as `nvs_types::ExprInfo::Call` and nothing
else, so a `new`, a call through a `callable` signature and an erased call on a `mixed` receiver each wait
on the recorded variant carrying `param_names` — a table question rather than a walk one, and one this
milestone pays for on the compile path, where the table is, to buy a hint that is not. `nvs dap`
uses safepoints for breakpoints — among them the `DEBUG_BREAK` flag `nvs_safepoint` clears without acting
on while no adapter exists to take a stopped frame — plus deopt-to-debug in codegen, and
**reports the capabilities the editor's debugger UI is
only as deep as** — conditional breakpoints, hit counts, logpoints, exception filters, stepping
exclusions, path mappings, the value returned after a step out, and a `spawn`ed isolate presented as a
thread — because each of those renders in a UI that already exists and appears only if the adapter says it
is there
(`rule:ide/the-debugger-ui-is-as-deep-as-the-adapter`).
Then a sampling profiler, emitting output in the open speedscope
format so it opens in existing viewers rather than a bespoke flamegraph renderer
(`rule:ide/every-feature-is-staged-behind-its-dependency`); `nvs pkg` with lockfile, semver
resolution and a registry; and `nvs check --json`, the same `Diagnostic` records the text renderer prints
— codes, spans, severity, help and `suggestions` — under a schema frozen the way `nvs ast --json`'s is,
for CI and for the agents that drive this compiler
(`rule:ide/check-json-is-the-diagnostic-record-as-a-document`;
the text rendering stays the default and the Tasks `problemMatcher` keeps reading it). Also here: `Core\Debug`, the `[debug]` `nvs.toml` section and
`debug.trace`/`debug.profile` capabilities, and the Callgrind exporter wired to `nvs run --profile=…`
beside the Clover/lcov line coverage `nvs test --coverage-lcov`/`--coverage-clover` already writes
(`rule:testing/coverage-report`) — the developer-facing coverage/tracing/profiling feature whose
probe mechanism landed with M3
(`rule:testing/debug-probes`, a deterministic per-call
profiler distinct from the sampling one above), plus a speedscope-evented export rendering that same
trace data — now tagged `call`/`gc`/`spawn` — as one scrollable timeline
(`rule:observability/trace-events-carry-a-kind`). The same probe sites, in their
**counting** mode, are what `nvs test --bench` reports: statements, calls, allocations, bytes and GC cycles,
bit-identical across machines and OSes and therefore gateable in CI, with wall-clock printed as advisory
only (`rule:testing/bench-counters`). `nvs test --mutate` lands here too,
generating type-valid mutants from typed HIR and running each against only the tests the coverage data says
touch the mutated line (§ 21).

**`nvs test` runs its suite in parallel here.** `crates/nvs-cli/src/runner.rs` makes and joins one isolate
at a time, where [0079](../decisions/0079.md) § 2 has the suite parallel and every test in an isolate of
its own — the second half only, since the isolation half landed with the runner. It lands in this milestone
because this is where a suite run stops being one run: `--mutate` repeats the selected tests once per
mutant and `--coverage` repeats them instrumented, so the serial runner's cost turns from a developer's
minute into a CI job. A task group under
`rule:concurrency/limit-and-deadline-are-the-only-bounds`'s two bounds is the shape, and what a case that
reads the terminal does when its neighbours are running is the decision that comes with it.

**Also here: the generated API document stops being one a strict validator refuses.**
`rule:routing/api-document-is-generated-from-the-route-table` renders it off the finished route table,
so `crates/nvs-cli/src/openapi.rs` leaves out whatever the row does not carry: a class response or
request body gets the empty schema, since `rule:core-classes/derive-attribute`'s codec roster is not on
the row and nothing on it says which parameter *is* the body, and `components.securitySchemes` names
schemes the document never defines, since nothing in the tree declares what a named scheme is. Each is a
surface outside the emitter — a widening of the route row, and a place a scheme is declared where the row
can carry it — and they land here, with the rest of the machine-readable contracts beside `nvs check
--json`'s frozen schema, on the same trade the inlay-hint slice above takes: the compile path pays for a
table it does not need, to buy a tooling consumer that cannot derive it. The emitter renders them with no
change of its own, and `nvs api diff` is what makes a complete document worth carrying.

**Also in this milestone: the rest of the two editor clients.** M4B already shipped `nvs-lsp`'s minimal
slice and `editors/vscode`'s baseline; what lands here per
`rule:ide/one-server-two-thin-clients`/`rule:ide/every-feature-is-staged-behind-its-dependency` is
the deep half:

- **`editors/vscode`** (extending the M4B package, not a second one) — format-on-save and format commands
  wired to `nvs fmt`; inspections and quick fixes for every ADR-named diagnostic that has an obvious fix
  (missing property init, `include`→`require`, `tainted`/`secret` laundering — **casing and legacy casts
  already shipped at M4B**, being the two whose replacement text a `Diagnostic` already carries, so what
  is left here is every fix the checker has to compute something new for);
  workspace-wide rename, extract-to-method/variable, alias-free organize-imports; signature help and
  cross-file completion; inlay hints; a native Test Explorer wired to `nvs test`/`.nvst` with coverage via
  VS Code's own `FileCoverage` API (no custom gutter UI); a "View Profile" command opening the
  speedscope-format sampling output; and — the VS Code wiring `rule:ide/the-debug-adapter-does-not-wait-for-an-editor` commits to — a
  `DebugAdapterDescriptorFactory` and `launch.json` schema wiring `nvs dap` into VS Code's existing debugger
  UI. Full rationale and per-feature dependencies: `rule:ide/every-feature-is-staged-behind-its-dependency`.

  **Six more, added by `rule:ide/five-features-are-one-reference-index`
  after a review of a mature PHP extension in the same niche**, which found the plan level or ahead on
  everything a *language server* does and short on the layer above it. **`textDocument/references`** — absent
  from the list above rather than deferred, since rename already needs the index — plus the four features
  that are the same index read four more ways: `documentHighlight`, CodeLens (references, implementors,
  overrides), `typeHierarchy`, and dimming an unreferenced private member through LSP's `Unnecessary` tag,
  which is only correct at the workspace scope `nvs.check.scope` selects. **Completion from the tables the
  compiler already builds** — route names and their parameters
  ([0077](../decisions/0077.md)/[0102](../decisions/0102.md)),
  `nvs.toml` directives and their types ([0064](../decisions/0064.md)), `#[Api]` fields
  — under one closed rule: a value is offered only where the compiler already derives it for another reason,
  never from a convention scan, an annotation dialect or a network request. That rule is the whole of Novis's
  "framework support", and it is why no per-framework module enters `nvs-lsp` and why the reviewed product's
  largest feature — resolving a template engine's components and an ORM's columns — has nothing here to
  build. **HTML, CSS and JavaScript services inside an inline-HTML region**, forwarded to VS Code's own
  services across boundaries the server reports as `nvs/regions`: Emmet, tag closing and renaming, the
  colour picker, validation — and **no formatting**, because a second formatter inside a `.nvs` file is what
  `rule:tooling/fmt-is-never-a-diagnostic` exists to prevent. Since
  `rule:programs/first-party-framework` makes inline HTML the template engine, that region is
  where an application's markup is written, and it currently gets colour and nothing else. **Three code
  actions that generate rather than fix** — implement missing members, override a method, declare the
  function you just called — each bounded to text a declaration already determines, never a guessed body or
  a chosen signature. And the identifiers all of it freezes:
  `nvs.check.scope` (`"open"`/`"workspace"`, default `"open"`), `nvs.codeLens.enable`,
  `nvs.template.services`, the command `nvs.checkWorkspace`, and `extensionKind: ["workspace"]` so a WSL
  distro, an SSH host and a devcontainer spawn the remote's `nvs` rather than none.


  **And the narrowing action**, added by
  `rule:ide/narrow-an-annotation-to-its-literal`: a declaration
  whose initializer is an array literal offers to rewrite its `array<mixed>` annotation to the type that
  literal determines — each element's type widened to its base and joined into one canonical union, nested
  literals recursed, so a three-level structure gets its annotation in one keystroke. It declines where
  there is no literal to read (`Core\Json::decode` and every other value arriving from input), where the
  answer would be `array<mixed>` anyway, and past `rule:types/arrays`'s depth-32 bound. This milestone is also
  where its **one core change** lands, and it is the only one this whole editor layer needs: a single
  function in `nvs-types` synthesizing a literal's type, called by `nvs-lsp` and by no compile path — with
  the guard test that says so, since `check_array_literal`'s own unchanged return is what holds `rule:types/arrays` and `rule:types/var-inference` in place. The action is previewed as a diff and stays out of
  `source.fixAll.nvs` for the reason `rule:ide/narrowing-is-a-diff-never-a-save-time-fix` gives.
- **`editors/phpstorm`** — unchanged from `rule:ide/one-server-two-thin-clients`: a Kotlin/Gradle plugin
  that registers `.nvs` as its own file type (distinct from PhpStorm's bundled PHP support, which must not
  claim it), bridges to the **same** `nvs lsp`/`nvs fmt` binaries through JetBrains' LSP client support (or
  LSP4IJ, per `rule:ide/one-server-two-thin-clients` *Revisiting*), and ships an equivalent TextMate-or-equivalent baseline grammar.
  PSI-level refactoring, structural search, a native Formatter/Code Style page, a Test Explorer, and
  debugger UI wiring are all still out of scope for PhpStorm — `rule:ide/one-server-two-thin-clients`
  names the native-plugin path as a later decision, not a silent gap, and `rule:ide/every-feature-is-staged-behind-its-dependency`
  does not touch PhpStorm at all.

**Also here: the debug service, and the editor features that read a request rather than a file.**
[0163](../decisions/0163.md)'s service is built in this milestone, since nothing earlier schedules it and
two of the features below have no data without it. Every editor surface here is a code lens, a hover or
a decoration LSP already has (`rule:ide/the-extension-builds-no-ui-the-editor-already-has`), and each
feature's decision record is written by the goal that builds it:

- **The debug service, first** — the per-writer spool file
  (`rule:testing/the-debug-stream-reaches-the-service-through-the-disk`), the `[debug] store` gate
  (`rule:testing/writing-a-debug-record-to-disk-is-its-own-gate`), the service that ingests sealed spool
  files, and its viewer listing correlated requests
  (`rule:testing/the-viewer-shows-the-stream-and-hands-off-every-artifact`). The last two items below
  read what it recorded, so they land after it.
- **"Used by" code lens** — above a method, "used by N routes, M tests", read from
  `rule:ide/five-features-are-one-reference-index`'s index joined to the compiled route table
  (`rule:routing/routes-are-compiled-not-registered`). One click runs exactly those tests, which needs
  the per-test lines goal `coverage-depth` adds to `nvs test`'s JSON report, so this lands after the
  reference index and after that goal.
- **What a route can reach** — hovering a route shows the files, hosts and databases its handler may
  use, read from the grants and limits the runtime enforces
  (`rule:security/capability-question-is-grant-and-scope`) and never inferred from the code, so the
  hover is exactly as deep as the grant table on disk.
- **Taint flow** — the editor shows the path a `tainted` or `secret` value takes from where it enters
  (`rule:security/tainted-sources`) to where it is used, with the point it is laundered marked
  (`rule:security/launderers-are-sink-named`). The checker records that path only where `nvs-lsp` asks
  for it, so a compile for running pays nothing; it sits beside the `tainted`/`secret` laundering quick
  fixes above.
- **A recorded request becomes a test** — from a request the service recorded, one command writes a
  `Core\Test::request` case (`rule:testing/in-process-request`) with the input it arrived with and
  assertions on the response it produced. What the case does with a header carrying a credential is
  that goal's record to settle.
- **Queries per call site** — for one recorded request, a code lens on each query call site shows the
  count, the total time and the slowest time, and flags the same query running many times in that one
  request (the N+1 problem). It is aggregated per call site, so the data is bounded by the query sites a
  request reaches and not by how often a loop iterates — `rule:testing/debug-surface`'s argument for
  line counters. A query given as a string literal (`rule:core-classes/db-compile-time-query-checking`) is grouped by its site
  exactly; one built at run time is grouped by its text with the parameters removed. One parameter set,
  the slowest run's, is kept per site.

**Not built: variable values shown inline from recorded requests**, because recording values grows with
every iteration and every request, far past what any bounded per-site figure holds; `nvs dap`'s
conditional breakpoints and logpoints answer the same question on demand. What all of this spends is
development-mode or editor-side: a deployment with `[debug] store` off pays the predicted-not-taken
probe branch `rule:testing/debug-probes` already prices and nothing further, and the query lens holds a
few numbers per query site per recorded request.

**Verify:** `nvs fmt` is idempotent across the whole corpus, a file carrying a comment in every position the
grammar allows one round-trips through it with all of them intact and attached where they started, and
neither editor extension contains its own formatting logic. The VS Code extension's inspections/refactorings/rename round-trip as LSP code actions
and requests with no logic duplicated locally; format-on-save leaves every Novis byte exactly as `nvs fmt`
writes it and indents each markup chunk from the `?>` that opened it (`rule:ide/a-template-region-gets-the-editors-services-and-formatter`); the
Test Explorer runs `.nvst` cases and shows coverage sourced from the Clover/lcov exporters; a captured
profile opens correctly in a speedscope-compatible viewer; a breakpoint set in VS Code's UI hits in
JIT-compiled code with correct variable values through the wired-up `nvs dap` adapter, with no
Novis-authored debugger UI code. Of `rule:ide/five-features-are-one-reference-index`'s six: a `.lspt` case per added request resolves at a cursor and
matches a frozen rendering, and `every_request_answers_every_construct` gains a row for each; `nvs-lsp` has
exactly one symbol-index construction site and all five of § 1's features read it; a test enumerates the
completion sources and fails one that reads a directory layout, an annotation dialect or the network, with
the server itself answering every request under denied outbound sockets; route-name and `nvs.toml`
completion are asserted against the producing table rather than a copied list; an Emmet expansion and a CSS
colour decoration are produced inside an inline-HTML region while formatting that file stays byte-identical
to `nvs fmt` and `nvs fmt --check` passes; each generator's output compiles and applying it twice is a
no-op; `nvs dap` reports each capability at `initialize` and a fixture session exercises all of them; and
`nvs check --json` emits one record per diagnostic the text renderer prints, with the same codes and spans.
Of the request-aware features: with `[debug] store` on, a fixture's requests appear in the viewer
correlated by trace id from sealed spool files only, and with it off the run writes no spool file and its
probe counts match a run with no `[debug]` block; a method's "used by" lens counts match the route table
and the per-test coverage of a fixture, and its click runs exactly that test set; a route's hover lists
the paths, hosts and databases a fixture's grants give its handler and changes when those grants do, with
no source edit; a `.lspt` case shows a `tainted` and a `secret` value's path from its source to its sink
with the launderer marked, and a compile without `nvs-lsp` records no path; a test generated from a
recorded request passes against the unchanged program and fails when its handler's response changes; and
a fixture running one query inside a loop of many iterations shows one lens entry at that site with the
right count, flags it as repeated, and its recorded size does not grow with the iteration count.
The PhpStorm plugin registers `.nvs` as its own file type (opening one does
not invoke PhpStorm's bundled PHP support) and gets the same completion/hover/diagnostics/rename/formatting
round trip through the identical `nvs lsp`/`nvs fmt` binaries as VS Code — evidenced by both editors
agreeing byte-for-byte on the same file's formatted output and diagnostics — with breakpoints verified via
`nvs dap` directly, since PhpStorm's debugger UI is still not expected to exist yet.
