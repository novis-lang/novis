# The throwable tree

Every error in Novis is an object of a class under `Throwable`, and the whole tree is short. There
is no `Exception` and no `Error`.

`LogicError` means a bug in your own program, such as a `match` with no arm for the value it was
given. `RuntimeError` means the world said no: a missing array key, a value that cannot be
converted, a file you are not allowed to read. `IOError`, `ParseError`, `TimeoutError` and
`RecursionError` are kinds of `RuntimeError`. `ArithmeticError` is its own branch, for division by
zero and for a number that does not fit.

A `catch` arm also catches every class under the one it names, so `catch (Throwable $e)` catches
everything.

**The examples below** show which class each common failure throws, how one arm takes a whole
branch, and a job that treats a bug and a bad input differently. The last one shows the error for
`Exception`.

`Exception` and `Error` are not declared. `class ConfigError extends Exception`, `catch (Error $e)` and
`new Exception("…")` are each the error `E0303`. Write `Throwable`, `LogicError` or `RuntimeError`.

`Throwable` is a class. You can create one with `new Throwable("…")`, and you can extend it directly.

`ArithmeticError` extends `Throwable`, not `RuntimeError`. A `catch (RuntimeError $e)` clause does not
catch it. These are the messages it has:

- Division by zero gives `Division by zero`.
- `%` by zero gives `Modulo by zero`.
- An `int` addition past the largest `int` gives `Integer addition overflowed`.
- `2.5 as int` gives ``cannot convert `float` 2.5 to `int` ``. A `float` with a fraction does not
  convert to `int`.

Your own class can extend any class in the tree, `ArithmeticError` and `ParseError` too. A class that
extends `ParseError` has `issues`, and the list is empty. A class in the tree may be `final` or
`abstract`.

`Core\Test\Failure` is the class of a failed assertion. It extends `Throwable` directly, and your own
class cannot extend it: that is the error `E0303`.

`Core\Script::finish()` ends the program, and no `catch` catches it. A `finally` block still runs.

## Example 01: which class a failure throws

```nvs
<?nvs
// Shows which class each common failure throws. The class tells you what kind
// of problem it is, so you can catch only the kind you can handle.

int $zero = 0;
array<int> $stock = ['mugs' => 4];
mixed $text = 'abc';

// Division by zero is an `ArithmeticError`.
try {
    echo 1 / $zero, "\n";
} catch (ArithmeticError $divided) {
    echo $divided->message, "\n";
}

// A key that is not in the array is a `RuntimeError`.
try {
    echo $stock['plates'], "\n";
} catch (RuntimeError $missing) {
    echo $missing->message, "\n";
}

// A value that cannot be converted is a `RuntimeError` as well.
try {
    echo $text as int, "\n";
} catch (RuntimeError $bad) {
    echo $bad->message, "\n";
}

// A `match` with no arm for the value is a bug in the program, so it is a
// `LogicError`.
try {
    echo match ($zero) { 1 => 'one' }, "\n";
} catch (LogicError $noArm) {
    echo $noArm->message, "\n";
}
```

```output
Division by zero
undefined array key `plates`
cannot convert this value to `int`
no `match` arm matched the subject
```

## Example 02: one arm takes a whole branch

```nvs
<?nvs
// Shows that a `catch` arm also catches every class under the one it names.
// `IOError`, `ParseError` and `TimeoutError` are kinds of `RuntimeError`.

final class Feed
{
    public static function fetch(string $source): tainted string
    {
        if ($source == 'slow') {
            throw new TimeoutError('the feed did not answer in time');
        }
        if ($source == 'gone') {
            throw new IOError('the feed file is missing');
        }
        return Core\Json::encode(Core\Json::decode($source));
    }
}

array<string> $sources = ["{\"ok\": true}", 'slow', 'gone', "{\"ok\": }"];
foreach ($sources as string $source) {
    try {
        echo Feed::fetch($source), "\n";
    } catch (ParseError $bad) {
        // The narrow arm goes first. It takes the parse errors and nothing else.
        echo 'bad input: ', $bad->message, "\n";
    } catch (RuntimeError $other) {
        // The wide arm takes the rest of the branch, here a timeout and a
        // missing file.
        echo 'the feed said no: ', $other->message, "\n";
    }
}
```

```output
{"ok":true}
the feed said no: the feed did not answer in time
the feed said no: the feed file is missing
bad input: Core\Json::decode(): expected value at line 1 column 8
```

## Example 03: a bug and a bad input

```nvs
<?nvs
// Shows a job that treats the two halves of the tree differently. A
// `RuntimeError` is bad input, so the job reports the line and carries on. A
// `LogicError` is a bug in the program, so the job stops.

final class Cart
{
    public static function total(array<int> $line): int
    {
        // A field that is not there throws a `RuntimeError`.
        int $price = $line['price'];
        int $count = $line['count'];
        if ($count < 0) {
            // A count below zero can only come from our own code.
            throw new LogicError('a line with a count below zero');
        }
        return $price * $count;
    }
}

array<array<int>> $lines = [
    ['price' => 250, 'count' => 2],
    ['price' => 400],
    ['price' => 100, 'count' => 0 - 1],
];

int $sum = 0;
foreach ($lines as array<int> $line) {
    try {
        $sum = $sum + Cart::total($line);
    } catch (RuntimeError $input) {
        echo 'skipped a line: ', $input->message, "\n";
    } catch (LogicError $bug) {
        echo 'stopping, this is a bug: ', $bug->message, "\n";
        break;
    }
}
echo 'total ', $sum, "\n";
```

```output
skipped a line: undefined array key `count`
stopping, this is a bug: a line with a count below zero
total 500
```

# Properties, not accessors

You read a caught error through its properties. There are no accessor methods.

`getMessage()`, `getPrevious()`, `getTrace()`, `getFile()`, `getLine()` and `getCode()` do not
exist. Write `$e->message` instead.

Every error has the same four properties. `message` is the text it was created with. `previous` is
the error that caused it, or `null`. `backtrace` is one line per function the throw came out of,
innermost first. `location` is the file and the line of the `throw`. A `ParseError` adds `issues`,
one entry per problem the parser found, each with a `path` and a `message`.

**Good to know:** there is no error code anywhere. The class of the error is what says what kind of
problem it is.

**The examples below** show where a throw came from, the list of problems in a parse error, and one
log line built out of a caught error. The last one shows the error for `getMessage()`.

`getMessage()`, `getPrevious()`, `getTrace()`, `getTraceAsString()`, `getFile()`, `getLine()` and
`getCode()` are each the error `E0405`. The help names the property to read instead. For `getCode()` it
lists the four properties, because there is no error code. `$e->code` is the error `E0405` too.

All four properties are `readonly`. `$e->message = "…"` is the error `E0782`.

`location` is the empty string until the object is thrown. When the same object is thrown a second
time, `location` changes to the line of the second `throw`.

`backtrace` has one line for each method the throw left. A throw in the top-level code of a file has
one line, `<script>() at main.nvs:2`. An object that was never thrown has an empty `backtrace`.

`previous` is a `?Throwable`. `$e->previous->message` is the error `E0459`, because `previous` may be
`null`. Write `$e->previous?->message`.

`issues` exists on `ParseError` and its subclasses. On any other class, `$e->issues` is the error
`E0405`. A `ParseError` that your own code creates has an empty `issues` list.

`Core\Debug::dump($e)` prints the four properties. `echo $e` is the error `E0412`, and
`Core\Json::encode($e)` throws a `RuntimeError`. Build the text from `$e->message` and the other
properties.

## Example 03: one log line for a failure

```nvs
<?nvs
// Shows one log line built out of a caught error. It says what went wrong,
// where it was thrown, and which error caused it. The chain is followed to the
// first cause.

class CheckoutFailed extends RuntimeError
{
    public function constructor(string $message, ?Throwable $cause)
    {
        parent::constructor($message, { previous: $cause });
    }
}

final class Checkout
{
    public static function pay(string $order): string
    {
        try {
            throw new TimeoutError('the payment service did not answer');
        } catch (TimeoutError $slow) {
            throw new CheckoutFailed('order ' . $order . ' was not paid', $slow);
        }
    }
}

try {
    echo Checkout::pay('4021'), "\n";
} catch (Throwable $failed) {
    string $line = $failed->message . ' at ' . $failed->location;
    var $cause = $failed->previous;
    bool $more = true;
    while ($more) {
        // `previous` is `null` at the end of the chain. So the code copies it
        // into a variable and checks it before it reads `message`.
        var $here = $cause;
        if ($here == null) {
            $more = false;
        } else {
            $line = $line . ', caused by: ' . $here->message;
            $cause = $here->previous;
        }
    }
    echo $line, "\n";
    echo 'frames: ', Core\Arr::count($failed->backtrace), "\n";
}
```

```output
order 4021 was not paid at main.nvs:21, caused by: the payment service did not answer
frames: 1
```

# Constructing and subclassing

Every error is built the same way: `new` with a message, and an optional second argument naming the
error that caused this one.

You can write an error class of your own. It extends `Throwable` or any class under it. A class that
writes no constructor uses the one it inherits, so `new OutOfStock("no mugs left")` works with
nothing else to write. A class that wants more can write its own constructor, add properties, and
pass the message on with `parent::constructor($message)`.

A message is always required. `new RuntimeError()` does not compile.

**Good to know:** both arguments have names, so you can write
`new RuntimeError(message: "the server said no")` and read the call without counting positions.

**The examples below** show an error class of your own, one that adds properties in its own
constructor, and a loader that keeps the error it caught as the cause of the error it throws.

The message must be a `string`. `new RuntimeError(5)` is the error `E0401`. A `tainted string` is the
error `E0401` too, so check text from outside the program before you put it in a message.

`previous` takes a `Throwable` or `null`. Another type is the error `E0401`. Any other option, such as
`{cause: $e}`, is the error `E0454`, and its help lists `previous`.

With names, the arguments may come in any order:
`new RuntimeError(options: {previous: $e}, message: "…")`. A subclass that writes no constructor
accepts the names too.

A subclass with its own constructor must call `parent::constructor(...)` on every path. A path without
the call is the error `E0410`. `parent::constructor()` with no message is the error `E0402`.

A subclass may add properties with a default value, such as `public int $status = 500;`, without a
constructor of its own.

## Example 01: your own error class

```nvs
<?nvs
// Shows how to write an error class of your own. The class extends `Throwable`
// and writes no constructor, so it uses the one it inherits. You pass a message
// to `new` and nothing else.

class OutOfStock extends Throwable
{
}

final class Warehouse
{
    public static function pack(string $item, int $inStock): string
    {
        if ($inStock == 0) {
            throw new OutOfStock('no ' . $item . ' left');
        }
        return 'packed one ' . $item;
    }
}

try {
    // This prints `packed one blue mug`.
    echo Warehouse::pack('blue mug', 4), "\n";
    echo Warehouse::pack('red mug', 0), "\n";
} catch (OutOfStock $empty) {
    // `message` is the text you passed to `new`. This prints `no red mug left`.
    echo $empty->message, "\n";
}

// The message may also be passed by name.
try {
    throw new OutOfStock(message: 'the shelf is empty');
} catch (OutOfStock $shelf) {
    echo $shelf->message, "\n";
}
```

```output
packed one blue mug
no red mug left
the shelf is empty
```

```nvs
// Shows how one error names the error that caused it. A settings loader catches
// the error from the JSON reader and throws its own, with the first one kept as

class ConfigError extends RuntimeError
```

# `throw`

`throw` reports an error and stops the work in progress. It takes an object of a class under
`Throwable`, such as `LogicError`, `IOError`, or a class you wrote yourself. The nearest `catch`
clause whose class matches takes over, and the lines after the `throw` never run.

`throw new RuntimeError("the reason");` is the usual form. The message is the first argument, and a
class may add more. If no `catch` matches, the program ends with status 1.

`throw` is a statement, and it is also an expression. You can write it where a value is expected:
after `??` when a value may be missing, in the `default` arm of a `match`, and in a ternary
arm. In each of those places the program either has a value or throws, so
every line after it can use the value.

**The examples below** show `throw` after `??` for a missing field, in the `default` arm of a
`match` over order statuses, and in the checks a program runs before it ships an order. The last
one shows a method that throws for a value it cannot use, and a `catch` around the call.

`throw "x"`, `throw 5` and `throw new Foo()` for a class not under `Throwable` are each the error
`E0780`. A variable whose type is an interface is `E0780` too, even when the object in it extends
`RuntimeError`.

A `?LogicError` variable may be thrown. When it is `null`, the `throw` throws a `LogicError` with the
message `Can only throw objects`. A `mixed` variable may be thrown as well. When its value is not a
`Throwable`, the result is the same `LogicError`.

`throw` as a value can stand after `??` and `?:`, in a `match` arm, in either arm of a ternary, after
`||`, and after `echo`. Its type is `never`. At a typed
variable or a method argument, `int $x = throw …;` is the error `E0401`. In arithmetic such as
`1 + throw …`, the result is `mixed`.

A method whose return type is `int` may end with a `throw` and no `return`. A method may also have the
return type `never` and always throw.

`throw LogicError("x")` without `new` is the error `E0320`.

## Example 01: a value that may be missing

```nvs
<?nvs
// Shows `throw` written after `??`. The value on the left is used when it is
// there. When it is missing, the `throw` on the right stops the method with an
// error.

final class Rows
{
    public static function email(array<string> $row): string
    {
        // `??` gives the value stored under `"email"`. If the row has no such
        // key, `throw` raises a `LogicError` and the method returns nothing.
        return $row['email'] ?? throw new LogicError('the row has no email');
    }
}

array<string> $complete = ['id' => '7', 'email' => 'ada@example.com'];
array<string> $partial = ['id' => '8'];

// This prints ada@example.com.
echo Rows::email($complete), "\n";

try {
    echo Rows::email($partial), "\n";
} catch (LogicError $missing) {
    // This prints "the row has no email".
    echo $missing->message, "\n";
}
```

```output
the row has no email
```

## Example 02: a status the program does not know

```nvs
<?nvs
// Shows `throw` in a `match` arm. Every status the program knows has an arm of
// its own. An unknown status reaches the `default` arm, and that arm throws.

final class Orders
{
    public static function nextStep(string $status): string
    {
        return match ($status) {
            'paid' => 'pack the order',
            'packed' => 'print the label',

            default => throw new LogicError('unknown order status: ' . $status),

        string $step = Orders::nextStep($status);

    } catch (LogicError $unknown) {
```

# `try`, `catch`, `finally`

`try` guards a block of code that can throw. Write `try { … }`, then `catch` clauses, a `finally`
block, or both. Each `catch` clause names one class from the throwable tree.

A clause matches its own class and every class under it, so `catch (RuntimeError $e)` also takes an
`IOError`. The clauses are tried from top to bottom, so the narrow classes go first. You may leave
the variable out when you do not need the error itself.

`finally` runs on every way out of the block: after the body, after a `catch`, and on `return`,
`break`, `continue` or an error that nothing caught.

**The examples below** show two clauses picked by class, a `catch` that throws a new error with a
cause, and the clean-up around a job that reads rows. Then they show a loop that carries on after a
row that fails, two clauses with one variable name, which does not compile, and a `finally` that
runs on `continue`.

A `try` needs at least one `catch` clause or a `finally` block. A `try` with neither does not compile:
it is the error `E0242`.

A `catch` clause may name an interface. It then matches every class that implements that interface.

A clause for a parent class that is written before a clause for its subclass catches that error
first. The later clause never runs. This compiles without a warning.

`catch (LogicError | IOError $e)` does not compile: it is the error `E0245`. Write two clauses.

The variable of a `catch` clause is a variable of the whole function. Two clauses in one function may
use the same name when they catch the same type. When the types are different, the second clause does
not compile: that is the error `E0406`.

A `catch` clause may throw as well. The other clauses of the same `try` do not catch the new error.
The `finally` block of that `try` runs first, and then the next `try` outside handles the error. This
is how one layer reports an error of its own and keeps the caught one as its `previous`.

When one `try` is inside another, the inner `finally` block runs before the outer one.

A `return` inside a `finally` block does not compile: it is the error `E0250`. Change the result in
the `try` or in a `catch`, or after the whole block.

A `break` or `continue` that would leave a `finally` block does not compile: it is the error `E0251`.
This is also true for `break 2` from a loop inside the `finally`. A loop that is written completely
inside the `finally` block may use `break` and `continue`.

A `yield` inside a `finally` block does not compile: it is the error `E0255`. A generator cannot
pause there. Write the `yield` in the `try` block or after the whole block.

A `finally` block may contain its own `try` and `catch`. An error caught there does not leave the
block.

When the `try` returns a value, the value is computed first. The `finally` block runs after that, so
a change it makes does not change the value that the function returns.

When no `catch` handles an error, the `finally` blocks still run. Then the error leaves the function,
or ends the program at the top level.

A `finally` block can throw while an error is leaving the block. The handler outside then gets the
new error, and its `previous` is the first error. A method called in the `finally` that throws does
the same. If the new error already has a `previous`, it keeps that `previous`, and the first error is
lost.

# Rethrowing

`throw $e;` inside a `catch` sends the same error on to the next handler.

The object does not change. Its `message`, its `previous` and its class stay as they were. Only
`location` moves to the line of the rethrow, so a log line written later says where the error was
sent on. Rethrow when the code you are in has something to do first, such as closing a file or
counting a failure, and cannot handle the error itself.

**Good to know:** to add information of your own, do not rethrow. Throw a new error and give it the
caught one as its cause, with `{previous: $e}`. A handler further out then has both messages.

**The examples below** show a plain rethrow, a rethrow after a log line, and a retry that gives up
and sends the last error on.

`throw $e;` may also throw an error that was caught earlier and saved in a variable or a property.
Each throw moves `location` to the line of that `throw`. The object stays the same, so `==` with the
saved variable is `true`.

A clause that catches a wide class, such as `catch (Throwable $e)`, does not change the class of the
error. After `throw $e;`, a `catch (TimeoutError $t)` further out still catches a `TimeoutError`.

After a rethrow, `backtrace` still starts at the function that threw first. For the function that
rethrew, the line in `backtrace` is the line of `throw $e;`.

The `finally` block of the `try` that rethrows runs before the error leaves that `try`.

When nothing catches the rethrown error, it ends the program like any uncaught throw. The report on
the error output names the function that threw first.

## Example 01: send the same error on

```nvs
<?nvs
// Shows a plain rethrow. `throw $io;` inside the `catch` sends the same object
// on, so the handler further out reads the same message and the same class.

final class Relay
{
    public static function go(): void
    {
        try {
            throw new IOError('the socket closed');
        } catch (IOError $io) {
            echo "the relay saw it\n";
            throw $io;
        }
    }
}

try {
    Relay::go();
} catch (Throwable $sent) {
    echo $sent->message, "\n";
    // `location` is the line of the rethrow, which is line 13 here.
    echo 'sent on at ', $sent->location, "\n";
}
```

```output
the relay saw it
the socket closed
sent on at main.nvs:13
```

## Example 02: do something first

```nvs
<?nvs
// Shows the common reason to rethrow. This code counts the failure and writes a

    echo Uploads::send('photo.raw'), "\n";

    echo 'giving up: ', $failed->message, "\n";
```


## Example 03: a retry that gives up

```nvs
<?nvs
// Shows a retry. The call is tried three times. The first two errors are caught
// and the loop tries again. The third one is sent on, because there is nothing
// left to try.

final class Payments
{
    public static int $calls = 0;

    public static function charge(int $order): string
    {
        Payments::$calls = Payments::$calls + 1;
        throw new TimeoutError('the payment service did not answer');
    }

    public static function chargeWithRetries(int $order, int $tries): string
    {
        int $attempt = 1;
        while ($attempt <= $tries) {

                return Payments::charge($order);

                if ($attempt == $tries) {

                    throw $slow;
                }
            }
            $attempt = $attempt + 1;
        }
        return 'not reached';
    }
}

    echo Payments::chargeWithRetries(4021, 3), "\n";
} catch (TimeoutError $gaveUp) {
    echo 'gave up after ', Payments::$calls, ' calls: ', $gaveUp->message, "\n";
}
```

```output
attempt 2 timed out
attempt 3 timed out
gave up after 3 calls: the payment service did not answer
```

# An uncaught throw

A throw that no `catch` handles ends your program.

The program stops at the line that threw. Everything it printed before that line is still printed.
The exit status is 1. The error output gets a report with the error class, the message, and one line
for each function the throw passed through, innermost first.

There is no global handler that catches everything for you and lets the program carry on. Catch the
error where you can do something about it, or let it end the program.

Two methods let you watch this ending without changing it. `Core\Fatal::onUncaughtThrow` gives you
the error itself. `Core\Script::onExit` runs at every ending, normal or not. Both run before the
program exits, and the exit status is still 1.

**The examples below** show the plain ending first, then each of these two methods.

The report goes to the error output, and the normal output does not get it. By default the report is
one line of JSON. `msg` is the message, `fields.class` is the error class, and `nodes` has one entry
for each function with `function`, `file` and `line`. The last entry is `<script>`, the top level of
the file.

With `format = "text"` in the `[log]` table of `nvs.toml`, the report is text. The first line is
`[error]` and the message. The next line is the class. Then each function gets one line, such as
`#0 Repo::get() at main.nvs:4`.

The report has the class of your own error, such as `BadInput`, when you throw one.

The report does not have the error in `previous`. To see the cause, catch the error and print
`$e->previous?->message` yourself.

Before the program ends, every `finally` block that the error leaves still runs. What it prints
stays in the normal output.

The exit status is 1 for every uncaught throw.

## Example 01: the program stops here

```nvs exit=1
<?nvs
// Shows what happens when no `catch` handles a throw. The program ends at
// the line that threw, with exit status 1.
// proof: exit 1

class Repo
{
    public static function get(int $id): string
    {
        throw new RuntimeError('no row ' . $id);
    }
}

// This prints. Everything printed before the throw stays printed.
echo "loading order 7\n";

// Nothing catches this error, so the program ends here. The error output gets
// the class `RuntimeError`, the message, and one line for each function.
echo Repo::get(7), "\n";

// This line never runs.
echo "done\n";
```

```output
loading order 7
```

## Example 02: print your own message

```nvs exit=1
<?nvs

{
    public static function row(string $line): string
    {
        if (Core\Str::length($line) == 0) {
            throw new RuntimeError('an empty line is not a row');
        }
        return $line;
    }
}

// The second row is empty, so this throw ends the program. The anonymous function above
```


# Recursion depth

A function that calls itself without ever returning is stopped. When the call stack grows past the
depth Novis allows, the innermost call throws a `RecursionError`. The limit is on the size of the
stack rather than on a number of calls, so how deep you can go depends on what each call holds. A
small function reaches a few thousand calls.

A `RecursionError` is a kind of `RuntimeError`, so `catch (RecursionError $e)` and
`catch (RuntimeError $e)` both handle it, and the program carries on. The frames are already gone
when the handler runs, so the handler has the whole stack available again and may keep working.
Uncaught, a `RecursionError` ends the program like any other error.

This is what makes a recursive walk over data you did not write safe. Input nested far deeper than
you expected, or a cycle in a table you follow, gives you an error you can report instead of a
crash.

**The examples below** show a runaway recursion caught, a walk a thousand calls deep that finishes,
and a redirect chain that loops back on itself.

The message of the error is `the call stack is too deep`. `$e is RuntimeError` is `true`.

A function with a few parameters and locals reaches fewer calls than a function with one. The exact
number can change between versions of Novis, so do not write code that needs it.

A `catch` in any of the calls handles the error. The calls inside it are gone, and the calls outside
it go on as usual. The program may call the deep function again after a `catch`, and it throws a
`RecursionError` again.

`finally` blocks in each call run while the error leaves the calls.

`backtrace` has one entry for each call, so a `RecursionError` has a few thousand entries. An
uncaught one prints all of them in the report.

You may throw a `RecursionError` yourself with `new RecursionError("…")`.

## Example 01: catching a runaway recursion

```nvs
<?nvs
// Shows a function that calls itself with no way out. The runtime stops it at
// the depth limit with a `RecursionError`, the `catch` handles it, and the
// program carries on.

final class Down
{
    public static function forever(int $n): int
    {
        return Down::forever($n + 1) + 1;
    }
}

try {
    echo Down::forever(0), "\n";
} catch (RecursionError $tooDeep) {
    // This prints "stopped: the call stack is too deep".
    echo 'stopped: ', $tooDeep->message, "\n";
}

echo "the program carries on\n";
```

```output
stopped: the call stack is too deep
the program carries on
```

## Example 02: a deep walk that finishes

```nvs
<?nvs
// Shows how much room recursion has. This function calls itself a thousand
// times before it returns, which stays inside the limit, so it finishes and
// prints its result.

final class Sum
{
    public static function upTo(int $n): int
    {
        if ($n == 0) {
            return 0;
        }
        return $n + Sum::upTo($n - 1);
    }
}

// This prints 500500.
echo Sum::upTo(1000), "\n";
```

```output
500500
```

## Example 03: a redirect chain that loops

```nvs
<?nvs
// Shows a recursive walk over a table somebody else filled in. Two entries that
// point at each other make the walk endless, and the depth limit turns that
// into an error you can report.

final class Links
{
    public static function follow(array<string> $targets, string $from): string
    {
        string $next = $targets[$from] ?? '';
        if ($next == '') {
            return $from;
        }
        return Links::follow($targets, $next);
    }
}

array<string> $plain = ['/old' => '/new', '/new' => '/home'];
array<string> $loop = ['/a' => '/b', '/b' => '/a'];

// This prints /home.
echo Links::follow($plain, '/old'), "\n";

try {
    echo Links::follow($loop, '/a'), "\n";
} catch (RecursionError $endless) {
    echo "the redirect chain does not end\n";
}
```

```output
/home
the redirect chain does not end
```

## Example 04: a catch in the middle of the calls

```nvs
<?nvs
// Shows a `catch` in one of the calls of a deep recursion. The calls inside it
// are gone. The calls outside it go on and return a value.

final class Down
{
    public static int $caughtAt = -1;

    public static function count(int $depth): int
    {
        int $next = $depth + 1;
        if ($depth == 100) {
            try {
                return Down::count($next);
            } catch (RecursionError $tooDeep) {
                Down::$caughtAt = $depth;
                return 0;
            }
        }
        return Down::count($next) + 1;
    }
}

// The call at depth 100 returns 0, and each of the 100 calls outside it adds 1.
// This prints "100 calls returned, caught at depth 100".
echo Down::count(0), ' calls returned, caught at depth ', Down::$caughtAt, "\n";
```

```output
100 calls returned, caught at depth 100
```

# Fatal errors: limits no `catch` sees

A resource limit stops your program at once, and no `catch` sees it.

`nvs.toml` sets four limits for a program: `memory`, `cpu_time`, `wall_time` and `max_output`. A
program that goes past one of them is stopped where it stands. This is a `FATAL`. It is not a
`Throwable`, so no `catch` clause matches it and no `finally` runs. The program writes a line starting
with `FATAL:` to standard error and ends with status 1.

One hook runs before that end. `Core\Fatal::onLimit` registers a function that runs once when a limit
stops the program, and it is told which limit fired. Use it to write a last note about what the
program was doing. Registering a second function replaces the first. The program still ends after the
handler.

**The examples below** show a limit that no `catch` and no `finally` sees, and a handler that names
the limit that fired. The third is a job that records the order it stopped on.

The `FATAL:` line on standard error names the limit and the numbers. For `memory` it gives the bytes
the program held, the limit, and the part of the limit kept for the handler. With `memory = "16M"`,
1 megabyte is kept for the handler, so the program itself can use 15 megabytes. When `nvs.toml` sets
no `memory` limit, the limit is `128M`.

The handler receives an array with one key, `limit`. Its value is the name of the limit as
`nvs.toml` writes it: `memory`, `cpu_time`, `wall_time` or `max_output`. The handler may also declare
no parameter. A handler with a parameter of another type, such as `fn (int $x): void`, is the error
`E0401`.

`Core\Fatal::onLimit` keeps one handler. A second call replaces the first, so only the last handler
runs.

The handler runs once. If it throws an error, the error is not shown, and the program still writes
the `FATAL:` line and ends with status 1. After the `max_output` limit, what the handler prints with
`echo` still reaches standard output.

Two more errors end the program in the same way: `send` on a closed `Core\Task\Channel`, and
`new Core\Task\Channel<int>(0)`. Each writes a `FATAL:` line that names the method, and the program
ends with status 1. No `catch` and no `finally` runs. The `onLimit` handler does not run either,
because no limit fired.

## Example 01: no catch sees a limit

```toml file=nvs.toml
# Each example in this folder may use at most 16 megabytes of memory.
[limits]
memory = "16M"
```

```nvs exit=1
<?nvs
// Shows what a memory limit does to a program. `nvs.toml` gives this program
// 16 megabytes. Holding more than that stops it where it stands. No `catch`
// and no `finally` runs, and the program ends with status 1.
// proof: exit 1

echo "before the limit\n";

try {
    array<string> $ballast = [];
    int $slab = 0;
    while ($slab < 4) {
        $ballast[] = Core\Str::repeat('x', 8388608);
        $slab = $slab + 1;
    }
    echo "not reached\n";
} catch (Throwable $never) {
    // A limit is not a throw, so no class matches it. `Throwable` is the widest
    // clause there is, and it does not run either.
    echo "not reached: the catch ran\n";
} finally {
    echo "not reached: the finally ran\n";
}

echo "not reached: the program went on\n";
```

```output
before the limit
```

## Example 02: a handler for the last moment

```toml file=nvs.toml
# Each example in this folder may use at most 16 megabytes of memory.
[limits]
memory = "16M"
```

```nvs exit=1
<?nvs
// Shows the one hook a limit runs. `Core\Fatal::onLimit` registers a function
// that runs when a limit stops the program. The function receives the name of
// the limit that fired. The program still ends after it.
// proof: exit 1

Core\Fatal::onLimit(fn (array<string> $report): void => {
    echo 'stopped by the ', $report['limit'], " limit\n";
});

echo "working\n";

array<string> $ballast = [];
int $slab = 0;
while ($slab < 4) {
    $ballast[] = Core\Str::repeat('x', 8388608);
    $slab = $slab + 1;
}

echo "not reached\n";
```

```output
working
stopped by the memory limit
```

## Example 03: a job that says where it stopped

```toml file=nvs.toml
# Each example in this folder may use at most 16 megabytes of memory.
[limits]
memory = "16M"
```

```nvs exit=1
<?nvs
// Shows how to leave a note when a limit stops a job. The handler prints the
// order the job was on, so the person reading the log can start again from
// there.
// proof: exit 1

final class Job
{
    // The handler reads this. An anonymous function copies the variables it
    // captures when it is written, so a variable would still have its first value here.
    public static string $current = 'none';
}

Core\Fatal::onLimit(fn (array<string> $report): void => {
    echo 'stopped on order ', Job::$current, ', limit: ', $report['limit'], "\n";
});

array<string> $orders = ['A-1001', 'A-1002', 'A-1003', 'A-1004'];
array<string> $labels = [];

foreach ($orders as string $order) {
    Job::$current = $order;
    echo 'packing ', $order, "\n";
    $labels[] = Core\Str::repeat('x', 8388608);
}

echo "not reached\n";
```

```output
packing A-1001
packing A-1002
stopped on order A-1002, limit: memory
```

# Capability denials are catchable

A call your program is not allowed to make throws a `RuntimeError`.

Reading a file, writing a file and starting another script each need a capability. A capability is
permission to do one kind of thing. The person who runs the server grants it in `nvs.toml`. A
program you start from the command line may read and write any file. A server program may read its
application folder and write only its own temporary folders.

A call without the grant throws before it does any work. The message names the method, the capability
it needed and the path it was given. A `help:` line under it says where to write the grant. This is an
ordinary throw, so `catch (RuntimeError $denied)` takes it and the program keeps running.

Your program can use that. Try the call, catch the error, and do the work another way if it is not
allowed.

**The examples below** show a call nobody allowed, and a grant that lets one call through while a
second call is still denied. The third is a program that finishes its work without the capability.

The message has two lines. The first is ``Core\IO::read needs the capability `fs.read` for <path>,
which is not granted``, with the full path of the file. The second is the line to add to `nvs.toml`:
``help: add `read = ["<folder>"]` under `[capabilities.fs]` in nvs.toml``. `<folder>` is the
full path of the folder that contains the file.

`fs.read` covers every call that looks at a file, such as `Core\IO::exists`, and not only
`Core\IO::read`. `fs.write` is a separate capability. A grant of `read` for a folder does not let your
program write there.

A grant lists folders. Novis resolves each path to its real full path before it checks it. A `..` that
leads out of a granted folder is denied, and so is a symbolic link that points out of one. A path
with `..` that ends inside a granted folder is allowed.

A file that does not exist inside a granted folder is not a denial. The call throws `IOError`, a
subclass of `RuntimeError`, with the operating system's message. A path that does not exist outside
every granted folder is denied like any other path.

`spawn script "job.nvs"` needs `script.spawn`. Its message starts with ``spawn script` needs the
capability `script.spawn` ``, and the `help:` line names `[capabilities.script]`.

## Example 01: a call nobody allowed

```toml file=nvs.toml
# Example 01 may not read any file.
[[app]]
entry = "main.nvs"

[app.capabilities.fs]
read = []
```

```nvs
<?nvs
// Shows what a program sees when it reads a file and `nvs.toml` does not allow
// it. The call throws a `RuntimeError`. The `catch` takes it, and the program
// keeps running.

try {
    echo Core\IO::read('orders.csv');
} catch (RuntimeError $denied) {
    // The message names the method, the capability and the full path of the file.
    // This prints the part before the path.
    echo Core\Str::before($denied->message, ' for '), "\n";
    // The second line of the message is the line to add to `nvs.toml`.
    // It also contains the full path of the folder. This prints `...` in its place.
    string $help = Core\Str::after($denied->message, "\n") ?? '';
    echo Core\Str::before($help, "\""), '...]', Core\Str::after($help, "\"]"), "\n";
}

echo "still running\n";
```

```output
Core\IO::read needs the capability `fs.read`
help: add `read = [...]` under `[capabilities.fs]` in nvs.toml
still running
```

## Example 02: a grant in nvs toml

```text file=data/notice.txt
The shop closes at 18:00.
```

```toml file=nvs.toml
# Example 02 may read the files in the `data` folder. It may not write any file.
[[app]]
entry = "main.nvs"

[app.capabilities.fs]
read = ["data"]
write = []
```

```nvs
<?nvs
// Shows a program with one capability and not the other. `nvs.toml` grants
// `fs.read` for one directory, so reading a file there works. Writing a file
// needs `fs.write`, and this program does not have it.

echo Core\Str::trim(Core\IO::read('data/notice.txt')), "\n";

try {
    Core\IO::write('data/notice.txt', 'The shop is open all night.');
} catch (RuntimeError $denied) {
    // The message names the full path of the file. This prints the part before it.
    echo Core\Str::before($denied->message, ' for '), "\n";
}
```

```output
The shop closes at 18:00.
Core\IO::write needs the capability `fs.write`
```

## Example 03: a report when the disk is closed

```toml file=nvs.toml

[[app]]
entry = "main.nvs"

[app.capabilities.fs]
write = []
```

```nvs

// to a file. Writing is not allowed here, so it prints the report instead.
```

```output
orders: 3, total: 41.50
```

# Assertion failures

An assertion that fails throws `Core\Test\Failure`.

Every `Core\Test::assert…` method either returns and lets your code carry on, or throws. The message
names the method that failed and the values it compared, so you can read what went wrong without
opening the file again. The `message` option puts your own sentence in front of that text.

`Core\Test\Failure` is not a `RuntimeError`. It sits directly under `Throwable`, so a `catch
(RuntimeError $e)` in the code you are testing never catches it by accident. A `catch (Throwable $e)`
does catch it.

Inside a `#[Test]` method the test runner catches the failure and reports that test as failed.
Outside one it is an ordinary throw: catch it, or it ends your program.

**The examples below** show the message, the `catch` arm that takes it, and a check outside a test.

`$failure is RuntimeError` and `$failure is LogicError` are both `false`. Only a `catch` for
`Core\Test\Failure` or for `Throwable` takes a failed assertion.

An assertion that passes returns nothing and prints nothing.

You can create a failure yourself with `new Core\Test\Failure("…")`. Your own class cannot extend it.

A failure that nothing catches ends the program with status 1, like any uncaught error. The report on
standard error has the class `Core\Test\Failure` and the message.

## Example 01: what a failure says

```nvs
<?nvs
// Shows what a failed assertion throws, and what its message says.

// Every `Core\Test::assert...` method throws `Core\Test\Failure` when it fails.
try {
    Core\Test::assertEquals(41, 42);
} catch (Core\Test\Failure $failure) {
    // The message names the method and both values it compared.
    echo $failure->message, "\n";
}

// The `message` option puts your own sentence in front of that text.
try {
    Core\Test::assertTrue(false, { message: 'the flag should be set' });
} catch (Core\Test\Failure $failure) {
    echo $failure->message, "\n";
}

// `location` is the file and the line of the assertion that failed.
try {
    Core\Test::assertCount(['order', 'customer'], 3);
} catch (Core\Test\Failure $failure) {
    echo $failure->message, "\n";
    echo 'raised at ', $failure->location, "\n";
}
```

```output
Core\Test::assertEquals failed: `$actual` is 41, `$expected` is 42
the flag should be set: Core\Test::assertTrue failed: `$actual` is false
Core\Test::assertCount failed: `$actual` holds 2 entries, `$expected` is 3
raised at main.nvs:21
```

## Example 02: only a throwable arm catches it

```nvs
<?nvs
// Shows which `catch` arm takes a failed assertion. `Core\Test\Failure` is not
// a `RuntimeError`.

class Cart
{
    public static function total(array<int> $prices): int
    {
        int $sum = 0;
        foreach ($prices as int $price) {
            $sum = $sum + $price;
        }
        return $sum;
    }
}

// The `RuntimeError` arm does not match a failure. The `Throwable` arm is the
// one that runs.
try {
    Core\Test::assertEquals(Cart::total([100, 250]), 999);
} catch (RuntimeError $error) {
    echo "the RuntimeError arm caught it\n";
} catch (Throwable $failure) {
    echo "the Throwable arm caught it\n";
    echo $failure->message, "\n";
}
```

```output
the Throwable arm caught it
Core\Test::assertEquals failed: `$actual` is 350, `$expected` is 999
```

## Example 03: a check that ends the script

```nvs exit=1
<?nvs
// Shows a check outside a test. Nothing catches the failure, so the program
// ends with exit status 1.
// proof: exit 1

array<string> $config = ['host' => 'localhost', 'port' => '5432'];

echo "checking the configuration\n";

// This assertion passes, so the program carries on.
Core\Test::assertCount($config, 2);

// This one fails. Outside a `#[Test]` method a failure is an ordinary throw,
// so it ends the program here and the error output gets the message.
Core\Test::assertTrue(
    Core\Arr::hasKey($config, 'password'),
    { message: 'the password is missing' },
);

echo "this line never runs\n";
```

```output
checking the configuration
```

# Inspecting a value

Two members show you what a value really is while you are working on a program. `Core\Debug::dump`
writes one rendering per argument to standard error. `Core\Debug::render` builds the same rendering
and returns it as a `Core\Cli\Text` value. You can print it or put it in a log line.

A rendering names the type of every value, the length of every string and the class of every object.
Control bytes such as a tab are made visible, a structure that is very deep or very long is cut
short, a value that points back at itself is marked, and a property declared `secret` is shown as
`[redacted]`.

`dump` never writes to standard output, and a captured buffer never swallows it. What your program
prints stays exactly what it printed, so a `dump` you forget to remove cannot change a response.

**The examples below** show a rendering printed, a `dump` beside a program's own output, and a
password that stays hidden.

`Core\Debug::render` returns a `Core\Cli\Text`, not a `string`. `echo` prints it. Call `->text()` to
get the `string`, for example to compare it: `Core\Debug::render(1)->text() == "int(1)"` is `true`.
Two `Core\Cli\Text` values are objects, so `==` on them compares the objects, not the text.

Each value shows its type. `null` is `null`, and a number is `int(1)`, `uint(3)`, `float(1.5)` or
`decimal(2.50)`. An enum case shows its number, such as `int(1)`. A function shows the number of its
parameters, such as `callable(1 parameter)`. A string shows its length in bytes, so `"café"` is
`string(5)`.

A newline is shown as `\n` and a tab as `\t`. Other control bytes and the characters that change the
direction of text are shown as visible symbols.

An array shows its first 100 entries, then `[elided: 200 of 300 entries]` for the rest. A string over
1024 bytes shows its first 1024 bytes, as `string(1024+) "…" [elided: 3976 bytes]`. A structure shows
eight levels, and a deeper value is `[elided: below the depth cap]`. An object that was already shown
higher up is `[cycle -> #1]`, with the number of that object.

`Core\Debug::dump()` with no value writes nothing. Output from `dump` inside `Core\Out::capture` is
not captured. It still goes to standard error.

A `secret` property is shown as `[redacted]`. A `secret` variable cannot be passed to `dump` or
`render` at all: that is the error `E0724`.

Inside a web request, `dump` writes a log record at the `Debug` level. In production, that record is
kept only when `[log] level` is `"Debug"`.

## Example 01: seeing what a value is

```nvs
<?nvs
// Shows `Core\Debug::render`. It returns the rendering of a value as text, so
// this program prints it. Every value says what type it is, and a string says
// how many bytes it has.

final class Order
{
    public function constructor(public int $id, public string $customer)
    {
    }
}

echo Core\Debug::render(new Order(1042, 'Ada')), "\n";

// A tab inside a string is shown as `\t`, so you can see it.
echo Core\Debug::render(['paid' => true, 'note' => "two\tcolumns"]), "\n";
```

```output
Order#1 (2) {
  $id => int(1042)
  $customer => string(3) "Ada"
}
array(2) [
  "paid" => bool(true)
  "note" => string(11) "two\tcolumns"
]
```

## Example 02: a dump beside your own output

```nvs
<?nvs
// Shows `Core\Debug::dump`. It writes to standard error, so it appears in your
// terminal while the program's own output stays unchanged. The lines below are
// the output; the two renderings arrive on standard error.

final class Basket
{
    public function constructor(public int $items, public int $cents)
    {
    }
}

var $basket = new Basket(3, 4599);

Core\Debug::dump($basket);

// One call takes several values and renders each of them.
Core\Debug::dump($basket->items, $basket->cents, 'still here');

echo 'total: ', $basket->cents, " cents\n";
echo 'items: ', $basket->items, "\n";
```

```output
total: 4599 cents
items: 3
```

## Example 03: a password that stays hidden

```nvs
<?nvs
// Shows what happens to a password in a rendering. A property declared `secret`
// is printed as `[redacted]`. You can inspect a configuration object without
// putting its password in your terminal or your log file.

final class DbConfig
{
    public function constructor(
        public string $host,
        public string $user,
        public secret string $password,
    )
    {
    }
}

var $config = new DbConfig('db.internal', 'orders', 'hunter2');

// The host and the user are shown. The password is not.
echo Core\Debug::render($config), "\n";
```

```output
DbConfig#1 (3) {
  $host => string(11) "db.internal"
  $user => string(6) "orders"
  $password => [redacted]
}
```
