# A test is a method marked `#[Test]`

A test is a method with `#[Test]` written above it.

Any class in your program may have tests. There is no base class to extend, and no name a test
class or a test method has to have. You write `use Core\Test;` once, put `#[Test]` above a method,
and run `nvs test yourfile.nvs`. The compiler collects every `#[Test]` method while it checks your
program.

A test method is `public`, is not `static`, and returns `void`. A method that breaks one of those
three rules does not compile. A test that checks nothing fails, so every test calls at least one
assertion.

**Good to know:** `nvs run` on the same file runs your program and runs no test.

`#[Test]` and `#[Core\Test]` are the same attribute. `use Core\Test;` makes the short name work for the
attribute and for the assertions, such as `Test::assertSame`.

A `#[Test]` method that is `static`, `private` or `protected`, or that returns a value, is `E0733`.
The message names the rule the method breaks.

A test method may declare parameters. A fixture or a data row fills each one. A parameter that
nothing fills is `E0736`.

The report lists the classes in name order. Inside a class, the tests run in the order they are
written. Each test line starts with a mark: `✓` passed, `✗` failed, `-` skipped and `!` flaky.

A test that calls no assertion fails with the message `it asserted nothing`. To test that a call
finishes without an error, write `Core\Test::assertDoesNotThrow`.

A test that throws an error fails, and the error's message is printed under the test.

What a test prints with `echo` is not shown when the test passes. When the test fails, its output
is printed under the failure, after `output:`. `nvs test --show-output` prints the output of every
test.

A `#[Test]` method in an `abstract` class runs only in each class that extends it. A `#[Test]` on a
method of an interface does nothing.

A file with no `#[Test]` method runs no test. The summary is `0 failed, 0 passed, 0 skipped, 0
flaky`, and the exit status is `0`.

`nvs run` on a file with tests runs the statements outside the classes and runs no test.

## Example 01: a test beside the code it checks

```nvs
<?nvs
// Shows how to write a test. `#[Test]` above a method makes that method a
// test. `nvs test` on this file runs every `#[Test]` method it finds.

use Core\Test;

class Slug
{
    public static function of(string $title): string
    {
        return Core\Str::replace(Core\Str::lower($title), ' ', '-');
    }
}

class SlugTest
{
    #[Test]
    public function spacesBecomeDashes(): void
    {
        Test::assertSame(Slug::of('Hello World'), 'hello-world');
    }

    #[Test]
    public function capitalsBecomeSmallLetters(): void
    {
        Test::assertSame(Slug::of('ORDER Form'), 'order-form');
    }
}

// `nvs run` runs the program and leaves the tests alone.
// This prints `hello-world`.
echo Slug::of('Hello World'), "\n";
```

```output
hello-world
```

## Example 03: one marked method for each rule

```nvs
<?nvs
// Shows a test class written the way you would write one at work. Every rule
// gets its own `#[Test]` method, and the name of the method says what the rule
// is. A method without `#[Test]` is an ordinary method.

use Core\Test;

class PasswordPolicy
{
    public static function problem(string $password): string
    {
        if (Core\Str::length($password) < 12) {
            return 'too short';
        }
        if (Core\Str::lower($password) == $password) {
            return 'needs a capital letter';
        }
        return 'none';
    }
}

class PasswordPolicyTest
{
    #[Test]
    public function aShortPasswordIsRefused(): void
    {
        Test::assertSame($this->problemFor('Short1'), 'too short');
    }

    #[Test]
    public function aPasswordWithoutCapitalsIsRefused(): void
    {
        Test::assertSame($this->problemFor('correcthorsebattery'), 'needs a capital letter');
    }

    #[Test]
    public function aLongPasswordWithACapitalLetterPasses(): void
    {
        Test::assertSame($this->problemFor('CorrectHorseBattery'), 'none');
    }

    // This method has no `#[Test]`, so `nvs test` does not run it. The tests
    // above call it like any other method.
    private function problemFor(string $password): string
    {
        return PasswordPolicy::problem($password);
    }
}

// This prints `too short` and then `none`.
echo PasswordPolicy::problem('Short1'), "\n";
echo PasswordPolicy::problem('CorrectHorseBattery'), "\n";
```

```output
too short
none
```

# Every test is its own isolate, and the constructor is `setUp`

Every test runs on its own, and shares no stored value with any other test.

A `static` value that one test writes is back at its declared starting value in the next test. The
test class is built again for every test, so a property one test changes starts fresh in the next
one. The constructor of a test class is where you prepare what a test needs. It runs once before
every test body.

A test class constructor takes no parameters. One that takes a parameter is reported as that test
failing. Values that a test method itself needs come from a fixture or from a data row.

**The examples below** show a `static` that starts fresh in each test, a constructor that prepares
the same starting point for every test, and two tests that register the same address.

Each row of a `#[TestWith]` test runs on its own too. A `static` value one row writes is back at
its declared value in the next row.

The attempts of one test share their `static` values. With `retries:`, a counter that the first
attempt raised still has that value in the second attempt.

A constructor that throws an error makes the test fail, with the error's message.

A fixture is built outside the tests. A `static` value that a fixture method writes is back at its
declared value in every test.

A test that starts a script with `spawn script` and does not `await` it fails. The message says the
test left a task still running. `Core\Task::all` and `Core\Task::map` wait for every task they start,
so a test that uses them does not fail this way.

## Example 01: a static starts fresh in each test

```nvs
<?nvs
// Shows that one test cannot change what another test sees. A `static` value
// written by one test is back at its declared value in the next test.

use Core\Test;

class Counter
{
    public static int $hits = 0;
}

class CounterTest
{
    #[Test]
    public function theFirstTestWrites(): void
    {
        Counter::$hits = Counter::$hits + 1;
        Test::assertSame(Counter::$hits, 1);
    }

    #[Test]
    public function theSecondTestStartsFresh(): void
    {
        // The test above added one. This test reads `0` again.
        Test::assertSame(Counter::$hits, 0);
    }
}

// Outside a test there is one counter for the whole program, so it keeps both
// of these. This prints `2`.
Counter::$hits = Counter::$hits + 1;
Counter::$hits = Counter::$hits + 1;
echo Counter::$hits, "\n";
```

```output
2
```

## Example 02: the constructor prepares each test

```nvs
<?nvs
// Shows the constructor of a test class. It runs once before every test, so
// every test starts from the same prepared state.

use Core\Test;

class Basket
{
    public array<string> $items;

    public function constructor()
    {
        $this->items = [];
    }

    public function add(string $item): void
    {
        $this->items[] = $item;
    }
}

class BasketTest
{
    private Basket $basket;

    // This runs again before each test below, so each test gets a new basket.
    public function constructor()
    {
        $this->basket = new Basket();
        $this->basket->add('bread');
    }

    #[Test]
    public function itStartsWithThePreparedItem(): void
    {
        Test::assertCount($this->basket->items, 1);
    }

    #[Test]
    public function itAddsToThePreparedItem(): void
    {
        // The item this test adds is gone before the next test starts.
        $this->basket->add('milk');
        Test::assertCount($this->basket->items, 2);
    }
}

// This prints `2`.
var $basket = new Basket();
$basket->add('bread');
$basket->add('milk');
echo Core\Arr::count($basket->items), "\n";
```

```output
2
```

## Example 03: two tests that register the same address

```nvs
<?nvs
// Shows why this matters at work. Two tests register the same address, and
// both expect one account, because neither test sees the other's account.

use Core\Test;

class Registry
{
    public static array<string> $accounts = [];

    public static function register(string $email): void
    {
        Registry::$accounts[] = $email;
    }

    public static function count(): uint
    {
        return Core\Arr::count(Registry::$accounts);
    }
}

class RegistryTest
{
    #[Test]
    public function itRegistersAnAddress(): void
    {
        Registry::register('ada@example.com');
        Test::assertSame(Registry::count(), 1);
    }

    // The same address again. This test starts with an empty registry, so it
    // needs no code to remove what the test above registered.
    #[Test]
    public function itRegistersTheSameAddressAgain(): void
    {
        Registry::register('ada@example.com');
        Test::assertSame(Registry::count(), 1);
    }
}

// Outside a test the registry keeps both addresses. This prints `2`.
Registry::register('ada@example.com');
Registry::register('grace@example.com');
echo Registry::count(), "\n";
```

```output
2
```

# `#[Test(...)]` options

`#[Test(...)]` takes options that change how one test runs. Every option is optional, and a test that
needs none is written as plain `#[Test]`.

`skip:` states a reason, and the test is reported as skipped without being run. `at:` fixes the clock
at one instant, so a test of dates and times reads the same time on every run. `Core\Test::advance`
moves that fixed clock forward. `seed:` fixes the numbers `Core\Random` draws, so the test draws the
same sequence on every run. `retries:` allows more attempts after a failure, and needs `because:`
beside it to state why. A test that fails and then passes is reported as flaky, never as passed.
`timeout:` gives one test its own time limit. `tags:` labels a test, and `nvs test --tag` runs only the
tests with that label.

**Good to know:** an option with a wrong name does not compile, so a typo is found before the tests
run.

**The examples below** show a skipped test, a fixed clock, a test class that uses several options
together, a time limit, and tags.

The options are `skip: string`, `at: string`, `seed: int`, `retries: int`, `because: string`,
`db: string`, `server: bool`, `timeout: string` and `tags: array<string>`. An option with another name is `E0454`, and its help lists them. A
value of the wrong type is `E0401`, so `skip: true` does not compile. An option given twice is
`E0304`.

A skipped test is not built, so its constructor does not run. The fixtures only it needs are not
built either. The report prints the reason after `skipped:`.

`at:` takes a time in the RFC 3339 format, such as `"2026-01-01T00:00:00Z"`. `Core\Time::now()`
returns that time in the test. A text in another format compiles, and the test fails with a message
that shows the format.

`Core\Test::advance` moves the fixed clock forward by a duration, such as `90m`. In a test without
`at:`, it throws a `LogicError`. It throws the same error under `nvs run`. The clock of the computer
never moves.

With `seed:`, `Core\Random` and `Core\Uuid::v7` give the same values on every run. Two tests with the
same seed get the same values. A test without `seed:` gets different values on every run.

`retries:` without `because:` is `E0734`. `because:` alone compiles and changes nothing.

A test that fails and then passes is reported as flaky. The mark is `!`, and the report prints the
message of the failed attempt. A test that fails every attempt is reported as failed, with the
message of the last attempt.

`db: "main"` opens a transaction on the database connection `[db.main]` before the test, and
rolls it back after the test. The test sees the database as it was, and leaves no change in it. If no
`[db.main]` block is configured, the test fails with a message that says so.

`server: true` starts a real HTTP server for the test, on a free port of the local computer.
`Core\Test::serverUrl()` returns its address. In a test without `server: true`, it returns `null`.

## Example 01: skip a test and say why

```nvs
<?nvs
// Shows how to skip a test and say why. `skip:` needs a reason. The runner
// reports the test as skipped and does not run its body.

use Core\Test;

class Coupon
{
    public static function percentFor(string $code): uint
    {
        if ($code == 'SPRING24') {
            return 15;
        }
        return 0;
    }
}

class CouponTest
{
    #[Test]
    public function itGivesFifteenPercentForTheSpringCode(): void
    {
        Test::assertSame(Coupon::percentFor('SPRING24'), 15);
    }

    // The reason is part of the report, so anybody reading a run sees why
    // this test did not run.
    #[Test(skip: 'the refund table is not written yet')]
    public function itGivesNothingOnARefundedOrder(): void
    {
        Test::assertSame(Coupon::percentFor('SPRING24'), 0);
    }
}

// This prints `15 0`.
echo Coupon::percentFor('SPRING24'), ' ', Coupon::percentFor('AUTUMN24'), "\n";
```

## Example 02: a fixed clock for one test

```nvs
<?nvs
// Shows how to fix the time a test reads. `at:` sets the clock at one instant
// for that test. `Core\Test::advance` then moves the clock forward.

use Core\Test;
use Core\Time;

class Receipt
{
    public static function stampedAt(string $iso): string
    {
        return 'receipt at ' . $iso;
    }
}

class ReceiptTest
{
    // The clock stands still at this instant, for this test only.
    #[Test(at: '2026-01-01T00:00:00Z')]
    public function itStampsTheTimeTheClockShows(): void
    {
        string $first = Receipt::stampedAt(Time::now()->toIso());
        Test::assertSame($first, 'receipt at 2026-01-01T00:00:00Z');

        // This moves the fixed clock forward by 90 minutes.
        Test::advance(90m);

        string $later = Receipt::stampedAt(Time::now()->toIso());
        Test::assertSame($later, 'receipt at 2026-01-01T01:30:00Z');
    }
}

// This prints `receipt at 2026-01-01T00:00:00Z`, the text the test checks first.
echo Receipt::stampedAt('2026-01-01T00:00:00Z'), "\n";
```

```output
receipt at 2026-01-01T00:00:00Z
```

## Example 03: options in a real test class

```nvs
<?nvs
// Shows the options a real test class uses: a fixed clock, a fixed seed, an
// allowance of extra attempts with the reason for it, and a skip.

use Core\Random;
use Core\Test;
use Core\Time;

class Invite
{
    public static function code(string $draw): string
    {
        return 'INV-' . $draw;
    }

    public static function isWellFormed(string $code): bool
    {
        return Core\Str::length($code) == 8;
    }
}

class InviteTest
{
    // With `at:` this test reads the same time on every run.
    #[Test(at: '2026-03-01T09:00:00Z')]
    public function itReadsOneFixedTime(): void
    {
        Test::assertSame(Time::now()->toIso(), '2026-03-01T09:00:00Z');
    }

    // With `seed:` `Core\Random` draws the same numbers on every run.
    #[Test(seed: 42)]
    public function itBuildsACodeFromADrawnNumber(): void
    {
        int $draw = Random::int(1000, 9999);
        Test::assertTrue(Invite::isWellFormed(Invite::code($draw as string)));
    }

    // The payment sandbox fails now and then, so this test gets two more
    // attempts. `because:` is what a reader of the report has instead of the run.
    #[Test(retries: 2, because: 'the payment sandbox is slow to start')]
    public function itAcceptsACodeTheSandboxReturns(): void
    {
        Test::assertTrue(Invite::isWellFormed('INV-1234'));
    }

    // This test waits for work that is not done. It is reported as skipped.
    #[Test(skip: 'the refund endpoint is not built yet')]
    public function itRefundsAnInvite(): void
    {
        Test::assertTrue(Invite::isWellFormed('INV-0000'));
    }
}

// This prints `INV-1234`.
echo Invite::code('1234'), "\n";
```

```output
INV-1234
```

```nvs test
// attempt. The report shows `!` for that test, because it is flaky.

use Core\Random;
use Core\Test;
use Core\Time;

final class DeterminismTest
{
    // `Core\Test::advance` moves the fixed clock forward by 90 minutes.

    {
        Test::assertSame(Time::now()->toIso(), '2026-01-01T00:00:00Z');

    public function aSeedIsRepeatable(): void

    {

}

}
```

## Example 07: tags select which tests run

```nvs test
<?nvs
// Shows how to label tests with `tags:`. `nvs test --tag db` runs only the tests
// labelled `db`, and `nvs test --skip-tag slow` runs every test except the slow ones.
// proof: test

use Core\Test;

class Order
{
    public static function withShipping(int $cents): int
    {
        return $cents + 500;
    }
}

class OrderTest
{
    // A test without `tags:` runs when no `--tag` is given.
    #[Test]
    public function itAddsTheShippingCost(): void
    {
        Test::assertSame(Order::withShipping(1000), 1500);

    #[Test(tags: ['db', 'slow'])]
    public function itAddsShippingToEveryStoredOrder(): void
    {
        array<int> $stored = [500, 1000, 2500];

        foreach ($stored as int $cents) {
            $total = $total + Order::withShipping($cents);

        Test::assertSame($total, 5500);

    // `--skip-tag slow` leaves out this test.
    #[Test(tags: ['slow'])]
    public function itAddsShippingToAMillionOrders(): void
    {
        int $total = 0;
        for (int $i = 0; $i < 1000000; $i++) {
            $total = $total + Order::withShipping(100);
        }
        Test::assertSame($total, 600000000);
    }
}
```

# `#[Core\Test\Fixture]`: built once, injected by type

A fixture is a value your tests share. It is built once, and every test that needs it is called with
it.

You write a `public static` method and put `#[Fixture]` above it. The type that method returns is
what the fixture supplies. Every test in the same class that declares a parameter of that type is
called with the value. The name of the parameter does not matter, only its type. A fixture may
declare a parameter as well, so one fixture can be built from another.

The method runs once for the whole class, before the tests. Each test then works on its own copy, so
a change one test makes is not visible to another. Setup that costs time, such as reading a file or
building a large object, happens one time. Each test runs on its own, so without a fixture this setup
runs once for every test.

**Good to know:** a fixture belongs to its own class, and a test cannot use another class's fixture.
A parameter that no fixture supplies does not compile.

A fixture method that is not `static` or not `public`, or that returns `void`, is `E0735`. A
`#[Fixture]` with a field, such as `#[Fixture(name: "x")]`, is `E0454`.

Two fixtures of one class that return the same type are `E0304`. Fixtures that need each other, such
as `s` needing `r` and `r` needing `s`, are `E0737`, and the message shows the cycle.

The type must be the same. A fixture that returns a subclass `S2` does not fill a parameter of type
`S`, and that parameter is `E0736`. A fixture may return any type, such as `int`, `?int` or
`array<int>`.

A fixture is built only when a test that runs needs it. A fixture that only skipped tests need is
not built.

A fixture that throws an error makes each test that needs it fail, with the error's message. The
other tests of the class still run.

A variadic or `inout` parameter on a test method is `E0733`.

A fixture method is test code, like a test method. Only a test, a fixture or a class hook may call
it. A call from other code is the compile error `E0889`. `nvs run` and `nvs build` do not compile it.

## Example 01: one value for every test

```nvs
<?nvs
// Shows how every test gets one value. `#[Fixture]` goes above a `public static`
// method, and the type that method returns is what it supplies.

use Core\Test;
use Core\Test\Fixture;

class ShippingRates
{
    public function constructor(public int $baseCents, public int $perItemCents)
    {}

    public function totalCents(int $items): int
    {
        return $this->baseCents + $this->perItemCents * $items;
    }
}

class ShippingRatesTest
{
    // This method runs once for the whole class. Every test below that declares
    // a `ShippingRates` parameter is called with what it returns.
    #[Fixture]
    public static function rates(): ShippingRates
    {
        return new ShippingRates(499, 120);
    }

    #[Test]
    public function threeItemsPayTheBaseAndThreeItems(ShippingRates $rates): void
    {
        Test::assertSame($rates->totalCents(3), 859);
    }

    // The type of the parameter says which fixture fills it. The name is yours
    // to choose.
    #[Test]
    public function anEmptyOrderPaysTheBase(ShippingRates $anyNameYouLike): void
    {
        Test::assertSame($anyNameYouLike->totalCents(0), 499);
    }
}

// This prints 859.
```

# `#[Core\Test\TestWith]`: data rows

A data row gives one test a set of values. You write one row for each set, and each row is reported
as its own case.

`#[TestWith(name: value, …)]` goes above a `#[Test]` method. Each field of the row names one
parameter of that method, and the value is a constant. Repeat `#[TestWith]` for every set of values
you want. The runner calls the method once per row, in the order you wrote the rows, and reports
them as `method#0`, `method#1` and so on. A row that fails is reported on its own, and the rows
after it still run.

Rows and fixtures work together in one test. A parameter that a row names is filled by the row. A
parameter that no row names is filled by the fixture of that type.

**Good to know:** every row of a method fills the same parameters, and a field that names no
parameter does not compile.

A row value is a literal of the parameter's type: an `int`, `uint`, `float`, `bool` or `string`
written in the code. An `int` literal also fills a `float` parameter. A class constant, an enum case,
an array and a negative number for a `uint` are `E0738`.

A field that names no parameter is `E0738`, and so is a value of the wrong type. A field given twice
in one row is `E0304`. A row that leaves out a parameter that another row fills is `E0738`.

`#[TestWith]` on a method without `#[Test]` is `E0738`. A parameter with no row and no fixture is
`E0736`.

When a row and a fixture can both fill a parameter, the row is used.

`skip:` on a test with rows skips every row, and each row is reported as skipped. With `retries:`,
each row gets its own attempts.

`--filter` selects a single row by its name, such as `--filter SlugTest::itSlugs#1`.

## Example 01: one row for each case


# `#[Core\Test\Property]`: generated inputs

A property is a test that runs many times, with new inputs on every call. You say what must be
true for every input, and the runner looks for an input where it is false.

`#[Property]` goes on a method with the same shape as a `#[Test]` method. Each parameter gets a
generated value of its declared type. The runner calls the method 100 times, and `runs:` changes
that number. `gen: { level: "0..1000" }` gives `$level` a whole number from 0 to 1000.

When a call fails, the runner tries smaller inputs that still fail. The report shows the smallest
input it found, the input that failed first, and the seed. Write that seed as
`#[Property(seed: n)]`, and the test runs with the same inputs again.

**Good to know:** a generated string can have any character, including emoji and accents. A
property that only holds for English letters fails.

A parameter can have any of these types: a number, `bool`, `decimal`, `string`, `bytes`, an enum, `mixed`,
`?T`, `array<T>`, a shape, a union, and a class of your program with a `public` constructor. A class
is built with `new`, so its constructor runs. A function, an interface, an abstract class, a `Core`
class and a `secret` value are `E0890`.

`gen:` takes a range for a parameter, written as `"low..high"`. Both ends are included. On a
number, the range is the value. On a `string`, `bytes` or `array<T>`, the range is the length, up
to 10000. A string's length counts characters as a person reads them. On `?T`, the range is for
`T`. A range that names no parameter, or that does not fit the type, is `E0890`.

The options are those of `#[Test]`, without `retries:` and `because:`. `runs:` is from 1 to 100000.
A property never uses a `#[TestWith]` row or a fixture.

The seed also sets the test's own random numbers. Without `seed:`, every run has a new seed.

The runner tries at most 1000 smaller inputs. It also stops at the test's time limit. One call's
inputs have at most 1048576 elements, bytes and characters together. A property that needs more
fails before its first call.

In the JSON report, a failed property has a `counterexample` field. A subclass runs every property
it inherits, the same way it runs an inherited `#[Test]`.

# Hooks: `#[BeforeClass]`, `#[AfterClass]` and `#[AfterEachTest]`

A hook is a method that the test runner calls around your tests. You use one to clean up something a
test leaves outside itself, such as a file or a database table.

- `#[BeforeClass]` runs once, before the tests of the class. It is a `public static` method.
- `#[AfterClass]` runs once, after the last test. It is a `public static` method. It can take a
  `Core\Test\Summary`, which has the counts of passed and failed tests.
- `#[AfterEachTest]` runs after each test, on the same object as the test. It can take a
  `Core\Test\Outcome`, which has the name of the test and whether it passed.

The after hooks also run when a test fails. `#[AfterClass]` also runs when `#[BeforeClass]` throws
an error.

To prepare each test, use the constructor. To share a value with the tests, use a fixture.

**Good to know:** a class has at most one hook of each kind. A subclass inherits the hooks of its
parent class.

`#[BeforeClass]` takes no parameters. `#[AfterClass]` may take one `Core\Test\Summary`, and
`#[AfterEachTest]` one `Core\Test\Outcome`. A hook with another parameter is `E0862`. So is a hook
that returns a value or is not `public`. A class hook must be `static`, and `#[AfterEachTest]` must
not be. Each of those is `E0862` too.

A second hook of one kind in a class is `E0304`.

`#[BeforeClass]` and `#[AfterClass]` may not write a `static` property. That is `E0863`. Each test
reads the declared value, so a fixture is the way to give the tests a value. `#[AfterEachTest]`
runs with the test, and it may write one.

The class hooks run in this order: `#[BeforeClass]`, then the fixtures, then the tests, then
`#[AfterClass]`. They run when every test of the class is skipped. They do not run for a class with
no test, or for a class that `--filter` leaves out.

What a class hook prints with `echo` is part of the report, under the class name. What
`#[AfterEachTest]` prints belongs to the test, so it is shown only when the test fails.

`#[AfterEachTest]` runs after every attempt. It sees the properties the test set on the object.

`Core\Test\Outcome` has `class()`, `name()`, `attempt()`, `passed()` and `failures()`, the messages
of the failed assertions. `Core\Test\Summary` has `class()`, `passed()`, `failed()`, `skipped()`,
`flaky()` and `failedTests()`, the names of the failed tests.

When `#[BeforeClass]` throws an error, each test fails. The message names the hook and gives the
error's message. `#[AfterClass]` still runs.

When `#[AfterClass]` throws an error, the report has a line marked `✗` with the hook's name, and
the exit status is `1`. When `#[AfterEachTest]` throws an error, that attempt fails.

A subclass runs the tests, the fixtures and the hooks of its parent under its own name. The parent
also runs them under its name, unless it is `abstract`. A method that overrides a hook or a test
without its attribute is `E0862` or `E0733`.

There is no `#[BeforeEachTest]`. The constructor of the test class runs before each test.

## Example 01: remove the file a test wrote

```nvs
<?nvs
// Shows `#[AfterEachTest]` removing the file a test wrote, so the next run starts
// without it.

use Core\IO;
use Core\Path;
use Core\Test;
use Core\Test\AfterEachTest;

class ShoppingList
{

    {

        foreach ($items as string $item) {
            $text = $text . '- ' . $item . "\n";
        }
        return $text;
    }
}

class ShoppingListTest
{
    public string $file;

    public function constructor()
    {
        $this->file = Path::fromCwd('shopping-list-test.txt');
    }

    #[Test]
    public function itWritesOneLinePerItem(): void
    {
        IO::write($this->file, ShoppingList::text(['bread', 'milk']));
        Test::assertSame(IO::readText($this->file), "- bread\n- milk\n");
    }

    // This runs after the test, also when the test fails.
    #[AfterEachTest]
    public function removeTheFile(): void
    {
        IO::remove($this->file);
    }
```

## Example 02: create a table once for the class

```nvs
<?nvs
// Shows `#[BeforeClass]` creating a database table once for the class, and
// `#[AfterClass]` deleting it after the last test.

use Core\Db;
use Core\Test;
use Core\Test\AfterClass;
use Core\Test\BeforeClass;

class Seed
{
    // This builds one `insert` statement for many products.
    public static function insertProducts(array<string> $names): string
    {
        string $values = '';
        foreach ($names as string $name) {
            if ($values != '') {
                $values = $values . ', ';
            }
            $values = $values . "('" . $name . "')";
        }
        return 'insert into products (name) values ' . $values;
    }
}

class ProductTest
{
    // The table is outside every test, so a hook creates it one time.
    #[BeforeClass]
    public static function createTable(): void
    {
        var $db = Db::connect('test');
        $db->execute('create table products (name text)', []);
        $db->execute(Seed::insertProducts(['tea', 'cake']), []);
    }

    // `db: "test"` undoes what the test writes, so every test sees two rows.
    #[Test(db: 'test')]
    public function itFindsTheSeededProducts(): void
    {
        var $rows = Db::connect('test')->query('select name from products', []);
        Test::assertCount($rows->all(), 2);
    }

    // This runs after the last test, also when a test failed.
    #[AfterClass]
    public static function dropTable(): void
    {
        Db::connect('test')->execute('drop table products', []);
    }
}

// This prints the statement `createTable` runs.
echo Seed::insertProducts(['tea', 'cake']), "\n";
```

```output
insert into products (name) values ('tea'), ('cake')
```

## Example 03: keep the log of a failed test

```nvs
<?nvs
// Shows hooks that keep the log of a failed test and delete the log of a passed
// one. A build server can then show the logs of the failed tests.

use Core\IO;
use Core\Path;
use Core\Test;
use Core\Test\AfterClass;
use Core\Test\AfterEachTest;
use Core\Test\Outcome;
use Core\Test\Summary;

class Evidence
{
    // A retry is a new attempt, so the attempt number is part of the name.
    public static function fileName(string $class, string $test, int $attempt): string
    {
        return $class . '-' . $test . '-' . $attempt . '.log';
    }
}

class CheckoutTest
{
    public string $log;

    public function constructor()
    {
        $this->log = Path::fromCwd('checkout-test.log');
    }

    #[Test]
    public function itAddsTheShippingCost(): void
    {
        // The prices are in cents.
        IO::write($this->log, "total 1250, shipping 490\n");
        Test::assertSame(1250 + 490, 1740);
    }

    // `Outcome` says which test ran and whether it passed.
    #[AfterEachTest]
    public function keepTheLogIfItFailed(Outcome $outcome): void
    {
        if ($outcome->passed()) {
            IO::remove($this->log);
        } else {
            string $name = Evidence::fileName($outcome->class(), $outcome->name(), $outcome->attempt());
            IO::move($this->log, Path::fromCwd($name));
        }
    }

    // `Summary` has the counts for the whole class.
    #[AfterClass]
    public static function report(Summary $summary): void
    {
        echo $summary->failed(), " failed, their logs are kept\n";
```

# Assertions

An assertion checks one thing about a value. When the check is false, the test fails.

Every assertion is a static method of `Core\Test`. You write the value your code produced first,
and the value you expect second. An assertion that passes returns and does nothing. One that fails
records the failure and throws `Core\Test\Failure`, and the error message names both values. You
may add `{ message: "..." }` at the end of any assertion to put your own sentence in front of that
message.

Catching a `Core\Test\Failure` does not make a test pass. The runner keeps a record of every failed
assertion, so a test that caught its own failure still fails. The report lists every failed
assertion of a test.

**Good to know:** both sides of an assertion have the same type, so `assertSame(1, "1")` does not
compile.

`Core\Test::assertSame` compares numbers, strings and arrays by value. Two objects pass only when
they are the same object, so `assertSame(new P(1), new P(1))` fails.

`assertEquals` is the same as `assertSame`, but it compares two objects with their `compareTo`
method. It passes when `compareTo` returns `0`. For a class without `compareTo`, it throws a
`RuntimeError`, and the test fails.

`assertEqualsDeep` compares arrays entry by entry and objects property by property. The message
names the first place where the two differ, such as `$actual->rows["1"]->name`. A `secret`
property is compared, and the message shows `«redacted»` in place of its value.

Both sides of `assertSame`, `assertEquals` and `assertEqualsDeep` have one type. `assertSame(1, "1")`
and `assertSame(1, 1.0)` are `E0401`. `assertTrue` takes a `bool`, so `assertTrue(1)` is `E0401`.

`assertCount` counts every entry, with any keys.

`assertThrows` passes when the function throws the class you name or a subclass of it. Its message
names the class that was thrown instead, or says that the function returned. `assertDoesNotThrow`
fails with the message of the error the function threw.

An assertion that fails inside the function you give `assertThrows` still makes the test fail. To
test that an assertion fails, use `Core\Test::expectFailure`. It passes when an assertion inside the
function failed, and that failure does not count against the test. It fails when no assertion
inside the function failed.

A failing assertion throws, so the lines after it in the test do not run. A test that catches each
`Core\Test\Failure` goes on, and the report lists every failed assertion.

`Core\Test\Failure` is a `Throwable`. It is not a `RuntimeError` and not a `LogicError`.

Under `nvs run`, an assertion that fails throws the same `Core\Test\Failure`. If nothing catches it,
the program ends with exit status `1`.

`Core\Test::advance` is not an assertion. It moves the clock that `#[Test(at:)]` fixed.

# Running tests: `nvs test`

`nvs test main.nvs` compiles a program and runs every method that has the `#[Test]` attribute. It
prints one line for each test and a count at the end.

Tests can be in the same file as the code, or in a class of their own. The statements outside a
class do not run under `nvs test`.

`nvs test .` runs every `.nvs` file in a folder and its subfolders as one program. Run it in your
project folder, so every test can use the classes your `autoload` line loads. A `tests` folder
needs one file that requires your entry file.

`--filter <text>` runs only the tests whose name, `Class::method`, contains that text.
`--list` prints each test and its file, and runs none. `--format json` and `--format junit` print a
report for a build server. The exit status is `1` when a test failed, and `0` otherwise.

The examples show two tests, two test classes with a filter, and a report for a build server.

`nvs test main.nvs` runs the tests in `main.nvs` and in the files it loads. `autoload` loads only the
classes the program uses. A test class that the program never names does not run. `nvs test .`
runs it.

`nvs test tests/` runs every `.nvs` file in `tests/` and its subfolders as one program. One file
there requires the entry file of your application, and its name can be anything. The statements
outside the classes do not run, in any of the files.

A `.nvst` file, or a folder of `.nvst` files, is a different kind of test. Each file has a
`--TEST--` title, a program under `--FILE--` and its expected output under `--EXPECT--`. The report
is one line, such as `1 passed, 0 failed, 0 skipped`.

A folder with both `.nvs` and `.nvst` files is an error. `nvs test` takes one program at a time, so
a `.nvs` path and a `.nvst` path in one call are an error too. `--format`, `--list` and `--update`
do not work with `.nvst` files.

`--format json` prints one JSON document at the end. It has `schemaVersion` `2`, a `summary` with
`total`, `passed`, `failed`, `skipped`, `flaky` and `durationMs`, and a `tests` list. Each test has
`class`, `method`, `file`, `line`, `column`, `verdict` and `durationMs`. `line` and `column` are
where the method's name is written, counted from `1`. A skipped test also has `reason`. A failed or
flaky test has `failures`, and a flaky test has `attempts`.

`--coverage-lcov`, `--coverage-clover` and `--coverage-cobertura` write which lines the tests ran.
With one of them, the JSON document has `schemaVersion` `3`, and each test has `coverage`. It maps
each file name to the lines that test ran.

`--format junit` prints JUnit XML, with one `<testsuite>` for each class and one `<testcase>` for
each test. A test has `<skipped>`, `<failure>` or `<flakyFailure>` inside it. The `message` of a
failure is its first message, and the text inside is every message.

With `--format json` or `--format junit`, standard output has only the document. The output of a
test that fails goes to standard error.

`--list` prints each test and where it is written, such as `T::a  main.nvs:6`, and runs nothing. A
test with data rows has one line for each row. With `--format json`, it prints a document with
`schemaVersion` `2` and a `listed` list of `class`, `method`, `file`, `line` and `column`.

`--filter` is case-sensitive, so `--filter t::` does not select the class `T`. A data row
is `Class::method#0`, `Class::method#1` and so on. A class with no selected test is not printed, and
its fixtures are not built.

The exit status is `1` when a test failed, and `0` otherwise. It is the same in every format.

# `#[Bench]` and `nvs test --bench`

`#[Bench]` marks a method as a bench. A bench measures how much work a piece of code does.
`nvs test --bench main.nvs` runs every bench in the program, one at a time. It runs no test, and a
plain `nvs test` runs no bench.

A bench method has the same shape as a `#[Test]` method. Write `use Core\Test\Bench;` at the top of
the file, and `#[Bench]` above the method.

The report prints a `count:` line under each bench. It counts statements, calls, allocations,
allocated bytes and runs of the garbage collector. These counts are the same on every run and on
every computer. The line also prints the time the bench took, marked `(advisory)`, because that
time changes on every run.

A bench passes without an assertion. With `--format json`, a build server can compare the counts
with the last run.

**Good to know:** a new version of Novis can give the same program different counts.

The examples show a bench beside a test, two ways to write the same work, and benches that a build
server checks.

A bench method is `public`, it is not `static`, and it returns `void`. If an assertion inside a
bench fails, the bench fails. `#[Bench(skip: "reason")]` skips a bench and prints the reason.

The counts tell you if your code does more work. They do not tell you if Novis got faster.

Each bench runs once. Its counts are the same on every run, so a second run gives no new
information.

Each bench runs on its own, the same way each test does. A value that one bench puts in a `static`
property is not there when the next bench runs. So the counts of a bench do not depend on the
benches that ran before it.

A bench can have a `#[Fixture]` parameter. The fixture is built before the counting starts, so its
work is not part of the counts.

A bench cannot fix the clock or the random numbers. A bench that reads `Core\Time::now()` or calls
`Core\Random` can do different work on each run, and then its counts change too.

`#[Bench]` has two options, `skip:` and `because:`. Both are strings. Every other option of
`#[Test]`, such as `retries:`, `seed:` or `at:`, does not compile on a bench. A `#[TestWith]` row on
a bench does not compile either. A method that has `#[Bench]` and also `#[Test]` or `#[Fixture]`
does not compile.

`--filter` works with `--bench` and selects benches by `Class::method`. `--bench` does not work with
`--jobs` or `--mutate`, and it does not work with a `.nvst` file.

In the JSON report, a bench that ran has `counts` with `statements`, `calls`, `allocations`,
`bytes` and `gc`. It also has `advisoryWallMs`, the time it took in milliseconds. A skipped bench
has `reason` and no `counts`.

The exit status is `1` when a bench failed, and `0` otherwise.
