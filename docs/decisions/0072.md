# ADR 0072 — `Core\Task`: concurrency is a call that returns with nothing still running

- **Scope:** the `Core\Task` roster — `all`, `map`, `afterResponse` — the `{limit, deadline}` options they
  share, what a cancellation does and does not run, and the `[deferred]` directives that bound work
  outliving a response. It also names what M5's loose verb list (`all`, `race`, `timeout`, `parallel_map`)
  becomes under `rule:core-api/shape-rules`'s rules. Not in scope: `spawn`/`await`'s grammar
  and `Core\Task\Channel`'s surface, both of which stay M5's own design; and the scheduler itself.

> **In short:** the concurrency shape applications actually reach for is not a scope object — it is *"run
> these four things, give me all four results, and if one fails give me the failure."* That is
> **`Core\Task::all`** over a shape literal of closures, returning a shape of their results **field by
> field with each field's own type**, and **`Core\Task::map`** over a collection. Both take
> `{limit, deadline}`. **Control never leaves either call with work still running**: the first throw
> cancels its siblings and propagates, the deadline cancels everything and throws `TimeoutError`, and in
> both cases the call waits for the cancellation to complete before returning. **Cancellation runs no user
> code** — no `catch`, no `finally` — because the only three situations that produce one are situations in
> which the request is already failing and has no budget to lend. Separately,
> **`Core\Task::afterResponse(callable, {deadline})`** runs work after the response is on the wire, charged
> to the request tree, which therefore does not end when the connection does; past `[deferred]
> max_concurrent` it **throws at the call site rather than queueing**. It is **not a queue** — nothing is
> durable, nothing retries, a lost process loses the work — and the ADR says so because that is the
> sentence someone will need to have read.

## Context

- [docs/implementation-plan.md](../implementation-plan.md)'s M5 has named `spawn` / `await` / `all` /
  `race` / `timeout` / `Channel` / `parallel_map` since the plan was written, as a list of verbs with no
  home, no signatures and no owning ADR. Under
  `rule:classes/no-free-functions-or-constants` none of them can be a free function, and
  under `rule:core-api/shape-rules` `parallel_map` is subject-last and abbreviated. Left as
  they are, they become the library's first four members that do not obey the library's rules.
- The shape that matters is narrow and very common: a request handler fetching a user, their orders and a
  feature-flag set concurrently, then rendering all three. In PHP that is three sequential round trips,
  because PHP has no way to express it; `curl_multi_*` exists and essentially nobody uses it, which is the
  evidence that an awkward concurrency API is the same as no concurrency API.
- **Structured concurrency is the property worth buying, and it is a property of the *call*, not of a scope
  object.** Kotlin's `coroutineScope`, Swift's `withTaskGroup` and Trio's nursery all give an open-ended
  block you add tasks to. That is more general and it is more to learn, and Novis already has the same
  guarantee at a coarser grain — `rule:security/isolate-shares-nothing`'s "a task tree dies with its
  parent — no orphans". A call that cannot return while its children run gives the identical guarantee with
  no new concept.
- The genuinely new question is **work that outlives the response**. Every real application has some: a
  receipt email, a webhook, a cache warm, an audit ship. PHP's answers are `fastcgi_finish_request()` (which
  keeps the whole FPM worker busy and is invisible to any accounting) or a job queue (correct, and a
  dependency the application must run). Novis can do the first one honestly, because a request tree is already
  an accounted, capped, cancellable thing — but only if it is stated that the tree, not the connection, is
  what the budget follows.
- **There is no crate for any of this, and there cannot be.** `tokio::JoinSet` and `tokio::Semaphore` are
  the prior art and are unusable here: they are built on tokio's `async`/`Future` model, and this runtime is
  `corosensei` stackful coroutines on its own thread-per-core scheduler. This is a few hundred lines over
  M5's own primitives, which is exactly the split *Decisions taken at project start* names — scheduler
  primitives are ours.

## Decision

### 1. `Core\Task::all` — a fixed, heterogeneous set, each field keeping its own type

```php
use Core\Task;

$page = Task::all({
    user:   fn(): User          => Users::load($id),
    orders: fn(): array<Order>  => Orders::recent($id, 20),
    flags:  fn(): FlagSet       => Flags::forUser($id),
}, {deadline: 2s});

echo $page->user->name;          // typed User, not mixed
echo Core\Arr::length($page->orders);
```

The argument is an `rule:types/object-top` shape literal whose every field is a
zero-argument closure, and the result is a shape with **the same field names and each closure's own return
type**. This is the whole reason the member is worth having: the uniform alternative returns
`array<mixed>`, and every call site then pays a cast, which is the same defect that made a userland DI
container untypeable and got one rejected during the session this ADR came out of.

- **Each field's type binds from a written `fn` literal's declared return type.** A field whose value is a
  `callable`-typed variable rather than a literal is a compile error naming the field, because there is
  nothing to bind from — `rule:types/anonymous-function` leaves `callable` without a
  signature, and `rule:types/grammar`'s deferred typed-`callable` signatures are
  what would remove this restriction, and that ADR's *Revisiting* is where this case is counted with the
  others.
- The closures run as ordinary tasks on the calling core unless a body itself spawns elsewhere; each is a
  child of the calling task, so `rule:security/isolate-shares-nothing`'s tree accounting applies with
  nothing added.
- `all` over a shape with one field is legal and pointless; nothing special-cases it.

### 2. `Core\Task::map` — the homogeneous case, and what `parallel_map` becomes

```php
$responses = Task::map($urls, fn(string $u): Response => Http\Client::get($u), {limit: 8, deadline: 10s});
```

`map(array<T> $items, callable $fn, {limit?, deadline?}): array<U>`, subject first
(`rule:core-api/shape-rules` R1), the callback receiving `($value, $key)` like every other
callback in the library (R9), and the result **preserving the input's keys and order** regardless of
completion order. It replaces the plan's `parallel_map`, which was subject-last and abbreviated (R1, R7).

`all` and `map` are two members rather than one because they are two jobs — a fixed set of differently-typed
things, and one operation over many same-typed things — not two spellings of one (R15, R17). A shape literal
cannot express "one per element of a runtime array" and an array cannot carry a per-element type.

### 3. `{limit, deadline}`, and what `timeout` and `race` become

One trailing options shape (R2), the same two fields on both members:

- **`limit: uint`** — the maximum number of the call's own children running at once. Default: unbounded for
  `all` (a fixed shape literal is already bounded by its field count) and unbounded for `map`. Exceeding it
  **schedules**, it does not throw: this is a concurrency shaper, deliberately unlike § 4's
  `max_concurrent`, which is a host bound and does throw.
- **`deadline: Duration`** — a wall-clock bound on the whole call, not per child, expressed as an
  `rule:types/duration` literal. There is no default: a call that names no deadline is
  bounded by the request tree's own `wall_time`, which is finite by
  `rule:config/three-changeability-classes` and is the only reason omitting it is safe.

The plan's `timeout(...)` is therefore not a member: a timeout on a group of tasks is this option (R2 —
optional arguments are the options shape, never a wrapper function), and a timeout on a single I/O call is
that call's own `timeout` option, which `rule:core-classes/db-one-api` and `Core\Http\Client` already carry.

**The plan's `race` is deferred, not delivered here.** Over a heterogeneous shape its result is a union of
every branch's return type that the caller must discriminate — `mixed` plus a cast in practice, § 1's whole
objection. Its one clearly-valuable use, hedging one request across two replicas, is *homogeneous* and can
land later as `Core\Task::first(array<T>, callable, {deadline?})`, purely additively. Naming the future
spelling is what stops it arriving as a second `race`.

### 4. Failure, the deadline, and the promise that nothing is still running

| what happens | what the call does |
|---|---|
| every child returns | the shape (`all`) or the array (`map`) |
| one child throws | every sibling is cancelled; the call waits for those cancellations; the **first** throw propagates |
| two children throw | the first by completion order propagates; the second is written to `Core\Log` with the propagating error's trace id, never swallowed |
| the deadline expires | every child is cancelled; the call waits; `TimeoutError` is thrown |
| the *calling* task is cancelled | every child is cancelled; nothing is returned |

**Control does not leave the call with work still running.** That is the guarantee the whole member exists
for, and it is what makes a `Task::all` inside a `Core\Db` transaction safe to reason about: when the call
returns, no child is still holding a row lock.

It costs something honest, and here it is: **a deadline bounds when cancellation is *requested*, not when
the call returns.** A child blocked mid-statement in `Core\Db` cannot simply be abandoned — a connection
with an unread result set is unusable — so the connection is asked to cancel the statement through the
driver's own mechanism (`KILL QUERY`, `PQcancel`, `sqlite3_interrupt`) and the call waits until the
connection is back in a known state or is closed. That drain is bounded by the connection's own `timeout`
(`rule:core-classes/db-one-api`), after which the connection is closed rather than returned to the pool. A
`deadline: 2s` can therefore return at 2s plus one connection timeout in the pathological case; overrunning
by a bounded amount is the correct trade against handing a poisoned connection back to the pool.

### 5. Cancellation runs no user code

A cancelled task is torn down by the runtime at its next safepoint. **No `catch` clause runs, no
`finally`-shaped cleanup runs, and no user-registered handler runs.** Native teardown still runs — the
arena is dropped, refcounts are released, an open `Core\Db\Transaction` is rolled back by its own native
drop, an open file is closed — because none of that is script code.

This is deliberate and it is the same reasoning `rule:errors/escalation-ladder` applies at every
tier of its ladder. There are exactly three ways to be cancelled — a sibling threw, the deadline expired, or
the parent died, which for the root task includes its client disconnecting: the connection is the root's
parent, and `rule:http-server/a-request-outlives-a-client-that-goes-away` cancels the
whole request tree when it drops — and all three mean the request is already failing. Running arbitrary
user cleanup at that point means running unbudgeted code inside a failure, which is how a timeout becomes
a hang.

Cancellation is therefore **not a `Throwable`** and cannot be caught, exactly as a resource-limit report is
not one (`rule:errors/throwable-hierarchy`). The consequence a developer has to learn: work
that *must* happen does not go in a cancellable task's cleanup. It goes inside the database transaction, or
in § 6's deferred work, or in a durable queue the application owns.

### 6. `Core\Task::afterResponse` — the connection ends, the request tree does not

```php
Task::afterResponse(fn(): void => Receipts::send($order), {deadline: 30s});
return $response;                     // the client has its bytes; the receipt is still going out
```

The closure runs after the response is fully written. **On a host with no response — `nvs run`, and a
`spawn script` isolate — that trigger reads as the scheduling task's own frame returning**, which is the
same moment under a server, the response being what the request frame produced; one rule, and nothing
about the member's meaning changes with where it was called. A request that ended by a throw, an `exit`
or a `FATAL` runs none of it: the status the host is about to report is on the context and script running
over it would lose one of the two. `nvs_runtime::deferred` is the one home for that reading and for
everything it implies. **Memory, CPU and tasks stay charged to the request
tree**, so `rule:programs/memory-priority`'s "attributable, under an enforceable cap,
O(in-flight)" holds with nothing relaxed — the tree simply stays in flight a little longer than the
connection does. `[limits] wall_time` is what the client waited for and no longer applies; the deferred
`deadline` replaces it, and every other `[limits]` value continues to bound the tree.

- **An uncaught throw inside it goes through `rule:errors/escalation-ladder`'s ladder** to
  `Core\Log`, carrying the scheduling request's trace id. There is no response left for it to affect, and
  tier 2's `onUncaughtThrow` handler — registered by the request that is now finished — does **not** fire,
  because it was request-local and the request's own execution is over.
- **The closure may not touch `Core\Response`.** The response is on the wire; a write to it is a
  compile-time diagnostic where the call is statically visible and a throw otherwise. `Core\Request`,
  `Core\Server` and `Core\Session` remain readable — the tree is still the same tree.
- **`Core\Task::all`/`::map` compose inside it** with no special case, since it is an ordinary task.
- **Only the request's own task may register, and deferred work may not defer more.** The queue is the
  request's; a `Core\Task` child, an isolate and a deferred closure have none, so a registration made on
  one would be dropped when that child ended. It is a `RuntimeError` at the call site instead, while there
  is still a request to decide what to do. A queue that can extend itself is also a tree that never leaves
  flight, and the affordability argument above is that the tree outlives the connection only a little.
- **This is not a queue, and it is not sold as one.** Nothing is durable, nothing retries, and a process
  that dies loses the work with no record. Receipts, webhooks, cache warming, reindexing and audit shipping
  are what it is for. Anything that *must* happen belongs inside the transaction that made it necessary, or
  in a durable queue the application runs. The documentation says this in the first paragraph, not in a
  footnote.

This is the case `rule:security/isolate-shares-nothing`'s *Revisiting* gestured at and it is
**not** the one that ADR left open. That one asks what budget a fire-and-forget isolate spends **after its
parent is gone**; here the parent is not gone, which is precisely why this one is affordable and that one
is still open.

### 7. `[deferred]`, and what happens when it is full

```toml
[deferred]
max_concurrent = 256      # System   — request trees per core kept alive for deferred work
deadline       = "30s"    # Runtime  — the default a call inherits when it names none
```

- **`max_concurrent` is `System`.** It bounds how much a core holds after responses are on the wire, which
  is a host-sizing decision and not a request-local one — the same class and the same reasoning
  `rule:testing/debug-probes` gives for `[debug] mode`
  being unchangeable upward from inside a request.
- **Past the cap, `afterResponse` throws** — a `RuntimeError` at the call site, while the request is still
  running and can still decide what to do (respond anyway, do the work inline, tell the caller to retry).
  It does **not** queue. An unbounded queue in front of a non-durable executor is the worst of both designs:
  it hides the overload, then loses the work anyway. A deployment hitting this cap has outgrown deferred
  work and needs the durable queue § 6 declines to be.
- **`deadline` is `Runtime`**, an ordinary per-request default a call may name its own value for, bounded
  like every other limit by the tree's remaining budget.

Cost, stated as `rule:programs/memory-priority` requires: a deferred request tree holds its arena
at its peak for the length of its deferred work, so the worst case per core is `max_concurrent ×
[limits.hard] memory` **on top of** in-flight requests. That is a real number an operator must size for, it
is bounded, and it is O(in-flight deferred trees) rather than O(requests served).

## Consequences

**Positive**

- **The common concurrency shape is one call with typed results.** Three sequential round trips become one,
  in a language whose entire origin story is a language where that was not expressible.
- **Structured concurrency with no new concept.** The guarantee comes from the call's own contract, so there
  is no scope object, no nursery, and nothing new to learn beyond `all` and `map`.
- **M5's four loose verbs get a home and a shape.** `parallel_map` becomes `Task::map`, `timeout` becomes an
  option, `race` gets a named future spelling instead of arriving twice.
- **Post-response work stops being a footgun.** PHP's `fastcgi_finish_request` has no accounting, no cap, no
  cancellation and no logging; this has all four, and the price is one directive an operator sizes.
- **The cap failing loudly is the feature.** A deployment that has outgrown non-durable deferred work finds
  out at the call site rather than by discovering that receipts stopped being sent.

**Negative**

- **`Task::all` only accepts written `fn` literals.** A framework that stores closures in a variable and
  runs them cannot use it, and must use `map` over `array<callable>` with a `mixed` result. This is a real
  restriction, it is visible in the diagnostic, and it goes away with typed `callable` signatures.
- **Cancellation running no user code will surprise people.** A `finally`-shaped cleanup is exactly what a
  PHP developer would reach for and it does not run. The mitigation is that the three cancellation causes
  are all failures, but the rule has to be taught, not discovered.
- **A deadline is bounded, not exact** (§ 4). A driver-level statement cancel can add its own timeout on top
  of a stated deadline, so a `deadline` is not a hard wall-clock guarantee on return.
- **`afterResponse` keeps a request tree's arena alive past the response**, so peak memory per core is
  higher than the in-flight-request count alone suggests. Named in § 7 with its arithmetic so it is sized
  rather than discovered.
- **Two members will be asked to be three, then five.** `race`, `first`, `any`, `settled` and a scope object
  are all things somebody will want. The deferral in § 3 is the control, and it only holds if each addition
  is argued rather than added.
- **Nothing here is durable, and the word "task" will imply that it is** to anyone arriving from Celery,
  Sidekiq or Laravel queues. The class name is right — it is the runtime's own unit of work — and the
  documentation has to carry the correction.

## Alternatives rejected

- **An open-ended scope object** (`Task::scope(fn($scope) => { $scope->spawn(...); ... })`), the
  Kotlin/Swift/Trio shape. More general, and it is the general-purpose version of a specific need nobody has
  yet. Deferred rather than rejected: adding it later is purely additive and does not change anything
  decided here, and having `all`/`map` first means the scope object will be argued against real code.
- **`Task::all` returning `array<mixed>`.** One signature, no type binding, no `fn`-literal restriction.
  Rejected: every call site then casts, which is the untypeable-container failure the same session refused
  to build a DI container around. The restriction in § 1 is the honest cost of not doing that.
- **Letting the first throw propagate without waiting for siblings to cancel.** Returns faster and is what
  a naive implementation does. Rejected: it leaves work running that nobody is holding a handle to, which is
  the orphan class `rule:security/isolate-shares-nothing`'s tree accounting exists to make
  impossible, and it can leave a transaction's row locks held past the `catch`.
- **Making cancellation a catchable `Throwable`.** Familiar, and lets `finally` clean up. Rejected on
  `rule:errors/escalation-ladder`'s reasoning: it runs unbudgeted user code inside a failure,
  and a `catch (Throwable)` that swallows a cancellation turns a deadline into a hang.
- **Queueing past `[deferred] max_concurrent` instead of throwing.** Smoother under a burst. Rejected: an
  unbounded queue in front of a non-durable executor hides the overload and then drops the work, and a
  bounded one is a durable queue with none of the durability.
- **A durable job queue in `Core`.** The thing `afterResponse` is *not*, and the thing people will ask for.
  Rejected and previously rejected: it needs a store, a schema, a retry policy, a dead-letter policy, a
  visibility timeout and an admin surface — a subsystem, not a member — and the applications that need one
  already run one.
- **`fastcgi_finish_request`'s shape** — flush the response, keep running to the end of the script.
  Rejected: it is invisible to every limit and every accounting, has no deadline, no cap and no cancellation,
  and cannot be told apart from a slow request in any metric.

## Revisiting

- **A scope object** when a real use case cannot be written as `all` or `map` — not before.
- **`Task::first`** (§ 3) the first time hedged requests across replicas are actually wanted.
- **Cancellation running a narrow, budgeted cleanup hook** if the no-user-code rule proves to be what people
  hit rather than what protects them. Any such hook needs its own reserved budget and its own zero-retry
  rule, exactly as `rule:errors/escalation-ladder`'s tiers do; it is not a relaxation of § 5, it
  is a new mechanism, and it needs its own argument.
- **Typed `callable` signatures** (`rule:types/grammar`) remove § 1's `fn`-literal
  restriction and are now blocking three separate features.
- **An isolate that outlives its parent tree** stays exactly as open as
  `rule:security/isolate-shares-nothing` left it. § 6 is not a step toward it.

## Verification

- **M5:** `Task::all` over three closures returns a shape whose three fields carry their own declared types,
  asserted by a fixture that would not type-check under `mixed`; a field holding a `callable` variable rather
  than an `fn` literal is a compile error naming the field.
- **M5:** `Task::map` preserves input keys and order under deliberately staggered completion times; `limit`
  is observed by a counter that never exceeds it.
- **M5:** one child throwing cancels its siblings and the call does not return until they are gone —
  asserted by a sibling that would otherwise write to a shared observation slot after the `catch`; a second
  throw appears in `Core\Log`, not swallowed.
- **M5:** a `deadline` fires with children blocked, the call throws `TimeoutError`, and a task-leak check
  after it shows zero live children — the same shape as
  `rule:security/isolate-shares-nothing`'s existing "a cancelled parent leaves no orphan".
- **M5:** a cancelled task's `catch` and cleanup blocks do not execute, while its arena is released and its
  refcounts drop to zero — the second half checked under `valgrind --leak-check=full` per AGENTS.md.
- **M7:** `afterResponse` work runs after the response is fully written, is charged to the same tree
  (asserted against the tree's own memory accounting, not a separate counter), and its uncaught throw
  reaches `Core\Log` with the scheduling request's trace id and no `onUncaughtThrow` invocation.
- **M7:** `Core\Response` written from inside `afterResponse` is a diagnostic at a static call site and a
  throw at a dynamic one; `Core\Session` read from inside it still works.
- **M6/M7:** `afterResponse` past `[deferred] max_concurrent` throws at the call site rather than queueing,
  and the request that called it still responds normally.
- **M8:** a `Task::all` child blocked in a `Core\Db` statement is cancelled through the driver's own cancel
  path, the call returns, and the connection is either back in a clean state or closed — never returned to
  the pool with an unread result set.
