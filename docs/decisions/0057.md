# ADR 0057 — Literal arguments to intrinsic `Core` calls are validated and prepared at compile time

- **Scope:** a closed list of `Core` methods the compiler knows by name; what it does when their
  pattern-like arguments are compile-time constants; and the rule that this never changes observable
  behaviour. Not in scope: general constant folding of arithmetic, which is an ordinary optimisation
  needing no ADR.

> **In short:** a short, closed list of `Core` methods take an argument that is really a small program — a
> regex pattern, a URI, a date-format string, a format string. When that argument is a compile-time
> constant, the compiler **validates it during checking** and **prepares** whatever the runtime call would
> otherwise build on first use, storing the result in the artifact cache. A malformed literal becomes a
> compile error naming the exact position instead of a runtime throw on the first request that reaches it.
> This adds **no syntax**: it is a property of a call whose arguments happen to be literals. The soundness
> rule is absolute — the prepared path and the runtime path share one implementation, so preparation can
> never produce a different answer, only an earlier one.

## Context

- Several `Core` surfaces accept a string that is not data but a *program*: a pattern, a format, a URI. In
  PHP every one of these is parsed on first use, every request, and a syntax error in one surfaces at run
  time on whichever code path happens to reach it — often the error path, often in production.
- Novis already has every ingredient. `rule:types/declaration` makes types known statically;
  `rule:attributes/inert-metadata` already defines "compile-time constant" precisely
  and already resolves a `Core` accessor during checking;
  `rule:packaging/an-artifact-is-one-immutable-content-addressed-file` already stores per-unit compiled artifacts. What is
  missing is only the decision that the compiler may know a few `Core` methods by name.
- The motivating case is `rule:core-classes/regex-two-tiers`. Deciding a pattern's engine tier at
  compile time is what lets `nvs check` report — or an operator's `nvs.toml` refuse — a pattern that can be
  made to backtrack. That is a security property, not an optimisation, and it is unavailable without this
  mechanism.
- The alternative shape considered and rejected in `rule:types/decimal`'s neighbourhood
  was *new syntax* — regex literals, date literals. Folding gets nearly all of the benefit with none of the
  grammar cost and none of the ambiguity (`/` is division).

## Decision

### 1. A closed list of intrinsics, maintained deliberately

The compiler holds a list of `Core` methods it recognises by fully-qualified name. The list is a **closed
set in the compiler's own source**, not an open extension point: there is no attribute, no manifest field
and no configuration by which a `Core` class, a Tier 2 subsystem or a Tier 1 extension declares itself
intrinsic. Adding an entry is a compiler change with a fixture.

The initial list:

| Intrinsic | Validated | Prepared |
|---|---|---|
| `Core\Regex::compile` | pattern syntax; engine tier (`rule:core-classes/regex-compile-time-tiering`) | the compiled program |
| `Core\Uri::parse` | RFC/WHATWG well-formedness | the parsed components |
| `Core\Time\DateTime::format` / `Core\Time::parse` | CLDR pattern syntax | the parsed format plan |
| `Core\Time\Duration::parse` | the duration grammar (`rule:types/duration`) | the resolved nanosecond count |
| `Core\Str::format` | format-string syntax; placeholder count and types against the argument list | the parsed format plan |
| `Core\Db\Connection`'s and `Core\Db\Transaction`'s `query` / `queryAs` / `execute` | placeholder count and positional-vs-named consistency against a literal params array (`rule:core-classes/db-compile-time-query-checking`) | nothing: the vendors' SQL is not parsed, and § 10 says why |

The type check on `Core\Str::format`'s placeholders is worth naming separately: it turns
`printf`-style argument mismatches — a whole family of PHP bugs — into compile errors.

### 2. What "constant" means, and what happens when it is not

An argument qualifies when it is a compile-time constant under
`rule:attributes/inert-metadata`'s existing definition — a literal, a class constant,
or an expression over them. No new notion of constant is introduced.

When the argument does not qualify, the call compiles to an ordinary runtime call with ordinary runtime
validation. Nothing is refused for being dynamic. The difference is that the three benefits — the early
error, the static tier report, the prepared artifact — are only available to the literal form, which is a
reason to prefer it, recorded here rather than left to be discovered.

### 3. Two effects, and only the second is an optimisation

- **Validation always applies.** A malformed constant is a compile-time diagnostic pointing at the exact
  offset inside the literal, in the same shape any other diagnostic takes.
- **Preparation applies where there is something to prepare.** The derived artifact — a compiled regex
  program, a parsed format plan — is built during compilation and stored with the unit in the artifact
  cache, so the runtime call uses it directly.

**Preparation is not evaluation.** A call whose result depends on runtime state is not evaluated at compile
time; only the state-independent part is. `$now->format("Y-m-d")` prepares the format plan and
formats at run time, because the instant, the timezone and the calendar are all runtime values. The
narrower case where the whole call is constant — `Core\Str::length("abc")` — folds to its value, but that is
ordinary constant folding and not what this ADR is for.

### 4. Preparation never changes behaviour

The prepared path and the runtime path **share one implementation**. The compiler calls the same pattern
compiler, the same URI parser and the same format-plan builder the runtime would have called, and stores
its output. A divergence between the two would be a bug in the same class as an incorrect optimisation, not
a permitted difference, and § *Verification* tests for it directly.

Because preparation depends only on the literal and on the compiler's own version, it is keyed by the
artifact cache exactly as any other compiled output is
(`rule:packaging/an-artifact-is-one-immutable-content-addressed-file`) — including on the compiler-environment component of
the cache key, so a prepared artifact from a different compiler build is a cache miss rather than a
mismatch.

### 5. Probes

A fully folded call is no longer a call, so `rule:testing/debug-probes`'s
per-call probe does not fire for it, exactly as for any constant-folded expression. The enclosing
statement's probe is unaffected, so line coverage is unchanged. A *prepared* call — the common case — is
still a call and still probes normally.

## Consequences

- **A small, permanent coupling between the compiler and the stdlib.** The compiler knows four `Core`
  method names. This is the real cost of the ADR, and it is bounded by § 1's closed-list rule: the coupling
  grows only when someone adds an entry deliberately, never by a library declaring itself special.
- **`nvs check` gets meaningfully stronger** without new syntax: malformed patterns, malformed URIs,
  malformed format strings and `printf`-style argument mismatches all move from run time to check time.
- **`rule:core-classes/regex-compile-time-tiering` becomes implementable.** Without this, "refuse backtracking
  patterns" would be a runtime check that has already lost the argument.
- **Pattern compilation leaves the request path**, which is a latency win (priority 3) but a secondary one;
  the early diagnostics are the reason this exists.
- **Third-party code cannot participate.** An extension author who wants their pattern-shaped argument
  validated early cannot get it. That is deliberate — an open intrinsic mechanism would let a manifest ask
  the compiler to run arbitrary preparation, which is a much larger surface than four names in a list.

## Alternatives rejected

- **Regex literal syntax (`/pattern/i`) and date literals.** The most ergonomic form, and it makes the
  compile-time treatment obvious at the call site. Rejected: `/` is division, and the disambiguation rules
  other languages use for this are a recurring source of parser bugs; the grammar cost is permanent while
  the benefit over folding is presentational.
- **An open intrinsic mechanism** — an attribute or manifest field by which any library declares a method
  foldable. More general, and it would let Tier 2 subsystems and extensions benefit. Rejected on priority 1
  and 4: it turns "the compiler knows four names" into "the compiler runs library-designated code during
  compilation", which is both a larger attack surface and a much harder thing to reason about.
- **Do nothing; validate at run time as PHP does.** No coupling at all. Rejected: it leaves `rule:core-classes/regex-two-tiers`'s
  central security control unimplementable, and it keeps a family of errors that are statically decidable
  in the class of errors discovered in production.
- **Fold eagerly, evaluating whole calls where possible.** Simpler to describe than § 3's split. Rejected:
  the calls worth touching mostly depend on runtime state, so an eager rule would either be wrong or would
  need exactly the same carve-out, stated less clearly.

## Verification

- **M8:** a fixture per intrinsic — a malformed literal pattern, URI, and format string are each compile
  errors pointing inside the literal; a `Core\Str::format` call with a placeholder/argument mismatch is a
  compile error; the same calls with a runtime-assembled argument compile and fail at run time instead.
- **M8:** a differential test asserting § 4 directly — for a corpus of literals, the prepared artifact and
  the artifact the runtime path builds from the same string are byte-identical.
- **M8:** an artifact-cache test that a prepared entry produced by a different compiler build is a cache
  miss, not a load.
- **M8:** a coverage test asserting § 5 — a statement containing a folded call is still reported as
  covered.
