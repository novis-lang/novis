# ADR 0271 — every served entry runs under the `[[app]]` blocks that match its own file, and the door under the host's snapshot

- **Scope:** which configuration snapshot a served request, a scheduled fire and a queued job run
  under, what one publish holds, and which keys are read per mount and which once for the process.
  What an `[[app]]` block may write, and how blocks fold, stay
  `rule:config/an-application-is-its-entry-file-path`'s and
  `rule:config/every-matching-app-block-applies-least-specific-first`'s.
- **Depends on:** [0200](0200.md), [0104](0104.md), [0078](0078.md), [0097](0097.md).
- **Validated by:** the tests the goal `serve-per-mount-config` names in
  `crates/nvs-config/tests/snapshot.rs` and `crates/nvs-cli/tests/per_mount_config.rs`, among them
  `a_mount_cannot_use_a_capability_only_another_applications_block_grants`, and the attack under
  `tests/hostile/tools/config/app-per-application-blocks/`.

> **In short:** `nvs serve` built one snapshot for the process and handed it to every mount, so a
> second application's `[app.limits]`, `[app.capabilities]`, `[app.log]`, `mode` and `origin` were
> ignored, or it ran with the first application's grants. One publish now holds the host's snapshot
> and one snapshot per entry file, folded from the blocks that match that file. A request, a scheduled
> fire and a queued job run under their own file's snapshot; the door, and everything it reads before a
> mount is selected, reads the host's. The named `<file>` selects no configuration any more: over a
> mount table it only has to be one of the mounted entries.

## Context

### 1. One snapshot served every mount

`crates/nvs-cli/src/serve.rs` holds one `nvs_config::Current`, built for the named file or, with
none, as `Snapshot::host` (`crates/nvs-config/src/snapshot.rs:163`). The door clones it at each
request's start and writes it onto the request's context, so every mount reads one application's
blocks or none ([0200](0200.md) § 4). A per-application grant is a security boundary
(`rule:http-server/a-mount-carries-no-policy`), and a boundary that holds for one application of a
host and not the others is a request-isolation defect. [0200](0200.md) § *Revisiting* named this
change.

### 2. `nvs run` already had the right shape

`nvs run <file>` builds the snapshot for its own file, and `rule:config/an-application-is-its-entry-file-path`
says an application is that path. A served request has an entry file too: the row the mount table
selected, or under `dispatch = "path"` the file the request resolved to. Nothing but the snapshot's
holder stood between the server and the same answer.

## Decision

### 1. Per mount is what an `[[app]]` block may write; process-wide is everything else

An `[[app]]` block holds `root` or `entry`, `mode`, `origin`, `[app.limits]`, `[app.limits.hard]`,
`[app.capabilities]` and `[app.log]` (`Snapshot::folded`, `crates/nvs-config/src/snapshot.rs:169`).
Those are read per request, off the snapshot the request's context carries:

- `[limits]` and `[limits.hard]`, and `cancel_on_disconnect` and `disconnect_grace` with them;
- `[capabilities]`, `[log]`, `mode` as `Core\Env::mode` reads it, `origin`, `Core\Config::get`, and
  the process cache tier's scope.

Every other key is read once for the process, or by the door before a mount exists, from the host's
snapshot: `[server]` and its admission arithmetic, waits and connection bounds; `trusted_proxies`,
`[http.headers]` and `[http.cors]`; `dispatch`, `static`, `health_path` and the mount table;
`[opcache]`; `[http.client.tls]`; `[control]`; `[trace] sample`, `[http] csrf_key` and the session
cookie name; `[mode] default` and `ceiling` as startup values; `[[schedule]]`, `[queue]` and `[db.*]`.

A key neither list names is process-wide until a record says otherwise, because a value read before
a mount is selected cannot be per mount.

### 2. One publish is the host's snapshot and the way from an entry file to its own

`Current` holds one value per publish: the host's snapshot, and a map from canonical entry file to
that file's snapshot. `Current::load` keeps returning the host's, so the callers that read
process-wide keys do not move; a second method returns the publish. The host and its entries are
swapped together under the one lock, so no request reads from two publishes.

### 3. One snapshot per chain of blocks

An entry's snapshot depends only on which blocks match it and in what order
(`app::matching`, `crates/nvs-config/src/app.rs:436`), so every entry that matches the same chain
shares one `Arc`, and an entry no block matches gets the host's `Arc` itself. The fold runs over the
host's tree **after its `Boot` carry**, so a `Boot` key reads the running value in every snapshot of
the publish.

### 4. One generation per publish

Every snapshot of one publish carries the host's `generation`. The database pool keys on it, so a
server with many applications keeps one pool per `[db.<name>]`, and the drain after a reload keeps
reading one number. The process cache tier stays distinct per application, because its key also
names the block. If a test shows a pooled connection carrying state from one application to another,
the pool keys on the application as well, and the record that does it says what it spends.

### 5. Matching runs once per entry per publish

Eagerly for every mounted entry when the publish is built, so a block that does not fold for one of
them refuses the boot or the reload with the existing `E0601`; lazily, and then kept in the publish,
for a file first compiled later — a `dispatch = "path"` file, or a scheduled or queued script. Never
per request (`rule:config/every-matching-app-block-applies-least-specific-first`).

### 6. A file is matched as itself

Under `dispatch = "path"` the file a request runs is the entry whose blocks apply, not the row's
`entry`, because an application is its entry file path. A scheduled fire and a queued job run under
the blocks of their own script. A spawned script runs under its parent's snapshot, as before
(`Ctx::isolate`), and never under the blocks of the file it spawns: a child narrows its parent and
never widens it.

### 7. The named file selects no configuration

`nvs serve <file>` over a mount table still requires the file to be among the mounted entries, and
that is now its only role. A start with no file and a start with one serve the same configuration,
and a reload resolves the publish whole either way. `nvs ctl config` reports the host's snapshot.

No key and no diagnostic code is added.

## Consequences

- **Performance:** one map lookup and one `Arc` clone per request, after the mount is selected, with
  no syscall and no allocation. The door's policy is derived from the host's snapshot alone, so
  alternating mounts never re-derives it.
- **Memory:** one snapshot per distinct chain of matching blocks per publish, kilobytes each and
  bounded by the configuration, not by traffic; one map entry per entry file resolved under that
  publish, bounded by the files on disk as the compiled-unit cache is; two publishes alive during a
  swap, plus one per in-flight request still holding an older one.
- **Usability:** a host of many applications gets each application's own limits, grants, log,
  `mode` and `origin` with no file named, which is what the `[[app]]` block already promised.
- **Simplicity:** the named file loses its second meaning, and a served entry configures the way
  `nvs run` of the same file does.
- **Admission:** the per-request memory the admission arithmetic reserves is the largest any
  snapshot of the publish can reach — the global `[limits]` and every block's — which the roster
  gives without an entry.

## Alternatives rejected

- **Per-mount keys on `[[server.mount]]`.** A mount routes and carries no policy
  (`rule:http-server/a-mount-carries-no-policy`), and policy keyed on a mount would not reach `nvs run`.
- **One snapshot per entry file, unshared.** Correct, but it spends a snapshot per file where most
  files share a chain, and a host whose blocks match nothing would hold one copy of the global tree per
  file.
- **A generation per snapshot.** It would open one database pool per application for every
  `[db.<name>]`, multiplying connections with the number of applications, and the drain would have to
  track a set of numbers. Nothing yet shows a pooled connection carrying state across applications.

## Verification

The Stage 2 to 5 checks of the goal `serve-per-mount-config`: the published set and its sharing in
`crates/nvs-config/tests/snapshot.rs`; two mounts under one server, a reload and a rescan in
`crates/nvs-cli/tests/per_mount_config.rs`; a scheduled fire and a queued job under their own
script's blocks; and the attack, in which a program uses, sets and spawns its way towards a right only
another application's block grants, and every attempt fails.
