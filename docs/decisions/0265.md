# ADR 0265 — A request whose client goes away runs to its end, and cancellation at the drop is turned on per method

- **Scope:** what a served request does when its connection drops before its response is on the
  wire: the default, the two `[limits]` keys that change it, the bound that replaces the one
  cancellation gave, and what a write to the gone client returns. Upgraded connections (`Core\Sse`,
  a WebSocket) are not requests and are not decided here, and neither is a runtime switch or a way
  for a script to learn its client has gone.
- **Depends on:** [0106](0106.md), [0072](0072.md), [0074](0074.md).
- **Validated by:** the disconnect tests in `crates/nvs-server/src/serve.rs` and the key tests in
  `crates/nvs-config/src/tree.rs`.

> **In short:** a request whose client disconnects is no longer cancelled at the drop. It runs to its
> end under every limit it already has, its writes succeed and are discarded, and it keeps its
> admission place until it ends. `[limits] cancel_on_disconnect = [...]`, default `[]`, lists the
> methods that are still cancelled at the drop. `[limits] disconnect_grace`, default `"30s"`, bounds a
> detached request that has no `wall_time`; a request with a `wall_time` has that one limit. Both
> keys are `System` keys and may be written in `[app.limits]`. The rule
> `http-server/an-abandoned-request-is-cancelled-at-the-drop` is renamed to
> `http-server/a-request-outlives-a-client-that-goes-away` and rewritten.

## Context

[0106](0106.md) made the drop of a connection cancel the request tree at the next safepoint, to close
the FastCGI failure where an abandoned request holds a worker until `max_execution_time`. That failure
does not exist here: a parked request costs a pooled stack, not a worker. What the cancellation does
cost is correctness. A user who refreshes, navigates away, closes a tab or submits a form twice
abandons a request, so a disconnect is the everyday case. Cancelling then stops a script between two
writes that share no transaction, and leaves half-written data. A PHP developer does not expect that:
PHP-FPM learns of a disconnect only at the next output, and with output buffering most PHP pages
write nothing until the end, so in practice a PHP script finishes its work.

## Options considered

1. **Keep cancellation as the default** and document it. Rejected: the everyday case breaks data,
   and the fix every application would need is the same one line.
2. **Completion for every request, no opt-out.** Rejected: a deployment serving expensive read-only
   searches loses nothing by stopping them, and wants the capacity back.
3. **Completion by default, cancellation per method in `nvs.toml`** — chosen. The method is what
   says whether stopping is safe: a `GET` or `HEAD` that writes nothing can stop, a `POST` should not.
4. **Per route or per request.** Rejected for now: a route table is not a configuration concept here,
   and a per-request switch is a runtime method this decision does not add.

## Decision

### 1. The default is completion

A request whose connection drops before its response is on the wire is detached: an owner on the
same core runs it to its end and discards its result. It keeps its admission place until it ends,
because a place given back at the drop breaks tier C of
`rule:http-server/a-requests-blast-radius-is-bounded-at-four-tiers` — a client could open a request,
disconnect and repeat until the core runs unbounded work. After-response work runs as for any request
whose frame returns.

### 2. `cancel_on_disconnect`

An array of method names under `[limits]` and `[app.limits]`, default `[]`. A listed method is
cancelled at the drop exactly as before, under `rule:concurrency/cancellation-runs-no-user-code`. A
name is matched exactly and case-sensitively, as HTTP matches methods. A name that is not a valid HTTP
token is refused at load naming the key, and so is a repeated name. Any token is allowed, so a custom
method can be listed.

### 3. `disconnect_grace`

Cancellation was the only bound on a request parked on a dependency that never answers, because
`wall_time` has no default. Completion removes it, and
`rule:http-server/an-unsafe-or-unbounded-default-is-a-defect` requires one back. `disconnect_grace`
is a duration under `[limits]` and `[app.limits]`, default `"30s"`, and `false` and `0` are refused as
`[server]`'s waits refuse them. It applies only to a request with no effective `wall_time`: at the
drop such a request gets a deadline of the drop plus the grace. A request with a `wall_time` gets
nothing new, so a long job whose client left is not cut short by a second limit. `wall_time` is a
`Runtime` key, so the deadline follows it after the drop, and a request always has exactly one of the
two bounds. A request past its grace is cancelled as a listed method is. The key has no
`[limits.hard]` ceiling, because no request may set it.

### 4. Writes to a gone client

Every write to the response, buffered or streamed, succeeds at once and its bytes are discarded.
`Core\Response\Stream::write` stops throwing a `RuntimeError` when the client closed the connection
or did not read a part before the send timeout: a send timeout closes the connection and counts as
the client having gone, and from then on a write returns at once without parking. A streaming script
is stopped by its `wall_time`, its grace or a listed method, never by a throw. A read of the request
body after the drop fails as any failed read does.

### 5. The drain, the log and what is not added

A graceful drain waits for a detached request as for an attached one, up to `drain_timeout`, then
cancels what is left. The request's log line and root span record how it really ended and that its
client had gone. There is no `Core` method that changes either key for one request, and none that
tells a script its client has gone.

### 6. What is spent

- **Performance:** nothing on a request whose client stays. A detached request uses its core until
  it ends.
- **Memory:** a detached request keeps its heap until it ends, reaches its `wall_time` or, with none,
  `disconnect_grace` — per request, O(in-flight), and under its own `memory` cap.
- **Usability:** a script's writes finish as a PHP developer expects, and a disconnect no longer
  leaves half-written data.
- **Simplicity:** two keys, and the default needs neither.

## Consequences

The key names and their place in `[limits]`, the `30s` default, a buffered write succeeding silently,
a send timeout counting as a gone client, and the drain treating a detached request as an attached
one are calls made with this decision and open to the user's review; the default and the per-method
switch are the user's own. A request cancelled for either reason still runs no user code.

## Alternatives rejected

- **A `Core` method like `ignore_user_abort()`.** It makes completion something each script must
  remember, which is the wrong default for the everyday case.
- **Giving the admission place back at the drop.** It turns a disconnect loop into unbounded work on
  one core.
- **A grace on every detached request, `wall_time` or not.** Two limits on one request, and a long
  job cut short because its client left.
