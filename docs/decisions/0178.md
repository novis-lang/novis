# ADR 0178 — a finished response is a fourth ending beside `exit`, and every `finally` runs on the way out of it

- **Scope:** the fourth ending — what it means for a response to be *finished* rather than
  terminated, which class carries the member that says so, and why the unwind that carries it runs
  every `finally` between the frame that asked and the request root. It re-opens neither `exit`'s
  semantics nor the escalation ladder [0020](0020.md) owns, and decides nothing about what a response
  body holds, which [0176](0176.md) owns.
- **Depends on:** [0127](0127.md), [0072](0072.md).

> **In short:** a program ends its response from any frame with `Core\Script::finish()`, and what
> that names is an **ordinary** end: the unwind runs every `finally` on the way to the request root,
> the exit queue fires, and `Core\Task::afterResponse`'s work drains. `exit` is the other thing — a
> process-termination keyword whose status is what the host is about to report — and it stays exactly
> as it is: no `finally`, no deferred work. The two sit beside each other because they answer
> different questions, *this program is over* and *this response is done*, and a program that only
> has the first reaches for it when it means the second.

## Context

Today the only way to stop a request early is `exit`. It answers `Err(Fault::Pending(EXITED))`
(`crates/nvs-runtime/src/helpers.rs:2591`) and propagates the way a `FATAL` does — no `catch` sees
it and no `finally` runs, which is PHP's own `exit`
(`crates/nvs-runtime/src/abi.rs:49-58`). Both drain gates on the served path test
`completion.ok` (`crates/nvs-host/src/isolate.rs:818`, `:884`), and an `EXITED` fails both, so a
request's `afterResponse` registrations are handed back unrun with its context
(`crates/nvs-runtime/src/ctx/mod.rs:1296`). That is
`rule:concurrency/after-response-outlives-the-connection` working exactly as written: the status is
what the host is about to report, and script running over it would lose one of the two.

So the gap is not that `exit` is wrong. It is that a program with nothing left to report and cleanup
still to run has no other way to stop, and the PHP reflex `echo json_encode($x); exit;` is how that
gap is reached — silently, with no diagnostic, dropping both halves of a request's cleanup on a line
that reads like a return.

## Decision

### 1. The ending sits beside `exit`, not inside it

`exit` is a *process-termination* keyword (`rule:statements/exit-is-the-only-termination-keyword`),
and `docs/adr/README.md` § *Decisions taken at project start* owns why its status is one of its own
rather than a `FATAL` carrying a code. Widening it — an `exit` that sometimes runs `finally` because
a host is a server — would make one keyword mean two things and make which one it means a property
of the deployment. The fourth ending is therefore a member, decided here, and `exit` is untouched.

The two are distinguishable everywhere they are observed: the exit queue is fired by both and its
report says which ending it was, so a hook that flushes a buffer whatever the ending keeps working
and a hook that only cares about termination can still tell. `rule:observability/three-endings-fire-the-exit-queue`
already sanctions this shape — *a future termination kind that should fire the queue is a new case on
this queue* — and a second queue would be the wrong answer to the same need.

### 2. Every `finally` runs, and that is the line between the two

A `finally` body lives behind the handler edge: a fallible call site tests `status != OK` and its
landing block asks exactly one further question, `status == THROWN`
(`crates/nvs-codegen/src/emit.rs:3473`) — everything else releases the frame's locals and leaves. An
ending spelled as a new status therefore inherits `exit`'s mechanics for free and skips every
`finally`, which is the one property this ending exists to have. It is not a status.

That is the whole line between the two endings. A design that reaches the root without running every
`finally` on the way is `exit` with a different name, and is refused on that ground alone: the
migration trap this closes is a `finally` that does not run, so an ending that does not run one
closes nothing. The unwind is raised on the throw path, which is where `finally` runs and where the
region's re-propagate already carries a pending value out frame by frame, and it carries a value no
`catch` arm admits.

### 3. The member is `Core\Script::finish()`

Not `Core\Response::finish()`. The moment this brings forward is the one
`rule:concurrency/after-response-outlives-the-connection` already defines — the request task's own
frame returning — and that trigger is host-neutral: under a server it is the response being written,
under `nvs run` it is the end of the script. A member on `Core\Response` would mean nothing under
`nvs run` and need a second spelling there, which is one moment with two names. `Core\Script` is
where the endings already live, beside `onExit`.

## Consequences

**What this spends, stated rather than weighed.** Priority 4 pays for priority 2: a fourth ending and
one refusal are new language surface on a class that already carries the endings, bought to close a
migration trap that is silent today. It costs nothing on the request path of a program that does not
use it — the unwind is the one a `throw` already pays for, and no new test appears at a call site.
