# ADR 0185 — The extension-host run is on every acceptance sweep, isolated from the developer's editor, and never answered from the memo

- **Scope:** where the extension-host tier runs, what makes running it beside a working developer
  safe, and why its verdict is never taken from the acceptance memo. Not in scope: what the host
  suite asserts, which the goal's own stages fix case by case; the headless tier, which is unchanged;
  publishing a `.vsix`, which `rule:ide/one-server-two-thin-clients` § *Revisiting* keeps open; a
  pixel tier, which stays refused.
- **Depends on:** [0099](0099.md), which created the two-tier rule and put the host run in CI alone;
  [0101](0101.md), which amended it for the concealment surfaces; [0143](0143.md) for the lanes the
  CI half runs in; [0004](0004.md) for the ordering a minute of wall-clock is spent under.
- **Validated by:** the host suite's own first case, `runs in a throwaway profile and never the
  developer's`, which asserts the app root, the user-data directory and the open folder; and the
  three `command` checks that drive `npm run test:host` from the acceptance list.

> **In short:** the extension-host suite runs on every acceptance sweep — on the Windows desktop the
> loop runs on, and in CI under `xvfb-run -a` — rather than in CI alone. What made it unsafe beside a
> working developer was never the display: it was a second instance of *their* install reading *their*
> profile. A downloaded pinned build, a throwaway `--user-data-dir` and `--extensions-dir`, and a
> copied fixture folder remove that, and the window it opens for about a minute is the price. Its
> verdict is never answered from `.loop/goal-green.json`, because the run reads state no partition of
> the tree hashes, and a stale green there claims an editor launched when none did.

## Context

`rule:ide/headless-gates-the-loop-the-host-run-gates-the-milestone` put the extension-host tier in CI
only, and gave two reasons: an unisolated second instance attaches to the editor the developer already
has open and exits with no results, and a test that writes a setting writes it into that developer's
own `settings.json`. Both are true. Neither is a property of running an editor — they are properties
of running *their* editor against *their* profile.

The cost of leaving it there is that the tier proving activation, the Tasks, the status item, the AST
panel, the concealment and the semantic legend runs nowhere the loop can see. CI is not running at all
while a billing block stands, so "CI only" currently means "never", and the surfaces M4B's *Verify*
paragraph names would be reported done on a suite nothing has executed.

## Investigation

`@vscode/test-electron`'s `runTests` downloads a pinned build and caches it under `.vscode-test/`,
which `.gitignore:97` already ignores. Whether that pinned stable build starts cleanly beside the
user's own running stable VS Code on this machine is **not checked**; if it does not, the answer is a
pinned Insiders build, never a dropped isolation flag.

The memo is the half that had to be read rather than assumed, and what the tree holds is not what the
goal's own comment says it holds. `tools/loop.py:1726`'s `reads_of` gives a `command` check whose
`argv[0]` is `npm` and whose `cwd` is under `editors/` the `EDITOR_READS` partitions
(`tools/loop.py:1706`) — `crates` and `editors`. The host checks are written exactly that way, so as
things stand they *are* memoized, and a session that touched only `docs/` would have its host verdict
answered from `.loop/goal-green.json` without an editor starting. The `memoize` key those checks could
carry is accepted by the schema and read by nothing (`tools/loop.py:1859`).

The memo's argument is that a deterministic check over bit-identical inputs cannot reach a different
verdict. That argument holds for every check in the list before this one, because their inputs are
tracked bytes plus the compiler version. The host run's are not: `NOT_INPUTS` (`tools/loop.py:1701`)
prunes `.vscode-test/` and `node_modules/` from the walk, and `partition_ids` hashes nothing git
ignores on purpose (`tools/loop.py:2364-2368`) — hashing the sweep's own build output made every run a
new tree and the memo never fired. So the pinned editor build, the installed packages and a usable
display are all inputs the hash cannot see. This is the first check in this repository whose verdict
depends on a downloaded build rather than on the repository.

## Options considered

1. **Leave the tier in CI, unchanged.** Free, and proves nothing while CI is blocked.
2. **Run it locally and let it memoize on `crates` and `editors`.** Cheapest, and wrong in the one
   direction that matters: the sweep would report a green host run on a machine where the pinned build
   had been deleted.
3. **Hash `.vscode-test/` and `node_modules/` into a partition.** Makes the memo's argument true again
   by widening what it sees — and re-runs everything on every machine, which is the failure
   `partition_ids` already records for the packaged `.vsix` and the queue's database.
4. **Never answer the host checks from the memo**, and say so with the key the schema already has.

## Decision

### 1. The host tier runs wherever a developer does

It is on the acceptance list as `npm run test:host`, on this machine's native leg and in CI on Linux
under `xvfb-run -a`. Locally that opens a VS Code window for about a minute on each acceptance sweep,
and that window is accepted rather than worked around.

### 2. Isolation answers both of the reasons the rule gave

A downloaded pinned build rather than the user's install; `--user-data-dir` and `--extensions-dir`
under `.vscode-test/`; `--disable-extensions`; and a copy of `test/host/fixture/` as the workspace
rather than the repository. The attach-and-exit reason is a second instance of the *same* install
sharing a user-data directory, and a build with its own profile is not one. The `settings.json` reason
is a write into the developer's profile, and the only `settings.json` any host test can reach is the
throwaway one — which is also the only place `nvs.path` is written, so no host run edits a setting a
person will see again.

### 3. The verdict is never answered from the memo, and `memoize = false` is what says so

The `memoize` key becomes load-bearing in one direction: `false` means `remembered()`
(`tools/loop.py:2432`) returns `False` for that check, so it runs on every sweep whatever the tree
hashes to. `true` and absent keep today's behaviour, and no check in the goals directory carried
`false` before this decision, so no existing verdict changes. The three host checks carry it.

The rule this makes room for is that a check whose inputs include something outside the tree opts out
rather than being given a wider partition to hash — widening the hash to cover a downloaded build
would cost every other check its memo to fix one.

### 4. What it spends

Nothing at run time: no byte of the binary, the server or a request changes. On an acceptance sweep it
spends one editor launch — a window and about a minute — that a memo could have skipped, plus the
pinned build and throwaway profile under `editors/vscode/.vscode-test/`, once per machine. Under
[0004](0004.md)'s ordering that minute buys correctness of the verdict, which outranks it. A stale
green is the one outcome worse than the window: it reports the surfaces of M4B as proved by a suite
that did not run.

## Consequences

- The rule's title and body are rewritten whole and its id is unchanged: renaming a rule under its
  citations is a tree-wide sweep that buys nothing here. The headless half of the rule is untouched —
  it still runs every iteration, with no editor, no display and no network.
- `.loop/goal-green.json` no longer carries a host verdict, so the sweep's cost line grows by one
  editor launch on every session rather than on the sessions that touched `editors/`.
- The host tier is on the acceptance list, so a goal is not reached while it fails. That is the point:
  the milestone's editor claims now have something that fails when they are broken.

## Alternatives rejected

- **A pixel tier.** Colour is asserted through the editor's own commands —
  `_workbench.captureSyntaxTokens` for the TextMate layer, `vscode.provideDocumentSemanticTokens` and
  its legend for the semantic one — because a screenshot comparison fails on a font, a theme and a
  scaling factor without a single scope being wrong.
- **A test surface with a setter on it.** What `activate` returns stays read-only and exposes nothing
  another extension cannot already read; a function on it that changed state would let any installed
  extension unconceal a secret, which trades priority 1 for test convenience.
- **Skipping the local run when a display is busy.** A tier that runs only when convenient is a tier
  whose green means nothing, and the conditional would be invisible in the sweep's output.

## Revisiting

If the pinned stable build cannot start beside the user's own running stable VS Code, pin an Insiders
build; the isolation flags are not what gives way. If a future check's inputs likewise sit outside the
tree, it carries `memoize = false` for the same reason rather than the memo learning to hash another
directory.

## Verification

`python tools/rules.py --show ide/headless-gates-the-loop-the-host-run-gates-the-milestone` prints the
rewritten rule naming `test:host`. The host suite's first case asserts its own isolation — `env.appRoot`
under `.vscode-test/`, the user-data directory the throwaway one, the open folder the fixture copy —
and the three acceptance checks read `host: N passing, M failing` off the launcher's own stdout on both
platforms. CI's `extension-host` job is proven by a read of `.github/workflows/ci.yml` while the
billing block stands; goal `gap-zero`'s green run is what proves the job itself works.
