# ADR 0106 — Nothing a request can send terminates or wedges a worker

- **Scope:** decides what happens on the failure paths that reach a worker *around* the mechanisms already
  in place — a process `abort()`, a `SIGSEGV` raised by the engine's own recursion, a `SIGBUS` from a file
  that moved under a mapping, an accept loop that spins, a core that is alive but never returns. Decides the
  admission arithmetic that makes a memory cap mean something, and names the one fault class that survives
  all of it. Does **not** re-decide how a `FATAL` is reported once it reaches a boundary
  ([0020](0020.md)), which text a parser refuses
  ([0095](0095.md)), what a proxy owns
  ([0074](0074.md)), or the regex engine's own bound
  ([0056](0056.md)).
- **Depends on:** [0002](0002.md) — this ADR extends its containment rule outward and has
  nothing to decide without it.

> **In short:** `catch_unwind` contains a panic. It does not contain `abort()`, it does not contain a
> signal, and it does nothing at all for a worker that is alive and never makes progress — and those three
> are the only ways left for one request to cost more than itself. So: containment moves outward from the
> helper to the worker task; nothing on a teardown path may panic and teardown stops recursing; every
> depth and every duration a request can drive is bounded on the *engine's* stack and inside a *single*
> helper, not only between them; a core never blocks on a syscall; and admission is arithmetic against the
> memory budget rather than a number someone picked. What is left after that is **one** class — a
> memory-safety fault in `unsafe` code or a Cranelift miscompile — which is stated as a residue rather than
> hidden, because the boundary that would contain it does not contain the thing that actually matters
> about it.

## Context

Four decisions already stand between a request and its neighbours, and each closes a real path.
`rule:errors/propagation` contains a runtime panic to one request at the ABI.
`rule:errors/escalation-ladder` gives every `FATAL` a path that ends in a log line, including
the call-stack limit that would otherwise be a `SIGSEGV`.
`rule:errors/ambiguous-input-refused` refuses text whose spelling and meaning come
apart instead of repairing it. `rule:http-server/two-deployments-and-nothing-a-proxy-owns` caps in-flight
work and waits for nothing forever.

None of them says what happens on the paths that go *around* all four. The audit that produced this ADR
walked every request-reachable path in the design and found that they fall into three shapes, and only
three:

- **A process `abort()`.** `panic = "unwind"` is load-bearing, but it is not sufficient: a panic raised
  while a panic is already unwinding aborts unconditionally, as does Rust's default allocation-failure
  handler. Both are reachable from request-sized data — the first through any `Drop` on a teardown path,
  the second through any engine-side buffer that grows with input.
- **A signal.** `rule:errors/on-limit` bounds recursion through *Novis* frames,
  which is the case it was written for. Request data also drives recursion through *Rust* frames — a
  nested document handed to a decoder, a nested expression handed to the parser, and a nested value graph
  handed to `Drop` at request end, which runs after the request is over and therefore cannot be refused by
  any limit that acts on the request. A mapped file that is replaced underneath a reader is the same shape
  with a different signal.
- **A core that never comes back.** Nothing here crashes. A safepoint bounds Novis code between helpers, but
  a helper whose runtime is O(input) is a single call with no safepoint inside it, and a blocking syscall
  on a thread-per-core runtime stalls every coroutine pinned to that core.
  `rule:core-classes/regex-two-tiers` already named this shape exactly right for one member — a
  catastrophic pattern "is not a slow request; it is a lost core" — and the observation generalises past
  regex.

The requirement driving this ADR is that the answer be **falsifiable**. "The server is stable" cannot be
tested; a tier that names what may and may not happen can be.

## Decision

**A request's blast radius is bounded by construction at four named tiers, and the residue below them is
one stated fault class rather than an unexamined gap.**

### 1. The guarantee, in four tiers

| Tier | Statement | Held by |
|---|---|---|
| **A** | No input a request can send terminates a worker process. | §§ 2, 3, 4, 11, 12 |
| **B** | No request causes another to fail, stall, or observe its data. | §§ 5, 6, 7, [0004](0004.md) |
| **C** | No request consumes beyond its own budget, a core's time included. | §§ 5, 6, 13 |
| **D** | *Residue.* An engine fault may terminate the process; the service recovers under its supervisor in about a cold start, and the requests in flight at that moment are lost. | § 14, [0093](0093.md) |

Tier D is written down because a residue that is named can be measured, argued with, and revisited. The
one that is not named is the one that gets discovered by an operator.

### 2. Containment does not end at the helper

`rule:errors/propagation`'s `nvs_helper!` wrapper contains a panic raised beneath a JIT frame.
Code that runs on a worker with no request beneath it — the accept loop, the HTTP reader, the compiled-unit
cache index — is outside it. **The worker task's root is wrapped in `catch_unwind` as well**, and the
wrapper is applied by the task-spawning helper rather than written per call site, for the same reason
`nvs_helper!` exists.

Two outcomes, split on whether a request owns the fault:

- **Beneath a request root** — the request fails through [0020](0020.md)'s ladder as
  an internal panic, which § 5 of that ADR already routes past user code. The worker continues; its other
  in-flight requests are untouched, because everything the failing request owned is in an arena released
  wholesale.
- **Outside any request** — there is nothing to charge it to and the state that faulted is shared, so the
  worker is **retired**: it stops accepting, its in-flight requests are allowed to finish under the
  existing drain, and a replacement is started. Retiring rather than continuing is the conservative
  reading of [0020](0020.md) § 5 — after an internal panic the runtime's own state
  is what cannot be trusted — applied to shared state instead of request state.

This costs nothing on the path that does not panic, and is one wrap per *task* rather than per call.
`docs/perf/userland-gap.md` § *Two things ruled out* holds the measurement and the instruction not to
re-investigate it.

### 3. No path reaches `abort()`

`panic = "unwind"` prevents the abort that `panic = "abort"` would cause. It does not prevent the two that
remain, and both are reachable from request-sized data:

- **Nothing on a teardown path may panic.** A panic during unwinding aborts the process, so a `Drop` that
  can fail turns a contained fault into an uncontained one. This is a rule, and a rule every contributor
  must remember is the shape [AGENTS.md](../../AGENTS.md) warns against — so it is made mechanical by the
  next bullet rather than left as discipline.
- **Teardown is iterative, never recursive.** A value graph is released by draining an explicit worklist,
  not by `Drop` calling `Drop`. This removes the panic-during-unwind surface along the only path that
  handles unbounded user-shaped data, and independently removes the stack overflow that a deeply nested
  graph would otherwise cause at request end — the one depth that no request-level limit can refuse,
  because it is reached after the request has finished. Its cost is one worklist allocation per teardown,
  which is a fraction of a percent of any request that allocated enough to need one, and it is not
  obviously slower than recursion in the first place.
- **An allocation sized by request data is fallible.** Every engine-side buffer that grows with input uses
  `try_reserve` and fails the request rather than the process. The honest bound on this rule: it covers
  allocations that scale with input, which is where an attacker has leverage. It does not make the whole
  standard library fallible and does not claim to.

### 4. Depth is bounded on the engine's stack, not only on the script's

`rule:errors/on-limit` bounds recursion through Novis frames, where every user call
is a real machine frame. The same request data recurses through *engine* frames in the decoders and in the
parser, where the § 1 mechanism does not reach: its check is emitted at Novis function entry, and a decoder's
recursion has no Novis frames in it at all.

**Every engine-side recursive descent over request data carries an explicit depth counter and refuses past
its limit**, with the refusal reaching the caller as an ordinary catchable failure — a `413`-class
condition for a body, a diagnostic for source. The limit is an `nvs.toml` directive per
[0064](0064.md), one per decoder rather than one shared number, because the
depth that is reasonable for a JSON body is not the depth that is reasonable for a source file.

The default for `Core\Json` is **512**, which is `json_decode`'s own default in PHP. Chosen for priority 2
rather than for any property of the number: a migrated application that decodes a 300-deep document keeps
working, and one that would have failed on PHP fails here too, at the same place. This is the ADR's one
user-visible behaviour change, and it is visible only to a program that was already at PHP's edge.

### 5. Time is bounded inside a helper, not only between helpers

The safepoint poll bounds Novis code because it sits between calls. A helper whose runtime is O(its input) —
a sort, a scan, an encode, a hash over a large value — is one call, and a deadline that can only fire
between calls cannot fire inside it.

**A helper whose runtime scales with its input polls the request's deadline flag, and the flag lives in
`Ctx`'s existing hot cache line** — the one [0020](0020.md) § 1's stack check
already loads, so the poll adds no load, only a compare against a line that is already resident. The poll
is amortised over a batch of iterations rather than taken per iteration; the batch is chosen so that the
amortised cost stays **under the stack check's own per-call cost**, which is the bound this ADR owns and
`benches/abi-probe/tests/perf_guards.rs` holds.

Reading a flag rather than a clock is the whole of why this is affordable. A clock read amortised over the
same batch would cost more than the loop iteration it protects, which is the arithmetic that chose this
design.

Two constraints on where a poll may go, both about correctness rather than cost:

- **The poll is supplied by a bounded-loop combinator, not remembered per helper.** Same reasoning as
  `nvs_helper!` in [0002](0002.md): a helper adopts a shape and the shape carries the
  obligation, so a future member cannot omit it by not knowing about it.
- **A poll site must be a point at which abandoning leaves the value consistent.** A sort cannot be
  abandoned mid-permutation and its array handed back. Where no such point exists inside the operation,
  the bound belongs on the *input* instead — which is what [0056](0056.md) already did
  for patterns, and the precedent generalises rather than being re-argued here.

### 6. A core is never blocked on a syscall

The runtime is one single-threaded scheduler of our own pinned per core — `corosensei` stackful
coroutines, not `async`, per [0072](0072.md) — and a request never
migrates (`docs/plan/design.md` § *Thread-per-core, shared-nothing runtime*). A blocking syscall on that
thread therefore stalls every coroutine pinned to the same core, which is tier B's failure, not tier C's —
the requests that lose are the neighbours, and they did nothing.

A socket read is *not* one of those syscalls: `nvs-host`'s stream parks the coroutine and hands the core
back, which is what makes a synchronous-looking `Read`/`Write` safe here at all. What follows is about the
calls that have no readiness to wait on.

**Filesystem calls, name resolution, and waiting on a child process go to the blocking pool**; the reactor
thread issues no call that can block on external state. What it spends, as [0004](0004.md)
requires: a pool bounded at **twice the core count**, which is per worker and never grows with requests
served. The handoff costs microseconds against operations that cost milliseconds, and the alternative it
avoids is an entire core idle for the same interval.

The bound is stated because the default it replaces is not: an unbounded pool of threads that each reserve
a stack is a footprint that grows with a workload's blocking fan-out rather than with its concurrency.

### 7. A worker that stops making progress is detected

Every mechanism above answers a fault. None answers a worker that faults in no way at all and simply
stops — an engine deadlock, or a loop with no poll site in it that § 5's combinator did not reach.

**A watchdog thread reads the in-flight deadline each worker already maintains** and reports a worker whose
oldest in-flight request has passed its deadline by a configured margin. It costs the worker nothing: it
reads state the deadline mechanism keeps anyway, so no heartbeat is written on any hot path.

What it does on firing is **report and shed, never kill**: the event goes to
[0020](0020.md) § 4's floor, the affected core stops accepting new work, and
`max_in_flight` accounts for its share as unavailable so the remaining cores are not asked to carry a
ceiling that assumes it. Killing is not available here and this ADR does not pretend otherwise — a thread
cannot be safely killed in-process, and § 14 declines the boundary that would make it possible. Detection
without a kill is still worth its cost, because a wedged core that is reported degrades a service
measurably while a wedged core that is silent looks like a capacity problem for as long as anyone is
willing to add capacity.

### 7a. An abandoned request is cancelled, not waited out

The scenario every FastCGI operator knows: a request hangs on something slow, the user closes the tab,
and PHP-FPM neither notices — FastCGI pushes no abort, so the script learns of the disconnect only at its
next write, which a request blocked on an upstream never makes — nor lets go: the request holds an entire
worker process until `max_execution_time`, and a handful of them empties the pool for every user at once.

Neither half exists here, and this section's job is to say so explicitly, because the guarantee is
composed from pieces that each live elsewhere. The hang itself never held anything a neighbour wanted: a
request waiting on readiness is a parked coroutine (§ 6,
[0115](0115.md)) costing a pooled stack
rather than a worker, and § 13's admission prices exactly what is genuinely in flight. And the
abandonment is an event, not a discovery: the connection lives on the reactor, so its drop is delivered
like any other readiness, and **the server cancels the request tree at the drop** —
[0072](0072.md) § 5's cancellation, delivered at the next safepoint
(`docs/plan/design.md` § *Safepoints*), running native teardown and no user code, with a task inside a
driver statement drained under [0072](0072.md) § 4's bound. M7's
acceptance holds the composite end to end: a disconnect leaves no task of the request behind. After the
response is on the wire, the connection's end stops meaning abandonment — the tree outlives it for
exactly the work [0072](0072.md) § 6 admits, and nothing else.

### 8. The accept loop backs off

An `accept` that fails with `EMFILE`/`ENFILE` returns immediately and will fail again immediately, which
turns descriptor exhaustion into a core pinned at full utilisation for as long as the condition lasts —
and, because the log is written per iteration, into a disk filled at the speed of the loop.

**The loop applies a bounded backoff on a descriptor-exhaustion error and logs once per window**, not once
per attempt. Descriptors are already charged to a request by
[0095](0095.md) § 4, so the condition is bounded from the other
side too; this closes the behaviour when it happens anyway.

### 9. Every deadline is monotonic

Every timeout, deadline and backoff in the engine is computed on a monotonic clock. A wall-clock deadline
is disabled by a clock step, which is not an exotic event — it is what happens the first time an instance
synchronises time after a long boot. This is a substitution, not an addition, and is stated only because
the failure it prevents is silent: the deadline does not fire late, it does not fire at all.

### 10. The floor cannot fill the disk it writes to

`rule:errors/engine-floor`'s floor writes unconditionally, which is correct, and a
request that faults in a loop therefore writes in a loop. Two bounds, both on the sink rather than on the
callers, so that no caller has to be trusted to be rare:

- **Rotation and a retention bound** on any file target, for the diagnostic log and the access log alike.
- **A rate limit with a coalescing counter** — repeated identical records within a window become one
  record carrying a count. The record shape is [0092](0092.md)'s and
  gains a count field rather than a second shape.

A full disk also stops compilation, which would convert a log problem into a total outage. **A write
failure in the on-disk artifact cache falls back to compiling in memory** and reports once; the cache is an
optimisation and is treated as one.

### 11. The artifact cache is read, not mapped

A mapped file that is truncated or replaced underneath a reader raises `SIGBUS` in the reader, which is a
signal, which is tier A's failure. The compiled-unit cache is **read into memory** rather than mapped.

The cost is one copy per unit at load, on the compile pool that `docs/plan/design.md`
§ *Compiled-unit cache with single-flight compilation* already keeps off every request core, against a
whole class of fault that has no in-process answer. Priority 5 buys priority 1, which is the direction
[0004](0004.md) exists to permit.

### 12. A JIT page is never writable and executable at once

Pages holding generated code are mapped writable while being written and executable only after being made
read-only; the transition is one call per compiled unit, on the compile pool, at compile time. This is a
security property before it is a stability one — a page that is both is a write primitive for any bug that
reaches it — and it is stated here because the JIT is this runtime's distinguishing component and nothing
else owns the question.

### 13. Admission is arithmetic, not a number

`rule:http-server/two-deployments-and-nothing-a-proxy-owns`'s `max_in_flight` refuses work before allocating
an isolate, which is the right shape. But a ceiling on *concurrency* and a cap on *per-request memory* that
have no stated relationship do not bound anything together: their product is what the machine must hold,
and if that product exceeds what it has, the operating system's out-of-memory killer is the real admission
control — and it terminates the process, which is tier A's failure arriving through a door that every cap
above was supposed to have closed.

**The effective ceiling is the smaller of the configured `max_in_flight` and what the memory budget
affords** — the budget divided by the per-request cap, less the engine's own fixed footprint. When the
configured number is the larger, it is clamped and the clamp is logged once at boot, naming both
directives and both numbers.

Clamping rather than refusing to start: a server that will not boot because two directives disagree is a
worse outage than the one being prevented, and the operator learns the same fact either way. Clamping
*silently* was rejected for the obvious reason — the observed capacity of a small instance changes with
this ADR, and an operator who is surprised by that should be able to find out why from the log rather than
from a benchmark.

### 14. The residue, stated

What survives every section above is **a memory-safety fault in `unsafe` code, or a miscompilation from
the code generator**. Neither is containable in-process: `catch_unwind` does not catch a `SIGSEGV`, and
wrong machine code has already done whatever it does before any check runs.

For these, tier D applies: the process dies, the supervisor already decided in
[0093](0093.md) restarts it, the requests in
flight are lost, and recovery takes about a cold start — a figure `docs/perf/userland-gap.md` owns and
which is, for this runtime, unusually small.

The engineering response to this class is **not** a boundary (§ *Alternatives rejected*); it is to reduce
the rate at which the class occurs, which is differential testing of generated code against the PHP oracle
in `tests/differential/`, fuzzing the code generator the way the lexer and
parser are already fuzzed, and running the reference-counting paths under `tools/leak-check.sh`. A fault
class that cannot be contained is one whose frequency is the only variable left, and that is where the
effort goes.

## Consequences

**Positive**

- Tier A becomes testable rather than asserted: a corpus of hostile requests either terminates a worker or
  does not, and § *Verification* names the harness that asks.
- The deep-nesting fault — the likeliest request-triggerable termination in the design, because it is
  reachable from an ordinary request body through three separate paths — is closed at all three (§§ 3, 4).
- A wedged core stops being invisible (§ 7), which is the failure operators currently have no signal for in
  any comparable runtime.
- The memory caps that already exist begin to bound something (§ 13). They did not before, in the sense
  that mattered.
- The residue is one named class with a named response, so the next contributor argues with a decision
  instead of discovering a gap.

**Negative, or accepted**

- **The observed capacity of a small instance drops** where § 13's clamp binds. This is a real change in a
  number people will notice, and it replaces an out-of-memory kill with a `503` — the right trade, but not
  a free one.
- **A depth limit is user-visible** (§ 4). A document deeper than 512 now fails that previously would have
  been decoded. Matching PHP's own default keeps this to programs that were already at that edge.
- **§ 5's combinator constrains how a helper is written.** A member whose loop has no consistent
  abandonment point must bound its input instead, which is a design obligation on every future O(input)
  member.
- **Two footprints grow** and neither is per-request: § 6's blocking pool at twice the core count, and
  § 11's read-in cache against a mapped one. Both are [0004](0004.md)'s permitted
  direction — memory spent for safety — and both are O(worker), not O(traffic).
- **§ 7 detects without acting.** Reporting a wedged core is less than fixing one, and this ADR accepts
  that gap rather than taking the boundary that would close it.

## Alternatives rejected

- **Worker processes under a supervisor** — the alternative that would close § 14, and the one this ADR
  spent the most effort on. It uniquely buys survival of a memory-safety fault or a miscompile. Three
  findings say it does not pay:

  First, **it does not contain the consequence that matters.** A reference-counting fault means one request
  reads another's memory. A boundary helps only when the two requests are in different processes, so with
  N processes it lowers a probability and eliminates nothing. Containing disclosure requires
  process-*per-request*, which is the next entry.

  Second, **it buys nothing against a deterministic fault.** A miscompilation on one route kills every
  process in turn. The boundary helps only against a fault that is rare and racy, which is a subset of a
  class that is already the residue.

  Third, **the substitute is unusually good here**, precisely because this runtime's cold start is small —
  `docs/perf/userland-gap.md` owns the figure and it is the fastest of the engines measured there. The
  entire delta between an external supervisor and N worker processes is: lose a fraction of the in-flight
  requests instead of all of them, and skip one boot.

  Against that: the compiled-unit cache is process-wide ([0006](0006.md)) and
  would be duplicated per process, at a memory and warm-up cost that **nobody has measured**;
  [0067](0067.md) § 13's `cores × max` pool sizing silently becomes `processes × cores × max`,
  which on ordinary defaults exceeds a database server's own connection limit; and
  [0083](0083.md)'s topic broadcast stops being an in-process fan-out
  and becomes a cross-process subsystem. The benefit is narrow and partly theoretical; the cost is broad
  and certain. See § *Revisiting* for the one condition that changes this.

- **Process-per-request, the PHP-FPM shape.** The only arrangement that genuinely contains a disclosure
  fault, and the one that would discard the entire performance thesis
  ([design.md](../plan/design.md) § *Thread-per-core, shared-nothing runtime*). Not a close call, and
  listed because it is the honest endpoint of the previous entry's logic.

- **`panic = "abort"` plus a supervisor.** Simpler than everything in § 2 and § 3 combined, and rejected
  where it was first raised: [0002](0002.md) shows it converts every containable runtime
  bug into a process kill, which is the guarantee this ADR exists to strengthen.

- **`io_uring` for § 6's blocking paths.** Faster, and it would remove the handoff rather than bound it.
  Rejected on priority 4: it is a second I/O model on one platform only, in a workspace that has
  deliberately kept its runtime dependency surface narrow ([0099](0099.md)
  § 2 is the same instinct applied to tooling). Reopen if a measurement demands it, not before.

- **A heartbeat counter written at the safepoint poll**, for § 7's watchdog. Rejected: it puts a store on
  the hottest path in the runtime to produce a fact a cold reader can already derive from the in-flight
  deadline. The design that costs the worker nothing was available, so the one that costs it something is
  not defensible.

- **Refusing to boot when § 13's arithmetic disagrees with the configured ceiling.** Rejected: it converts
  a misconfiguration into an outage, and the clamp communicates the identical fact without one.

- **Killing a wedged worker** (§ 7). Rejected because it is not available: an in-process thread cannot be
  killed safely, and the boundary that would make it possible is the first entry in this list.

## Revisiting

**The worker-process boundary is reopened when
[0083](0083.md) ships**, and the trigger is specific rather than a
gesture at future doubt. A server holding many live connections that dies is a materially different event
from a request server that dies: the recovery cost is client-side reconnection across the whole
population at once, and a fast restart does not reduce it. That is the first situation in which the
boundary's narrow benefit becomes the dominant one — and it is also, precisely, the situation whose topic
broadcast makes the boundary expensive. Both arrive together, which is why they are decided together
rather than now.

Two numbers must exist before any worker count above one is recommended, and neither does today: **the
per-unit size of compiled code**, which sets the duplicated-cache footprint, and **the per-unit
compilation time**, which sets the warm-up cost. Cold start bounds them jointly and separates neither.
Whoever reopens this measures both first.

## Verification

None of these guards exists yet; each is named here so that the claim it holds is not left to inspection.

- **A hostile-corpus test that a worker survives** — a body nested past every § 4 limit, an expression
  nested past the parser's, a value graph deep enough that a recursive teardown would overflow, a payload
  that drives an engine buffer past available memory. The assertion is process survival, not a particular
  error.
- **Fuzz targets for HTTP framing and for each decoder**, run the way `corpus_parse.rs` and the existing
  `cargo fuzz` targets are. The assertion is **no crash**, which for stack exhaustion is a strictly
  stronger claim than the no-panic assertion the lexer and parser targets already make.
- **The § 5 poll's amortised cost stays in its named class**, in
  `benches/abi-probe/tests/perf_guards.rs`, against the bound § 5 states.
- **A teardown test** that releases a graph deeper than the native stack could recurse, asserting
  completion — the guard for § 3 that also holds § 4's third path.
- **An accept-loop test** that a descriptor-exhaustion error produces bounded retries and one log record
  per window, not one per attempt.
- **A watchdog test** that a worker whose in-flight deadline is exceeded is reported and shed.
- **An admission test** that a configured `max_in_flight` above what the budget affords is clamped, logged
  once, and that the clamped value is what the `503` path actually enforces.
- **`tests/invariants.rs`** gains the § 2 claim, alongside the panic-containment claim it already holds
  for [0002](0002.md).
- **`tools/leak-check.sh` under valgrind** over the reference-counting paths, as § 14's frequency-reduction
  half rather than as a containment guard.
