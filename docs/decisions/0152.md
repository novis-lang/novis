# ADR 0152 — `nvs --help` is written for the person reading it, and it names no PHP input

- **Scope:** what a doc comment clap renders may contain, and the removal of `.php` from every input
  the CLI names — the four subcommands that never read an extension, and `nvs test`, which does. Not
  in scope: which short flags exist, which is [0151](0151.md)'s; what `nvs info` reports, which is
  [0065](0065.md)'s; and the lexer's treatment of a `<?php` tag, which is
  `rule:statements/nvs-is-the-only-open-tag` and unchanged.
- **Depends on:** [0151](0151.md), which made the banner the first thing a user reads.
- **Validated by:** `nvs --help`, and every subcommand's `--help`, carrying no `rule:` token, no bare
  `§`, no `docs/` path and no `.php`.

> **In short:** clap renders a `///` doc comment verbatim into `--help`, so those comments are
> user-facing text and had been written as if they were not: they cited rules by token, referred to
> numbered sections of records the reader cannot open, and carried rustdoc links that render as
> literal brackets. Each one moves down a line into an ordinary `//` comment, where it stays
> greppable and stays resolvable, and the `///` above it says what the flag does. In the same
> surface, `ast`, `check`, `run` and `serve` stop advertising a `.php` input they never checked for,
> and `nvs test` — the one command that reads an extension at all — stops accepting one.

## Context

- A `///` on a clap `Subcommand` variant or an argument field is not documentation about the code, it
  is the program's output. Nothing said so, and the comments were written to the same standard as
  every other comment in the repository: cite the rule, name the record's section, link the module.
- The result is on the first screen. `nvs --help` printed
  `rule:config/the-root-is-config-else-nvs-toml-else-the-shipped-defaults` to anyone who asked for
  long help, and every subcommand's `--help` printed at least one more.
- `§ 4` and `§ 2` are worse than the tokens, because they read as if the help text itself had
  sections. `see [`config`]` is worse still: rustdoc's link syntax renders as literal brackets in a
  terminal and names a Rust module.
- Four subcommands described their input as a `.nvs`/`.php` file. Not one of them reads an extension
  — `parse_file` takes a path and the front end takes content — so the phrase was never a statement
  about what the binary accepts. What a reader takes from it is that Novis runs PHP, which
  `rule:programs/no-compatibility-promise` forbids the project to say and which is not true: a file
  opening with `<?php` is refused with `E0229` whatever it is named.
- One place did read the extension, and accepted `.php`: `nvs test`, choosing between a program's
  compiled test table and a `.nvst` case tree. That is a real acceptance, and it is the only one, so
  the phrase was accurate in exactly the command whose help did not use it.

## Decision

### 1. A doc comment clap renders is written for its reader

`rule:packaging/help-text-speaks-to-its-reader`. The `///` says what the flag does, in the words of
someone who has the binary and not the repository. The citation moves into a `//` comment between the
doc comment and the item, which `grep -rn 'rule:'` still finds and `python tools/rules.py --citations`
still resolves, so the rulebook's gate is unaffected.

An enum's own doc comment is not rendered — clap takes the parent variant's — so `ApiCommand`,
`ConfigCommand` and their like stay ordinary rustdoc. The test is the output rather than the
position: run the help and grep it.

### 2. The CLI names no `.php` input

`ast`, `check`, `run` and `serve` describe their argument as a Novis file, which is what it is. The
manual keeps the fact underneath — the extension is a convention, the front end reads content — and
states the thing a PHP developer actually wants to know, which is that there is no PHP front end in
this binary and renaming a file changes nothing.

`is_program` takes `.nvs` alone. `nvs test` has two suites to choose between and the path is all it
has to choose from, so the test is the extension and nothing else; a program in a differently named
file is read as a case tree there and fails to parse as one.

`rule:programs/no-compatibility-promise` is amended rather than overturned: naming `.php` as an
accepted input is added to the phrasings it forbids, because it is the form the promise took here —
a line that meant "this ignores the name" and read as "this runs PHP".

## Consequences

- `nvs test path/to/program.php` no longer runs that program's `#[Test]` methods. Nothing in the tree
  invoked it that way, and the diagnostic is the case parser's rather than a message naming the
  extension.
- Every subcommand's long help gets shorter, because a sentence that existed to cite something is
  usually a sentence with nothing else in it.
- A future argument's doc comment now has a rule to be written against, which is the whole reason
  this is a rule and not a cleanup.

## Alternatives rejected

- **Strip the citations at build time**, from a `build.rs` or a clap `help_template`. It makes the
  source the wrong shape on purpose and hides the defect instead of fixing it, and the next person to
  read `main.rs` still cannot tell which sentences a user sees.
- **Keep `.php` in `nvs test` and drop it only from the prose.** Leaves the binary accepting an
  extension no document names, which is the same defect pointed the other way.
- **Say "a `.nvs` file" in the four subcommands' help.** Nearly right, and wrong in the way the
  original was: those commands accept any path, so naming one extension there would be a second
  claim about extensions that the front end does not make.

## Verification

`nvs --help`, and `--help` for every subcommand and nested subcommand, contain no `rule:`, no `§`, no
`docs/` path, no rustdoc bracket link and no `.php`. `nvs test` on a `.php`-named program reports the
case parser's failure rather than running it. `python tools/rules.py --check` resolves every citation
moved into a `//` comment.
