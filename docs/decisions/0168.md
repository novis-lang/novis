# ADR 0168 — `Core\Xml` is a materialising tree beside a one-window stream, and it refuses a document type declaration whole

- **Scope:** the two shapes `Core\Xml` offers and why they share no operation; what a strict XML parse
  refuses and why each refusal is an absent code path rather than a bounded one; where a `<!DOCTYPE …>`
  stops. Not in scope: the node family and the WHATWG parser that shares it, which are
  [0122](0122.md)'s and are not reopened here; the members' signatures, which
  `crates/nvs-stdlib/src/xml.rs` declares; the compression bound this record declines to reuse, which is
  [0154](0154.md)'s.
- **Depends on:** [0122](0122.md) — the node family both doors produce, and
  the refuse-hard contract this record gives its refusals to; [0051](0051.md)
  — `Core\Xml` as Tier 0, one API replacing six extensions;
  [0019](0019.md) — inert parsed data with no path back into execution.
- **Validated by:** `an_external_entity_is_not_a_code_path_rather_than_a_flag_defaulting_to_off`,
  `a_dtd_naming_an_external_subset_is_refused_rather_than_fetched` and
  `a_billion_laughs_document_is_refused_at_its_doctype_rather_than_bounded`, in
  `crates/nvs-stdlib/src/xml.rs`'s test module.

> **In short:** `Core\Xml` is one subsystem in two shapes — a tree that materialises the whole document
> and answers walks in any order, and a reader and writer that hold one window — and **no operation is
> available through both**, so a program picks the shape that fits how much of the document it needs at
> once and pays for that shape only. On the refusal side, the three classic XML attacks are not bounded,
> they are absent: **there is no code in the module that resolves an entity**, so external-entity
> resolution has no flag to have defaulted to off, and a `<!DOCTYPE …>` is refused **whole** — the
> external subset is never a thing that could have been fetched and the internal subset defines nothing
> that could be expanded, which is billion-laughs closed at its declaration rather than metered by
> `rule:core-classes/decompression-bound`'s ratio and ceiling. The only quantitative bound left is depth,
> because element nesting is written by the document rather than declared by it. The five predefined
> entities and numeric character references still expand: they are the document's own characters written
> another way, and resolve to nothing outside the text they sit in.

## Context

`Core\Xml` replaces six PHP extensions with one API (`rule:core-api/tier-roster`, 0051 § 3): `dom`,
`simplexml`, `xml`, `xmlreader`, `xmlwriter` and the `libxml` surface underneath them. Two questions had
to be answered before its first member landed, and both are the kind that a later member silently
answers the wrong way if the record does not exist.

The first is shape. `rule:core-api/one-paradigm-per-operation` says one operation gets one paradigm, and
a document API that offers both a tree and a stream looks on its face like the counterexample. PHP's
does not resolve it either — `DOMDocument`, `SimpleXMLElement`, `XMLReader` and the expat callbacks are
four vocabularies for the same document, and the choice between them is made by whichever one the
programmer met first.

The second is what a parse refuses. PHP's XML surface is the textbook XXE case: `libxml_disable_entity_loader`
existed because the loader existed, its default flipped twice across releases, and `LIBXML_NOENT` names the
opposite of what it does. Every mitigation in that history is a **flag over a live code path**, which is a
class of bug that recurs whenever a caller, a framework or a library forgets to set it.

## Investigation

The parser on disk resolves references in exactly one function,
`crates/nvs-stdlib/src/xml.rs:601`, and that function's whole vocabulary is the five predefined entities
and numeric character references (`xml.rs:620`). Anything else is a sentence naming what was written
(`xml.rs:626`). There is no lookup table to consult, no resolver interface, and no argument threaded
through the parse that a resolver would have been reached from.

`<!DOCTYPE` is matched in two places — the prolog walk (`xml.rs:933`) and the element walk
(`xml.rs:875`) — and both return the single message at `xml.rs:462`, written once so the two cannot
drift.

The depth bound is `DEPTH_CEILING` at `xml.rs:455`, checked as elements open (`xml.rs:886`). It is the
same number `Core\Json::decode` uses, and the parse loop is iterative, so it is a stated policy rather
than a guard over the native stack.

## Options considered

**For the shape**, three: one tree API only, with a stream added later if anyone asks; one stream API
only, with a tree built in userland; or both, disjoint. **For the DTD**, two: refuse the declaration
whole, or accept an internal subset and expand its entities under
`rule:core-classes/decompression-bound`'s ratio-and-ceiling, refusing only an external identifier.

## Decision

### 1. Two shapes, and no operation reaches through both

`Core\Xml` materialises a whole document through `Core\Xml::parse`, and holds one window through the
reader and writer that replace `XMLReader` and `XMLWriter`. Spec § 17 states this outright as "the one
place in this file where two shapes of the same subsystem coexist", so it is **named** as the exception
to `rule:core-api/one-paradigm-per-operation` rather than smuggled past it, and the naming is what keeps
the exception from spreading: a subsystem that wants two shapes has to earn its own sentence.

What makes it earn one here is that the two shapes are not two spellings of one capability. The tree's
defining property is that a program may walk it in any order and any number of times; the stream's is
that memory is O(one window) rather than O(document). Neither property can be offered by the other
shape, so a program with a 2 GiB export and a program with a 4 KiB config are not being offered a
preference — they are being offered the only two answers that exist.

**The disjointness is the load-bearing half.** If one operation were reachable through both, the API
would have a seam where the memory story stops being a property of the door a program came in through,
and every member added afterwards would have to answer which side it belongs to. The member cards
therefore never re-argue the split; the module doc states it once
(`crates/nvs-stdlib/src/xml.rs:24`) and that is its only home.

### 2. Both shapes answer one node family, and this record does not reopen it

The nodes are 0122's, closed at five, and produced identically by the WHATWG parser on `Core\Html` and
the strict parser here. That the *stream* answers the same family is the part this record adds: a
program that outgrows the tree does not learn a second vocabulary, which is most of what makes the split
survivable.

### 3. A `<!DOCTYPE …>` is refused whole, so there is nothing to bound

The whole-refusal position is `crates/nvs-stdlib/src/xml.rs:462`. It answers all three of the classic
attacks at once, and it answers them by **subtraction**:

- **External entity resolution** is not a code path. `xml.rs:601` is the only place a reference is
  resolved and its vocabulary is closed; there is no branch that reaches a filesystem, a network or
  another document, so a flag would have nothing to default to off. This is what
  `rule:security/no-runtime-grant` looks like applied to a parser: the authority is not withheld, it was
  never wired.
- **A DTD naming an external subset** is refused at the `<!DOCTYPE` token, before the identifier is even
  read, so the refusal cannot depend on telling a `SYSTEM` identifier from a `PUBLIC` one.
- **Billion-laughs** needs an internal subset to declare `<!ENTITY lol "lollol…">` in. There is no
  internal subset, so there is no expansion, so there is no expansion factor to meter. **This is the one
  place the decision is not merely the safe option but the smaller one**: metering would mean a DTD
  parser, an entity table, a substitution pass and a bound over it — four things that can be wrong —
  where refusal is one comparison.

The five predefined entities and numeric character references stay, and they are not an exception to any
of the above: `&amp;` and `&#x41;` are spellings of characters that are already in the document, they
resolve without consulting anything, and a parser that refused them would be refusing well-formed XML
rather than refusing an attack.

### 4. Depth is the one bound that stays a number

Nesting is not declared anywhere a refusal could catch, so it is the one attack surface that has to be
metered rather than removed: `DEPTH_CEILING` (`xml.rs:455`) at 1024, the same figure `Core\Json::decode`
carries and for the same reason — a document engineered to be deep costs work before any value exists,
and a bound that is stated is one a caller can reason about.

## Diagnostics

Neither refusal is a compiler diagnostic; both are `ParseError` throws from the parse member, each
naming what was written rather than repairing it (`rule:errors/ambiguous-input-refused`). The DTD
sentence names all three
places an entity is not resolved from — external subset, internal subset, network — because a reader who
reaches it is usually holding a document that worked somewhere else, and the useful answer is which of
their assumptions is gone rather than which token failed.

## Consequences

**What this costs a program.** A document that carries a `<!DOCTYPE html>` line, or any DTD at all, does
not parse. That is a real population — SOAP envelopes, XHTML documents, and anything emitted by a
generator that writes a doctype out of habit — and their authors have to strip the declaration before
handing the bytes over. `Core\Html`'s WHATWG entry is the door for the HTML-shaped half of that
population, and it never fails (`rule:core-classes/html-parsing`), so the loss is narrower than the raw
count suggests: what is left is XML that names a DTD it does not need.

**What it buys.** The XXE class is closed for every program, including the ones whose authors have never
heard of it, with no configuration to get wrong at any layer — and closed in a way that a future member
cannot quietly reopen, because reopening it means writing a resolver rather than flipping a default.

**What it spends**, per `rule:programs/memory-priority`: the tree is proportional to the document,
attributed to the request that parsed it and released with its arena; the parse holds the document once
more while it builds. The stream holds one window. Neither figure changes with anything this record
decides — refusal is what stops them from being multiplied by an expansion factor.

## Alternatives rejected

**An internal subset expanded under a ratio and ceiling.** This was the live alternative, and it is the
one `rule:core-classes/decompression-bound` would have supplied the machinery for at no design cost. It
loses on three counts. It buys back only documents that declare their own entities, which is a smaller
population than the doctype-carrying one and is served by writing the characters out. It converts a
class of bug that is *absent* into one that is *bounded*, and a bound is a number someone will later
want configurable — the priority ordering puts request isolation above every convenience that argument
would trade for. And a ceiling is the wrong shape for the attack anyway: the damage from a decompression
bomb is the bytes it produces, which a ratio measures, while the damage from a hostile DTD includes
whatever the resolver was pointed at, which no ratio sees.

**One shape only.** A tree-only API cannot serve a document larger than the request's memory ceiling,
which is a real workload rather than a hypothetical one. A stream-only API means every program that
wants random access writes its own tree, so the tree exists anyway, once per program, unreviewed, and
the node family stops being shared with `Core\Html` — which is the thing 0122 exists to prevent.

**A mode flag on one parser** — `Core\Xml::parse($src, allowDtd: true)`, or an HTML mode. The goal's
standing decisions rule this out for the HTML half and the same reasoning covers this one: a parameter
that flips a contract between refuse-hard and recover-always is the `LIBXML_*` matrix, and the flag's
default becomes the real security boundary while the signature says nothing about it.

## Revisiting

Two triggers, and neither is "a program wanted a doctype". If a **specification Novis must interoperate
with** requires an internal subset to be read — not merely tolerated in the prolog, but read for meaning
— then § 3 is reopened with that specification named. And if a document that carries a doctype but
declares no entity turns out to dominate the refusals in practice, the narrower change is to skip a
declaration with no internal subset rather than to parse one, which is a different decision from the one
rejected above and would need its own record.

## Verification

`crates/nvs-stdlib/src/xml.rs`'s test module holds the three refusal cases named under *Validated by*,
and the `.nvst` cases under `tests/conformance/core/xml-*` exercise the tree from a program.
`rule:core-classes/xml-refuses-by-construction` is `shipped` on that basis.
`rule:core-classes/xml-tree-and-stream` stays `designed` until the reader and writer exist, because its
central claim — that no operation is available through both — is not assertable while only one of the
two shapes is on disk; the goal stage that lands the stream flips it and adds
`no_operation_is_available_through_both_the_tree_and_the_stream` as its guard.
