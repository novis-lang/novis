# ADR 0263 — The website reads examples in place, and every handwritten page is stamped against the features it covers

- **Scope:** how the website's handwritten pages and snippets are kept true to the features they explain, and where its examples
  are read from. What the site's areas are and what each holds is the website goal's, and is not decided here.
- **Depends on:** [0134](0134.md).
- **Validated by:** `tools/nv/test/site.test.ts`, and `bun nv site --check` in CI's `proofs` job.

> **In short:** the website build reads `docs/examples/` where it is, and keeps no mirror. Every
> handwritten page names the roster ids it covers in `covers:`, and `website/site.lock.json` records a
> hash of each covered feature as the page last saw it. A removed id is broken and a moved hash is
> stale. The wrap refuses a broken id and a page the session made stale; CI refuses both over the whole
> tree, and every snippet runs against its `.out` in the same step. One tool, `bun nv site`, owns all of it.

## Context

The generated half of the site, Reference, is rewritten from the binary and the roster on every
render, so it cannot drift. The handwritten half could: a guide explains a method, the method's
behaviour moves, and nothing connects the two. Before this record the examples were also copied into
`website/` by a sync script, so the same program existed twice and a check had to keep the copies equal.

## Options considered

### 1. A mirror of the examples, and a check that it matches

What the site did. Two copies of every example, a sync script and a check script, and a failure mode
(the mirror is behind) whose only fix is to run the script that should have run.

### 2. Read the examples in place

The Astro content loader takes a directory outside `website/`. One copy, nothing to sync.

### 3. Staleness by date or by hand

A page's "last reviewed" date says nothing about whether the feature moved since. A periodic review
pass finds drift late and never says which page a change reached.

### 4. Staleness by content hash, gated at the wrap

Each page lists what it covers; the lock records the hash of each covered feature's card or chapter
section, `about.md` and examples. A change to any of them makes exactly the pages that cover it stale,
and the session that made the change is the one holding the context to reread them.

## Decision

### 1. Examples are read in place

The build reads `docs/examples/` directly, and the mirror, its sync script and its check are gone.
`rule:testing/examples-live-in-the-repository` states it.

### 2. Pages are stamped, and the stamp is checked at two places

Option 4. `covers:` uses the proofs roster's ids, so a page and a feature proof name a feature the same
way. `bun nv session --wrap` refuses every broken id, and the stale pages whose page, example directory,
or anchored implementation or chapter file the session changed. A stale page the wrap cannot attribute,
because its card moved through a file the anchor does not name, is caught by CI's `--check stale`, which
judges the whole tree. `rule:testing/website-pages-are-stamped` states it.

### 3. One tool with parts

`bun nv site` holds the guard, the stamp, the build and every `--check` part, in place of a script per
check. The parts run in the CI job that has already built `nvs`, because the snippets and the roster
both need it.

## Consequences

A change to a feature costs its author a reread of the pages that cover it. That is the cost the
decision buys: a reader of the site gets text that matches the binary, and code that is known to run.
Nothing in `nvs` changes, so request-path performance and memory are untouched. CI's `proofs` lane now
also runs on a change under `website/`.

## Revisiting

If the wrap's attribution misses often enough that CI's whole-tree check is the usual place a stale
page is found, the gate should hash the card at the session's base as well, rather than infer the
cause from the paths changed.
