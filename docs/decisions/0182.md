# ADR 0182 — A forward proxy is the operator's alone, and one mandatory word says whether the pin survives it

- **Scope:** how a deployment whose egress leaves through a forward proxy runs `Core\Http\Client`, what
  configures it, and what the address policy can still see once it does. Covers the `[http.client.proxy]`
  block, the `CONNECT` tunnel, the bypass list, proxy authentication and the pool key. Not in scope: a TLS
  connection *to* the proxy, SOCKS, PAC files, NTLM or Kerberos proxy authentication, a per-program or
  per-call proxy, and reading `HTTP_PROXY`, `HTTPS_PROXY` or `NO_PROXY` from the environment.
- **Depends on:** [0058](0058.md) for the launderer, the address policy and the pin this either keeps or
  narrows; [0180](0180.md) for the client, its per-core pool and the `System`-class block its TLS trust
  already lives in; [0073](0073.md) for a mandatory word with no default, whose reasoning this reuses
  wholesale; [0005](0005.md) and [0064](0064.md) for the changeability class every directive carries;
  [0103](0103.md) for the `_file` sibling the proxy password gets.
- **Validated by:** `crates/nvs-config/tests/resolve.rs` for the block's refusals and
  `crates/nvs-stdlib/src/http/transport.rs` for the tunnel and the pool key.

> **In short:** an operator writes `[http.client.proxy]`, and nothing else — no program, no call option and
> no environment variable — can route an outbound call. The block carries one **mandatory** word, `resolve`,
> with no default, because both answers are right in some network and either default silently does the wrong
> thing in another. `resolve = "local"` keeps everything 0058 built: Novis resolves the destination, checks
> every address against `rule:security/net-address-policy`, and asks the proxy to `CONNECT` to **the address
> it approved**, so the pin survives the tunnel. `resolve = "proxy"` is for the network where only the proxy
> can resolve a name: Novis sends the host name, judges the URL's text alone, and **says so in a `Warn`
> record at every single boot**, because a policy that has been narrowed and forgotten is the failure the
> word exists to prevent. Only `Core\Http\Client` is proxied; a raw socket, a database and mail connect
> directly. This is the explicit grant syntax 0058 § *Consequences* asked a later decision to write.

## Context

`rule:security/net-address-policy` assumes Novis makes the connection: it resolves the host, refuses every
address in a denied range, and `rule:http-server/allow-url-pins-the-address` hands the transport the
approved set so no second resolution can substitute an address. `crates/nvs-stdlib/src/http/transport.rs:1344`
is where that set is spent — one attempt per approved address, pooled under
`crates/nvs-stdlib/src/http/transport.rs:1503`'s key.

A large share of the deployments this client is for cannot make that connection. Corporate networks, and
every cloud VPC with no NAT gateway on the subnet, egress only through a forward proxy; a container whose
security group allows one destination is the same shape. Today Novis has no spelling for it, so those
deployments cannot run an outbound call at all. 0058 § *Consequences* recorded the gap and said the grant
syntax should make a proxy explicit rather than leaving it implied — this is that record.

The awkward part is not the tunnel. It is that in some of those networks the proxy is also the only thing
that can resolve a name: the application subnet has no DNS route to the outside, and `getaddrinfo` on an
external host either fails or answers an internal placeholder. In that network Novis cannot check the
destination's address, because it never learns one. The policy is then the proxy's to enforce, and pretending
otherwise would be worse than saying it.

## Investigation

**How the tunnel is spelled.** A forward proxy for an outbound HTTPS call is `CONNECT host:port HTTP/1.1`
followed by a `2xx`, after which the socket is a byte pipe and the client speaks TLS over it exactly as it
would over a direct socket. The alternative for a plain `http` URL — an absolute-form request line,
`GET http://example.com/x HTTP/1.1`, sent to the proxy — is a second code path in which the proxy reads and
may rewrite the request, and it has no equivalent for `https`.

**What `CONNECT` accepts as a target.** The target is a host and a port, and a **literal IP address is a
valid host**. Every proxy in common use dials whatever it is given rather than insisting on a name; the ones
that refuse do so by policy — an allowlist written as host names — and those are the same deployments whose
operator must write `resolve = "proxy"` anyway. So the pin is not structurally lost to a proxy: it is lost
only where the operator's proxy policy or the network's DNS takes it.

**What the host name is still needed for.** With an IP address in the `CONNECT` line, the destination host
name is still carried in TLS's server name extension and in the request's `Host` header, which is what the
launderer approved and what the certificate is verified against
(`rule:http-server/the-client-trust-roots-are-the-operators`). Nothing about verification changes.

**What everyone else does, and why none of it is a model.** curl, PHP's stream wrappers, Python's `requests`
and Go's default transport all read `HTTP_PROXY`/`HTTPS_PROXY` from the environment, and all of them route
to a name. That is ambient state that changes where every byte goes, readable and settable by anything that
can set an environment variable for the process — which `rule:security/no-cross-request-state` keeps out of
behaviour on principle, and which is a known `httpoxy`-class hazard when a CGI header lands in the same
namespace. None of them can keep a pin, because none of them has one.

## Options considered

1. **No proxy support.** Honest about the guarantee and useless to a whole class of deployment, which then
   runs no Novis at all rather than running it with a narrower policy.
2. **Read `HTTPS_PROXY` like everyone else.** Familiar, and it makes where every outbound byte goes a
   property of ambient process state. Rejected in § 1.
3. **A proxy that always resolves** — `CONNECT` with the host name, always. One code path, and it gives up
   the pin in every deployment including the majority whose proxy is perfectly able to dial an address.
4. **A proxy that never resolves** — `CONNECT` with the approved address, always. Keeps the guarantee
   everywhere it can be kept, and cannot boot in a network where Novis has no DNS route.
5. **Either, chosen by a default plus an override.** Whichever default is picked is wrong somewhere, and the
   wrongness is invisible: `local` fails outright in the DNS-less network, which is at least loud, while
   `proxy` quietly hands the policy away in every network where option 4 would have held.
6. **Either, chosen by a mandatory word.** Option 5 without the default. One line of configuration per
   deployment, and the deployment that gives up the pin is the one whose operator wrote the word that gives
   it up. Chosen.

## Decision

### 1. The operator configures it, and nothing else can

`[http.client.proxy]` in `nvs.toml` is the only source. The block is `System` class
(`rule:config/three-changeability-classes`): `Core\Config::set` fails on every key, there is no call option
and no client option, and **no environment variable is read** — not `HTTP_PROXY`, not `HTTPS_PROXY`, not
`NO_PROXY`, in any case spelling.

Where every outbound byte goes is a deployment's decision and not a request's. A per-call proxy would also be
a per-call way to choose who resolves the destination, which is a per-call way to narrow
`rule:security/net-address-policy` — exactly the widening that rule exists to refuse. The environment is the
same argument with a worse blast radius: it is read-only ambient state, shared by every request in the
process, that nothing in the deployment's own configuration records.

### 2. `resolve` is mandatory, and there is no default

A `[http.client.proxy]` block without `resolve` **refuses the boot**, naming the block and both words with
one sentence each. A third word is the same refusal.

This is `rule:config/scope-has-no-default`'s argument, and it holds here for the same reason: both answers
are commonly correct, and either default silently does the wrong thing in somebody's production. Defaulting
to `"local"` fails outright in the network where only the proxy resolves — loud, but it makes the common
corporate case look broken out of the box. Defaulting to `"proxy"` gives up the pin in every deployment
whose proxy could have dialled an address, and nothing at run time distinguishes that from a deployment that
meant it. One required word per block removes a class of incident otherwise discovered by its consequences.

### 3. `resolve = "local"` tunnels to the address Novis approved

Everything before the connection is unchanged: `Core\Http::allowUrl` resolves and checks, or the member's own
four questions do for a program-authored URL (`crates/nvs-stdlib/src/http.rs:389`), and the call holds the
approved set. The transport then opens a socket to the proxy and sends `CONNECT <approved address>:<port>`,
with `Host` naming the same, and waits for a `2xx` under the call's `connectTimeout` — clamped, as every wait
is, by what is left of the deadline (`rule:http-server/one-deadline-covers-the-whole-call`). Over the
established tunnel it speaks exactly what it speaks today: TLS with the server name the launderer approved,
or plain HTTP for an `http` URL.

The guarantee is therefore intact, and the reason is worth stating plainly: the address the proxy is asked to
reach is one that passed the policy, and there is no second resolution anywhere in the path that could return
a different one. Falling back across the approved set works unchanged — a refused `CONNECT` to one address is
that address's attempt failing, and the next approved address is tried.

### 4. `resolve = "proxy"` narrows the policy to the URL's text, and says so at every boot

`CONNECT <host>:<port>`, with the name. Novis judges what it can judge from the text — the scheme, the
`net.connect` grant's host list, the tainted-URL check — and **cannot** check the address, because it never
learns one. `rule:security/net-address-policy` is not being violated here; it is being told, in configuration,
that this deployment has moved the address question to the proxy.

Because that is a real weakening, it is not allowed to be silent:

- **Every boot writes one `Warn` record** naming the block, the word, and
  `rule:security/net-address-policy` — not once per process lifetime as a novelty, but on every start, so
  the log of a deployment that has been running this way for a year still says so.
- **`nvs config dump` renders the key beside the rule's id**, so the offline audit
  (`rule:config/check-and-dump-audit-the-tree-offline`) shows the narrowing without a running server.

A warning nobody reads is a fair objection to a warning issued once. Issued at every boot and rendered in the
tree dump, it is what an auditor greps for.

### 5. Only `Core\Http\Client` is proxied

`Core\Net`, a database connection, the shared cache tier and mail all connect directly, and no key in this
block touches them. A raw socket is a transport the program asked for by address and has no notion of a
tunnel; the others are endpoints an operator already wrote into root-owned configuration, which is the exact
address `rule:security/net-address-policy`'s exception is about. Proxying them would be a second mechanism
serving no deployment that asked for one.

### 6. `http://` proxies only, and every scheme is tunnelled

The proxy URL's scheme is `http`, and `https` refuses the boot naming this record. TLS to the proxy is a
second trust decision — whose roots verify the proxy, and what a failure there means for a call — and it
belongs to whichever later record has a deployment asking for it.

A plain `http` destination is tunnelled through `CONNECT` like every other, rather than sent as an
absolute-form request line. One mechanism, one place the pin is spent, and no path on which the proxy is
handed a full request it may rewrite.

### 7. `bypass` is host names, and three things it is not

`bypass` is an array of host names, each exact (`internal.example.com`) or with a leading dot for a suffix
(`.example.com`). A destination matching one is reached **directly and under the full policy** —
unchanged behaviour, including under `resolve = "proxy"`, because a bypassed host is one Novis resolves
itself.

It is not a CIDR range, not a wildcard pattern, and carries no port. The reasoning is
`rule:security/net-address-policy`'s own, one level down: matching is on the URL's host text, which is what
is known before any resolution, and a range or a `*` in that position is an operator handing back more than
they can see they are handing back. An entry with a port, a scheme, a `*` or a `/` refuses the boot naming
the entry.

### 8. Authentication is `Proxy-Authorization` on `CONNECT`, and nowhere else

`username` and `password` produce a `Proxy-Authorization: Basic` header on the `CONNECT` request. `password`
is a secret directive, so it has the `password_file` sibling every secret has, exactly one of the pair may be
set, and both is a refusal (`rule:config/a-secret-is-a-file-whose-content-is-the-value`).

The header goes on `CONNECT` alone — never to the destination, never re-sent on a redirect hop, and never in a
trace event, a log record or an error message. A `407` from the proxy is a `RuntimeError` naming proxy
authentication and carrying no credential; any other refusal of `CONNECT` is an `IOError`. **Neither is
retried** by `retryAttempts` (`rule:http-server/retry-is-opt-in-jittered-and-closed`), which retries an
answer from the destination, and a proxy that has refused the tunnel is not one.

### 9. The pool key gains the proxy

`crates/nvs-stdlib/src/http/transport.rs:1503` builds the key from scheme, host, socket, client identity and
call policy; the proxy joins it. A tunnelled connection and a direct one are then never confused, a bypassed
host's connections are their own, and a reload that changes the block leaves the old value's connections
unmatchable, so they age out of the pool rather than serving a call the operator has already redirected.
This is `rule:http-server/an-outbound-connection-is-pooled-per-core-and-stays-pinned`'s principle applied
once more: the key carries everything the check approved.

The block is `Reload` class (`rule:config/reloadability-is-its-own-field`) for the same reason — the next
call reads the current value, and nothing that the old value made can be drawn from the pool.

### 10. The directives

`[http.client.proxy]`, all `System` class and all `Reload`:

| Directive | Ships | Refuses |
|---|---|---|
| `url` | — | anything but an `http://` URL with a host; a port is optional and defaults to the URL's |
| `resolve` | **none — mandatory** | a missing value, and any word but `local` or `proxy` |
| `bypass` | `[]` | an entry with a port, a scheme, a `*` or a `/` |
| `username` | — | — |
| `password` / `password_file` | — | both of the pair set |

An absent block is no proxy, which is today's behaviour and needs no spelling.

### 11. What it spends

**Per new connection**: one `CONNECT` round trip, under the call's existing `connectTimeout` and deadline,
and the request line and response head it writes and reads — a few hundred octets, released with the
handshake. **Per request: nothing**, because a tunnelled connection is pooled like any other and the second
call through it pays no `CONNECT`. **Per core**: no new memory — the pool's existing cap bounds tunnelled
connections exactly as it bounds direct ones, and the key grows by the proxy's text. **Per process**: the
parsed block and, where `password_file` is used, the credential read once at boot beside every other secret.
Nothing is held per request beyond what an outbound call already holds.

## Diagnostics

All the boot refusals are configuration diagnostics, in the `E06xx` band with the rest of the block-level
refusals and reported from `crates/nvs-config`: a block with no `resolve`, naming both words; a `resolve`
that is a third word; a `url` that is not `http://` or carries no host; a `bypass` entry with a port, a
scheme, a wildcard or a slash, naming the entry; `password` and `password_file` both set, which is the
secret registry's existing refusal reaching one more pair.

At run time there are two, both from the transport and neither retried: a `407` is a `RuntimeError` naming
proxy authentication, and any other non-`2xx` answer to `CONNECT` — or a connection to the proxy that fails
outright — is an `IOError` naming the proxy's address and the destination it was asked for. Neither message
carries the credential.

The `Warn` record § 4 writes is not a diagnostic; it is an observability record, and it fires on a tree that
is entirely valid.

## Consequences

- A deployment behind a corporate or cloud forward proxy can run outbound calls, which today it cannot.
- The default case keeps every guarantee 0058 built. A proxy does not weaken the policy; a **word** does,
  and that word is in a root-owned file with a boot warning attached to it.
- The narrowed case is visible three ways — the configuration itself, a `Warn` at every boot, and
  `nvs config dump` — so "does this deployment still check outbound addresses" is answerable without
  reading any code.
- A program cannot tell whether it is proxied. There is no member, option or constant that reports it,
  which is the same reason there is no per-call spelling: it is not the program's decision to make or to
  branch on.
- The environment stays unread, so a Novis process's egress path cannot be changed by anything that can set
  a variable for it. This diverges from every other client an operator is used to, and § 10's block is the
  one place to look instead.

## Alternatives rejected

- **Reading `HTTPS_PROXY`.** § 1. Familiarity does not buy back ambient, process-wide, request-invisible
  control over where every outbound byte goes.
- **A default for `resolve`.** § 2, and `rule:config/scope-has-no-default`'s reasoning in full.
- **Warning once per process rather than at every boot.** A warning issued at the first proxied call is one
  a long-lived server writes before anyone is watching and never again. The boot log is where a deployment's
  posture is read.
- **An absolute-form request line for `http` destinations.** A second code path, on which the proxy sees and
  may rewrite the whole request, in exchange for saving one round trip on the scheme this client uses least.
- **Proxying `Core\Net` too.** A datagram has no `CONNECT`, and a raw stream socket a program opened by
  address is not a thing a forward proxy for HTTP is for.
- **A capability for "may be proxied".** The proxy is not a right a program holds or drops; it is where the
  deployment's packets go. A grant would imply a program could ask not to be proxied.

## Revisiting

Two triggers. A deployment whose proxy must itself be reached over TLS — the trust question § 6 defers, and
a record of its own. And a deployment that needs different destinations to take different proxies, which is
a routing table rather than a block, and which this deliberately does not start.

## Verification

- `crates/nvs-config/tests/resolve.rs`: a block with no `resolve` refuses the boot and the message names
  both words; a third word refuses; an `https://` proxy URL refuses; a `bypass` entry with a port refuses
  naming the entry; `password` with `password_file` refuses.
- `crates/nvs-stdlib/src/http/transport.rs`: with `resolve = "local"`, the `CONNECT` line carries the
  **approved address** and not the host name, and the TLS server name is still the host; with
  `resolve = "proxy"`, it carries the host name; an `http` destination is tunnelled and no absolute-form
  request line is ever written; a `407` throws a `RuntimeError` naming proxy authentication and is not
  retried; a bypassed host is dialled directly; two calls to one destination share one tunnel from the pool,
  and a direct connection is never drawn for a proxied call.
- `crates/nvs-config/tests/tree.rs`: every key is `System` class, and `Core\Config::set` on each returns
  `false`.
- A conformance case that `resolve = "proxy"` writes its `Warn` record at boot and that `nvs config dump`
  renders the key beside `rule:security/net-address-policy`'s id.
