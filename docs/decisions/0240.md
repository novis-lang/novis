# ADR 0240 — A `require` or `autoload` path literal completes as a path, an `autoload` root or glob links to its directory, and a directory link reveals it in the Explorer

- **Scope:** Path completion and links inside the path literals of `require` and `autoload`, the
  trigger characters that open that list, and what the VS Code client does with a link to a
  directory. Completion of any other string is not decided here.
- **Depends on:** [0099](0099.md) (the request set, and `documentLink` as a projection of the walk),
  [0193](0193.md) (trigger characters answered only where a spelling ends).
- **Validated by:** `tests/lsp/completion/a-require-literal-offers-the-directories-and-nvs-files-its-text-reaches.lspt`,
  `tests/lsp/links/an-autoload-root-links-to-the-directory-it-names.lspt`, `crates/nvs-lsp/tests/completion.rs`
  and `editors/vscode/test/client/links.test.ts`.

> **In short:** inside the literal of a `require`, of an `autoload` root or of an `autoload discover`
> glob, completion offers the entries of the directory the text before the cursor reaches, resolved
> against the declaring file's directory: directories with a `/` after them, and `.nvs` files inside
> a `require` only. The listing is `nvs_hir::autoload::entries_of`, the one the compiler resolves a
> glob with. `'`, `"` and `/` become trigger characters, answered only inside such a literal. Each
> `autoload` root and each glob gets a `documentLink` to the directory it names, resolved by
> `nvs_hir::autoload::Site::directories` out of the literal spans the walk now keeps; a missing root
> and a malformed glob get none. A directory link is a `file:` URI ending in `/`, and the VS Code
> client turns it into a `revealInExplorer` command.

## Context

`documentLink` already promised "the resolved path literal of a `require` or `autoload`", and only the
`require` half existed: `nvs_hir::autoload::Site` kept the whole declaration's span and no span per
literal, so there was no literal-to-directory edge to read, and deriving one in the language server
would have been a second copy of the resolution rule. Writing a path in a `require` or an `autoload`
had no help at all: completion answered nothing inside a string.

## Decision

### 1. The walk keeps each literal's span, and hir resolves it

`SiteKind::Prefix` carries each root with its literal's span, and `SiteKind::Discover` the glob's.
`Site::directories` pairs each literal with the directory it names, through the functions
`AutoloadMap::build` resolves with (`canonical` for a root, `glob_base` for a glob), and keeps only a
literal whose directory exists. Nothing calls it while compiling. The language server keeps the entry
document's own sites and asks them when a link request arrives.

### 2. Completion lists one directory through the compiler's listing

The text between the opening quote and the cursor is split at its last separator. The part before it
is joined to the declaring file's directory, which is the base `require` and `autoload` both resolve
against, and listed through `nvs_hir::autoload::entries_of`. Names are offered as the disk spells them
(`rule:programs/path-case`), names starting with `.` are hidden, and each item's text edit replaces
only the segment after the last separator. A directory item writes a `/` and runs the editor's
suggest command. Nothing is offered once the directory part holds a `*`.

`completion.rs` itself reads no filesystem, which is what
`rule:ide/completion-offers-only-what-the-compiler-derived`'s guard test checks. The listing is the
compiler's, so a name offered is one resolution would find.

### 3. Three more trigger characters, each answered only inside a path literal

A client offers nothing inside a string unless asked, so without a trigger the list would need
Ctrl+Space every time. `'` and `"` open a path literal and `/` extends one. Each is far more often
something else, so `continues_a_trigger` answers them only where the cursor is inside a `require` or
`autoload` path literal.

### 4. A directory link is a URI ending in `/`, and VS Code reveals it

A directory cannot open in an editor tab. The server stays on the standard protocol and marks a
directory the way a URI does, with a trailing `/`. The VS Code client's `provideDocumentLinks`
middleware rewrites such a target into `command:revealInExplorer?<the directory>`. No trust setting is
added: `isTrusted` is a field of a `MarkdownString`, and a `DocumentLink` has no such field.

## Consequences

What this spends: one span per `autoload` literal per compile, kept in `Site`. A `PathBuf` and one
existence test per literal per link request, in the server only. One directory listing per completion
request inside a path literal. Nothing on the request path at run time.

Another client receives a directory link as an ordinary `file:` URI and opens it however it opens a
directory.

## Alternatives rejected

- **Resolving the root in `crates/nvs-lsp`.** A second copy of the resolution rule, which is what the
  links module refused before this record.
- **A `std::fs` listing in `completion.rs`.** It would bypass the guard that keeps every completion
  source on a table the compiler builds, and could disagree with what resolution finds.
- **Marking a directory link in `data` or `tooltip`.** Both are free-form fields a client has to know
  about. A trailing `/` is what a URI already means by a directory.
- **Turning on `editor.quickSuggestions` for strings in the extension.** It opens the editor's
  word list inside every string in the file, not only in path literals.
