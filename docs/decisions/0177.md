# ADR 0177 — `Core\Sse` is one type behind two doors, its waits are derived rather than configured, and every framing hazard is refused instead of stripped

- **Scope:** the event-stream surface — the two doors onto it, what `receive()` means on each, the
  three refusals its framing has, the two waits an operator does not write, and the headers it opens
  with. It decides nothing about the body a stream writes into, which [0176](0176.md) owns, and
  nothing about the isolate a connection is, which [0083](0083.md) owns.
- **Depends on:** [0083](0083.md), [0176](0176.md).
- **Validated by:** `tests/conformance/core/an-event-stream-refuses-what-a-client-could-not-act-on.nvst`,
  `tests/conformance/core/an-event-stream-that-ends-with-its-request-frames-every-event.nvst`,
  `crates/nvs-server/src/bounds.rs`'s cases over the derived beat and the drawn hint.

> **In short:** one `Core\Sse` type is reached through both of 0083 § 5's hand-overs — a connection
> the request hands over to, and a body the request writes itself — and each member that only one
> door can serve refuses honestly on the other rather than being split into a second type. Its two
> time bounds are *derived*: the keep-alive from the wait that would otherwise close the stream, and
> the reconnection hint by a per-stream draw around the number the server holds, so neither is a
> constant an operator has to discover. Every way a payload could corrupt the framing is a refusal
> at the call site, never a silent repair.

## Context

0083 § 5 gives the event stream the socket's isolate and a different door, and stops there. What it
does not settle is everything a program actually writes: which type it holds, what `receive()` does
when there is no peer, what happens to an event name containing a newline, how long a quiet stream
stays open, and what a client is told to do when the instance it is attached to goes away. Each of
those has an answer that is either a refusal or a number, and a number nobody chose is the failure
`rule:concurrency/connection-bounds-are-finite` exists to prevent.

The pressure against one type is real and is why this is written down. The two doors have different
lifetimes — one outlives its request, the other ends with it — and a type whose members are not all
available on both looks like two types that were not separated. The pressure the other way is that
a helper taking a `Core\Sse` and writing events into it should be writable once and callable from
both sides, which is the whole reason a shared type is worth having.

## Decision

### 1. One type, two doors, and a refusal where a door cannot serve a member

`Core\Sse::upgrade` opens the connection-scoped door and `Core\Sse::stream` the request-scoped one.
Both answer the same type, so a function taking `Core\Sse` and writing events is written once and
called from either side — the shape `Core\Socket::current` already has for code that runs inside a
connection.

Where a member cannot mean anything on a door, it throws rather than being absent. A narrower writer
type for the request-scoped door would remove the throw and take the reason for one type with it, and
the member each door is missing is already the thing `rule:concurrency/two-doors-one-isolate` says
each hand-over reports for itself.

### 2. `receive()` is topics-only, and § 5's "no receive" is about the peer

0083 § 5 gives the event-stream isolate "`send` and no `receive`". Read as a statement about the
*wait*, that leaves a connection isolate able only to poll, which is the thing server-sent events
exist to avoid. Read as a statement about the *peer* it is exactly right and costs nothing: an SSE
client cannot send on the stream, so there is no second source of frames for a wait to select over.

So `receive()` on a connection-scoped event stream waits on its subscriptions and answers a topic
message. On the request-scoped door it throws `LogicError`: there is no isolate for the wait to park
in, and a request that parked on one would be a request that never ends. A frozen record is not
edited when a later decision refines what it rests on, so § 5 keeps its sentence and this section
carries the reading.

### 3. Three refusals, all `LogicError`, and none of them a repair

An `$event` or `$id` carrying `\n`, `\r` or NUL is refused. Stripping the byte would silently change
an event's name — the thing a client dispatches on — and a NUL makes a client discard the id outright,
so a repair here produces a stream that works and delivers the wrong events. An empty `$data` is
refused because a client provably does not dispatch an event whose data buffer is empty: it is a send
that cannot arrive, and a send that cannot arrive is a program error. And `setStatus` on a path that
opens an event stream is refused, because an event stream is `200` by protocol; that is the same
answer the both-cells-filled `500` already gives to a contradiction, rather than picking a winner.
`Core\Response::stream` takes any status — the refusal is the event stream's alone.

The payload itself is classified rather than refused. `$data` accepts a `tainted` value, for the
argument `Core\Response::json` already makes: framing belongs to us and to the serializer, and
normalization happens before the payload is split, so a payload cannot escape its `data:` lines.
`$event` and `$id` are sinks under `rule:security/unclassified-parameter-refuses-tainted` — a client
dispatches on the name and sends the id back in `Last-Event-ID`, so an attacker-chosen one is a live
cross-tenant hazard.

### 4. Both waits are derived, so neither is a number an operator discovers

The keep-alive is read off the wait that would otherwise close the stream — half of it, floored at a
second wherever the wait leaves room for one. Halving is what makes it a bound rather than a race: a
beat equal to the wait writes its keep-alive at the instant the connection is already being closed
for not having written one, and one scheduling delay either way decides which happens. Deriving it
means an operator who changes the write wait does not then have to find a second number that agrees
with it.

The reconnection hint is drawn **per stream**, spread by up to a third either side of the number the
server holds. A constant tells every client of a drained instance to come back at the same moment, so
the instance replacing it takes the whole fleet in one arrival — the same argument
`rule:http-server/retry-is-opt-in-jittered-and-closed` makes outbound, reachable here because a
deploy drains every connection a process holds at once. Full jitter from zero, which the database
client uses, is wrong for this wait: it is the single gap before a client returns rather than a
backoff against a contended resource, and a client drawn near zero reconnects into the restart it was
told to wait out.

### 5. The head says `no-transform` and `X-Accel-Buffering: no`, and that is not a proxy feature

A production deployment of this server is a proxied origin by definition
(`rule:http-server/two-deployments-and-nothing-a-proxy-owns`), nginx buffers proxied responses by
default, and that one default breaks server-sent events completely — the client receives nothing
until the response ends, which for a stream is never. `X-Accel-Buffering: no` beside
`Cache-Control: no-cache, no-transform` is an *instruction to* a proxy rather than a proxy behaviour
implemented here, so that rule's closed list of absences is untouched. Caddy, HAProxy and Envoy need
nothing.

### 6. Resumption is `Last-Event-ID` read off the request, and there is no replay buffer

A connection isolate shares nothing with the request that opened it
(`rule:security/isolate-shares-nothing`), so it cannot read the header itself; the handler reads it
and passes it through `args:`. The request-scoped door reads it directly, being in the request
isolate already.

A runtime ring buffer would be a bounded lie about durability: it would answer some resumptions and
silently not others, with the boundary decided by how fast the client reconnected. Replay needs the
application's own event log, and the id is the key into it.

## Consequences

A request-scoped event stream is reconnected by `EventSource` when the request ends, and that is
documented rather than fought — the request-scoped door is for `fetch`-based readers and for progress
UIs that close themselves, and a handler that wants the client to stop answers a non-`200` on the next
request. This is what keeps the two doors distinct rather than two spellings of one job.

What it spends, per `rule:programs/memory-priority`'s ordering: one wake pair and one chunk in flight
per open stream, plus the framing buffer and the subscriber queue a connection already pays for, and
one draw from the random number generator per stream opened. That is O(in-flight) and never O(events
sent), and a non-streaming response is untouched.

## Alternatives rejected

**A `send`/`sendJson` split**, on `Core\Socket::send`/`sendBytes`'s precedent. More consistent with
the sibling class, and rejected anyway: it doubles the surface for a distinction the caller never has
to make. `send(mixed $data, …)` sends a `string` raw and JSON-encodes anything else, and
`send($order, event: "order")` is the line people write.

**A narrower writer type for the request-scoped door**, which would make every member available on
the type that declares it and remove § 1's throw. It also removes the reason one type exists — a
helper written once against `Core\Sse` and called from both sides — and replaces a runtime refusal
with a design a reader has to learn twice.

**A replay buffer in the runtime**, covered in § 6.
