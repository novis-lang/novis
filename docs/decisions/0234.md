# ADR 0234 — A method that overrides or implements a documented method inherits its doc comment under `--strict-docs`, and `nvs doc` shows it

- **Scope:** which public members `nvs check --strict-docs` reports (`E0326`), and what `nvs doc` shows
  for a method with no `///` of its own. Properties, constants and every other diagnostic are unchanged.
- **Depends on:** [0137](0137.md) (`--strict-docs` reports a public member with no doc comment, and
  `nvs doc` renders the `nvs meta --json` document), [0233](0233.md) (the document names a class's
  parent and interfaces).
- **Validated by:** `crates/nvs-cli/tests/strict_docs.rs`
  (`strict_docs_accepts_an_override_of_a_documented_method`,
  `strict_docs_reports_a_subclass_method_that_overrides_nothing`) and `crates/nvs-cli/tests/doc.rs`
  (`nvs_doc_shows_an_undocumented_override_the_doc_it_inherits`).

> **In short:** `--strict-docs` reported every undocumented public method, including one that only
> implements an interface method or overrides a parent method that is already documented. Such a method
> now inherits the ancestor's doc comment and passes. The ancestor is found by name, through the parent
> class, the implemented interfaces, and whatever those extend or implement in turn. `nvs doc` shows the
> inherited comment under the method, with a line naming where it comes from.

## Context

A package that defines an interface documents each of its methods once, on the interface. Every class
that implements it then had to repeat the sentence above each implementation to pass `--strict-docs`,
and the same held for each override of a documented parent method. That repetition is the generated
noise `rule:tooling/strict-docs` exists to avoid: the sentence says nothing the interface does not, and
it drifts from the interface's sentence when only one of them is edited.

## Decision

1. **A public method with no `///` passes when an ancestor documents a method of the same name.** The
   ancestors are the parent class and the implemented interfaces, followed through every `extends` and
   `implements` at any depth, over the class graph the compiler already built. The member table records
   which method names were declared with a doc comment, so the check is a walk over names it already
   has.
2. **Only methods inherit.** A property or a constant redeclared on a subclass is a new declaration
   with its own value, and it is reported as before. A method whose ancestor is itself undocumented is
   reported, and so is the ancestor.
3. **`nvs doc` shows the inherited comment.** It follows the document's `extends` and `implements` keys
   from [0233](0233.md) to the nearest documented method of the same name among this run's pages, and
   writes `Inherited from <Owner::name>.` before that method's card. A method inherited from a `Core`
   class or interface shows no card, because a `Core` member has no page in this run.

## Consequences

An interface's documentation is written once and read on every implementation's page. The check costs
one walk up the class graph per undocumented public method, at `--strict-docs` time only, and the member
table holds one more set of names per class. Nothing changes at run time.

## Alternatives rejected

- **An explicit marker such as `/// @inheritdoc`.** It is a third tag, which
  `rule:tooling/doc-comment-tags-are-see-and-example` refuses, and it is a line that says nothing, which
  is what the rule exists to prevent.
- **Inheriting only from interfaces.** Overriding a documented parent method has the same problem, and
  one rule for both is simpler.
- **Copying the inherited comment into the `nvs meta --json` document.** The document would then say a
  member has a doc comment it does not have, and a consumer could not tell the two apart. The renderer
  follows the edges the document already carries.
