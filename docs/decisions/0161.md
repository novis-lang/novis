# ADR 0161 — `nvs serve` accepts on one worker per core over every listener, and the compiled unit is published once for the fleet

- **Scope:** how many accept loops a served process runs, what each of them binds, which key bounds
  the count, and what the cores share. It decides nothing about how a request is resolved once
  accepted ([0097](0097.md) § 4), nothing about the in-flight ceiling's arithmetic
  ([0106](0106.md)), and nothing about the drain that stops the process ([0078](0078.md),
  [0154](0154.md)) beyond the fact that a fleet has more than one loop to stop.
- **Depends on:** [0097](0097.md) § 5 for the `[server]` block and its listeners, [0017](0017.md)
  for the compiled-unit cache and its single publisher, [0006](0006.md) for an isolate sharing
  immutable compiled code and nothing else, [0004](0004.md) for what the fan-out is allowed to
  spend.
- **Validated by:** `benches/serve-proxied.json`'s two arms, and the fan-out's own checks —
  `crates/nvs-cli/src/serve.rs`'s `a_server_workers_key_bounds_the_count_and_defaults_to_available_parallelism`
  beside the entry and worker cases § *Verification* names.

> **In short:** a served process runs **one worker per core**, each with its own scheduler, its own
> accept loop and its own handle on **every** listener the tree named — not one core that accepts and
> hands connections on, which would make the accepting core the bottleneck the fan-out exists to
> remove. `[server] workers` bounds the count and defaults to the machine's available parallelism, is
> taken as written in both directions, and has no `auto` spelling. The compiled unit stays **one** for
> the whole fleet: it is published once behind an `Arc` every core reads, so "compile exactly once"
> stays a count per source rather than a count per source per core.

## Context

`nvs serve` binds one socket and accepts on the thread that bound it. Every primitive the fan-out
needs is already built and reached only from tests: `nvs_host::NvsListener::from_std` exists so that
each core can take its own handle on a descriptor, and `nvs_host::Worker::spawn(cpu, …)` pins a
scheduler per core with a handshake that makes `Worker::pinned` answerable rather than racing. What
was missing is the command that calls them and the key that says how many.

The cost is measured rather than assumed. `benches/serve-proxied.json` holds two rows for the same
case against the same peer: with one CPU each, `nvs serve` leads php-fpm by `2.9157`; with four CPUs
each, that lead is `1.186`. FPM spends the three extra cores and this server does not, so the ratio
falls with every core the box gains. On a bigger machine it inverts.

## Options considered

- **One acceptor, N request workers.** The accepting thread hands each accepted connection to a
  worker. It is the smaller change and it keeps one listener handle, but the acceptor is a single
  thread doing a syscall per connection and a handoff per connection, which is the bottleneck being
  removed rather than a different place to put it.
- **One process per core, as php-fpm does.** Rejected by [0097](0097.md)'s premise: the whole point
  of the built-in server is that it is one process with one memory budget and one compiled unit, and
  N processes would compile N times and hold N caches.
- **A worker per core, each accepting on its own handle.** Taken. The kernel picks which blocked
  acceptor a connection wakes, so there is no handoff, no shared queue and no thread that every
  connection passes through.

## Decision

### 1. Every listener is bound before any core is started

The listeners are bound once, at boot, in the order `[server] listen` wrote them, and each worker
then takes its own handle on each of them. Binding is therefore a boot step with one outcome: a
process that is listening on everything the tree named, or one that refused and started nothing.

That is also why an entry this build has no listener for — a Unix-domain socket on a platform
without one — is refused **once**, before the first worker exists. A fan-out that classified as it
started would report one deployment mistake once per core and would leave a half-listening process
behind while it did.

### 2. One worker per core, and `[server] workers` is the count

Each worker is a pinned OS thread with its own scheduler, its own run queue and its own accept loop,
which is `design.md`'s thread-per-core shape and what [0106](0106.md)'s relaxed in-flight counter and
[0097](0097.md) § 5's per-worker watchdog were already written against.

`[server] workers` bounds the count. With the key absent it is `std::thread::available_parallelism`,
and one core on a host that answers nothing, so a deployment moved to a bigger box scales without an
edit. A written count is the bound in both directions — not raised to the machine's parallelism, not
clamped down to it. A clamp would make the effective core count something the file cannot state, and
the operator who sized a container against its CPU quota is better informed about the box than this
process is. There is no `auto` spelling: leaving the key out is how the machine is asked.

### 3. The compiled unit is one for the fleet, with one publisher

Every mounted entry is compiled before the first socket is bound, and the unit is published once
behind an `Arc` that every core reads — [0006](0006.md)'s "shares immutable compiled code", which is
the exception shared-nothing already makes, and [0017](0017.md)'s single publisher for the
revalidation that replaces it. Per-core caches are rejected: they cost N compiles of the same file
and would make [0017](0017.md)'s "compile exactly once" mean something different at four cores than
at one.

What a core does **not** share is everything else it holds: scheduler, run queue, accept loop,
backoff window, and the isolates running on it. A request stays on the core that accepted it.

## Diagnostics

`E0636` for `[server] workers` written as `0`: every listener is accepted on by a worker, so zero
workers is a process that binds the addresses the tree names and answers nobody on any of them —
`E0620`'s empty `listen` array reached from the other end. Only zero is refused; a count above the
machine's parallelism is what the operator asked for and is started.

## Consequences

- The proxied bench's four-CPU arm becomes a comparison of two runtimes using four cores rather than
  of one using four against one using one.
- What it spends, per [0004](0004.md): one scheduler, one accept loop and one listener handle per
  listener per core, all paid at process start and O(cores) rather than O(requests served). The
  shared unit cache holds strictly less than N per-core caches would, so the fleet's compiled-code
  footprint does not grow with the core count at all.
- Anything that must be true of "the server" rather than of a core now has a fleet to be true of: the
  drain state every core reads, the in-flight ceiling divided across cores, and the watchdog reading
  each worker's own deadline.
- A deployment that wants one core says so in one line, and the number it writes is the number it
  gets.

## Alternatives rejected

- **Clamping `workers` to the machine's parallelism.** It reads as safety and is not: the count is
  already bounded by the file, the CPU quota a container was given is invisible from inside the
  process in the general case, and a directive silently overridden is the failure mode
  [0106](0106.md) accepted logging for only because *there* the competing bound is a memory budget
  the operator cannot see.
- **An `auto` spelling.** A second way to write the default is a second thing to explain and a place
  for `auto` to come to mean "and also something else". Leaving the key out already means "ask the
  machine".
- **Reading a core count from the environment.** The configuration is the one place a deployment is
  stated ([0005](0005.md)); a second input for one number would be the first exception.

## Verification

- `a_server_workers_key_bounds_the_count_and_defaults_to_available_parallelism` — the default is the
  machine's own parallelism, a written count wins below **and above** it, and `0` is `E0636`.
- `every_entry_of_server_listen_is_bound_rather_than_the_first` and
  `a_unix_domain_entry_is_refused_once_rather_than_once_per_core` — the listeners, and the refusal
  that happens before any core.
- `one_worker_is_spawned_per_core_and_each_takes_its_own_listener_handle` — the fan-out itself.
- `a_compiled_unit_is_read_by_every_core_through_one_arc` and
  `the_compile_counter_counts_compiles_and_not_cores` — one unit, N readers, one compile.
- `benches/serve-proxied.json`'s deployed arm, re-run: the ratio moves with the core count instead of
  staying where the single-core arm left it.
