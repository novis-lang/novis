# ADR 0251 — A `foreach` binding may write `var` wherever a local declaration may, and means what it means there

- **Scope:** The type position of a `foreach` key and value binding, `inout` included: what `var`
  there gives the binding, and the one subject it refuses. `catch`, destructuring, parameters,
  properties, constants, closures and returns keep their written types, and are not decided here.
- **Depends on:** [0037](0037.md) (`var` takes a local's type from its initializer),
  [0053](0053.md) (what a `foreach` subject may be, and what its bindings type as),
  [0007](0007.md) (every binding declares its type).
- **Validated by:** the Stage 2 checks of goal `foreach-var`: three parser tests in
  `crates/nvs-syntax/src/parser/tests/stmt.rs`, seven checker tests in
  `crates/nvs-types/tests/locals.rs`, and the two `.nvst` cases named under *Verification*.

> **In short:** `foreach ($users as var $u)` gives `$u` the subject's element type, and
> `foreach ($stock as var $name => var $qty)` gives `$name` a `string`, each fixed for good as a
> written type is. The subject plays the part a `var` local's initializer plays, so a `mixed` subject
> gives `mixed`, a qualifier on the element type arrives on the binding, and a bare array literal
> under a `var` value binding is `E0414`, the local's code. `inout var` binds at the element type
> itself. A written type is still accepted everywhere, and is what a binding wider than the element
> writes.

## Context

### 1. The loop header repeated what its subject already said

`for (var $i = 0; …)` parses (`rule:iteration/for-init-clause`), and `foreach` was the one loop
header `var` could not appear in. Its value binding is the most common binding after a local, and
the checker already holds the element type before it reaches the binding: the subject is classified
first, and the binding's written type is then checked against what the subject gives. So the
written type said nothing the checker did not already know.

## Decision

### 2. One sentence, answered by asking what a `var` local does

A `foreach` binding may write `var` wherever a local declaration may, and means what it means
there. The subject is the binding's initializer:

- the **value** binding takes the subject's element type — `T` for an `array<T>`, an `Iterable<T>`
  and an `Iterator<T>` alike — and a subject with no element type (`mixed`, `iterable`, or one
  already refused) gives `mixed`, which is what `var $x = $mixed;` gives;
- the **key** binding takes `string`, the one type an array's key binding may have
  (`rule:types/arrays`); over a cursor it is still `E0444`, because a cursor has no key;
- the type is then fixed on the binding, and passes through the same `void`/`never` refusal a
  `var` local's does.

`inout var $v` binds at the element type exactly, so `rule:statements/inout-is-the-by-reference-spelling`'s
"both sides declare the same type" holds by construction.

### 3. The one refused subject

A bare array literal under a `var` **value** binding is `E0414`, the code `var $x = [1, 2];` gets,
for the same reason: a literal is checked against a target and infers none. A call around the
literal gives it a target, so `foreach (f([1, 2]) as var $x)` is fine. A `var` key over a literal is
not refused, since its type comes from the array's key and not from the literal's elements. No new
code: the message is true of both sites, and the help line names the fix that fits a loop header —
a typed local first.

### 4. How the type crosses to lowering

A `var` binding's span is recorded with the type the checker gave it, in the table that already
carries every written annotation's resolved type, and lowering erases it the way it erases a
written one. The two spellings of one loop lower the same.

## Consequences

- Performance: nothing. `var` is gone before any IR exists.
- Memory: nothing.
- Usability: a shorter loop header, and the type the subject states is no longer written twice.
- Simplicity: one more position where a type is not visible in the source. An editor's inlay hint
  shows it; a diff shows nothing.

A `mixed` subject still does not lower — a gap in `nvs-ir` this record neither closes nor widens —
so `var` over one is pinned by a checker test, not by a program that runs.

## Alternatives rejected

- **`var` in `catch`, destructuring and the other binding sites.** A `catch` type is the filter,
  not an annotation, and the others have no single expression to take a type from.
- **A new code for the literal subject.** The local's message is true here too, and one mistake gets
  one code.
- **Letting an untyped `as $v` mean `var`.** The binding would look like PHP's and mean something PHP
  does not; `var` says in the source that the type was taken.
