# ADR 0218 — every file a program reached is checked in the background, in every mode, and a change is compiled whole from a quiet tree before it is swapped in

- **Scope:** how a running process notices a source change and gets it to the next request: what a
  compiled unit is keyed on, what a check of it looks at, where that check runs, when a changed
  program is compiled, and how the mount table follows the disk. It removes `[opcache] validate =
  "never"` and adds `[opcache] settle`. It does not decide how a *configuration* change is applied,
  which keys still need a restart, or anything a reload reports — the second record this work
  writes owns those.
- **Depends on:** [0017](0017.md) for the unit table, its path pointer and the single-flight
  compile; [0042](0042.md) for the on-disk artifact cache and its whole-program key;
  [0061](0061.md) for `autoload` and the discovery query; [0097](0097.md) and [0200](0200.md) for the
  mount table; [0091](0091.md) for the mode's startup rows.
- **Validated by:** `crates/nvs-cli/tests/live_edit.rs`, which starts the built `nvs serve` over a
  program in a temporary directory, edits the tree, and polls until the answer changes; and
  `crates/nvs-config`'s tests that `validate = "never"` does not load and that `settle` has its two
  mode defaults.

> **In short:** a source change never needs a restart or a reload, in any mode. A compiled unit is
> keyed on its whole program — every file the compile read, the `autoload` paths it probed, the
> directories a discovery query listed — and a task on the compile pool checks every loaded program
> once per `revalidate_freq`, so no request spends a file-system call on revalidation. A changed
> program is compiled only once no file of it has moved for `[opcache] settle`, from the real
> directory its root link names; a compile during which anything moved is thrown away and retried.
> Only a finished compile is swapped in. A `[[server.mount]] scan` is expanded again by the same
> check. `validate = "never"` is gone: `mtime` is the default in both modes, and `hash` stays.

## Context

### 1. Production never saw a code change

`validate = "never"` was production's startup default ([0091](0091.md) § 3a), and it did what it
said: a path compiled once was answered from the table for the life of the process. A reload did
not help, because it re-keys the table only when the extension set moves, and reported
`invalidated: 0` while the old code kept serving. The only deploy was a restart, and a restart is an
outage for every connection the server holds, and a deploy that forgets one is a server running
code nobody can see on disk.

### 2. Development saw only the entry file

The in-memory key hashed the entry file's content, the `autoload` probe trace and the environment.
An edit to a `require`d file or to an autoloaded class moved none of the three, so it was invisible
until the entry file itself changed — and then everything recompiled at once. The on-disk artifact
cache already keyed on the whole program (`crates/nvs-cli/src/cache.rs`, `program_digest`), which is
why a restart was always correct and the running process was not.

### 3. The check was on the request path

[0017](0017.md)'s five steps put the `stat` in the resolve: the first request after
`revalidate_freq` paid for it, and on a change it also paid for the compile, or waited behind the
flight another request started. A request that arrived during a `git pull` could compile a program
from half of the old tree and half of the new one.

### 4. The mount table was built once

`[server.mount] scan` expanded against the disk at boot. A module added under a scan needed a
restart, and the reference's claim that a reload re-expands it was not true.

## Decision

### 1. The user's rule

**A source change never needs a restart or a reload, in any mode.** Where a design choice makes this
harder, this rule wins over latency, simplicity and memory, and never over security. Everything
below follows from it.

### 2. A unit is keyed on its program

A compile records **every file it read**, with the stamp (`mtime` and size) and the digest it read.
The unit's key is the whole-program digest the artifact cache already computes, beside the probe
trace ([0061](0061.md)'s negative entries, kept as they are) and the environment. The path pointer
names that key. Two entry files that reach the same program, byte for byte, share one unit.

A **check** of a unit looks at all of it: every file the compile read, every `autoload` path it
probed (misses included), and every directory a discovery query listed. Under `mtime` a file whose
stamp did not move is not read; under `hash` every file is re-read and re-hashed. A directory's
stamp is compared, and one that moved is listed again; the sorted list of discovered names is what
joins the key, so a listing that changed without changing what was discovered recompiles nothing.

### 3. The check runs in the background

**No request makes a file-system call to revalidate.** A task on the compile pool checks every
loaded program once per `revalidate_freq`. A request resolves a path to the unit its pointer names,
and that is a map lookup. A path nothing has resolved yet is a cold compile, as it always was.

On a change, the task compiles the new program and only then swaps the pointer, so no request waits
for a recompile of a program it already had. An idle server takes a change within `revalidate_freq`
plus `settle`, with no request needed to trigger it. The swap keeps [0017](0017.md)'s rule that it
publishes only where the pointer still names what the check started from.

### 4. `[opcache] settle`: a program is compiled from a quiet tree

`settle` is how long no file of a program may have changed before it is compiled. The check that
sees a change waits until every file's stamp has been still for that long. After the compile it
checks every file again, and **a compile during which any file changed is thrown away** and retried
once the tree is quiet. A fast deploy — `git pull`, `rsync`, an unzip — is compiled once, from the
finished tree.

`settle` is `System`-class and reloadable, for the reason `revalidate_freq` is: a request that could
set it could hold a fix back, or force a compile per keystroke of somebody else's deploy. Its default
is `"1s"` in production and `"100ms"` in development, chosen by the mode as a startup row
(`rule:config/a-startup-default-is-never-flipped`). It takes the row `validate` leaves, so the two
tables still have eight rows between them.

### 5. An atomic deploy is atomic

At the start of each compile, the entry file's path is resolved through every symlink and junction
once, and every file the program names is read through the real directory that gives. After the
compile, the path is resolved again, and a different answer means the compile is thrown away. A
deploy that switches a `current` link from one release to the next can therefore never produce a
program built from both.

A slow copy into the directory being served can still be seen half done, if it pauses for longer
than `settle`. No compiler can tell a pause from the end. The reference says to switch a link to a
finished directory for that case, and that way is always safe.

### 6. `validate = "never"` is removed

`validate` takes `mtime` or `hash`. `mtime` is the default in both modes; `hash` is the stricter one,
for a file system whose stamps cannot be trusted. A configuration that writes `never`, or the boolean
`false` that meant it, **does not load**. It is removed rather than deprecated because the one thing
it did — pin the code the process started with — is the thing this record ends, and a value kept for
compatibility would keep the outage it caused.

### 7. A deleted file, a broken edit, a reverted edit

A file a program still reaches that is **deleted** makes that program's next compile fail, and its
requests fail loudly (`rule:config/a-broken-edit-fails-the-requests-that-resolve-it`, unchanged). A
**broken edit** is the same: the pointer stays on the last program that compiled, and the requests
that resolve the path get the failure, which is compiled once and answered from the table after
that. The last good version is never served in its place.

A **reverted edit** is answered from the unit already compiled for that content. The table keeps,
per path, the unit in force and the one it replaced, so undoing the last change is a pointer swap
and not a compile.

### 8. Memory stays bounded

A unit that is neither the one in force nor the one before it is freed when the last request holding
it ends. A server that has seen ten thousand edits holds units in proportion to its entry files,
never to its edits (`rule:programs/memory-priority`).

### 9. The mount table follows the disk

A `scan` is expanded again under the same background check: each scanned directory's stamp is
compared, and one that moved is listed again. A new module is compiled, has the boot-time `origin`
check run on it, and is served. A removed module answers `404`. A new module that does not compile
fails its own requests and nothing else. An explicit mount whose entry file appears or disappears is
the same case.

A path is still never derived from a URL (`rule:http-server/a-path-is-never-derived-from-a-url`): the
table is enumerated from the configuration's globs, only more than once. Every expansion checks
every path it produced against `[server] root`. A match that boot would refuse is logged and left
out, and the rest of the table is published.

## Diagnostics

`validate = "never"` and `validate = false` are a load error, reported the way the configuration
crate reports any value outside a directive's set: the key, the value written, its file and line,
and the two values that remain, `mtime` and `hash`. `nvs config check` reports the same error.

A background compile that fails is logged once per program content, with the spans the front end
reports, and is the same failure the next request to resolve that path is answered with.

## Consequences

- **Performance:** one `stat` per loaded file per `revalidate_freq`, in the background, and none on
  the request path. A directory a discovery query or a scan listed costs one more `stat` each. A
  change costs one compile per program, once the tree is quiet — never one per request, and never
  one per file a deploy touched.
- **Memory:** a file list per unit, with a stamp and a digest per file, and two units per path while
  a swap is possible — the one in force and the one before it. Bounded by the program's text and its
  entry files, never by edits or requests.
- **Usability:** there is no deploy step. A copy, a pull or a link switch reaches the next request
  within `revalidate_freq` plus `settle`, in production as in development.
- **Simplicity:** `validate` has two values instead of three, and no mode needs a restart to see
  code.
- **Startup:** production no longer skips reading source at a warm start. Every file a program
  reached is `stat`ed at the first check, which is the price of seeing a change at all.

## Alternatives rejected

- **A file-system watcher** (`inotify`, `ReadDirectoryChangesW`). It needs a platform backend each,
  it loses events under load and on network file systems, and a lost event is a deploy that never
  arrives. A timed `stat` of a known list is bounded, portable and cannot miss a change.
- **Keeping `never` for operators who want it.** It is exactly the outage this record removes, and
  the cost it saved is one background `stat` per file per window.
- **Serving the last good version when a deploy does not compile.** Rejected in
  [0017](0017.md) and not reopened: an edit that is a security fix must never be silently ignored.
- **Checking on the request path, as before, but for every file.** Correct, and it puts the
  whole-program `stat` and every recompile in front of whichever request arrives first.

## Verification

`crates/nvs-cli/tests/live_edit.rs` holds one test per claim above that a request can see: an edit to
the entry file, a `require`d file and an autoloaded class in production; a new class file, a file
that shadows a probe miss, and a new module under a discovery directory; a deleted file, a broken
edit and its fix, a reverted edit; a queue job and a scheduled fire; a running WebSocket; no
revalidation `stat` from a request; a compile before the swap; an idle server; a fast copy compiled
once; a change during a compile; a link switch during a compile; ten thousand edits; and the four
mount cases.
