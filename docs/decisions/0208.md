# ADR 0208 — A directory handed to `nvs test` is one program that requires every `.nvs` file under it

- **Scope:** what `nvs test <directory>` runs when the directory holds `.nvs` files, where that
  program's `autoload` map comes from, and which files the editor lends a map to so the directory reads
  as it runs. The `#[Test]` table, the report formats and the `.nvst` case tree are unchanged.
- **Depends on:** [0207](0207.md), [0198](0198.md).
- **Validated by:** `crates/nvs-cli/tests/test_dir.rs` and
  `a_plain_file_under_a_lenders_directory_borrows_its_map` in `crates/nvs-lsp/tests/autoload.rs`.

> **In short:** a test program used to need an entry file that named every test file by hand, and a
> large suite pays for that list on every file added. A directory named to `nvs test` is now one
> program: the runner writes an entry that requires every `.nvs` file under it in name order, never
> puts that entry on disk, and runs the program's test table. The directory brings its own bootstrap —
> one file in it requires the application's bootstrap file — and the editor lends that bootstrap's map
> to every plain file under the same directory, so the two agree about what a test file resolves.

## Context

The testing reference said there was no directory scan, on purpose: a program's test table is built
by the compile, so a test file is in the program only if something requires it. A developer with
several applications and growing suites asked for a way to run a whole test directory without listing
each file. They also believed the hand-written `require` order fixed the test order; it does not
(`rule:testing/runner-is-strict` reports in declaration order, classes in name order), so the list
bought nothing but the compile.

Two things made the obvious spelling hard. A directory handed to `nvs test` already meant a tree of
`.nvst` cases, decided off the extension alone. And a directory of test files has no entry point, so
nothing said where its `autoload` map would come from — the `main.rs` comment on `is_program` said as
much.

## Options considered

1. **A directory of `.nvs` files is one program, and the bootstrap is whichever file in it requires
   the application's bootstrap.** Chosen: no flag, no configuration key, and the editor's existing
   lending extends to it.
2. **A glob in a literal `require`**, `require 'tests/*Test.nvs';`. Coherent with the walk and free
   for the editor, but a `require` site is one call to one file's script frame in the IR
   (`ExprTypeTable::record_require_target`), and a site that expands to many files reaches into
   `nvs-types` and `nvs-ir` for a feature the tests never execute.
3. **A `[test]` block naming a bootstrap and directories.** The configuration is per server and an
   application's tests are per application; the editor does not read a `--config`; and a suite needs
   a setting before its first run.
4. **A `--bootstrap` flag beside the directory.** Every run spells it, and the editor cannot see it.

## Decision

### 1. A directory holding `.nvs` files is a program

`Program::named_by` reads a `.nvs` file as the program it starts and a directory as a program when
any `.nvs` file lies under it, subdirectories walked. A directory holding `.nvs` and `.nvst` files
together is refused with the "run separately" error the mixed-path case already has, and a directory
holding only `.nvst` files is the case tree it was. One program per invocation, as before.

### 2. The entry is written, never stored, and never runs

`directory_entry` writes one `require` per file, relative to the directory and spelled with `/`, in
the walk's name order. `front_end_synthesized` overlays that text at a path under the directory whose
name no file there carries, so every `require` resolves against the directory exactly as a written
entry's would and the overlay never shadows a real file. Under `nvs test` the entry's statements do
not run, so the requires only bring each file into the compile; the test records name each test's own
file, since the table is built from where a `#[Test]` is written.

### 3. The bootstrap is a file in the directory

Nothing is added for the map: a file in the directory that requires the application's bootstrap is
required like every other file, and `rule:programs/autoload`'s union over the require chain gives the
program its declarations. A directory with no such file compiles as it is, and a test that names a
class outside it reports `E0306` there as it would if run by hand.

### 4. The configuration is folded for the directory

`boot_snapshot` is handed the directory. `[[app]]` matching canonicalizes what it is given and a
block's `root` covers anything under it, so a suite inside an application's root takes that block; an
`entry` key names one file and matches no directory.

### 5. The editor lends to a plain file under a lender's directory

A lender now keeps the directory of its entry. `Documents::lender_for` matches, after the files a
lender read and the files under its roots, a file under that directory whose text holds neither
`require` nor `autoload`. The two keywords are the same gate the survey uses: a file holding either
starts a program of its own, which is why a bootstrap-requiring file in a test directory lends and a
test file beside it borrows. A file under a lender's directory that starts its own program is
analysed as that program, `E0306` included.

## Consequences

- **Performance:** one directory walk per invocation before the compile, and a compile whose require
  count is the file count, which the hand-written entry already paid. In the editor, one text read per
  analysis of a file that lies under a lender's directory and matched nothing earlier. Nothing is on
  a request path of the runtime.
- **Memory:** one path per lender. The synthesized entry is one string for the run.
- **Usability:** `nvs test tests/` runs a suite, and a new test file is in it the moment it exists. A
  plain script beside an application's bootstrap is analysed through that bootstrap's map in the
  editor, which resolves names that `nvs run` on the script alone would not; the build's answer is the
  strict one, and the editor's is the answer for the program the directory is.
- **Simplicity:** one enum and two helpers in the runner, one field and one branch in the server. No
  language change, no configuration key, no flag.

## Alternatives rejected

- **Running each `.nvs` file under the directory as its own program.** A test file that requires
  nothing resolves nothing, and a report per file has no summary.
- **Requiring the bootstrap from every test file.** The mirror of the list this removes: one line per
  file across the suite instead of one per file in the entry.
- **Reading the directory as a program only when it holds no `index.nvs`.** A convention on a name the
  runner would have to explain, for a case the mixed-file refusal already covers.

## Verification

Through the built binary, `crates/nvs-cli/tests/test_dir.rs` runs a fixture application's `tests/`
directory and sees both its top-level test and one in a subdirectory, lists them with each test's own
file, runs a subdirectory on its own, and is refused on a directory holding both kinds of file. The
language-server suite pins a plain file under a lender's directory resolving through the borrowed map
and a file there that requires something analysed as its own program.
