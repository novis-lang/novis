# ADR 0200 — `nvs serve` needs no file over a written mount table, a mount table needs a written root, and a start that names nothing is refused

- **Scope:** what `nvs serve` serves when its command line names no file, which configuration that
  process reads, where a mount table is found, and what `nvs service install` asks of a stored
  `serve`. The rest of the mount table's rules are [0097](0097.md)'s and unchanged, and so is a
  start that names a file over a tree that writes no mount.
- **Depends on:** [0097](0097.md), [0104](0104.md), [0093](0093.md).
- **Validated by:** `a_start_with_no_file_serves_every_mount_the_configuration_writes` and
  `a_start_with_no_file_and_no_mounts_is_refused` in `crates/nvs-cli/src/serve.rs`,
  `a_serve_argv_with_no_file_is_stored_only_over_a_configuration_that_mounts_an_entry` in
  `crates/nvs-cli/src/service.rs`, `a_mount_table_with_no_root_written_is_refused` in
  `crates/nvs-config/tests/mount.rs`, `the_hosts_snapshot_folds_no_block_and_names_no_entry` in
  `crates/nvs-config/tests/snapshot.rs`, and the run under *Verification*.

> **In short:** `nvs serve <file>` required the file even where the configuration's
> `[[server.mount]]` table already named every entry the server would run, so a host of many modules
> had to pick one of them to start, and stopped starting when that one was removed. The file is now
> optional over a tree that writes mounts: the server serves that table whole and reads the global
> configuration with no `[[app]]` block folded. A start that names no file over a tree that writes no
> mount is refused, so nothing runs that nobody named. And a mount table with no `[server] root`
> written does not resolve at all: a server is told which directory it serves out of, and a mount
> only maps a URL onto a file under it.

## Context

A configuration whose one `[[server.mount]]` block is a `scan` over `*/public/index.nvs` mounts every
module under the root. Starting it needed `nvs serve <one of those files> --config …`, and the file had
to be one of the mounted entries or the start was refused. `nvs service install` stores an argv and
refuses one this binary would answer with a usage error, so a service over that configuration could not
be installed without naming one module absolutely — and the stored service then depended on that module
staying on disk, whatever the scan still found beside it.

The argument did two things. With no mount written it was the whole table: that file at `/`. And it
chose which `[[app]]` blocks the process's one snapshot folded. With a mount table written, the first is
already answered by the table.

An unwritten `[server] root` was the directory the process was started in. From a shell in the
project's directory that is the project; for a service it is the service manager's directory, and the
same `scan` finds a different set of files, or none.

## Options considered

1. **Optional only where `[[server.mount]]` is written.** Chosen.
2. **Optional wherever `mount::expand` gives a table**, which adds the implicit `public/index.nvs`
   mount of a tree that writes none. A bare `nvs serve` would then run a file that neither the command
   line nor the configuration named, found from a root that is itself a default.
3. **Keep the argument and let the installer pick a mounted entry.** The stored argv would name a file
   nobody chose, and the dependence on that one module would remain.

## Decision

### 1. With no file, a written table is served whole

`nvs_config::mount::expand` builds it, as it does for a start that names one of its entries. A start
that names a file over a tree that writes no mount is unchanged: that file at `/`, its own directory as
the mount root.

### 2. A start that names nothing is refused

No file and no `[[server.mount]]` is a refusal naming both ways out. `expand`'s implicit mount is not
reached from `nvs serve`. A table with no rows — a `scan` that matched no file — is refused too.

### 3. A named file must still be in a written table

A file the table does not mount is refused before a socket exists, as before. The message now also
names the third way out: name no file.

### 4. With no file, no `[[app]]` block is folded

`nvs_config::Snapshot::host` is the global tree alone, with `entry`, `mode`, `origin` and `blocks`
empty. `Snapshot::entry` is an `Option` for it. A reload re-resolves the same way the boot did, so a
process started with no file stays on the host's snapshot.

### 5. A mount table has a written root

`nvs_config::mount::check` refuses a tree that writes `[[server.mount]]` and no `[server] root`, so
`nvs config check`, every boot and the service installer all say so, and `expand` refuses an unwritten
root for a caller that only has the disk half. A relative root still resolves against the file it is
written in. A named file over a tree that writes no mount needs no root: its own directory is the mount
root, as before.

### 6. The installer asks for a table

`serve` with no file is a command line the parser takes, so the usage-error refusal no longer covers
it. `nvs service install` reads the configuration the stored argv names, and stores a `serve` with no
file only where the written table expands to at least one entry.

## Diagnostics

- The two refusals in § 2 are a sentence on standard error and exit status 1. There is no span to point
  into: the command line is what is incomplete, and every line of the configuration is well formed.
- An unwritten root under a mount table is `E0621`, the mount table's own code, pointing at the first
  block where the origin is known.
- The installer's missing table is `E0630`, on that code's own reasoning: the process would exit at
  once, which a service manager reports as a crash loop.

## Consequences

- **Performance:** none on a request path. A start with no file skips the `[[app]]` match; the
  installer runs one `expand` over the named configuration.
- **Memory:** unchanged. One snapshot per process either way.
- **Usability:** a host of many modules starts and installs with `serve --config <file>`, and removing
  any one module does not stop it. A process started with no file applies no `[[app]]` block to
  anything it serves, where naming a file applies that file's blocks to every mount; a host that needs
  per-application policy still has to name a file, and gets one application's policy for all of them. A
  configuration that writes mounts and no root stops resolving, for every command that reads it, until
  one line is added; the refusal names the line.
- **Simplicity:** the command has one optional argument in place of one required one, and `serve` has
  one function that answers what the table is. `Snapshot` gains a constructor and its `entry` becomes
  optional.

## Alternatives rejected

- **Folding every `[[app]]` block that matches any mounted entry.** A union is a configuration no one
  application was written against, and a capability one block grants would reach every mount.
- **Using the configuration file's own path as the entry.** An `[[app]]` block whose `root` covers the
  configuration's directory would match it, which reads as applying to the host and is not what the
  block says.
- **Resolving an unwritten `[server] root` beside the configuration file.** It makes a service find
  what the shell found, and it is still a root nobody wrote: the directory a server executes files out
  of is the one setting that should never be inferred.
- **Requiring the root only of `nvs service install`.** The same configuration would then mean one set
  of files from one shell, another from a second, and be refused by a third command.

## Revisiting

One snapshot serves every mount, so `rule:http-server/a-mount-carries-no-policy`'s per-application
policy reaches only the application a start names. A snapshot selected per mount would make the named
file irrelevant to policy, and this record's § 4 would then be the ordinary case.

## Verification

The suite pins a scan of two modules served with no file, the same table with one of them named, a
named file outside the table refused, a start with no file and no mount refused over a disk that holds
`public/index.nvs`, an empty scan refused, a mount table with no root refused by both halves, the
installer's answers, and the host's snapshot over a tree with three `[[app]]` blocks. By hand: a tree
whose one block is `scan = "*/public/index.nvs"` with `prefix = "/fw/{1:lower}.dev"` over two modules
and a written root, started as `nvs serve --config <file>`, printed `listening on
http://127.0.0.1:18471 — 2 mounted entries` and answered `200` at `/fw/blog.dev/` and `/fw/shop.dev/`
with each module's own output, and `404` elsewhere. The same block with no root was `E0621` from
`nvs serve` and from `nvs config check`, and a tree with no mount and no file named was refused with
the sentence in § 2.

Not run: `nvs service install` against a real service manager.
