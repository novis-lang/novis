# ADR 0247 — The image and intl components are built into every `nvs` binary, sandboxed and always present under `Novis\`

- **Scope:** where the two first-party Tier 1 components live, how a build produces them, and what
  that costs. How any component is loaded, typed, limited and granted is [0246](0246.md); what the
  image component does is [0120](0120.md); the intl component's API is the record goal `ext-intl`
  opens.
- **Depends on:** [0051](0051.md) (the tier roster, and the trade § *Consequences* made for intl),
  [0120](0120.md), [0246](0246.md).
- **Validated by:** goal `ext-image`'s and goal `ext-intl`'s acceptance checks.

> **In short:** `Novis\Image` and `Novis\Intl` are `.nvsx` components embedded in every `nvs`
> binary at build time and always loaded. They need no `[[extension]]` entry and no pin, because
> the binary is their pin, and nothing turns them off. They still run in the sandbox under the
> request's caps, so the tier is unchanged and visible in the namespace: `Novis\`, never `Core\`.
> Their wasm is compiled on first use, so a program that never calls them pays nothing at run time.
> A build script compiles their Rust crates for `wasm32-wasip2`; libwebp, the one C library, is
> compiled by a `bun nv` tool into a wasm static library committed beside its source hash, and CI
> rebuilds it and fails on a difference. This reverses 0051's decision that intl is installed.

## Context

`Core` is always in the binary and cannot be turned off (`rule:core-api/core-means-always-present`).
[0051](0051.md) placed image decoding and intl at Tier 1 and accepted, in its *Consequences*, that
"locale-correct formatting requires installing something", to keep multi-megabyte CLDR data out of
every CLI binary and every single-file executable. Under that trade a program cannot know whether
`Novis\Image` exists without asking its deployment, which is the conditional presence 0051 § 5
refused for `Core` itself.

## Options considered

- **Embedded and always on.** Present everywhere, like `Core`; the binary grows.
- **Embedded, removable** by a setting or a Cargo feature. Smaller when removed, but presence depends
  on configuration again.
- **Installed**, as 0051 decided: the two files ship beside the binary and an operator adds entries.

For the build: the Rust crates compiled by a build script with libwebp prebuilt and checked; every
part including libwebp compiled on every clean build; or both finished `.nvsx` files committed.

## Decision

### 1. Two components ship inside the binary, and nothing removes them

The image component ([0120](0120.md)) and the intl component are embedded in every `nvs` binary as
`.nvsx` bytes and are part of every loaded set, before any `[[extension]]` entry. They are always
present: a program may `use Novis\Image` on any host, in any bundle, under any configuration. There is
no setting and no Cargo feature that removes them.

They are still Tier 1. Each call runs in the sandbox under [0246](0246.md) §§ 5–7: its own instance
per request, the request's CPU and memory caps, and an empty WASI with no grant — neither needs I/O.
The namespace `Novis\` is reserved for them, so a loaded `.nvsx` declaring a class there does not load
([0246](0246.md) § 4), and `Core\` stays reserved for Tier 0.

### 2. The binary is the pin

A built-in component has no `[[extension]]` entry. Its digest is computed at build time and folded
into `env_hash` as part of the compiler identity, so a binary carrying different component bytes
keys apart from every other. Its settings blocks, `[image]` and `[intl]`, are ordinary configuration
blocks (`rule:config/every-block-is-argued-where-it-is-added`).

### 3. Nothing is paid until a program calls one

The embedded bytes are compiled to machine code on a component's first use in a process and stored in
the artifact cache like any other module
(`rule:packaging/a-wasm-module-cache-reuses-the-artifact-cache`). A process that never calls them
compiles nothing and instantiates nothing; the cost is the binary's size on disk and in the page cache.

### 4. The build

The components' Rust crates live under `extensions/` and are excluded from the workspace, so the
ordinary `cargo build` of the tree never resolves them for the host target. A build script compiles
them for `wasm32-wasip2` into their own target directory and assembles each `.nvsx` with the same
packer `nvs ext build` uses; `rust-toolchain.toml` lists the target, so no contributor installs
anything by hand.

libwebp is compiled with wasi-sdk by a `bun nv` tool into a wasm static library committed under
`extensions/image/` beside the hash of the source it was built from. CI rebuilds it from that source
and fails when the bytes differ (`rule:packaging/a-prebuilt-wasm-library-is-rebuilt-in-ci`).
Contributors need no C toolchain; only a change to libwebp needs wasi-sdk.

### 5. The intl component's scope

The intl component is ICU4X with every CLDR locale compiled in, and covers: collation (sort keys and
whole-array sort), numbers (decimal, percent, currency, compact), dates and times over `Core\Time`
values, plural rules, relative time, list formatting, word and sentence segmentation, and locale
negotiation from an `Accept-Language` value. Message formatting is not in it, because ICU4X's
MessageFormat 2 is not stable; it is the next addition. Its API is designed in its own record by goal
`ext-intl`, batch-shaped as 0051 requires.

## Consequences

- **Usability:** image handling and locale formatting work on every install with no configuration,
  in every single-file executable, and in tests.
- **Binary size:** larger by the two components — mostly CLDR data and the codecs. Not measured
  yet; goal `ext-intl` measures it and records the figure in the component's module doc.
- **Memory:** nothing until first use; then the compiled module, shared by every core, and each
  calling request's instance under its own cap.
- **Build time:** a clean build compiles two extra crates for wasm, ICU4X's compiled data among them;
  incremental builds reuse their target directory.
- **Simplicity:** one more build step, and one committed binary library with a check that it matches
  its source.
- **0051's trade is reversed.** Its *Consequences* bullet on installing intl no longer holds; the
  rule `rule:core-api/core-means-always-present` now carries the built-in components beside `Core`.

## Alternatives rejected

- **Embedded, removable.** "Is `Novis\Image` there?" would depend on configuration, which is the
  failure the reserved namespace exists to prevent.
- **Installed.** One configuration step for two features every web application uses.
- **libwebp compiled on every clean build.** Every contributor and every CI leg would need wasi-sdk
  before `cargo build` works.
- **Both `.nvsx` files committed.** Tens of megabytes of binary in git on every CLDR or codec update.

## Revisiting

Reopen § 1 if the measured binary growth makes the single-file executable impractical for CLI
programs; the answer then is a slimmer locale set, not an optional component.

## Verification

- **`ext-image`:** a clean build produces a binary in which `Novis\Image::info` answers with no
  `nvs.toml`; a `[[extension]]` declaring a `Novis\` class is refused; CI's rebuild of libwebp
  matches the committed library.
- **`ext-intl`:** `Novis\Intl` answers with no `nvs.toml`; a bundle built with `nvs build --compile`
  calls both components; the binary's growth is measured and recorded.
