# ADR 0165 — The envelope's `source` and `count` are filled, and each is filled where it belongs

- **Scope:** the two envelope fields [0092](0092.md) declared and nothing outside the engine floor
  writes — where a record says it was produced, and how a run of identical records is bounded. It
  adds no captured call stack, and it changes no part of the record model, which already has both
  slots.
- **Depends on:** [0092](0092.md), whose envelope declares `source` and `count`; [0106](0106.md) and
  [0020](0020.md), whose floor already coalesces and whose target is already bounded;
  [0002](0002.md), whose propagation design is where a call-site constant already reaches the
  runtime; [0163](0163.md), whose viewer is the reader that makes the second half worth deciding now.
- **Validated by:** the conformance and unit cases the two rules name, landed by the goal that
  carries them. Nothing holds this record on its own today, which is why both rules are `designed`.

> **In short:** `Envelope.source` exists in the model, is named by the rule, and **is constructed
> nowhere** — the only `Source` values in the workspace belong to an unrelated type. `Throwable`'s
> `location` slot has the same shape of gap and is written as the empty string at construction. Both
> are filled from the call site the compiler already knows. `Envelope.count` is filled only by the
> engine floor; this record extends coalescing to the ordinary log target, whose bound is a disk, and
> deliberately **does not** extend it to the debug stream, whose bound is an index and which groups
> at read time instead — keeping every occurrence rather than merging them before they are stored.

## Context

- A record's envelope carries `source` per `rule:errors/diagnostic-record`, and `nvs-render` defines
  it precisely — a file as the program named it, a one-based line, and the enclosing `Class::member`
  or `None` at file scope. It is `Option<Source>` and nothing anywhere constructs one.
- `Throwable::$location` is a declared, readable property occupying its own slot, and it is set to
  the empty string when the object is built. A property that always answers `""` is shipped surface
  that says nothing while looking as though it says something.
- `Envelope.count` is filled, but only by `crates/nvs-runtime/src/floor.rs`, whose window belongs to
  `rule:http-server/the-floor-cannot-fill-the-disk`. `Core\Log::write` renders the same record to the
  program's own stream and passes that window entirely, so a request that logs in a loop is unbounded
  where a request that *faults* in a loop is not.
- [0163](0163.md)'s viewer is what makes both gaps matter at once: its whole proposition is showing a
  developer which line produced a record, and its second problem is a hundred thousand identical rows.

## Investigation

- **The call-site datum already reaches the runtime.** `nvs_ir`'s `Terminator::Propagate` carries a
  frame label, `crates/nvs-codegen/src/emit.rs` materialises it as static bytes in the unit's own
  data, and `nvs_trace_push` receives it as a pointer and a length. So a compile-time constant
  identifying a site is an established pattern here rather than something to invent; what is missing
  is a second use of it, on the success path, for a producer rather than for an unwind.
- **Its cost profile is why it is a constant.** `rule:errors/propagation` puts the backtrace push on
  the *error* path precisely so a call costs a compare-and-branch, and nothing in this record moves
  that. A producer's `source` is read at the call, not maintained as running state, so no path that
  does not produce a record pays for it.
- **A captured call stack is a different thing and is not bought here.** PHP snapshots the whole
  stack at construction, and matching that needs a walk of Novis's own frame chain. It is also
  unnecessary for the question being asked: a record already carries `span_id` when a trace is active
  (`rule:observability/a-log-record-carries-trace-ids-when-a-trace-is-active`) and the trace already
  records call entry and exit at every call site under its own bit, so *how execution arrived* is
  reconstructable from the trace for exactly the sessions that asked for one, at no cost to the
  records that did not.
- **The floor's coalescer is one slot, deliberately.** `COALESCING_WINDOW` is a second, the window is
  a `thread_local` `{ key, deadline, suppressed }`, and its own comment argues that a table keyed by
  record "would spend memory to bound a case that does not arise" — because a fault loop repeats one
  record. Its identity clears `ts`, `request_id`, `trace_id`, `span_id` and any existing `count`
  first, since those are what distinguish two occurrences of one failure.
- **That argument does not survive the move to application logging.** Application code interleaves —
  log A, log B, log A — and a single slot coalesces none of it. This is the one place the floor's
  design cannot simply be reused as it stands.
- **Coalescing saves the write, not the work.** The key is a hash of the record's rendering, so a
  duplicate is only known to be one after the record has been built — the object graph walked,
  redaction and elision applied — and rendered. A loop still pays for every record it makes. What it
  stops paying for is every record it *stores*.

## Options considered

For `source`: fill it at the producer from a compile-time constant; maintain a current-location word
in `Ctx`; or capture a stack per record. The first is taken — the second puts a store on every
statement whether or not a record is ever produced, and the third is the expense § 3 declines.

For `count`, three, and the decision is that they are not alternatives but answers to different
sinks:

1. **Coalesce at the sink**, as the floor does, before the bytes exist.
2. **Rate-limit per call site**, which is O(1) and needs no record built at all past the first.
3. **Group at read time**, keeping every occurrence stored.

## Decision

### 1. A record names where it was produced, and one datum serves both readers

`Envelope.source` is filled by the producer with the file as the program named it, the one-based
line, and the enclosing `Class::member` where there is one. `Throwable::$location` is the same datum
and stops being the empty string. Two spellings of "where" that disagree would be worse than one that
was missing, so they are one construction with two readers.

### 2. The call path is the trace's answer, not the record's

No stack is captured per record. Where a trace is active the record already carries `span_id`, and
the trace already has the call events; where one is not, the file, line and member are the answer and
they are enough to open an editor at the right place. This keeps a producer's cost at reading a
constant.

### 3. A repeat is bounded at the sink that would suffer from it, and nowhere else

`rule:http-server/the-floor-cannot-fill-the-disk` already puts the bound on the sink "so that no
caller has to be trusted to be rare", and this record keeps that and applies it per sink rather than
once for all of them:

- **A disk-bounded target** — the diagnostic log — **coalesces before the write.** What the floor
  does, extended to `Core\Log`'s target, because the thing being protected is a finite disk and the
  cheapest place to protect it is before the bytes exist.
- **An indexed target** — [0163](0163.md)'s debug stream — **does not coalesce, and groups at read
  time.** Its bound is an index that holds a million rows without complaint, so merging occurrences
  before storing them would spend the developer's information to save nothing that is scarce. The
  ingester already computes a per-record hash for its dedupe key, so a content hash beside it is
  nearly free, and the viewer collapses a run into one row that says how many it stands for and
  expands.

### 4. The log target's window is a small table, not one slot

The floor's single slot is kept for the floor and is not what the log target gets. A fixed, small
number of slots with a trivial eviction, so that interleaved records still coalesce — memory stays a
constant, just a larger one, and the argument the floor's comment makes against a table is answered
rather than ignored: the case it says "does not arise" is exactly the case that arises here.

### 5. The identity is the floor's identity, and a differing record is never held back

`ts`, `request_id`, `trace_id`, `span_id` and any existing `count` are cleared before hashing,
because those are what distinguish two occurrences of one thing. Everything else counts, `source`
included — two identical messages from two lines are two facts. A record that differs in any
remaining field is written immediately and never queued behind a window.

### 6. A per-call-site rate limit is not taken now

It is the only option that makes a hot loop *cheap* rather than merely quiet, and it is a semantics
change wearing an optimisation's clothes: it drops records that differ. Nothing has been measured
that asks for it. If it is ever taken, it is a new record, and it inherits `rule:errors/log-fields`'s
existing requirement that a shed record increments a counter that is exported.

## Consequences

- **A viewer can name the line.** [0163](0163.md)'s request timeline shows file, line and member per
  record, which is the whole reason a developer opens it.
- **`Throwable::$location` becomes true**, which is a small correctness debt closed rather than a
  feature added.
- **A logging loop stops filling a disk**, and stops doing so at the sink, so no library author has
  to be trusted to be rare.
- **A logging loop still costs what it costs.** Coalescing is not a CPU optimisation and this record
  does not claim it is one.
- **The debug stream keeps every occurrence**, which is what makes "expand this group" possible and
  what would have been thrown away by coalescing it at the sink for symmetry's sake.
- **A producer that has no source to give still omits the field**, on the envelope's existing rule
  that an absent field is omitted rather than rendered empty.

## Alternatives rejected

- **A current-location word maintained in `Ctx`** — a store on every statement to serve the rare
  statement that produces a record, against a constant read at the call that does.
- **A captured call stack per record** — § 2; the trace already answers it where it is asked.
- **One coalescing policy for every sink** — § 3. The floor, a disk-bounded log and an index have
  different things worth protecting, and one policy would either fill a disk or discard what a
  developer went looking for.
- **Reusing the floor's single slot for the log target** — § 4.
- **A per-call-site rate limit** — § 6, deferred rather than refused.

## Verification

The two rules name what holds them. What must be tested rather than argued: a record produced from a
known line reports that line and its enclosing member; a `Throwable` built anywhere reports a
location that is not empty; interleaved identical records coalesce where a single-slot window would
not; a record differing only in a field that is not an occurrence key is never merged; and one
differing in `request_id` alone still merges, since that is what the floor's identity already
decides.
