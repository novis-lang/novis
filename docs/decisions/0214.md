# ADR 0214 — every `Core` name hovers to its card and jumps to a generated stub

- **Scope:** what an editor answers for a name under `Core` that is not a resolved member call — a
  class, an enum, an enum case, a constant, a compiler attribute, a namespace segment — on hover, on
  go-to-definition and in the semantic tokens; the stub tree those jumps open, where it lives and who
  writes it; and the reference intros compiled into the registry. It does not change what a `Core`
  member call hovers to, which is [0117](0117.md)'s card, or what a completion row shows, which is
  [0203](0203.md)'s.
- **Depends on:** [0117](0117.md) for the reference card, [0203](0203.md) for the class line and the
  card renderer, [0099](0099.md) for the request set and the one server behind two clients,
  [0195](0195.md) for the per-version storage the extension already keeps.
- **Validated by:** `crates/nvs-lsp/src/stubs.rs`'s tests (every stub parses, every name and member
  has a line, one file is frozen verbatim, a tree is written once and rewritten when a file is
  missing), the `tests/lsp/hover/`, `tests/lsp/definition/` and `tests/lsp/semantic/` cases that name
  this record's rule, `crates/nvs-types/src/derive.rs`'s attribute roster, `crates/nvs-stdlib`'s
  `every_intro_page_names_a_registry_class`, and `editors/vscode/test/client/stubs.test.ts`.

> **In short:** nothing under `Core` used to be ctrl+clickable, and only a fully written member call
> hovered. Now every `Core` class, enum, case, constant and compiler attribute hovers to its card, a
> namespace segment hovers to what it contains, and a jump to any of them opens a generated `.nvs`
> stub — a declaration with its real signature, an empty body and the same card as a `///` run — from
> a tree the server writes once per version, or `nvs stubs --out` writes for anyone. The checker
> records what an attribute's name resolved to, the server reaches into attribute payloads by its own
> walk, and the 56 hand-written reference intros are compiled in and shown under the class's card.

## Context

### 1. Nothing under `Core` gave help

A user of the VS Code extension reported that
`#[Core\Route(path: '/', method: Core\Http\Method::Get, name: 'x')]` explained none of `Core\Route`,
`Core\Http\Method`, `Core\Http\Method::Get` or `Core\Http`, that only a fully written static call got a
hover, and that nothing under `Core` was ctrl+clickable. PhpStorm answers the same situation with a
stub tree: generated declaration files with documentation, opened on ctrl+click.

### 2. Why: `Core` has no declaration anywhere

`Core` names never enter the symbol table. `nvs_hir` holds them as a name list
(`CoreRoster::Names`), so every jump died at `definition::site_of`'s symbol lookup. Hover had one
`Core` arm, for `Target::Method` only. The card for a class, an enum, a case and a constant was already
rendered for `completionItem/resolve` in `nvs_lsp::card` and hover never called it. Attributes were
invisible: the compiler attributes were strings in `nvs_types::derive::ATTRIBUTES`, the name was
resolved inside the checker with no record kept, and the syntax walk never descends into a `#[...]`
payload — an attribute is a property of the declaration it is attached to, by that walk's own
decision — so a cursor inside one landed in the enclosing method and no node carried the expression
under it. `semantic::library_at` consulted `registry::class` only, so a `Core` enum was not marked as
the default library. The 56 intro pages under `docs/reference/core/` were not compiled into anything.

### 3. What existed to build on

The registry is the one source of what a `Core` member is and does, and `hover::reference_card` is
the one renderer of a card. Every `.lspt` case already spells a location in another file as the case
wrote it. The extension keeps a verified copy of the server under its own storage, per version. Three
renderers turn the registry into text — `nvs meta --json`, `nvs doc`, `nvs agent show` — and none
emits Novis source.

## Decision

1. **Every `Core` target hovers to its card, through one renderer.** `nvs_lsp::card` renders a class
   (its declaration line, its `short`, its intro), an enum (its line, its `short`, one line per case), a
   compiler attribute (as it is written with each field at its type, what it does, what it is written
   above), a constant's sentence and a case's line; hover routes `Target::Type` and `Target::Constant`
   through it and completion resolve keeps reading the same functions. A cursor on the class half of a
   member access answers the class rather than the member, and a cursor on a segment in front of the
   type — `Core\Http` in `Core\Http\Method::Get` — answers what that namespace holds: the classes,
   enums, interfaces and attributes directly under it, and the namespaces below it. A namespace has
   nothing to open, so ctrl+click on a segment keeps answering the type at the end of the path.

2. **The checker records an attribute's name, and the server reaches its payload.**
   `ExprTypeTable::record_attribute_name` keeps `(span, QName)` at the one place
   `nvs_types::attributes` resolves a name; hover, definition and semantic tokens read it. Every payload
   value is inferred, so `Core\Http\Method::Get` inside `#[...]` records `ExprInfo::EnumCase` like
   ordinary code — through the roster or the shape where one checks it, and over an empty scope for
   the bare form and the recognized names with no roster. The server reaches a payload itself:
   `definition::payload_path` walks the declarations' own attribute lists at every attach site and
   descends each value with `nvs_syntax::visit::each_child_expr`, answering the path the index would
   answer if it held the payload. The walk is left as it is, because `nvs fmt`'s indenter and
   `Core\Ast` consume it and a payload node under a method changes what both print.

3. **Compiler attributes carry a card.** `nvs_types::derive::ATTRIBUTE_DOCS` gives each of the
   thirteen a `short`, the declaration it is written above and its fields at their types, held against
   `ATTRIBUTES` and against each pass's option roster by a test. The card is what the hover, the stub
   and a completion row show.

4. **A jump to a `Core` name opens a generated stub, from a tree written to real files.** One `.nvs`
   file per class, enum, derive interface and attribute at its namespace path; a class is a `final
   class` with each constant, static member, constructor and instance member as a declaration with an
   empty body and its real signature, an enum is an `enum` with its cases, an attribute is the
   shape-typed `type` alias a userland attribute already is, each under its card as a `///` run, and a
   header saying the file is generated for which version and that edits are lost. An attribute whose
   name is also a class — `Core\Test`, `Core\Command` — is declared in the class's file with the
   attribute's card joined to the class's. Registry prose is rendered verbatim. The generator,
   `nvs_lsp::stubs`, hands back a line table `(qualified name, member) → line` with the text, so the
   server never parses a stub to find a line. Real files rather than virtual documents: a `file:`
   location works unchanged in both thin clients and a cursor inside a stub keeps every answer.

5. **Where the tree lives, and who writes it.** The server writes it under `nvs.stubs.dir`, a new
   setting the extension fills with `<globalStorageUri>/stubs/<version>` beside the server copy it
   keeps, and under this account's cache directory (`%LOCALAPPDATA%\novis\stubs\<version>`,
   `$XDG_CACHE_HOME`'s or `~/.cache`'s `novis/stubs/<version>`) when no client named one. It is written
   at the first `Core` jump, once per render — a stamp names the build and a hash of the text — and
   again when a file is missing. Every file is made read-only on disk. `nvs stubs --out <dir>` writes
   the same tree from the same generator. In a `.lspt` case the tree is written under the case's own
   directory and spelled `stubs/Core/Str.nvs:L:C`.

6. **A stub is never diagnosed.** The server publishes an empty diagnostic list for a document under
   the tree: the bodies are empty and do not type-check, the `namespace Core` line is `E0217` in user
   source, and nothing in a stub is the reader's to fix. Hover, definition and semantic tokens inside
   one answer as in any document.

7. **Definition falls back to the stub only where the graph holds nothing.** `definition::at` and
   `type_at` ask the symbol table first and the line table second, so a program's own class is never
   answered with a stub; a `use Core\Http\Method;` line now answers the enum's stub.

8. **The semantic tokens say what a name resolved to.** `library_at` consults `registry::core_enum`
   beside `registry::class`; the name in front of a `::` is coloured as the enum or class it resolved
   to, which it never was before; an attribute's name is a `type` token carrying `defaultLibrary` for a
   compiler attribute, and its payload is coloured as the expressions it holds. The one existing case
   that pinned the receiver of `Status::Draft` as uncoloured is re-frozen with the enum coloured, and
   this record is why.

9. **The reference intros are compiled in.** `crates/nvs-stdlib/build.rs` joins every
   `docs/reference/core/<Class>.md`, front matter cut off, into a `(class, body)` table that
   `CoreClass::intro` reads — a method over a generated table rather than a field on every `ClassDoc`
   literal, so no class carries a hand-typed path to its own page and a page added tomorrow is compiled
   in the day it is written. The class hover and the stub's class header show it under the `short`.
   `tools/reference.py` and the website keep reading the `.md` files.

## Consequences

- **Latency:** nothing on the request path. A hover on a `Core` name is a registry lookup; the first
  `Core` jump of a process renders the whole tree once and writes it once per version; every later jump
  is a map lookup and one stamp read.
- **Memory:** the rendered tree — a few hundred kilobytes of text and its line table — held for the
  server process's life after the first jump, and once more on disk per server version, per account.
  Static strings per process for the 13 attribute cards and the 56 intros, the cheap side of
  [0117](0117.md)'s trade.
- **Simplicity:** one new module in `nvs-lsp`, one new subcommand, one new setting, and a second table
  in a build script that already had one. The server holds a second walk to payloads beside the
  index, which is the cost of leaving the index as the formatter reads it. A `Core\Str` hover is now
  a page long where the class has an intro, which is the page a reader would otherwise have opened.
- **A stub reads like the registry writes.** Cards written in this repository's own voice read that
  way in a stub; which of them read badly there is the handoff's list, and rewriting them is a goal of
  its own, not this record's.
- **Read-only is on disk only.** VS Code marks such a file read-only only under
  `files.readonlyFromPermissions`; a save into a stub otherwise fails with the editor's own message,
  and the file is written over at the next stamp change either way.

## Alternatives rejected

- **Virtual documents under a URI scheme of the server's.** Every client would learn the scheme and
  register a content provider, against `rule:ide/one-server-two-thin-clients`, and a cursor inside such
  a document would need every request re-plumbed for it. Real files cost a directory.
- **Parsing the stub to find a member's line.** A second reading of a text the generator wrote a
  moment ago, and a parse per jump. The generator knows every line as it writes it.
- **An `intro` field on `ClassDoc`.** Every class literal would carry `intro: None` or a hand-typed
  reference to its own page — the copy-by-hand the decision set out to avoid. A method over a generated
  table keeps the literals as they are and the pages where they are.
- **Payload values as nodes of the syntax walk.** The walk's own doc says an attribute's nested
  expressions are children of the declaration, and adding them made twenty-one corpus files change
  under `nvs fmt` and every `Core\Ast::parse` grow nodes. The server's own walk costs a few lines and
  changes nothing a program or a formatter reads.
- **Reading a `.lspt` stub location as an absolute path.** An absolute path in a frozen expectation is
  a path nobody else has; under the case's own directory it is spelled like every other cross-file
  answer.

## Revisiting

If a client wants the tree served rather than written — a remote workspace with no writable storage —
the generator is the same and a content provider over it is the extension's to add; nothing in the
server would change but the location it answers.
