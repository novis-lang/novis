# ADR 0183 — A program opens a WebSocket the way it makes a call, and holds it as a value that dies with its task

- **Scope:** how a Novis program opens a WebSocket to another server and talks over it — the door it is
  opened through, the schemes, the bounds, what owns the open socket, and how a test answers one. Not in
  scope: the server's half, which [0083](0083.md) settled and this decision does not touch;
  `permessage-deflate`; WebSocket over HTTP/2 (RFC 8441); reconnecting; a socket handed to another isolate;
  and the subprotocol libraries — STOMP, Socket.IO, GraphQL over WebSocket — that are packages built on
  this.
- **Depends on:** [0058](0058.md) for the launderer, the address policy and the pin;
  [0180](0180.md) for the client whose door this row joins, its bag, its TLS trust and its per-core pool;
  [0182](0182.md) for the tunnel a proxied deployment reaches the other host through;
  [0074](0074.md) for a bound that has no unbounded spelling and a default that is a defect when it is one;
  [0083](0083.md) for `Core\Socket\Message`, the shape both halves now answer in;
  [0060](0060.md) for the admission test a transport passes and a flow does not.
- **Validated by:** the four rules it creates are `designed` on acceptance; the goal's last stage fills
  their `guardedBy` from what stages 3–5 write — a scripted-peer conformance suite under
  `tests/conformance/core/`, and loopback Rust tests beside the ones
  `crates/nvs-stdlib/src/http/transport.rs` already carries for what a scripted peer cannot reach.

> **In short:** a WebSocket is opened by `Core\Http\Client::openSocket`, a row on the same class as `get`
> and `stream`, and everything that governs an outbound call governs the opening handshake: the URL is
> `rule:security/outbound-url-is-a-sink`'s sink, `Core\Http::allowUrl` pins it, the `net.connect` grant, the
> TLS policy, a client identity and the operator's proxy all apply, and a test answers it from a table
> instead of a listener. `ws` and `wss` join the scheme roster for this row alone. What comes back is
> `Core\Http\Socket`, answering the `Core\Socket\Message` a server-side connection already answers with,
> because one RFC 6455 frame gets one shape in this language. A client socket is **not** a root isolate: it
> is a value the program opened, charged to the task that opened it, closed with `1001` when that task ends,
> so memory stays O(in-flight). Every wait on it is finite — `idle`, `maxDuration`, `maxMessage` and
> `sendTimeout`, each inheriting `[http.client]` when omitted, none with a spelling for "forever".

## Context

A program that drives a modern API talks to something that pushes: a chat platform's gateway, a market data
feed, a model provider streaming tokens, another Novis instance. [0180](0180.md) built the half where Novis
asks and the other host answers. The half where the other host speaks whenever it likes is a WebSocket, and
without it the class of program this language exists to run has to shell out or poll.

Novis already holds both pieces. [0083](0083.md) put `tungstenite` in the tree for the server's half —
`Core\Socket`, `Core\Socket\Message`, masking, fragmentation, UTF-8 validation and the close handshake, over
the parking stream with no adapter. [0180](0180.md) built a transport that resolves, pins, connects, hands
`https` to `nvs_host::tls` and can answer a URL from a test's table. An outbound WebSocket is an HTTP
request that gets a `101` instead of a `200`, so it is the two pieces joined rather than a third one.

The question this record answers is therefore not *whether* — [0060](0060.md)'s admission test lets it in,
because RFC 6455 is a transport whose failure mode is a library bug rather than a flow with per-provider
discovery, nonce storage and expiry policy. The question is **whose rules it inherits**, and there are two
plausible parents: an outbound call, and a connection. Answering that wrongly is expensive in both
directions — an outbound door that skips the pin is server-side request forgery with a longer-lived
connection attached, and a socket modelled on the server's isolate is memory that grows with traffic served
rather than with traffic in flight.

## Investigation

**The server's half is not reusable as-is, and the reason is ownership rather than framing.** A
server-side connection is a root isolate ([0083](0083.md), `rule:concurrency/a-connection-is-a-root-isolate`)
because it *outlives* the request that upgraded it: the request ends normally, and what reaches the long-lived
isolate is only what the application copied in. That model is bought with its own arena, its own globals, its
own `[limits]` budget and its own timeline entry, and it is worth the price because the alternative is holding
a finished request's heap open for hours. An outbound socket has no such request to escape from. It is opened
*by* a running program, which is already the thing holding it, and giving it an isolate of its own would mean
a program that opened one could not read from it without crossing an isolate boundary — the arrangement would
cost an arena and a copy per socket and buy nothing.

**The frame is the same frame.** `Core\Socket\Message` already answers `null` for `topic` and `value` on a
peer frame (`crates/nvs-stdlib/src/socket.rs:446-517`), which is precisely what a client sees, so the shape
needs no widening to serve both halves — only its doc comment rewritten to say it is the shape both
directions answer in.

**The handshake is an ordinary request until the `101`.** It carries a method, a URL, headers and a TLS
handshake before any of it, which is the whole of what `pin` and the transport already judge. Anything that
opened a socket through its own door would be a second implementation of
`rule:security/the-policy-lives-in-the-capability` — and the one an attacker reaches first, since a URL
handed to a socket opener is the same attacker-chosen address a URL handed to `get` is.

## Options considered

**A door of its own — `Core\Socket::connect(...)` beside the server's class.** Reads well and groups the
socket surface in one namespace. Rejected: the connect is an outbound call, so every question `pin`,
`allowUrl`, the `net.connect` grant, the TLS options and the proxy answer would have to be asked again in a
second place, and the second copy is the one that will be missing a check a year from now.

**A row on `Core\Http\Client`.** Chosen. The door, the bag, the pin, the identity, the proxy and the test
table are all already there, and the row inherits them by being on the class rather than by being told to.

**A second message class for the outbound direction.** Rejected outright. It would be a copy of
`Core\Socket\Message` that differs only in where the bytes came from, and the two would disagree — one
gaining a member, one gaining a qualifier — the first time either was touched.

**An isolate per outbound socket.** Rejected, above, and the memory argument is the decisive half:
O(in-flight) is a property this runtime enforces rather than hopes for.

## Decision

### 1. The door is `Core\Http\Client`, and the row is `openSocket`

```
Core\Http\Client::openSocket(string|Core\Http\Target $url, ...$options): Core\Http\Socket
```

The name is fixed here because the surface leaves it open and `rule:core-api/verb-lexicon` narrows it to
one. `connect` is unavailable: every other row on this class is named for an HTTP method, `CONNECT` is one,
and `connectTimeout` and `connectTo` already spend the word on reaching a host. Bare `open` is the verb this
language uses for a resource a program then holds and closes — `Core\Cache::open`, `Core\Io`'s and
`Core\Db`'s — but alone on this class it does not say what is opened, and this is the only row whose result
outlives the call. `openSocket` is that verb with its object, it is a full word
(`rule:core-api/members-are-full-words`), and the verb predicts the return type, which is what the
lexicon asks of a name.

### 2. The class is `Core\Http\Socket`, and the message is `Core\Socket\Message`

The value a row on `Core\Http\Client` answers with lives under `Core\Http`, as `Core\Http\Response`,
`Core\Http\Stream`, `Core\Http\Target` and `Core\Http\Identity` do. What it answers *with* is
`Core\Socket\Message`, unchanged: one RFC 6455 frame, one shape, both directions.

### 3. `ws` and `wss` join the roster, for one row

`rule:http-server/allow-url-pins-the-address`'s "refuses a scheme outside the grant" now has four schemes in
the grant rather than two, and each row names which of them it serves: the request rows refuse `ws` and
`wss`, `openSocket` refuses `http` and `https`. What a URL is *for* is therefore written in the row that
takes it, and a URL that arrived meaning one thing cannot be spent as the other. `allowUrl` pins all four
identically — it resolves, checks every address against `rule:security/net-address-policy` and answers a
`Target` — so a `Target` laundered for a socket and one laundered for a call are the same value, which is
correct: what was approved is a host and a set of addresses, not an intention.

`ws` is admitted as plain `http` is, and there is no upgrade-to-`wss` question to answer, because a socket
follows no redirect. A `3xx` answering an upgrade is a `RuntimeError` naming the `Location` rather than a hop
taken, so `rule:http-server/redirects-are-off-and-every-hop-is-re-pinned` has nothing to re-pin here.

### 4. The handshake is an outbound call, in full

The same pin and the same fallback across every approved address, the same `connectTimeout`, a `deadline`
that covers the whole opening and ends at the `101`, the same TLS policy options and their grants, a client
identity, and the operator's proxy tunnel from [0182](0182.md) — a socket opened behind a proxy goes through
`CONNECT` like everything else, and `resolve`'s word governs whether the pin survives it.

`headers` is on this row and may carry a `secret` value, because a gateway is authenticated with a bearer
token in the opening request and that is one of the three places
`rule:security/secret-sinks-refuse` lets a credential reach. `protocols?: array<string>` is
`Sec-WebSocket-Protocol`; a `101` that chooses a subprotocol which was never offered is refused, and the
socket reports the one chosen through `protocol()`.

The bag is the connection half of `rule:core-api/shape-rules` R2's closed set — the two waits, `headers`,
the TLS options, `identity`, `connectTo` — plus this row's own group in § 7. The keys that describe a
request-and-reply exchange are **not** on it: there is no `body`, no `followRedirects` and no retry trio. A
bag is a closed set of keys, so a key that could never do anything here is a key a program would write and
then wait for.

`tungstenite`'s client half runs over the stream the transport already holds — the parking stream, or
`nvs_host::tls`'s decrypted one — with no adapter and no new dependency, for the reason the server's half
gives: masking, fragmentation, UTF-8 validation and the close handshake are that crate's, and a second
implementation of any of them in this repository would be a second thing to get wrong.

**A socket is never pooled.** It consumes its connection and nothing goes back to
`rule:http-server/an-outbound-connection-is-pooled-per-core-and-stays-pinned`'s pool, because a connection
that has been upgraded is no longer able to carry a request.

### 5. It belongs to the task that opened it, and is never a root isolate

The socket is a value in the task that opened it. Its connection, its buffers and its reassembly space are
charged to that task's budget; when the task ends, the socket is closed with `1001` and its memory is
released with everything else the task held. A request's `wall_time` therefore bounds a socket opened inside
a request without needing to know about sockets at all.

It never crosses an isolate boundary: `rule:classes/graph-copy` refuses it as it refuses every other
resource, so there is no way to hand one to a spawned script and no lifetime question about who closes it. A
program that wants a socket to outlive a request opens it in something that outlives a request — a command,
a queue job, a spawned script — which is an existing spelling rather than a new mechanism. Two `receive`s
waiting at once on one socket is a `LogicError`: one message has one recipient, and the alternative is
inventing a fan-out policy for a case that is a program bug.

### 6. The conversation

`receive()`, `send(string $frame)`, `sendBytes(bytes $frame)`, `close(?uint $code, ?string $reason)` and
`protocol()`. The first three are `Core\Socket`'s own shapes and are here for its reason, which is the
qualifier and not symmetry: two classified parameters rather than one spelled `string|bytes`, because a
union carries no classification and a text-like parameter that carries none refuses a `tainted` argument —
the union spelling would have made `send` a sink by accident.

`receive` answers `?Core\Socket\Message` — `text` or `bytes` filled and **`tainted`**, `topic` and `value`
`null` — and `null` once the peer has closed. A sent frame is not a sink
(`rule:security/sink-predicate`'s test: it is not an instruction on this side of the wire), so a program may
forward what it received without laundering it.

`close` sends the close frame and waits for the peer's under the send wait. A peer that never answers is
closed anyway, and that is not an error — the connection is gone either way, and a throw would make every
program write a `catch` around a normal ending.

### 7. The bounds, and none of them has an unbounded spelling

| Option | Bounds | Inherits |
|---|---|---|
| `idle` | the longest silence | `[http.client] idle` |
| `maxDuration` | the socket's whole life | `[http.client] max_duration` |
| `maxMessage` | the largest message after reassembly | `[http.client.socket] max_message` |
| `sendTimeout` | how long a frame may wait to be written | `[http.client.socket] send_timeout` |
| `ping` | silence after which a ping is sent | unset — none is sent |

`idle` and `maxDuration` are the same two bounds and the same two directives `stream` already reads, for the
same reason one level down: an idle check alone never ends a peer that dribbles, and a lifetime alone lets a
dead connection sit until it expires. A message past `maxMessage` closes the socket with `1009`, which is
what the code is for. `ping` is the one knob with an off position, and it is off by default because a ping
is traffic a peer did not ask for; a program that sets it is choosing to have `idle` end a *dead* peer
rather than a quiet one. A peer's ping is always answered regardless — that is the protocol, not a policy.

Every one of them is a `Duration` or a `uint` of bytes, and neither type has an infinite value
(`rule:types/duration`, `rule:core-api/units-are-types`). There is no `null` meaning unbounded and
no `0` meaning unbounded, so an outbound socket that waits forever is not something a program can express —
the guarantee comes from the absence of a spelling, exactly as it does for a call
(`rule:http-server/no-spelling-for-an-unbounded-wait`).

### 8. The directives, and their shipped values

`[http.client.socket]` carries `max_message` and `send_timeout`, both **`Runtime`**, as `[http.client]
deadline` is and for its reason: each bounds one call, a program that knows its own peer may widen or narrow
it, and neither is a shared resource one request could spend on another's behalf
(`rule:config/three-changeability-classes`). They are not in `[http.client]` itself because they mean
nothing to a row that is not `openSocket`, and a block is the smallest thing a `nvs config dump` reader can
skip.

Shipped: `max_message = 4194304` — four mebibytes — and `send_timeout = "30s"`. Both are taken rather than
picked: they are the numbers this process already applies to the *other* half of RFC 6455
(`crates/nvs-server/src/bounds.rs:159-171`), and one process holding two opinions about the size of one
message is how a program comes to work in one direction and not the other. Neither has a default that is
unbounded, which `rule:http-server/an-unsafe-or-unbounded-default-is-a-defect` requires of exactly this kind
of wait.

### 9. A test answers a socket from the table, not from a listener

`Core\Test` gains `answerSocket` and `sentSocket`, beside the `answerHttp` and `sentHttp` that
`rule:testing/an-outbound-call-is-answered-from-a-table` already gives an outbound call. A test registers a
URL with the frames a peer should send; a socket matching it completes its handshake **without connecting**,
receives those frames in order and then a close, and every frame the program sent is recorded for the test
to read back. An unmatched socket throws naming the URL, exactly as an unmatched call does, so a test that
forgot to script a peer fails saying so rather than reaching the network.

This is the keystone rather than a convenience: it is what lets every later conformance case be written
without a listener, a port or a timing assumption. What it cannot reach — masking, fragmentation, the close
handshake, a ping — is proved by Rust tests against a loopback peer, as the transport's own are.

### 10. What it spends

Per open socket: one connection — a socket, and for `wss` a TLS session — `tungstenite`'s read and write
buffers, and at most `maxMessage` for a message being reassembled. All of it is charged to the task that
opened the socket and released when it closes. That is O(open sockets), and a socket never outlives its
task, so it is O(in-flight) and not O(sockets opened). Nothing per core, and nothing per process.

## Diagnostics

At compile time there is nothing new to report. The URL parameter is unqualified on both of its spellings,
so a `tainted` argument at `openSocket` is the same sink diagnostic it is at `get`, reported by the same
check over the same roster.

The configuration refusals are in the `E06xx` band with the rest of the block-level ones and reported from
`crates/nvs-config`: a `max_message` of zero, and a `send_timeout` that is not a positive duration.

At run time, each is a throw and none is retried: a URL whose scheme is `http` or `https` at this row, or
`ws`/`wss` at a request row, is a `RuntimeError` naming both the scheme and the row; a `3xx` answering the
upgrade is a `RuntimeError` naming the `Location`; any other non-`101` answer is a `RuntimeError` naming the
status; a `101` choosing a subprotocol that was not offered is a `RuntimeError` naming it; a second
concurrent `receive` is a `LogicError`; and `idle`, `maxDuration` or `connectTimeout` expiring throws
`TimeoutError` (`rule:core-api/failure-throws`). A message past `maxMessage` is not a throw on the sending
side of the ledger — the socket is closed with `1009` and the pending `receive` throws naming the cap.

## Consequences

- A Novis program can drive a realtime API, which today it cannot do without a subprocess.
- The outbound surface gains a row and no new door, so every check an outbound call passes is a check a
  socket passes — including the ones added after this record, which is the durable half of the choice.
- `Core\Socket\Message` becomes the shape both halves of RFC 6455 answer in, and its module doc is rewritten
  to say so rather than being left describing one direction.
- A socket cannot outlive the task that opened it, so a long-lived subscription is written as a command or a
  queue job. That is a real constraint on the program's shape, and it is the one that keeps a leaking
  program impossible rather than merely discouraged.
- The pool keeps its invariant by exclusion: a socket never enters it, so nothing in
  `rule:http-server/an-outbound-connection-is-pooled-per-core-and-stays-pinned` needs a case for a
  connection that stopped being HTTP.
- A deployment behind a forward proxy reaches a socket through the same tunnel as a call, so there is no
  second egress path for an operator to discover.

## Alternatives rejected

- **`permessage-deflate`.** It is what makes a chatty gateway cheap, and it is out of this decision on two
  grounds that are not about effort: context takeover holds a compression window per socket for the socket's
  whole life, which is memory this record would have to account for per peer rather than per message; and
  inflating a peer's frames is a decompression bomb surface with no length known in advance, which is a
  security question of its own and deserves its own record rather than a paragraph in this one. A later
  decision can add it as an option; nothing here forecloses it.
- **WebSocket over HTTP/2 (RFC 8441).** Novis speaks HTTP/1.1 outbound. When that changes, this is one of
  the things that changes with it.
- **Reconnecting.** A reconnect policy is backoff, jitter, resumption tokens and a replay question, all of
  which are the application's and none of which is the same for two APIs. A socket that ends says why; what
  to do about it is the program's.
- **A socket handed to another isolate.** It would make ownership a runtime question — who closes it, whose
  budget holds it — for the sake of a pattern (open in one place, read in another) that a program can write
  by opening it where it reads it.
- **Subprotocol libraries.** STOMP, Socket.IO and GraphQL over WebSocket are frames with a convention on
  top, which is exactly what a package is for under `rule:core-api/tier-placement`.

## Revisiting

Two triggers, and nothing else. If the outbound transport gains HTTP/2, RFC 8441 is reconsidered with it.
If measurement on a real gateway shows that the bytes a chatty peer sends dominate a program's cost, the
compression question gets the record its two objections above ask for.

## Verification

The scripted peer carries the conformance half: a socket opens against a scripted URL and receives its
frames in order; an unmatched URL throws naming it; every frame the program sent is read back; a received
payload is `tainted` at a sink and a diagnostic proves it; `ws` and `wss` at a request row and `http` and
`https` at `openSocket` are each refused; a tainted URL at `openSocket` is a compile-time diagnostic; a
`Target` laundered from a `wss` URL is accepted and connects only to an address `allowUrl` approved.

The loopback Rust tests carry what a table cannot reach: masking and fragmentation against a real peer; a
message past `maxMessage` closing with `1009`; `idle` and `maxDuration` each ending a socket that the other
would not; a ping answered and a `ping` option sent after silence; the close handshake, including a peer
that never answers; and a socket closed with `1001` when the task that opened it ends, asserted from the
peer's side.

`crates/nvs-config/tests/tree.rs` holds the block: both directives present, `Runtime` class, the shipped
values, and the refusals in § *Diagnostics*.
