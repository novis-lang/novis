# ADR 0122 — HTML parsing is a WHATWG entry on `Core\Html`, over `Core\Xml`'s tree

- **Scope:** that HTML parsing exists in Core and where it lives; the algorithm it implements and the
  contract that separates it from `Core\Xml`; that both parsers produce one tree; the engine and what it
  shares with [0121](0121.md)'s PDF component; the
  scheduling constraint tying it to `Core\Xml`. Not in scope: the signatures of the tree, the streaming
  reader/writer and the parse entries, which the milestone that builds them designs; the sanitizer's
  filtering rules ([0024](0024.md) owns the launderers); the PDF
  render contract (0121).
- **Depends on:** [0024](0024.md) — `Core\Html` as the HTML domain
  home this entry joins; [0063](0063.md) — R17 and the retired-twin table this
  extends.

> **In short:** Novis parses HTML with the WHATWG algorithm — the one browsers run — as an entry on
> `Core\Html`, and it produces the same tree `Core\Xml`'s tree API materialises: one node family, two
> front doors. It is never a mode of `Core\Xml`, because the two contracts are opposites: XML parsing
> **refuses** malformed input under [0095](0095.md), while
> HTML parsing **never fails** — error recovery is not repair-by-guess but the specified behaviour every
> browser agrees on, which is the entire value of implementing it. PHP spent two decades on the other
> design — `DOMDocument::loadHTML` over libxml2's HTML4 parser, which mangles HTML5, guesses encodings
> and parses differently from every browser, the divergence behind the mXSS sanitizer-bypass class —
> then conceded in 8.4 with `Dom\HTMLDocument`. The engine is `html5ever`, Servo's parser, driven
> through a Novis-owned tree builder into our own request-attributed nodes — the same crate 0121's PDF
> engine names, so the language and `Novis\Pdf` parse HTML identically — and `Core\Xml` keeps a strict
> XML parser, not `xml5ever`. Unscheduled, with one constraint: whichever milestone builds `Core\Xml`'s
> tree builds this parser with it, because the tree is one implementation.

## Context

- **PHP demonstrates both halves.** `DOMDocument::loadHTML` rides libxml2's pre-HTML5 parser: `<main>`
  and custom elements mangled, encodings guessed from meta tags, and a parse that diverges from what any
  browser builds. That divergence is a security class, not a nuisance — mXSS is precisely a sanitizer
  parsing a different document than the browser renders — and PHP 8.4's `Dom\HTMLDocument` (WHATWG,
  spec-conformant) is the upstream concession that HTML bolted onto the XML DOM was the wrong shape.
- **The audience does this on the request path.** Scraping a page, cleaning user-submitted rich text,
  extracting links from a feed — near-universal in the applications
  [0080](0080.md) describes, and today served in PHP by the broken parser
  above or by userland reimplementations.
- **`Core\Html` already exists** as the HTML domain home: `escape`, `sanitize` and `Markup`, all
  [0024](0024.md)'s. A sanitizer worth trusting is parse → filter →
  serialize over a browser-equivalent parse; the parser is the sanitizer's own foundation arriving,
  not a new neighbour.
- **The engine already has a name in this repository.**
  [0121](0121.md) selects `html5ever` — Servo's
  production parser, spec-complete tokenizer and tree construction — as the PDF engine's front end.

## Decision

### 1. An entry on `Core\Html`, never a mode of `Core\Xml`

HTML parses through `Core\Html`, by the WHATWG parsing algorithm, and the parse **never fails**: implied
tags, error recovery and foster parenting are the specified output every conforming parser produces, so
recovery here is [0095](0095.md)-clean — nothing is guessed,
because the spec fixes the answer. `Core\Xml` keeps the opposite contract: malformed XML **throws**.
One API flipping between refuse-hard and recover-always under a flag would be the exact ambiguity R11
and R17 exist to prevent, and is the libxml2 design being retired. Migration:
`DOMDocument::loadHTML`/`loadHTMLFile` and PHP 8.4's `Dom\HTMLDocument` map to `Core\Html`; the DOM's
XML half stays with `Core\Xml`, unchanged.

### 2. One tree, two front doors

Both parsers materialise **the same node family** — `Core\Xml`'s tree API's types. Queries, traversal
and the tree's memory story are written once; which door parsed a document does not change what a
program can do with it. Serialization follows the door: `Core\Html` serializes by the WHATWG algorithm,
`Core\Xml` by XML's rules. This matches the shape PHP 8.4 itself landed on — two document entries over
one shared node family — and extends the carve-out [0063](0063.md) § 2 already
states for tree-versus-stream: different jobs, not twins, and no operation reachable through both.

### 3. The engine is `html5ever`, through a Novis-owned tree builder

`html5ever` drives a tree-builder interface rather than imposing its own DOM; ours builds `Core\Xml`'s
request-attributed nodes directly. Its bundled example DOM (`markup5ever_rcdom`, reference-cycled and
maintained as a sample) is not used. The crate is the one 0121's engine names, shared at the source
level and compiled into each home — native in Core, inside the sandboxed `nvs/pdf` engine — so the
language and its PDF component parse HTML identically: one behaviour to document, one parser to fuzz.
`Core\Xml`'s parser stays strict; `xml5ever` is rejected there because it implements the
error-recovering XML5 draft, the wrong contract for § 1's refuse rule.

**What it spends**, per parse: the materialised tree, proportional to the document, attributed to the
request and gone with it — the same account `Core\Xml`'s tree API already opens, spent once because the
tree is one implementation.

### 4. Unscheduled, and lands with `Core\Xml`

No milestone owns either parser. The constraint this ADR records: **the milestone that schedules
`Core\Xml`'s tree API builds `Core\Html`'s parse in the same milestone.** The tree, the node types and
the builder interface are one implementation; scheduled apart, each half would price the shared tree
again, and the second one built would be shaped by whichever landed first instead of by this ADR.

## Consequences

- **The sanitizer gains its foundation.** `Core\Html::sanitize` becomes parse → filter → serialize over
  the browser's own algorithm, so the mXSS divergence class is absent by construction — there is no
  second parse to disagree with the browser's.
- **Browser equivalence becomes a compatibility surface.** What `html5ever` parses is what Novis
  parses; a divergence from WHATWG is an upstream bug to fix, never a Novis dialect to document.
- The inventory rows for `Core\Html` and `Core\Xml` in
  [docs/spec/01-core-library.md](../spec/01-core-library.md) § 17 carry the parser and the shared tree;
  the DOM domain's row-by-row accounting in `02-php-migration.md` is owed
  when that domain is filled in, as usual.

## Alternatives rejected

- **An HTML mode on `Core\Xml`** — libxml2's and `loadHTML`'s design. Two opposite failure contracts
  under one API, switched by a flag: R11's and R17's shared target, and the shape whose twenty-year
  record is § *Context*'s first bullet.
- **A separate HTML node type.** Doubles every query and serializer for no semantic gain; PHP 8.4
  needed new classes only to escape its legacy ones, and Novis has no legacy to escape.
- **Writing the parser ourselves.** An unfuzzed reimplementation of one of the largest parsing specs in
  existence, losing on priorities 1 and 2 to buy nothing `html5ever` does not already give.
- **Leaving HTML parsing to an extension or the ecosystem.** The sanitizer is Core
  ([0024](0024.md)) and must parse to filter; parsing is request-path
  core work with hostile input, exactly what Tier 0 exists to own with one spelling.

## Verification

Owed by the milestone that builds the parsers, recorded here so scheduling inherits them:

- The html5lib-tests tree-construction corpus passes over `Core\Html`'s parse — browser equivalence
  demonstrated against the shared suite, not asserted.
- One fixture, parsed through both doors: malformed as XML it throws through `Core\Xml` naming § 1;
  as HTML it parses, and the recovered tree matches the corpus's expected construction.
- The `.nvst` trees hold R17: no tree operation is reachable through both `Core\Html` and `Core\Xml`,
  and the member lists pin which door owns which entry.
