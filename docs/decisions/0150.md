# ADR 0150 — `is` tests a value against a type, answers `bool`, and is total

- **Scope:** the `is` operator, the type forms it accepts, the three it refuses, and the narrowing it
  performs. It decides nothing about *patterns* — destructuring, array shapes, comparison patterns,
  pinning, binding — which § 7 reserves and does not design.
- **Depends on:** [0007](0007.md) (the type system and `mixed`), [0047](0047.md) and
  [0066](0066.md) (narrowing), [0124](0124.md) (`let` and `is` reserved),
  [0033](0033.md) (the `tainted` qualifier), [0004](0004.md) (the priority ordering).
- **Validated by:** goal `type-test`'s acceptance list.

> **In short:** `$x is T` asks whether a value currently holds a `T` and answers `bool`. It is
> **total** — it always compiles and never refuses because the answer happens to be knowable — and it
> narrows its subject on the true edge. The spelling is not ours: PHP reserved `is` for its Pattern
> Matching RFC, and we implement that RFC's *type pattern* row exactly, refuse three things it has no
> equivalent for, and leave every genuinely pattern-shaped construct unclaimed until PHP votes. The
> operator closes a real hole — `as ?T` asks whether a value *can become* a `T`, and until now
> nothing asked whether it *is* one.

## Context

### 1. Two questions, one spelling, and only the wrong one was reachable

`rule:types/conversion` makes `as ?T` a **coercion**: `"7" as ?int` is `7`, not `null`, because the
row `string → int` succeeds whenever the whole string is an exact numeric literal. So the idiom a
program reached for —

```php
if (($m as ?int) != null) { … }
```

— answers *"can this become an int"*. Nothing answered *"is this an int"*.

The representation question had exactly one door, `Core\Reflect::typeOf`, and it does not narrow:
`rule:types/narrowing` says an equality against an enum case leaves the subject at its declared type,
and `typeOf` returns an enum case. So the shape a program had to write was

```php
if (Core\Reflect::typeOf($m) == Core\Reflect\TypeKind::Int) {
    int $n = $m as int;      // provably redundant, and the checker cannot know it
}
```

where the `as int` is dead work with a live throw path. That is the hole this record closes.

### 2. `mixed` is where this bites, and `mixed` is not rare

`rule:types/unions-and-mixed` puts untrusted input in `mixed` deliberately —
`Core\Request::query()`/`::post()`, `Core\Server::*`, `Core\Script::args()`, `Core\Json::decode`. Every
one of those is a place a program wants to ask what it actually received before deciding what to do,
and the only spellings available were a coercion that throws or a reflection call that does not narrow.

## Investigation

### 3. Why PHP reserved `is`, established rather than assumed

`rule:statements/let-and-is-are-reserved` reserved `is` on the strength of PHP 8.6 deprecating it as
an identifier, and recorded the motivation as "future use" — which is not a fact anything can be
designed against. The *Deprecations for PHP 8.6* RFC states it outright:

> "The motivation for this deprecation is to properly reserve this identifier for the pattern matching
> RFC. If accepted, calling a class, interface, trait, enum, constant, or function 'is' will emit a
> deprecation"

That passed 29 Yes / 10 No / 6 Abstain. `let` was reserved in the same RFC for an unrelated reason —
the block-scoping construct, whose own RFC was declined — so the two share a deprecation and nothing
else, which is why § 8 splits them.

The *Pattern Matching* RFC (Larry Garfield, Ilija Tovilo; part of the ADT epic) makes `is` a binary
operator whose right-hand side is a **pattern** and whose result is always `bool`. Its rows are type
patterns, literal patterns, class-constant patterns, numeric comparison patterns, array sequence and
associative patterns, object destructuring, compound DNF patterns, and variable binding. It targets the
strict semantics `is_int()` has, not PHP's coercing comparisons. **It is in discussion and has not been
voted**; the authors deferred a vote, and the binding syntax and the `is` placement inside `match()`
are both actively contested.

So the spelling arrives with a meaning already attached, and the honest question is not "what should
`is` mean in Novis" but "how much of what it will mean in PHP can we implement now without being
wrong later".

### 4. The type-pattern row maps onto our type grammar exactly

PHP's type patterns are `is string`, `is Request`, `is ?array`, `is int|float`, `is iterable`,
`is true`, `is mixed`, with `|` and `&` under DNF; its literal patterns are `is 5`, `is 'yay'`,
`is "beep"|"boop"`, `is 3.14`, `is null`; its class-constant patterns are `is self::Wild` and
`is MyEnum::Case`.

Every one of those is a `Type` in our grammar already. `nvs_syntax::ast::TypeAtom` carries `True`,
`False`, `StringLiteral`, `IntLiteral`, `Member` (which is exactly "class constant or enum case"),
`Iterable`, `Mixed`, and `TypeKind` carries `Union` and `Intersection`. The one row we cannot match is
`is 3.14`, because `rule:types/single-value-types` deliberately has **no float literal type** — "float
equality is imprecise enough that a singleton `0.1` is a footgun". We refuse it rather than answering
it differently, which is the safe side of a divergence.

### 5. `is` is not a superset of `instanceof`, and cannot become one

The obvious simplification — retire `instanceof`, since `is` does everything it does and more — is
wrong, and the reason is structural rather than a matter of taste.

`is`'s right-hand side is a **pattern**: compile-time syntax. A class reference is a **runtime value**.
In PHP's grammar the slot a dynamic class would occupy is already spent on capture — a bare `$var` on
the right of `is` *binds*, and always matches — and the escape hatch, pinning with `^$var`, compares
with identity `===`, which asks whether the subject *is* that descriptor rather than an instance of it.
The RFC does not discuss dynamic class names at all, and says plainly that `is` and `instanceof`
coexist.

`rule:types/class-reference-sites` gives `class<T>` three sites and `$x instanceof $cls` is one of
them — "nothing; the descriptor is the test". Retiring `instanceof` would delete a third of that rule's
surface with no replacement spelling, and would strand the migration path
`rule:types/a-declared-type-answers-before-the-program-runs` documents for PHP's own dynamic
`$x instanceof $name`.

Defining `$x is $cls` as the dynamic test *ourselves* is worse than either: if PHP ships binding, the
same line means two different things in the two languages and compiles silently in both. § 6's third
refusal is that trap, closed.

### 6. `E0497` does not generalize, and the first draft of this design assumed it did

`rule:types/a-declared-type-answers-before-the-program-runs` reads, in prose, as though a test
whose answer the declaration already settles is refused. The implementation is narrower.
`nvs_types::expr::members::infer_instanceof` fires on one condition:

```rust
if !can_hold_an_object(subject, env.interner) {
```

That is "this value can never be an object **at all**" — `instanceof` needs a class to test against and
a scalar has none, so the operator is *inapplicable*, not merely predictable. Two accepted conformance
cases prove the distinction: `instanceof-answers-for-every-supertype` writes `$leaf instanceof Leaf`
where `$leaf` is inferred `Leaf` — statically true, accepted, prints `1` — and
`instanceof-is-false-for-a-sibling-branch` is statically false at the class level and equally accepted.

`is` has no such inapplicable case. Every value has a representation, so `is` is total over every
subject and every accepted `T`. "The answer is knowable" and "the question is meaningless" are
different properties and only the second is a diagnostic.

There is a second, independent reason not to refuse a knowable test: **narrowing manufactures them.**
Once `is` narrows, a guard written inside an already-narrowed branch — or a helper inlined into one —
is statically true by construction. Refusing that would mean narrowing turns working code into a
compile error, which is a property no flow analysis should have.

## Options considered

1. **Leave `is` reserved and spell the question `Core\Reflect::typeOf`.** Rejected: it does not narrow,
   so every use pays a redundant `as` with a live throw path, and § 1's shape stays the idiom.
2. **A general `is` designed from first principles, ignoring PHP.** Rejected once § 3 established that
   the spelling already has a meaning. A familiar spelling with different behaviour is the expensive
   kind of divergence.
3. **Implement PHP's whole Pattern Matching RFC now.** Rejected: it is unvoted, and its binding and
   `match()` syntax are the parts under active objection. Building them means building them twice.
4. **Take the type-pattern row, refuse what has no answer, reserve the rest.** Adopted.
5. **Retire `instanceof` into `is`.** Rejected on § 5.
6. **Refuse a test whose answer is statically known.** Rejected on § 6.

## Decision

### 7. The operator

`$x is T` where `T` is any type a value can inhabit. It answers `bool`. It is **strict** — no
coercion, matching the RFC's own "consistent with `is_int()`" — and it is **total**: it always
compiles, and a provably-constant result folds rather than diagnosing. The full accepted set and the
three refusals are `rule:types/type-test`, which is this decision's rule and the only place that table
lives.

The right-hand side is the **existing `Type` production**, the one `as` already parses, not an
expression. That is the whole implementation lever: `ExprKind::Conversion { expr, ty }` exists, so this
is a sibling node rather than new grammar. `is` keeps the precedence level the reserved-word hook
already sits at in `nvs_syntax::parser::expr::parse_instanceof` — it is a comparison, like the operator
beside it.

### 8. What `is` does not take, and why the reservation stays

Binding and capture, object destructuring, array sequence and associative patterns, comparison
patterns, and pinning are **not implemented and not designed**. Each parses to a refusal naming itself
as reserved rather than being given a meaning we would have to take back. This is not caution for its
own sake: § 3 established that these are exactly the rows PHP has not settled, and § 5 established what
it costs to guess one wrong. `php-migration/is-takes-pattern-matchings-type-patterns` is the
standing contract, and it is what a future session reads before claiming any of that syntax.

`let` stays reserved on `rule:statements/let-and-is-are-reserved`'s original ground, which is
untouched — its construct genuinely does not exist, and PHP's own reason for it was declined.

### 9. Narrowing

`is` is narrowing's fifth spelling, on the **true edge only**, matching what
`an-instanceof-narrows-its-subject-on-the-true-edge` already asserts for the operator beside it. It
narrows the binding, never the declared type, exactly as `rule:types/narrowing`'s closing paragraph
requires of every other spelling; a write inside the block widens again.

False-edge narrowing — subtracting a union member on the failing branch — is deliberately **not** taken
here. It is a real and separable improvement, it applies equally to `instanceof` and `== null`, and
adding it inside this record would mean stating it once for `is` and leaving three spellings behind.

### 10. Where the answer differs from PHP's, on identical source

Two rows, both consequences of our type system being finer than PHP's rather than of anything `is`
does, and both newly reachable from PHP-shaped source because `is` is the first spelling that exposes
them:

- **`int` and `uint` are separate tags.** A value from a `BIGINT UNSIGNED` column answers `is uint` and
  **not** `is int`, where PHP's `is_int()` answers true for both. The migration spelling is
  `is int|uint`.
- **`string` and `bytes` are separate tags.** Binary data answers `is bytes`; PHP's `is_string()`
  answers true for it.

Both are already listed divergences of the type system. What is new is that `is` makes them reachable
by a mechanical `is_int($x)` → `$x is int` rewrite, so each gets a row of its own rather than riding on
`Core\Reflect::typeOf`'s.

`rule:types/uint`'s standing sentence — "there is no `is_int`-style predicate to disagree with it,
because there are no free functions" — stops being sound reasoning the moment this operator exists.
The rule stays true, since `is` is an operator and not a free function, but its argument is replaced
rather than left to read as though the question cannot arise.

## Diagnostics

Three, all in the `E08xx` band, since `E04xx` and `E07xx` are full:

- **`E0810`** — `is` against a qualifier with no runtime existence: `$x is tainted string`,
  `is secret bytes`. `rule:security/tainted-qualifier` erases both before codegen, so there is no bit
  to read. Help names the unqualified test and points at the `as` that launders.
- **`E0811`** — `is` against a type no value inhabits: `void`, `never`.
- **`E0812`** — `is` against a value where a type belongs: `$x is $cls`. Help names
  `$x instanceof $cls` and `rule:types/class-reference-sites`, and says that the spelling is reserved
  because PHP's grammar binds there.

A float literal on the right (`$x is 3.14`) reuses `rule:types/single-value-types`' existing refusal rather
than claiming a fourth code — the type does not exist, and that is already what the diagnostic says.

## Consequences

**Performance (priority 3):** positive and small. A guarded branch loses a `Type`-checked `as` and its
throw path; the test itself is one tag comparison for every scalar row, the existing descriptor walk
for a class, and an O(n) element walk for `array<T>` — the same walk `as array<T>` already documents,
at the same cost, in a spelling that does not throw.

**Memory:** none. `is` adds no representation; every row it reads is a tag that already exists.

**Simplicity (priority 4):** one operator added and one narrowing spelling stated. Against that: the
`as ?T` idiom stops standing in for a question it never answered, `typeOf` stops being the only door to
a value's representation, and the coercion/representation distinction becomes visible in the source
instead of being folklore. Net positive, and the operator is recognisable on sight — *is `$a` of type
`$b`* — which is most of its value.

**Usability:** the largest single gain. § 1's shape is three lines and a redundant throw path today and
one line after.

**Migration:** `is_int($x)` → `$x is int` is mechanical everywhere except § 10's two rows, which the
migration checker flags rather than rewrites, because only the author knows whether an unsigned column
is in play.

## Alternatives rejected

- **A fourth diagnostic for a statically-known result.** Rejected on § 6: it would fire on code that
  narrowing itself generates. If dead branches are worth surfacing, that is a lint over every
  condition, not a property of this operator.
- **`is` accepting `array<T>` only in its bare form**, to keep every test O(1). Rejected as incoherent:
  `as array<T>` already performs the same walk and is accepted, so refusing the cheaper spelling of the
  same question optimizes nothing and teaches the reader something false about the cost.
- **A `Callable` case, and `is callable`, refused by analogy with `Core\Reflect\TypeKind`.** The
  analogy does not hold. `TypeKind` excludes `Callable` because its cases must *partition* the tag
  space and a closure is already an `Object` — a second case one value satisfies. `is` has no
  partition to preserve; overlapping questions are exactly what an operator over an open type grammar
  is for, and `$x is callable` is well defined.
- **An `integer`-style spelling matching either integer tag**, to paper over § 10. Rejected: it adds
  surface to hide a divergence rather than stating it, and `int|uint` already says it in the grammar
  the reader knows.

## Revisiting

**This record's § 7 and § 8 split is a bet on an unvoted RFC.** Three triggers, each of which is a
session's worth of work and none of which invalidates what lands here:

1. **The Pattern Matching RFC passes.** Then § 8's reserved rows have a settled meaning and can be
   taken deliberately, starting with binding. Re-read the accepted text rather than the version § 3
   describes: the binding shorthand and the `match()` placement were the contested parts and are the
   most likely to have moved.
2. **The RFC is declined or abandoned.** Then `is` is ours, § 8's reservation has no external claim
   behind it, and the question becomes whether Novis wants patterns at all — which is a design
   question, not a compatibility one.
3. **False-edge narrowing is taken** for any spelling. § 9 deliberately left it out of this record for
   all four existing spellings as well; whoever takes it takes it for all five at once.

## Verification

Goal `type-test` is the implementation and its acceptance list is the authority. The properties this record
requires a case for:

- Every accepted row of `rule:types/type-test`'s table answers correctly over a `mixed` subject,
  including `uint` and `decimal`, which PHP has no predicate for.
- `is` is total: `int $n; $n is int` compiles and is `true`; `int $n; $n is string` compiles and is
  `false`. Neither is a diagnostic.
- `"7" is int` is `false` where `"7" as ?int` is `7` — § 1's distinction, asserted directly.
- `is` narrows on the true edge and not the false one, and a write inside the block widens.
- `E0810`, `E0811` and `E0812` each fire on their own case under `tests/conformance/reject/`.
- A `uint`-tagged value answers `is uint` and not `is int` — § 10's first divergence row, as a
  conformance case rather than as prose.
- The differential tree does not gain an `is` case: PHP cannot run one, which is itself the reason
  § 10's rows need conformance cases instead.
