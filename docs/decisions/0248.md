# ADR 0248 — `Core\Path::fromCwd` removes `tainted` from a path typed on the command line, and nothing else

- **Scope:** Which qualifier `Core\Path::fromCwd`'s answer carries, and the one exception that makes it
  a launderer for the file-path sink. The member's join, its refusal during a request and every `fs`
  grant are unchanged.
- **Depends on:** [0241](0241.md) (a relative path built at run time throws, and `fromCwd` is the one
  way to the working directory), [0024](0024.md) (laundering is sink-named), [0133](0133.md) (which
  launderers answer a carrier).
- **Validated by:** the Stage 4 checks of goal `path-literals-follow-up`: `nvs-stdlib`'s
  `from_cwd_returns_a_string_without_tainted`, and the two `.nvst` cases named under *Verification*.

> **In short:** `Core\Path::fromCwd`'s parameter is a launderer, so its answer is a plain `string` and
> reaches `Core\IO::read` and every other path door. A path the user typed arrives `tainted` from
> `Core\Cli::arguments`, and before this a command-line tool could not open the file its user named
> without `Core\Taint::assertTrusted`. The member still throws while a request is being answered, so
> request data is never laundered by it, and the `fs` grants still bound every file the answer can
> name. `secret` is not removed: the parameter refuses a `secret` argument, as every launderer does.

## Context

[0241](0241.md) made a relative path built at run time throw at every `Core` door, and named
`Core\Path::fromCwd` as the way to join a path typed on a command line to the working directory. Its
parameter was `Qual::Contagious`, so the answer kept the argument's `tainted`. Every argument a
program is started with is `tainted` (`rule:security/tainted-qualifier`), and every path parameter is
a sink that refuses a `tainted` argument. The one use the member exists for, `nvs run tool.nvs
report.txt` opening `report.txt`, therefore did not compile without `Core\Taint::assertTrusted` at
every call.

## Decision

### 1. The parameter is `Qual::Launder`, and the sink it names is a file path

`fromCwd`'s `$path` is `Qual::Launder`, and its answer is `CoreTy::Str`. The sink is the file path a
`Core` door opens. By `rule:security/launderer-answers-a-carrier` the answer is a plain `string`: no
path sink transforms a value on its own, so the first condition fails before the second is asked.

### 2. Why this sink may be laundered by a join

`rule:security/launderers-are-sink-named` asks each launderer to make its value safe for one sink.
`fromCwd` does not inspect the bytes, so the safety comes from three facts outside them:

- **It throws while a request is being answered.** `nvs_runtime::capability::working_dir` reads the
  working directory first and throws when the context has a request, whatever the argument is. Data a
  request sent never reaches the answer inside that request.
- **The person who typed the path already runs the program.** A command-line argument is `tainted`
  because the program did not choose it, but the user who chose it can already open any file the
  process can. Laundering it hands them nothing they did not have.
- **The `fs` grants still bound every file.** The answer is checked at the door that opens it, after
  the path is canonicalized (`rule:security/path-scope-canonicalise-then-prefix`). A `..` in the
  argument reaches no file outside a grant.

A request that must open a file named by its own data keeps `Core\IO::within($base, $path)`, the
path-component launderer, which checks that the path stays under `$base`.

### 3. `secret` is not removed

`Qual::Launder` refuses a `secret` argument, as every mark except `Qual::Reveal` does
(`rule:core-classes/secret-reveal`). A `secret` path does not compile at `fromCwd`, so the answer never
carries a revealed secret.

### 4. Tradeoffs

- **Performance:** nothing. The qualifier is a compile-time fact; the native function is unchanged.
- **Memory:** nothing.
- **Usability:** a command-line tool reads the file its user typed with one call, from any folder.
- **Simplicity:** one exception to the security rule more, stated in the rule's fragment, and one
  `Core\Taint::assertTrusted` fewer in every command-line program that opens a file.

## Consequences

- `Core\Path::fromCwd` joins the launderer roster in `nvs_stdlib::html`'s
  `every_launderer_for_an_auto_escaping_sink_answers_a_carrier`, answering a plain `string`.
- A queued job and a spawned isolate answer no request, so `fromCwd` runs there whatever text they
  were handed. The `fs` grants of that isolate bound the file the answer names.
- No other member gains or widens a launder mark.

## Alternatives rejected

- **A new `CoreTy` for "path from the command line".** It would mark the same fact a qualifier
  already marks, and every path door would have to accept the new type.
- **Keeping the answer `tainted`, and documenting `Core\Taint::assertTrusted`.** That makes the
  greppable escape hatch a line every command-line tool writes, so it stops marking the unusual call.
- **Laundering `Core\Cli::arguments` itself.** An argument is also a shell word, an SQL value and an
  HTML text, and the rule names one sink per launderer.

## Verification

- `nvs-stdlib`'s `from_cwd_returns_a_string_without_tainted`: the row's parameter is `Qual::Launder`,
  its answer is a `string`, and a context answering a request still throws.
- `tests/conformance/core/path-from-cwd-gives-a-path-core-io-read-accepts.nvst`: a path from
  `Core\Cli::arguments` reaches `Core\IO::read` through `fromCwd`.
- `tests/conformance/reject/path-a-tainted-path-not-from-cwd-does-not-reach-io-read.nvst`: the same
  path passed to `Core\IO::read` directly does not compile.
