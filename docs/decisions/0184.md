# ADR 0184 — A worker placement starts the child on another core through that core's inbox, and answers it with a copy in a slot

- **Scope:** the mechanism behind `on: "worker"` — which core runs the child, how it is started there,
  how its answer comes back, what cancels it, and what bounds the set of cores that can take one. Not in
  scope: what a worker placement *means*, which [0006](0006.md) settled; what may cross the boundary,
  which `rule:security/isolate-values-cross-by-copy` settles; the surface itself — the `on:` option key is
  parsed already (`crates/nvs-types/src/expr/isolate.rs:387`) and the type check that narrows its value is
  written where that check is; `limits:` and `grants:`, whose enforcement M5 deferred.
- **Depends on:** [0006](0006.md) for the isolate, its budget accounting and the two crossings;
  [0138](0138.md) for the cross-thread wake that carries an id and nothing else;
  [0072](0072.md) for the guarantee that nothing is still running when a call returns;
  [0004](0004.md) for the ordering that puts the copy's cost below correctness and isolation.
- **Validated by:** the one rule it creates is `designed` on acceptance; its `guardedBy` is filled from
  the `.nvst` cases and the `nvs-host` tests the goal's later stages write, beside the existing
  `an_os_process_costs_orders_of_magnitude_more_than_a_task` baseline in `tests/perf_guards.rs`.

> **In short:** `on: "worker"` **starts** the child on a core other than its parent's, because a task
> never migrates (`rule:concurrency/a-wake-never-moves-a-task`) and so a placement can only be a decision
> made once, at the spawn site. The compiled unit, the copied argument and a `RemoteWake` for the parent
> go into the destination core's inbox; that core's reactor drains the inbox, starts the child as a root
> task on its own scheduler, copies the answer into the handle's slot when it finishes, and drops the
> handle, which ends the parent's park. It is the blocking pool's handoff turned around, and it crosses a
> thread boundary with an id and a poke, nothing else. The crossing is the same walk the boundary already
> audits with one thing subtracted — the **move is not available**, because a non-atomic refcount is only
> sound while a value is reachable from one core — so argument and answer are copied at every node. The
> child is still its parent's child: cancelled with it, charged to its tree, and holding the return
> guarantee across the thread. Under `nvs serve` the core is a sibling serving core, chosen round-robin;
> everywhere else worker cores are started lazily and bounded at the core count.

## Context

[0006](0006.md) decided that `spawn script` is an in-process isolate and that `on: 'worker'` composes the
placement axis with it rather than multiplying the syntax (`docs/decisions/0006.md:151-153`), and it
priced the placement in one sentence: a cross-core isolate pays the deep copy twice, so a large result
argues for keeping the child on the parent's core (`:328-329`). What neither that record nor
`rule:security/isolate-values-cross-by-copy` says is anything about the *machinery*: which core a worker
placement picks, how a program's unit and argument get there, how a result gets back, what happens to a
worker-placed child when its parent is cancelled, and what stops a program from starting a thread per
spawn. That is the whole of what is left, and the host seam that has to answer it
(`crates/nvs-host/src/group.rs:190-203`) currently starts every isolate on the calling core.

The constraint that shapes all of it is already decided and is not this record's to reopen: a task never
migrates (`rule:concurrency/a-wake-never-moves-a-task`). What crosses a thread boundary in this runtime
is a task id and a poke of one core's poller, and the scheduler, the arena and the stack are reachable
from one core only. A placement mechanism that moved a running child would be a second concurrency model
beside the coroutines, which `rule:concurrency/one-scheduler` forbids outright.

## Investigation

There is already a handoff in this crate that does exactly the hard half. `crates/nvs-host/src/blocking.rs`
takes a `RemoteWake` for the running task, boxes the work with that handle and a slot for its answer,
hands it to a thread, and parks; the far side runs it, fills the slot and drops the handle, and the wake
ends the park while the slot carries the value (`crates/nvs-host/src/blocking.rs:14-20`). `RemoteWake` is
the only `Send` thing in the crate, carries no reference to a scheduler, a reactor or a stack, and
delivers exactly once between `wake` and its drop (`crates/nvs-host/src/reactor.rs:205-223`). The pool's
bound is the second half of the pattern worth copying: threads are started lazily, so a worker that does
no blocking work has none, and the ceiling is a function of the core count rather than of traffic
(`crates/nvs-host/src/blocking.rs:27-36`).

A worker core is also not a new kind of thing. `Worker::spawn(cpu, body)` already starts a thread, pins
it to a core and runs that core's scheduler on it (`crates/nvs-host/src/lib.rs:180-205`), which is how
`nvs serve` gets its serving cores. What is missing is only the channel by which one core asks another to
start a task.

## Options considered

**Migrate the child to an idle core.** Rejected, and not narrowly: refcounts are non-atomic and an arena
belongs to a core, so this is unsound rather than expensive, and it contradicts
`rule:concurrency/a-wake-never-moves-a-task` — which exists because a design admitting migration has no
diagnostic for the day it is violated.

**A shared global run queue that any core steals from.** Rejected. It is one piece of contended state on
the request path, it makes which core runs a child unpredictable — and therefore makes the budget, the
grants and the cancellation path harder to reason about for no gain — and it is the same objection that
keeps the blocking pool per worker rather than shared.

**A per-core inbox, drained by the reactor that is already polling.** Chosen. The core being asked is
already asleep in a poll that a cross-thread poke ends, so starting a child on it costs the same wake
that a blocking-pool answer costs, and the queue is single-consumer by construction.

**A subprocess for a worker placement.** Rejected by [0006](0006.md) for the whole construct, and the
measurement is in that record: an OS process costs orders of magnitude more than a task.

## Decision

### 1. The placement is a *start*, and it is decided once

`on: "worker"` selects the core the child is **started** on. Nothing about the child moves afterwards: it
runs to completion on that core, on a stack pooled there, under that core's reactor. `on: "here"` is the
same child on the parent's core, which is what a spawn with no `on:` already does.

### 2. The crossing is the audited walk, minus the move

Argument in and answer out use the one graph walk and the one set of refusals
`rule:security/isolate-values-cross-by-copy` describes — a closure, an `inout` alias, a host handle, a
class the far side cannot resolve and a `secret` property are refused identically at both crossings. The
single difference is that the **move-when-refcount-is-1 shortcut is not available**: the refcounts are
non-atomic precisely because a value is reachable from one core, so every node is copied. That cost
belongs to the placement, not to the boundary, and a program that wants it back writes `on: "here"`.

### 3. The mechanism is the blocking pool's, turned around

Each core owns an **inbox**: a queue of start requests, written by any core and drained by its own
reactor alongside the readiness it already reports. A worker placement takes a `RemoteWake` for the
parent task, puts the `Arc<CompiledUnit>`, the copied argument, the entry, the child's grants and that
handle into the destination core's inbox, pokes that core's poller, and parks the parent. The destination
core drains the inbox on its next turn and starts the child as a root task on its own scheduler. When the
child finishes, its `ScriptResult` — the same shape a same-core child answers with, `ok = false` and all
— is copied into the handle's slot and the handle is dropped, which ends the parent's park. The slot is
the record and the wake is only the end of the wait, so a spurious wake re-reads an empty slot and parks
again, exactly as `crates/nvs-host/src/blocking.rs:14-20` describes for the other direction.

### 4. It is still its parent's child

A worker-placed child is a child of the task that spawned it in every respect except which core runs it.
It dies with its parent; its budget is the tree's root's, never a per-call limit
(`rule:security/isolate-budget-is-the-trees`); and
`rule:concurrency/nothing-is-still-running-when-a-call-returns` holds across the thread — a cancelled
parent's call does not return until the cancellation it sent through the inbox has been acknowledged from
the other core and the child's teardown has run there. Cancellation therefore travels the same way the
start did: a request in an inbox, a poke, and an acknowledgement carried by the same handle. The parent
can be blocked on that acknowledgement, and that is the price of the guarantee, which
[0072](0072.md) already argued is worth paying.

### 5. Which core, and what bounds the set

Under `nvs serve` the destination is a **sibling serving core**, chosen round-robin over the cores this
process is already running schedulers on. Those threads exist, they are pinned, and adding a second thread
per core for placement work would oversubscribe exactly the cores the server's own latency depends on.

Everywhere else — `nvs run`, a queue job, a test — one scheduler is all there is
(`crates/nvs-cli/src/runner.rs:454`), so **worker cores are started lazily**: a core's scheduler thread is
started the first time a program places a child on one, and the set is bounded at the core count. A
program that never writes `on: "worker"` therefore starts no extra thread, which is the same shape, and
the same reason, as a worker with no blocking work having no pool threads.

### 6. What it spends

Per in-flight worker-placed child, charged to its tree: one task context and one pooled stack on the
destination core, plus the argument copied at every node on the way in and the answer copied at every
node on the way out — twice what a same-core child pays, which is [0006](0006.md)'s stated price. Per
process: at most one scheduler thread per core, and only for cores a program has actually placed a child
on. That is O(cores) and O(in-flight); nothing here grows with requests served, which is what
`rule:programs/memory-priority` asks to be said out loud.

## Diagnostics

This record claims no diagnostic code. The refusals a worker placement can produce are the boundary's own
and fire identically on both crossings, naming the value and the class as they already do; an `on:` value
that is neither `"worker"` nor `"here"` is refused at compile time by the check that narrows the option
key, and the code for that is claimed where the check is written. The one runtime failure this mechanism
adds of its own — a worker core that cannot be started because the OS refused a thread — surfaces as the
spawn failing, with `ok = false` and the OS error in `error.message`, rather than as a silent fallback to
the parent's core: a program that asked for another core and got this one would be measuring a speedup
that is not there.

## Consequences

- A worker placement's latency floor is two copies plus two cross-thread wakes, which is what makes the
  same-core placement the right default and `on: "worker"` the thing a program reaches for when the child
  is CPU-bound and its values are small. This is the construct `docs/plan/design.md:262` points CPU-bound
  work at, and the one M5's near-linear-speedup sentence is proved through.
- `nvs serve` gains no thread from this feature. A deployment that never places a child on a worker has
  exactly the threads it has today.
- The inbox is the second cross-core channel in the crate, after the wake itself. It is single-consumer
  and drained by the reactor, so it adds no lock to the request path, but it is a place where a start can
  be *queued* behind another core's current turn — a worker placement is asynchronous in the sense that
  the child may not have begun when the spawn expression returns its handle, which is already true of a
  same-core spawn.

## Alternatives rejected

- **Falling back to the parent's core when no worker core can be started.** Rejected in § *Diagnostics*:
  silently answering a placement with the thing it was written to avoid is unmeasurable from the program.
- **A thread per worker-placed child.** Rejected. It is O(in-flight children) in threads rather than
  O(cores), it defeats the pinning the whole thread-per-core design rests on, and it is the subprocess
  argument in cheaper clothes.
- **Work stealing between serving cores.** Rejected for now, and it is a different decision: it would make
  placement implicit, and implicit placement cannot be reasoned about from the spawn site, which is where
  a program states what it wants.

## Revisiting

One trigger. If measurement on a loaded server shows that placing children on sibling serving cores
starves the requests those cores exist to answer, `nvs serve` uses the lazily started worker cores too —
the same mechanism, a different destination set — and the rule's last paragraph is what changes.

## Verification

The conformance half, under `tests/conformance/isolate/`: a child placed `on: "worker"` runs and answers
the same `ScriptResult` a same-core child answers; it cannot read a parent variable, global, static or
output buffer; a closure, an `inout` binding and a host handle are refused at the crossing with the same
diagnostics as on this core; a cyclic argument crosses without hanging; a child's uncaught throw leaves
the parent running with `ok = false`; a cancelled parent leaves no orphan and returns only after the
child's teardown has run.

The `nvs-host` half: a worker-placed child runs on a thread other than its parent's, asserted from the
child; the inbox delivers a start to a core that was asleep in its poll; a dropped handle wakes the parent
rather than wedging it; the lazily started worker cores never exceed the core count; and a `nvs serve`
process places children round-robin over its existing serving cores, starting no thread.
