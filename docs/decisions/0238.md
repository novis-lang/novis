# ADR 0238 — An array literal at `array<float>` stores floats, an existing `array<int>` is not an `array<float>`, and `as array<float>` converts one into a new array

- **Scope:** How an `int` or `uint` meets a `float` element of an array: in an array literal, in an
  array that already exists, and in `as array<float>`. The shape half is [0236](0236.md).
- **Depends on:** [0007](0007.md) and [0054](0054.md) (the `int` → `float` widening is the one implicit
  conversion), [0236](0236.md) (an existing value's `int` field does not satisfy a `float` one).
- **Validated by:** `tests/conformance/lang/an-array-literal-at-a-float-element-type-stores-floats-and-as-converts-an-int-array.nvst`
  and `tests/conformance/reject/an-existing-int-array-does-not-widen-to-a-float-array.nvst`.

> **In short:** an array literal placed at `array<float>` places each element at `float`, so a whole
> number literal, an `int` variable and an `int` expression are stored as floats, at any depth and in
> a shape field. An `array<int>` or `array<uint>` that already exists does not satisfy `array<float>`,
> at any depth: assigning, passing or returning one there is `E0401` (`E0403` for a return), with a
> help line that names `as array<float>`. `array<int> as array<float>` converts: it builds a new array
> of the operand's size with each `int` or `uint` element converted, exact or throwing above 2^53.
> `array<int|float>` still takes an `array<int>` as it is.

## Context

An array stores each element with the tag of the value written, and a read through an `array<float>`
loads the element as a `float` without looking at the tag. Two paths put an `int` there.

An array literal lowered every element with no expected type, so `array<float> $a = [1, 2];` stored
two `int`s, and `$a[0] + 0.5` printed `0.5`. The checker already checked each element against `float`,
and nothing recorded it.

The checker compared array element types with the widening on, so an `array<int>` satisfied
`array<float>` as an assignment, an argument and a return. Nothing converted the elements, and a read
loaded the `int`'s bits as a `float`: `2` printed `9.8813129168249E-324`. `foreach ($f as float $v)`
gave the same wrong values. `as array<float>`, the written conversion, did not help: its walk compares
tags and threw for every `int` element.

[0236](0236.md) refused the same pair inside a shape field and left the array case to another record.

## Options considered

1. **Refuse the existing array, convert at the literal, and make `as` copy.** No cost on any read.
   Code that passed an `array<int>` where an `array<float>` is declared stops compiling and writes
   `as array<float>`.
2. **Convert at the boundary.** Every assignment, argument and return from `array<int>` to
   `array<float>` copies the array. Nothing stops compiling, and a hidden O(n) copy runs on every such
   call.
3. **Convert at the read.** Every `array<float>` read tests the tag and converts an `int`. That is a
   test and a branch on every float array read, and an `array<float>` can still hold `int` tags, so
   `Core\Json::encode` and `Core\Arr::sum` see `int`s and `as array<float>` still throws.

The user chose option 1.

## Decision

### 1. A literal places each element at the element type

`nvs_types::expr::literals::check_array_literal` records the declared element type at each element's
span when the element fits it. `nvs_ir::lower`'s `lower_array_element` reads it back. Where the
element type is `float`, the element is lowered with `float` as its expected type, so a literal is a
`float` constant, and any other value is converted with the widening every `float` position performs.
A nested literal and a literal in a shape field get their element type from their own position, so
both are covered.

### 2. An existing array's elements are compared without the widening

`nvs_types::expr::assign`'s array arm compares element types with `Widening::InPlace`, the comparison
[0236](0236.md) gave shape fields. The widening is off at every depth of the element type, so
`array<array<int>>` does not satisfy `array<array<float>>`. A union element that has `int` as a member
still accepts it, and so does `mixed`.

### 3. `as array<float>` converts into a new array

The runtime walk behind `array<T> as array<U>` keeps its free answer: where every element already
has `U`'s tag, the result is the operand's own buffer under one more reference. Where an `int` or
`uint` element meets a `float` in `U`, at any level, the result is a new array with the same keys in
the same order and that element converted. The conversion is `$n as float`'s: exact, or the
`ArithmeticError` it throws above 2^53. `as ?array<float>` gives `null` there. The copy asks the
request's memory budget first, as every array write does.

## Diagnostics

`E0401` (and `E0403` for a return) keeps its message. Where the only reason is an `int` or `uint`
element type meeting a `float` one, the help line says the existing array keeps its element types
and names the conversion, for example `$value as array<float>`.

## Consequences

Performance: no cost on any read. A literal at `array<float>` converts each `int` element where it
stores it, which is one conversion per element it already wrote. `as array<float>` over `int`
elements costs one new array of the operand's size per level that holds such elements, plus one
conversion per element. Memory: that copy, per conversion, freed with the array; nothing per request
beyond it. Usability: a literal of whole numbers works everywhere a `float` array is declared, and the
wrong values are gone. Code that passed an existing `array<int>` to an `array<float>` position no
longer compiles, and writes `as array<float>`. Simplicity: arrays and shape fields follow one rule
for the widening.

## Alternatives rejected

Converting at the boundary was rejected because it hides an O(n) copy inside an assignment or a
call, where nothing in the source shows it. Converting at the read was rejected because it costs a
test on every read of a float array, the request path's most common array read, and leaves `int`
tags in an array declared to hold floats.

## Verification

The two `.nvst` cases named above. The `lang` case prints each literal form, the conversion, a
`foreach`, `Core\Arr::sum`, `Core\Json::encode` and the throw above 2^53. The `reject` case pins the
assignment, the argument, the return, a nullable target, a nested array, a `uint` element and a
spread. `docs/examples/lang/types/widening-without-as/03-a-price-list-that-mixes-both.nvs` prints
its whole numbers as written.
