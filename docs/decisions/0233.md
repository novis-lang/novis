# ADR 0233 — `nvs meta --json <entry>` names a user class's parent and interfaces fully qualified, and `nvs doc` prints them

- **Scope:** the program half of `nvs meta --json <entry>` and the page `nvs doc` renders from it. The
  registry half is unchanged, and so is the no-argument form.
- **Depends on:** [0137](0137.md) (`nvs meta --json` takes a program, and `nvs doc` renders that
  document and nothing else).
- **Validated by:** `crates/nvs-cli/tests/meta.rs` (`a_user_class_names_its_parent_and_interfaces_fully_qualified`)
  and `crates/nvs-cli/tests/doc.rs` (`nvs_doc_names_the_parent_class_and_the_interfaces`,
  `nvs_doc_writes_static_in_front_of_a_static_methods_signature`).

> **In short:** a user class's entry in the document now carries `extends`, its parent class, and
> `implements`, its interfaces, and an interface's entry carries `extends`, the interfaces it extends.
> Every name is fully qualified through the declaring file's namespace and `use` imports, and a key is
> left out when there is nothing to list. `nvs doc` prints both under the page's title, as links where
> the target has a page, and writes `static` in front of a static method's signature, which the
> document carries as the member's `kind`.

## Context

The parser already holds a class's `extends` and `implements` and an interface's `extends`, and the
compiler resolves them into its class graph, but the document left them out. A page for a class gave
no way to reach the methods it inherits, and `@see parent::m` could not be linked, because the
renderer had no parent to name. Separately, a static method's page signature read as an instance
method's: the document records `static` as the member's `kind` and deliberately not in `signature`, which
is the registry's own spelling of a member, and the renderer never put it back.

## Decision

1. **Three keys on the program half.** A class has `extends`, one name, and `implements`, a list in
   source order; an interface has `extends`, a list, because an interface may extend several. Each name
   is resolved by `nvs_hir::resolve_ref`, the function the compiler resolves it with, from the
   namespace and `use` imports in force where the declaration is written. Each key follows the
   registry's omission rule.
2. **Only the declaration's own names.** An interface reached through the parent class, or through an
   interface's own `extends`, is not repeated. The document states each edge once, on the declaration
   that writes it, and a consumer that wants the closure walks the edges.
3. **The renderer prints what the document says.** `nvs doc` writes `Extends:` and `Implements:` lines
   under the page's kind, each name a link when this run wrote its page, and `parent::` in a `@see`
   names the page's `extends`. A member whose `kind` is `static` gets `static ` in front of its
   signature.

## Consequences

A consumer of the document reads a class's lineage without resolving a name itself, so `bun nv
reference` and the website can render it the same way. The keys are compile-time output only; nothing
changes at run time, and the document grows by one short string per edge.

## Alternatives rejected

- **The names as written.** `Item` means `Shop\Item` only in the file that imported it, so a renderer
  would have to repeat the compiler's resolution to link it, which is the second resolver
  `rule:statements/one-function-resolves-every-name` forbids.
- **The transitive closure of every ancestor.** It repeats each edge on every descendant and makes a
  renderer unable to tell a direct parent from an inherited one.
- **`static` inside `signature`.** The signature is the member's own spelling, the same as the
  registry's, where `kind` already carries `static`; adding it would make the two halves disagree.
