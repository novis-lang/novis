# ADR 0181 — A third cache tier is the serving process's own, and a secret outlives a request only sealed

- **Scope:** `Core\Cache::process()` and what backs it; a lifetime and a `forget` on every tier; the two
  members through which a secret may meet a cache at all, and the single-flight `fill` behind the second;
  the same sealing in `Core\Session`; and the `[cache.process]` block. Not in scope: a fleet-wide single
  fill, which is a lease over the shared tier and has no record yet; a `secret bytes` value; and the
  `nvs/rest` package, which is the first caller of all of this.
- **Depends on:** [0059](0059.md) for the two tiers, the copy across the boundary and the cap;
  [0033](0033.md) for the `secret` qualifier and the boundary that refuses it; [0161](0161.md) for the
  per-core workers this tier is shared between; [0174](0174.md) for the detached balance a store's bytes
  move; [0179](0179.md) for the AEAD roster the seal comes from; [0075](0075.md) and [0073](0073.md) for
  what the shared tier already carries; [0004](0004.md) for the ordering that lets this spend memory.
- **Validated by:** the conformance cases goal `process-cache` adds in its stages 3–7, which become each
  created rule's `guardedBy` when that goal's last stage flips the four from `designed` to `shipped`.

> **In short:** `Core\Cache` gains a third member. `process()` is **one store per serving process**,
> coherent across every core of it, in memory only, gone when the process ends — O(working set) where
> `local()` is O(cores × working set), and the first mutable state the cores share. It is a **general
> tier**, not a secrets store. Separately, a secret may now outlive the request that fetched it, through
> exactly two members — `putSecret` and `getSecret`, both taking a key ring — which store
> XChaCha20-Poly1305 **ciphertext** bound to the app, the entry's name and its expiry, so no `secret`
> value ever crosses a cache boundary and `rule:security/secret-crosses-no-boundary` is untouched. On a
> miss, `getSecret`'s `fill` runs in **exactly one caller per process** while the others wait; a failure is
> never shared. `Core\Session` seals a user's own token the same way. Sealing keeps a secret from code
> that knows an entry's name but not the ring, and from a store on the far side of the network; it does
> **not** protect it from a compromised process.

## Context

### 1. Two tiers, and a hole between them

`Core\Cache` hands back two stores (`rule:core-api/two-cache-tiers`). `local()` is per-core and
in-process: no coherence between cores, any entry absent at any time, capped at
`[cache.local] max_size`, which ships at 32 MiB per core (`crates/nvs-stdlib/src/cache.rs:376-380`).
`shared()` is a real store over the network, coherent across a fleet and gated by the capability naming
the store an operator configured.

Between them there is nothing that is **one per machine**. A value a whole box could share — a parsed
remote document, a discovery response, a rendered fragment — is either held once per core, which is the
same bytes multiplied by `[server] workers` (`rule:http-server/the-accept-fan-out-is-one-worker-per-core`),
or pushed onto a network store that the box then re-fetches over a socket for something it already had in
memory.

### 2. A secret cannot be kept at all

The sharper hole is the one goal `http-client` walked into. A `secret` value is refused at the recursive
graph copy, for every caller of it alike (`rule:security/secret-crosses-no-boundary`), and the cache
boundary **is** that copy (`rule:concurrency/a-cached-value-is-copied-across-the-boundary`). So an OAuth
access token — the thing a REST client fetches once and then uses for an hour — cannot be put anywhere
that outlives the request that fetched it. Every request re-authenticates. That is a per-request round
trip to an identity provider on the latency path (priority 3), and it is a fleet of processes hammering
one endpoint at whatever rate the fleet serves.

The refusal is right and is not being reopened. What is missing is a door that lets the *ciphertext* of a
secret cross, so the boundary still sees only `bytes`.

### 3. Nowhere to put a result that exactly one core should compute

Both halves above have a third problem in common: when a value is absent, every core that wants it fetches
it. With no coordination, a cold start or an expiry is N simultaneous fetches of the same thing — the
classic stampede, and worse here than in a single-process runtime because each core is its own scheduler
with its own accept loop and they wake together.

## Investigation

What is already on disk, and therefore what this decision is allowed to assume:

- The one store class every tier answers, and the byte payload an entry is —
  `crates/nvs-stdlib/src/cache.rs:11-36` and `:147-250`. An entry is bytes plus a class name resolved on
  the way out, not a live graph, so a second tier holding the same payload resolves the same way.
- The local tier's map, cap and eviction — `cache.rs:385-420`. `get` is a lookup and never a write, which
  is what keeps it off a `&mut` on the request path (`cache.rs:93-100`).
- The crate-private seal seams in `crate::crypto` — `crates/nvs-stdlib/src/crypto.rs:103-113` — and the
  key ring every keyed member in the crate already takes, `array<secret bytes>`, newest first, with its
  own `LogicError` for a ring that cannot key anything (`crates/nvs-stdlib/src/keyring.rs:1-20`,
  `:39-50`).
- The accounting bracket a cross-request store's bytes move on
  (`rule:concurrency/a-cross-request-stores-bytes-are-its-own-balance`,
  `crates/nvs-runtime/tests/detached_accounting.rs`).
- The session record already crosses its store as a byte carrier
  (`docs/rules/http-server/a-session-store-answers-four-operations.md:15-16`), so sealed bytes need no new
  carrier there either.
- The session backend enum carries no variant for a weak tier at all, by construction
  (`crates/nvs-config/src/session.rs:28-40`), and `E0626` is the refusal an operator sees.

And one measurement, because § 1 of the *Decision* turns on it: `rule:core-api/two-cache-tiers` is cited
82 times across 49 files. Seven of those files are accepted decision records — 0024, 0059, 0073, 0075,
0118, 0142, 0175 — which are frozen and are not edited to track a later decision.

## Options considered

1. **A secrets-only process store**, separate from `Core\Cache` — `Core\Secrets` or similar. Smallest
   surface for the immediate need.
2. **A general third tier, with a sealed door on top of it** — `process()` beside `local()` and
   `shared()`, and `putSecret`/`getSecret` on the store class every tier answers. Chosen.
3. **A general third tier that holds `secret` values in the clear**, arguing that a process that already
   holds the ring may as well hold the plaintext.
4. **No new tier**: let the caller keep a token in a process-wide static of its own.

4 is closed by `rule:security/no-cross-request-state` and is the reason `Core\Cache` exists as the
sanctioned exception at all. 1 buys a smaller surface and pays for it twice: a machine-wide cache is
wanted for ordinary values too (§ 1 of *Context*), and a secrets-only store would answer that with a
second half-tier or not at all. 3 is answered in § 7 below.

## Decision

### 1. `rule:core-api/two-cache-tiers` is amended in place, and keeps its id

A third tier makes the rule's id read as a count that is now wrong. It is amended in place anyway: the id
stays `core-api/two-cache-tiers`, and the title becomes a statement about members and contracts rather
than about how many there are.

**A rule id is a path, not a claim.** It is the fragment's location on disk
(`docs/rules/core-api/two-cache-tiers.md`) and the flat token every citation carries, and the thing that
makes the token useful is that it does not move. Against that: 82 citations in 49 files, of which nine sit
in seven accepted records. A rename would either leave those nine dangling or edit frozen rationale, and
this repository does neither — a record states what was decided when it was written and is never edited to
track a later decision. The alternative that avoids both, retiring the id and creating a near-identical
one, spends a tree-wide sweep to change one word inside a path that no reader is asked to parse.

What is substantively unchanged is the rule itself: cross-request state is reached through **a member per
tier, each with its own contract, never one API with a flag**. A third member is that rule applied once
more, not a different rule, and the argument for it — one name covering two guarantees invites using the
weaker one by accident — is what makes a `Core\Cache::store(tier: …)` argument still refused today.

This is the one place in this record where an id's wording is allowed to age. `docs/ground-rules.md`,
`docs/rules/core-api.md` and the website mirror all print the **title**, which is current.

### 2. `process()` is a general tier, not a secrets store

`Core\Cache::process(): Core\Cache\Store` answers the same store class `local()` and `shared()` do, with a
third tier behind it. Its contract:

- **One map per process**, read and written by every core of it. Coherent within the process, and not
  beyond it: two processes on one machine share nothing, and neither do two machines.
- **Memory only.** It is created where `nvs serve` starts its workers, before the first one accepts, and
  under `nvs run` for the length of the run. When the process ends the tier is gone, and nothing is
  written anywhere.
- **A cache, not a store.** Every sentence
  `rule:concurrency/cross-request-state-is-explicit` says about the local tier holds here: an entry may be
  absent at any time, for the cap, for a lifetime, or because this is a different process than the one
  that wrote it. A program that would be incorrect on a miss is using the wrong tier.
- **Copied in and copied out**, by the same graph copy (`rule:concurrency/a-cached-value-is-copied-across-the-boundary`).
  An entry is the byte payload the local tier already holds, so a unit swap resolves a class by name there
  exactly as it does here.

Being general is the point of the shape. The secrets half below is two members *on the store class*, so it
is available on all three tiers and is not what the third tier is for.

### 3. The map is sharded 64 ways, fixed

This is the first mutable state the cores share, so the map is sharded behind read/write locks, and the
shard count is a **fixed 64**, not derived from `[server] workers` or from the machine's parallelism.

`get` takes a shard's read lock and never a write, for the reason the local tier's `get` takes no `&mut`:
a read that reordered anything would put a second live borrow on the request path. Eviction is therefore
by write age, as it already is in the local tier, and not by use.

Fixed rather than derived, for three reasons. The map is created **before** the workers exist under
`nvs serve` and there is exactly one worker under `nvs run`, so a derived count would either be computed
from a directive the map does not otherwise read or would size the CLI's map at one shard. A constant is a
mask over the one hash the key already needs — the top bits pick the shard, the rest index inside it — so
sharding costs no second hash. And 64 empty shards are 64 locks and 64 empty maps, allocated once per
process: below the granularity at which footprint is worth a directive, which is why there is no
`[cache.process] shards` key.

64 rather than 8 or 16 because contention here is write-side only and the number cannot be raised later
without changing which shard a key lands in — which costs nothing for a cache, but a machine with more
cores than shards would be paying for a choice nobody can see. 64 covers the core counts a serving box
plausibly has, in both directions.

### 4. Keys are scoped per `[[app]]` and per configuration generation

An entry's real key is the written key under the app and the generation of the configuration that was live
when it was written, the way `rule:security/db-pool-reset-is-a-boundary` scopes a pool. Two apps on one
server never read each other's entries, and a reload never serves an entry written under the configuration
it replaced — the same reasoning that makes an edit reach the next request without a restart makes a
carried-over entry a stale answer from a program that no longer exists.

### 5. No grant, and what is bounded is footprint

The tier needs no capability, for the reason the local tier needs none: a capability is checked at the door
to an *effect*, and this tier has no door — nothing leaves the process, no name is resolved, no socket is
opened. What is left to bound is memory, and the instrument for that is a size cap, not a boolean.

Every byte the tier holds is on the detached balance, under `nvs_runtime::budget::Detached`, **held by the
store** around every path that allocates or frees what it holds — never by a call site that happens to be
storing (`rule:concurrency/a-cross-request-stores-bytes-are-its-own-balance`). The store copies what it is
handed for exactly that reason: the allocation and the free must be on one balance.

A session backend still cannot name it. `E0626` refuses the local tier as a backend today; it widens to
refuse the process tier in the same sentence, because coherent within one process is not coherent across a
fleet and `load` on the *other* process is the question this tier gets wrong.

### 6. A lifetime and a `forget`, on every tier at once

`put(string $key, mixed $value, {ttl?: Duration})` and `forget(string $key): void`, on the store class, so
all three tiers gain them together. An entry past its `ttl` is absent: the local and process tiers check on
`get` and drop what they find expired, the shared tier writes `PX` and `DEL`. An omitted `ttl` is today's
behaviour — the entry lives until it is overwritten, forgotten or evicted. Adding `ttl` to the trailing
options shape is an addition to the row rather than a change to it (`rule:core-api/shape-rules` R2).

An expiry checked on `get` and not swept is deliberate: a sweep is a timer and a write pass over a shard,
and what it would buy — memory returned slightly sooner — is bought instead by the cap, which is already
enforced and already evicts.

### 7. A secret meets a cache only through `putSecret` and `getSecret`, and only sealed

Two members on the store class, and they are the only two:

- `putSecret(string $key, secret string $value, Duration $ttl, array<secret bytes> $keys): void` — `ttl` is
  **required**, because a secret never outlives a lifetime someone stated.
- `getSecret(string $key, array<secret bytes> $keys, {fill?, wait?}): ?secret string`.

**What is stored is ciphertext.** The plaintext is the expiry and the value; the ring's newest key seals it
through `crate::crypto`'s `seal_under`, and the additional data is a domain byte of the cache's own ‖ the
app ‖ the entry's name. So a ciphertext moved to another key, another app or another entry name does not
open, and one written back under a longer store lifetime is still past its own sealed expiry. The sealed
bytes enter the tier by its ordinary path, as `bytes`.

**No `secret` crosses the boundary**, so `rule:security/secret-crosses-no-boundary` is unchanged and a
sealed entry is as safe on the shared tier as on the process one. `put` still refuses a `secret` value and
`get` still answers `null` for a sealed entry: the sealed door is the only door, and a program cannot reach
one half of the pair by accident from the other.

Option 3 of *Options considered* — plaintext in the process tier — is refused here. It is not that a
process holding the ring is meaningfully safer than one holding the token; it is that a plaintext tier
would have to be a *different* tier from the one an ordinary value uses, or the boundary refusal would have
to be conditional on which tier was asked for. Both are a second contract, and the sealed door needs
neither: one boundary rule, one payload type, and the tier does not know what it is holding.

### 8. What sealing buys, stated exactly

It keeps a secret from being read by code that knows an entry's name but not the ring. It lets a secret
reach the **shared** tier without leaving the process in the clear — over a socket, into a store an
operator runs, onto that store's disk if it persists. And it makes a tampered, moved or replayed entry a
**miss**.

**It does not protect a secret from a compromised process, or from a memory dump.** The ring lives in the
same memory as the plaintext, and code inside the process that has the ring can open anything sealed under
it. This record says so, and `putSecret`'s reference card says so, so that "encrypted" is not read as more
than it is.

The cost is one XChaCha20-Poly1305 seal per `putSecret`, and one open per ring key tried per `getSecret`,
on top of the tier's own copy. A ring with the newest key first makes the common case one open.

### 9. A sealed entry that does not open is a miss

Under every key of the ring, or past its sealed expiry, `getSecret` answers as it does for an absent
entry — `fill` runs if it was given, `null` if it was not. Never an error. A rotated ring therefore
re-fetches rather than failing, which is what makes rotation a deployment operation rather than an outage.
A ring that is wrong *in itself* — empty, or a key of the wrong length — is still `crate::keyring`'s
`LogicError`, because that is a bug in the program and not a fact about the entry.

### 10. `fill` runs once per process, and a failure is not shared

`fill: callable(): Core\Cache\SecretEntry`, where `SecretEntry::of(secret string $value, Duration $ttl)`
carries what the fetch learned, a token endpoint being the authority on its own lifetime. On a miss,
**exactly one caller in the process runs `fill`**, in its own request and under its own capabilities; every
other caller on every core waits for that one, each for at most its `wait`, and past it throws
`TimeoutError`.

- **A failure is not shared.** When `fill` throws, the waiters are released with nothing and the next
  caller runs `fill` itself. An exception crossing from one request into another is exactly the
  cross-request state `rule:security/no-cross-request-state` closes, and an error cached for other requests
  would turn one bad minute at a provider into a failure every later request inherits.
- **A `fill` that asks for its own key** is a `LogicError` rather than a wait on itself.
- **A request that ends while holding the fill releases it**, so a cancelled fetch never wedges a key.
- **Once per process, not once per fleet.** On the shared tier the other processes each run their own
  `fill`. A fleet-wide single fill is a lease over that store, with an owner, a renewal and a recovery
  path, and it is not this decision.

This is the one step in `Core\Cache` that observes an entry and writes it, so
`rule:concurrency/put-and-get-are-the-whole-boundary` is amended for `getSecret`'s `fill` **alone**. It
does not become a coordination primitive: a program cannot take the fill, cannot see who holds it, and
cannot make one entry's fill wait on another's. There is still no set-if-absent, no compare-and-set and no
counter, and the mechanisms that need those still have their own homes.

### 11. Refresh-ahead is the last fifth of the lifetime

An entry inside the **last fifth** of the lifetime it was stored with is still answered to every caller,
while exactly one of them runs `fill` to replace it. So the expiry of a hot key costs nobody a wait, and
the window is proportional rather than absolute because the tier does not know what a lifetime means to its
caller.

A fifth, rather than a tenth or a half: a tenth of a short lifetime is a window a slow fetch does not fit
inside, which puts the callers back into § 10's wait for the case refresh-ahead exists to remove. A half
doubles the fetch rate against the provider for values that are still perfectly good. A fifth leaves four
fifths of every lifetime untouched and gives a fetch room to fail once and be retried by the next caller
before anybody waits.

Refresh-ahead applies to `getSecret` with a `fill` and to nothing else. A plain `get` has no fill, and an
expired entry there is simply absent.

### 12. A user's own secret lives in the session, sealed the same way

`$session->setSecret(string $key, secret string $value, array<secret bytes> $keys): void` and
`$session->getSecret(string $key, array<secret bytes> $keys): ?secret string`, over § 7's construction with
the session door's **own domain byte**, so a value sealed for the cache never opens as a session value.
This is where a web application keeps the access and refresh token of the user it is acting for — not in a
cache tier, which may evict at any time and would log that user out.

- **No `ttl`.** A session value lives as long as its session
  (`rule:http-server/session-expiry-belongs-to-the-store`), and the sealed plaintext carries no expiry.
- **The additional data is the domain byte ‖ the app ‖ the key, and not the session id**, because
  `regenerate` issues a new id over the same record and a value bound to the old id would stop opening at
  exactly the moment a login hardens. Moving a ciphertext between two sessions takes write access to the
  store, which already means owning every session in it.
- **`get` answers `null` for a sealed value and `set` still refuses a secret**, as the cache's pair does,
  and a sealed value that does not open under the ring is absent rather than an error.
- The record crosses the store as the byte carrier it already does, so no `secret` reaches the store here
  either.

### 13. The registry gains `secret string`

The signature registry spells `secret bytes`, `secret tainted string` and their parameter forms
(`crates/nvs-stdlib/src/registry.rs:312-377`) and no plain `secret string`, which all four members above
need: as a return it is a promise, as a parameter it demands what assignment already grants. It is a
spelling the type system has, not a new type.

### 14. The directives, and the numbers they ship

A new `[cache.process]` block with two keys, both `System`-class and `Reload`-apply, like
`[cache.local] max_size` (`crates/nvs-config/src/directive.rs:169-173`). Both are facts about the process
rather than about a request: the memory a shared map holds is spent by every request on the box, and the
time one core's request may block on another's fetch is not a bargain a single request gets to strike for
everyone. A caller who wants a different wait writes `wait` at the call site, which is where that decision
is visible in review.

- **`max_size` ships at `32M`** — the same figure `[cache.local] max_size` ships. One number to remember,
  and the same number means **less** memory here, not more: this tier is held once per process where the
  local tier is held once per core, so a working set moved from `local()` to `process()` at stock
  configuration lowers the machine's ceiling from `32M × workers` to `32M`. Exceeding it evicts the key
  written longest ago and never fails a `put`, which is § 2's "absent at any time" reached from the cap.
  `false` is no ceiling at all, as it is for the local tier.
- **`fill_wait` ships at `5s`**, and it is the default for `getSecret`'s `wait`. It is deliberately much
  shorter than `[http.client] deadline`'s shipped `30s` (`crates/nvs-stdlib/src/http.rs:1235`): the filler
  may spend its whole deadline, but a waiter is a request held on the latency path, and a slow provider
  that blocked every in-flight request on the box for half a minute is the outage the tier was supposed to
  prevent. Five seconds is generous for a token endpoint and short enough that what a caller gets instead
  is a `TimeoutError` it can answer. The consequence is real and stated: a `fill` slower than five seconds
  succeeds for the filler while its waiters throw, and the callers after it find the entry. An operator
  whose provider is slower raises the key.
- **`0` is refused** for `fill_wait`, under **`E0642`**. A zero wait makes every concurrent caller but one
  throw, which is the stampede's failure mode with the fetches removed and nothing gained; and there is no
  spelling for an unbounded one, per `rule:http-server/no-spelling-for-an-unbounded-wait`.

There is no `[cache.process] shards` key (§ 3) and no capability key (§ 5).

### 15. What it spends

Per `rule:programs/memory-priority`, in the form it requires:

- The tier holds at most `[cache.process] max_size` bytes, **once per process** — O(working set), where
  the local tier is O(cores × working set) — on the detached balance, never O(requests served).
- 64 shards: 64 locks and 64 map headers per process, at process start.
- The fill table holds one slot per key being filled **at that moment**, so O(concurrent fills), not
  O(keys) and not O(requests).
- A sealed entry costs its ciphertext: the value, a nonce, a tag, and eight octets of expiry.
- On the latency path: one seal per `putSecret`, one open per ring key tried per `getSecret`, one read lock
  per `get`, and the copy every tier already charges.

## Diagnostics

Almost nothing here is a new code, which is the intended outcome of building on doors that already exist.

- **`E0626`** widens: it refuses the local tier as a session backend today and refuses the process tier in
  the same sentence, naming the file the key was written in.
- **`E0642`** is new: `[cache.process] fill_wait` is zero (§ 14).
- A `secret` value passed to `put`, or reaching any tier other than through § 7's pair, is the existing
  boundary refusal and gains no code of its own.
- `TimeoutError` past `wait`, and `LogicError` for a re-entrant `fill` or for a ring that cannot key
  anything, are run-time throws with no compile-time code, because none of the three is decidable from the
  source.

## Consequences

A REST client can hold an application's own access token across requests, which is what goals
`http-client` and `outbound-proxy` were split apart to make possible, and a web application can hold a
user's token in their session across requests. Neither costs a `secret` value crossing a boundary.

The cores now share mutable state. That is a real change to what a worker is: until now every worker held
its own everything but the compiled program text
(`rule:http-server/the-accept-fan-out-is-one-worker-per-core`, `rule:security/isolate-shares-nothing`),
and the amended rule says so. What keeps it from being a coherence surface a program can build on is § 2's
contract — an entry may be absent at any time — and § 10's refusal to expose the fill.

A program that puts a secret in a cache without a ring gets a compile error rather than a plaintext token
in Redis, which is the whole return on making the door narrow.

The refresh-ahead and single-flight behaviour means the number of fetches a fleet makes against a provider
is bounded by its **process** count rather than its request rate, which is the practical difference between
an integration that works at scale and one that gets rate-limited. It is not bounded by one, and a
deployment that needs that needs the lease this record does not decide.

Every tier grows two members and an option key, which is surface on a class whose whole appeal is that it
has almost none. The pair is justified by being the only door; `ttl` and `forget` are the two things
`cache.rs`'s own module doc already recorded as owed.

## Alternatives rejected

- **A `Core\Secrets` class.** A secrets-only store leaves § 1 of *Context* unanswered, and a machine-wide
  cache for ordinary values would then arrive later as a fourth thing. Two shapes for one mechanism.
- **`store(tier: Cache\Tier)`.** A flag argument, refused for the same reason it was refused at two tiers:
  the choice stops being visible in review at the moment a variable can carry it.
- **Deriving the shard count from `[server] workers`.** § 3.
- **A sweeper thread for expiries.** § 6.
- **Renaming the rule id.** § 1.
- **Caching a `fill` failure**, so that a provider outage is not re-attempted by every caller. It puts one
  request's exception into another's path, and the cure for a hammered provider is the caller's own retry
  policy, which is already jittered and bounded.
- **A fleet-wide single fill.** Out of scope, and it is a lease, not a cache entry: it needs an owner, a
  renewal, a recovery from an owner that died mid-fetch, and a story for a network partition. None of that
  belongs behind a `fill` key.

## Revisiting

Three triggers, each with a shape a later record would take:

1. **A deployment that needs one fetch per fleet, not per process.** That is the lease named above, over
   the shared tier, and it is a new record rather than an amendment to this one.
2. **Shard contention measured under a real load** — if the fixed 64 of § 3 turns out to be the wrong
   constant on a large box, the number moves, the id does not, and nothing in the contract changes because
   sharding is invisible to a program.
3. **A `secret bytes` value.** § 7 is written over `secret string`; a binary secret is the same
   construction with a different spelling, and the reason it waits is that nothing needs it yet.

## Verification

- A value put on the process tier by a request on one core is read by a request on another, and is gone in
  a second process started beside the first.
- Two apps writing the same key read their own entries; a reload does not serve an entry written under the
  previous configuration (§ 4).
- The tier's bytes appear on the detached balance and move no request's reading, by the same test
  `crates/nvs-runtime/tests/detached_accounting.rs` holds the existing stores to.
- A `[cache.process] max_size` reached evicts the key written longest ago; no `put` throws.
- Naming the process tier as a session backend fails at boot under `E0626`, naming the file;
  `[cache.process] fill_wait = 0` fails under `E0642`.
- `put` of a `secret` is still a compile error; a sealed entry read back through `get` answers `null`; the
  bytes in the tier under a sealed entry are not the plaintext.
- A ciphertext moved to another entry name, another app, or opened under a ring that does not contain its
  key, is a miss and not an error — and with a `fill` given, a miss that re-fetches.
- An entry past its sealed expiry is a miss even when the tier's own lifetime would have kept it.
- Concurrent `getSecret` calls on every core for one absent key run `fill` exactly once; a throwing `fill`
  releases the waiters with nothing and the next caller runs it again; a caller whose `wait` elapses throws
  `TimeoutError` while the fill is still in flight.
- An entry inside the last fifth of its lifetime is answered to every caller while exactly one fill runs
  (§ 11).
- A session value set through `setSecret` survives `regenerate`, and does not open through the cache's
  `getSecret` under the same ring (§ 12).
