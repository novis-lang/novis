# ADR 0198 — A file a program autoloads is analysed through that program's `autoload` map

- **Scope:** which `autoload` declarations the language server resolves an open document's names
  through, how it finds them, and what an edit to a declaring file re-analyses. The map's own rules are
  [0061](0061.md)'s and unchanged, and so is everything `nvs check` does.
- **Depends on:** [0099](0099.md), [0061](0061.md).
- **Validated by:** `crates/nvs-lsp/tests/autoload.rs`,
  `a_borrowed_declaration_yields_to_the_programs_own_and_is_silent` in `crates/nvs-hir/src/requires.rs`,
  and the run under *Verification*.

> **In short:** the server analyses the open document as its own entry point, and a class file a program
> autoloads may not declare `autoload`, so every autoloaded name in it was reported unresolved in a
> program that builds clean. The server now surveys the workspace for programs that declare `autoload`
> and lends such a file the map of the first program whose roots it lies under. The file's own
> declarations come first and a borrowed one never reports anything.

## Context

A developer opened a class file of an application whose entry point declares
`autoload 'Framework' from '../../Framework/src';` and `autoload 'Blog' from '../src';`. The editor put
`E0306` on every `use Framework\…;` in it. The program was correct: `nvs check` on the entry point is clean, and on the
class file it reports the same `E0306`, because a walk that starts there meets no declaration.
[0099](0099.md) made the open document the unit of analysis and [0061](0061.md) made an `autoload` inside
an autoloaded file an error, and no file of a framework application other than its entry point can
satisfy both.

## Options considered

1. **Lend the file the map of the program that autoloads it, found by a survey.** Chosen.
2. **A setting naming the entry point.** Exact, and it makes a false error the default until somebody
   finds the setting; a workspace holding several applications needs a list of them.
3. **Analyse the program's entry point and publish for the open file out of that walk.** The closest to
   the build, and it changes what an analysis *is*: the cursor tables, the trivia and the syntax index
   are the entry document's, and a class the entry point never names would not be reached at all.
4. **Hold `E0306` back for a file with no map.** It hides the squiggle and leaves hover, completion and
   go-to-definition without the type, and it hides a real misspelt import with it.

## Decision

### 1. A survey finds the lenders

Before the first analysis the server walks the tree `nvs.check.scope` selects. A file whose text holds
the keyword is resolved as a program — name resolution without the type phase — and one whose `require`
chain declares anything is kept as a lender: its entry path, the files that wrote a declaration, and the
resolved map. After that, each document change re-walks the changed file and the lenders it wrote a
declaration for, and nothing else.

### 2. A file borrows from the first lender it lies under

A file lies under a lender when its path is under a root one of the lender's own declarations names. The
first such lender in entry-path order lends, and a lender never lends to its own entry point. A union of
every matching lender was rejected: two programs over one source tree may give one prefix different
roots, and a union is a map neither of them runs with.

### 3. Own declarations first, and a borrowed one is silent

`AutoloadMap::build_borrowing` takes the walk's own sites before the borrowed ones in both of its passes,
so a prefix both declare is the walk's own and no diagnostic names a borrowed site as the earlier of two.
A borrowed site reports nothing, a malformed glob included: its span is a position in a file the walk
never read, and the lender's own analysis reports it where it was written.

### 4. The declaring files are dependencies

`Analysed::files` names the lender's declaring files after the graph the walk read. The republish list
and the symbol index's invalidation both follow that set, so an edit to a declaring file re-analyses
every open document that borrowed from it.

### 5. `nvs check` does not borrow

It is handed the file a program starts from. `resolve_program_borrowing` is a separate entry point, and
the language server is its only caller.

## Consequences

- **Performance:** at startup, one read of each file under the root and one name-resolution walk per file
  that holds the keyword, which reads the program that file starts. Per edit, one search of the changed
  text; an edit to a declaring file repeats that lender's walk. Per analysis, one `canonicalize` and a
  prefix test per lender. Nothing is on a request path of the runtime.
- **Memory:** one resolved map and two short path lists per lender, held for the session. It grows with
  the number of programs in the workspace, not with edits.
- **Usability:** a class file of a framework application is analysed as the build sees it, with nothing
  to configure. Under `nvs.check.scope = open` the map is lent only once the declaring file is open. In a
  workspace with two programs over one tree, the first in path order decides, and nothing says which.
- **Simplicity:** the graph walk gains one input and the map one constructor. The rule that an open
  document is its own entry point now has one named exception.

## Alternatives rejected

- **Rejecting the entry's own `autoload` when it borrows**, as the build does for an autoloaded file. A
  bootstrap file reached by `require` may sit under a root too, and it would be given an error the build
  does not give it.
- **Keying a lender's staleness on every file its walk read.** That set is the whole application, so
  every keystroke anywhere would repeat the walk; only the files that wrote a declaration can change the
  map.
- **Surveying by parsing every file.** The keyword search refuses almost every file for the cost of the
  read the index is about to make anyway.

## Verification

The suite pins the unresolved import with no survey, its absence after one with the framework outside
the workspace root, the entry point analysed unchanged, `open` scope lending only from open documents,
an edit to the declaring buffer reaching the borrower, and path order between two lenders. Over stdio
against `nvs lsp`, with the workspace root at the application and the class file opened: a binary built
before this change published `E0306` and `E0303` for it, and one built after published nothing.

One case is not covered: a document analysed before any lender claimed it is not republished when a
declaration is first written elsewhere, because it borrowed from nothing and so depends on nothing. Its
next edit, or reopening it, analyses it through the new map.
