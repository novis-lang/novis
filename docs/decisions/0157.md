# ADR 0157 — a shape field's key may be optional, `tainted` qualifies a whole shape, and an absent optional field is the throw an absent array key already is

- **Scope:** the two things a shape type could not say — `{name?: T}`, and `tainted {…}` over a shape whose
  text-carrying fields all arrived from outside — and what a read of an optional field answers. The
  converter that hydrates a shape from `array<mixed>` and the two request members that wrap it are their
  own slices; this record is the type surface they are written against.
- **Depends on:** [0036](0036.md) — the shape type and the erased-member access it shares its throw with;
  [0024](0024.md) § 1 — the qualifier's grammar and its "structured input stays `array<mixed>`" boundary;
  [0071](0071.md) — required, optional and nullable as three separate questions.
- **Validated by:** `crates/nvs-types/tests/objects_and_shapes.rs`, `crates/nvs-types/tests/tainted.rs`.

> **In short:** a shape field carries a required bit, `{name?: T}` clears it, and `{a?: int}` and
> `{a: ?int}` stay different types that accept different values. A read of an optional field is **not**
> widened to `?T`: it answers the declared `T`, and an absent key is `rule:types/erased-member-access`'s
> checked, catchable throw — the same answer an absent array key already gives, with `??` and `isset` as
> the guarded spellings that ask without throwing. Widening the read would fuse optionality into
> nullability, which `rule:core-api/required-optional-and-nullable` keeps apart, and would leave the
> language two different answers to one question. `tainted {…}` widens the qualifier's grammar from the
> two scalars to a shape and is a parse-time desugaring — each text-carrying field, transitively, is
> rewritten to its tainted variant — so it needs no `Ty` variant, no qualifier axis and no run-time
> representation. A shape carrying no text anywhere is a diagnostic rather than a no-op. `tainted mixed`
> stays out of the grammar: a qualifier over an erased container promises what the checker cannot
> deliver, and goal `request-json`'s prose spelling is corrected to the plain `mixed` the registry already declares.

## Context

A shape type (`rule:types/shape-type`) could say that a key is present and what type it holds. Request
input needs the third thing: a key that may not be there at all. Without it, every optional field of a
JSON body has to be declared `?T` and the two facts — *the client may omit this* and *the client may send
`null` here* — collapse into one, which is the ambiguity `rule:errors/ambiguous-input-refused` refuses
everywhere else.

`tainted` has the mirror gap. `rule:security/tainted-qualifier`'s grammar is `'tainted'? scalar_type`, so
the qualifier can be written on a `string` and on a `bytes` and nowhere else. A shape hydrated from a
request body is a value every text-carrying field of which is untrusted, and spelling that today means
writing `tainted` on each field by hand — which is not wrong, only long enough that a program stops doing
it, and `rule:security/tainted-sources` is only worth as much as the declarations that carry it forward.

## Investigation

The required bit was already in the tree one struct away. `CoreShapeField::required`
(`crates/nvs-types/src/ty.rs:359`) is the same bit for a `Core` options bag under
`rule:core-api/shape-parameter`, so the user-facing half is one representation reaching a second spelling
rather than a second representation.

The read is the question the bit does not answer by itself. `crates/nvs-types/src/expr/members.rs:1183`
types `$p->a` off the shape's field list and records an `ExprInfo::ShapeProperty`; the fetch is name-keyed
and `nvs_runtime::ClassDesc::field_slot`'s by-name search already throws a catchable error for a name the
concrete object does not carry. So an optional field that the value omits *already* behaves as an erased
name does, and the only open question was whether the checker should say more than that.

The precedent that settles it is one storage kind along. An absent array key is a catchable throw on a
plain read (`php-migration/every-divergence-is-deliberate-and-listed` row 11), and `??` and `isset`
answer it without throwing because every `Index` level of their operand is marked in
`Env::coalesce_guarded` (`crates/nvs-types/src/expr/presence.rs`'s module doc is that mechanism). "The key
may be absent" therefore already has an answer in this language, and it is not a nullable type.

## Options considered

1. **The read answers `?T`.** The absence lands in the type, `as ?T` and the nullable-condition lint pick
   it up, and nothing throws. It is what TypeScript does.
2. **The read answers `T` and an absent key throws** — `rule:types/erased-member-access`'s existing
   mechanism, with `??`/`isset` extended one level to guard it.
3. **The read is refused** and only a guarded spelling reaches an optional field.

## Decision

### 1. `{name?: T}` marks the key optional, and it is not nullability

A shape field carries `required`. A written `?` before the `:` clears it. `{a?: int}` accepts a value with
no `a`; `{a: ?int}` demands an `a` that may hold `null`; the two intern apart because they accept
different values, and `{a?: ?int}` says both. Assignability is the one-line consequence: a source missing
an optional field satisfies the shape, missing a required one does not, and a source with extra fields
still satisfies — width subtyping unchanged.

### 2. A read of an optional field answers `T`, and an absent key is a checked throw

Option 2. The shape proves the field's *type* and no longer proves its *presence*, so the access is
`rule:types/erased-member-access`'s checked, catchable throw — narrowed only in that the result type is
the field's declared `T` rather than `mixed`, because that half is still proven. `??` and `isset` are the
spellings that ask without throwing, and a shape-property level of their operand is marked guarded exactly
as an `Index` level is.

Option 1 is rejected on `rule:core-api/required-optional-and-nullable`: required, optional and nullable
are three separate questions, and a read that answers `?T` merges two of them at exactly the site a
program acts on the difference. It also leaves the language two answers for one question — an absent array
key throws, an absent field would be `null` — and the cost of that is paid by every reader who has to
remember which container they are in. Option 3 is rejected because a refusal has to name a replacement
spelling, and the replacement is `$p->a ?? d`, which option 2 already admits.

### 3. `tainted {…}` distributes over the shape, at parse time

The grammar widens from `'tainted'? scalar_type` to admit a shape type. `tainted {a: string, b: {c:
bytes}}` is rewritten, while parsing, to the shape whose text-carrying fields are their tainted variants,
transitively — through a nested shape, through a nullable, through a union member and through an
`array<string>` element. Taint is spelled as type atoms (`TypeAtom::TaintedString` and its three
siblings), so this needs no new `Ty` variant, no qualifier axis and nothing at run time: it is gone before
the checker sees it, and the field-by-field spelling it replaces is what it produces.

A shape with no text-carrying field anywhere is `E0132`, not a no-op. A qualifier that promises nothing
still reads as a promise, and the program that wrote it believes something the checker will not enforce.

### 4. `tainted mixed` is not admitted, and goal `request-json`'s spelling is the thing corrected

`mixed` is erased: the checker cannot distribute a qualifier through it, and every way of getting a value
back out is a conversion the qualifier rules would then have to special-case. 0024 § 1 already drew this
boundary — structured input stays `array<mixed>`, and the qualifier is about the scalar payload once it is
pulled out — so the grammar admitting two scalars and now a shape is that decision holding, not an
oversight. `Core\Request::json` declares `mixed` in the registry
(`crates/nvs-stdlib/src/request.rs:2269`) and keeps it; the `tainted mixed` in goal `request-json`'s prose was a
spelling the grammar never admitted, and it is corrected there rather than legalised here.

What recovers the taint is the shape, not the container: a body reaching `jsonAs<T>` or `postAs<T>` with
`T` written as `tainted {…}` arrives with every text field qualified, which is the same fact stated where
the program actually names its fields.

## Diagnostics

- **`E0132`** — `tainted` over a shape that carries no `string` or `bytes` anywhere, naming the shape and
  helping toward removing the qualifier.
- **`E0109`** (`E_TAINTED_NON_SCALAR`) keeps every other rejection, its message widened to name the shape
  as a third thing `tainted` may qualify. `tainted mixed`, `tainted int` and `tainted array<string>` are
  all still it.
- Nothing new is reported for an optional read. It is `rule:types/erased-member-access`'s throw, and that
  rule's own diagnostics are unchanged.

## Consequences

- **Cost.** One `bool` per shape field, in an interned descriptor — O(distinct types in the program),
  nothing per value and nothing per request. `tainted {…}` costs zero: it is erased before codegen with
  the rest of the qualifier, exactly as `rule:security/tainted-qualifier` already promises.
- **`??` and `isset` grow one guarded level.** A shape-property operand joins the `Index` level in
  `Env::coalesce_guarded`. Until that lands, an optional field is readable only where the value provably
  carries it, and `$p->a ?? d` throws instead of answering the default — the one place where this
  record's rule is ahead of its tree.
- **The known gap this does not close.** A program that reads a request body as `mixed` and pulls a
  `string` out of it holds an unqualified string, because the container was never qualified. That is
  0024 § 1's boundary, and this goal's answer to it is the converter — not a wider qualifier.

## Alternatives rejected

- **A shaped `array<T>`, key by key.** Rejected in this goal's standing decisions before it began:
  `array<T>` is homogeneous and invariant with one interned descriptor per header, so a per-key-typed
  array is a second array family with its own variance and `Core\Arr` story. Converting at the boundary is
  the safer half of the trade anyway.
- **An `exact` option that refuses extra fields.** A client adding a field must not break a server, and a
  flag choosing between two behaviours is what `rule:core-api/shape-rules` R4 refuses.
- **Auto-tainting a hydrated shape** instead of writing `tainted {…}`. The declaration would then
  understate the value, which is the objection that killed every other implicit-qualifier proposal:
  a type that is not what it says is worse than a long one.

## Revisiting

If a measured corpus shows programs writing `$p->a ?? d` on nearly every optional field, the lint that
warns on a bare read — not a widened type — is the cheaper answer, and it can be added without moving
anything decided here.

## Verification

`crates/nvs-types/tests/objects_and_shapes.rs` holds the optional-field half: the two spellings interning
apart, and assignability admitting an absent optional key while refusing an absent required one.
`crates/nvs-types/tests/tainted.rs` holds the qualifier half: `tainted {…}` producing the field-by-field
tainted shape, and a text-free shape reporting `E0132`.
