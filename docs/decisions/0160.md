# ADR 0160 — a capture typed at a class built from text converts where the match crosses into the program, and a segment that class refuses is a `400`

- **Scope:** where a route capture declared at a class implementing `Parses` runs that class's `parse`,
  and what a segment it refuses becomes. Not the `#[Query]` half of
  `rule:routing/a-bad-query-value-is-a-400`, which still binds nothing; not the command-argument half,
  which `nvs_runtime::commands::ArgConv::Parses` already settled.
- **Depends on:** [0077](0077.md) and [0102](0102.md) for the capture's type list and the `404`,
  [0024](0024.md) for what a converted capture carries, [0066](0066.md) for the `parse`/`tryParse` pair
  the interface encodes.
- **Validated by:** `tests/conformance/core/a-matched-routes-name-is-the-units-own-and-its-captures-are-the-peers.nvst`
  and `crates/nvs-stdlib/src/router.rs`'s `capture_value`.

> **In short:** the router narrows a path on the conversions it reads natively — `int`, `uint`,
> `decimal`, `Core\Uuid` and a closed set — and a segment one of those refuses is not a match, so the
> walk carries on and a miss is a `404`. A capture declared at any *other* class implementing `Parses`
> cannot join that list: matching runs at the door with no program installed, so calling a compiled
> `parse` there would put an implementor's body — one that can loop, allocate and throw — over every
> request URL, including the ones that match no route, ahead of everything that rate-limits it. Such a
> capture therefore matches on **shape**, and the class's own `parse` runs at the binding site, where
> the match crosses into the program. A segment the class refuses throws there, over a route that did
> match, which a handler answers `400` — the same failure a bad query value has and for the same
> reason.

## Context

`rule:security/route-capture-is-laundered-by-its-type` says the parameter's declared type is what the
segment converts to during matching, and that a failed conversion is not a match. That held for as long
as every admitted type was one the matcher could read itself. Goal `parses` turned the type roster into a
predicate — a capture may stand at any class implementing `Parses` — which admits an open set of
classes whose conversion is *program code*.

Two facts about where matching happens close the question. `nvs_server::route` takes the match before
the unit is installed on a context, and `nvs-cli`'s runner matches before `unit.install_in(ctx)`, so
there is no class table to resolve a label in at that point. Arming one earlier is the smaller half of
the objection. The larger half is that an implementor's `parse` would then be application-authored code
over the request path running before anything rate-limits it — which is precisely the priority-1
objection `rule:routing/a-capture-narrows-to-a-closed-set` already makes to a regex constraint, and a
`parse` body is strictly more than a regex.

## Decision

### 1. The router keeps narrowing on what it reads natively, and nothing else

`int`, `uint`, `decimal`, `Core\Uuid` and a closed set are unchanged: a segment one of them refuses is
no match, the walk continues, and a miss is a `404`. `Core\Uuid` stays a name the matcher knows rather
than an implementor of the interface, because it answers what the *engine* converts and not which types
a capture admits.

### 2. Every other `Parses` class matches on shape and converts at the binding site

`nvs_runtime::routes::CaptureConv::Parses` carries the class's own name beside the segment, and
`nvs_runtime::routes::Param::Parses` carries both across the crossing — the class name rides on the
capture because a `Match` hands over the name and the captures and never the row. `nvs_stdlib::router`'s
`capture_value` decodes the segment once, as it already does for a `string` capture, and calls
`<class>::parse` with the result. That is the binding site: it is inside the program, after the door,
behind the access decision and `Core\RateLimit`, which are both the program's own.

### 3. A segment the class refuses throws where the match is read, and that is a `400`

The throw is the class's own and travels unchanged, so what a program catches is the sentence the
implementor wrote. It is not a failed match: the route matched, the input is bad, and that is what
`400` means — the same reading `rule:routing/a-bad-query-value-is-a-400` already gives a query value,
reached from the other side. The engine does not send the status, because
`rule:routing/matching-is-not-dispatching` leaves dispatch to the program; the handler answers it,
exactly as it already does for a `[a-z0-9-]+` slug it sends through a `Core\Validate` check.

### 4. `Core\Router\Match::params` gains the interface as a union member

The captures cross as `array<tainted string|int|uint|decimal|Core\Uuid|Parses>`. The last member is an
interface rather than a class because the set of classes it means is open, which is a first for a
`CoreTy::Instance` and is admitted by the same kind of written roster `Core`'s exception tree already
needs there.

## Consequences

**Two captures spelled the same way fail two ways**, and the line between them is who runs at the door:
a `Core\Uuid` capture that will not convert falls through to the next route and ends as a `404`, while a
user class's capture that will not parse is a `400`. That is one sentence to document and it is the line
the rulebook already draws.

**What it spends**, per `rule:programs/memory-priority`: one `call_static` into the program per such
capture, on the matched route and nowhere else. The walk itself is unchanged, a request that matches
nothing pays nothing, and the row holds one extra `String` — the class's name — per class-typed capture.
`Core\Request::route()` now takes its match off the carrier by clone rather than by borrow, which is one
`Arc` bump on the row plus one `String` per capture, because the crossing needs the context the carrier
is read through.

**A refusal is a throw, so a program that reads the match without a `catch` fails the request** rather
than seeing a `null` capture. That is the same shape `Core\Uuid::parse` already has and the reason
`rule:expressions/try-parse` exists: a handler that wants the non-throwing answer asks the class.

## Alternatives rejected

**Arming a class table at the door.** It would let the matcher call `parse` and keep one failure mode
for every capture. It also puts an unbounded, application-authored body on the unauthenticated request
path, which priority 1 does not trade — and the same argument already refused a regex constraint, which
is strictly less code than a `parse`.

**Carrying the segment through as text and leaving the program to parse it.** That is the tree as it
stood, and it makes the declared type of the parameter a lie: a `Slug $slug` capture would arrive as a
`tainted string`, and every handler would repeat the conversion the declaration already named.

**Answering `null` for a refused segment instead of throwing.** It would need `tryParse` rather than
`parse` at the binding site and would hand every handler a nullable it did not declare, moving the
failure to wherever the program first dereferenced it.

## Verification

`crates/nvs-stdlib/src/router.rs`'s `capture_value` and `parsed` are the binding site;
`tests/conformance/core/a-matched-routes-name-is-the-units-own-and-its-captures-are-the-peers.nvst`
pins the union a capture crosses as.
