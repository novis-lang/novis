# ADR 0219 — a saved configuration is applied by the server itself, every reloadable key really reloads, and only `listen`, `socket_mode` and `workers` need a restart

- **Scope:** how a running server gets a configuration change into effect: what a published snapshot
  rebuilds, how the server notices a saved file, what it reports about a key it cannot apply, and
  which keys still need a restart. It does not decide how a *source* change reaches a request, which
  [0218](0218.md) owns.
- **Depends on:** [0078](0078.md) for the snapshot, the reload, the `Reload`/`Boot` field and the
  control socket; [0218](0218.md) for the background check and the mount table that follows the disk;
  [0097](0097.md) for the `[server]` block; [0106](0106.md) for the admission ceiling; [0103](0103.md)
  for what `nvs ctl config` reports.
- **Validated by:** `crates/nvs-cli/tests/live_config.rs`, which starts the built `nvs serve`, changes
  its configuration and checks the next request; the census
  `every_directive_has_a_live_apply_proof_or_a_restart_proof` in `crates/nvs-config/tests/directives.rs`;
  and `only_listen_socket_mode_and_workers_need_a_restart` in `crates/nvs-config/tests/snapshot.rs`.

> **In short:** a restart or a reload is never required unless it is technically impossible without
> one. Everything a published snapshot changes is rebuilt from that snapshot — security headers, CORS,
> the admission ceiling, the unit cache's `[opcache]`, the schedule roster, each queue job's
> configuration, the metrics and trace exporters, the mount rows' origins — and a census holds every
> directive to a live proof of it. The server checks the stamps of its own configuration files off
> the request path, and a saved file is validated and published the way `nvs ctl reload` publishes
> one. Exactly three keys need a restart: `[server] listen`, `[server] socket_mode` and
> `[server] workers`. A change to one is logged by name the moment it is seen and listed by
> `nvs ctl status` until the process restarts. Every other key builds its new resource, lets the
> requests and jobs already running finish on the old one, and closes the old one after them.

## Context

### 1. A reload said it applied keys it did not apply

A reload published a new snapshot, and a request read its own directives from it. But several
subsystems had taken their values once, at boot, and never looked at a snapshot again: `Secure` and
`Cors` were derived once per process, the admission ceiling was computed once from `limits.memory`,
the unit cache held the boot's `[opcache]`, the `[[schedule]]` roster was armed once, a queue worker
held the boot snapshot for every job it ran, the metrics registry and the trace exporter were built
once, and `[[app]] origin` was folded into the mount rows once. The reload's report listed all of
them as applied. [0078](0078.md)'s promise that a report names what did not take effect was broken
by keys the report did not know were stale.

### 2. Nothing noticed a saved file

A reload was only ever pushed, by an operator running `nvs ctl reload` or by a service manager's
`PARAMCHANGE`. A configuration edited and saved did nothing until somebody remembered to push it,
which is the same forgotten deploy step [0218](0218.md) removed for source.

### 3. The restart list was wide

`Boot` covered the whole `[server]` block — its timeouts, `max_in_flight`, `trusted_proxies`,
`health_path`, `dispatch`, `static`, `root`, the mounts and `[server.connection]` — and also
`[session]`, `cache.shared`, `http.client.tls`, `io.temp_root`, `opcache.file_cache_dir`,
`[control] socket` and `[queue]`'s `connection` and `workers`. Most of these name a resource that
can be built a second time while the first is still in use. Only a few name one that cannot.

## Decision

### 1. The user's rule

**A restart or a reload is never required unless it is technically impossible without one.** A
configuration change is applied by the server itself, and `nvs ctl reload` remains, for applying one
at once. `SIGHUP` still stops the server: nothing needs a reload any more, so no signal is given one.

### 2. Everything a snapshot changes is rebuilt from the published snapshot

Each subsystem that derives state from the configuration derives it again when a snapshot is
published, and a request or job that starts afterwards sees the new state:

- `Secure` and `Cors` are derived once per published snapshot, not once per process.
- The admission ceiling is recomputed from the published snapshot. Requests already admitted keep
  their places, so a lowered ceiling refuses new work until enough of them end.
- The unit cache reads `[opcache]` from the published snapshot. A changed `file_cache*` swaps the
  on-disk artifact cache for new compiles, and units already in memory are untouched. A changed
  `[[extension]]` set moves the artifact cache to the new `env_hash`.
- The `[[schedule]]` roster is compared with the new one. A fire already running finishes, and the
  new roster arms from the next tick.
- A queue worker takes the published snapshot for each job it claims, and `visibility` with it.
- The metrics registry, the scrape socket, the push endpoint and the trace exporter are rebuilt,
  with a new socket bound before the old one closes. A change that cannot be followed — a port that
  will not bind, an exporter with no endpoint — is logged, and the running one is kept.
- `[[app]] origin` is folded into the mount rows again.

### 3. A census makes it permanent

Every directive in the registry names exactly one proof. A `Reload` row names a case in
`crates/nvs-cli/tests/live_config.rs` that changes the key under a running server and checks a real
request. A `Boot` row names the test that changes it and checks that the running value is kept and
the key is reported. A directive added with neither fails the census. This is the test that would
have caught every key in § 1.

### 4. The server checks its configuration files

A timer on the compile pool, off the request path, checks the stamp (`mtime` and size) of every path
the last published resolution read — the root file, every `include`, and every optional include that
was absent, so one that appears is seen. The interval is a fixed two seconds, not a directive: no
operator needs to tune how quickly a saved file is noticed, and a key for it would be one more thing
to explain.

A moved stamp is not applied at once. The file must keep the same stamp for one more check, so an
editor or a copy that writes a file in pieces is read only when it has finished. Then the tree is
resolved, validated and published through **the same function `nvs ctl reload` calls**, under the
same lock, so a pushed reload and a noticed one cannot interleave two snapshots. Every
validate-then-publish step of `rule:config/the-config-is-an-immutable-snapshot` runs, the ownership
checks included: a file that became writable by another account is refused, exactly as a pushed
reload refuses it.

A file that does not validate is logged once for that content, with its file and line, and the
running configuration stays. The next save is checked again. A saved file whose contents did not
change publishes nothing.

### 5. A pending restart is loud

A changed restart key is logged by name, with its running value and its written value, the moment
the change is seen — once for each written value, not once per check. `nvs ctl status` lists every
pending one until the process restarts, and a reload's answer still names each one
(`rule:config/a-reload-names-what-it-could-not-apply`). A file changed back to the running value
clears the entry.

### 6. `Boot` is three keys

The `server` row is split into one row per key. **`[server] listen`, `[server] socket_mode` and
`[server] workers` are `Boot`, and nothing else is.**

- `listen` cannot move in general: a port below 1024 needs a privilege the process dropped after it
  bound, and a server that could bind it again would have to keep that privilege for its whole life.
- `socket_mode` is applied when a Unix listener is bound, so it moves only with `listen`.
- `workers` stays by the user's choice. Each core holds its own runtime state, and resizing that
  while it runs is a large change for a key set once per machine.

### 7. Every other key: build the new, finish on the old, close the old after

A key that names a resource applies the same way. The new resource is built from the published
snapshot. Requests and jobs that started before the publish finish on the old one, and the old one
is closed after the last of them ends.

- The timeouts and `[server.connection]` apply to the next connection. A connection already accepted
  keeps the bounds it was accepted under.
- `max_in_flight` moves the admission ceiling, as in § 2.
- `trusted_proxies`, `health_path`, `dispatch` and `static` are read per request from the snapshot
  the request cloned.
- `root` and the mounts rebuild the mount table through the expansion [0218](0218.md) § 9 runs, and
  every path it produces is checked against the new `root`.
- `[session]` and `cache.shared` build a new store. New requests use it, and the old one is closed
  after its last request. Sessions held by the old store are not carried over, so changing the
  backend signs every user out; that is the operator's choice to make.
- `http.client.tls` applies to the next outbound connection, and `io.temp_root` to the next
  temporary file.
- `opcache.file_cache_dir` applies to the next compile, as `file_cache*` does in § 2.
- `[control] socket` binds the new endpoint before it closes the old one. The directory holding the
  new one passes the trust check the boot runs (`rule:config/one-local-control-socket`), and `false`
  closes the endpoint.
- `[queue] connection`: each worker finishes its current job on the old connection and claims its
  next one on the new. `[queue] workers`: a new count starts workers, or stops them after their
  current job.

A resource that cannot be built — a session database that does not answer, a control socket whose
directory fails the trust check — is logged by name with the reason. That key keeps its running
value and is reported as not applied, and the rest of the snapshot is published. One unreachable
store must not hold back an unrelated change, which may be a security fix.

## Diagnostics

Every outcome of a noticed change is one `Core\Log` record, written where a pushed reload's already
goes: *applied*, with the files that changed; *refused*, with the diagnostic's file and line and the
words that the running configuration is unchanged; *restart pending*, with the key, its running
value and its written value; and *not applied*, with the key and the reason its resource could not be
built. Under a service manager these reach the event log or the journal
(`rule:packaging/a-service-answers-its-manager`). `nvs ctl status` prints the pending list, one key
per line, with both values.

## Consequences

- **Performance:** one `stat` per configuration file every two seconds, in the background, and none
  on the request path. A request still clones one `Arc`. A publish rebuilds the derived state once,
  never per request.
- **Memory:** two snapshots during a swap, as before, and each replaced resource — a store, a
  connection pool, an exporter, a control endpoint — until the last request or job using it ends.
  Bounded by what is in flight, never by the number of reloads.
- **Usability:** saving the file is the deploy. A restart is needed for three keys, and the server
  says so the moment one changes. Changing the session backend signs users out.
- **Simplicity:** the restart list is three keys, and every subsystem answers one question — what it
  rebuilds when a snapshot is published — instead of a class it has to remember. The price is that
  each subsystem carries its own publish step, and the census is what keeps a new one honest.

## Alternatives rejected

- **A file-system watcher** (`inotify`, `ReadDirectoryChangesW`), for the reasons
  [0218](0218.md) gives: a lost event is a change that never arrives, and a timed `stat` of a known
  list cannot miss one.
- **Reloading on `SIGHUP`.** Not reopened: the server applies a saved file itself, and a signal that
  stops the server in one place and reloads it in another is a trap.
- **Applying a changed file at once.** A file read while it is being written can be valid and still
  incomplete — a block cut off at a line boundary — and publishing it would drop every key after the
  cut. One quiet check costs two seconds.
- **Refusing the whole reload when one resource cannot be built.** It would let an unreachable
  session database hold back a tightened header policy written in the same save.
- **Making `listen` reloadable.** It needs the process to keep a privilege for its whole life so it
  can bind a low port again, and priority 1 is not traded for a restart saved.
- **Resizing `workers` live.** The user's call: the change is large and the key is set once per
  machine.

## Verification

`crates/nvs-cli/tests/live_config.rs` holds one case per `Reload` row the census names, and the
cases for this record's own claims: a saved file is applied without a reload; a half-written file is
logged and the running configuration kept; a changed restart key is logged as pending and listed by
`nvs ctl status`; a changed session backend applies to new requests; a changed queue worker count
starts and stops workers after their current job; a changed control socket moves the endpoint; a
changed server timeout applies to the next connection; and watching the configuration costs no
request a file-system call.
