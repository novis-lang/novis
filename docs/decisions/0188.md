# ADR 0188 — `array<T>` reads covariantly in its element type, because an array is a copy-on-write value

- **Scope:** the variance of `array<T>` in the assignability relation, and nothing about the `as`
  conversion that restamps one. What a *write* through a widened view is checked against is decided
  here too, because it is the half that makes the read sound.
- **Depends on:** [0007](0007.md) (the element type and its invariance), [0002](0002.md) (copy-on-write
  value semantics), [0125](0125.md) (`class<T>`'s covariance, the other road to the same answer).
- **Validated by:** `crates/nvs-types/tests/arrays.rs`,
  `tests/conformance/core/arr-flip-takes-an-array-of-string-without-a-conversion.nvst`,
  `tests/conformance/lang/an-array-of-string-is-passed-where-an-array-of-int-or-string-is-read.nvst`.

> **In short:** an `array<int>` satisfies an `array<int|string>` wherever one is read, and never the
> reverse. The objection that sinks covariant arrays elsewhere is about *aliasing*: a write through the
> widened view lands in storage the narrow view still reads. A Novis array is a copy-on-write value, so
> the widened binding becomes a separate array the moment anything writes to it and the narrow one can
> never observe the write — and the write is checked against the widened view's own element type
> regardless. The `as` conversion keeps its O(n) restamp; the covariant read is what no longer needs it.

## Context

### 1.

`rule:types/arrays` declared `array<T>` invariant, which is the answer a language with aliasing
containers has to give. The cost of that answer showed up wherever the standard library writes a
signature over a union. `Core\Arr::flip(array<int|string> $a): array<string>` is the clearest case: a
caller holding the `array<string>` it built could not pass it, and had to declare `array<int|string>`
at the binding instead — annotating for the callee rather than for the value. `Core\Arr::sum`'s
`array<int|float|decimal>` is the same shape, and refusing an `array<int>` there is refusing what a
caller means by the call.

The invariance was bought for a reason the record states plainly: widening costs an O(n) restamp, and
an implicit widening would hide that cost inside an assignment. That reason survives — it is about the
`as` conversion, which really does walk the array — but it never applied to a *read*, where nothing is
walked and nothing is rewritten.

## Options considered

### 2.

- **Keep the invariance and annotate at the caller.** Every caller of a union-typed signature declares
  the union, whether or not its own values are ever anything but one member. Simple in the checker, and
  it pushes the callee's type into bindings that have no other reason to carry it.
- **Covariant read, invariant conversion.** The relation accepts a narrower element type where a wider
  one is read; `as array<U>` still means the restamp and still costs O(n). One recursion in
  `nvs_types::expr::assign::is_assignable`, element to element.
- **Covariance plus a runtime barrier on writes through widened views.** The answer an aliasing
  language needs. Nothing here needs it, and it spends request-path latency on a hazard the value
  semantics already exclude.

## Decision

### 3.

The second. `array<T>` is covariant in its element type at every position the assignability relation is
applied at — a parameter, a return, and an assignment to a wider binding — and narrowing is still
written `as array<T>` and still restamps.

### 4. Why it is sound here

The unsoundness of covariant containers is a statement about aliasing, not about variance. Where the
wide view and the narrow view name one buffer, a `string` written through the wide view is read back as
an `int` through the narrow one. `rule:types/arrays` makes an array a copy-on-write **value**: the
widened binding shares the buffer only until something writes, and the write is what separates them. So
the narrow view cannot observe a write through the wide one, and there is no read to be wrong.

The second half is the checker's, and it does not depend on any of that: a write through the widened
view is checked against the element type the *widened view* declares. Widening a view never widens what
may be written through it beyond what that view itself admits, so the covariance opens no write that
the annotation did not already open.

This is the same conclusion `rule:types/class-reference-variance` reaches for `class<T>`, by the other
road: there the argument has no write side at all, so the trap cannot be set. `array<T>` has a write
side and defuses it. `property<T>` is left as the one that widens on neither argument, its argument
bounding a receiver rather than a payload.

## Consequences

### 5.

- Strictly more programs compile and none stops compiling. The relation gained a direction; it lost
  nothing, and the invariant spelling a caller may already have written is still accepted.
- The `as array<U>` conversion is unchanged — same row in `rule:types/conversion`, same O(n) restamp,
  same shared copy-on-write buffer. What changes is that reading no longer requires writing one.
- No memory is spent. Nothing is allocated, copied or interned that was not interned before: the call
  passes the array it was handed, stamped as the caller declared it.
- Every `Core` signature written over a union becomes reachable from the narrower array a caller
  naturally holds, which is what the standard library's array rows assumed all along.

## Alternatives rejected

### 6.

Keeping the invariance and annotating at the caller was rejected because the annotation it demands says
something false about the value: a binding that only ever holds strings is declared `array<int|string>`
to satisfy a callee. That is the callee's type leaking into the caller's vocabulary, and priority 4's
simplicity of the language surface is what pays for it.

The runtime write barrier was rejected for spending priority 3 on a hazard priority 2's value semantics
already exclude.

## Verification

### 7.

`crates/nvs-types/tests/arrays.rs` holds the relation's own tests: the widening accepted at each of the
three positions, the narrowing refused at each with the code belonging to that position, a table
asserting the accepted set grew and the refused set did not, and the write through a widened view
checked against that view's element type. The two conformance cases named above run the same claims as
programs, one through `Core\Arr::flip` and one through a user-declared parameter, and both assert the
caller's array is unchanged by the callee's write.
