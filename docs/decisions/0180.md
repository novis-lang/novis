# ADR 0180 — `Core\Http\Client` is a client an API is driven through: one body per call, bounded streams, a pool keyed on what was approved, and trust the operator owns

- **Scope:** everything `Core`'s outbound HTTP half still owes a program driving a real API — a request
  body and a run-time verb, a reply read through its headers and its shape, a streamed reply and the two
  bounds on it, connection reuse, content decoding, credentials across a redirect, a client identity, who
  decides which certificates are trusted and where a program may relax that, naming an address, what a
  handshake reports back, resolving a name off the core and trying every address it answers, and the trace
  event one call files. Not in scope: the `nvs/rest` package and OAuth, and where a token lives between
  requests, which is goal `process-cache`'s; HTTP/2 and HTTP/3; a forward proxy and TLS to it, which is
  goal `outbound-proxy`'s; a resolver of Novis's own, DNS over HTTPS, CRL, OCSP, the OS certificate store,
  cipher-suite selection, HSTS, a cookie jar, and parsing `Link` or RFC 9457 problem details for a
  program.
- **Depends on:** [0058](0058.md) for the launderer, the address policy and the pin; [0074](0074.md) for
  the options bag, the one deadline and jittered opt-in retry; [0166](0166.md) for the decompression bound
  this reuses rather than sets; [0179](0179.md) for the `Crypto\KeyPair` a client identity is built from;
  [0041](0041.md) for the trace event a fifth kind joins; [0033](0033.md) and [0088](0088.md) for which of
  these positions are sinks; [0005](0005.md) and [0064](0064.md) for the changeability class every new
  directive carries.
- **Validated by:** the conformance cases stages 3–13 of goal `http-client` add, all of them written
  against § 1's table with no listener and no outbound grant; the first end-to-end `https` test, a
  loopback origin with an `rcgen` certificate reached through `Core\Http\Client` under a `roots` file;
  `crates/nvs-config/tests/tree.rs` for the two new blocks and the refusals in § 16; and
  `crates/nvs-stdlib/tests/spec_registry_coverage.rs` for the surface.

> **In short:** `Core\Http\Client` can fetch, and that is all it can do — no body, no reply headers, no
> stream, one connection per attempt, one process-wide answer to *whose certificates do you believe*, and
> one address per name. This decides all of it at once, because every piece constrains the others: a body
> is at most **one** of four flat keys and a body on `get` is a **compile-time** diagnostic, since the bag
> is an R2 literal and the verb is the member's name; `request(Core\Http\Method, …)` replaces the spec's
> `send(Request)` and there is no `Core\Http\Request` class; a streamed reply is read one way, once, under
> `idle` and `maxDuration`, because `deadline` ends at the head and a body that arrives forever would
> otherwise have no bound; the pool is per core and **keyed on exactly what the check approved** — the
> pinned address, the port, the scheme, the server name, the client identity and the call's TLS policy —
> so reuse cannot hand a call a connection its own policy would have refused; a hop to another origin
> **drops** the caller's credentials. Trust is the operator's: `[http.client.tls]` names the roots, and
> code relaxes verification only for a host a `capabilities.tls` grant lists, in a grant with **no `true`
> spelling**. A name resolves on the blocking pool, **every** address it answers is checked and one denied
> refuses the host, and the call falls back across the approved set without ever resolving twice. Every
> reply is `tainted`, every bound is finite, and a test answers outbound calls from a table so none of
> this needs a listener to prove.

## Context

`Core\Http\Client` today is five request members over one options bag
([`http.rs`](../../crates/nvs-stdlib/src/http.rs)'s `CLIENT`), one HTTP/1.1 exchange per attempt over the
parking stream ([`transport.rs`](../../crates/nvs-stdlib/src/http/transport.rs)), a reply that answers
`status()` and `text()`, and a deadline that covers every attempt and hop. The parts it is missing are not
independent features a program can wait for one at a time; they are one shape, and the module's own doc
says so — its § *What is not here yet* names a request body and the reply's headers and argues that each
was left out because the decision belonged to a record rather than to a signature
(`crates/nvs-stdlib/src/http.rs:102-111`).

What a program driving an API actually does, in one sitting: `POST` a JSON body, read a header off the
reply, decode the reply into a declared shape, stream a long one rather than hold it, reuse the
connection for the next call, follow a redirect without leaking its `Authorization` to another origin,
present a client certificate to a partner that demands one, trust a corporate CA the public bundle does
not carry, and see where the time went when it is slow. Every one of those is blocked today, and several
of them are blocked *on each other*: a pool is only safe once the reply's framing is known to the end,
framing is only knowable once bodies and content codings are decided, and a content coding is only
decodable under a bound that already exists for a different reason.

Three existing guarantees constrain every line below, and none of them is re-opened here. An outbound URL
is a sink and a `tainted` one is refused where it is written
(`rule:security/outbound-url-is-a-sink`). `Core\Http::allowUrl` resolves, checks and **pins**, and the
connection is made to what it pinned, which is what closes the check-then-connect gap
(`rule:http-server/allow-url-pins-the-address`). And there is no spelling for an unbounded wait
(`rule:http-server/no-spelling-for-an-unbounded-wait`), because a default that is unbounded outbound is a
defect rather than a neutral starting point (`rule:http-server/an-unsafe-or-unbounded-default-is-a-defect`).

## Investigation

Three things were read before any of this was written, and each moved a decision.

**What the transport already knows.** `REPLY_CEILING` is 8 MiB and its doc already names the member that
would relieve it as the one this class does not have
(`crates/nvs-stdlib/src/http/transport.rs:67-73`); the reply's headers are parsed and then not handed to
a program; and `Retry-After` is read in its delay-seconds form only, the HTTP-date form left unread for
want of a clock agreement, after four statuses where the rule names two. So § 4 and § 5 are largely
*unblocking what is parsed already*, not new machinery.

**What `Core\Compress` already decides.** `decompress_within` decodes gzip, zlib, deflate, brotli and
zstd behind one bound that cannot be switched off, reading one octet past the ceiling so a bomb costs the
ceiling and never its declared size (`crates/nvs-stdlib/src/compress.rs:522`). Three of those decoders are
exactly the three content codings worth offering, so accepting `gzip, br, zstd` adds no dependency and no
second ceiling — and the ratio question already has a home, which is why § 8 sets no number of its own.

**Where the one TLS client sits.** `nvs_host::tls` holds a single process-wide `ClientConfig`, and its doc
records that a *program* choosing anchors, or turning verification off, is closed permanently. That
sentence is what stages 9 to 11 have to reopen without reopening the thing it protects, and `rustls`'s
custom-verifier seam is what makes that possible: a caller hands in a policy value and the module builds
the config, so there is still exactly one TLS client and still no way to hand one in
(`rule:security/one-tls-client`).

## Options considered

**For the run-time verb**, the spec's own `send(Core\Http\Request)` against `request(Method, $url, {…})`.
A `Request` class is a second place a call is described, with its own construction, its own mutability
question and its own place for a body to disagree with the bag. The verb is the only thing the five
existing members cannot express, so widening one member to take it is the whole of what is needed.

**For bodies**, one `body` key over a union against four keys naming what they send. A single key forces
either a mode string beside it — which `rule:core-api/no-mode-strings` refuses — or type-sniffing, where
an `array<string, string>` would have to guess between a form and a JSON object.

**For the streamed reply**, a `Response` whose `text()` throws until you read the body against a separate
`Core\Http\Stream`. A class whose members throw depending on how it was obtained is the worse surface;
the inbound half already made this call, where buffering readers share the body and streaming readers
consume it (`rule:http-server/buffering-readers-share-the-body-and-streaming-readers-consume-it`).

**For relaxed trust**, a boolean grant (`tls.insecure = true`) against a host list. A boolean is one line
in a deployment that nobody reads again; a host list makes what was relaxed legible host by host in
review, which is `net.internal`'s own reason for having no `true` spelling.

**For the address set**, keeping one pinned address and letting the connect fail against pinning the
whole approved set. One address is a single point of failure for a name that answers four, and it makes
the client worse than `curl` for no security gain — the gain is in *checking* every address, not in
discarding all but one.

## Decision

### 1. A test answers outbound calls from a table, and that is the keystone

`Core\Test::answerHttp(string $url, uint $status, {json?, body?, headers?})` registers an answer;
`Core\Test::sentHttp(): array<Core\Test\SentRequest>` hands back what the program sent, in order. `$url`
matches exactly, or as a prefix ending in `*`.

Once **any** answer is registered in a test, every outbound call that test makes is answered from the
table, and an unmatched one throws a `LogicError` naming the URL. The all-or-nothing switch is the point:
a table that answers some calls and lets the rest reach the network is a test suite that passes on a
laptop and fails in CI, and the failure is silent until it is a bill. A faked call is judged exactly as a
real one where the judging is about *text* — the scheme and the grant — and resolution and the address
check are skipped, because no connection is made for an address to be pinned to.

`SentRequest` is readonly: `method(): Core\Http\Method`, `url(): string`, `header(string $name): ?string`
and `body(): bytes`. Nothing on it is `tainted`, and that asymmetry with every reply member below is
deliberate — a sent request is text the program itself authored, so the qualifier would be a lie about
where it came from, which is the one question `rule:security/tainted-qualifier` answers.

This is the keystone because every later stage's `.nvst` case is written against it, with no listener and
no outbound grant. What it cannot reach is everything *below* the table — the pool, the framing, a
content coding, a redirect hop, a handshake — and those are proved by Rust tests against a loopback
origin, as the transport's own tests already are.

### 2. A request carries at most one body, and which key it is says what is sent

Four keys join `Core\Http\Options`, flat per `rule:core-api/shape-rules` R2, beside a fifth that types a
raw one:

| Key | Sends |
|---|---|
| `json?: mixed` | `application/json`, encoded once per call |
| `form?: array<string, string>` | `application/x-www-form-urlencoded` |
| `body?: string\|bytes\|Core\Http\Part` with `contentType?: string` | the octets as given; a `Part::file` is streamed from disk under `fs.read` with `Content-Length` from its size |
| `multipart?: array<string, string\|Core\Http\Part>` | `multipart/form-data` |

`Http\Part::file($path, {filename?, contentType?})` streams from disk under `fs.read`;
`Http\Part::bytes($data, $filename, {contentType?})` sends what it holds. A `Part` in `body` is how a
large upload — an S3 presigned `PUT`, a resumable upload — is sent without ever being held whole, which
is the same reason the inbound half streams a part to disk rather than through memory.

**At most one body key, and it is checked while compiling.** Two body keys, a body on `get` or `head`, or
`contentType` without `body`, is a diagnostic naming the key, emitted beside `reject_keyless_retry` in
`crates/nvs-types/src/expr/args.rs`. This is available for the same reason the missing idempotency key is:
the bag is a compile-time-constant literal and the verb is the member's name, so both halves of the
question are in front of the checker. Nothing here is a runtime check that could have been a diagnostic.

`Content-Length` is always written, because every body's size is known before the first byte — a form and
a JSON body are built in memory, a `Part::file` reports its size from the filesystem. There is no chunked
request body, and a program that wants one is describing a protocol this client does not speak yet rather
than a missing option.

The body is built **once per call** and resent unchanged on every attempt; a file part is re-read per
attempt. Encoding a JSON body once is what keeps a retry from paying for the encode again, and re-reading
a file is what keeps a retry from holding it.

### 3. `request(Method, …)` replaces `send(Request)`, and `patch` joins the members

`patch` joins `get`, `post`, `put`, `delete` and `head` as a member of its own, and
`Client::request(Core\Http\Method $method, $url, {…})` takes the same bag for a verb chosen at run time.
There is **no `Core\Http\Request` class**, and the spec row moves with this record.

Where the verb is dynamic, the two checks § 2 makes at compile time have to happen somewhere, so they
happen before the first attempt: a body on `Get` or `Head`, and a `Post` or `Patch` with `retryAttempts`
and no `retryIdempotencyKey`, both throw a `LogicError` before a byte leaves the process. That is what
[0074](0074.md) § 7 already asks of a dynamic verb, and the rule it created is edited by this record to
name `request` where it named `send`.

### 4. A reply is read through its headers, its shape or its bytes, and all of it is `tainted`

`Core\Http\Response` gains `header(string $name): ?tainted string`, `headers(string $name):
array<tainted string>`, `jsonAs<T>()` and `bytes(): tainted bytes`. Names match case-insensitively.

`header` joins repeated values with `, ` as RFC 9110 § 5.3 allows, and is a `LogicError` naming `headers`
for `set-cookie`, which RFC 6265 forbids joining — a joined `set-cookie` is not a value any parser can
recover the original pair from, so answering one would be answering wrongly. The pair is therefore not
two ways to do one thing under `rule:core-api/shape-rules` R17: one answers the value a program expects to
be single, the other answers a list, and `set-cookie` is the case that proves they are different
questions. Neither takes no argument: there is no whole-map member, because a map invites a program to
iterate raw names and forces a joined-or-not decision per key with no case to decide it on.

An absent header is `?T` rather than a throw, because absence is what `?T` means and a missing optional
header is not a failure (`rule:core-api/failure-throws`). The noun spelling is right for the same reason:
the subject is the reply, so `header` reads as *this reply's header*, and `findHeader` would claim a
search over something the caller does not hold.

`jsonAs<T>` joins `Core\Request::jsonAs` on the decode-site roster in
`crates/nvs-types/src/expr/args.rs`: `T` is a `tainted` shape, or a class whose text fields declare
`tainted`, per `rule:security/derived-codec-qualifiers`. Every text a reply hands back carries the
qualifier — `text`, `bytes`, `header`, `headers`, `jsonAs`'s fields and every streamed piece — because
another host chose those bytes, which is exactly the question `tainted` answers. A `4xx` or `5xx` remains
an answer rather than a throw, unchanged.

**`Retry-After` is read in both of its forms.** The HTTP-date form was left unread for want of an
agreement about clocks, and the deadline already is one: a date past the remaining deadline throws now
rather than sleeping into it, and a date **already past** keeps the jittered backoff rather than becoming
a zero wait — otherwise every client a failing service handed the same date retries in the same
millisecond, which is the failure mode jitter exists to prevent
(`rule:http-server/retry-is-opt-in-jittered-and-closed`). The header is read after a `429` or a `503`
alone, as that rule says and as the code today does not.

### 5. A streamed reply is read one way, once, and bounded by `idle` and `maxDuration`

`Client::stream(Core\Http\Method $method, $url, {…})` answers `Core\Http\Stream` once the head has
arrived. The verb is a parameter because a streamed reply is usually a `POST` — a chat completion, a query
that returns rows — and a `stream` that could only `GET` would be the member nobody uses.

The head is readable on the stream — `status()`, `header()`, `headers()`, `tls()` — and the body is read
exactly one way, exactly once: `events()`, `lines()`, `chunks()` or `saveTo(string $path, uint $max)`
under `fs.write`, whose byte bound is required for the reason `rule:core-classes/io-write-stream`'s `max`
is. A second read throws a `LogicError`. `Core\Request::bodyStream` is the precedent for the reader's
shape, and the inbound rule about consuming readers is the precedent for the one-way-once part.

- **`events(): Iterable<Core\Http\Event>`** parses the WHATWG EventSource format: a line ends at `\r\n`,
  `\r` or `\n`; `data`, `event` and `id` are read; `retry` is read and ignored, because reconnecting is
  the program's decision and a server-chosen sleep inside a `Core` iterator is a wait with no bound the
  caller wrote; a comment line is skipped. `Event` is readonly `data(): tainted string`, `name(): ?tainted
  string` and `id(): ?tainted string` — `name` rather than `event`, because `Event::event()` reads as the
  whole event rather than as the field.
- **`lines(): Iterable<tainted string>`** ends a line at `\n` and strips a trailing `\r`.
- **`chunks(): Iterable<tainted bytes>`** yields what the transport read, and takes no size argument: the
  wire cannot promise a piece size for the last piece anyway, and a reader that must have fixed blocks is
  doing its own framing and can buffer.
- **A line and an event are each length-capped**, at 64 KiB for a line and 1 MiB for one event's
  accumulated `data`, as constants beside `REPLY_CEILING` and for its argument — these are bytes another
  host chose, so "until memory runs out" would be that host deciding this process's footprint.

**The bound.** `deadline` covers the connection and the head, and ends there. After that the body runs
under two `Duration`s: `idle`, the longest silence allowed, and `maxDuration`, the longest the body may
take at all. Both inherit `[http.client]` when omitted and neither has an unbounded spelling, so a stream
has no more spelling for *forever* than a buffered call does. Two bounds rather than one because they
catch different failures: a server that stops sending is caught by `idle` in seconds, while a server that
dribbles one byte per second forever passes every idle check ever written and is caught only by a
lifetime. On a buffered member either key is a diagnostic.

**A stream is retried only before its head.** After the first byte of body, a failure ends the stream —
the caller has already seen part of the answer, and re-requesting would hand it a second prefix of a
different body. `chunks()` on a reply the table answered yields its bytes in one piece.

### 6. A connection is pooled per core, and the key is exactly what was approved

HTTP/1.1 keep-alive over a **per-core** pool, keyed by the pinned address, the port, the scheme, the TLS
server name, the client identity of § 7 and the call's TLS policy of § 11. Per core because a core owns
its requests and a cross-core pool is a lock on the request path, and because a bound per core is a bound
this process can state:
O(cores × `pool_idle`), never O(requests served) — the same shape
`rule:security/db-pool-reset-is-a-boundary` already holds for the database pool.

The key is the load-bearing part, and every element of it is there because leaving it out lets reuse hand
a call a connection its own check would have refused. The pinned address keeps
`rule:http-server/redirects-are-off-and-every-hop-is-re-pinned` true *through reuse*; the server name
keeps two hosts behind one address from sharing a session; the identity keeps a call that presents no
certificate from reusing one that did; the policy keeps a connection opened under `tlsVerify: false` from
ever serving a call that verifies. A pool keyed on the URL's host — which is what most clients key on —
would silently undo the pin.

A connection goes back to the pool **only** after its reply was read to the end under known framing —
`Content-Length` or chunked's last chunk — with no `Connection: close` from either side. On any doubt it
is closed, because a connection whose remaining bytes are unknown is a connection that will hand the next
request someone else's body. A reused connection that fails before the request's last byte is written is
replaced once **without spending an attempt**, since a server closing an idle connection is not a failed
request; any later failure is an attempt under the retry rules. The pool holds at most `pool_idle` idle
connections per core and closes one idle past `pool_idle_timeout`. `Connection: close` leaves the request,
and `Accept-Encoding: gzip, br, zstd` joins it.

### 7. A client identity is an option, built from a key pair, and part of the pool key

`identity?: Core\Http\Identity` joins the bag, built by `Http\Identity::read(bytes $chainPem,
Crypto\KeyPair $key)` over [0179](0179.md)'s key pair — whose kind is what the handshake is signed with,
so there is no algorithm argument here either. `read` refuses a chain whose leaf does not match the key,
at the point the identity is built rather than at the handshake, where the error would arrive as a remote
alert with nothing useful in it.

A call with an identity presents it when the server asks and never otherwise. One `ClientConfig` serves
the whole process; an identity is a second config, built once per `Identity` and held as long as it is,
which is the reason an `Identity` is an object rather than two bag keys
(`rule:core-api/shape-rules` R14).

### 8. gzip, brotli and zstd are decoded under the bound that already exists

The three codings are decoded through `crate::compress::decompress_within`, so the ratio and the ceiling
are one number with one home, and by the three decoders that module already links, so no dependency is
added. A streamed reply decodes incrementally under the same ratio.

**A decoder's window is bounded before it is allocated**, which the output bound alone does not do:
brotli's is at most 16 MiB by RFC 7932's own format, and a zstd frame whose `Window_Size` passes 8 MiB —
RFC 9659's ceiling for the `zstd` content coding — is refused naming the limit. A 63-byte frame header
can otherwise ask for a gigabyte of window before one output byte is produced, and the output ceiling
never sees it.

A `Content-Encoding` the request did not offer — `deflate` among them, which the request deliberately
never offers — is a `RuntimeError` naming it. Bytes are never handed on still encoded, because a program
that asked for `text()` and got a compressed blob has no way to tell that from a server bug.

### 9. A hop to another origin drops the caller's credentials

A hop to another origin — scheme, host or port differing — drops `Authorization`, `Cookie`,
`Proxy-Authorization` and every header whose value was `secret`; a hop within one origin keeps them.
Forwarding a bearer token to whatever host a `Location` names is a credential-exfiltration primitive with
one line of setup, and the `secret` clause is what makes it general: a program's own API-key header is
dropped for the same reason the three named ones are, without this record having to enumerate every
spelling a partner invented.

No header value is written into a trace span, an access log record or an error message. The transport's
header guard already names the header and never the value, and this record makes that a test rather than
a habit.

### 10. The trust roots are the operator's, in a `System`-class block

`[http.client.tls]` is new, `System` class in all three keys because it is the one `ClientConfig` the
process shares, and it has no code-side spelling for any of them:

| Key | Ships | Allows |
|---|---|---|
| `roots` | `["bundled"]` | Each entry is `"bundled"` — the compiled-in Mozilla set — or a PEM file. `["bundled", "/etc/novis/corp-ca.pem"]` adds a company CA; a list without `"bundled"` trusts only its files. Each file is resolved and trust-checked at boot exactly as `[db.<name>] tls_ca_file` is, and parsed by `nvs_host::tls` alone. |
| `min_version` | `"1.2"` | `"1.3"` raises the floor for every call. There is nothing below `1.2` to write: `rustls` speaks neither 1.0 nor 1.1. |
| `keylog` | unset | A file every session's secrets are appended to in the `SSLKEYLOGFILE` format, so an operator can read their own traffic in Wireshark. **Refused at boot in `production`**, with a diagnostic naming the key; in `development` the boot says it is on, every start. |

`1.2` rather than `1.3` as the shipped floor is the one place here where compatibility wins: a great many
corporate and payment endpoints are still 1.2-only, and a client that cannot reach them is a client a
deployment replaces with `curl`. The floor is one line to raise, and `nvs config dump` shows what it is.

`keylog` is the only directive in this record whose safe value depends on the mode, and it gets a boot
refusal rather than a warning because a file of session secrets in production is not a configuration
mistake a warning improves — the process must not start with it.

### 11. Code relaxes trust only for a host a grant names, and only by asking in the call

Four options join the bag, each unlocked by a grant under a new `[capabilities.tls]` area. Every grant is
a list of hosts, matched as `net.connect` matches them, and **none has a `true` spelling**:

| Option | Grant | Does | curl |
|---|---|---|---|
| `tlsCa: string` | `tls.anchors` | trusts exactly the PEM certificates given, for this call, in place of `roots` | `CAINFO_BLOB` |
| `tlsPin: string\|array<string>` | `tls.pin` | accepts a peer whose SubjectPublicKeyInfo hashes to one of the `sha256//<base64>` values, with no chain | `--pinnedpubkey` |
| `tlsVerifyHost: false` | `tls.any_name` | builds and checks the chain, and skips only the name | `SSL_VERIFYHOST=0` |
| `tlsVerify: false` | `tls.insecure` | checks neither | `-k` |

- **The grant and the option are both owed.** A grant changes nothing about a call that does not ask, and
  an option whose host is not in its grant throws before a connection is made, naming the grant — asked
  of the request's own configuration snapshot, per
  `rule:security/capability-question-is-grant-and-scope`. Two halves rather than one because each answers
  a different party's question: the deployment says *where* this may happen, the code says *here*.
- **Every relaxed session still checks the handshake signature** against the key the peer presented, so
  the peer does hold that key; what is skipped is only the question of whose key it is. The verifiers plug
  into `rustls`'s custom-verifier seam inside `nvs_host::tls`, so there is still one TLS client, a caller
  still cannot hand in a `ClientConfig` — it hands in a policy value the module builds one from — and
  `rule:security/one-tls-client`'s sentence about verification having no off switch becomes: strict by
  default, relaxed only for a host a grant names.
- **`tlsMinVersion: "1.3"` needs no grant**, because it can only tighten; a value below
  `[http.client.tls] min_version` throws.
- A call naming any of these five options builds its own `ClientConfig`, released with the call; a call
  naming none keeps the process's shared one. The policy is part of § 6's pool key.
- **The boot prints every relaxed grant, every start**, one line per grant and host, as goal
  `outbound-proxy` does for its own weakening. A weakening nobody is reminded of is a weakening that
  outlives the incident it was added for.

### 12. An address may be named under a grant, and an `https` hop never becomes plaintext

**`connectTo: string`**, under a new `net.connect_to` grant listing hosts. The value is an IP literal, and
the call connects there instead of resolving the URL's host, while the certificate is still checked
against that host. The address is judged by `rule:security/net-address-policy` and `net.internal` exactly
as a resolved one is, so the option chooses among addresses the deployment already allows and widens
nothing — it is `curl --resolve` with the address policy still underneath. A `Core\Http\Target` already
carries its approved set, so `connectTo` beside one is a `LogicError` rather than a silent override.

**A redirect from `https` to `http` is refused** unless its target host is in a new `net.downgrade` grant
*and* the call says `redirectToHttp: true`. Today every hop may be `http`, so a server can strip a call's
TLS with one `Location` header, and the caller sees a `200`. A plain `http` URL asked for **directly**
stays allowed — a program fetching an internal `http` endpoint is not being attacked by itself — and the
refusal names the grant. Two conditions rather than one for § 11's reason: the deployment says where, the
call says here.

### 13. A reply reports its TLS session, from the parser already in the lock file

**`Response::tls(): ?Core\Http\TlsInfo`**, read through members as every `Core` instance is: `version()`,
`cipher()`, `verified(): bool` — `true` only when the chain and the name were both checked, against
`roots` or `tlsCa` — `peerChain(): array<tainted string>` as PEM, and the leaf's `subject(): tainted
string`, `issuer(): tainted string` and `expiry(): Time\Instant`. `null` for a plain `http` reply and for
a reply the table answered, since neither had a session.

`verified()` is the member this exists for. A deployment that granted `tls.insecure` for one partner host
needs a way to assert, in a test and in production telemetry, that every *other* call still verified —
and without it the grant is unobservable from inside the language.

The leaf's three facts come from **`x509-parser`, which is already in the lock file** through `rcgen`'s
dev graph; this promotes it to an ordinary dependency of `nvs-host`. It is pure Rust and links no C, so
`rule:packaging/a-c-dependency-answers-two-questions` has nothing to answer, and the alternative is
handing a program PEM alone and expecting it to write an ASN.1 parser in Novis to learn when a
certificate expires — which is the check an operator most wants a program to make.

### 14. A name is resolved off the core, and every address it answers is checked

**The lookup leaves the core.** `rule:http-server/a-core-is-never-blocked-on-a-syscall` already sends name
resolution to the blocking pool; `nvs-runtime`'s capability door put that off until this client ran over
the parking stream, and it does. `nvs-runtime` cannot reach `nvs_host` — its manifest names `nvs-config`
and `nvs-render` — so the order is: the grant is asked on the core before any lookup, the lookup runs
through `nvs_host::blocking::run` as `Core\Process` already does, and the address check runs back on the
core. `Core\Net` and `Core\Db::open` pass the same door and move with it. If a caller-supplied resolver
will not fit the door's signature, the fallback is a resolver `nvs-host` installs into `nvs-runtime` once
at boot.

**Every address is checked, and one denied refuses the host.** A name answering both a public address and
one the address policy denies is what a rebinding attack looks like from the resolver's side, so the whole
host is refused naming that address rather than the denied answer being quietly dropped from the set.
`net.internal`'s exceptions apply per address exactly as today. An IP literal and a `connectTo` value are
a set of one.

**`Core\Http\Target` carries the approved set**, in the resolver's order, at most eight of it, and still
has no members — a program that could read the set back out could rebuild a request around one member of
it, which is `rule:http-server/allow-url-pins-the-address`'s reason for the `Target` existing at all. A
retry reuses the set and never re-resolves, so a retried call still performs exactly one resolution; a
redirect hop resolves and checks anew.

**The connection falls back across the set, RFC 8305's way**: families interleaved from the resolver's
first answer, the next attempt started when the previous has not connected within an attempt delay of
`250ms` — RFC 8305's own recommendation, and a constant rather than a directive because it trades against
nothing an operator can see — the first to connect kept and the rest closed, all under the one
`connectTimeout` clamped by the deadline, so no new bound is introduced. If the parking stream cannot hold
two connects in flight, the fallback is sequential in the same order and under the same bound. Every
address failing is one `IOError` naming each, because an error naming only the last address sends the
reader to the wrong host. A pooled connection to any address of the set may serve the call, since each
was approved.

### 15. An outbound call is an `http` trace event, and the reply carries no timing member

**A fifth trace kind, `http`**, filed once per call from the transport's own routine — which is rare and
already slow, which is `rule:observability/trace-events-carry-a-kind`'s own reason for filing the other
three where it does. It is the event `rule:observability/four-kinds-become-a-span` already derives the
outbound span from, and a retried call is **one** event carrying its attempt count, as that rule says.

Its fields are fixed, `crates/nvs-db/src/span.rs` being the precedent for a kind's field set being fixed
at all: the method; the scheme, host and port; the path without its query; the status; the attempt count
and the redirect hops; the address connected to; and the time spent resolving, connecting, in the
handshake, to the first byte and in total — curl's `-w` timings, with one home. Never a query string, a
header value or a body, because a trace is a `secret` sink.

**No timing member on `Core\Http\Response`.** A program that wants the numbers reads the trace. A second
surface for one measurement is the copy that disagrees, and a `Response::timings()` would also have to
answer something for a reply the table answered, where no time was spent on anything. A call the table
answered files no `http` event at all: nothing crossed a network.

### 16. The directives, and the numbers they ship

`[http.client]` gains four keys beside `connect_timeout`, `deadline` and `max_redirects`:

| Directive | Ships | Class | Bounds |
|---|---|---|---|
| `idle` | `30s` | `Runtime` | the longest silence allowed on a streamed body |
| `max_duration` | `5m` | `Runtime` | the longest a streamed body may take |
| `pool_idle` | `16` | `System` | idle connections held per core |
| `pool_idle_timeout` | `30s` | `System` | how long one may sit idle before it is closed |

The first two are `Runtime` for the reason `deadline` is ([0074](0074.md) § 5): they bound one call, a
request may want a longer stream than the default, and the change dies with the request. The pool's two
are `System` because they bound a **core's** memory rather than a request's, and a request widening a
bound on memory it shares with every co-resident request is
`rule:config/ceilings-are-their-own-directives`'s failure. None of the four has an unbounded spelling.

The numbers: `30s` of silence is longer than any SSE heartbeat interval in common use and short enough
that a dead server is noticed inside one request's patience; `5m` bounds a stream a program did not
bound itself, and a long-lived consumer names its own `maxDuration`; `16` idle connections per core is
enough for a handful of upstream APIs without a per-core footprint worth writing about, and
`pool_idle_timeout` at `30s` sits under the idle timeout of every common proxy and load balancer — nginx
at `75s`, ALB at `60s` — so this client is normally the side that closes, which is the side that cannot
lose a request to the race.

### 17. What it spends

Per call: a request body built once and charged to the request; a file part — a multipart one or the whole
`body` — streamed at one chunk; a buffered reply under `REPLY_CEILING` or a streamed one at one chunk plus
§ 5's line and event caps; a streamed compressed reply its decoder's window, 32 KiB for gzip and at most
8 MiB for zstd or 16 MiB for brotli, charged to the request and released with the stream. A `Target` holds
at most eight addresses; a falling-back call holds at most one socket per address until one connects; a
lookup holds one blocking-pool job under that pool's own bound. Per call naming a § 11 option, one
`ClientConfig` — parsed anchors or a verifier — released with the call, so O(in-flight). Per core, at most
`pool_idle` idle connections, a socket and a TLS session each, held between requests and charged to the
core: O(cores × `pool_idle`), never O(requests served). Per process, the `roots` files, parsed once at
boot beside or in place of the bundled set.

## Diagnostics

Compile-time, all of it in `crates/nvs-types/src/expr/args.rs` beside the check that already refuses a
keyless retry: two body keys, a body on `get` or `head`, `contentType` without `body`, and `idle` or
`maxDuration` on a buffered member, each naming the key. A `jsonAs<T>` whose `T` does not carry `tainted`
is `rule:security/derived-codec-qualifiers`' existing diagnostic naming the field.

Before the first attempt, for a verb chosen at run time: a body on `Get` or `Head`, and a `Post` or
`Patch` retried without a key. Both `LogicError`, because the program asked for something it cannot have
rather than meeting something the world did.

At boot: a `roots` file that does not resolve or does not pass the trust check, a `min_version` below
`1.2`, and `keylog` in `production`, each naming the key.

At runtime the split is the standing one. A `LogicError` is the program's mistake and names what it
wanted: an unmatched URL in a test, a second read of a stream, `set-cookie` through `header`, `connectTo`
beside a `Target`, an identity whose leaf does not match its key, a relaxing option whose host no grant
lists. A `RuntimeError` is a verdict on what arrived and is one sentence: a `Content-Encoding` the request
did not offer, a zstd window past the ceiling, a decompression bound reached, a redirect to plaintext. A
timeout is `TimeoutError` and an exhausted address set is one `IOError` naming each address, unchanged in
class from what the transport throws today.

## Consequences

**For a program.** The client is now the thing an API is driven through, and the shapes are the ones a
PHP developer already knows from `curl_setopt` — with the array of 200 constants replaced by one bag the
compiler checks. What is deliberately harder than in `curl`: relaxing verification takes a deployment
edit as well as a call, and there is no `-k` that only touches code.

**For the runtime.** Four new bounds, all finite; two new configuration blocks; one dependency promoted
out of the dev graph; and a second and third place where `nvs_host::tls` is constructed, which is why the
policy value rather than the config object is what crosses that boundary. The pool is the one piece of
per-core state a request now inherits from the request before it, and § 6's framing condition is the whole
of what keeps that safe.

**For the rulebook.** Eleven rules created, five edited. Three sentences on disk stop being true and are
rewritten by the stages that make them false rather than left to a later sweep: the module doc's list of
what is not here yet, the transport's *a pool is a later slice*, and the TLS module's *a program choosing
anchors is closed permanently*.

**What is still missing after this.** HTTP/2, which would change the pool's shape and nothing else here;
a cookie jar; a resolver of Novis's own; and every protocol convenience the `nvs/rest` package exists to
hold — `Link` pagination, problem details, OAuth's own flows.

## Alternatives rejected

**A `Core\Http\Request` class.** Two places a call is described, and a body that can disagree with the
bag. `request(Method, …)` needs one member.

**A single `body` key with sniffing.** An `array<string, string>` cannot be told apart from a form by
looking at it, and the alternative is a mode string `rule:core-api/no-mode-strings` refuses.

**A process-wide or cross-core connection pool.** A lock on the request path, and a bound that is
O(process) rather than per core, which is the accounting `rule:security/db-pool-reset-is-a-boundary`
already refused for the database.

**A pool keyed on the URL's host.** The common implementation, and it undoes the pin: two names behind one
address, or one name whose approved address changed between calls, would share a connection that only one
of them had approved.

**`tls.insecure = true` as a boolean grant.** One line nobody reads again. The host list is the same
mechanism `net.internal` already uses, for the same reason.

**One `idle` bound instead of `idle` and `maxDuration`.** A server dribbling one byte per second passes
every idle check and never ends.

**A `timings()` member on the reply.** A second home for one measurement, and nothing to answer for a
faked reply.

**Keeping one pinned address.** A single point of failure for a name that answers four, with no security
gained: the security is in checking all of them, not in discarding all but one.

## Revisiting

Two triggers. **HTTP/2** changes what a pooled connection is — many calls in flight on one socket — so § 6
is re-derived when it lands, though its key does not change. And **`min_version`**: `1.2` ships because
endpoints that speak nothing else are still common; when that stops being true the shipped floor moves to
`1.3`, which is a one-line change to a `System` directive and a line in this record's § 10 that is then
history rather than rule.

## Verification

Stage by stage, as goal `http-client` walks them. § 1's table is proved first and everything above the
socket is proved through it: bodies and verbs, the reply's members, the streams, the credential drop on a
cross-origin hop, the compile-time refusals. Below the table, against a loopback origin in Rust: the pool
and its framing condition, the content codings and the window bound, the `https` end-to-end path under a
`roots` file with an `rcgen` certificate, each relaxing option with and without its grant, the downgrade
refusal, `connectTo`, the address-set fallback with one denied address, and the `http` trace event's
fields. `crates/nvs-config/tests/tree.rs` holds the two blocks, their classes and the three boot
refusals. The rules created here are `designed` until their guards exist, and goal `http-client`'s last
stage flips them to `shipped` with `guardedBy` filled from exactly these cases.
