# ADR 0179 — Novis reads what a browser encrypts and what an issuer signs, over a closed algorithm roster and one streamlined `Core\Crypto`

- **Scope:** which cryptographic primitives `Core\Crypto` exposes and in what shape; the closed roster of
  algorithms the language will implement; the JWE and JWS subsets `Core\Jwe` and `Core\Jwt` speak; and
  the dependency set all of it rests on. Not in scope: fetching, caching or discovering a key set, which
  `rule:security/protocol-admission-test` puts outside `Core`; the `nvs/rest` package built over this.
- **Depends on:** [0051](0051.md) for the tier the class already sits at, [0060](0060.md) for the
  roster and for the algorithm coming from the key, [0033](0033.md) for the `secret` qualifier,
  [0146](0146.md) for the payload-canonicalization half of the roster.
- **Validated by:** `tools/webcrypto-vectors.mjs`'s frozen set, which is WebCrypto's own output for
  every algorithm here, and the conformance cases each stage of goal `webcrypto` adds beside it.

> **In short:** a Novis program has to be able to open what a browser sealed and verify what an identity
> provider signed, and today it can do neither. This adds the primitives that make those two things
> possible — AES-256-GCM beside XChaCha20-Poly1305, PBKDF2 and HKDF, ECDH over P-256 and X25519, and
> RSASSA-PKCS1-v1_5, RSASSA-PSS, ECDSA-P-256 and Ed25519 for signatures — and the two JOSE subsets
> `Core\Jwe` and `Core\Jwt` need to carry them. **The roster is closed and the surface is streamlined:**
> one member per job, a required `Crypto\Cipher` enum where two algorithms take the same parameters, and
> **no algorithm argument anywhere has a default**. The failure class every line of this is written
> against is the one [0060](0060.md) already named — an algorithm chosen by an attacker-supplied string —
> so `alg` is read only to be *compared*, and a key's own type is what selects the operation.

## Context

`Core\Crypto` is three members over one construction: `generateKey`, `seal` and `open`, all
XChaCha20-Poly1305, with no cipher argument at all ([`crypto.rs`](../../crates/nvs-stdlib/src/crypto.rs)'s
module doc argues why a cipher is not a string). That is the right surface for a program talking to
itself, and it is the whole surface, which means a Novis program cannot do any of the following: open a
blob a browser's `crypto.subtle.encrypt` produced, derive a key from a password the way the other end of
an already-agreed protocol derives it, agree a key with a peer, or verify a token an identity provider
signed with its own key. `Core\Jwt` speaks HS256 and nothing else, so every OpenID Connect ID token in
existence — all of which are RS256, PS256, ES256 or EdDSA — is unreadable.

Each of those is a *library* failure by `rule:security/protocol-admission-test`'s first condition: a
program that implements AES-GCM's nonce placement or PBES2's iteration bound in userland gets it wrong
silently, and the wrongness is in the implementation rather than in the call. So the answer is members,
not documentation. The question this record decides is which members, and — because the last twenty
years of cryptographic API failures are failures of *choice* rather than of arithmetic — what a caller
is allowed to choose.

## Investigation

**Two things about the type checker had to be asked before the surface could be written**, because the
goal's table spelled two parameters as unions carrying `secret` members and nothing in the tree does
that today. Both were checked against the code rather than assumed.

**A union may carry a `secret bytes` arm, and it works.** `CoreTy::SecretBlob` is one of the two
spellings that intern as a *qualified atom* rather than as their unclassified base
(`crates/nvs-types/src/core_lib.rs:430`), `CoreTy::Union` lowers member-wise into
`interner.make_union` (`core_lib.rs:548-554`), and a union target is satisfied by membership in
`is_assignable` (`crates/nvs-types/src/expr/assign.rs:103-117`). So `secret bytes|Crypto\KeyPair` on
`Jwt::sign`'s key is an ordinary row and needs nothing new. One constraint rides with it: each secret
arm must be written `CoreTy::SecretBlob(Qual)` and never the bare `CoreTy::SecretBytes`, because the
registry's unclassified-parameter audit walks union members and treats the bare spelling as
unclassified (`crates/nvs-stdlib/src/registry.rs:3799-3806`).

**A union may not carry a `secret string` arm, because no such type exists to carry.** `CoreTy`'s atom
list has `secret bytes`, `tainted string`, `tainted bytes` and `secret tainted string` and no plain
`secret string` (`registry.rs:1100-1105`). The only way a row accepts a `secret string` argument today
is a `Qual::Reveal` *mark* on an ordinary `string` parameter, which is what `Core\Password::hash`
writes (`crates/nvs-stdlib/src/password.rs:208`) — and a mark is refused twice over inside a union.
`qual_of` answers `None` for a `CoreTy::Union`, and `core_lib.rs:405-411` states outright that "a union
can never be given an *accepting* mark without widening this function"; and `Qual::Reveal`'s roster is
closed to `Core\Secret` and `Core\Password`, held by `nvs-types`'
`reveal_and_the_password_helpers_are_the_only_launderers_of_secret` (`registry.rs:199-210`).
`Core\Jwe` may not write one at all.

**So JWE's key takes the fallback, for a reason narrower than the one it was written against.** § 6
below records the shape. The union was never impossible; the *password* arm was, and that arm is
exactly the one the union existed to tell apart from a shared key.

**The structured-claims question was settled by the same reading.** A `CoreTy::Shape` may never be a
member of a union (`registry.rs:702-707`, held by `a_shape_is_only_ever_a_whole_parameter`), and there
is no `object` spelling in `CoreTy` at all — so `array<string>|object` is not a row anyone can write.
The only member that would admit both a shape literal and a deriving-class instance is `CoreTy::Mixed`,
which admits an `int` as well and would have taken today's `array<string>` claims out of the checker's
hands. § 7 therefore makes it a second member.

## Decision

### 1. One member per job, and a required enum where the parameters are the same

Where two algorithms take the same parameters they are one member with a **closed enum argument**, the
way `Core\Hash::of` takes a `Core\Digest`. Where the parameters differ they are separate members. **No
member name carries an algorithm** (`rule:core-api/verb-lexicon`), and no algorithm is ever a string:
there is no `Crypto::aesEncrypt` and no `Crypto::seal($m, $k, "aes-256-gcm")`.

**No algorithm argument has a default — not a cipher, not a digest, not a curve.** A call names what it
uses. `Core\Hash` already holds this, every row `defaults: &[]`
(`crates/nvs-stdlib/src/hash.rs:304-343`), and nothing about it changes. A default is how a call site
that was copied from another file in another year silently keeps an algorithm nobody re-read; making
the argument required costs one enum case at each call and buys a `grep` that finds every use of a
primitive when it has to be retired.

The one member that answers a key with no algorithm in it takes no algorithm argument at all, and that
is `generateKey()`: its 32 octets are the single key length both ciphers and every roster protocol
share, and one ring of them already reaches `Core\Signature` and `Core\SignedCookie` alike
(`crates/nvs-stdlib/src/signature.rs:48-73`). Parameterizing it would invent a choice whose only wrong
answers are shorter ones.

### 2. The roster, closed

**In:** AES-256-GCM; PBKDF2-HMAC-SHA256; HKDF-SHA256; ECDH over P-256 and X25519; and four signature
algorithms — RSASSA-PKCS1-v1_5 and RSASSA-PSS over SHA-256, ECDSA over P-256, and Ed25519. XChaCha20-Poly1305
stays exactly as it is.

**Internal only, never a member:** AES Key Wrap, which PBES2 needs, and the Concat KDF, which ECDH-ES
needs. Both are protocol plumbing with no standalone use that is not a mistake.

**Out, and not to be added by any session of this goal:** AES-CBC, AES-CTR, AES-128, RSA encryption in
every form (RSA-OAEP and RSA1_5 alike), RSA key *generation*, P-384 and ES384, RS384, RS512, PS384,
PS512, ES256K, and JWE's `A*CBC-HS*` content encryption. The list is written down rather than left
implicit because a closed roster that is only a habit reopens at the first ticket, and each of these has
a standing request behind it somewhere. Unauthenticated and legacy modes are out by
`rule:core-api/tier-roster`'s existing "AEAD only, no ECB, no unauthenticated CBC"; the size variants
are out because two of everything doubles the surface for no property a program can name; and RSA
encryption is out because RSA1_5 is a padding-oracle machine and RSA-OAEP buys nothing ECDH-ES does not
buy at a fraction of the key size.

**AES-256-GCM is in for one reason and it is sufficient:** it is what `crypto.subtle` gives a browser,
so it is what a Novis server must read. `crypto.rs`'s module doc argues XChaCha20-Poly1305 over AES-GCM
and that argument is unchanged and unretracted — this adds the second cipher for interoperability,
not because the first one stopped being the right default.

### 3. `Core\Crypto`'s surface

| Member | Does |
|---|---|
| `Crypto::generateKey(): secret bytes` | 32 random octets, a key for either cipher and for every roster protocol |
| `Crypto::seal(bytes $message, secret bytes $key, Crypto\Cipher $cipher): bytes` | `nonce ‖ ciphertext ‖ tag` |
| `Crypto::open(bytes $sealed, secret bytes $key, Crypto\Cipher $cipher): bytes` | the plaintext, or one forgery `RuntimeError` |
| `Crypto::deriveKey(secret string $password, bytes $salt, uint $iterations): secret bytes` | PBKDF2-HMAC-SHA256, 32 octets |
| `Crypto::expandKey(secret bytes $material, bytes $salt, string $info): secret bytes` | HKDF-SHA256, 32 octets |
| `Crypto::generateKeyPair(Crypto\KeyKind $kind): Crypto\KeyPair` | P-256, X25519 or Ed25519; never RSA |
| `Crypto::agree(Crypto\KeyPair $mine, Crypto\PublicKey $theirs): secret bytes` | the raw shared secret, meant for `expandKey` |
| `Crypto::sign(bytes $message, Crypto\KeyPair $key): bytes` | the signature, its scheme the pair's kind |
| `Crypto::verify(bytes $message, bytes $signature, Crypto\PublicKey $key): void` | nothing, or one `RuntimeError` |
| `Crypto\PublicKey::read(bytes $encoded, Crypto\KeyKind $kind, Crypto\KeyFormat $format)` | raw, SPKI or JWK, validated on read |
| `$publicKey->write(Crypto\KeyFormat $format): bytes` | the same three forms |
| `$publicKey->kind(): Crypto\KeyKind` | which kind it is |
| `Crypto\KeyPair::read(secret bytes $pkcs8, Crypto\KeyKind $kind): Crypto\KeyPair` | a stored pair back, DER or PEM |
| `$keyPair->write(): secret bytes` | PKCS#8, so a server keeps its pair across requests |
| `$keyPair->publicKey(): Crypto\PublicKey` | the half that is sent |

`Crypto\Cipher` is `XChaCha20Poly1305` and `Aes256Gcm`. `Crypto\KeyKind` is `P256`, `X25519`,
`Ed25519`, `RsaPkcs1` and `RsaPss`. `Crypto\KeyFormat` is `Raw`, `Spki` and `Jwk`.

`deriveKey`'s password is a `Qual::Reveal` parameter, which is the mark `Core\Password::hash` already
writes for the identical value; the Investigation section is why that is a mark rather than a type, and
§ 6 is what follows from it when the same value has to sit in a union.

**Existing call sites move with the signature, in the same commit.** Nothing has shipped publicly, so
`seal` and `open` gain their required third argument and every caller is corrected alongside. A case's
*source* is corrected, never its expected output, and a case is renamed only where its name has become
false. What does not move: XChaCha20-Poly1305 and its sealed layout, `generateKey()`, every
`Core\Digest` case and every `Core\Hash` signature, `Core\Password`, and
[`signed_cookie.rs`](../../crates/nvs-stdlib/src/signed_cookie.rs)'s use of the construction.

### 3a. AES-GCM's sealed bytes are `nonce(12) ‖ ciphertext ‖ tag(16)`

That is exactly what WebCrypto's `encrypt` answers with its IV put in front, so a browser splits at byte
12 and does nothing else; XChaCha's stay `nonce(24) ‖ ciphertext ‖ tag(16)`. Any other framing would
make the one member that exists for interoperability require a userland shim on the other side, which
is the whole failure this is here to remove.

The nonce is random and drawn through `crate::random::draw`, and **there is no nonce parameter**, for
`crypto.rs`'s standing reason. AES-GCM's 96-bit nonce therefore carries the birthday bound that module
doc already states — a repeat is catastrophic rather than degrading, and at random 96-bit nonces the
collision is reachable around 2^32 messages under one key. `seal`'s reference card and this record both
say so, and both name XChaCha20-Poly1305 as the answer when a program's own volume approaches it. That
bound is the cost of reading what a browser wrote; it is not a reason to make the caller keep a counter,
which is a worse failure with a wider blast radius.

**Opening under the wrong cipher is a forgery, never plausible bytes** — both constructions authenticate
before they decrypt, so a mismatched `Crypto\Cipher` lands on the one `RuntimeError` sentence that every
other way of not being authentic lands on. No additional-data parameter in this goal; JWE uses AAD
internally, where the protocol fixes what it is.

### 4. Keys are validated where they are read, and a private key leaves only as PKCS#8

A symmetric key is `secret bytes`, length-checked, and the wrong length is a `LogicError` naming the
length wanted and never the bytes got (`crates/nvs-stdlib/src/crypto.rs:68-74`). A private key never
leaves a `Crypto\KeyPair` except as `secret bytes` through `write`.

**Every public key is validated at `read`**: on the curve for P-256, so the off-curve point, the point at
infinity and a short encoding are each refused there, and an all-zero X25519 shared secret is refused at
`agree`. Validating at `read` rather than at use is the same structural move as
`rule:security/algorithm-comes-from-the-key`: it removes the class of bug where one of five call sites
forgot the check, because there is no later site at which the check could be forgotten.

**A key off the wire that fails is a `RuntimeError`; a malformed key the program built is a
`LogicError`** — the roster's standing split between a verdict on a message and a bug in the program
(`rule:security/verification-throws-and-compares-in-constant-time`). Two keys on different curves handed
to `agree` is a `LogicError`. A JWK `read` accepts what a browser exports, `ext` and `key_ops` included,
and ignores them; **a JWK carrying `d` is refused**, because a private key handed over as a public one is
a bug rather than an attack. `write` answers RFC 7638's required members, sorted. JWK export of a private
key is out of scope.

**RSA and Ed25519 join on the same terms.** An RSA public key reads from SPKI or JWK — `Crypto\KeyFormat::Raw`
is a `LogicError`, there being no raw encoding of an RSA key — and one outside 2048–8192 bits is refused
at `read`. An RSA pair reads from PKCS#8 and **is never generated**: `generateKeyPair` refuses both RSA
kinds with a `LogicError` naming `Crypto\KeyPair::read`, because `ring` generates none and a program is
handed its RSA key by whoever issued it. **An RSA key's scheme is fixed when it is read** — `RsaPkcs1` or
`RsaPss` — which is `rule:security/algorithm-comes-from-the-key` held for the one key type that two JWS
algorithms share; without it, a key alone would not name an algorithm and the token would have to, which
is the confusion class that rule exists to close.

`Crypto\KeyPair::read` accepts PKCS#8 as DER or as one PEM `PRIVATE KEY` block for every kind, because a
service-account file carries exactly that, and refuses PKCS#1 and encrypted PKCS#8. An X25519 pair signs
nothing and an Ed25519 or RSA pair agrees nothing: each is a `LogicError`.

### 5. PBKDF2 has a floor and a ceiling, and both are checked before the first HMAC

The iteration count is a **required parameter**, because the other end of an already-agreed protocol
chose it and a default here would be a number that is either wrong or ignored. It is refused below
100,000 and above 2,000,000, and a salt shorter than 16 octets is refused.

**The ceiling is what makes PBES2 safe.** A JWE header's `p2c` is attacker-supplied, so without an upper
bound one token buys unbounded CPU on the request path — a denial of service with a two-byte payload.
PBES2's `p2s` and `p2c` are held to the same two bounds as the member, in the same code, rather than to a
second pair of numbers that could drift from these.

Both edges are in the frozen vector set as refusals, so **neither number moves without the user
regenerating the set**, which is what makes them a decision rather than a constant.

### 6. JWE: the compact subset, and the key is a `Jwe\Key`

Compact serialization only. `enc` is `A256GCM` and nothing else. **The algorithm comes from the key**
(`rule:security/algorithm-comes-from-the-key`): a shared key means `dir`, a password means
`PBES2-HS256+A128KW`, and a recipient's public key or the program's own pair means `ECDH-ES` — direct
agreement, no key wrap, empty `apu` and `apv`. The header's `alg` and `enc` are read **only to be
compared**, as [`jwt.rs:11-22`](../../crates/nvs-stdlib/src/jwt.rs) already does, and a mismatch is a refusal.

**The key is a `Jwe\Key`, built by one static per kind**, and this is the fallback the goal reserved:

```
Jwe\Key::shared(secret bytes $key): Jwe\Key          // dir
Jwe\Key::password(secret bytes $password): Jwe\Key   // PBES2-HS256+A128KW
Jwe\Key::recipient(Crypto\PublicKey $theirs): Jwe\Key // ECDH-ES, encrypting
Jwe\Key::own(Crypto\KeyPair $mine): Jwe\Key          // ECDH-ES, decrypting

Jwe::encrypt(string $payload, Jwe\Key $key): string
Jwe::decrypt(string $token, array<Jwe\Key> $keys): tainted string
```

The Investigation section is why: a shared key and a password are both confidential text-or-octets, the
`secret string` that would have told them apart has no type to be written as, and the mark that accepts
one is closed to two other classes and unavailable inside a union regardless. **Moving the distinction
from the argument's type to the static that built it loses nothing and is arguably the better surface** —
the algorithm still comes from the key rather than from the token, it now comes from a name the caller
wrote rather than from a type inference the caller cannot see, and `Jwe` stays at two members. The
password static takes `secret bytes`; a program holding a `secret string` password writes `as bytes`,
which carries the qualifier across by `rule:security/secret-propagation`.

**The allowed header parameters are `alg`, `enc`, `epk`, `p2s`, `p2c`, `kid`, `typ` and `cty`.** `zip`,
`crit`, `jku`, `x5u`, `x5c`, a `jwk` other than `epk`, and anything unknown are refused — `zip` is a
decompression bomb (`rule:core-classes/decompression-bound`), the URL-bearing ones are fetches a token
would be talking us into, and an unknown member in a *ciphertext* header is either an extension we do not
implement or an attack, with no third reading. The protected header is length-capped before it is parsed.

**`encrypt` writes its header canonically** — members sorted, no whitespace, at every level — which is
the form the vector set's tokens are in and what lets `encrypt` be held to them byte for byte rather
than only round-tripped against itself.

The payload is `string` in and **`tainted string`** out, exactly as `Core\Signature::verify`'s is
(`rule:security/verification-does-not-launder`): decrypting proves who wrote it, never that it is safe.
Every refusal is one `RuntimeError` with one sentence. Decrypt's key ring is tried in order, as
`Core\Signature::verify`'s is — **except that a ring containing a password key must hold exactly one
key**, because every try costs a full derivation and an attacker choosing the ring's length is § 5's
bound defeated one layer up.

### 7. JWS: `sign`, `signObject` and `verifyIssued`

Compact serialization only. **The algorithm comes from the key**: a shared key is HS256, and a pair or
public key of kind `P256`, `Ed25519`, `RsaPkcs1` or `RsaPss` is ES256, EdDSA, RS256 or PS256. The
header's `alg` is read only to be compared, as `jwt.rs:11-22` does today.

```
Jwt::sign(array<string> $claims, Duration $lifetime, secret bytes|Crypto\KeyPair $key,
          {kid?, typ?, embedKey?}): string
Jwt::signObject(object $claims, Duration $lifetime, Crypto\KeyPair $key,
                {kid?, typ?, embedKey?}): string
Jwt::verifyIssued<T>(string $token, Jwt\KeySet|Crypto\PublicKey $keys, string $issuer,
                     string $audience, {leeway?, typ?, nonce?, maxAge?}): T
Jwt\KeySet::read(tainted string $jwks, {rsaScheme?}): Jwt\KeySet
```

**Structured claims are a second member rather than a union arm**, which the Investigation section
settles on the checker's own terms — a shape may not be a union member and there is no `object` spelling
in `CoreTy`, so the only union that would have worked is one admitting an `int`. The split pays for
itself twice over: today's `array<string>` claims keep their element type instead of collapsing to
`mixed`, and `signObject`'s key parameter is a `Crypto\KeyPair` **alone**, which turns "structured claims
under a shared key" from a runtime `LogicError` into a type mismatch the compiler reports. A token this
program signs under a shared key therefore still carries only what `Jwt::verify` reads back. The name
carries the subject and not an algorithm, per `rule:core-api/verb-lexicon`.

**`sign` and `signObject` write their header canonically** — `{alg, jwk?, kid?, typ}`, sorted, no
whitespace, `typ` `JWT` unless the bag names another — and their payload in today's layout: the caller's
claims in order, then `iat`, then `exp` (`crates/nvs-stdlib/src/jwt.rs:364-425`). Under RS256 and EdDSA a
token is therefore reproducible byte for byte, which is what lets the frozen set hold them. `signObject`
writes its subject as `Core\Json::encode` writes it, with `iat` and `exp` appended in that order; `iat`
or `exp` among the fields is a `LogicError`, as it is on `sign` today, and a `secret` field is refused
exactly as `encode` refuses one. `embedKey` writes the pair's public half as RFC 7638's minimal JWK
under `jwk`, which is what a DPoP proof carries, and is a `LogicError` under a shared key. `exp` stays
mandatory on everything either member writes (`rule:security/jwt-expiry-is-mandatory`).

**`verifyIssued` refuses a header carrying `jku`, `x5u`, `x5c`, `jwk`, `crit`, `b64`, `zip` or `cty`** —
a key or a fetch the token brings with it, an extension, an unencoded or compressed payload, a nested
token — and **ignores every other member it does not read**. That is deliberately looser than § 6's JWE
policy: an issuer sends hints such as `x5t`, and a verifier refusing them refuses real ID tokens. The
asymmetry is the point — a JWE header we refuse is one *we* would have had to act on, while a JWS header
member we ignore cannot select anything, the key having already decided the algorithm. The token is
length-capped before it is parsed.

**A key is found, never tried.** `kid` is a lookup into the set and selects nothing else; a token with no
`kid` verifies only against a set holding exactly one key. There is no try-every-key loop, so a token
costs at most one signature check no matter how large the set is — which is the same bound § 5's ceiling
buys one protocol over, and for the same reason.

**The clock.** `exp` is required and `nbf` is checked when present, both under `leeway`: a `Duration`,
`60s` when omitted, and a `LogicError` when negative or **above `5m`**. A token is accepted while
`now < exp + leeway` and `now ≥ nbf − leeway`. The ceiling is there because a leeway large enough to
matter is an expiry policy the caller did not mean to write.

**The claims.** `iss` equals `$issuer`. `aud` is `$audience` or a list holding it, and a list of more
than one **requires `azp` equal to `$audience`**, which is OpenID Connect's own rule and the one that
stops a token minted for another client being replayed at this one. A `nonce` asked for is compared in
constant time and an absent one is refused. `typ` is compared case-insensitively with any `application/`
prefix removed. `maxAge` requires an `auth_time` no older than `maxAge + leeway`.

**The order, and what each refusal says:** shape, header policy, key, signature — then the clock and the
claims, which are reached only under a signature that held. Policy and authenticity are the one
`RuntimeError` sentence. Expiry keeps its own message for the reason `jwt.rs:57-64` gives — only the
holder of a genuinely signed token ever sees it — and a claims refusal names the claim, safe for exactly
the same reason.

**`Jwt\KeySet::read`** *skips* a key marked `use: enc` and a key whose `alg` or kind is outside the
roster, because a real JWKS document carries keys for purposes we do not serve and refusing the set over
one of them would make every rotation an outage. It **refuses the whole set** for a private member (`d`,
`p`, `q`, `dp`, `dq`, `qi`, `k`), an RSA key under 2048 bits, two keys under one `kid`, an `alg` its kind
cannot carry, a document that is not JSON, more than **16** keys, and an RSA key carrying no `alg` when
no `rsaScheme` was named. The split is between a key we have no use for and a document that is wrong:
the first is ordinary, the second means the program is pointed at something it should not trust.
`rsaScheme` is `RsaPkcs1` or `RsaPss` and reaches only an RSA key carrying no `alg`; a key's own `alg`
always wins.

**Fetching, caching and discovery are not `Core`.** `rule:security/protocol-admission-test` puts the flow
in a package, and every member here is stateless over a key it is handed. `Core` caches no key set.

### 7a. Claims arrive as a shape, not as flattened text

`verifyIssued<T>`'s `T` is held to `rule:security/derived-codec-qualifiers` at the call site, exactly as
`Core\Request::jsonAs<T>`'s is: an inline shape must be `tainted {…}`, a class must declare `tainted` on
every text field reachable from it, and anything else is a compile-time diagnostic naming the field. That
is how `rule:security/verification-does-not-launder` is kept here — **by the type rather than by
flattening every claim to text**, which is the widening `jwt.rs`'s own module doc already names as the
way out of its `array<tainted string>` answer. The registered claims are checked before `T` is decoded,
and `T` may declare them in order to read them.

`Jwt::verify` is untouched: it keeps its `array<tainted string>` answer and its refusal of structured
claims. Nothing about a token this program signs for itself changes.

### 8. Dependencies: pure Rust on the locked generation, and `ring` for signatures only

`aes-gcm` 0.11 (bringing `aes` 0.9), `aes-kw` 0.3, `p256` 0.14 with its `ecdh` feature, `x25519-dalek`
3.0, `hkdf` 0.13, and `pbkdf2` 0.13 as a direct dependency. Default features off, and **no `getrandom`
anywhere**: randomness reaches all of them through an adapter over `crate::random::draw`, so the runtime
keeps one entropy source. **No new C crypto crate** — [`deny.toml:70-73`](../../deny.toml) bans OpenSSL and
`aws-lc-rs` stays off.

**`p256`'s curve arithmetic has never been independently audited**, which its own README says, and this
record accepts that rather than eliding it. P-256 is the one curve every browser's WebCrypto has, so
there is no version of this goal that omits it; the crate is written constant-time, and the alternative
on offer is a C library the dependency rules already refuse. It is a real cost and it is priced here so
that a future reader does not have to rediscover it.

**`ring` is the one exception, and it is not new**: it is already linked as TLS's provider
([`Cargo.toml:215-236`](../../Cargo.toml)), and this adds it to `nvs-stdlib` directly, at the version the
lockfile already resolves, for the four signature algorithms and nothing else. Every AEAD, KDF and key
agreement stays RustCrypto. `rule:packaging/a-c-dependency-answers-two-questions`'s recorded answer for
`ring` widens from TLS to JWS on the same two questions and needs no new one: attacker bytes reach a
token verifier by construction exactly as they reach a TLS handshake, and BoringSSL's review record is
the same record either way. PEM is read with what the graph already carries
([`crates/nvs-host/src/tls.rs:121`](../../crates/nvs-host/src/tls.rs)).

Each added crate regenerates `THIRD-PARTY-LICENSES.txt` in the same commit
(`rule:packaging/the-third-party-notice-is-generated-never-written-by-hand`). If a pinned version will
not build against the locked base, the nearest one that does is taken and the commit says so.

### 9. The interop proof is WebCrypto's own output, frozen

`tools/webcrypto-vectors.mjs` writes the vector set from Node's `crypto.subtle` — the W3C API a browser
ships — with **every input derived from a label**, so a rerun writes the same bytes and `--check` says
whether the file on disk is current. The script reproduces RFC 7518 Appendix C's Concat KDF output
before it writes anything, and its JWE tokens were opened by `jose`, an independent JOSE
implementation, when the set was made. Node is needed only to regenerate the set, which the user fires;
no check and no session runs the script.

The set's `jws` section is the same proof for signatures: WebCrypto signed every token, its RSA keys are
built from label-derived primes because WebCrypto derives none from a seed, and an ES256 or PS256
signature — randomized by its own algorithm — is kept from the file on disk while it still verifies, so
a rerun still writes the same bytes. The script's `referee` judges every JWS vector and every refusal
against § 7 before the file is written.

**This is what makes "interoperable" a checkable claim rather than an intention.** A test suite we wrote
against an implementation we wrote proves that our encoder and our decoder agree; only the other side's
own output proves the thing the goal exists for.

## Diagnostics

Compile-time, all of them existing machinery rather than new checks: a missing `Crypto\Cipher`,
`Crypto\KeyKind` or `Crypto\KeyFormat` argument is an ordinary arity diagnostic, since no row carries a
default; a `Jwt::signObject` call under a shared key is an ordinary type mismatch, the parameter being a
`Crypto\KeyPair`; and a `verifyIssued<T>` whose `T` does not carry `tainted` is
`rule:security/derived-codec-qualifiers`' diagnostic naming the field, which `Core\Request::jsonAs`
already emits.

At runtime the split is the roster's standing one: a verdict on bytes that arrived from somewhere is a
`RuntimeError` with one sentence, and a bug in the program is a `LogicError` that names what it wanted.
§ 4 and § 5 list which is which for every refusal here.

## Consequences

**What it spends.** Per call: a few hundred bytes of cipher or curve state on the stack, and one output
buffer charged to the request through `nvs_runtime::budget` and passed through `nvs_runtime::affordable`
first, exactly as `seal` is today. A `Crypto\KeyPair` holds its private scalar for as long as the program
holds the object, and a `Jwt\KeySet` holds its public keys the same way, capped at 16. PBKDF2 is bounded
in CPU by § 5's ceiling, and `verifyIssued` is at most one signature check per token — RSA verification
being the dearest, held to one by the key-count cap and the no-try rule. **Nothing is held between
calls, so all of it is O(in-flight).**

**Surface.** `Core\Crypto` goes from three members to fifteen across three types, plus `Core\Jwe` and two
members on `Core\Jwt`. That is a real charge against priority 4, and it is paid deliberately: the
alternative to a member is userland code for the same protocol, which fails silently and is the first
condition of `rule:security/protocol-admission-test`.

**Latency.** Nothing on the existing request path changes. A `seal` or `open` call gains an enum argument
the compiler resolves, and the sealed layout of an XChaCha message is byte-identical to today's.

**Migration.** `seal` and `open` change signature, so every existing call site and conformance case moves
in the same commit. Nothing has shipped publicly, so there is no external cost.

**What this does not do:** JWK export of private keys, an additional-data parameter, streaming
encryption, the JWS JSON serialization, a detached or unencoded JWS payload, JWE-encrypted ID tokens and
RSA-OAEP with them — skipped as rare and opt-in at every provider — fetching or caching a key set, and
structured claims under a shared key.

## Alternatives rejected

**A `string` algorithm argument, or a `Crypto\Algorithm` enum spanning every primitive.** One member
taking any algorithm is the shape `openssl_encrypt` has, and it is how a program ends up with
`aes-256-ecb` in one file. An enum is safer than a string but still lets `seal` be handed a signature
algorithm; separate members where the parameters differ makes that unrepresentable.

**Defaulting the cipher to XChaCha20-Poly1305.** Tempting, because it is the one to prefer when both ends
are Novis, and it would have left every existing call site untouched. Rejected because a default is
invisible at the call site, and the call sites that matter here are the interoperating ones, where the
cipher is not ours to choose. The advice stays in `seal`'s reference card, where a reader meets it while
writing the argument.

**A `secret bytes|Crypto\PublicKey|secret string` union on `Jwe`'s key.** The surface the goal drafted,
and the Investigation section is why it cannot be written. It is worth recording that the *type* system
was not the obstacle it looked like — `secret bytes` unions fine — so `Jwt::sign`'s key keeps its union
and only JWE's, which needs the password arm, takes a named constructor.

**Widening `Qual::Reveal`'s roster to admit `Core\Jwe`.** It would have made the union writable, and it
is rejected outright: the roster being two classes long is what makes a reveal greppable, it is checked
by a test, and spending `rule:core-classes/secret-reveal` to save one static method is the wrong side of
every priority in `AGENTS.md`.

**RSA-OAEP for JWE, so a program can talk to an issuer that encrypts ID tokens.** Rejected with the
user's agreement as rare and opt-in at every provider, and it would have brought RSA encryption's whole
padding surface in for one feature almost nobody turns on. ECDH-ES covers the public-key case at a
fraction of the key size.

**Trying every key in a `Jwt\KeySet`.** It would have let a token without a `kid` verify against a large
set. Rejected because it makes verification cost linear in a number the token's sender influences, which
is a denial of service dressed as a convenience; requiring a single-key set for a token with no `kid` is
the same guarantee without the loop.

## Revisiting

Two triggers, and nothing else here is expected to move. **If `p256` is independently audited, or if a
Rust P-256 implementation that has been becomes the obvious one**, § 8's accepted cost should be
re-read. **If a `secret string` atom is added to `CoreTy`** for some other member's sake, § 6's
`Jwe\Key` becomes optional — though the named constructors are the better surface on their own merits
and would not be worth unwinding for that reason alone.

## Verification

The frozen set in § 9 is the primary gate: every AEAD, KDF, agreement and signature here reproduces
WebCrypto's own bytes, and every refusal in § 4 through § 7 has a vector that must be refused. Beyond
it: conformance cases per member; the PBKDF2 floor and ceiling refused at each edge; a P-256 off-curve
point, the point at infinity and a short encoding each refused at `read`; an all-zero X25519 shared
secret refused at `agree`; a JWK carrying `d` refused; each of § 6's forbidden JWE header parameters and
§ 7's forbidden JWS header parameters refused with the one sentence; a token whose `alg` disagrees with
its key refused; a `Jwt\KeySet` of 17 keys refused and one carrying `use: enc` accepted with that key
skipped; and a `verifyIssued<T>` whose `T` omits `tainted` reported as a compile-time diagnostic.
