# ADR 0195 — Every process the extension starts runs from a verified copy of the binary, and a new build takes over the server without a gap

- **Scope:** which file the VS Code extension spawns — for the server, the Tasks, the formatter, the AST
  panel and the test controller — how that file is kept the same program as the binary the user named,
  how the server moves to a new build, and what is run when no copy can be. Which binary that is, is
  `nvs.path` and then `PATH`, unchanged; the version comparison is [0158](0158.md)'s and unchanged.
- **Depends on:** [0099](0099.md), [0155](0155.md).
- **Validated by:** `editors/vscode/test/client/shadow.test.ts`, and the measurement under *Verification*.

> **In short:** nothing the extension starts runs the file the user named. Each spawn asks one function
> for the file to run and gets a copy in the extension's own storage, used only after both files hash
> equal, and that function reads the binary's size and modification time on every call, so no process is
> started from an older build than the one on disk. The server, which outlives a build, is moved by a
> once-a-second poll: the new build is copied, verified, started and version-checked while the old server
> still answers, and then the old one is stopped. It is the same on every platform, and it has no setting.

## Context

The extension spawned every process from the path `nvs.path` named, and the server lives as long as the
window. On Windows the file of a running program cannot be overwritten or deleted, so with an editor open
a build could not write `nvs.exe` and an upgrade could not replace it. The error names the file and not
the editor holding it, and the developer met it several times before connecting the two. The developer's
requirements were three: the editor never holds the binary, whatever it is doing; what it runs is in step
with the binary in every case; and the move to a new build happens by itself, without interrupting work.

## Investigation

- **It is not only Windows.** Linux fails an in-place write into a running binary with `ETXTBSY`, and
  macOS may kill a signed process whose file is rewritten under it. A tool that unlinks and recreates the
  file avoids both, but which tools do is not something an extension can rely on.
- **Every platform has the other half of the problem.** Where the file *can* be replaced, the old process
  keeps running, and the editor answers from a build that is no longer on disk with nothing to say so.
- **It is not only the server.** A program started by the `nvs run` Task runs until the user stops it, and
  holds its file exactly as the server does.
- **`nvs` reads its own path in two places that matter**, and a copy is sound in both. A bundle's payload
  is read from the end of the running executable (`crates/nvs-cli/src/bundle.rs`), which a byte copy
  keeps. The compile cache's build stamp hashes the executable's path, length and modification time
  (`crates/nvs-config/src/cache.rs`), so a copy keys apart from its source: one cold compile per new
  build, and the same key on every later run of that copy.
- **A Windows copy keeps its source's modification time and other platforms give it a new one**, and the
  creation time is the reverse. The later of the two is when a copy was made, on all of them.
- **A Task carries its process path from the moment it is built**, and the editor keeps Task objects of
  its own. Whether it rebuilds one on every run was not established, so the design does not depend on it.

## Options considered

1. **Copy the binary and run the copy, checking the source at every spawn and polling it for the
   server.** Chosen.
2. **Rename the old binary aside when updating.** Windows allows renaming a running executable, so an
   updater can move it and write the new file. It helps a deploy script and the extension's own install
   command, and does nothing for `nvs.path` pointed into `target/`, where the linker writes the file.
3. **Have `nvs lsp` copy and re-execute itself.** The editor tracks the process it spawned, so the parent
   has to stay alive, and the parent is the file that is held.
4. **A command that stops the server.** It asks the user to remember the cause, which is the thing that
   keeps not happening.

## Decision

### 1. Everything runs from a copy, and one function says which

`src/binary.ts`'s `runnable` resolves the named command to a file — a name with a separator is a path
relative to the first workspace folder, anything else is searched along `PATH`, with `PATHEXT` on
Windows — and hands back a copy of it under `server/` in the extension's global storage. All five spawns
call it at the moment they spawn and hold the answer for that one spawn. The copy is named
`nvs-<digest of the source path>-<size>-<modification time>`, with `.exe` on Windows, so windows on one
build share a file and no window replaces a file another is running.

### 2. A copy is used only when it hashes equal to its source

Both files are hashed, and the source's size and modification time are read again afterwards; a copy is
handed out only when the hashes agree and the stamp did not move. That holds for a copy found already
there as much as for one just made. The bytes land under a name of the writing process's own and are
renamed once verified. A copy taken mid-write is discarded and made again, five times at most.

### 3. A verified copy is reused only while both files still read as they did

The verified copy is remembered with the source's stamp and the copy's own. A later call reuses it when
both files still read the same — two `stat`s — and otherwise goes back through § 2. So a process started
a moment after a rebuild is started from that rebuild, without waiting on § 4's poll, and a copy that was
touched or deleted is never run.

### 4. The server moves to a new build beside the old one

One `stat` a second. The extension acts when a reading differs from the running build and equals the
reading before it; a missing file is never a change, because a build deletes its output before writing
it. Polling is chosen over a file-system watch because the file is replaced and not edited: a watch on
the path dies with the file, and a watch on the directory reports differently per platform and not at
all on some network and WSL mounts.

The new copy is made and verified, the new server started and its version compared, all while the old
server is answering; then the rest of the extension is pointed at the new client and the old one is
stopped. The status item is not set to `starting` while a server is answering. **The old server never
outlives a new build that failed**: if the new one will not start or is refused, the old one is stopped
and the status item says why, because a server answering from a build that is not on disk is the failure
this record exists to remove. The watch is set whatever the start came to, and restarts are serialised.

### 5. A Task over an earlier build is stopped and run again

When a Task of this extension's type starts, its process path is compared with what `runnable` hands
back now. A different one is terminated and the same definition executed over the current copy.

### 6. The named binary is the fallback, and the status item says so

When no copy can be made, or the server's copy will not start, the named binary is run and the status
item's detail says the file is being held and why. Otherwise the detail names the binary and when the
build being run was written.

### 7. What is deleted

Each time a copy is made: every copy of an earlier build of the same source at once, a copy of another
source once it is a week old, another process's unfinished copy once it is a minute old. A failure to
delete is ignored — it is a file some window is running — and nothing not written by this module is
touched, so the binary the install command puts in the same storage is safe.

## Consequences

- **Performance:** a new build costs one copy and two hashes of `nvs`, once per window. Every other spawn
  costs two `stat`s, and an open window one `stat` a second. Nothing is on a request path.
- **Memory:** none beyond a second server process for the moment of a switch. It spends disk: one file
  the size of `nvs` per source binary in use, under the extension's storage.
- **Usability:** a rebuilt binary is what every command runs at once and what the server answers from
  within a few seconds, with nothing to remember and nothing to see. For the moment two servers answer,
  a request may be answered by both. Antivirus software may scan a new copy before its first run.
- **Simplicity:** one module with no `vscode` import, one function every spawn asks, no setting, no
  contribution to the manifest, and one behaviour on every platform.

## Alternatives rejected

- **Copying on Windows only.** The lock is not only Windows', the stale server is every platform's, and a
  branch taken on one platform is a branch the other platforms' test runs never execute.
- **Copying only for the server.** The first design, on the reasoning that the other processes are short.
  `nvs run` is not, and "the editor never holds the binary" is a rule a user can rely on where "the
  editor holds it only sometimes" is not.
- **Stopping the old server before starting the new one.** Simpler by one function, and it costs a gap in
  diagnostics and completion on every rebuild, which during work on the compiler is every few minutes.
- **Keeping the old server when the new build fails.** It is the more available choice and the wrong one:
  the answers would come from a program that no longer exists, behind a status item nobody is reading.
- **Naming the copy for a hash of its content.** It needs the source hashed before there is a name to
  look for; the stamp gives the name for one `stat`, and the hash still decides whether the file is used.
- **A setting to turn it off.** The fallback is automatic, and a frozen setting is kept forever.

## Verification

The suite pins the copy's bytes, its reuse, a new copy for a new build, the replacement of a file that
does not match, reuse and refusal to reuse across calls, what a sweep deletes and leaves, command
resolution, and the two-reading rule of the watch. Against a release `nvs.exe` of 41.7 MB on Windows,
with `nvs lsp` running: overwriting the binary failed with `EBUSY` when the server ran from it and
succeeded when the server ran from the copy; the copy was made and verified in 86 ms and re-verified in
56 ms; the watch fired 1.5 s after the overwrite; and the earlier copy was left while it ran and deleted
once it had stopped.
