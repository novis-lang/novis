# ADR 0175 — The artifact cache's directory has one spelling, `opcache.file_cache_dir`, and `[cache]` holds `Core\Cache`'s two tiers and nothing else

- **Scope:** which of two parsed keys names the directory compiled artifacts are read from, and what
  happens to a file that writes the other one. It changes nothing about the cache's layout, how an
  entry is verified before it is mapped, the ownership check on the directory, or either
  `Core\Cache` tier.
- **Depends on:** [0042](0042.md), [0005](0005.md), [0078](0078.md), [0103](0103.md).
- **Validated by:** `crates/nvs-config/tests/directives.rs`, `crates/nvs-config/tests/snapshot.rs`,
  `crates/nvs-config/tests/request.rs`, `crates/nvs-config/tests/tree.rs`,
  `tests/conformance/core/config-unconfigured-host-answers-as-an-empty-configuration.nvst`, and
  `python tools/directives.py --check`, which fails on any leaf key that reaches no reader.

> **In short:** the tree parsed two names for one thing. `opcache.file_cache_dir` is the one the
> artifact cache reads; `[cache] dir` was parsed, classified `System`/`Boot` and read by nobody, so
> an operator who wrote it moved no cache and was told nothing. `opcache.file_cache_dir` survives —
> it is where every other knob about the same cache already lives, and it is the spelling with a
> reader — and it takes the `Boot` row `[cache] dir` held, because moving the directory re-creates
> the runtime's mapping of every cached unit while the rest of `[opcache]` is read by the next
> compile. `[cache]` is now `Core\Cache`'s `local` and `shared` tiers and nothing else. Writing
> `[cache] dir` is `E0601`, an unknown directive, which is the point: a refusal naming the file and
> the line is what the silence was hiding.

## Context

Two keys described the same directory. `[cache] dir` was a field of the typed tree, carried a
`System`/`Boot` row in the registry, was named by three rules and by the shipped reference's
directive table — and no code anywhere read it. `nvs_cli::cache::from_config` took the directory
from `opcache.file_cache_dir`, or from the per-build default beneath the account's own cache root
when that was unwritten.

Both halves of that are defects on their own terms. An operator who read the rulebook, wrote
`[cache] dir = "/srv/cache"` and restarted got a process still writing artifacts under
`~/.cache/novis`, with nothing in the boot log to say so: the file was accepted, the key was stored,
`nvs config dump` reported it, and `Core\Config::get("cache.dir")` answered it. Silence is the worst
available answer here, because the directory is a trust boundary — `rule:packaging/the-checksum-proves-integrity-and-ownership-proves-trust`
refuses a world-writable one — and an operator who believes they moved it has moved nothing and
checked nothing.

## Options considered

1. **`[cache] dir` becomes the primary spelling, `opcache.file_cache_dir` an alias.** `from_config`
   reads `dir` first and falls back. Cheapest in files touched, because the rulebook and the
   reference already name `cache.dir`.
2. **Keep both, with no precedence, and document them as equal.** Not seriously available: two keys
   that can disagree need a rule for which wins, which is option 1 with the argument left unwritten.
3. **`opcache.file_cache_dir` is the only spelling; `[cache] dir` leaves the tree.**

Option 1 keeps a second name for one thing forever and adds a precedence an operator has to know.
It also splits one subsystem's knobs across two blocks: `file_cache` decides whether the artifact
cache runs, `file_cache_max_size` and the GC pair bound it, and under option 1 the directory it all
writes to is in a different block, which is the arrangement that produced this defect in the first
place. The familiarity argument for the `[cache]` name does not survive [0064](0064.md): `[opcache]`
is not a `php.ini` block either — `opcache.validate` is a new name as much as `cache.dir` was — so
neither spelling is the one a PHP operator already has in hand.

What option 3 costs is documentation, four tests and one migration, all of them in this record's own
commit, against a permanent simplification of the operator surface. Under `AGENTS.md`'s ordering
that is the direction to spend in: the surface is priority 4 and the edits are priority 4's
implementation half.

## Decision

### 1. `opcache.file_cache_dir` is the artifact cache's directory, and it is the only spelling

Every directive about the on-disk artifact cache is a key of `[opcache]`:
`rule:config/opcache-file-cache-directives-are-system`'s roster, the directory among them. Nothing
else names a directory for it, and no alias is kept.

### 2. It carries `System` and `Boot`, as a row longer than its block's

The registry holds `opcache` as `System`/`Reload` and `opcache.file_cache_dir` as `System`/`Boot`.
`lookup` takes the longest row that governs a key, so the specific row answers for the directory and
the block row answers for everything else. That pairing is exactly what
`rule:config/reloadability-is-its-own-field` exists to express: the class says a request may not set
it, and the second field says a change needs a restart. `Boot` is not inherited from `[opcache]`'s
row but argued for the key — the rest of the block is read by the next compile, while a moved
directory re-creates the runtime's mapping of every cached unit.

### 3. `[cache]` is `Core\Cache`'s two tiers

`[cache.local]` and `[cache.shared]` stay where they are, under the class an operator looks for them
by name, and the block holds no third key. `rule:core-api/two-cache-tiers`'s store and
`rule:packaging/an-artifact-is-one-immutable-content-addressed-file`'s compiled artifacts are two
caches that share a word, and one block claiming both is what let one directory have two names.

### 4. Migration: `[cache] dir` is `E0601`, and that is the whole of it

The field leaves a `deny_unknown_fields` struct, so a file that carried it is refused at boot rather
than ignored — `E0601`, an `nvs.toml` directive that does not exist, naming the file and the line
(`rule:config/a-duplicate-key-is-an-error-and-so-is-an-unknown-one`). The fix is one line: write the
same path as `file_cache_dir` under `[opcache]`. A file that never wrote the key is unaffected, and
no deployment loses a cache it was actually using, because the key it was writing changed nothing.

This is the one key the `nvs.toml`-is-written work removes rather than marks. Every other
unimplemented directive stays parsed and is emitted commented-out in the generated file, because
removing it would break a file for no gain; here the gain is the defect above, and leaving the key
parsed is what keeps it.

## Diagnostics

No new code. `E0601` at boot for `[cache] dir`, from the per-file refusal the tree already applies
to an unknown key. `Core\Config::set("cache.dir", ...)` returns `false` as it did before, now
because no directive governs the name rather than because a `System` one does — both are the same
`false`, and `rule:config/a-refused-set-returns-false` is unchanged.

## Consequences

- The shipped reference's directive table loses a row and gains one; it is generated from
  `nvs meta --json`, so it follows the registry with nothing to remember.
- `[opcache]` is the whole answer to "where does compiled code come from and go", which is the
  question `rule:config/opcache-file-cache-directives-are-system` is the roster for.
- One more `Boot` row exists than before, and `rule:config/reloadability-is-its-own-field`'s narrow
  set names this key where it named the other. The census test in
  `crates/nvs-config/tests/directives.rs` walks that list key by key, so the rule and the registry
  cannot drift apart quietly.

## Verification

- `crates/nvs-config/tests/directives.rs` asserts `opcache.file_cache_dir` is the `Boot` member of
  the set the rule names, and that no `Runtime` directive is `Boot`.
- `crates/nvs-config/tests/snapshot.rs` reloads a tree that moves the directory: the reload reports
  `opcache.file_cache_dir` as a `Boot` key it could not apply, and the published snapshot still
  carries the running value.
- `crates/nvs-config/tests/tree.rs` parses a `[cache]` block written as its two tiers.
- `crates/nvs-config/tests/request.rs` and
  `tests/conformance/core/config-unconfigured-host-answers-as-an-empty-configuration.nvst` refuse a
  request's `set` of the key, which is the `System` half.
- `python tools/directives.py --check` derives every leaf key of the typed tree and fails on one no
  code reads, which is what would have caught this before it was written.
