# ADR 0241 — A relative path literal resolves from the file that wrote it, and a relative path built at run time throws

- **Scope:** Which directory a relative file path names when a program passes one to a `Core` member
  or to a parameter marked `#[Core\Path]`, how the registry marks such a parameter, and the one member
  that reads the working directory. How `nvs.toml` anchors a relative *grant* is unchanged.
- **Depends on:** [0021](0021.md) (`require` resolves against the requiring file), [0062](0062.md)
  (path case), [0118](0118.md) (a path scope is compared after it is canonicalized).
- **Validated by:** `crates/nvs-types/tests/paths.rs`, `nvs_runtime::capability`'s
  `a_relative_path_throws_before_any_grant_is_asked`, and the `.nvst` cases named under
  *Verification*.

> **In short:** a relative string literal passed to a path parameter is joined to the folder of the
> source file that contains it, while compiling, exactly as `require` resolves its path. The program
> runs with the absolute path in its place. A relative path that reaches a `Core` door at run time —
> one the program built — throws a `RuntimeError` that names the path and says to use
> `Core\Path::join` or `Core\Path::fromCwd`. Nothing resolves against the working directory
> implicitly. `Core\Path::fromCwd` is the one way to read it, for a path typed on a command line, and
> it throws while a request is being answered. A user method marks a parameter as a path with
> `#[Core\Path]`. The registry marks `Core`'s path parameters with `CoreTy::Path`, and two class-name
> parameters with `CoreTy::ClassName`, for the editor.

## Context

A relative path given to `Core\IO::read('data/x.json')` was resolved against the process's working
directory. Nothing in Novis changes that directory, so every program in a process shares it. That
breaks in three places:

- Under `nvs serve` with several mounts, every app has the same base, so two apps cannot both read
  their own `data/x.json`.
- Under a Windows service manager the working directory is `System32`, so a program that works from
  a terminal fails as a service.
- A relative *grant* in `nvs.toml` is anchored to the folder of the configuration file
  (`rule:config/a-relative-path-resolves-against-the-file-it-is-written-in`), while a relative path in
  the program was resolved against the working directory. The grant and the read named the same text
  and could mean two different files.

PHP has `__DIR__` for this, and Novis does not (`E0319`). `chdir` and `getcwd` are dropped.

## Options considered

1. **Keep the working directory as the base.** It is PHP's rule for `fopen`. It is the rule that
   breaks all three cases above.
2. **The entry file's folder as the base for every relative path.** One base per program, so it
   fixes the multi-app case. A library file reached through `require` or `autoload` would read its
   data relative to whoever ran it, so a package could not ship a data file beside its code.
3. **`nvs.toml`'s folder as the base.** Agrees with the grants. A program run without a configuration
   file has no base, and a program's own source would mean something different depending on where the
   operator keeps the file.
4. **The folder of the file that wrote the literal, as `require` does, and a throw for a relative
   path built at run time.** Each file's literals mean what they say to someone reading that file.
   A path built at run time has no file of its own, so it has to be made absolute on purpose.

## Decision

Option 4.

### 1. A path parameter is marked, in the registry and in a program

`nvs_stdlib::registry::ParamText` is `Plain`, `Path` or `ClassName`. A `Core` row writes the mark on
the parameter's type: `CoreTy::Path(Qual)` and `CoreTy::ClassName(Qual)` are `CoreTy::Text(Qual)`
with one more fact, and they intern as plain `string`. `CoreTy::param_text` and
`CoreMethod::param_text` read it. A field of a `Core` shape carries it too (`Db\Settings`' `path`).
The mark is on the type, not in a roster beside the rows, for `CoreTy::Entry`'s reason: a member that
takes a path gets the rule in the edit that writes its signature.

Every `Core` parameter that names a file on disk is `Path`: `Core\IO`'s path members, `Core\Process`'s
program, `Core\Response::sendFile`, `Core\Http\Part::file`, the two `saveTo` members,
`Core\Net::connectLocal` and `listenLocal`, `Core\Zip::extract`'s destination and `Db\Settings`' path.
`Core\Path`'s own members work on path *text* and are not marked. `Core\Reflect::forClass` and
`Core\Test::assertThrows` mark their class-name parameter `ClassName`, which changes nothing a
program does and lets an editor offer class names.

A user method marks a parameter with `#[Core\Path]`, a compiler-recognized attribute with no payload,
on `rule:core-classes/derive-attribute`'s closed roster. It is allowed only on a method parameter
whose type is a `string`, alone or with `null`; anywhere else it is `E0836`.

### 2. A relative literal is joined to its file while compiling

A plain string literal written as the argument for a `Path` parameter, or as the value of a `Path`
shape field, is resolved: joined to the folder of the file that contains it, with `.` and `..`
removed, and nothing read from the disk. The compiler emits that absolute path in place of the
literal. A literal that already starts at a root is unchanged. A default value of a `#[Core\Path]`
parameter is resolved against the file that declares it.

**Only a plain literal.** A class constant, a concatenation of literals and a variable are run-time
values: a constant declared in one file and used in another has no single file to resolve against.

**A lexical join, not a canonical path.** The answer must not depend on whether the file exists yet,
and a bundled executable compiles from its payload, where no folder is on disk. The security question
is not changed: every door canonicalizes the path before it compares it with a grant, so a literal
that climbs out with `..` is judged where it lands.

**Inside a bundled executable** the declaring file's folder is synthetic, and it maps to the same
relative folder beside the executable (`nvs_diagnostics::embedded::on_disk`). A bundle reads its data
files from where the source tree kept them, placed next to the executable.

**A file named relative to the shell** (`nvs run tool.nvs`) is made absolute against the working
directory while compiling. That is what the person who typed the name meant.

### 3. A relative path at a door throws

`nvs_runtime::capability::require` throws a `RuntimeError` for a path scope that does not start at a
root, before any grant is read. The message names the member and the path and says to use
`Core\Path::join` or `Core\Path::fromCwd`. "Starts at a root" is `Path::has_root`, the same test as
the compile-time join, so the two agree. Every door that takes a path calls `require`, so the rule is
one check in one place.

### 4. `Core\Path::fromCwd`

`Core\Path::fromCwd(string $path): string` joins a relative path to the process's working directory
and returns the absolute, normalized path; an absolute argument is returned normalized. It is how a
command-line tool handles `nvs run tool.nvs ./input.txt`. It reads the directory through
`nvs_runtime::capability::working_dir`, which throws while a request is being answered, because a
server's working directory is not the app's.

### 5. Grants and configured roots

With every path absolute when it reaches the check, a relative grant anchored to `nvs.toml`'s folder
and a relative literal in a program beside it name the same files. Grant anchoring is unchanged.

A `[storage.<name>] root` is a path the runtime joins an object key to and opens through the same
doors, so a relative one is resolved against the file that wrote it, as a `[db.<name>] path` already
is (`rule:config/a-relative-path-resolves-against-the-file-it-is-written-in`). Left relative, every
object on the disk would meet § 3's refusal.

## Diagnostics

- `E0836` `E_PATH_MARKER_NOT_ON_A_STRING`: `#[Core\Path]` on a declaration, a property, a constant, an
  enum case, a method, or a parameter whose type is not a `string`.
- Run time: `RuntimeError`, "`<member>` needs an absolute path, and `<path>` is relative", with a help
  line naming `Core\Path::join` and `Core\Path::fromCwd`.
- Run time: `RuntimeError` from `Core\Path::fromCwd` while a request is being answered.

## Consequences

- A literal costs one join while compiling and nothing at run time: the instruction is the same
  constant string with different bytes. A door pays one root test per call.
- A program that built a relative path at run time and relied on the working directory now throws.
  The message says what to write instead.
- A message that prints a resolved literal prints the absolute path.
- PHP resolves a relative `fopen` path against the working directory. This is a deliberate
  divergence.

## Alternatives rejected

- **The working directory** — breaks several apps in one server and every service.
- **The entry file's folder** — a library cannot ship a data file beside its own code.
- **`nvs.toml`'s folder** — a program without a configuration file has no base, and the program's
  meaning would depend on where the operator keeps the file.
- **A `__DIR__` constant** — every call site would have to write the join, and a forgotten one would
  still resolve against the working directory.
- **Canonicalizing the literal while compiling** — the answer would depend on the build machine's
  disk, and a bundle has none to ask.
