# ADR 0229 — a wake handle the task it names gives up is collected without a wake

- **Scope:** what dropping a `RemoteWake` does when the thread dropping it is the core that issued it,
  running the task the handle names. It does not change what a drop does anywhere else, what
  `RemoteWake::wake` does, or [0115](0115.md) § 2's parking contract.
- **Depends on:** [0115](0115.md) (the reactor, its cross-thread wake and the outstanding count),
  [0138](0138.md) (one permission per drive, given up when the drive ends).
- **Validated by:** `a_remote_wake_its_own_task_gives_up_wakes_nothing` and
  `a_drain_wake_let_go_by_its_task_does_not_end_that_tasks_next_wait` in
  `crates/nvs-host/src/reactor.rs`, and the measurement under *Verification*.

> **In short:** a `RemoteWake` dropped unused wakes the task it names, because the far side of a handoff
> that went away must not leave that task parked. When the task itself drops the handle, it is running
> and nothing is parked, so the handle is collected on the spot: the reactor's outstanding count comes
> down and nothing is queued or poked. Before this, that drop queued a wake, and the wake ended the
> task's **next** wait. A task that took a handle for every wait in a loop never waited, and an idle
> server kept one core busy.

## Context

An idle `nvs serve` kept one core fully busy. No request was in flight and no configuration turned it
off.

The thread was the worker that runs the task following `[metrics]` and `[trace]` across a reload. That
task loops: it registers a wake on the server's drain, waits up to a second, lets the registration go,
and looks at the published configuration. The registration holds a `RemoteWake` for the task.

A `RemoteWake` dropped without being fired delivers its wake: the task's id goes into the core's queue
and the core's poller is poked. That is [0115](0115.md)'s answer to a pool thread that panics, and it is
right there. Here the task dropping the handle was the task the handle names. It was running, so the
queued wake had nothing to end. The core reads that queue only when its run queue is empty, which is
after the task has parked again. So the wake from one iteration ended the wait of the next, at once,
and every iteration queued another.

The same drop happens wherever a task holds a handle for itself and outlives the wait: once when a
connection's drive returns, once per sleep inside a WebSocket program, once when a connection that
registered on the drain ends. Each cost one poke and one early resume. Only a loop that registers per
wait turns it into a busy core.

## Decision

### 1. A handle dropped by its own running task is collected on the spot

`RemoteWake`'s drop asks one question first: is this thread the core that issued the handle, and is the
task it names the one running here? Both halves are asked, because a task id is issued per scheduler and
names a different task on every core.

When the answer is yes, the handle is marked delivered and the outstanding count is lowered by one.
Nothing is queued and the poller is not poked. The count still has both of its ends on the core, which
is what lets the reactor read it as "something off this core can still wake a task".

When the answer is no, the drop delivers the wake, as it does for a pool thread that went away. A
reactor that is borrowed, gone or another core's answers no.

### 2. A wake that is asked for is queued whoever asks

`RemoteWake::wake` is not changed. A registration made against a drain that has already begun fires its
wake before it returns, on the task's own stack, and a stream's drain cut raises its flag the same way.
Both leave a wake queued for the task's next wait. Only the drop is given the new answer, so neither
changes.

### 3. The loop that showed it is left as it is written

The exporter task still registers for each wait. With § 1 that costs a registration and nothing else,
and a stop still ends the wait at once. Moving the registration out of the loop would have hidden the
cause and left every later caller one loop away from the same busy core.

## Consequences

- **Performance.** An idle server does no work on the core that follows the exporters. Every connection
  saves one poke of its core's poller and one wasted turn when its drive returns, and a program that
  sleeps on a WebSocket saves the same per sleep.
- **Memory.** Nothing changes. No allocation is added per request, per task or per wait.
- **Usability.** Nothing a program can observe changes, other than the idle cost.
- **Simplicity.** The drop has one more branch, and a contributor may now take a handle per wait without
  knowing how the queue is drained. The rule "every handle issued is a wake delivered" becomes "every
  handle issued is collected on the core", which `rule:concurrency/one-permission-per-drive` states.

## Alternatives rejected

- **Register once, outside the loop.** It fixes the one caller and keeps the trap.
- **A `cancel` the caller must choose.** Every site that gives up its own handle would have to remember
  to call it, and the registration on a drain holds its handle inside a closure that a drop is the only
  way to reach.
- **Collect every self-delivered wake on the spot, the explicit one too.** It would also change what a
  registration against a drain that has already begun leaves behind (§ 2), and the busy core needs none
  of that changed.

## Verification

The two tests named above fail with § 1's branch disabled and pass with it. With it disabled, the second
reports two of its three waits ending before their deadline.

One `nvs serve` of a one-line program, no configuration file, one request answered and then ten idle
seconds, debug builds on one machine:

| Build | Threads | CPU time used by the process in the ten seconds |
|---|---|---|
| before | 23 | 9156 ms, all of it on one thread |
| after | 23 | 0 ms |
| after, with one keep-alive connection held open and idle | 23 | 0 ms |
