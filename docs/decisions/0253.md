# ADR 0253 — `Core\Program`'s enumeration selects by a class as well as an interface, and `constructors<T, C>()` hands back one typed constructor per class

- **Scope:** what `implementing<T>` and `implementingWith<T, S>` accept as `T`, and one new compiler-owned
  member, `constructors<T, C>()`, answering the same list as closures. The scan, the order and the
  per-request instances are unchanged and stay with their own records.
- **Depends on:** [0061](0061.md), [0212](0212.md), [0136](0136.md).
- **Validated by:** the conformance and reject cases the three rules' `guardedBy` names, and the scan
  opt-in test in `crates/nvs-hir/src/requires.rs`.

> **In short:** plugin families built on an abstract base could not be enumerated, because the
> selector had to be an interface, and a plugin that needed a dependency could not be enumerated at
> all, because every listed class needed a no-argument constructor. The selector now takes a class:
> the list is every non-abstract class `C` for which `$c is T` holds, so a concrete `T` is in its own
> list. And `constructors<T, C>()` lists the same classes in the same order as `{class, make}` rows,
> where `make` is the closure `fn(<C's parameters>): T => new Class(<the same arguments>)`, checked
> where the call stands. Both are answered while compiling; the selector costs nothing at run time,
> and `constructors` costs one closure per listed class per call and builds no object until `make`
> runs.

## Context

### 1. The interface was demanded for its static type, and a class has one too

[0061](0061.md) made the selector an interface because the loop body needs a static type to call
through, and `object`, a shape and bare `callable` give none. A class gives one exactly as an
interface does. What it refused was therefore broader than its reason, and a framework whose plugins
share an abstract base — state and a template method an interface cannot carry — had to declare an
interface beside the base only to be enumerable, and keep the two in step.

### 2. The no-argument constructor pushed dependencies into a second step

Because the expansion is one `new C()` per class with no call site to write arguments at, every
listed class needed a no-argument constructor, and a dependency arrived through a method called after
construction. An object was therefore reachable half-built, and every class owed a setter its type
could not require. [0061](0061.md)'s *Alternatives rejected* named constructor references as the better
shape, blocked on a typed `callable` signature; `rule:types/callable-signature` has since shipped.

### 3. The hierarchy walk already answers the class question

`nvs_hir::implementors` filters the class graph with `implements_interface`, which walks `extends` as
well as `implements` and counts a declaration as reaching itself. A class `T` therefore selects itself
and its descendants with no change to the walk; the interface demand lived only in the checker's one
refusal.

## Options considered

### 4. For the selector

A new `extending<T>()` member; the existing `implementing<T>` and `implementingWith<T, S>` taking a
class; or a hierarchy reader on `Core\Reflect\ClassInfo` for a program to filter with.

### 5. For the dependencies

A list of class names to pass to `Core\Reflect::construct`; a `constructors<T, C>()` member whose rows
carry a closure typed by a written callable signature; or keeping the limit and documenting the
second step.

## Decision

### 6. The existing members take a class

The selector is `implementing<T>` and `implementingWith<T, S>` taking an interface or a class,
abstract or not. **Membership is `is`:** a class is listed exactly when it is non-abstract and
`$c is T` holds, so a concrete `T` is in its own list and no second notion of "subclass" exists. Every
other type argument is refused as before.

### 7. `constructors<T, C>()` answers closures

`constructors<T, C>()` expands to an array literal of `{class: string, make: C}` rows, one per class
`implementing<T>()` would list and **in the same order**, so the two can be zipped. `class` is the
fully-qualified name. `make` is the ordinary closure `fn(<C's parameters>): T => new Class(<the same
arguments, in order>)`, checked exactly as that closure would be if it were written at the call site:
argument types, defaults and the visibility `new` faces there. `C` must be a `callable(...)` type whose
return type is `T`. The no-argument constructor demand does not apply to this member.

No new calling path, no reflection and no runtime table: the rows are what a program could have
written by hand, had it known the list.

### 8. One scan opt-in for every enumeration member

`constructors` joins `implementing` and `implementingWith` in the set of members that opt a program
into the scan, so a program calling any one of them sees every autoloaded class, and a program calling
none performs no scan.

## Diagnostics

### 9. One widened refusal and two new ones

`E0743` keeps its number and says "an interface or a class". `constructors` adds two codes in the
types band: a `C` that is not a callable type naming its parameters, or whose return type is not `T`;
and a class whose constructor the closure does not fit — a wrong argument type, a missing required
parameter, a constructor not visible at the call site — reported on the call, naming the class, with
the ordinary error it stands for attached as a note. `E0744` is never reported by `constructors`.

## Consequences

### 10. Cost

The class selector is compile-time only and adds nothing to the request path. `constructors` builds
one closure object per listed class per call, charged to the request and freed with the array, and no
listed object until its `make` is called. Two more members' worth of surface on `Core\Program` —
`constructors` itself, and `implementing` meaning a little more — buys the removal of the
no-argument-constructor limit for frameworks whose plugins need dependencies.

## Alternatives rejected

### 11. `extending<T>()`

A second member answering the same walk with a different word, and a program would have to learn which
one applies to an abstract base that also implements an interface.

### 12. Class names for `Core\Reflect::construct`

It moves the constructor check from the call site to run time, and the arguments lose their static
types; the rows `constructors` answers are checked where they are written.

### 13. A hierarchy reader on `Core\Reflect\ClassInfo`

`parent`, `interfaces` and `isAbstract` would let a program filter a list it still could not obtain
without a scan. They remain a separate question.

## Verification

### 14. Guards

An accept case with an abstract base, a concrete base with subclasses and a class two levels down,
printing the order; a multi-file case where `implementingWith` alone finds autoloaded classes; the
reject case for the selector, widened to an enum and a shape; an accept and a reject case for
`constructors`, the reject one diagnostic per kind of misfit; and the test pinning `constructors` as a
scan opt-in.
