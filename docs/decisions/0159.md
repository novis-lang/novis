# ADR 0159 — the type-argument door is a roster of members admitting a class or an inline shape, and the diagnostic names both

- **Scope:** what a call site may write between the angle brackets of a compiler-owned member that
  declares a type variable it cannot infer, and which members have that door. Not in scope: the members
  themselves, whose rosters are [docs/spec/01-core-library.md](../spec/01-core-library.md) §§ 6, 15 and
  18, and the hydration walk a shape argument runs, which is [0157](0157.md)'s type surface and
  `crates/nvs-stdlib/src/json.rs`'s module doc.
- **Depends on:** [0007](0007.md) § 5 — the door itself, and why user-written generics are not part of
  it; [0036](0036.md) — the inline shape type; [0157](0157.md) — the optional key and the qualifier
  that made a shape worth writing there.
- **Validated by:** `tests/conformance/core/db-query-as-builds-a-class-and-not-a-scalar.nvst`.

> **In short:** [0007](0007.md) § 5 opened the door as a two-item list — `Core\Json::decodeAs<User>` and
> `Core\Db`'s `queryAs<T>` — and named a **class** as the only thing that could go through it, because a
> class was the only thing that could carry a derived codec. Both halves of that have moved. The roster
> is three members, `Core\Request::jsonAs<T>` having joined it, and it is a roster the compiler holds
> (`nvs_stdlib::registry::WRITTEN_CLASS_MEMBERS`) rather than a pair a record enumerates — so a member
> gaining the door is a row, not a decision. And what may be written there is a class **or an inline
> shape**: a shape declares its own fields where it is written, so the two whole-program questions a
> class raises — where the deriving attribute is, and what the property list says — are already answered
> at the call site. `array<…>` of either stays the list form. `rule:types/arrays` is where the current
> answer lives; this record is why it stopped naming a class alone.

## Context

The door exists because a decode has no argument to infer its result from: `decodeAs` is handed a
`string` and asked for a `User`, and nothing but the written type says which. [0007](0007.md) § 5 granted
that one exception to "type variables belong to declarations the compiler owns", listed the two members
that needed it, and said the argument names **the class to construct** — which was true, because
`rule:core-classes/derive-attribute`'s generated codec is the only thing that could hydrate anything, and
it is generated onto a class.

Two things then landed that the sentence does not describe. `Core\Request::jsonAs<T>` took the door as a
third member. And [0157](0157.md) gave the inline shape everything a hydration target needs — a field
list, a per-field required bit, and a qualifier that reaches the whole of it — at which point a class is
no longer the only answer to "what should this document become". The checker's arm accepting a shape
landed with the hydration walk; the rule and the refusal did not follow it.

## Decision

### 1. What may be written is a class, an inline shape, or an `array<…>` of either

A class carries a derived codec and raises two questions about the rest of the program — whether the
deriving attribute is on it, and whether its declared properties fit the format — which is why
`nvs_types::derive` records a decode site or a row site where one is written. An inline shape raises
neither: there is no declaration further down the file to look at, and the contract is read straight off
the type and emitted beside the call. So the two are different *at the call site* and the same
afterwards, and the door admits both rather than a shape needing a class wrapped around it first.

`array<C>` and `array<{…}>` are the list form, and nesting stops one level down: `array<array<C>>` is
not a document shape any format gives a field, so it is refused rather than recorded as a class it is
not.

### 2. The roster is the compiler's, not this record's

Which members have the door is `nvs_stdlib::registry::WRITTEN_CLASS_MEMBERS`, and `rule:types/arrays`
names the members it currently holds. A member joining it is a row in that table plus the conformance
case the coverage gate already demands — not a new decision, because the *grant* is what this record and
[0007](0007.md) § 5 decide and the grant does not change when a fourth member takes it. Enumerating the
roster in a frozen record is what left `rule:types/arrays` describing a two-member door for as long as it
did.

## Diagnostics

`E0465` is unchanged in code and in when it fires; its **message** said "builds a class or a list of one,
and `int` is neither", which is now false in the half that matters, and its **help** sent the reader to
`rule:core-classes/derive-field-list` — the right advice for a class and no advice at all for a document
whose fields are known at the call site. Both name the shape door now, and the help cites
`rule:types/arrays`, which owns the door, with `rule:core-classes/derive-field-list` kept as the reason
the class form is an ordinary `new`.

## Consequences

Nothing changes in what compiles: the shape arm was already accepting shapes, and this record catches the
rule and the refusal up to it. What a reader gains is that the rule and the diagnostic now agree with the
checker, which is the ordinary state and was not the state before.

The cost, per [0004](0004.md)'s ledger: none. A shape at the door is compile-time work and an interned
descriptor, and the wire contract it emits is `rule:types/shape-type`'s existing per-field bit —
O(distinct types in the program), not per request.

## Alternatives rejected

**Keep the door class-only and require a named class for a shaped decode.** That is the position
[0007](0007.md) § 5 held, and it costs the developer a declaration whose only purpose is to be named
once — exactly the "no shape needs declaring anywhere for two sides to agree" that [0036](0036.md)
bought. It also makes a request boundary the one place a program must invent a nominal type to describe
data it does not own.

**Enumerate the roster here and cite this record from the checker.** Rejected for the reason above: a
frozen record cannot track a table, and the last one that tried is why this record exists.
