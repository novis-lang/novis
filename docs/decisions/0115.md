# ADR 0115 — The reactor reports readiness, and a stream that would block parks its own task

- **Scope:** the readiness mechanism each platform uses, the contract between a parking task and the
  reactor, what a `WouldBlock` costs and in which order a stream pays it, and how a task's stack is
  accounted against the request that owns it. It does **not** decide: what a worker admits, which is
  `rule:http-server/a-wedged-core-is-detected-by-its-deadline`'s arithmetic; what the
  blocking pool is for or how large it is, which is that ADR's § 6; the `Core\Task` surface, which is
  `rule:concurrency/one-scheduler`; the HTTP client that will sit on top of a
  stream, which is `docs/agent/goals/` goal `core-part-ii`'s; or the configurable spelling of any number below,
  which is goal `governance`'s `[limits]`.
- **Depends on:** [0106](0106.md), whose § 6 says
  a core is never blocked on a syscall and leaves the mechanism to this one.

> **In short:** every platform reports **readiness**, never completion — `mio` over epoll, kqueue and
> Windows' AFD — and one contract covers all three: a task registers its interest under its own
> `TaskId`, *then* suspends, re-tries the syscall when it is woken, and treats a wake as a hint rather
> than a promise. A stream tries the syscall **first** and parks only on `WouldBlock`, so a warm socket
> pays nothing at all. A task's stack is 1 MiB of reserved address space whose resident cost is the
> pages it touches, pooled per worker and charged to its request, which keeps it O(in-flight).

## Context

`nvs-host` exists (`crates/nvs-host`): a [`Worker`] is one OS thread pinned to one CPU, a `Scheduler` is
its run queue, and a task is a `corosensei` stackful coroutine that suspends by reaching its yielder
through `Ctx`. That crate deliberately shipped with no I/O in it — `Waiting::Parked` hands the core back
and the task sits in the parked set until something calls `Scheduler::wake` with its `TaskId`. This ADR
is what calls it.

Three things make the choice non-obvious, and each is decided below rather than inherited:

- **The three platforms do not agree on what an I/O notification is.** epoll and kqueue report that a
  file descriptor is *ready*; Windows' IOCP reports that an operation you already submitted has
  *completed*. Those are different contracts, not two spellings of one, and picking wrong means every
  stream in Novis has two implementations.
- **The runtime is ours and it is not `async`** (`docs/plan/design.md` § *Thread-per-core,
  shared-nothing runtime*). Every readiness API in Rust that is widely used arrives attached to an
  executor; the one this needs must be the readiness half alone.
- **A stack is the largest thing a task owns**, and M5 asks for 100k concurrent tasks. `rule:programs/memory-priority` requires
  that what memory is spent stays attributable to a request, under an enforceable cap, and O(in-flight)
  rather than O(requests served) — a stack per task is exactly the shape that fails that test if it is
  allocated carelessly.

## Decision

### 1. Readiness on every platform, including Windows

The reactor reports **readiness**. `mio` is the mechanism: epoll on Linux, kqueue on the BSDs and macOS,
and on Windows a poll of `\Device\Afd` through IOCP, which turns the completion port into a readiness
source. One contract, three back ends, and the stream code above it is written once.

`mio` is not an async runtime and brings none: it is the readiness layer, with no executor, no task
type, no `Future`, and no `tokio` in its dependency graph. That distinction is the whole reason this is
not the `BLOCKED` the goal's standing decisions reserve for "a capability appears to require an async
runtime" — the capability requires a *poller*, and a poller is what this crate is. It is pure Rust with
no build script and no C, which is the default `rule:packaging/a-c-dependency-answers-two-questions` sets, and
its first question is answered "no": nothing attacker-controlled reaches a registration, which carries a
descriptor and an interest set and no parsed input at all.

### 2. The parking contract

Five rules, and the first two are ordering rules that a reader will otherwise get backwards:

1. **Register, then suspend.** A task tells the reactor what it is waiting for, keyed by its own
   `TaskId`, and only afterwards yields `Waiting::Parked`. The reverse order is a lost wakeup: readiness
   that arrives in the gap has nothing registered to record it against.
2. **A wake is a hint, not a promise.** The reactor's job is to make the task runnable again, not to
   guarantee the syscall will now succeed. A woken task **re-tries the syscall** and parks again on
   another `WouldBlock`. Spurious wakeups are ordinary — a level-triggered poller reports a socket that
   another read already drained, and a wake can race a task that finished — which is why
   `Scheduler::wake` answers `false` for an unknown id rather than treating it as a fault.
3. **Deregister when the task ends.** The scheduler hands back a `Finished` task; the reactor drops
   every registration under that `TaskId` at that point. `wake` on a stale id is already harmless, but
   the registration itself is not: leaving it is a per-request kernel object that outlives its request,
   which is the O(requests served) growth `rule:programs/memory-priority` calls a leak rather than a trade-off.
4. **The reactor blocks only when the run queue is empty and something is parked.** With work ready it
   is polled with a zero timeout, so readiness is collected without giving up the core; with nothing
   ready and nothing parked, the worker has no work at all and the accept loop — itself a parked task —
   is what it is waiting on. There is no fourth state.
5. **One reactor per worker, and it is `!Send` like everything else on the core.** A descriptor a
   request owns is registered with, and woken by, that request's own core. Nothing crosses, which is
   what keeps the refcounts non-atomic.

### 3. A stream tries first and parks second

`NvsTcp` implements plain `std::io::Read` and `std::io::Write`. That is the whole point: a helper reads
a socket with the same call it would use on a blocking one, its signature says nothing, and no caller up
the chain is marked — the yielder travels in `Ctx` (`nvs-host`'s `scheduler::suspend`) precisely so that
this is possible.

Underneath, `read` is: **issue the syscall; on success return; on `WouldBlock` register, suspend, and
loop.** Optimistic, not pessimistic, and that order is the priority-3 decision in this ADR.

What each half costs, which is why the order is that way round:

| step | cost |
|---|---|
| the syscall that succeeds | one `recv`, and nothing else at all |
| the syscall that returns `WouldBlock` | one failed `recv` — tens of nanoseconds, no ready-list work in the kernel |
| registering interest | one `epoll_ctl` / AFD submission — the microsecond class, and the expensive half |
| the suspension | one stack switch each way, which `benches/abi-probe`'s `a_coroutine_round_trip_stays_cheap` holds to the tens of nanoseconds |

A poll-then-read order would pay the microsecond-class registration on **every** read including the ones
that would have succeeded, and the ones that would have succeeded are the common case: the first read of
an accepted connection almost always finds the request bytes already buffered, because they arrived with
the connection. Trying first costs one failed syscall in the case that parks, and nothing in the case
that does not.

A registration is **kept while the task holds the stream**, not torn down per park, so a stream that
parks repeatedly pays the modification and not the creation.

### 4. A task's stack: reserved wide, resident narrow, pooled per worker

Novis compiles natively, so a Novis call is a real machine frame and a task's stack has to be a real
stack. The decision, in the terms `rule:programs/memory-priority` asks for:

- **1 MiB of reserved address space per task, with a guard page.** Reserved, not committed: the pages a
  task never touches are never resident, on all three platforms, so a task that runs a shallow handler
  costs the handful of pages it actually uses. 100k concurrent tasks is therefore 100 GiB of *address
  space* — unremarkable in a 64-bit process — against a resident cost measured in the pages the handlers
  touched. The width is set by `rule:errors/on-limit`'s existing bounds pair
  and not chosen freely: `STACK_RESERVE` is already 256 KiB of unwinding room between the soft limit and
  the hard floor, so a stack has to be several times that before the two are coherent.
- **Charged to the request that owns the task**, and it is the *reservation* that enters `rule:http-server/a-wedged-core-is-detected-by-its-deadline`'s
  admission arithmetic, because address space is the resource an admission decision can actually count
  ahead of time. Resident growth is bounded by the same recursion limit that already bounds it.
- **Pooled per worker, bounded by that worker's in-flight cap.** A stack is an `mmap`/`VirtualAlloc`
  pair, which is the wrong thing to do per request on the hot path; a freed stack goes back to the
  worker's pool and is handed to the next task. The pool is O(in-flight) by construction — it can never
  hold more stacks than the worker has admitted tasks — which is the property `rule:programs/memory-priority` asks for, and the
  same shape the blocking pool in `rule:http-server/a-core-is-never-blocked-on-a-syscall` already has.
- **The host arms the recursion limit from the stack it just handed out.** `crates/nvs-runtime/src/ctx/mod.rs`'s
  module doc records a known gap — the call-stack ceiling is asserted from `STACK_CEILING` rather than
  discovered, because that crate has no way to learn a thread's true bounds. A task on a stack this
  crate allocated has no such gap: `nvs-host` knows the base and the length exactly and calls
  `Ctx::arm_stack_limit` with them, which is what that doc means by "an embedder that knows its bounds".

Every number here is **compiled in** for this goal. Making the stack size and the pool bound
configurable is goal `governance`'s `[limits]` work, and nothing below depends on which way that goes.

## Consequences

- **One stream implementation, not two.** Choosing readiness on Windows rather than completion is what
  buys this, and it is the simplicity half of the priority ordering being spent deliberately.
- **A blocking-looking read is honestly non-blocking**, so `rule:http-server/a-core-is-never-blocked-on-a-syscall`'s "a core is never blocked on a
  syscall" holds for the calls that have readiness — and the calls that have none still go to that
  section's blocking pool. There remains no third option.
- **A spurious wake is correct, not a bug**, so neither the reactor nor a stream needs to prove
  exactly-once delivery. That is what makes rule 2 above cheap to implement and impossible to get subtly
  wrong.
- **A developer sees no colour.** There is no `await`, no async member, and no second spelling of any
  `Core` member that touches I/O. The cost is that a stack is the unit of concurrency, so a task is
  ~1 MiB of address space rather than the ~100 bytes a stackless future would be — which is the memory-
  for-simplicity trade `rule:programs/memory-priority` exists to authorize, taken knowingly.
- **`mio` is a dependency of the trusted core.** It is pure Rust and it is the readiness layer under
  most of the ecosystem, but it is a new crate in the path every request takes, and its Windows back end
  is the least-travelled of the three.

## Alternatives rejected

- **IOCP completion semantics on Windows.** The native contract, and the faster one for very high
  connection counts: a buffer is handed to the kernel before the operation and the notification says it
  is filled. Rejected because it is a *different* contract — a completion-based read owns its buffer
  across a suspension, a readiness-based one does not — so every stream, and every helper that reads
  one, would exist twice. Novis's Windows support is a first-class target, not a port, which makes two
  implementations two chances to diverge on the platform that gets less traffic.
- **Hand-rolling epoll/kqueue/AFD.** Three `unsafe` FFI back ends with no Novis-specific content in any
  of them, against a pure-Rust crate whose whole surface is exactly this. `docs/ground-rules.md`'s
  implementation invariants point the same way: the interesting part here is the parking contract in
  § 2, not the ioctl.
- **`tokio`.** Excluded outright by the goal's standing decisions, and it would be the wrong shape even
  if it were not: its value is an executor and a task model, and Novis has its own — one that a stackful
  coroutine can suspend from *inside a helper*, which a `Future` cannot.
- **A stackless transform of Novis functions.** Would shrink a task from ~1 MiB of reservation to
  something tiny, and is how `async` languages get their concurrency counts. Rejected because it colours
  every function that can suspend, and the colour reaches the *language surface* — a `Core` member that
  reads a socket would need a spelling that ordinary code cannot call. That is priority 4 (simplicity of
  the language surface first) against priority 5, and the ordering in `AGENTS.md` decides it.
- **A per-task stack sized to fit more tasks — 64 KiB, say.** Rejected on arithmetic rather than taste:
  `rule:errors/on-limit` already reserves 256 KiB between the soft recursion limit and the hard floor, so a stack
  that small has no room for the mechanism that is meant to make recursion survivable.

## Verification

- A task that reads a socket with no data available parks, is woken when a byte arrives, and returns it
  — asserted through `std::io::Read` alone, with no scheduler-aware call in the test body, which is what
  proves the absence of colour.
- A woken task whose syscall still returns `WouldBlock` parks again and completes, so a spurious wake is
  a scheduling event and not a failure.
- A task that ends while registered leaves the reactor holding nothing, checked by count rather than by
  inspection, so a registration that outlives its request fails the test.
- Two tasks on one worker, one parked on a socket and one CPU-bound, interleave: the parked one does not
  starve the runnable one and the runnable one does not delay the parked one's wake beyond the poll.
- A `Ctx` on a host-allocated stack reports a recursion limit derived from that stack's real bounds, and
  deep recursion inside a task throws `ThrownClass::Recursion` rather than reaching a guard page.
- 100k concurrent parked tasks on one worker, with resident memory measured rather than assumed, against
  M5's own acceptance paragraph in `docs/plan/m5.md`.
