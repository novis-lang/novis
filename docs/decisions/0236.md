# ADR 0236 — An object literal at a declared shape takes the declared field types, and an existing value's `int` field does not satisfy a `float` one

- **Scope:** how an `int` value meets a `float` field of a shape: in an object literal written where a
  shape is declared, and in a shape value or object that already exists. The general `array<int>` →
  `array<float>` widening outside a shape is left to another record.
- **Depends on:** [0036](0036.md) (shape types and object literals), [0007](0007.md) and
  [0054](0054.md) (the `int` → `float` widening is the one implicit conversion).
- **Validated by:** `tests/conformance/lang/an-anonymous-object-at-a-declared-shape-takes-the-declared-field-types.nvst`
  and `tests/conformance/reject/an-existing-int-shape-field-does-not-widen-to-float.nvst`.

> **In short:** an object literal written where a shape is declared checks each field the declaration
> names against the declared field type, and a value that fits it gets that type: `{w: 2}` and
> `{w: $count}` at `{w: float}` are `{w: float}`, lowering converts the value where the literal stores
> it, and the slot is a `float` slot. A shape value or object that already exists keeps the field types
> it was built with, so the `int` → `float` widening does not reach its fields at any depth: `{w: int}`
> does not satisfy `{w: float}`, `{w: ?float}`, `{w: float|string}` or `{w: array<float>}`. The
> refusal stays `E0401`, with a help line that names the field and says to build a new value.

## Context

A shape's field types were compared by ordinary assignability, which includes the `int` → `float`
widening. An object literal's fields were typed from their own values, so `{w: 2}` was `{w: int}` and
was accepted at `{w: float}` by that widening. Nothing converted the value: lowering stored the `int`
as it was and recorded an `int` slot, and a read through the `{w: float}` view loaded the `int`'s bits
as a `float`. `2` printed `9.8813129168249E-324`. The same misread followed for a literal passed as an
argument, returned, placed in an array literal or written as an `int` variable or sum, for an existing
`{w: int}` value assigned to a `{w: float}` binding, and for a class with an `int $w` property passed
to a `{w: float}` parameter. A later `2.5` write into such a literal's field threw at run time,
because the slot was an `int` slot, and so did one into an `{n: int|float}` field built from `{n: 2}`.

## Decision

### 1. A literal takes the declared field types

`nvs_types::expr::literals::check_object_literal` reads the shape its position declares: the shape
itself, the shape inside a `?{…}`, or the one shape member of a union. Each field the declaration
names is inferred with the declared field type as its expectation, so a numeric literal is placed
there (`rule:types/numeric-literal-placement`). When the value is assignable to the declared type, the
field has the declared type and the checker records it at the field name's span. A value that does
not fit keeps its own type, so the assignment that follows reports the mismatch as before. A value
with a `secret` or `tainted` qualifier the declared type lacks also keeps its own type. A field the
declaration does not name keeps its own type.

`nvs_ir::lower`'s `lower_object_literal` reads that recorded type, lowers the value with it as the
expected type, converts the value to it, and records it as the slot type. `{w: 2}` stores `2.0` in a
`float` slot, and `{n: 2}` at `{n: int|float}` gets a tagged slot, so a later `2.5` write is accepted.

### 2. An existing value's field is compared without the widening

`nvs_types::expr::assign::shape_satisfied` compares a field with `field_fits`, which is
`is_assignable` without the `int`/`uint` → `float` row. The flag is passed down through every
recursion, so the row is off inside a union, an array element, a nested shape and a callable
signature in the field type. `{w: int}` still satisfies `{w: int|float}`, because `int` is a member.

An `array<int>` field read through an `array<float>` view gave the same wrong values, so it is refused
by the same rule rather than left accepted.

### 3. Union expectations

A union with exactly one shape member gives that member's field types to the literal. A union with two
or more shape members gives none, and the literal keeps the field types of its values.

## Diagnostics

`E0401` keeps its message. When the only reason a field fails is the missing widening, and the field
is an `int` or `uint`, the help line names the field and says to build a new value, for example
`{w: $value->w}`.

## Consequences

A literal at a declared shape costs one map entry per declared field at check time and nothing at run
time beyond the conversion it now performs. Code that passed an existing `{w: int}` value or an `int`
property object to a `{w: float}` position no longer compiles; it read wrong values before. A literal
at a declared shape with an `array<float>` field now accepts an array literal of whole numbers, which
it typed as `array<mixed>` before. Its elements are then read the way an `array<float> $a = [1, 2];`
binding reads them, which is the array question this record leaves to another.

## Alternatives rejected

Converting an existing value's field on assignment was rejected, because the value is shared: a
conversion would change what every other reference to it reads. Copying the value at the widening
was rejected for the same reason, and because it would make a shape assignment cost a copy.

## Verification

The two `.nvst` cases named above, and the reporter's reproducers, which print `2` and `2.5` where they
printed `9.8813129168249E-324` and threw.
