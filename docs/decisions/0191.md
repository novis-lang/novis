# ADR 0191 — A member's perf record is four counts that compare on any machine and one clock that compares on its own, and a bench declares what its first run must show

- **Scope:** what `docs/perf/members.ndjson` records per feature, which of it is comparable across
  machines and across days, how a bench with no history is judged, and what makes a figure stale. It
  does not reopen [ADR 0026](0026.md)'s two mechanisms — the per-PR guards and the instruction-count
  dashboard stay as they are — and it does not add a column for another engine.
- **Depends on:** [0134](0134.md) (the four proofs, and the ledger as one of them), [0026](0026.md)
  (wall clock is not comparable across machines; instruction counts are), [0079](0079.md) § 15 (what
  a benchmark of Novis code is, and its counter stream), [0018](0018.md) (the probe sites every
  compiled unit carries).
- **Validated by:** `crates/nvs-runtime/src/ctx/trace.rs`'s
  `count_totals_statements_and_calls_and_files_nothing`, and `tools/dossier.py --record-perf` over
  `benches/members/core/Str/length.nvs` and its `.scale.nvs` sibling.

> **In short:** a perf record is four counts — statements executed, calls made, allocations, bytes,
> per operation — and one clock. The counts come from `nvs run --count`, are bit-identical on every
> machine for the same commit, and are the columns the report diffs and flags; the clock keeps its
> machine fingerprint and is diffed only against the same one. A bench may declare what one operation
> should count and how its cost may grow with the input, and `--record-perf` judges the very first
> run against that rather than against history: a bench that misses what it declared writes no record
> and fails the sweep. A figure is current while the implementing file's text, minus its `mod tests`,
> is unchanged. What the counts cannot see — a `Core` member doing more work inside one helper call —
> is accepted and written into the rule.

## Context

### 1. A ledger of wall clock forks the day the machine changes

The ledger as [0134](0134.md) § 4 wrote it recorded one figure per feature: nanoseconds per
operation, the fastest of a few runs, with the empty program's start-up subtracted and a ratio
against a calibration loop taken in the same sweep. Every record carried a machine fingerprint, and
the report refused to print a delta across two fingerprints, because [0026](0026.md) had already
found that no honest one exists.

That is correct and it is not enough. The ledger is committed and shared, so the moment a
measurement is taken on a different box — a new machine, a colleague's, the WSL leg instead of the
Windows one — the history forks: a fresh section with no delta until it has two readings of its own,
and the old section goes quiet. The one column meant to survive the change, `units`, divides out
clock speed and nothing else, and the rule itself says it is good to about a tenth. For the question
the ledger exists to answer — *did this member get slower since it was last measured, wherever that
was* — a clock alone does not deliver.

### 2. The purpose is finding problems, not certifying speed

The user's framing of what the perf proof is for: *find problems and optimization opportunities.*
That sets the bar. A number on its own says nothing; it needs a yardstick, and the ledger's yardsticks
were all historical — a previous reading, on the same machine, of the same feature. A first run had
none, and a run after a machine change had none either.

### 3. What is already deterministic

[0018](0018.md)'s probe sites are in every compiled unit — a load-and-branch at every statement
boundary and around every compiled call — and `rule:testing/bench-counters` had already decided that
counts read off them are *bit-identical across machines, operating systems and architectures, because
they count what the program did rather than what a CPU did.* The allocator counts requests and bytes
per thread in every build, because a memory cap nothing counts against is not a cap. All of that
existed; none of it reached a bench.

## Options considered

### 4. Four ways to a cross-machine figure, and the cost of each

- **Retired-instruction counts under callgrind**, [0026](0026.md)'s dashboard mechanism. Reproducible
  to six figures, and a bench under it runs tens of times slower than native, only on Linux or WSL.
  Hundreds of member benches per goal would move the perf step of every dossier goal to a second
  runner and price it in minutes rather than seconds. Declined.
- **Hardware performance counters** through `perf stat`. Near-deterministic and nearly free — and
  unavailable on Windows, and not exposed to WSL2 without host configuration. Declined.
- **A better calibration**, several reference loops instead of one. Still a proxy for a clock,
  still not a tenth better than a tenth. Declined.
- **Semantic counts** — statements, calls, allocations, bytes — from the probe sites and the
  allocator that are already there. Exact, free to take, on every platform, and blind to exactly one
  thing (§ 7). Taken.

### 5. How a first run is judged

With no history there are three yardsticks, each answering a different question, and the record
carries all three:

- **What the bench declares.** Most members have a cost the author can state before measuring — a
  member that returns a scalar allocates nothing per call. Stated in the bench as
  `// bench: allocations 0`, it becomes a guard the sweep checks on day one. This is a guard test and
  not a hand-written cost table, which `rule:testing/bench-counters` refuses: nothing here is a claim
  about a member, only a check a bench fails.
- **Scaling within one run.** A bench that declares `// bench: complexity constant` and has a
  sibling `<name>.scale.nvs` over an input K times larger is timed at both sizes seconds apart on the
  same machine. The ratio of the two figures is the shape [0026](0026.md)'s per-PR guards already use
  — self-relative, loose, order-of-magnitude — and it is the only wall-clock comparison that survives
  a machine change. It is also the only check that sees inside a Rust member.
- **Siblings in the same group.** Once a class has its figures, members of the same complexity
  cluster in `units`, and one far above its neighbours is a candidate. This is a report view, not a
  gate, and it is the comparison most likely to surface an optimization.

## Decision

### 6. The record

One record per feature per sweep, appended to the ledger, holding: the four counts per operation
with the empty program's share subtracted; the clock — fastest and median of the reps — with the
calibration ratio; the machine fingerprint; the commit, whether the tree was dirty, a hash of the
`nvs` binary that ran, and the implementing file's `impl_commit` and `impl_hash`; what the bench
declared, and the scaling ratio where a sibling exists. `nvs run --count` is the source of the four
counts: it sets `DebugFlags::COUNT` on the run's context, the two probe slow paths increment two
words under that bit and record nothing per site, and the allocator's per-thread totals are read
across the run. The line is printed on stderr, so a program's stdout is what it always was.

### 7. What the counts cannot see is written into the rule

A `Core` member is a helper, not a compiled call site. To the probes one call to it is one call
whatever it does inside, so a member rewritten to walk the whole string would move neither
`statements` nor `calls`; only the allocator sees into it. A member that got slower without allocating
is invisible to every count and visible only to the clock on one machine, and to the scaling ratio.
That gap is accepted and the rule says so, because an extra allocation or copy is the common
regression and a pure compute regression in a leaf member is rare. The report's *Candidates* section
is where the clock still earns its place.

The counts compare across commits of one compiler tier. An optimising tier would eliminate statements
and inline calls, which `rule:testing/bench-counters` already names; while there is one tier, the
commit identifies it.

### 8. A bench that misses what it declared is a failing proof

No record is written and the sweep fails, exactly as an example whose output disagrees with its
`.out` does. `rule:testing/a-failing-proof-is-fixed-or-recorded` names the two answers, and a
`// dossier: known-gap` marker on the bench is the second: the record is then written with the
findings in it, the sweep counts it as a known gap, and the report lists it as a candidate.

### 9. Currency is the implementing file's text, not its commit

A figure is current while the hash of the implementing file's text, with its trailing `mod tests`
cut off, still matches. The commit was the wrong key for a reason the dossier's own fan-out exposes:
a session splices its features' Rust tests into the implementing file *before* the parent measures,
and a figure keyed on the commit went stale at the wrap that committed those tests — every session
re-owing what it had just taken. A test is not the implementation; a comment still is, and staling on
a comment is the conservative direction.

### 10. The report

Three parts, in the order they are worth reading: the counts, one row per feature, diffed against the
previous record wherever it was taken; the candidates — a `units` figure more than a policy-set factor
above its group's median, past the ceiling the policy sets for its declared complexity, or a bench
recorded as a known gap — advisory, never a gate; then the clock, per machine, with a delta marked as
inside the spread when the median says so.

## Consequences

- **A measurement costs one more run per bench** — the counting run is separate from the timed
  ones, so the clock stays clean — and one more per bench that has a scaling sibling. Still under a
  minute per goal, and only for features whose figure is stale.
- **The five records on disk before this decision carry no counts and no `impl_hash`**, so they are
  stale and their features are owed a figure again. That is one command, and they were owed other
  proofs anyway.
- **A generated dossier goal's workers write declarations into their benches** where the author
  knows them, and the parent's `--record-perf` step can now fail on a bench and not only on a missing
  one. The generated prose already routes that through the fix-or-record rule.
- **`nvs run --count` is a user-facing flag**, and its one stderr line is the format
  `tools/dossier.py` parses. Changing the line is changing the tool.

## Alternatives rejected

- **Refusing to record on a dirty tree.** Every record on disk said `dirty: true`, which is the
  symptom the refusal was meant to cure — a `commit` that does not name the code that ran. It would
  have fired on every dossier session, because the tree is dirty with the session's own proofs when
  the parent measures. The `impl_hash` and the binary hash name the code that ran directly, and
  `dirty` stays as a fact about the tree.
- **A per-member cost table** — an absolute `units` ceiling per member, hand-written. Refused by
  `rule:testing/bench-counters` for the reason it gives: a number with no guard test. The per-
  complexity ceiling in the policy file is one number per shape, advisory, and never a claim about a
  member.
- **A PHP column.** Excluded by [0134](0134.md) and by the user's standing decision; the userland
  benches own that comparison.
- **A symmetric scaling check** — refusing a `linear` bench whose ratio falls short of K as well as
  one that exceeds it. A linear member over a short input is dominated by its fixed per-call cost and
  looks nearly constant, which is not a bug. Only growing faster than declared is.

## Revisiting

When a second compiler tier lands, the counts stop comparing across the tier boundary and the record
needs to say which tier compiled the bench. Until then the commit identifies it.
