# ADR 0279 — Novis keeps its own files in one data folder, `.nvsdata` beside the binary unless `--data` names another, and its `nvs.toml` is the third step of the configuration lookup

- **Scope:** where Novis keeps the files it makes for itself — the default configuration file, the
  compiled-code cache, the temporary-directory root and the language server's stub tree — how that
  folder is found, created and checked, where a project command's implicit `nvs.toml` goes, and what
  `nvs service install` stores, prepares and grants for it. Not in scope: the configuration keys that
  move each of those paths, which keep their meaning and only lose their old defaults; the file's
  syntax and the merge, which stay [0103](0103.md)'s and [0064](0064.md)'s.
- **Depends on:** [0103](0103.md) (the configuration tree and the ownership check), [0093](0093.md)
  (the service installer), [0004](0004.md) (the priority ordering).
- **Validated by:** `crates/nvs-config/tests/resolve.rs` (the four steps), the tests in
  `crates/nvs-config/src/data.rs` (location, private creation, the check), `crates/nvs-cli/tests/run_command.rs`
  and `crates/nvs-cli/tests/init.rs` (the implicit write lands in the data folder and never in the
  working directory), and the plan tests in `crates/nvs-cli/src/service.rs` (the stored `--config`,
  `E0631`, `E0653` and the grant list).

> **In short:** Novis keeps everything it writes for itself in one folder, the data folder:
> `.nvsdata` beside the running binary (symlinks resolved), or the folder the global `--data <path>`
> flag names. Inside it are `nvs.toml`, `cache/`, `tmp/` and `lsp/<version>/`; `[opcache]
> file_cache_dir`, `[io] temp_root` and an editor's stub setting still move theirs. The data folder's
> `nvs.toml` is step 3 of the configuration lookup, after every `--config` and `./nvs.toml`, and a
> project command that finds no file writes the shipped template there — never into the working
> directory. Novis creates the folder private to its account; the default folder is checked without
> its parent, which is the binary's own directory. An unusable folder is one warning and the command
> keeps running. `nvs service install` with no `--config` stores the data folder's `nvs.toml`
> explicitly, prepares the folder, and gives a named service account read on it and write on its
> three subfolders only.

## Context

Before this record, Novis wrote its own files in four places, and three of them depended on the
platform: the compiled-code cache under `%LOCALAPPDATA%\novis\opcache` or `~/.cache/novis/opcache`,
the stub tree beside it under `stubs/<version>`, and the temporary-directory root as a `novis`
subdirectory of the system temporary directory. The fourth was the working directory: a project
command that found no configuration file wrote the shipped `nvs.toml` there, so `nvs run` in any
folder left a file behind in it. There was no one place an operator could look to see what Novis
keeps, nor one place to move it all, and the temporary root sat in a shared `/tmp`.

[0103](0103.md) had rejected a configuration lookup beside the binary: package upgrades replace
files under `/usr`, one binary serving several deployments would share one implicit file, and the
running binary's path is a platform question with a symlink policy. Each of those is answered below,
and the record's sentence "there is no lookup beside the binary" does not survive this one.

## Decision

### 1. One data folder, and what is in it

The data folder is `.nvsdata` in the directory of the running binary — `std::env::current_exe()`,
canonicalized so a binary reached through a link uses the folder beside the file it really is — or the
folder the global `--data <path>` flag names. A relative `--data` resolves against the working
directory, as every command-line path does (`rule:config/a-relative-path-resolves-against-the-file-it-is-written-in`).
Every subcommand accepts the flag.

| Path | What it is | The key that moves it |
|---|---|---|
| `nvs.toml` | the configuration file step 3 reads, and the implicit write's target | none: `--config` replaces the lookup |
| `cache/` | the compiled-code cache | `[opcache] file_cache_dir` |
| `tmp/` | the root under which `Core\IO::temporaryDir` creates directories | `[io] temp_root` |
| `lsp/<version>/` | the language server's stub tree, one per server version | the client's stub setting |
| `logs/nvs.log` | a service's log, when its configuration names no `[log] target` (§ 7) | `[log] target` |

The old locations are left as they are; nothing migrates, because each is a cache or a temporary
root whose contents are rebuilt on demand.

`nvs_config::data` is the one home of the name, the location, the five paths and the creation. The
CLI sets the folder once at startup, every reader asks the module, and a process that never set one —
an in-process test, a library caller — gets the folder beside its own binary.

### 2. Created private, never re-permissioned

The folder is created by one function the runtime's temporary directories use too. On Unix every
directory it creates is `0700` from the moment it exists. On Windows the topmost directory it creates
gets a protected DACL — full control for the current account, `SYSTEM` and `Administrators`,
inherited by everything below — because beside a binary the inherited ACL is not private. Only the
top directory carries its own DACL, so a grant added to the folder later, such as the installer's to
a service account (§ 6), still reaches the subfolders. A folder that already exists is never
re-permissioned: it is checked.

### 3. The default folder is checked without its parent

`rule:config/ownership-is-the-trust-boundary` checks a directory and the directory containing it. For
`.nvsdata` beside the binary the parent is the binary's own directory, and a stock Windows drive ACL
lets `Authenticated Users` modify a non-system drive's root and every folder that inherits from it, so
the full check would make the default folder unusable on most Windows machines. **The default folder
is checked by itself.** An account that can write the binary's directory can already replace the
binary, so examining that directory guards nothing the binary itself does not. A folder `--data`
names, and every path the configuration names (`[opcache] file_cache_dir`, `[io] temp_root`), keep
the full check, parent included. A file inside the data folder, its `nvs.toml` included, is checked
as any file is: itself and its directory, which is the private data folder.

### 4. The lookup gains a step, and the implicit write moves

The configuration root is found in four steps, first hit wins: every `--config` in order; `./nvs.toml`
in the working directory; the data folder's `nvs.toml`; the shipped defaults. Any `--config` disables
steps 2 and 3. The language server's per-document lookup takes the same steps with the document's
folder in place of the working directory.

**Novis never writes `./nvs.toml` on its own.** A project command — `run`, `serve`, `test`, `build`,
`check` — that reaches step 4 writes the shipped template as the data folder's `nvs.toml` and reads
it. `--no-init` and `NOVIS_NO_INIT` skip that one file; the folder and its subfolders are still
created. `nvs init` is unchanged: it writes `./nvs.toml`, or the one `--config` path, on request.

### 5. Which commands create the folder, and what an unusable one costs

`run`, `serve`, `test`, `build`, `check` and `lsp` create the folder and its three subfolders at
startup. Every other command — `config check`, `config dump`, `tmp clean` and the rest — only reads
what is there, so an audit never creates a folder.

A folder that cannot be created or fails the check is **one warning naming the folder, the reason and
`--data`, and the command keeps running**: no compile cache, no temporary root, no stub tree, no
implicit `nvs.toml`, and step 3 is skipped. `Core\IO::temporaryDir` throws only when a program calls
it. The one place that cannot hold is a test runner: `nvs test` and `nvs lsp-test` write their cases
under the temporary root, so with no usable folder and no `[io] temp_root` they stop with one error
naming `--data`. The conformance harness gives each case its own `--data` folder beside the case's
working directory.

### 6. The service installer stores the file, prepares the folder, and grants read

`nvs service install` no longer requires `--config`. With none, the stored argv gets `--config` and
the absolute path of the data folder's `nvs.toml` right after the subcommand — explicit, because a
service manager starts a service in `/` or `System32`, which must never be searched for `./nvs.toml`.
The data folder is the argv's own `--data`, which must be absolute like every stored path, else
`.nvsdata` beside the binary the service runs. Every check that ran over a named configuration runs
over that file.

An install that is not a dry run creates the folder privately and writes the shipped template there
if no file is there yet, before the service manager is asked for anything. When the folder cannot be
made or used and the stored `--config` is that folder's own `nvs.toml`, the install is refused with
`E0653`: that file is the service's whole configuration. With a `--config` elsewhere an unusable
folder is the usual warning, the install proceeds, and nothing is granted on the folder.

A named service account gets **read** on the data folder, on its `nvs.toml` and on every `--config`
file, and **read/write** on `cache/`, `tmp/`, `lsp/` and `logs/` only, each inherited only inside its
own subfolder; a configured log folder, `file_cache_dir` or `temp_root` outside those four gets its own
read/write grant as before. **The service account never writes its own configuration.** An uninstall
finds the data folder from the binary the platform holds for the service, not from the binary running
the uninstall, and revokes the same list.

### 7. Service log files

A service has no terminal, and its `stderr` is the journal or the Event Log, where a busy server's
records crowd out the service manager's own. So a process the service manager started — systemd's
`$NOTIFY_SOCKET` on Linux, the SCM on Windows, and `nvs service run`, which runs the same line in the
foreground — whose resolved configuration has no `[log] target` from any file writes to
`file:<data>/logs/nvs.log`. "No target" is read from the merge's origins, so a `target = "stderr"`
written in a file is kept. With no usable data folder the target stays `stderr`, after the one warning
every command prints. The command line keeps `stderr`. What is reported before the configuration is
read, such as a refused compile at boot, still goes to `stderr`.

Rotation and its cap apply to every `file:` target, the default and any target an operator names. Two
`System`-class keys, `[log] max_size` (default `"10M"`) and `[log] keep` (default `5`), bound it: the
target holds at most `max_size × (keep + 1)`, 60 MB by default. `keep = 0` deletes the full file and
starts a new one. A rotation that fails, such as a rename another program blocks, keeps the record in
the live file, prints one warning, and is tried again after another `max_size`; dropping records to
hold the bound would hide the failure the floor exists to report. Every writer in the process that
names one path shares one file and one count behind one lock, so the bound is per file, not per
writer, and the size is counted in memory with no `stat` per record.

Tradeoffs: security is better, because a log can no longer fill the disk by default; the request path
pays one lock and one comparison per record written to a file; the surface grows by two keys; memory
is one shared entry per open log path.

## Diagnostics

- **`E0631`** keeps its relative-path rows — `--config`, `--data`, the entry file, and the
  configuration's `[log] target` file, `[opcache] file_cache_dir` and `[io] temp_root` — and loses the
  "no `--config` at all" row, which § 6 completes instead of refusing.
- **`E0653`** is new: `nvs service install` cannot create or use the service's data folder, and that
  folder's `nvs.toml` is the stored configuration. It names the folder and the reason.

## Consequences

- **Security and request isolation:** slightly better. Temporary directories leave the shared system
  temporary directory for a folder only this account can write, and a service account can no longer
  write its own configuration.
- **Latency and throughput:** no change on the request path. Locating the folder is one
  `current_exe` and one canonicalization per process; preparing it is one create attempt per folder
  and the check's reads, once at startup.
- **Simplicity:** one lookup, one creation function and one check, where there were three
  platform-dependent defaults with a copy each. The operator has one folder to look in, back up or
  delete.
- **Memory:** none.
- **Usability, the cost:** a binary in a directory its account cannot write — a packaged
  `/usr/bin/nvs` run by an ordinary user — finds no usable default folder, prints the warning, and
  runs without a cache until `--data` names one. One binary serving several deployments shares one
  default folder; a deployment that wants its own passes `--config` or `--data`, and a service always
  stores one.

## Alternatives rejected

- **Keep the per-platform defaults.** Three locations an operator has to know, one of them shared with
  every other program on the host, and still a write into the working directory.
- **The full check on the default folder.** Correct in principle, and unusable on a stock Windows
  drive; it protects only against an account that could replace the binary anyway.
- **Read/write on the whole data folder for the service account.** Simpler to grant, and it lets the
  service rewrite the configuration that limits it.
- **A data folder under the user's profile.** It moves with the account, not with the binary, so two
  installed versions or a portable copy would share it, and a service account's profile is a place
  nobody looks.
