# ADR 0155 — The extension ships no binary, and a missing `nvs` is a guided install the user starts and can check for themselves

- **Scope:** how a VS Code user with no `nvs` on their machine gets one, and what the client may do
  about it without being asked. It does not decide Marketplace publishing, which [ADR 0099](0099.md)
  *Revisiting* still holds, and it introduces no toolchain version manager.
- **Depends on:** [0016](0016.md), [0099](0099.md).
- **Validated by:** the extension's headless suite — the target table checked against
  `.github/workflows/release.yml`'s build matrix, the series selection, and a tampered archive that
  has to be refused.

> **In short:** the extension bundles no `nvs`. When none resolves, the client does not fail with a
> sentence about `PATH`; it offers a **Download** command that fetches the release matching the
> extension's own `major.minor` series and verifies it against that release's `SHA256SUMS`, and a
> **Releases** command that opens the release page so a user can check the bytes themselves. The
> fetch happens because a user ran the command and never on its own, the copy it installs is the
> last thing tried after `nvs.path` and `PATH`, and it never writes `nvs.path`.

## Context

### 1. A first run with nothing installed is a dead end

The client spawns `nvs lsp` at `editors/vscode/src/extension.ts:100`: an empty `nvs.path` means the
bare name and the platform's own lookup. A user who installs the extension before the compiler gets
a spawn failure and a status item naming a binary they do not have, which is a message about the
problem rather than a way out of it.

The same shape appears one step later. `rule:ide/the-extension-refuses-a-binary-it-does-not-understand`
refuses a server outside the client's `major.minor` series, and `editors/vscode/src/version.ts`
spells the refusal *"Point `nvs.path` at a matching binary, or install the extension that matches this
one."* That is correct and it is still a dead end: the user is told what is wrong and left to find
the fix. ADR 0099 called the stale-`nvs`-on-`PATH` case the single most likely support question this
extension will ever get.

### 2. The release pipeline already emits what a safe download needs

`.github/workflows/release.yml` builds seven targets — `linux-x86_64`, `linux-aarch64`,
`linux-x86_64-musl`, `windows-x86_64`, `windows-aarch64`, `macos-x86_64`, `macos-aarch64` — packages
each as `nvs-<version>-<name>.tar.gz` (`.zip` on Windows), writes a `SHA256SUMS` over the set, and
uploads it beside the archives. Every archive also carries keyless Sigstore build provenance, so the
bytes can be traced to a run and a commit with `gh attestation verify`.

None of that was built for this decision, and all of it is what makes a download button something
other than a blind fetch.

## Options considered

### 1. Bundle the binary in platform-specific `.vsix` packages

The rust-analyzer shape: publish one artifact per platform with the server inside, and let the
Marketplace serve the matching one. Solves first run completely and needs no network code.

### 2. Download on activation, automatically

Fetch on first run when nothing resolves, without asking.

### 3. Guided install, started by the user

Detect nothing, explain, and offer the fetch as a command alongside a link to the release page.

### 4. Leave it at `PATH` only

What is on disk today.

## Decision

### 1. The extension ships no `nvs` binary

Option 1 is rejected on cost rather than on principle: seven publish legs, macOS codesigning, and the
executable bit through a zip, all to solve a problem that occurs once per user. The deciding argument
is not the cost though — see § 2.

### 2. Resolution order is `nvs.path`, then `PATH`, then the managed install

The client tries the explicit setting, then the platform lookup, then the copy this extension
installed, and uses the first that answers.

A bundled or managed copy must not outrank a toolchain the user installed themselves. The language
server's answer is a claim about whether the code compiles, and if the editor analyses with one `nvs`
while the terminal runs another, the editor is reporting on a program nobody is going to run. That is
priority 2 — correctness of language semantics — and it is the same invariant
`extensionKind: ["workspace"]` exists to protect in `rule:ide/the-extension-runs-where-the-binary-is`:
analyse with the binary that sits next to the code. A managed copy placed first would break it for
every user who has a real toolchain, which is every user who is past their first hour.

### 3. A missing binary is an offer, and the extension fetches nothing on its own

When no candidate resolves, the status item says so and the client surfaces two commands. Neither
runs unasked; there is no fetch on activation, no background update check, and no retry loop. An
executable arriving on a machine is something a person chose, every time.

### 4. The download takes the series the client speaks, not the newest release

The extension asks for the newest release whose version shares its own `major.minor`, because
`version.ts` will refuse anything else at `initialize`. Fetching "latest" and then refusing what
arrived is a worse first run than not offering the fetch at all.

### 5. Every downloaded byte is checked against the release's own `SHA256SUMS`

The archive and the `SHA256SUMS` come from the same release. The archive is hashed and compared
before anything is unpacked; a mismatch aborts, keeps nothing, and says which file failed. This is a
network fetch of an executable in a language whose first priority is security, and the file that
makes it checkable already ships.

The Sigstore attestation is the stronger proof and is deliberately *not* verified in-process — it
needs `gh` and a Sigstore client, which is a dependency and a second trust store inside an editor
extension. It is what the **Releases** command exists to let a careful user reach by hand.

### 6. The managed install never writes `nvs.path`

The copy lives under the extension's own storage and is remembered there. Writing the path into the
user's settings would outlive its usefulness: the day that user installs `nvs` through a package
manager, a stale absolute path silently keeps winning and their real toolchain is ignored. A setting
the extension wrote and the user did not is a support question with no visible cause.

### 7. The status item names the binary in use

`rule:ide/the-extension-builds-no-ui-the-editor-already-has` already puts server health in a
`LanguageStatusItem`. Which of the three candidates answered is part of that health, because with
more than one possible source the question "which `nvs` is this" has to be answerable without
guessing.

### 8. Two command ids, frozen here

`nvs.downloadBinary` and `nvs.openReleases`, added to the roster ADR 0099 § froze.
`rule:ide/contributions-are-frozen-and-only-ever-added` permits the addition and forbids the later
rename, which is why they are named in a record rather than chosen in an editor.

## Consequences

- **Security** — the extension gains a network fetch and writes an executable to disk. Both are
  user-initiated, one host, and hash-checked against an artifact from the same release. This is new
  surface and it is the reason § 5 is not optional.
- **Latency** — nothing on the request path; the fetch is a one-off on a machine with no compiler.
- **Simplicity** — one platform table in TypeScript that has to agree with the release matrix, and a
  test holds them together rather than a reviewer. Cheaper than seven publish legs, more than the
  nothing that is there today.
- **Memory** — one archive extracted under the extension's storage, per machine, once. Priority 5,
  spent without argument.
- **For a developer using the language** — the extension stops being useful only to people who
  already have the compiler, and a user who does not want the editor fetching anything keeps a
  working extension and a link.

## Alternatives rejected

- **Bundling, per option 1.** Rejected for § 2's reason first and cost second: a bundled copy either
  outranks the user's own toolchain, which breaks the invariant, or it does not, in which case it is
  a managed install that seven publish legs paid for.
- **Automatic download, per option 2.** Rejected. It is the same bytes as § 3 with the person taken
  out of the decision, and it turns the extension into something that fetches and executes code on
  activation.
- **`PATH` only, per option 4.** Rejected: it is where the dead ends in *Context § 1* come from.
- **Writing `nvs.path` to point at the managed copy.** Rejected in § 6 — visible, but it is a setting
  that outlives its reason and silently defeats a later real install.
- **Verifying the Sigstore attestation in the extension.** Rejected in § 5 as a dependency and a
  second trust store inside an editor process; the release page is where that check belongs.

## Revisiting

- **A setting that forbids the download outright**, if a locked-down environment asks for one. The
  offer is refusable per-invocation today, and a permanent switch is an addition
  `rule:ide/contributions-are-frozen-and-only-ever-added` allows whenever it is wanted.
- **A version pin in `nvs.toml`**, if managing several Novis versions per project ever becomes real
  work. It would slot into § 2's order between `nvs.path` and `PATH` and change nothing else. Not
  scheduled: it is a problem a language acquires with deployed code, and this one has none yet.
- **Marketplace publishing** stays exactly where [ADR 0099](0099.md) *Revisiting* left it. This record
  decides how a binary is obtained, not how the extension is.

## Verification

- The platform table maps every `(process.platform, process.arch)` pair the extension claims onto an
  archive name that `.github/workflows/release.yml`'s matrix actually builds, and a test fails when
  either side gains a target the other does not have. Alpine resolves to the musl archive.
- The series selector, given a release list spanning several `major.minor` series, picks the newest
  release in the client's own series and never a higher one.
- An archive whose bytes do not match the `SHA256SUMS` entry is refused: nothing is unpacked, nothing
  is left behind, and the failure names the file.
- With a managed copy installed and an `nvs` on `PATH`, the client spawns the one on `PATH`; with
  `nvs.path` set as well, it spawns that. The status item names the one it used in all three cases.
- No code path reaches the network without a command having been invoked.
