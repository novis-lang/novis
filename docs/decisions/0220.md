# ADR 0220 — a perf figure is current against its implementing file's code, so a comment, a card or a reformat stales nothing

- **Scope:** what a member-perf record's `impl_hash` is a hash of, and what that means for the
  records already in the ledger. It does not change what a record measures, how the report compares
  two records, or which binary measures.
- **Depends on:** [0191](0191.md) for the ledger's counts and its currency by text rather than commit;
  [0134](0134.md) for the feature proofs that owe a figure.
- **Validated by:** `bun nv proofs --owed` and `python tools/dossier.py --owed` print the same list
  before and after the ledger migration, and `bun nv parity proofs`.

> **In short:** `impl_hash` is the implementing file's `card` tier — its tokens with comments, layout,
> inline test modules and reference-card constant initialisers removed — computed by `bun nv proofs
> --impl-hash`. A reference chapter that implements a language feature is hashed as its text. Every
> record whose old hash matched its file on disk was rewritten to the new hash in the same commit, so
> no current figure became owed.

## Context

A figure was current while the implementing file's text, with its trailing `mod tests` cut off,
hashed to the record's `impl_hash`. That text includes every comment and every reference card, and
most `Core` member files carry their cards beside the code (`rule:core-api/reference-card`). A
session writing cards, rewording a doc comment or running `rustfmt` therefore staled every figure in
the file. The next sweep then owed a re-measurement that could not come out different, and a
measurement needs an idle release build. The build keys already had a tier that ignores exactly
these edits: `card`, in `tools/nv/keys/scan.ts`, which a check that only runs programs keys on.

## Decision

### 1. The hash is the `card` tier

`implHash` in `tools/nv/proofs/collect.ts` hashes a `.rs` implementing file at the `card` tier of
`analyse`. It drops comments, layout, the body of every inline `#[cfg(test)]` module and the
initialiser of every constant of a card type. What is left is what the compiler turns into the
shipped binary, with a card's text blanked. Any other implementing file, such as a reference
chapter under `docs/reference/`, is hashed as its text with line endings made `\n`. The digest is the
build keys' own 32-hex-digit blake2b, so an old record and a new one are told apart by length.

### 2. One implementation

`dossier.py` reads the hash from `bun nv proofs --impl-hash`, once per audit for every implementing
file, and has no hashing of its own. The two tools cannot disagree about which figure is current
while both exist.

### 3. The ledger is migrated, not re-measured

Every record whose 12-digit old-form hash matched a file on disk now carries that file's new hash. A
record whose old hash matched nothing was already stale and keeps its old value, which the new hash
never equals.

## Consequences

- A comment, a doc comment, a card, a reformat or a new test in the file no longer costs a
  re-measurement.
- An edit to a string literal, an attribute or any token of shipped code still stales the file's
  figures, as before.
- A file with a bidirectional-text character in any comment has all its comments folded into every
  tier, so its comments stale its figures, as the build keys do.
- The granularity is still the file.

## Alternatives rejected

- **The `shipped` tier**, which keeps cards. A card is text a hover and `nvs agent show` print, and
  the bench never reads it.
- **A per-member hash.** It would need the registry's dispatch mapped onto source ranges, and the file
  already errs in the safe direction.
- **Re-measuring the whole ledger instead of migrating it.** It re-times hundreds of unchanged
  members on one machine and proves nothing a hash comparison does not.
