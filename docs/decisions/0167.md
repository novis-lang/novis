# ADR 0167 — A coding agent learns Novis by asking the binary, and every adapter that points it there carries no language content of its own

- **Scope:** how an agent writing Novis gets what it needs — the surface it asks, what that surface
  answers, and what an install writes into a user's project. It decides nothing about the language,
  nothing about `nvs-lsp`, whose audience is an editor rather than a model, and nothing about the
  one-file reference, which keeps the job [0089](0089.md) gave it.
- **Depends on:** [0089](0089.md) for the reference pipeline, and `rule:tooling/one-json-several-renderers`
  for the shape a fourth consumer joins.
- **Validated by:** `tests/conformance/tooling/` — the index resolving member for member against the
  registry, and every refusal the primer states proven against the compiler that refuses it.

> **In short:** Novis is new, so no model has distilled it, and the whole reference is far larger than
> a context window. The answer is not to ship a smaller document but to make the compiler answerable:
> `nvs agent` prints a short primer, searches a one-line-per-member index and shows one card, all
> rendered from the registry the binary already carries. An agent then reads about two thousand tokens
> once and pays a few hundred per lookup, instead of reading the repository. `nvs agent init` writes
> one pointer file per harness, and a pointer never states a language fact, because a stated fact is a
> copy that goes stale the day a member changes.

## Context

### 1. Nothing has distilled this language, and nothing will for a while

A model writes PHP, Python and TypeScript well because those languages saturate its training data.
Novis is not in any model's weights and will not be until well after it is published, so every agent
that writes it does so from documents supplied at the time it writes. That is a permanent condition
for the early life of the language and a temporary one after — and the mechanism that serves it must
therefore be cheap enough to run on every session, not just impressive once.

The prior a model *does* hold is the problem rather than the absence of one. Novis reads like PHP and
refuses most of PHP's spellings, so an agent's confident guess is systematically wrong in a way that
an unfamiliar syntax would not be. The most valuable sentence available to it is not what Novis has;
it is what Novis refuses and what to write instead.

### 2. The reference is complete, and that is why it cannot be read

`docs/novis.md` is generated from the registry and every example in it is executed before it ships
(`rule:tooling/one-json-several-renderers`), so it is correct by construction and it is also 1.2 MB —
about 300k tokens, more than a context window, for a file whose reader was defined as "a search
engine, a language model, a person". The language half is small: the hand-written chapters under
`docs/reference/lang/` total ~207 KB. The library half is what is large, and it is the half that is
perfectly indexable, because it is a registry of 125 classes and 653 members rather than prose.

Flattened to one signature per line, the entire `Core` surface is ~38 KB. That number is the whole
argument of this record: **an agent can hold every name the language has and still have its context
window.** What it cannot hold is the prose around them.

## Investigation

Three agents were given the same task — read a CSV, sum a column, print one line — and the same
compiler, and differed only in what documentation they held. None had seen Novis.

| Arm | Held | Language correct at |
|---|---|---|
| A | the whole repository, no pointer to anything | after reading four examples and three reference pages |
| B | a generated primer, and a **broken** pointer to an index that was not there | the **first** `nvs check` |
| C | the same primer and the index beside it | the second `nvs check` |

Four findings, and each one decides a section below.

1. **The language stopped being the problem.** B and C wrote a correct program almost immediately.
   A got there too, by reading `examples/hello.nvs`, `files.nvs`, `arrays.nvs`, `numbers.nvs` and
   three `docs/reference/core/` pages — roughly 500 lines, of which the repository's own `nvs.toml`
   was 330 and taught it one line. That reading is what the primer replaces.
2. **The index is what answers "what is it called".** C reported grepping it as the single
   highest-value action available, resolving `Core\Csv::parse`, `Core\IO::read` and
   `Core\Math::format` in one call each, and — the case a prose document cannot serve — listing every
   class in the language with one `sed` when `Core\File` came up empty. An empty grep is a *fact*
   about the language, which is a thing only a complete list can give.
3. **B rebuilt the index from `nvs meta --json` when the file was missing**, unprompted, and then
   recommended the primer name that command rather than a file that can go missing. That is the
   strongest evidence available for the shape in § 1 of the Decision: an agent handed a broken
   pointer to a derived artifact reconstructs it from the binary, so the binary should have been the
   pointer.
4. **Every arm then spent most of its budget on the same wall, and it was not the language.** A
   correct, type-checking program that reads a file does not run: `fs.read` is deny-by-default and
   the grant lives in `nvs.toml`. All three hit it, none had been told, and two reverse-engineered
   the configuration schema by feeding `nvs config check` deliberate bogus keys and reading the
   `expected one of …` list back. Half of C's total effort went to that one hop.

Three narrower gaps the same run named, all of which the Decision closes:

- **The options bag has no call-site spelling anywhere in the primer.** A signature renders it
  `{header?: bool}` with no `$name`, and C read that as named parameters and wrote
  `Core\Csv::parse($text, header: true)`.
- **A `foreach` binding declares a type**, and the primer showed no `foreach` at all. B and C both
  guessed it from the destructuring rule; a guess is not a document.
- **A signature carries names and types and not behaviour.** `Core\Csv::parse` returns
  `array<array<string>>` whether or not `header: true` was passed, so nothing in the index says that
  flag rekeys each row by column name. C wrote `$row["amount"]` on faith. The card says it; the index
  cannot, and that is the line between them rather than a defect in either.

## Options considered

| | Ship a smaller document | Ship the index as a file | **Make the binary answerable** |
|---|---|---|---|
| Goes stale | on every release | on every release | never — rendered at the call |
| Install | a copy per project | a copy per project | one pointer file |
| Cost of a lookup | re-read the document | grep, modulo shell quoting | one call, bounded answer |
| Completeness | whatever the author remembered | mechanical | mechanical |

The middle column is what the experiment actually tested, and it is beaten on its own terms by a
detail neither the author nor the arms predicted: **`grep "^Core\\Str::"` silently matches nothing**,
because the shell eats the backslash in a namespaced name before `grep` sees it. C reported the trap
and the `grep -F` workaround. A command that does the searching cannot be quoted wrong, and an empty
answer from it is evidence rather than an artifact.

## Decision

### 1. `nvs agent` is the surface, and it is four read commands over the registry

    nvs agent primer            the primer, on stdout
    nvs agent index             one line per member, one line per enum, exception and attribute
    nvs agent find <query>      the index lines matching a query
    nvs agent show <symbol>     one member's card — signature, parameters, returns, throws

All four render `nvs meta --json`'s document and nothing else, which makes them a fourth arm on
`rule:tooling/one-json-several-renderers`'s diagram rather than a new source of truth. Nothing is
written to disk and nothing is cached: the binary that compiles the program is the binary that
answers for it, so the answer cannot describe a different version than the one installed.

`find` exists because `index` piped into a shell is the one operation the investigation caught
failing silently. `show` exists because a card carries behaviour and a signature does not.

### 2. The primer is generated, and its content is the four findings

It is rendered from marked sections of the reference chapters, the chapters' own front matter, and
the registry — never hand-maintained, so it cannot drift from the language. It carries, in this
order: the lookup protocol above; one complete worked program with every shape in it annotated —
a typed local, a `foreach` binding, an options bag at a call site, a conversion; the capability
model and the smallest `nvs.toml` that grants a file read; the refusal table; and the chapter map.

Its budget is a low four figures of tokens. That is not a length target on prose
(`docs/agent/doc-style.md` § *Length targets* is why there are none) — it is the property the artifact
exists to have, and it is met by what the primer *selects*, never by trimming what it says.

### 3. The capability table reaches the registry document, and every renderer joins on it

The wall all three arms hit is already declared: `rule:security/capability-declaration-is-one-table`
holds what each member needs in one table, `crates/nvs-stdlib/src/registry.rs`'s `CAPABILITIES`, and
that rule is `shipped`. It states two consumers — "the metadata command renders it, the reference
documentation prints it beside a member's card" — and **neither exists**:
`crates/nvs-cli/src/meta.rs` never reads the table, `nvs meta --json` has no `capabilities` key
beside its six, and `docs/novis.md` prints the word beside no card. The table is written, tested and
unread.

So this record adds no field to a member. `rule:tooling/meta-json`'s document gains the table as a
seventh roster, beside `exceptions`, `interfaces`, `attributes` and `directives`, which is the shape
the other four already have; every renderer then joins a member to its row, and `index` renders
`Core\IO::read(string $path): string  [fs.read]`. An agent reads the gate off the name of the thing
it is about to call.

**A per-member field is refused**, and not by this record: the table's own rule rejected that shape
because "what can this runtime do to my machine" must be one screen of one file rather than a
judgement about whether you found every class literal. Nothing here trades that away — the join is
at render time, the table stays the one declaration, and enforcement stays at the doors, which
consult neither.

It does not decide static capability checking, which is `nvs check`'s own outstanding item and
another goal's.

### 4. `nvs agent init` writes one pointer per harness, and a pointer carries no language content

It writes an `AGENTS.md` stanza, which is harness-neutral, and — where the harness is present — one
adapter beside it, such as a Claude Code skill at `.claude/skills/novis/SKILL.md`. Each names the
four commands, the `nvs check` loop, and nothing else. **No adapter states a language fact.** A
refusal table copied into a skill is a copy that goes stale the day a member changes, and the whole
mechanism above exists so that no copy is needed. The adapter list is open: another harness is
another twenty-line pointer, and adding one decides nothing.

## Diagnostics

Two messages the investigation caught being right and unhelpful, both fixed here:

- **An unknown member suggests the nearest registered name.** `Core\Str::lenght` reports `E0309`
  today with no suggestion, while the registry that holds `length` is in the same process. A
  diagnostic that names the fix is the cheapest documentation in the system — it is read only by the
  agent that got it wrong, and it costs nothing when nothing is wrong.
- **A capability denial names where the grant is written.** `Core\IO::read needs the capability
  `fs.read` for orders.csv, which is not granted` is precise about what happened and silent about
  what to do, and it cost the arms more than any other single sentence. It gains a `help:` line
  naming `nvs.toml` and the `[capabilities.fs]` table.

## Consequences

- **Memory and latency: nothing on the request path changes.** `nvs agent` is a CLI-only path over a
  document the binary already builds for `nvs meta --json`; no server, no isolate and no request ever
  reaches it.
- **The binary grows by one subcommand and one renderer**, which is the simplicity cost (priority 4)
  and the only one this record spends. The registry's new capability field is one enum-shaped value
  per gated member, held once per process rather than per request.
- **A user's project gains one small file per harness**, and it does not gain a vendored copy of the
  documentation, which is the outcome this record is arranged to avoid.
- **This repository's own sessions are a consumer.** A session writing a `.nvst` case or an example
  currently greps the spec for a member's spelling; `nvs agent find` is one call with a bounded
  answer, and it is the same call a user makes.

## Alternatives rejected

- **A smaller hand-written document.** It is the obvious answer and it is wrong twice: it goes stale
  on a language that is still adding members every goal, and its completeness is whatever its author
  remembered, so an empty search proves nothing.
- **An MCP server.** It answers the same questions over a protocol that fewer harnesses speak, needs
  a process to be running, and buys nothing over a subcommand that any agent can already invoke. It
  is a pointer like any other and can be added later without reopening this.
- **Vendoring the primer and index into the user's project.** Tested as arm C and beaten by arm B,
  which had no index and rebuilt one. On-disk copies go stale silently, add diff noise to the user's
  repository, and reintroduce the shell-quoting trap that `find` removes.
- **Teaching the agent through the LSP.** `nvs-lsp` answers an editor's questions at a cursor. An
  agent has no cursor, and most harnesses do not speak the protocol.
- **A size gate on the primer.** Trimming prose against a tripwire is a cost this repository has
  already paid once. The primer's budget is met by selection and held by nothing but review.

## Revisiting

- **When a model ships that already knows Novis.** The primer's refusal table is aimed at a wrong
  prior; a model without one needs less of it. The index and `show` are unaffected — a name is a
  name — so this trims one section rather than reopening the record.
- **If an agent is measured re-reading the primer within a session.** That is the signal that the
  protocol is not landing where a harness can hold it, and it is an argument about adapters rather
  than about content.
- **An embedded form**, `nvs agent init --embed`, writing the primer to disk for a sandbox where the
  binary cannot be invoked per session. Deliberately not built: nothing has asked for it, and it
  reintroduces staleness the moment it exists.

## Verification

- Every registry member has exactly one `index` line, and every `index` line resolves through
  `nvs agent show` — enumerated from the registry, so a member that lands owes its line at once and
  nothing is a hand-kept list (`rule:testing/roster-is-derived`'s shape).
- Every spelling the primer states as refused is fed to `nvs check` and is refused, and every example
  in it runs and prints what the primer says it prints — the discipline `docs/novis.md`'s examples
  already hold, applied to the one document that ships to strangers.
- `nvs agent init` in an empty tree writes exactly the declared files, and each one parses as its
  harness's format.
- A cold-start walk — `primer`, then `find`, then `show`, then `check` — runs end to end over a fixed
  task list with every step returning a resolving answer, so the protocol is proven navigable without
  a model in the loop.
