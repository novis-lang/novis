# ADR 0203 — a completion row reads as a declaration, and its card is read on resolve

- **Scope:** what a completion item carries on the wire — the label details an editor draws on the
  row, the `detail` it draws in the panel, the key its documentation is resolved by — what accepting a
  method writes, and the card a `Core` class carries of its own. It does not change which items are
  offered where, which is [0193](0193.md)'s, or what accepting a type writes, which is [0194](0194.md)'s.
- **Depends on:** [0193](0193.md) for the list, [0194](0194.md) for the follow text, [0117](0117.md)
  for the reference card in the registry.
- **Validated by:** `crates/nvs-lsp/tests/completion_edits.rs`, the `tests/lsp/completion/` cases,
  `crates/nvs-stdlib/src/registry.rs`'s `every_registry_row_carries_a_reference_card`.

> **In short:** a row used to be a name at the left and a string at the right — a method's signature, a
> class's qualified name — and the right column was all a reader had, far from the name and empty for
> most of the row's width. A row now shows what the declaration shows: `length(string $s)` with `int`
> at the right, `LIMIT = 10` with `int` at the right, `ErrorKind [Core\Db]`. The qualified name and the
> qualified signature move to the panel. What a name *does* is not on the row at all: each item carries
> a key, and `completionItem/resolve` reads the card for the one item the editor shows, which is the
> text hovering the declaration already shows. Accepting a method writes its call the way accepting a
> class after `new` does. A `Core` class gains a card of its own, one sentence, because the row is the
> one place a reader meets a class before its members.

## Context

### 1. The row said too little, and said it in the wrong place

A user of the VS Code extension reported two things about the list ([0194](0194.md) had settled what
accepting a name writes, not what a row shows). Neither a class row nor a member row said what the name
was for: `Debug` beside `Core\Debug` says where the class lives and nothing else, and `length` beside
`(string $s): int` makes the reader carry the name across the row to the signature. And the two-column
layout — a name at the left, a string at the right, the width of the widget between them — looked
empty, where another editor writes `Debug [App\Util]` in one run and puts only a type at the right.

The server built every row through one shape, `item(label, kind, detail)`, and set nothing else: no
`labelDetails`, no `documentation`, and `resolveProvider` off, on the reasoning that the detail was
already computed and there was nothing to save by a second round trip.

### 2. The information existed and was not sent

Every `Core` member row carries its reference card (`rule:core-api/reference-card`), and hover already
renders it. Every user declaration's `///` run is on its node, and hover renders that too. What did not
exist was a line for a `Core` *class*: `CoreClass` had no documentation field, and the reference pages
under `docs/reference/core/` cover a third of the registry's classes and are not compiled into anything.

### 3. What an editor draws where

LSP 3.17's `CompletionItemLabelDetails` has two fields: `detail`, drawn directly after the label with no
space, and `description`, drawn after that. VS Code draws `detail` in the label's own run, dimmed, and
`description` at the right of the row; an item's own `detail` is drawn at the right only where there are
no label details, and otherwise heads the documentation panel. The panel opens on a second Ctrl+Space
and stays open across sessions. So the same four fields let a row read as a declaration and let the
long text stay off the row.

## Decision

1. **A row shows what the declaration shows.** A method is `name(params)` with the return type at the
   right; a property or alias is its name with its type at the right; a constant or case is
   `NAME = value` with its type at the right where one is declared; a type offered by a shorter spelling
   than its qualified name carries ` [namespace]` after the label, and one offered by its qualified name
   carries nothing. The qualified name of a type and `Owner::name(params): ret` of a member are the
   item's `detail`, for the panel. `nvs_lsp::render` freezes the row as an editor draws it — the label
   with what follows it, the kind, the text at the right — so the `.lspt` corpus pins the row and not
   the wire.

2. **Documentation is resolved, never listed.** Every item carries a key under `data` — `{"type"}` for
   a type, `{"owner","member"}` for a member — and the server stamps the document's URI onto it.
   `completionItem/resolve` reads the card for that key: a `Core` member's reference card, a `Core`
   class's, enum's, constant's or case's line, a user declaration's `///` run, all through the renderer
   hover uses. A key naming nothing documented resolves to the item unchanged.

3. **Accepting a method writes its call**, on [0194](0194.md)'s terms for `new`: `name($0)` with
   signature help where a parameter is declared, `name()` where none is, plain text without snippet
   support, and nothing in front of a `(` already written.

4. **A `Core` class carries a `ClassDoc`** — one `short` — under `doc` on its row, printed by `nvs meta`
   under the class's `doc` key. The card guard fails a class without one, except the classes that
   landed before the field existed, which the test lists by name and which goal `core-class-cards`
   drains; a class that gains its card is deleted from the list the same session, and the test says so.

## Consequences

- **Latency:** a list carries a few bytes of key per row instead of a card per row; the round trip a
  resolve costs is paid once per highlighted item, never per keystroke. Nothing on the request path.
- **Memory:** a `ClassDoc` is a static string per class, per process — the cheap side of
  [0117](0117.md)'s trade.
- **Simplicity:** one more module, `nvs_lsp::card`, and five row shapes where there was one. The freeze
  format changed once, and every completion case was re-frozen at the new rendering in the same commit.
- **The `.lspt` renderer** cannot see `documentation`, so the card is asserted from Rust tests.

## Alternatives rejected

- **Cards on the list.** Simpler on the wire, and the bare-name list names every type in reach, so every
  keystroke would carry every card. Rejected on priority 3.
- **The namespace at the right.** That is the layout the report was about.
- **Reading a class's line from `docs/reference/core/` at build time.** Fifty of a hundred and
  seventy-seven classes have a page, and the page summaries are written in the repository's own voice.
  The registry is the one artifact that matches shipped behaviour, so the line goes where the members'
  cards already are.

## Revisiting

If a client without `labelDetailsSupport` matters, the server would need to fold the label details
back into `detail` for it; none of the two thin clients is such a client.
