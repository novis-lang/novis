# ADR 0111 — A PHP built-in completes to its Novis destination, and a completion item may only insert what the registry holds

- **Scope:** the PHP-name completion layer in `nvs-lsp` — which names a keystroke may match, where an
  item's text comes from, the rule deciding whether an item inserts anything at all, how the layer is
  built, and the one setting that turns it off. Not in scope: which `Core` member a given PHP name
  becomes, which is `docs/spec/02-php-migration.md`'s one row per name; what
  `nvs convert` does with those same rows, which is
  [0089](0089.md); the reference index and the other completion
  sources, which are [0108](0108.md)
  §§ 1–2; `Core` member completion itself, which is ordinary language completion and was M4B's; and M4B's
  frozen contribution set, which is [0099](0099.md) §§ 1–6.
- **Depends on:** [0108](0108.md)
  — its § 2 states the terms on which anything is admitted to a completion list at all.

> **In short:** Somebody arriving from PHP types the name they already know, and the editor answers with
> the Novis one. The layer doing it reads **two files with two different jobs**. The *candidate* set — what
> a keystroke may match — is the PHP inventory `tools/data/php-builtins.txt`,
> generated from the same build the differential suite uses as its oracle and therefore complete by
> construction. The *answer* — what an item says and inserts — is
> `docs/spec/02-php-migration.md`'s row for that name. Keeping them separate is
> the whole design: **every PHP name appears from the first day, whatever the table's coverage**, because a
> name that does not appear reads as *Novis cannot do this*, while a name that appears and says *not
> classified yet* reads as *Novis has audited this and owes you an answer*. A third file decides whether an
> item may type anything at all: **an item inserts only a `Core` member that `nvs-stdlib`'s registry
> actually holds**, so a destination the spec promises and no milestone has built yet is shown and is
> inert. Three of the four item shapes insert nothing, which is what stops a suggestion from ever producing
> a call that does not resolve. The layer is one table generated at build time from those three sources,
> and that join is itself a check — a destination spelling no registry row matches fails the build instead
> of shipping as a broken suggestion. `nvs.completion.phpNames` turns the layer off.

## Context

- **This is the adoption path at the keystroke.** `rule:programs/audience` names
  who Novis is built for, and `tooling/convert-one-table-two-modes` gives them a
  whole-codebase converter. Neither helps the developer who has switched already and is typing a name they
  have typed for a decade. Muscle memory is what survives a language change, and the names are the muscle
  memory.
- **Two of the three sources exist and are audited for another reason.** The inventory is generated by
  `tools/dump-php-builtins.php` from the PHP build the differential
  oracle already pins, and `python tools/check-migration.py` reports what share of it is classified. The
  migration table is machine-read by the converter under
  [0089](0089.md). Nothing here proposes a new table, and 0089's
  rule that neither translation table is copied into the other binds this reader the same way.
- **The registry, not the spec, is what "exists" means.** `crates/nvs-stdlib/src/registry.rs` is
  [01-core-library.md](../spec/01-core-library.md) in the form a compiler can read, and `nvs-types` seeds
  its signature table from it. The spec schedules its own classes across milestones — its § *Milestones*
  puts §§ 1–12 at M4S, §§ 14–17 at M8, and § 13 with whichever milestone closes each entry's dependency —
  so until the library is finished the registry holds strictly less than the spec names.
- **`rule:ide/completion-offers-only-what-the-compiler-derived`
  does not settle this either way.** Its rule is about offering a *value a program contains* — a route
  name, a directive — and refuses convention scans and annotation dialects as sources for those. A PHP
  built-in's name is not a value in anybody's program; it is a fact about a different language, held in a
  checked-in table. The rule as written neither admits nor refuses it, which is a gap to close rather than
  an exception to take.
- **This cannot be solved in the language.** A PHP spelling that resolves at runtime is exactly the second
  name `rule:statements/nothing-gets-a-second-name` removes. The editor is the only correct place for it, because
  the editor's output is the Novis spelling and the PHP one never reaches a file.

## Decision

**The editor offers every PHP built-in name as a completion candidate, answers each from the migration
table, and inserts only what the `Core` registry can resolve.**

### 1. The candidate set is the inventory; the answer is the table

Two sources, two jobs, and neither is copied into the other:

| | Source | Job |
|---|---|---|
| Candidates | `tools/data/php-builtins.txt` | what a keystroke may match |
| Answers | `docs/spec/02-php-migration.md` | what the item says, and inserts |

The consequence that motivates the split: **coverage of the table never gates whether the feature works**,
only how good an individual answer is. The inventory is generated from the oracle build, so the candidate
list is complete the day the layer ships, while the table is filled in one PHP domain at a time and is the
parity program's own measure. A name with no row is not missing from the list — it is an item that says so.

A name and a type share the inventory file; both are candidates, under the same rules below.

### 2. The registry is the gate

**An item may insert text only when its destination resolves.** The build-time join checks every
destination spelling against `nvs-stdlib`'s registry — the same table `nvs-types` seeds from, so "resolves"
means the same thing here as it does to the checker. A destination the spec promises and the registry does
not yet hold produces an item that appears, names the milestone it is waiting on, and inserts nothing.

This is the rule the whole layer rests on, and it is what keeps this ADR inside § 2 of
[0108](0108.md) rather
than beside it: a *name* may come from an audited table, but the *text an editor types on a developer's
behalf* still comes only from something the compiler can already resolve. An editor that inserts a call
which then fails to resolve is worse than an editor that offers nothing, because the developer has no way
to tell a suggestion's mistake from their own.

### 3. Four item shapes, three of which insert nothing

The migration table's four outcomes, plus the registry gate, give four shapes:

| Row | Item |
|---|---|
| `member` or `language`, destination registered | inserts it, with the signature the registry holds |
| `member` or `language`, destination not registered | appears, names the milestone, inserts nothing |
| `dropped` | appears, gives the row's reason and rewrite, inserts nothing |
| `open`, or no row at all | appears, says undecided, inserts nothing |

A missing row and an `open` row are one case, exactly as `check-migration.py` already treats them.

A row whose cell names more than one destination is **prose the converter may not guess at** under
[0089](0089.md), and is a genuine ambiguity there. It is not one
here: completion has a person in the loop, so such a row becomes one item per destination and the developer
picks. This is the single place where the editor can offer more than the converter, and it follows from the
human, not from a better table.

### 4. The layer is generated at build time, and the join is a check

The three sources are joined once, at build time, into a static table compiled into `nvs-lsp`. The server
reads no file under `docs/` at runtime: a shipped binary must not depend on the documentation tree, and a
sorted static array answers in the time a lookup takes.

**The join is a consistency check, and this is a benefit the feature buys rather than a cost it pays.** A
destination spelling in the migration table that matches no registry row is either a typo in the docs or a
member the registry renamed, and today nothing compares the two files at all. Under this decision that
mismatch fails the build. A destination that is merely *unbuilt* is not a mismatch — it is the second row
of § 3's table, and is distinguished by the spec naming it where the registry does not.

### 5. Position, ranking, and the one setting

- **Position.** These items appear only where a top-level identifier is legal. A PHP built-in's name is
  never a member, so the layer contributes nothing after a receiver or a `::`.
- **Ranking.** They sort below every real Novis symbol. The layer is a fallback for a name the developer
  has not learned yet, and must never outrank the name they are halfway through typing.
- **One response.** The set is returned complete, and the client filters it on subsequent keystrokes. It is
  a static table of a known size, so there is nothing to stream and no reason to make the editor ask again.
- **The label is the PHP name**, because that is what was typed and what the eye is scanning for; the
  Novis destination is the item's detail, and the inserted text where § 2 permits any.
- **`nvs.completion.phpNames`** — `all` (default) | `resolved` | `off`. `resolved` keeps only the items
  that insert something, for a developer who has finished migrating and wants the reminder layer quiet;
  `off` removes the layer. The split is on **answer quality**, not on a source, because "show me only the
  ones that go somewhere" is the request people actually have. It is added to
  [0099](0099.md) § 6's frozen roster under that section's rule.
- **The setting governs this layer only.** `Core` member completion is ordinary language completion and is
  never behind it — a setting that can switch off completion for the language itself would be a bug in the
  wiring, not a preference.

## Consequences

**Positive**

- The feature ships useful at any table coverage, and gets better as the parity program fills the table in
  for `tooling/convert-one-table-two-modes`'s sake anyway. No new maintenance
  surface: nobody writes a mapping for the editor.
- A `dropped` row's reasoning reaches a developer at the moment they reach for the removed function, which
  is the only moment it is worth reading. That prose was written once and is currently read by nobody until
  a conversion run produces it.
- Two files that describe the same members — the migration table and the registry — start being checked
  against each other, which nothing does today.
- The layer is one table and one lookup in `nvs-lsp`, so both editor clients get it from the same place,
  per `rule:ide/one-server-two-thin-clients`.

**Negative**

- **Most items answer "undecided" until the table is filled.** That is honest and still better than
  silence, but the first release is closer to a completeness signal than a migration aid, and it should be
  described that way rather than oversold.
- **A per-keystroke candidate set of the whole PHP surface is a lot of items** in one position of one
  language's completion list. Ranking keeps them out of the way; nothing makes them small.
- **The build gains a generator and a join** across a docs file, a data file and a Rust table — three
  things that can disagree, now failing loudly instead of quietly. Loud is the right direction, but it is a
  new way for a build to break.

## Alternatives rejected

- **PHP names as runtime aliases in `Core`.** Rejected outright by
  `rule:statements/nothing-gets-a-second-name`: a second reachable spelling for one member is the thing that ADR
  exists to remove, and it would leave PHP names in committed Novis source forever.
- **Candidates from the migration table alone.** Rejected: the feature would then cover only what has been
  classified, and a PHP name Novis has not yet audited would be indistinguishable from one Novis cannot do
  — the exact wrong signal, and it inverts as the table fills, so early users get the worst version.
- **Destinations from the spec alone, without the registry gate.** Rejected: the spec is a promise across
  several milestones, so the editor would insert calls that do not resolve, and the developer would have no
  way to tell the suggestion's mistake from their own.
- **A separate mapping table owned by the editor layer.** Rejected under
  [0089](0089.md)'s own rule against copying a translation table:
  two mappings drift, and the drift shows up as the editor and the converter disagreeing about one name.
- **Reading the migration table at runtime.** Rejected: it makes a shipped binary depend on the docs tree,
  and buys nothing a rebuild does not.
- **A boolean setting.** Rejected: it collapses "quiet the undecided ones" into "switch the feature off",
  and the first is what a developer part-way through a migration actually wants.
- **Hiding items whose destination is not built yet.** Rejected for the same reason as the `open` rows: a
  name that vanishes reads as a language that cannot do the job, where one that names its milestone reads
  as a language with a schedule.

## Verification

- Every function and type name in the inventory is a candidate: a completion request at a top-level
  identifier position returns one item per inventory entry, asserted against the file's own count so an
  inventory regeneration cannot silently shrink the layer.
- Each of § 3's four shapes is pinned by an `.lspt` case: a registered destination inserts its member text,
  and the other three insert nothing — the last asserted as absence of an edit, not as an empty string.
- A destination spelling in the migration table matching no registry row and named by no spec section fails
  the build, asserted by a fixture holding a deliberately wrong spelling.
- A row naming more than one destination produces one item per destination, and the converter's own tier
  for that row is unchanged by it — the two readers agree about the row and disagree only about what they
  are allowed to do with it.
- No item appears after a receiver or a `::`, and every item of this layer sorts after every `Core` member
  item in the same response.
- `nvs.completion.phpNames: "off"` returns a response with no item of this layer and every other completion
  source intact, which is the assertion that the setting is scoped to the layer and not to completion.
- The server reads no file under `docs/` at runtime, asserted the way the rest of the binary's
  no-runtime-docs assumption is.
