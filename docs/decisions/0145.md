# ADR 0145 — A schema is a value: `Core\Db\Schema` converges a closed vocabulary, and neither versions nor parses SQL

- **Scope:** what a database schema *is* in Novis — the closed vocabulary of tables, columns and indexes,
  its three interchangeable spellings, and the canonical form that makes them one thing; the diff against a
  live server and the normalization it needs; the three grades a difference carries and the rule for an
  unknown one; the plan as a pasteable document; the gate between planning and applying; and which crate
  owns each half. Not in scope: the member signatures, which are
  [spec § 18](../spec/01-core-library.md)'s and are designed against
  [0063](0063.md) like every other `Core` row; migration *semantics* — ordering,
  reversibility, dependency and fleet locking — which stay
  [0082](0082.md) § 7's deliberately blocked gap and are not opened here; the
  read direction of the SQL↔Novis type map, which is [0067](0067.md) § 9's and is only re-used;
  and how a driver puts bytes on a wire, which is
  [0132](0132.md)'s.
- **Depends on:** [0067](0067.md) — this has no storage engine, no connection, no statement and no
  identifier judgement of its own, and inherits all four.
  [0132](0132.md) — its sans-io seam is what decides
  that the vocabulary, the emitters, the introspectors and the diff are `nvs-db` and not `nvs-stdlib`.

> **In short:** a schema is **a value**, not a directory of scripts. It is written with typed builders,
> serialized to an array, or read back off a live server by catalog query — three spellings of one thing,
> pinned together by a round trip through the array form. A **plan** is the difference between such a value
> and what a connection actually holds, and that is the whole model: **no version number, no history table,
> no ordering, no `up`/`down`, no fleet lock**, and `Core` never learns what "a migration" is —
> [0082](0082.md) § 7 stays blocked. The vocabulary is **closed** — tables,
> columns, indexes, the constructs all five backends share — and there is deliberately **no raw escape
> hatch**, which is what makes the diff total and makes a vendor's new feature cost this project nothing.
> Reverse-engineering is **live introspection and never a SQL parser**: [0067](0067.md) § 10's
> refusal to own four vendors' grammars covers DDL too, and a catalog is structured tables rather than a
> language. Every difference carries one of **three grades** — `Safe`, `Locking`, `Destructive` — computed
> per dialect *and server version*, and **an emitter that does not know grades up**, so the one ageing part
> of the system is an annoyance rather than a correctness bug. **Absence never destroys**: a table or
> column the server has and the value does not is reported with the SQL that would drop it, and never
> dropped. Every step of a plan carries **complete, terminated, dialect-correct SQL**, including the steps
> `apply` refuses — so a dry run is useful against a database Novis will never be granted permission to
> write to. Planning is an ordinary read; applying takes a new deny-by-default **`db.schema`**, and the two
> entry points are named for what they risk.

## Context

`rule:core-classes/db-one-api` left a door in its *Revisiting* list — *"a portable `Core\Db\Schema`, **if
migration tooling in `nvs` itself needs it**, rather than userland"* — and the condition has since been
met from inside the runtime rather than from userland. [0084](0084.md) § 2 makes
the job queue's storage the one schema the runtime itself owns, created by `nvs queue migrate`, on all
five backends. What that turned into is `crates/nvs-stdlib/src/queue.rs`: four hand-written per-dialect
DDL string lists for **two tables**, a guard test whose only purpose is to stop those lists drifting from
each other, and a `migration()` that answers `None` for SQL Server and SQLite because nobody wrote their
arms. That is not a queue problem. It is the first instance of a job — *say what a table should be, and
make a server hold it* — that a web framework, an application and this runtime each need exactly once,
which is [0051](0051.md) test 6 arriving on schedule.

The prior art is unusually clear about where this goes wrong. Every schema tool that survives contact with
production converges on the same two failures. The first is **versioning as the model**: a numbered
sequence of scripts, a history table, an ordering constraint between changes, a lock so two instances of a
fleet do not run one script twice, and a `down` nobody ever runs and everybody maintains. That machinery is
real and hard — [0082](0082.md) § 7 enumerates it and deliberately does not
decide it — and it is not needed to answer the question actually being asked, which is *what is the
difference between this and that*. The second is **round-trip drift**: the server rewrites what you gave
it, and the tool reports a phantom difference it wants to re-apply forever. A unique constraint creates an
implicit index; `int(11)` loses its display width; a `varchar` is promoted; a default expression comes back
spelled differently; column order is not what you wrote. A tool that compares SQL text loses this fight on
the first release; a tool that compares normalized values can win it, and can *prove* it has won with one
property.

So the shape here is chosen to buy the second property while refusing to build the first. What is left is
small enough to be total, and total is what makes it trustworthy.

## Decision

### 1. A schema is a value, and its array form is canonical

`Core\Db\Schema` is a value with three interchangeable spellings, and no privileged one:

- **built**, with typed builders in Novis source — the spelling an application writes;
- **serialized**, to and from a plain array, which is therefore also a file through
  [0071](0071.md)'s codecs or `Core\Json`, and is what the user's "save the structure and
  read it back later" means;
- **introspected**, read off a live connection by catalog query (§ 4), which is what `nvs schema dump` is.

The array form is **canonical**. Two schema values are the same schema exactly when their array forms
agree, and the property that holds the three spellings together is `toArray(fromArray(a)) == a` over every
construct in the vocabulary. It is stated over the *array* rather than over the objects on purpose:
[0090](0090.md) § 4 makes `==` on two objects
identity, there is no `__equals` to override, and a schema value has no natural total order to give it a
`compareTo` — so the canonical form is the comparison, and it is also the thing a diff normalizes into.

The canonical form is therefore **ordered**, not merely structural: that same ADR's table makes key order
part of an array's value, so `toArray` emits tables, columns, constraints and indexes in a defined order —
declaration order for columns, since it is what a `CREATE TABLE` must reproduce, and name order for
everything else, since nothing observable depends on it. An introspector that returned the server's own
catalog order would otherwise fail the round trip on a database that is not wrong in any way.

This is one mechanism, not three. An introspection that produced something a builder could not is a bug in
the introspector; a file a builder cannot round-trip is a bug in the array form. Both are caught by the
same test.

### 2. The vocabulary is closed, and it never grows to chase a release note

The vocabulary is **tables, columns, primary keys, unique constraints and indexes** — the constructs all
five [0067](0067.md) backends genuinely share. A column carries a name, a type, nullability, a
default, and whether it is the table's **identity** — the server-assigned key that all five spell
differently (`GENERATED AS IDENTITY`, `AUTO_INCREMENT`, `IDENTITY(1,1)`, `INTEGER PRIMARY KEY
AUTOINCREMENT`) and none of them lacks. Nothing else. Identity is in rather than out because the rule for
admitting a construct is met exactly: every backend has it, it is introspectable, and a vocabulary in which
a table cannot have an `id` is not one anybody's schema fits into. It carries three rules the four
spellings share — an integer type, at most one per table, and in the primary key, which is SQLite's
requirement and the other four's assumption.

A **unique constraint is the canonical spelling of uniqueness**, and an index in the vocabulary is
therefore never unique. Admitting both would make one schema expressible two ways, which is the phantom
difference § 5 spends its normalization budget removing rather than a convenience.

The column type enum is **[0067](0067.md) § 9's type map in the write direction**. That map already
exists, is already tested in the read direction, and is now read both ways: one table used twice rather
than a second table to keep in step. The write direction is narrower by construction, because it must be a
function — one canonical SQL type per Novis type per dialect, chosen so that introspecting the result maps
back to the type that was written. Where § 9's read direction is many-to-one (`SMALLINT`/`INT`/`BIGINT` all
read as `int`), the vocabulary keeps the distinction the writer needs and the introspector can recover.

Defaults are a **closed set**: a literal of a vocabulary scalar type, or the current timestamp. There are no
expression defaults. That one rule closes two holes at once — an expression default is both an unbindable
string reaching a DDL sink ([0024](0024.md); a schema has no parameters
to bind through) and the value a server is most likely to spell back differently, which is § 5's whole
difficulty.

**There is no raw escape hatch.** No `Schema::raw()`, no `->rawSql()`, no opaque fragment anywhere inside a
schema value. Two things follow and both are the point. The diff is **total**: since nothing opaque can be
inside a value, there is no construct the plan is silently unable to reason about, and "this tool does not
understand part of your schema" is not a state that exists. And a vendor shipping a new feature costs this
project **nothing** — a new PostgreSQL index type, a MySQL column option, a SQL Server data type are all
outside the vocabulary and reachable through `Core\Db::execute` exactly as they are today, which is where a
statement a human wrote belongs.

The vocabulary grows only when a construct exists on **all five backends** *and* something concrete needs
it. Not because a release note appeared. § 11 lists what this rule keeps out of v1 and why each one is a
harder decision than it looks.

Identifiers are **validated, never delimited**. `Core\Db::quoteIdentifier` already made that judgement for
this project and it is not re-made here: a table or column name that is not a plain identifier is refused
at the point it enters a schema value, rather than escaped into safety by a second answer to a question
[0024](0024.md) allows only one answer to.

### 3. Convergence, not versioning — `Core` never learns what a migration is

A schema value says what the tables **should be**. A plan is the difference between that and what a
connection **has**. That is the entire model, and everything a versioned migrator carries is absent by
construction: no version number, no history table in the target database, no ordering between changes, no
`up`/`down` pair, no fleet lock, and no notion of "which migrations have run".

Convergence is what makes that possible. A plan is derived from the current state every time it is
computed, so it is correct after a manual change, after a partially applied earlier plan, and against a
database this tool has never seen — the three situations in which a history table is exactly wrong, because
it records what a tool believes rather than what is true.

**`Core` therefore holds no notion of a migration**, and this ADR does not open
[0082](0082.md) § 7. Ordering, reversibility, dependency between changes and
fleet locking remain that section's blocked gap; nothing in `nvs/web` may ship a migration runner until it
is decided. This is the layer such a runner would one day sit on, and it stops there deliberately: every
one of § 7's open questions is a question convergence does not have to answer, which is precisely why
convergence is what got built.

### 4. The reverse direction is live introspection, and there is no SQL parser

Reading an existing database is **one catalog reader per driver**, answering the same schema value a
builder produces: `information_schema` for MySQL, MariaDB and SQL Server, `pg_catalog` for PostgreSQL, and
`sqlite_master` with `pragma table_info`/`index_list` for SQLite.

There is **no DDL parser, at any tier, in any form** — not "just for the CLI", not "best-effort", not "just
for `CREATE TABLE`". [0067](0067.md) § 10 already refuses to maintain four vendors' query grammars
in `nvs-syntax` forever, and that reasoning does not weaken for DDL, where the dialects diverge more rather
than less. Introspection is also the *better* answer, not merely the cheaper one: a catalog is structured
tables rather than a language, the `CREATE TABLE` a server prints came from that server's own catalog
anyway, and the introspector must exist for the diff regardless — so a parser would be a second, worse
implementation of a job already done, which is [0051](0051.md) test 6 again. If
offline `.sql` input is ever wanted, it is a separate tool with its own decision and its own ADR.

### 5. The diff compares normalized values, never SQL text

The diff runs over the canonical form of § 1, after normalization, and never over emitted or retrieved SQL.
Normalization is where this class of tool lives or dies, and the cases are known in advance: a unique
constraint's implicitly created index, integer display widths, `varchar` promotion and length units, column
order, case-folding of identifiers where a server folds them, and the server's own spelling of a default.
Each is normalized *out* on both sides before comparison, so that a value written by a builder and the same
value read back off the server it was applied to are literally the same array.

That is not asserted by inspection. **The acceptance criterion is one property**: apply a schema to a real
server, introspect it back, and assert the resulting plan is **empty** — on all five backends. Every
normalization rule exists because that property failed without it, and a normalization nothing needs is a
rule this system does not carry. It is also the reason § 11's exclusions are what they are: a construct
that cannot yet be round-tripped emptily is not in the vocabulary.

### 6. Three grades, and an unknown grade grades up

Every step of a plan carries a grade, and there are three rather than two:

- **`Safe`** — cannot lose data, cannot fail on existing rows, cannot hold a long lock.
- **`Locking`** — cannot lose data, but can fail or block writes for a long time. A unique index over data
  that already contains duplicates, `not null` on a populated column, a type change that rewrites the
  table.
- **`Destructive`** — can lose data.

Two grades would have to merge the middle into one of the outer ones, and both merges are wrong in
production: calling a table rewrite `Safe` is how an "automatic" tool takes a site down without losing a
byte, and calling it `Destructive` makes the dangerous class so large that operators stop reading it.

A grade is **computed by the dialect emitter, keyed on driver *and* server version**, because the same
statement is not the same risk across versions — adding a column with a default is instant on PostgreSQL
11+ and MySQL 8.0.12+ and a full table rewrite on older servers. **When the emitter does not know the
server's version, or does not have a rule for it, it grades up.** That single rule is what keeps the one
part of this system that ages harmlessly: an out-of-date grader over-reports risk, which costs an operator
a confirmation, where an out-of-date optimist costs them an outage. A grade is a floor, never a promise
that a step is cheap.

**SQLite's non-additive alters go through create-copy-drop-rename, graded `Destructive` unconditionally.**
Its `ALTER TABLE` can add a column, rename one (3.25+) and drop one (3.35+), and essentially nothing else,
so anything past that is a rebuild — and a rebuild copies data, which makes `Destructive` the honest grade
rather than a concession. Refusing the rebuild outright would make SQLite second-class in the one place a
dev-machine SQLite is most useful.

### 7. Absence never destroys

A table, column, constraint or index present in the database and **not** present in the schema value is
**reported** by the plan, with the complete SQL that would drop it, and is **never dropped**.

This is not conservatism about a risky default; it is the only reading that survives a shared database. A
schema value describes what its author knows about, and an application legitimately shares a server with
another application, a reporting view, an operator's own table and — under
[0084](0084.md) — the queue's own two tables. A converger that treated its own
value as the complete truth of the database would drop every one of those on the first run.

Dropping is therefore an operation someone **writes**, and it is `Destructive`. There is no `--prune`, no
`allowDrops` and no strict mode: the escape hatch for "I really do want that gone" is the SQL the plan
already printed, in the same `Core\Db::execute` that has always been where a statement a human wrote goes.

A report is a step the plan **carries and never applies**, and that distinction is what keeps § 9's
`applySafe` usable at all: every plan against a shared database holds reports, they are `Destructive` by
the paragraph above, and a rule reading *every* step's grade would therefore refuse every plan ever
computed against a real database. `applySafe` reads the grades of the steps it would **run**. Both kinds
are counted, printed and given complete SQL — a report the plan did not show would be worse than one it
will not apply.

### 8. The plan is a document, and every step carries complete SQL

A plan is a value whose steps each expose their grade, the reason for that grade, and **complete,
terminated, dialect-correct SQL** — including the steps this tool will refuse to run. `nvs schema plan`
prints all of it.

That last clause is what makes a dry run worth having. The common case in a serious deployment is that the
application's own database credentials cannot issue DDL at all, and the change is applied by a DBA, in a
change window, from a ticket. A plan whose risky steps are elided into "3 unsafe changes" is useless to
that person; a plan they can paste is the whole product. It also makes the tool honest about its own
limits: a step Novis will not apply is still a step Novis is willing to show you in full.

Emitters follow **`Dialect`, not `Driver` — four, not five**. `nvs_db::Dialect` is already four values for
five drivers because MariaDB and MySQL share SQL text exactly and differ in auth plugins and error tables,
neither of which reaches DDL. Nothing here re-splits them.

### 9. Planning is a read; applying is `db.schema`

`planAgainst` is an ordinary read. It issues catalog queries through the connection a program already
holds, under the `db.connect` it already has, and nothing about computing a plan is privileged.

Applying is not. It takes a **new deny-by-default `db.schema` capability**, which joins § 3 of
[0067](0067.md) beside `db.connect` and `db.open` and gates a different thing from either: not
which database may be reached, but whether this program may issue DDL to it at all. It names connection
blocks, like `db.connect` and unlike `db.open`, and an ungranted name throws naming the capability.

The two entry points are named for what they risk, at the call site:

- **`applySafe()`** — refuses if any step is not `Safe`, and throws naming the first step that is not.
- **`applyIncludingRisky()`** — says so where it is written, so that a reviewer reading the call sees the
  claim being made.

This is the same shape [0084](0084.md) § 2 already requires — DDL is a privileged
act and the runtime never issues it implicitly at boot or from a request — with the convention promoted to
a capability. `nvs schema plan|apply|dump` is the operator's spelling of the same thing, and sits beside
`nvs queue migrate` for the same reason.

### 10. `nvs-db` owns the schema; `nvs-stdlib` owns the member; `nvs-cli` owns the command

The vocabulary, the four emitters, the five introspectors and the diff are all sans-io and live in
`nvs-db`, beside `Dialect`, by
[0132](0132.md)'s seam. `nvs-stdlib` holds the
`Core\Db\Schema` rows and their [0117](0117.md)
cards; `nvs-cli` holds the subcommand. Neither of the upper two decides anything about DDL.

That it is `Core` at all is [0051](0051.md)'s six tests, in their own order, and no
new rule:

- **Test 1 — runtime privilege.** Introspection reads a pooled connection whose lifetime outlives the call.
  [0067](0067.md) § 13's pool is host-owned, and a guest re-instantiated per request cannot hold
  it. Native or nothing.
- **Test 2 — injection sink or launderer.** DDL is a sink, and a schema value's identifiers reach it
  unparameterized because DDL has no parameters. Under
  [0024](0024.md) § 3 only a `Core` function whose contract names a sink
  may make that judgement, and § 2 above deliberately makes it exactly once.
- **Test 6 — would two of these exist?** Yes, and one already does: the queue's four hand-written lists,
  whatever `nvs/web` would need for `Web\Migration`, and every application that hand-rolls it. One
  spelling per job.

### 11. What v1 leaves out, and why each one is a decision

**Foreign keys are out of v1.** The five backends agree on the *syntax* and disagree on the *behaviour*:
SQLite enforces them only under a pragma, adding one is `Locking` because the server validates existing
rows, and on several backends they create an implicit index — which is precisely the normalization trap § 5
exists to survive. They are added once § 5's empty-plan property is proven without them, and not before.

Also out, and each for the same reason — **no portable spelling**: partial and expression indexes, index
types (`GIN`, `GIST`, `FULLTEXT`), collations and charsets, storage and engine options, comments, check
constraints, generated columns, triggers, views, sequences, partitioning. Every one of them is a construct
whose meaning or whose introspected form differs across the five, so admitting it would either break the
empty-plan property or fork the vocabulary per backend, and a vocabulary that is not the same on all five
is not a portable schema.

None of these is unreachable. All of them are `Core\Db::execute`, today, with a statement a human wrote.

## Consequences

- **The queue's DDL retires.** All four `MIGRATION_*` lists in `crates/nvs-stdlib/src/queue.rs` collapse
  into one schema value, `migration()`'s `None` arm for SQL Server and SQLite goes away, and those two
  backends gain the support [0084](0084.md) § 2 already claimed. The drift-guard
  test's job disappears with the second list. Because the queue's frozen `nvs queue migrate` output is
  already an acceptance check, this is a behaviour-preserving refactor against an oracle rather than a
  rewrite anyone has to trust. **One construct in those lists is outside the vocabulary and is the
  retirement's own open question**: the PostgreSQL list dedupes with a *partial* unique index
  (`… where state = 0`), which § 11 keeps out of v1, and its MySQL list already answers the same
  requirement another way because MySQL has no partial index at all. The retirement owes that index a
  spelling the vocabulary can hold — the same one on both — and it is the first real test of § 2's rule
  that the vocabulary grows only when a construct exists on all five *and* something needs it.
- **A schema value is memory the request pays for**, and that is the [0004](0004.md)
  trade taken deliberately: introspection materializes the catalog rows for the tables under comparison —
  O(schema), not O(data) — and a plan holds its steps' SQL as text. Both are bounded by the schema's size
  and both are freed with the request. Nothing is cached across requests, because a plan computed from a
  stale catalog is the failure mode convergence exists to remove.
- **Planning costs a handful of catalog queries**, not a query per table: the introspectors read the
  catalog in one pass per object kind. This is not on the request path in any expected deployment — it is
  an operator act — so priority 3 is not being spent here.
- **The grader ages, and ages upward.** New server versions relax constraints faster than this project will
  track them, so a plan will over-report `Locking` on a server new enough to make a step instant. § 6 makes
  that the designed failure direction.
- **An application cannot express a schema Novis does not have a vocabulary for**, and will reach for
  `Core\Db::execute` for the rest. That is the honest consequence of a closed vocabulary, and the diff's
  totality is what is bought with it: the plan never silently ignores part of your schema, because part of
  your schema cannot be in the value.

## Alternatives rejected

- **Versioned migrations with a history table** — the industry default, and it answers a question nobody
  asked. It requires ordering, locking, a runner, reversibility and a source of truth in the target
  database, all of which [0082](0082.md) § 7 correctly refuses to decide in
  passing, and it is *wrong* after any change the history table did not record. Convergence needs none of
  it and is correct against a database it has never seen.
- **Parse `CREATE TABLE` to read an existing database** — four vendors' DDL grammars, maintained forever,
  to reproduce information the catalog hands over as rows. § 4.
- **A raw SQL escape hatch inside a schema value** — the one change that would let the vocabulary cover
  everything, and it destroys the property the whole design rests on: a value containing an opaque fragment
  cannot be diffed, so the plan becomes best-effort and every guarantee above becomes a hedge.
- **Two grades** — see § 6. The middle class is the one that actually causes production incidents.
- **Dropping what the schema value omits**, behind a flag or a strict mode — § 7. A flag that is correct
  only when your application owns the entire database is a flag whose default is a data-loss bug in every
  other deployment.
- **Making `applySafe` the only entry point** — a tool that cannot express a risky change is a tool
  operators stop using, and they then hand-write the risky change with no grading at all. Naming the risk
  at the call site is stronger than refusing to have one.
- **Emitting per `Driver` rather than per `Dialect`** — five emitters for four SQL texts, and a fifth copy
  of MySQL's to keep in step with it. § 8.

## Revisiting

- **Foreign keys**, once § 5's empty-plan property is proven on all five backends without them. § 11 says
  what has to be true first; this is the exclusion most likely to be lifted.
- **Offline `.sql` input**, if a real workflow needs a schema read from a dump rather than from a server.
  It is a separate tool with its own ADR, and it does not become a parser inside this one.
- **`Web\Migration`**, which is [0082](0082.md) § 7's decision and not this
  one's. If it is ever taken, this is the layer it sits on: an ordered runner would still compute each
  step's SQL and grade through the mechanism here.
- **Schema-aware checking** (`nvs check --schema`), still [0067](0067.md)'s *Revisiting* item.
  Introspection landing here removes half of what that item was waiting for — it needs a cache format for
  an introspected schema, and § 1's array form is one.

## Verification

- **The empty-plan property, on all five backends**: apply a schema value to a real server, introspect it
  back, assert the plan is empty. This is § 5's acceptance criterion and the whole feasibility question;
  every normalization rule is justified by a case of it.
- **The array round trip**, `toArray(fromArray(a)) == a`, as a named test over every construct in the
  vocabulary — the property that makes a file, a live introspection and a builder be one value (§ 1).
- **Every construct emits in all four dialects**, one named test per construct, including the traps already
  written down in the queue's emitter: MySQL has no `create index if not exists`, no partial index at all,
  and cannot index a `text` column without a prefix length.
- **The type map is one table used twice** — a named test holds § 2's write direction against
  [0067](0067.md) § 9's read direction, so the two cannot drift.
- **`nvs queue migrate` keeps its frozen output.** Goal `database`'s two acceptance checks — that it prints both
  tables and creates both tables — stand unchanged over the retired emitter, which is what makes § 8's
  replacement provable rather than plausible.
- **A program without `db.schema` cannot apply a plan**, and `applySafe` refuses a plan containing a
  `Locking` or `Destructive` step, each named.
