# ADR 0154 — `nvs serve` is one process for requests, schedules and jobs, and the drain stops all three

- **Scope:** where queue workers run, what stops them, which core arms them, and the changeability
  class of the `[queue]` block. It changes nothing about how a job is claimed, retried, dead-lettered
  or removed, and it adds no surface a program can see.
- **Depends on:** [0084](0084.md), whose `workers` is a count per instance; [0073](0073.md), whose
  ticker is the shape this copies; [0078](0078.md), whose drain is what stops it.
- **Validated by:** `examples/queue.nvs` run under the served binary, and the checks
  § *Verification* names.

> **In short:** `rule:concurrency/who-runs-a-job-is-configuration` says in as many words that running
> workers in-process is the default shape and that moving work between shapes is operational rather
> than behavioural. The tree honours that in `nvs run` and not in `nvs serve` — the one binary a
> deployment actually runs — so `[queue] workers` is silently inert in production and every
> deployment needs a second process it was never told about. `nvs serve` therefore arms the queue
> exactly where and how it arms the schedule ticker: a task on the scheduler it already turns, before
> the accept loop is spawned. The worker's stop condition becomes the **drain** rather than a script's
> exit, which is the correct shutdown semantics and is what keeps a served process able to end once
> anything asks it to. The queue needs no lease, unlike a `fleet` schedule, because the claim statement is already the
> fleet's mutual exclusion. `[queue]` joins the directive table it was missing from entirely.

## Context

[0084](0084.md) § 2 made `workers` a count per instance and left where an instance *is* to the
binaries. `crates/nvs-cli/src/worker.rs` was written against `nvs run`, for a reason its own module
doc gives and which is still right: `nvs_host::Scheduler` is created in `nvs-cli`, and a task is a
thing only its owner can spawn. What did not follow is the conclusion that was drawn from it — that
the workers belong to `run` alone. `crates/nvs-cli/src/serve.rs` creates a scheduler too, and already
spawns exactly this shape of task for `[[schedule]]`'s ticker.

The result is an asymmetry with no argument behind it. A `[[schedule]]` entry fires under `nvs serve`;
`[queue] workers = 4` under `nvs serve` arms nothing, reports nothing and refuses nothing. A
deployment that writes both gets one of them.

**The rule that describes this is `designed` and half-built, and the half that is missing is the
default one.** `rule:concurrency/who-runs-a-job-is-configuration` states that running workers
in-process is the default shape and that `workers = 0` is how a deployment *separates* the machines
that accept requests from the ones that drain the queue. Under the tree as it stands that separation
is not a choice — it is the only arrangement there is, and the key meant to express it expresses
nothing. A rule can be `designed` and unbuilt without harm; what is not harmless is a configuration
key that is read, validated at boot, and then silently ignored by the binary an operator runs.

## Investigation

**Arming is a handful of lines, and that is the whole point.** `worker::start` already takes a
`&mut nvs_host::Scheduler`, a `QueueBounds`, a `Database` and a config snapshot. `serve.rs` holds all
four at the point it arms the ticker. Nothing about the worker is `run`-shaped except its stop
condition.

**The stop condition is the one real problem.** In `nvs run`, `nvs_host::run_until_idle` returns when
nothing is runnable, and a worker polling for work is always runnable — so the script's own task sets
`Workers::stop` on its way out. `serve.rs`'s loop is different: it continues while `report.parked > 0`
and ends only when the accept loop itself has returned and nothing is parked. A worker parks on its
idle turn, so **a served process with workers would never reach `parked == 0`**. The drain has to
reach the workers or nothing but killing the process ends it — which today is how a served instance
ends anyway, there being no signal handler yet. § 2 of the Decision is where that qualification and
its three callers live.

**A `fleet` schedule needs a lease and the queue does not.** `serve.rs` passes `None` for
`nvs_server::Leases` and leaves every `fleet` entry unarmed, because `Core\Cache`'s shared tier has no
set-if-absent yet. That blocker does not touch the queue at all: the claim statement is
`for update skip locked`, so the database is already the mutual exclusion across the fleet
(`rule:concurrency/claiming-is-one-statement`), and two instances arming four workers each is eight
workers competing correctly rather than a fire that happened twice. **The queue is the subsystem that
needed no coordinator, and this is where that pays.**

**`[queue]` is not in the directive table at all.** `directive::lookup` answers `Option`, and there is
no row whose key governs `queue`, so the block has no changeability class and no apply class. In
`nvs run` that is invisible: the run is one script long. Under a server it is a live defect — a reload
that changed `workers` from 4 to 8 would be published, would change nothing, and would say nothing.
`rule:config/reloadability-is-its-own-field` enumerates the `Boot` set and does not mention the queue,
so the rule has the same hole the table does.

## Options considered

1. **Leave it; document the second process.** Rejected: it makes the documented default shape the one
   arrangement nobody can have, and it leaves a validated configuration key doing nothing under the
   binary an operator runs — which is a defect whatever a rule's status says.
2. **A `nvs queue work` command.** A third process shape, its own argv to store, its own lifecycle to
   supervise — and it still leaves `[queue] workers` inert under `serve`. It is also the thing
   `rule:concurrency/no-broker-and-no-driver-interface` is proud not to need: "nothing to install
   beside the runtime and no supervisor to keep alive."
3. **Arm the workers under `serve` and stop them with the drain.** Taken.

## Decision

### 1. `nvs serve` arms the queue where it arms the ticker

In `crates/nvs-cli/src/serve.rs`, beside `nvs_server::arm` and before the accept loop is spawned: read
`nvs_config::queue::queue_for` off the boot snapshot exactly as `run_run` does, and call
`worker::start` on the scheduler this command already creates. A tree with no `[queue]` block arms
nothing and spawns no task, which is the ticker's own shape and costs a boot-time `Option` and
nothing else.

**`TaskRoot::Worker` and not `TaskRoot::Request`.** The ticker holds `Request` because a fire is a
child of the loop that serves; a worker holds `Worker` because there is no request beneath it to
charge a panic to (`rule:http-server/containment-does-not-end-at-the-helper`). Copying the ticker's
root would be the one line of this change that looks right and is wrong.

### 2. The drain is the stop condition, and it is what keeps the process able to end

`Workers::stop` stays the flag; what sets it changes. Under `nvs run` it is the script's task on its
way out. Under `nvs serve` it is the drain: a worker reads `Draining::is_draining()` at the top of its
turn and returns.

**What this is not, today.** Nothing begins a drain under `nvs serve` yet: `Draining::begin` is called
in one place — the accept loop's tail, after its `keep_serving` seam breaks — and this command passes
a seam that continues forever. There is no signal handler either, in this crate or in `nvs-server`, so
**`nvs serve` has no graceful shutdown at all**: a `SIGTERM` takes the default disposition and the
process dies mid-request. `parked == 0` is therefore unreachable today, and workers that ignored the
drain would hang nothing that currently runs.

**What it is.** Three callers break that seam, and none of them is far off. `Core\Signal`'s handler is
the first and it is already scheduled — goal `net-os-signal`'s stage 4 lands the terminating signals as *"the
CLI-side entry into the same state machine, not a second one"*, and it sits ahead of this record's own
goal on the chain, so by the time these workers are armed a `SIGTERM` will be asking this command to
drain. A **test** answers `ControlFlow::Break`, which is how a harness stops a server and the only way
a check can assert anything about shutdown. A **service manager's stop** is the third. Each reaches a state
where the accept loop has returned, every connection has finished, and the only parked task left is a
worker polling for work — at which point `run_until_idle` never reports idle and nothing but killing
the process ends it. **A worker that ignores the drain turns the graceful shutdown goal `net-os-signal` builds back
into a kill.**

Wiring it here costs one predicate. Leaving it would put the failure in the slice that lands *first*,
where it would read as a defect in signal handling rather than in the queue.

It is also the right semantics on its own terms: a drain means *stop taking new work*, and claiming a
job is taking new work. A job already claimed runs to completion, exactly as a request already
accepted does and as a `[[schedule]]` fire already in flight does. The tail a shutdown pays is what
`worker.rs`'s module doc already prices — one idle turn in the ordinary case, one statement's round
trip while a claim is in flight, one connect deadline at worst.

### 3. `workers` is a count per instance, and an instance is not a core

[0084](0084.md) § 2 makes `workers` per *instance*, and today `serve` turns one scheduler on one core,
so the two coincide and nothing has to be said. They stop coinciding the moment the server is
thread-per-core: arming on every core would multiply the operator's number by the core count
silently, and `workers = 4` on a 32-core host would open 128 database connections.

**The workers are armed on one core**, the same one the ticker is armed on, and the per-core work is
where that has to be honoured rather than discovered. This paragraph is the decision that per-core
slice inherits; it is not a thing that slice may re-decide.

### 4. No lease, and the contrast is worth stating

`serve.rs` passes `None` for the schedule's `Leases` and names every `fleet` entry unarmed. The queue
takes no lease at all and needs no equivalent: `rule:concurrency/claiming-is-one-statement` puts the
mutual exclusion in the database, so a fleet of instances each running their own workers is the
intended deployment rather than a hazard. A `[[schedule]]` entry has to ask "is another host doing
this"; a worker asks the database for a row and gets one or does not.

### 5. `[queue]` joins the directive table, split the way `[deferred]` is

Every key `System` — the queue is armed at boot and a request may not move it — and the apply class
splits:

| Key | Class | Apply | Why |
|---|---|---|---|
| `queue.connection` | `System` | `Boot` | Changing it under running workers strands every claim in flight against a database nothing will report to. |
| `queue.workers` | `System` | `Boot` | A worker is a spawned task; applying a new count means starting or stopping tasks, which is what `Boot` means one subsystem over. |
| `queue.max_attempts` | `System` | `Reload` | Read per job, out of the snapshot, and applying it re-creates nothing. |
| `queue.visibility` | `System` | `Reload` | The same: a lease length read when a claim is taken. |

`rule:config/reloadability-is-its-own-field` says the two fields are independent and that a registry
deriving one from the other re-creates the conflation the field exists to end; `[deferred]`'s two
halves are already the worked example of one block holding two classes, and this is the second. A
changed `Boot` key is carried forward and **named** by the reload
(`rule:config/a-reload-names-what-it-could-not-apply`), so an operator who edits `workers` on a
running server is told it needs a restart instead of believing it took.

No new diagnostic: the reload's naming mechanism already exists and this only gives it rows to find.

### 6. The command keeps its name, and its description stops being wrong

`nvs serve` stays `nvs serve`. `nvs service` is already the platform-service-manager namespace, a
rename into it would collide; `daemon` is a noun in a list of verbs; and
`rule:packaging/a-service-is-one-stored-argv` makes the argv a thing already written into units on
disk, so the rename would invalidate deployments to buy accuracy a sentence can buy for free.

What changes is the sentence. "Serve a Novis file over HTTP, on one core, until stopped" describes one
of three subsystems, and after this record it describes the least of them. The command's help names
all three, because the mental model an operator forms of one process is what makes them stop looking
for a second one.

### 7. `nvs run` is unchanged

Its workers still stop when the script's task exits, for `worker.rs`'s original reason: a run with a
worker that ignored it would never end. The two binaries share `worker::start` and differ in one
predicate, which is the whole of "moving work between them is an operational decision and never a
behavioural one".

## Consequences

**Usability, and it is the whole point.** A deployment is one process: requests, schedules and jobs.
`workers = 0` becomes a real choice again — the way a deployment separates accepting machines from
draining ones — rather than a description of the only thing available.

**Performance.** Workers share the cores the server is already turning, so a busy server and a busy
queue now contend where before they were separate processes that did not. That is the trade `workers`
exists to let an operator make, and `workers = 0` plus a dedicated `nvs run` host is still available
and is still the answer for a deployment that wants isolation. Nothing on the request path changes:
the worker is another parked task, and a parked task costs its stack.

**Memory.** One database connection per worker, on the instance that arms them, held for the life of
the process — which is what the same workers already cost under `nvs run` and is per-instance rather
than per-request.

**Simplicity.** One `Option` and one call in `serve.rs`, one predicate in `worker.rs`, four rows in
the directive table. No new surface, no new command, no new capability, and one lie removed from the
help text.

**What it does not do.** It does not make the server multi-core, does not implement `Leases`, and does
not change what a worker does once it has a job.

## Alternatives rejected

**A `nvs queue work` command.** § *Options considered* has it: a third process shape that still leaves
`workers` inert under `serve`, and a supervisor the design is specifically proud not to need.

**Stopping the workers with a flag of the command's own rather than the drain.** Two bits meaning the
same thing, and the second one is the one somebody forgets to set — which `Draining`'s own doc calls
the fail-open direction and refuses for the accept loop for exactly this reason.

**Arming workers per core.** Multiplies an operator's number by a count they did not write. If a
deployment wants 32 workers it writes 32.

**Making `queue.workers` `Reload`.** It would mean starting and stopping tasks under a running server
to match a number, which is what `Boot` exists to name; and the failure mode of getting it subtly
wrong is workers that hold claims nothing will report against.

**Renaming the command.** § 5 of the Decision has it. The premise is right and the remedy is the
description.

## Revisiting

Reconsider § 3 when the server becomes thread-per-core — not to change the decision, but because that
is the slice that has to *implement* "one core arms them", and it is the one place the mistake is
cheap to make. Reconsider § 4 if `Core\Cache`'s shared tier gains a compare-and-set and `Leases` is
implemented: the schedule gains fleet arming there and the queue still needs nothing, which is worth
one sentence in that record rather than a change here.

## Verification

- `examples/queue.nvs`'s properties under the **served** binary, not only under `nvs run`: a job
  pushed to a server with `workers = 1` is claimed, runs and reaches `Succeeded`.
- A served process with workers **exits** once its drain begins — the check that would hang if § 2
  were missed, and the reason it is written as a bounded test rather than a smoke run.
- A `[queue]` block with `workers = 0` under `serve` arms no worker task, and a tree with no `[queue]`
  block at all spawns none and reports nothing.
- The directive census in `crates/nvs-config/tests/directives.rs` gains the four `[queue]` rows, and a
  reload that changes `workers` names it as a `Boot` key it could not apply.
- `nvs serve --help` names requests, schedules and queue workers.
