# ADR 0153 — a job is removed from the language, by receipt or by tag, and the removing half takes a capability

- **Scope:** the two members that remove rows from the queue's tables, the `tag` column they select on,
  and the capability that gates them. It decides no retention *policy* — no default lifetime, no
  sweeper of the runtime's own, no `[queue]` key that expires anything — and it changes nothing about
  how a job is claimed, retried or dead-lettered.
- **Depends on:** [0084](0084.md), which makes a job a row in two tables an operator names;
  [0145](0145.md), whose converging schema is what makes a new column cheap; [0067](0067.md), whose
  `db.connect`/`db.schema` split is the shape the new grant copies; [0112](0112.md), the capability
  roster it joins.
- **Validated by:** `examples/queue-purge.nvs` and the conformance cases § *Verification* names.

> **In short:** `Core\Queue` gains `delete(Queue\Id)` and `purge(string $queue, {…})`. The first is
> `cancel`'s twin and removes one row named by its receipt; the second is `stats`' twin and removes a
> population, selected by state, by a new `tag` column, by age, and bounded by a `limit` that is finite
> with nothing written. Terminal rows are the default set, `Claimed` is never removable at all, and
> `Dead` is removable only when the call names `State::Dead` — so nothing that records a failure is
> discarded without a line of source saying so. `purge` takes the deny-by-default `queue.purge`
> capability, scoped on queue names, because it is the only member of this class that can destroy
> evidence; `delete` takes it too, for the same reason at a smaller scale. `push`, `status`, `cancel`
> and `stats` are unchanged and still take nothing.

## Context

[0084](0084.md) made a job a row and never decided what removes one. Three of its consequences have
since become visible together.

**A succeeded row is kept forever.** Completion is `update nvs_jobs set state = 2`, so `nvs_jobs`
grows monotonically with every job the deployment has ever run, carrying every payload it was ever
handed. `AGENTS.md`'s priority 5 calls growth with traffic served — rather than with work in
flight — a leak and not a footprint, and this is one.

**A dead-lettered row is kept forever on purpose**, and that is right:
`rule:concurrency/attempts-are-finite-and-a-dead-letter-is-kept` says the runtime never deletes it,
because an unwatched dead-letter table is the classic way a queue silently loses work. But *never
deleted by the runtime* was read as *never deletable*, which leaves an operator who has read and fixed
a thousand dead rows with no way to clear them.

**A cancelled row is a state change and not a removal**
(`rule:concurrency/cancel-is-a-race-it-can-lose`), so cancelling a batch of 40,000 jobs leaves 40,000
rows behind. That is deliberate — `status` must still answer for a receipt someone holds — and it is
also not a reason the rows must stay for the life of the deployment.

The only answer available today is `Core\Db::execute` against the runtime's own tables. That is
outside the language in the sense that matters: it hardcodes `nvs_jobs`, the `state` ordinals and the
`dedupe_pending` invariant into application source, none of which `Core\Queue` promises to keep, and
it is reachable by any code holding `db.connect` — which is every code path that enqueues.

## Investigation

**What a caller actually wants to remove, from the three shapes that came up:** one job it has the
receipt for; every job belonging to something that no longer exists (a cancelled batch, a deleted
tenant); and everything terminal older than a retention window. The first is a row, the second is a
group, and the third is a sweep — and only the first has an identifier today.

**A group cannot be expressed with what the row already carries.** `dedupe_key` looks like the free
answer and is not: its meaning is *at most one pending job per key*, enforced by the unique index over
`dedupe_pending`. A group of 500 jobs sharing a key could have exactly one of them pending. The column
is structurally the wrong one, not merely a poor fit.

**Selecting inside `args` was the shape the request arrived in, and it does not survive the driver
matrix.** `args` is one JSON document in a `text` column, so a predicate over it is `@>` on
PostgreSQL, `JSON_CONTAINS` on MySQL, `json_extract` on SQLite and `JSON_VALUE` on SQL Server — four
dialects of one predicate, unindexed on all of them, over a table whose whole problem is that it
grows. `rule:concurrency/no-broker-and-no-driver-interface` refuses per-backend surface for a smaller
prize than this.

**A new column is unusually cheap here, and that is a fact about [0145](0145.md) rather than about the
queue.** A nullable column with no default is graded `Safe` by the plan — a catalog write on all four
dialects, because every existing row already has its value and it is null — so `tag` reaches a live
deployment through the same `nvs queue migrate` that is already the only way the queue's schema
changes, with no rewrite and no `--including-risky`.

## Options considered

1. **Nothing; document the SQL.** Costs nothing and keeps the surface at four members. Rejected: it
   makes `nvs_jobs`'s column names and its `state` ordinals part of the public contract by use, which
   is the opposite of what a runtime-owned table is for, and it gives the removal to everything
   holding `db.connect`.
2. **A `[queue] retention` key and a sweeper in the worker.** Fixes the growth and nothing else — a
   cancelled batch and a deleted tenant are not age-shaped. It also puts an unbounded `DELETE` on the
   worker's own connection, on a timer nobody watching a request would see.
3. **`delete` alone, by receipt.** Honest and small, and it answers one of the three shapes. A caller
   with 40,000 receipts to delete is a caller writing the loop the database should have run.
4. **`purge` alone, with `{id}` in the options bag.** One member instead of two. Rejected: a
   `Queue\Id` already carries its queue, so `purge("email", {id: $r})` has two spellings of the same
   fact that can disagree, and R1 wants the subject in parameter 1 rather than in the bag.
5. **The pair, on the two subjects that already exist.** Taken.

## Decision

### 1. Two members, each the twin of one that is already there

```
Core\Queue::delete(Core\Queue\Id $job): bool
Core\Queue::purge(string $queue, {
    state?:  Core\Queue\State,
    tag?:    string,
    before?: Core\Time\Instant,
    limit?:  uint,
}): uint
```

`delete` is `cancel`'s twin: same subject, same `bool`, and the `bool` means the same thing — *this
call is what removed it*. `purge` is `stats`' twin: same subject, one trailing options shape, and it
answers about a population. Nothing new is invented in either shape, which is the point;
`rule:core-api/shape-rules` R1, R2, R3, R4 and R6 are satisfied by copying rather than by care.

Two members rather than one because R15 is one name, one signature, and the two subjects are a receipt
and a queue name. Naming them for what they do rather than for their scale — there is no
`deleteMany` — keeps R5's lexicon: `delete` removes the thing named, `purge` removes what a filter
selects, and neither name is a claim about failure.

### 2. What may be removed, and what may not

| State | `delete` | `purge` |
|---|---|---|
| `Pending` | removes it, `true` | only when the call names `state: Pending` |
| `Claimed` | **`false`**, and nothing is removed | never, under any options |
| `Succeeded` | removes it, `true` | in the default set |
| `Cancelled` | removes it, `true` | in the default set |
| `Dead` | removes it from the dead-letter table, `true` | only when the call names `state: Dead` |

**`Claimed` is not removable, and this is the one arm that is not a policy choice.** A worker holds a
lease on that row and there is no protocol for interrupting work in flight —
`rule:concurrency/cancel-is-a-race-it-can-lose` already says so about `cancel`, and the same sentence
applies here with more force. Removing the row under a running worker makes its write-back match
nothing, which is survivable, because that is exactly the expired-lease path
`rule:concurrency/claiming-is-one-statement` builds; but a caller reaching that path by accident has
turned a job it wanted deleted into a job that runs to completion and reports into a void. `delete`
answers `false` there for `cancel`'s reason: a claim is a race a caller can lose, and losing it is
ordinary rather than exceptional.

**`Dead` is never in a default set.** The dead-letter table is the record that work was lost, and
`rule:concurrency/attempts-are-finite-and-a-dead-letter-is-kept` exists because an unwatched one loses
it silently. A purge that swept it by default would make that rule true of the runtime and false of
every deployment. Naming `State::Dead` in the source is what keeps "nothing is discarded silently"
a property of the system rather than of the runtime alone — the same argument that admits
`Core\Db\Schema::applyIncludingRisky` as a *name* rather than as a flag.

**`Pending` is likewise opt-in**, because the common purge is a retention sweep and a retention sweep
that quietly dropped work waiting to run would be a data-loss bug wearing a maintenance costume.

### 3. A tag groups; a key dedupes

`push` gains one option, `{tag: string}`, stored in a new nullable `tag` column with an index on
`(queue, tag)`. It is inert: nothing claims on it, nothing dedupes on it, and no statement on the
request path reads it. Its whole job is to be the thing `purge` selects on.

It is a second column and not a second meaning for `key` because the two are opposites at the point
they touch: `key` admits **at most one** pending job under a value, and a tag exists to name **many**.
Folding them would make a 500-job batch a 1-job batch, silently, at enqueue.

Selecting inside `args` is refused outright; § *Alternatives rejected* holds the reasoning.

### 4. Bounded with nothing written

`limit` is finite by default. `rule:http-server/an-unsafe-or-unbounded-default-is-a-defect` is the
general form, and the specific form is that the first production `purge` runs against the table this
record exists because it grows: an unbounded `DELETE` over several million rows holds a lock for as
long as it takes, on the connection the application enqueues through. The member answers the count it
removed, so the caller's loop is the shape that drains:

```php
while (Queue::purge('email', {state: State::Succeeded, before: $cutoff}) > 0) { }
```

A default that ran to completion would make the correct call and the catastrophic call look identical
in source.

### 5. The capability, and why the other four still take none

`queue.purge` joins `rule:security/capability-roster-is-closed`'s roster: deny-by-default, scoped on
**queue names**, spelled `[app.capabilities.queue] purge = [...]`, with `true` for every queue and an
absent block for none — `nvs_config::capability`'s existing three-way grant reading, unchanged.

`push` takes no capability, and § 2 of [0084](0084.md) is right that it should not: the connection is
operator-owned configuration and `push` names no block, so there is no name for a grant to be about.
That argument does not carry to these two. The queue *name* is program-written — `{queue: 'email'}` is
in application source — so there is something to scope on; and the act is different in kind. Enqueuing
adds work; purging destroys the record that work existed, including the dead-letter rows an incident
review reads. The grant is what keeps that out of the request path: a web entry keeps pushing with no
`queue` block at all, and the nightly retention entry is the one place in the deployment that holds
the name.

`delete` takes the same grant rather than a lesser one. A capability answers *may this program remove
queue records*, and one row at a time in a loop is the same answer at a different rate.

### 6. One member reads both tables

`purge` with `state: Dead` deletes from `nvs_dead_jobs`; every other selection deletes from
`nvs_jobs`. `delete` tries the receipt in `nvs_jobs` and then in `nvs_dead_jobs`, exactly as `status`
already does — a `Queue\Id` names a job across the move, and a member that stopped working the moment
a job exhausted its attempts would be a receipt that expires without saying so.

### 7. Removal is `Core\Db::execute`'s kind of act, not `db.schema`'s

Deleting rows is DML. It runs on the queue's own connection through
`nvs_runtime::Ctx::memoized_connection`, inside whatever transaction that connection has open — so a
`purge` beside a business write commits with it, for
`rule:concurrency/enqueue-commits-with-your-write`'s reason and by the same mechanism, with nothing
added to make it so. Nothing here issues DDL, so `db.schema` is not involved and `nvs queue migrate`
remains the only thing that changes the tables' shape.

## Diagnostics

**`E0635`** — a **written** `Core\Queue::purge` or `delete` whose queue name the compiling machine's
`queue.purge` grant does not cover. This is `E0618`'s shape one class over, and it is asked under
`E0618`'s conditions and no others: a literal queue name, a configuration this machine actually read,
and the same grant list walked by the same `Capabilities::allows`. A computed name says nothing and
leaves the refusal to the door, per `rule:expressions/preparation-preserves-behaviour`. `delete` has
no literal name to read — its queue comes out of a `Queue\Id` at run time — so the static half is
`purge`'s alone and `delete` is refused at the door like any other ungranted act.

`purge` naming `State::Claimed` throws `LogicError` at the call, beside `push`'s `maxAttempts: 0`,
rather than taking a code: it is one closed enum case out of five and the throw names the case.

## Consequences

**Simplicity — the real cost.** `Core\Queue` goes from four members to six and the capability roster
from eleven names to twelve, and `rule:concurrency/queue-four-members`' "and nothing else" stops being
true as written. That rule is amended rather than renamed: its id is cited from fourteen places in
`crates/` and from two frozen records' `changes:` blocks, and a record is not edited to track a later
decision. It keeps its id and owns what it always owned — the four members a *request* asks, each
about a job or about a queue and never about a row number — and its closing sentence now names this
record's two as the operator-facing pair beside them.

**Performance.** Nothing changes on the request path: no statement gains a clause, and the `tag`
column is written by `push` and read by nothing else. `purge` is one indexed `DELETE … LIMIT` per
call. The index on `(queue, tag)` is one more index to maintain on insert, which is the price of the
feature and is paid per enqueue.

**Memory.** One nullable `text` column per row, null for every job that names no tag. Priority 5 says
that is the right direction to spend in, and this spends it to close an actual unbounded growth.

**Usability.** The retention story stops being "write SQL against tables we do not promise to keep",
and a deployment gets a nightly `[[schedule]]` entry instead. A caller that wants a group deletable
must decide *at enqueue* to tag it — a real cost, and the honest one: nothing can group rows that were
never grouped.

**What it does not buy.** No default lifetime, no sweeper, no configuration key. A deployment that
never calls `purge` grows exactly as it does today, and this record deliberately does not decide
otherwise: a runtime that dropped completed rows on a timer would be deleting an operator's audit
trail on a default nobody chose.

## Alternatives rejected

**Selecting on the payload.** `purge(q, {args: {tenant: 7}})` was the request. It needs a JSON
predicate in four dialects, none of them indexed, over the table this record exists because it grows.
`tag` gives the same result for the case that motivates it, in one column, on every backend, with an
index — and it makes the grouping decision visible at the `push` that creates the group rather than
hidden in the sweep that removes it.

**`key` as the group.** Structurally wrong, not merely awkward: it would cap any group at one pending
job. § *Investigation* has it.

**A `[queue] retention = "30d"` key with a worker sweeper.** Answers the age case and neither of the
other two, and puts an unbounded delete on a timer inside the worker loop. If it is ever wanted it
sits *on* this record's `purge` rather than beside it, which is what § *Revisiting* points at.

**Deleting the row on success instead of `state = 2`.** Would remove the growth at its source and
costs `status`: a receipt would answer "succeeded" and "never existed" identically, and
`rule:concurrency/delivery-is-at-least-once` makes "did it run" a question programs genuinely ask.

**A separate `queue.delete` capability for the by-receipt half.** Two names for one question. The
roster rule keeps two capabilities apart when they answer *different* questions, and these answer the
same one at different rates.

**Wildcards in the grant.** `db.open` takes a `*.` pattern because hostnames are hierarchical at label
boundaries; queue names are flat strings a program picks, and are UUIDs in this repository's own
fixture. Exact names, or `true`.

## Revisiting

Reconsider if a `queue.*` grant gains a second member — at two, whether the namespace is scoped on
queue names or on acts becomes a real question rather than a foregone one. Reconsider the sweeper if
deployments are observed writing the same nightly `[[schedule]]` entry, since a thing everyone writes
identically is a thing that should have had a default.

## Verification

- `examples/queue-purge.nvs`, printing a frozen line per property: a tagged group purged, a tagged
  group's dead rows surviving a purge that did not name `State::Dead`, `delete` answering `false` for a
  claimed job, and the `limit` bounding one call.
- Conformance: `purge` refusing `State::Claimed`; `delete` finding a receipt in the dead-letter table;
  `purge` with no options touching neither `Pending` nor `Dead`; `tag` and `key` proven independent —
  500 jobs under one tag, all pending.
- A `nvs-config` test that `[app.capabilities.queue] purge` reads `true`, a list, a bare string and an
  empty list as the roster's other names do, and a `nvs-check` case that `E0635` fires on a written
  name outside the grant and stays silent on a computed one.
- `nvs queue migrate` against a database holding the pre-`tag` schema plans exactly one step, graded
  `Safe`.
