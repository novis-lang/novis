# ADR 0209 — A WebSocket program that only sends is ended by its next `send` once the period has passed, and a sleep on the connection is cut by the drain

- **Scope:** what the drain does with a WebSocket program that never calls `receive`: what its
  `send` does after the period, and what a `Core\Time::sleep` on that connection does under a
  drain. A program parked on something that is neither the socket nor a sleep is left as it is.
- **Depends on:** [0186](0186.md), [0206](0206.md).
- **Validated by:** `crates/nvs-server/src/serve.rs`'s
  `a_send_only_websocket_program_is_ended_at_the_periods_end`.

> **In short:** a push feed — a loop that sends, sleeps, sends — was reached by nothing under a
> drain. `send` did not read the drain, a sleep is a wait with no drain wake, and the accept loop's
> tail waits for every connection it spawned, so one such program held a stop until its lifetime
> ran out. Now the connection has a drain deadline, the moment it first saw the drain plus the
> connection block's period: `send` throws from that instant and closes the connection with
> `going away`, and a sleep on the connection ends there at the latest and is woken when the drain
> begins, so a long sleep does not hide a short period. A program parked elsewhere is still out of
> reach; a hard cap on the isolate was declined, since it would be the reset the rule refuses.

## Context

### 1. Nothing reached a program that never called `receive`

[0206](0206.md) made a `receive` parked on its peer see the drain at once. A program with no
`receive` in it has the shape of every push feed — send an update, sleep, send the next — and it
was reached by nothing: `send` read no drain bit, and the host's sleep re-arms past every wake
because the caller asked for an instant. With a day's lifetime as the only bound, and the accept
loop waiting for the connection, one open dashboard tab held Ctrl-C for the day. The socket has
no `Drop` that writes a close frame either, so when the program did end the peer read an
abnormal closure.

### 2. The period is the bound such a program was owed all along

Under `rule:concurrency/a-drain-closes-a-connection-cleanly` a program between one `receive` and
the next is work in progress and is given the period. A program that only sends is that program
forever, and the period is exactly what bounds work that does not finish on its own. `send` is
the one operation it calls, `nvs_server::socket` already makes a send failure the one error a
program has to see, and a sleep is where such a program spends the rest of its time.

## Decision

### 3. `send` throws from the drain deadline, and closes with `going away`

`Framed` keeps a drain deadline, filled the first time any operation on the connection reads the
drain begun: that instant plus [`Connection::drain`]. A `send` begun at or past it closes the
connection with `Closing::ShuttingDown` and returns the error the program throws. A `send` begun
before it, however late in the period it finishes, is never cut — that is the "one frame and its
answer" the period was sized for.

### 4. A sleep on the connection is bounded by the same instant and woken by the drain

`nvs_runtime::peer::sleep` is what `Core\Time::sleep` does inside a connection isolate. It holds a
drain wake for the calling task across the wait, parks until the sleep's end or the connection's
drain deadline where that is sooner, and on any wake re-reads both and re-parks past a wake that
changed nothing. A drain beginning mid-sleep therefore wakes the park at once, the deadline is
read then and the sleep runs on to it, and the program's next `send` throws. Off a connection the
member is `Host::sleep` unchanged. `PeerSocket` gains two defaulted members for this — `drain_deadline` and
`wake_at_drain` — so the runtime asks the socket and the socket answers from the server's drain.

### 5. A hard cap on the isolate is declined

A program parked on neither the socket nor a sleep — a topic subscription, a database wait — still
runs to that wait's own bound. Cancelling the connection isolate after the period would bound it
and would hand the peer a reset, which is the one thing the rule exists to prevent; it was raised
and declined. What remains out of reach is named here so a later decision can weigh it.

## Consequences

- A push feed ends within one period of the drain plus the time its current `send` takes, and its
  peer reads `going away`.
- A program mid-step keeps the whole period for the `send` it was about to make.
- What it spends, per `rule:programs/memory-priority`: one instant per WebSocket connection, one
  atomic load per `send`, and one drain registration per sleep on a connection, released when the
  sleep ends.

## Alternatives rejected

- **`send` throws the moment the drain begins.** A program that received a frame just before the
  drain and is about to answer it would lose the answer; the period is for exactly that frame.
- **A sleep under a begun drain returns at once.** A `send; sleep` loop would then send as fast as
  the peer reads for the whole period. Capping the sleep at the deadline sends nothing more from a
  program that was asleep, and a program that was awake sends the one update it was about to.
- **Cut the sleep in the host's timer against the process drain.** The host does not know the
  connection's deadline, and a test's detached drain would never reach it; the socket knows both,
  which is why the runtime asks it.

## Verification

- `crates/nvs-server/src/serve.rs`'s `a_send_only_websocket_program_is_ended_at_the_periods_end`:
  a program that sends and sleeps ten minutes is woken by the drain, sleeps on to the deadline,
  throws at its next `send`, and its peer reads `going away` within seconds with no further
  update.
