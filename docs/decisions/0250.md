# ADR 0250 — A string literal under `as class<T>` is the class's whole name, loaded through `autoload` and checked while compiling

- **Scope:** Which operands of `as class<T>` and `as ?class<T>` the compiler decides, how a string
  literal names its class, and that the literal loads the class through `autoload`. A value built at
  run time, and what editor completion offers inside the literal, are not decided here.
- **Depends on:** [0125](0125.md) (`class<T>`, and its `Foo::class` operand decided at compile time),
  [0061](0061.md) (a name reaches its file while compiling, and no loader runs at run time).
- **Validated by:** the Stage 6 checks of goal `path-literals-follow-up`: four tests in
  `crates/nvs-types/tests/classes.rs`, `nvs-hir`'s `a_class_literal_conversion_loads_its_class`, and
  the three `.nvst` cases named under *Verification*.

> **In short:** `'Shop\Dog' as class<Animal>` is decided while compiling, as `Shop\Dog::class as
> class<Animal>` already is. The literal's text is the class's whole name — no `namespace` and no
> `use` applies to it — and the compiler loads that class through `autoload`. A literal that names
> nothing is `E0303`, and one naming a class outside `T`'s hierarchy is `E0708`: the codes the
> `::class` operand already gets for the same two mistakes. A class constant, a concatenation and a
> variable are values built at run time and are unchanged: they are checked when they arrive, against
> the classes the program loaded.

## Context

### 1. The literal reached only the classes something else loaded

A factory written `'Shop\Handler\Mail' as class<Handler>` compiled, and at run time looked the name
up among the classes the program had loaded. Nothing loaded `Shop\Handler\Mail` unless some other
line named it, because `rule:programs/no-runtime-autoload` closes the file graph before the program
runs. So the line compiled cleanly and threw on its first run, and a misspelled name did the same.
The `::class` form of the same line was decided while compiling and loaded its class, so the two ways
of writing one factory behaved differently for a reason the reader could not see.

### 2. Why the literal was left alone

0125 kept the literal at run time because `"Dog"` names a class through no resolution rule the
language had: `::class` goes through the file's imports and namespace, and a string does not. That is
a reason to choose a reading, not a reason the literal cannot be decided. The run-time lookup already
reads the string as the whole name, so that reading is the one the compiler takes.

## Decision

### 3. The literal is the whole name, and is decided where it is written

A plain string literal written as the operand of `as class<T>` or `as ?class<T>`, parenthesized or
not, is read as the class's fully qualified name: segments of identifiers separated by `\`, with no
leading `\` (`rule:statements/a-leading-separator-does-not-parse` already refuses that form for a
name). The namespace and the imports in force do not apply, because the same text built at run time
gets none of them either, and the two must name the same class.

`nvs-hir`'s requires walk harvests the literal as a name, beside every name it already harvests, so
`autoload` loads the class's file while compiling. `nvs-types` then decides the conversion:

- a name no declaration answers is `E0303`, with a help line saying the string is the whole name;
- a name outside `T`'s hierarchy is `E0708`, the same diagnostic `Rock::class as class<Animal>` gets;
- anything else is a compile-time yes, and `nvs-ir` writes the class descriptor as a constant, as it
  does for `Dog::class`.

`as ?class<T>` is the same refusal: a decided operand has no run-time failure for the `?` to turn
into `null` (`rule:expressions/nullable-conversion-availability`).

### 4. Everything else is unchanged

A class constant, a concatenation of literals and a variable are values built at run time. They load
nothing and are checked when they arrive against the loaded classes, so a name only such a value
gives is `null` under `as ?class<T>` and a `RuntimeError` under `as class<T>`.
`rule:programs/no-runtime-autoload` holds: what is loaded is still decided from the source text alone.

## Consequences

- Performance: nothing on the request path, and the literal form is now a constant, not a lookup.
- Memory: nothing.
- Usability: the literal form works whether or not another line names the class, and a misspelled
  literal fails to compile.
- Simplicity: one more operand shape the compiler decides, and both written-out shapes now behave
  alike.

Two existing programs relied on a literal that named no class throwing at run time: a hostile attack
and a conformance case. Each now builds the name at run time, which is the behaviour they test.

## Alternatives rejected

- **Resolve the literal through the file's namespace and imports**, as `::class` does. The same text
  built at run time would then name a different class from the literal, and the run-time lookup has
  no imports to apply.
- **A new diagnostic code for the literal.** The mistakes are the ones `::class` already reports, and
  one code per mistake keeps `nvs agent show` to one page.
