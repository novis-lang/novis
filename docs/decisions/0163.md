# ADR 0163 — The debug service reads the disk, the application only writes to it, and the viewer renders the one thing no existing tool does

- **Scope:** how a developer sees what a request did while it is happening — where a debug record
  goes, what carries it to a service, how that service stores and serves it, and what its UI is
  allowed to draw. It decides nothing about the probes themselves, which [0018](0018.md) and
  [0041](0041.md) own and which this record only consumes, and it does not move `Core\Debug`'s
  surface or `Core\Log`'s.
- **Depends on:** [0018](0018.md), whose probe word and named sinks are what produces the stream;
  [0092](0092.md), whose record model is what crosses to disk and already answers redaction, elision
  and cycles; [0041](0041.md), whose four event kinds and speedscope export are the artifacts this
  hands off rather than renders; [0040](0040.md), whose no-bespoke-UI principle this record bounds an
  exception to; [0020](0020.md), whose log target is the second thing the service reads.
- **Validated by:** the conformance and integration cases the five rules below name, landed by the
  goals that carry them. Nothing holds this record on its own today, which is why every rule it
  creates is `designed`.

> **In short:** a debug record is **written to disk by the application and read from disk by a
> separate service** — no socket, no listener on the application side, and nothing on the request
> path but a buffered append to a file the writer owns alone. The service is two halves that share
> only an index: an **ingester** that drains the spool continuously whether or not anybody has a
> browser open, and a **viewer** that only ever reads. Its UI renders the one thing no existing tool
> renders — the live, correlated request stream — and hands every artifact that has an incumbent
> viewer to that viewer. Writing the records at all is `[debug] store`, off by default, and a gate
> that can only subtract.

## Context

- A dump today lands in the log ([0092](0092.md)), which is correct and is not always *reachable*: a
  log file is somewhere else in an arbitrary format, and an inline body is unavailable exactly when
  the request is an XHR whose response the developer is not looking at. The ecosystem this language
  is aimed at solved that with a side channel — Symfony's dump server, Clockwork, Ray — and the
  ergonomics are a real reason developers stay somewhere.
- **Almost all of the machinery already exists.** Every request carries a trace id
  (`rule:observability/a-trace-id-exists-for-every-request`), so correlation needs no new key. The
  log target's default rendering is already JSON Lines (`rule:errors/log-write`). The record model
  already applies redaction, control-byte substitution, elision and cycle identity before any
  rendering sees it (`rule:errors/record-transformations`), so a secret is a placeholder and a cycle
  is a reference *before* anything is written. What is missing is a destination and something to read
  it.
- **The counter-principle is real and is named here rather than worked around.**
  `rule:ide/the-extension-builds-no-ui-the-editor-already-has` says the project feeds existing
  renderers and draws nothing of its own, and calls that the simplicity priority applied directly.
  Every observability output was shaped for an incumbent consumer — Clover, lcov, Callgrind,
  speedscope, OTLP, Prometheus. This record is the first thing that maintains a viewer.
- The reason it survives that principle is the principle's own test: *where an existing renderer
  exists, feed it.* For a coverage report and a flame chart one exists. For "what did this request
  just do, live, next to the browser doing it" none does, in any ecosystem, without building it.
  [0092](0092.md) anticipated the shape — "a web-facing log viewer is an HTTP response, and reaches
  the HTML rendering through the response sink like everything else."

## Investigation

- **A socket collector was the first design and was rejected on cost.** It needs a bounded queue, a
  background drain, a circuit breaker, a retry window, a drop counter, a connect-timeout hazard on
  the request path, and a token-and-TLS story for the application-to-collector leg. Every one of
  those exists only to survive the collector being absent or slow.
- **Writing to disk deletes all of it.** An append to an already-open descriptor has no peer, no
  connection state and no failure mode that needs a state machine. It is also *cheaper* than a socket
  write, not more expensive — the millisecond intuition is only true of an `fsync` per record, which
  this does not do. Nothing is lost while the service is down, because the files are simply still
  there.
- **One file per record was considered and is the wrong granularity.** It removes concurrency, which
  is what it is for, but it costs a create, a write, a close and a later delete per record. On Windows
  each new file is scanned on close by real-time antivirus, which is exactly the per-dump millisecond
  cost the design was trying to avoid, and small files past the MFT-resident threshold occupy a whole
  cluster each. A directory that does accumulate — the service stopped, the application still
  dumping — then enumerates in seconds.
- **Sealed batches keep every property and pay none of that.** One file per writer, renamed into a
  ready directory at a size or an age: no two writers ever touch one file, an atomic rename means the
  reader never sees a partial file, and deleting after ingest means no rotation logic. The seal
  interval *is* the visible latency, and sub-second is well inside what this is for.
- **The application server is per core**, so several writers append concurrently. `O_APPEND` gives an
  atomic offset bump and not an atomic large write, and a dumped object tree is easily past any such
  bound, so a shared file would interleave and tear records. Per-writer files remove the question
  rather than bounding it.
- **The application log is the opposite case and must be read in place.** It is not ours to delete,
  it already rotates under a retention bound (`rule:errors/engine-floor`), and its records coalesce
  with a `count`. A resume checkpoint keyed on path and offset is wrong across a rotation.
- **SQLite is already a workspace dependency** and its driver already exists, so the index costs no
  new dependency and no new C library argument.

## Options considered

1. **A socket collector** with the application as client — the queue, breaker and auth surface above.
2. **One file per record**, drained by a directory scan — no concurrency problem, per-record
   filesystem cost, and a pathological undrained directory.
3. **Sealed per-writer spool files**, drained by a background ingester — chosen.

## Decision

### 1. The application writes files, and opens no listener and no connection

Nothing on the request path but a buffered append to a file this writer owns exclusively. No socket,
no queue, no drain task, no breaker, and no code path that can fail because something else is absent.
A debug record that slips into a deployment with the gate off costs the predicted-not-taken branch
`rule:testing/debug-probes` already pays and nothing else.

### 2. A sealed spool file is the unit the service reads

Each writer appends to its own file and seals it — an atomic rename into a ready directory — at a
size or an age, whichever comes first, with the defaults the goal pins. Only sealed files are read.
A file that a crash left unsealed and untouched for longer than any live writer would take is swept
by the same pass, so nothing is stranded.

### 3. Two ingest modes, and one dedupe key serves both

The spool is read whole, inserted, and **deleted**. The application log is read from a checkpoint,
inserted, and **never touched**. The checkpoint is keyed on the file's identity — inode or file id —
plus its offset plus a hash of its first line, because identity alone misses identity reuse and
truncation in place, and a path misses a rotation.

Every record then carries a **dedupe key** under a unique index and is inserted ignoring conflicts:
for a spool record the writer's id and sequence, for a tailed record the file identity and byte
offset. Re-ingesting anything is therefore cheap and harmless rather than something to prevent — and
that is what makes § 5's commit-before-delete safe.

### 4. The ingester and the viewer are two halves that share only the index

The **ingester** starts with the service and runs continuously whether or not a browser has ever
connected. It owns the spool, the checkpoints, and every write to the index. The **viewer** is a
reader: it serves the UI and answers queries, and never opens a log file, parses a line or scans a
directory.

That split is the whole of the performance argument. The viewer's worst case is a bounded indexed
query, so no corrupt or enormous file can reach the UI. It is also the correctness argument: draining
the spool is not an effect of somebody having a tab open.

Putting the ingester inside the *application* process is refused by name. It would put directory
scanning and index writes on the request path, in every deployment, to save a hop that costs nothing.

### 5. The index is a derived cache, and is written accordingly

The files are the source of truth and the index holds nothing that cannot be rebuilt, which is what
licenses running it in its fastest mode — write-ahead logging so the single writer and the readers do
not block each other, and synchronous writes off. The documented risk of that setting is corruption
rather than lost transactions, and here corruption is a cache miss: discard the index and re-ingest.
The viewer offers exactly that as an action, and a corrupt index is never an error the developer has
to resolve.

Order is therefore **read, insert, commit, then delete** — never delete before the commit. A crash in
that window re-ingests, and § 3's dedupe key makes the replay a no-op.

### 6. The viewer is pushed a watermark, not records

The ingester publishes a monotonic sequence after each committed batch, and the viewer's event stream
carries only "new data through sequence N". The browser then fetches the delta through the same query
endpoint it uses for everything else.

One rendering path serves live and historical data rather than two. A slow or backgrounded tab cannot
make the ingester buffer, because the ingester is publishing an integer. A browser that was closed
needs no replay buffer — it reconnects, sees a higher sequence, and queries. That sequence, not the
record's own timestamp, is what orders the live view, which makes it immune to clock skew between
writers and to a garbage timestamp in a corrupt file.

### 7. `[debug] store` is off by default, and can only subtract

Whether debug records are persisted is its own directive in the `[debug]` block, deliberately not a
reading of the run mode and deliberately not a level threshold. `[log] level` is a legitimate
operational dial whose production default is `Info` and which a tree may raise to chase a bug; if the
debug stream rode it, that ordinary action would silently begin persisting complete typed dumps of
request data. **A reasonable operational dial must not double as a data-exposure switch.**

The directive is a second gate, not an override: it is read together with every ceiling already in
force, and off anywhere either says off. `rule:testing/debug-mode-directive`'s reconnaissance
argument does not weaken because a second key said yes.

### 8. The viewer renders the live stream, and hands off every artifact that has an incumbent

What it draws is the correlated request stream and the log — the thing with no existing renderer. A
profile is handed to speedscope in the format [0041](0041.md) already commits to; a coverage report
is handed to whatever reads Clover or lcov. A coverage **heatmap** over source is drawn, because that
is a per-line background over text and not a viewer.

This is the boundary that keeps the exception bounded, and it is written as a rule rather than left
as an intention, because the failure mode of an in-house dashboard is that it grows a second copy of
every tool the project deliberately did not build.

### 9. The request is the primary object, and the flat stream is the second view

The main view is a list of requests — route, status, duration, query count, dump count — and one
request opens to its own timeline. The correlation key is the trace id every request already carries,
so this costs nothing to derive and answers the question the feature exists for: what did *this* call
do. A flat filterable stream is the secondary view, not the front page.

In development the response also carries its trace id in a header, so the viewer can move from the
call the developer is looking at to that request's timeline without guessing. It is mode-gated: in
production it is a correlation and fingerprinting leak.

### 10. The listener is the service's own, and nothing about it is the application's

The viewer binds loopback by default. A non-loopback bind needs a token read from a file, refused at
boot if absent, and TLS. The viewer is a subcommand and is never mounted on the application's
listener: there, every path-normalization bug and proxy misconfiguration would become disclosure, and a
reserved path prefix would collide with the compile-time route table.

Two things this design creates that a socket design did not, and both are closed here. The records
are now **at rest**: the spool and its directory are created for this account alone, in a directory
that fails the same ownership check a configuration file gets, and a byte cap with oldest-first
eviction is mandatory rather than advisory, because nothing consumes the spool while the service is
stopped. And the viewer is a browser-facing local listener, so `Host` and `Origin` are allowlisted
against DNS rebinding, its renderer builds DOM rather than assigning markup, and it runs no Novis
code.

### 11. The log viewer lands first, and the rest extends it

The staging is deliberate. The first goal reads the existing `[log] target` files, groups by trace
id, and serves the request-first view — it depends on configuration, the HTTP server, SQLite and
`Core\Log`, all of which exist, and on no part of `Core\Debug`. The spool, the `[debug] store` gate
and the artifact hand-offs extend it once the probe feature lands. The value here is adoption, and
adoption pays earliest or not at all.

## Consequences

- **Request path:** a buffered append when the gate is on, and one already-paid branch when it is off.
  No syscall on a shared resource, no allocation that outlives the record.
- **Memory:** a write buffer per writer, and no queue anywhere. The index is on disk.
- **Footprint:** the viewer's assets and the ingester ship in every binary, which is priority 5 and
  the one this ordering spends first. The mitigation is reachability rather than size — a server
  process never has a viewer in it.
- **Simplicity is what this costs**, and it is the honest bill: a UI, a storage shape and a release
  surface the project now maintains. § 8's boundary is what stops that bill from doubling.
- **The container case needs no transport**, because the developer already mounts the project
  directory and the files are in it. The same property makes the service a viewer for a copied-down
  log directory or a CI artifact.

## Alternatives rejected

- **A socket collector** — every mechanism it needs exists to survive its own absence, and the file
  is absent-proof by construction.
- **One file per record** — the per-record filesystem cost, the antivirus scan on Windows, and the
  undrained directory.
- **One shared spool file** — torn records under concurrent large appends.
- **Riding `[log] level`** — § 7. It makes raising log verbosity a disclosure event.
- **Ingesting inside the application process** — § 4.
- **Rendering profiles and coverage in the viewer** — § 8, and it is [0041](0041.md)'s decision
  restated, not a new one.
- **Lazy-fetching a value tree as the developer expands it** — the record that reaches the browser is
  already finite, because elision and cycle identity bounded it before it was written. Fetching per
  expansion would add round trips and server-side state to make a bounded thing safe again. Rendering
  children from data already loaded gives the same interaction with none of it.

## Revisiting

If a bind mount turns out not to cover the container case in practice — a developer setup where the
application's filesystem is genuinely unreachable from where the viewer runs — the file-first flow
still stands and the missing piece is a *shipper*, not a change to this record: something that moves
sealed spool files, with its own auth surface, leaving § 1 and § 4 untouched.

## Verification

The five rules name what holds them. The properties that must be tested rather than argued are: a
sealed file is never read while it is being written; a crash between commit and delete re-ingests
without duplicating; a rotation of the application log neither loses nor repeats records; a malformed
line and an unreadable file each leave the ingester running; and the gate off means nothing reaches
the disk at all.
