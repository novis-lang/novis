# ADR 0174 — A resource ceiling stops the request that broke it: the allocator publishes into the word compiled code polls, the value allocators refuse in front of the allocation, and a store no request owns is accounted apart

- **Scope:** how `rule:errors/on-limit`'s memory and CPU ceilings are enforced against a request that
  reaches no member call and no back edge that looks at them, and whose bytes a request is measured
  against. It changes nothing about what a breach *reports* — the tier it lands in, the
  `LimitReport` it carries, whether it is catchable — and it does not give a freed block per-request
  provenance, which waits on the request arena.
- **Depends on:** [0020](0020.md), [0004](0004.md), [0006](0006.md), [0059](0059.md).
- **Validated by:** `tests/conformance/error/a-loop-that-allocates-nothing-is-stopped-by-the-cpu-ceiling.nvst`,
  `tests/conformance/error/a-loop-that-calls-nothing-is-stopped-by-the-memory-ceiling.nvst`,
  `tests/conformance/error/one-operation-past-the-ceiling-is-refused-before-it-allocates.nvst`,
  `crates/nvs-runtime/tests/refusal.rs`, `crates/nvs-runtime/tests/allocator_ceiling.rs`,
  `crates/nvs-runtime/tests/detached_accounting.rs`.

> **In short:** a ceiling is enforced where the resource is spent rather than where a program happens
> to look. The safepoint word moves out of `Ctx` so a thread that does not own the request can write
> it; the watchdog samples each core's per-thread CPU clock and raises the CPU bit into it; the
> allocator compares an armed threshold and raises the memory bit, which bounds a loop; and the value
> allocators ask before they allocate, which bounds a single operation a loop's bound arrives too
> late for. A primitive that carries no `ctx` refuses by returning a degenerate value rather than
> acquiring a status channel, and that is sound because the request is already dead: between the
> refusal and the next poll it can build wrong values and compare them, and it can do nothing else.
> A refusal is otherwise a complete no-op. Finally, a request is measured against its own
> allocations: a store that outlives requests holds a `budget::Detached` bracket around every path
> that grows or shrinks it, so its bytes move a process balance and no request is charged or credited
> for them.

## Context

`rule:errors/on-limit` names the ceilings a request runs inside, and `rule:programs/memory-priority`
requires every per-request allocation to stay under one the runtime can *enforce*. Neither held for a
program that called nothing. Three shapes reached past every ceiling in the tree:

- `while (true) {}` allocated nothing, produced nothing and called no member. The safepoint fired on
  every back edge and read a word nothing ever set. The watchdog reads the reactor's timer wheel, and
  a bare loop arms no timer; when it did fire,
  `rule:http-server/a-wedged-core-is-shed-never-killed` reported and shed the core rather than
  killing it, so *N* such requests retired *N* cores for the life of the process.
- `while (true) { $a .= $a; }` reached no poll that looked at memory. Its doubling ended at Rust's
  `handle_alloc_error`, which aborts the worker and with it every other request sharing it — a
  memory-safety-preserving abort that is nonetheless a breach of request isolation.
- One operation past the ceiling was detected at the next poll, which is after the allocation. A
  request whose whole budget is 8 MiB could ask for 400 MiB in one concatenation and hold it.

A fourth shape reached past the *measurement* rather than the ceiling. `Ctx::memory_used` is
`live_bytes()` less the balance when the context was made, and `live_bytes` is a **thread** balance.
`Core\Cache::local` is a `thread_local` store that outlives requests
(`rule:concurrency/cache-memory-is-charged-to-the-core`), so a request that evicted entries an
earlier request had written drove that balance down and bought itself a ceiling of `[limits] memory`
plus whatever it evicted.

## Investigation

`Ctx::cpu_limit`'s field doc already said the sampling was the host's and that until a timer existed
the flag was raised by tests alone. It still was: every caller of `Ctx::expire_deadline` in the tree
was a test, so `[limits] cpu_time` was a number nothing read.

The obstacle common to the CPU and memory halves was the same word. Nothing can publish into the
word compiled code polls while that word lives inside `Ctx`: a writer would alias the `&mut Ctx` a
helper body holds, and the writers here are a sampler on another thread and the allocator, neither of
which has a context to reach it through. So the word has to be reachable by address.

Moving it was measured before anything else was written, because an indirection on the hottest path
in the language is the kind of cost that is assumed rather than checked. It is negative: the poll
drops from four instructions to three, because the handle is loaded once in the ABI entry block —
where it dominates every block below it, so a back edge keeps the single load it had — rather than
the flags word being re-formed at each site. The tightest loop goes from 23 instructions per
iteration to 22 and `01-arith-loop` from 51 to 50. Wall clock does not move; that loop runs about six
instructions per nanosecond and is not issue-limited.

On the memory half, `crate::budget::add` runs *behind* an allocation, comparing a balance the block is
already counted in. That bounds a loop of allocations, because the next one is stopped, and it cannot
bound a single allocation, because there is no next one. The two need different mechanisms rather
than a better-placed single one.

## Options considered

1. Leave the poll word in `Ctx` and have the sampler and the allocator reach it through a context.
2. Move the poll word out of line, behind a handle `Ctx` holds — the shape `Self::deadline` already
   takes, for the same aliasing reason.
3. Refuse in the global allocator, which covers every allocation in the process with one check.
4. Refuse one level up, in the value allocators, where the requested size is known before the
   allocation and every caller is ours.
5. Give the ctx-less primitives a status return so a refusal can be signalled.
6. Give every freed block per-request provenance, so a free is credited to whoever allocated it.
7. Bracket the stores that outlive a request, so their bytes are on a balance of their own.

2, 4 and 7 are the decision. 1, 3, 5 and 6 are in *Alternatives rejected*.

## Decision

### 1. The poll word moves out of `Ctx`, and the handle is hoisted

`Ctx::safepoint` is the *address* of an `AtomicU64` owned by a handle beside the cold fields;
`SAFEPOINT_OFFSET` and the arrangement `ctx::tests::the_hot_words_come_first_and_are_a_word_apart`
pins are unchanged, a pointer being the same eight bytes the flags word was. The accessors in
`crates/nvs-runtime/src/ctx/safepoint.rs` read and write through the handle, and only compiled code
follows the raw pointer. `crates/nvs-codegen/src/emit.rs`'s `emit_safepoint` loads the handle once in
the ABI entry block.

There is **one word per request tree**. `rule:security/isolate-shares-nothing` gives a tree one
budget to divide (`rule:security/isolate-budget-is-the-trees`), so `Ctx::child` and `Ctx::isolate`
clone the handle rather than making a fresh word: a child built after a flag was raised must not be
born clean.

### 2. The CPU ceiling is sampled per thread, on the thread that already wakes

`crates/nvs-host/src/watchdog.rs` is one thread for the process, already holding an entry per
registered core and already waking on an interval. It gains a per-thread clock read per core per
sweep — `pthread_getcpuclockid` on Linux, the thread id reopened with `GetThreadTimes` on Windows
(`crates/nvs-host/src/cpuclock.rs`). Crossing `[limits] cpu_time` raises both halves: the
`SafepointFlags::CPU_LIMIT` bit in the relocated word, which compiled code polls, and
`Ctx::expire_deadline`, which `rule:http-server/time-is-bounded-inside-a-helper`'s `bounded_loop`
polls inside a member whose runtime scales with its input.

**CPU time, never wall clock.** A wall clock cannot tell a runaway loop from a slow database query;
both sit in one request for a long time and only one is spending the machine. A platform with no
per-thread clock a stranger may read enforces **no** CPU ceiling and says so at boot, rather than
silently getting a wall-clock one that would stop exactly the requests the ceiling exists to leave
alone.

This also makes `rule:http-server/a-wedged-core-is-shed-never-killed` start working rather than
changing it. Its rule reads a core whose oldest in-flight request has passed its deadline; until now
no request had one. Nothing kills a wedged core — what changes is that a runaway request stops
*itself* at its own next poll, so the core is not wedged in the first place.

### 3. The allocator publishes, which bounds a loop

`crate::budget` holds an armed absolute threshold beside its counters. Every growing allocation
compares against it, and a crossing calls `publish`, which stores the memory bit into the polled word
by address — it allocates nothing and takes no lock, which is what lets the allocator be the caller.
An uncapped request arms zero and short-circuits on the first compare.

`Ctx::refresh_limits` is the one place a ceiling is computed and therefore the one place the
threshold is armed, so `Core\Config::set` moving `[limits] memory` mid-request leaves no stale copy;
it is saved and restored around an isolate sharing the thread.

### 4. The value allocators refuse, which bounds one operation

The refusal sits where the size is known before the block is taken.
`NvsStr::try_alloc_uninit` (`crates/nvs-runtime/src/string.rs:609`) and the grow path beside it ask
`budget::affords` in front of `alloc`, and `alloc_uninit`'s aborting wrapper is deleted so the
fallible constructor is the only way to make a string; `object.rs`'s aborting site goes the same way.
The primitives that already carry a `ctx` and a status — `nvs_array_append`, `nvs_array_spread`,
`nvs_object_key_set`, `nvs_object_slot_set` — refuse through the channel they have.

A refusal is recorded before it is returned: `budget::refuse` sets a sticky per-thread flag and
publishes the memory bit. Sticky because the request that is refused is over, and nothing it does
afterwards brings it back under a ceiling it never held the bytes against.

### 5. A ctx-less primitive returns a degenerate value, and that is sound because the request is already dead

**This is the load-bearing claim of this record.** `nvs_str_append`, `nvs_str_concat`,
`nvs_str_concat_n`, `nvs_array_set` and `nvs_array_set_index` take no `ctx` and answer no status.
None of them acquires one to carry a refusal: a refused call returns a value chosen so that the
reference it yields exactly balances the references it consumed.

- `nvs_str_append` returns its `target` unchanged, which balances the one reference
  `nvs_ir::ir::InstKind::StrAppend` says it consumes: the reference consumed and the reference
  yielded are the same reference, so a refusal neither leaks the accumulation nor over-releases it,
  and the slot the caller writes the result into ends up holding what it already held.
- `nvs_str_concat` and `nvs_str_concat_n` return the immortal empty string, whose release is already
  a no-op.
- `nvs_array_set` and `nvs_array_set_index` return their array unchanged, having released the key and
  the value they were handed.

No call site and no lowering changes, which is the whole reason this shape was chosen over a status
channel — see *Alternatives rejected*.

The soundness argument is that **the window in which a program observes a degenerate value is a
window in which it can do nothing with one.** At the moment of the refusal the request has already
been recorded as over and the memory bit is already in the word compiled code polls, so the program
runs only until its next poll. In that window it can build wrong values and compare them. It cannot
write output, reach a `Core` member, or touch anything durable, because every one of those passes
`run_helper`, which asks the ceiling *ahead* of the body
(`crates/nvs-runtime/src/abi.rs:388`) and reports the breach instead of running it. A wrong `string`
that no one can see, for the length of one basic block, in a request that is being terminated, is not
an observable-semantics defect; an aborted worker carrying every other request on the core is.

### 6. A refusal is a complete no-op, including not separating a shared array

A refused write performs none of the work of the write it refused. In particular it does not separate
a shared array. `foreach` walks the snapshot it started on and a write inside the body separates
(`nvs_array_next_slot`'s doc comment); a refused write that separated but did not write, or that
wrote into the shared original, is the one way this reaches `nvs_array_value_at`'s live-entry
expectation. The array primitives therefore ask `affords_write` before they touch the handle at all.

Objects are deliberately outside this pre-check: an object's allocation is sized by its class, so no
program drives one unbounded, and they remain bounded by § 3's published flag. `nvs_array_new` needs
nothing — it hands out a per-thread singleton.

### 7. Whose bytes they are: a store that outlives a request is accounted apart

A request is measured against **its own** allocations. `budget::Detached`
(`crates/nvs-runtime/src/budget.rs:278`) is a guard whose lifetime is an accounting bracket: an
allocation or a release made while one is held moves a separate process balance,
`budget::detached_bytes`, and leaves `live_bytes` — and with it every request's reading and every
armed ceiling — where it found it. `Drop` closes it on an unwind as well as on a return, so the
obligation cannot be half-kept, and nesting is safe because each guard puts back what it found.

**The bracket is held by the store, around every path that allocates or frees what it holds** — never
by a call site that happens to be storing. What a bracket owes is symmetry: a block allocated on one
balance and freed on the other corrupts both. `Core\Cache`'s local tier is the first to take it
(`crates/nvs-stdlib/src/cache.rs:544`), and it copies the entry into an allocation of its own so that
the store's bytes are allocated and freed on the same balance, rather than keeping the `Vec` the
request built. That copy is what the symmetry costs, on a path that has already encoded the value it
is storing.

`affords` answers `true` inside a bracket, because bytes the process owns are not the request's to be
refused. `allocations` and `allocated_bytes` keep moving inside one, because an allocation made on the
process's behalf is still an allocation this thread made.

### 8. A member whose output scales with its input bounds the input

The refusal in § 4 bounds a `Core` member only where the member's output grows through the value
allocator. A member that assembles a large result in its own `Vec` and hands it over at the end
reaches the ceiling once, at the end, having already held the bytes. So a member whose output scales
with its input takes one of two obligations: it allocates its result through the value allocator this
record guards, or it bounds the *input*, the way `rule:core-classes/regex-two-tiers` bounds a
backtracking search by steps and `rule:core-classes/decompression-bound` bounds a decode by
`min(input × ratio, ceiling)`.

This is written as a general rule rather than as one more member's paragraph because the residual in
§ 4 is a small format factor today and becomes a thousandfold one the moment a member with a large
expansion ratio lands. Stating the obligation before the member exists is cheaper than discovering
which members quietly took neither branch.

## Consequences

**What this spends**, per `rule:programs/memory-priority`'s *say what you spend*: one thread-local
load and one compare per growing allocation, in front of a platform-heap round trip
`docs/perf/userland-gap.md` measures at 28.7 ns; one word per request tree; one clock read per core
per watchdog interval, on a thread that already wakes on that interval; one copy of the payload per
local cache write; and nothing on the poll path, which gets cheaper.

A refused request keeps running until its next poll, and that poll is the report. This is the same
window `rule:errors/escalation-ladder` already describes for a published flag, not a new one.

**The general accounting property is not proven, only the bracketed cases.** Charging a free to
whoever allocated the block needs per-request provenance, which the request arena gives and this
decision does not build. What holds today is that every *named* cross-request store is bracketed, and
that a store adopting the guard adopts the obligation with it.

**One store stays unbracketed on purpose.** The compiled-pattern cache holds an `Rc` the compiling
request holds too, so a pattern's bytes have two owners and nothing can put the allocation and the
release on one balance. Bracketing it would make the compile the process's while the last `Rc`'s drop
stayed the request's — the same credit with no bound on it at all, where today the credit is bounded
by the cache's capacity. `crates/nvs-stdlib/src/regex.rs`'s known-gap list is its one home, and it
waits on the arena.

**macOS gets no CPU ceiling yet.** It has no `pthread_getcpuclockid`, and its `thread_info` answer on
a mach port is not reached from this tree; that platform takes the "says so at boot" arm of § 2
rather than a wall-clock substitute.

## Alternatives rejected

**Refusing in the global allocator.** It is the tidier chokepoint and it is wrong: a `Vec` or `Box`
inside helper code turns a null into Rust's own alloc-error path, so a refusal there reaches
`handle_alloc_error` and aborts the process — which is worse than the bug it was meant to fix. The
refusal has to sit where the caller can be told. **Closed; not to be reopened on tidiness grounds.**

**Giving the ctx-less primitives a status ABI.** It would make the refusal explicit at each call
site, at the cost of a new argument and a new return on the hottest primitives in the language, plus
a lowering change at every site in `nvs-codegen`, for a signal nothing can act on: the caller cannot
recover, because the request is already over. § 5 is the cheaper mechanism with the same observable
outcome.

**Sampling wall clock instead of CPU time.** It would cover every stuck request with one number,
including the ones that are stuck because a database is slow — which is precisely the request
`[limits] cpu_time` must not touch.

**Killing a wedged core.** `rule:http-server/a-wedged-core-is-shed-never-killed` stands; there is no
safe point at which another thread may unwind a core running compiled code. § 2 removes the need by
making the runaway request stop itself.

**Per-request provenance for every free, now.** It is the complete answer to § 7 and it is the arena's
work, not a bracket's. Doing it here would mean a second allocator design landing inside a ceiling
goal.

## Revisiting

The request arena is the trigger. When a freed block can be attributed to the request that allocated
it, § 7's bracket becomes one case of a general property rather than the mechanism, and the
compiled-pattern cache stops needing an exception. A second trigger is a platform gaining a readable
per-thread clock, which turns § 2's `None` arm into a supported ceiling with no decision to retake.

## Verification

The three shapes in *Context* are pinned as conformance cases:
`a-loop-that-allocates-nothing-is-stopped-by-the-cpu-ceiling.nvst` expects the `FATAL` and
`Core\Fatal::onLimit`'s report naming `cpu_time`; `a-loop-that-calls-nothing-is-stopped-by-the-memory-ceiling.nvst`
asserts that nothing printed before the breach, which is what says the loop was stopped rather than
the statement after it; and `one-operation-past-the-ceiling-is-refused-before-it-allocates.nvst`
expects a peak that never held the request's whole ask.

`crates/nvs-runtime/tests/refusal.rs` holds the reference balance of each degenerate return, including
a refused write leaving a live `foreach` cursor on its own snapshot.
`crates/nvs-runtime/tests/detached_accounting.rs` holds § 7: a request that frees inherited memory
gains no ceiling, a bracket moves the process counter and not the request reading, and a bracket
restores on an unwind as well as on a return. `crates/nvs-stdlib/src/cache.rs`'s own tests hold the
tier's half — a write charged to the process, an eviction from a later request lowering no ceiling,
and an entry still counting against the tier's `max_size`.
