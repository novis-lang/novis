# ADR 0194 — Accepting a type writes `Name::` inside an expression and `Name()` after `new`, and the name alone wherever a type or a statement may start

- **Scope:** what a type's completion item inserts, which names are offered after `new`, and which
  positions are read as a written type. What is offered at a bare position, the ranking and the `use` line
  are [0193](0193.md)'s and unchanged.
- **Depends on:** [0193](0193.md).
- **Validated by:** `crates/nvs-lsp/tests/completion_edits.rs`, `crates/nvs-lsp/tests/handshake.rs`, and
  the three cases under `tests/lsp/completion/` that cite the rule this creates.

> **In short:** a class accepted inside an expression writes `Name::` and the list of its static members
> opens at once. A class accepted after `new` writes `Name()`, with the cursor between the parentheses
> where the constructor takes an argument. At the start of a statement, and wherever a type is written,
> the item writes the name and nothing else. The server reads which of these it is off the tokens before
> the name, and sends an editor's command only to a client that listed it.

## Context

After [0193](0193.md) a bare name completed to every type, and accepting one wrote its name. The next
keystrokes were nearly always the same: `::` and a request for the list after a class in an expression,
because `Core` is static classes throughout, and `(` after a class that followed `new`. The developer
asked for both to be written by the item.

## Investigation

`written()` read one token before the name and knew `use`, `new`/`extends`/`implements` and the tokens
that start a statement; everything else was an expression. Under that reading `function f(Fo` is an
expression, and so are `catch (Fo`, `$x is Fo` and `#[Fo`, so an item that appended `::` inside an
expression would have written `function f(Foo:: $x)`. The module doc already listed the parameter list
and the return type as a known gap.

Two more findings changed the design. **A statement can start with a type** — `User $u = …` — so the
start of a statement is not a place `::` can be assumed. **`self::` with nothing after it offered
nothing**, because the access resolves to no class until its member is written, so a `self::` the item
wrote would have opened an empty list.

A trigger character fires on a keystroke and never on text an item inserted, so opening the list again
takes a command on the item. `editor.action.triggerSuggest` is VS Code's; nothing in LSP names an
equivalent.

## Options considered

1. **Append `::` everywhere but after `new`.** Wrong in every written type and at every typed local.
2. **Append `::` only where the tokens prove an expression, and the bare name at every doubt.** Chosen.
3. **Two items per class at the start of a statement**, `User` and `User::`. Doubles the type rows of the
   longest list the server sends.

For the command: the server always sending it, the extension adding it in a middleware, or the server
sending it to a client that asked. The third keeps the behaviour where a Rust test can hold it and sends
an unknown command id to nobody.

## Decision

The rule is `rule:ide/an-accepted-type-writes-what-follows-it`. The developer made five calls on the way:
no `;` after `new Name()`, since `new` is usually inside a larger expression; the command gated on
`capabilities.experimental.commands`; no setting to turn it off; `self`, `static` and `parent` on the
same terms as a class; and the bare name at the start of a statement.

The workspace index gains one field on a class's declaration — whether it is `abstract`, and how many
parameters its own `constructor` declares — which is what the `new` list is filtered and shaped by. That
spends two words per declaration, held for the life of the session.

## Consequences

- A written type in a parameter list, a `catch`, a return type, and after `is`, `as` and `#[` is offered
  types and no word or variable, which closes the known gap as a side effect.
- `self::`, `static::` and `parent::` offer the static half of the class they name before a member is
  written.
- A developer who accepts a class and types `::` from habit writes `Name::::`. No editor has type-over for
  inserted text. This is the cost, and a setting is the answer if it proves to be a real one.
- A client other than the reference one gets `Name::` and `Name()` as plain text and no command, and
  opens the list by typing the member's first letter.

## Alternatives rejected

- **`new Name();` with the semicolon.** Right only where `new` starts a statement, which the tokens
  cannot tell from `$x = new Name()` once the `=` is behind it.
- **A heuristic on the rest of the line** to decide the semicolon. Wrong while the first argument of an
  unfinished call is being typed.

## Revisiting

If `Name::::` is reported in use, add one `nvs.completion.*` setting rather than narrowing the positions.
A property's type and a type argument between `<` and `>` are still answered as the position around
them; both are read as a doubt and write the bare name.

## Verification
