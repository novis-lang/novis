# ADR 0227 — a heavy check is keyed on what a twin of its run on the covws build used, a Linux leg on the fixtures and suites it runs again, and every heavy check runs on one goal end in three

- **Scope:** how the release tests, the benches, the database matrix and the two Linux legs are selected. It
  replaces the prediction [0226](0226.md) § 6 kept for them. Fuzz and TSan keep that prediction. How a
  heavy check is judged, and the floor gate's cadence, do not change.
- **Depends on:** [0226](0226.md) for the store, the covws build and the recording run beside a judged one.
- **Validated by:** `tools/nv/test/select-checks.test.ts` § *the heavy set's twins* and
  `tools/nv/test/select-profile.test.ts` § *code only Linux compiles*, and the trial runs under
  *Verification*.

> **In short:** a heavy check still runs on its own build and is judged there. After it, a **twin** runs
> the same work on the instrumented `covws` debug build, and the twin's coverage is the check's keys. A
> release test's twin runs the same binary and filters with `--include-ignored`. A bench's twin runs once
> on the covws `nvs`. The database matrix's twin is its SQLite leg. Each also holds a key for what its twin
> cannot reach. A Linux leg runs every fixture and suite again, so it is selected whenever one of those
> atoms is. A change to code only Linux compiles moves a new key, `platform:elsewhere`. On one goal end in
> three, every heavy check and both legs run whatever changed. That is the safety net for these keys.

## Context

[0226](0226.md) keyed each heavy check on every Rust file of every crate it builds. For most of them that
is `nvs-cli` and everything it links, 19 crates. Any Rust change in those crates reached every heavy check.
A heavy check reached while the floor gate was shut stayed owed, so the goal-end sweep paid for all of them
at nearly every goal end.

Loop run `20260927-142556` shows the cost. At its 19:10 goal end, the session had changed no Rust at all:
it added proof programs. The gate-open sweep still ran the database matrix (about 65s), built the release
CLI (2m17s), the release perf guards (3m49s) and the release `nvs-cli` tests (3m06s), ran both benches, and
ran both Linux legs, 68 fixtures under valgrind among them. Rust changes earlier in the goal had left them
all owed. `bun nv affected` over a change to `crates/nvs-stdlib/src/json.rs` alone reached all 22 heavy
atoms.

## Investigation

1. **The debug twin of a release test runs none of its tests.** Each release test the plan runs is
   `#[cfg_attr(debug_assertions, ignore = ...)]` (`benches/abi-probe/tests/perf_guards.rs`,
   `crates/nvs-cli/src/cache.rs`, `crates/nvs-cli/src/serve.rs`, `crates/nvs-host/src/scheduler.rs`), so
   the footprint of the ordinary `test:` atom says nothing about them. With `--include-ignored` the debug perf guards ran in 52s. Their
   margins fail in debug, and that is no verdict.
2. **The debug twin of the database matrix returns early.** With `NVS_DB_MATRIX_DRIVER` unset, each suite
   returns before it touches a database: `test:nvs-stdlib test queue` holds 43 keys. The SQLite leg needs
   no server, so it can run on covws. Recorded there, it holds 2,386 keys. Its only `Core` items outside
   `nvs-db` in `json.rs` and `response.rs` are their `address` symbol resolvers.
3. **A bench runs on a debug `nvs`.** `bun nv bench --warm-start` and `--serve-vs-fpm` take `--nvs` and
   `--allow-debug`, and with one rep and 200 requests each exits 0 in seconds.
4. **A leg runs every fixture and suite of the plan.** `sweepOver` hands a leg every program check of the
   sweep's list, which at a goal end is the whole plan (`tools/nv/cmd/loop.ts`), and every fixture's and
   case's atom already has a footprint recorded on covws.
5. **Code only Linux compiles is in no footprint.** Footprints are recorded on the Windows development
   machine, and `select/profile.ts` already evaluates `cfg` predicates for the release-only case.

## Options considered

- **Instrument the release build.** [0226](0226.md) rejected it for proof programs: it changes what a time
  limit means. The same holds for a perf guard.
- **Key a leg on a copy of its fixtures' footprints.** The copy goes stale between leg runs, when a
  fixture's own footprint grows. Selecting the leg through the fixtures' own atoms reads the live
  footprints instead.
- **Run a leg over only the fixtures the change reached.** A fixture reached while the gate was shut would
  then need a Linux owed state of its own. The leg's cost is fixed. What this decision cuts is how often it
  runs.
- **Run the full heavy set on every goal end.** That is the cost this record removes. On every tenth goal
  end, a missed heavy regression would wait too long. Three goal ends is about as often as the floor
  gate's full run, one session in ten.

## Decision

1. A heavy check's twin (`tools/nv/select/checks.ts` `heavyTwin`) runs after the check, on covws, and is
   recorded. Its verdict counts for nothing. A release test's twin holds `profile:optimized` besides. A
   bench's twin holds `profile:optimized`. The database matrix's twin holds every file of `nvs-db`, whose
   server drivers only a server leg runs, `tree:tests/db`, and `platform:elsewhere` for its socket legs.
2. A twin that cannot run or be read records `*`. The next run whose twin is read drops it
   (`store.ts` `recordRun`).
3. A Linux leg is selected when the selection picks a fixture or case atom of the plan. Its own atom holds
   only `platform:elsewhere` and the modules that run it (`LEG_KEYS`).
4. `platform:elsewhere` moves when a changed item, or an item the closure reaches, has a `cfg` that is
   false on this platform and not false on Linux (`profile.ts` `elsewhereOnly`).
5. Fuzz and TSan build and run inside WSL and have no twin. They keep [0226](0226.md)'s prediction, and
   hold `platform:elsewhere` besides.
6. On one goal end in three (`HEAVY_FULL_EVERY`, counted in the store as `heavy-full:since`), the goal-end
   sweep picks every heavy check and both legs whatever changed. A store with no count runs them all.

## Consequences

- A goal whose change reaches no code a heavy check's twin ran does not run that check at its goal end,
  except on the safety net's turn.
- **What it costs.** Each run of a twinned heavy check is followed by its twin: about a minute for the
  perf guards, seconds for a bench, and about the SQLite leg's time for the database matrix. It is paid
  only when the heavy check itself runs. The twins' test binaries are built into covws.
- The first gate-open sweep after this lands runs every heavy check and leg once, because each one's
  definition changed.
- **What stays unobserved.** A path only a release build takes, with no debug twin, is held through
  `profile:optimized`. Server-only dialect code outside `nvs-db` that the SQLite leg never calls is held
  by nothing. The safety net finds a regression in either within three goal ends.

## Revisiting

If the safety net's turn finds a heavy check red that the goals before it did not select, that kind of
code gets a key of its own, or the cadence shortens.

## Verification

The tests named above hold the twins' shapes, the leg atoms and the Linux-only key. Each kind of twin was
run once through `bun nv loop --run` in a worktree, before the merge:

| Check | Keys before | Keys after | What they hold |
|---|---|---|---|
| the SQLite leg of the database matrix | every file of 19 crates | 2,386 | the items its suites ran, and every file of `nvs-db` |
| the hundred-thousand-task release test | every file of 6 crates | 87 | the scheduler code the test ran, and `profile:optimized` |
| the CLI's warm-start bench | every file of 19 crates | 875 | the items one warm start ran, and `profile:optimized` |

The trials found three faults, all fixed before the merge. A long record name put the coverage
profile's path past the Windows path limit, so the twin could not be read. A twin that could not be read
then left the crate prediction in the footprint for good, because a run widens a footprint it does not
restart; it records `*` now. And `bun nv bench` looked at every Rust file under `crates/` for its
staleness warning, which the reads log counted as reading each one; that warning runs `unrecorded` now.
