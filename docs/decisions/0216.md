# ADR 0216 — a feature is finished when the binary's own help reaches it and says everything its user needs

- **Scope:** a sixth feature proof, *Help*; what `nvs agent find` must reach beyond `Core` names and
  chapter headings; and a plain card for every diagnostic code. It does not change the four `nvs
  agent` commands, the reference chapters' content, or `--help`'s wording rule
  (`rule:packaging/help-text-speaks-to-its-reader`).
- **Depends on:** [0167](0167.md) for `nvs agent` and its index, [0134](0134.md) for the feature
  proofs, [0203](0203.md) for the class card and the "still owing" list this repeats.

> **In short:** early users found features that existed and that the binary could not show them. A
> feature now owes a sixth proof, *Help*: `nvs agent find` reaches it under its own name, and `nvs
> agent show` prints what it does, how it is written and what it throws or reports. `find` also
> reaches every configuration key, command, flag and diagnostic code as an index entry of its own,
> and every diagnostic code carries a plain card that `show` prints. Existing features, keys and codes
> are brought up to this by goal `core-class-cards`, behind a switch, as `about.md` was.

## Context

### 1. The binary is where a user looks first, and it could not answer

Reports from the first people to use Novis kept the same shape: a feature existed, and neither the
user nor their coding agent found it through the binary. `rule:tooling/an-agent-asks-the-binary`
teaches an agent that an empty `find` means the language lacks a name, so a gap in the index is not a
missing page but a wrong answer.

The five feature proofs said nothing about the binary. A `Core` member's card is enforced
(`rule:core-api/reference-card`), and every other kind of feature was reachable only by luck.

## Investigation

### 2. What the binary could not reach

Measured against the debug build on `main`:

- `nvs agent find E0621` prints "nothing matches", and so does every other code. The only
  explanation of a code is the `///` above its `Code::new` in `crates/nvs-diagnostics/src/lib.rs`,
  written for contributors and citing rules the user cannot open.
- `nvs agent find max_in_flight` prints "nothing matches", although the server chapter describes the
  key. `find` matches `Core` names and chapter headings, never the text under a heading, so no
  configuration key, flag or keyword inside a section is reachable.
- A syntactic form is reachable only when a heading names it. The guard
  `every_syntactic_form_is_reachable_through_a_heading` holds a hand-kept list of forms, so a form
  added later is covered only if somebody remembers the list.

## Options considered

### 3. How `find` reaches what it misses

- **An index entry per key, command, flag and code** — derived from the tables the binary already
  carries, one line each, exact.
- **Full-text search over every section** — reaches everything, and answers one word with many loose
  matches an agent has to read through.
- **Both, exact entries first** — the most complete, and more to build and to test.

The first was chosen: it keeps the index's defining property, that an empty answer means absence
(`rule:tooling/the-index-is-one-line-per-member`), and full text would make that false.

## Decision

### 4. Help is a proof, the index is complete, and a code carries a card

1. `rule:testing/feature-proofs` gains **Help**. Which kinds owe it is policy data, as for every
   proof.
2. `rule:tooling/the-index-names-every-key-command-and-code` makes every configuration key, command,
   flag and diagnostic code an index entry, derived at the call.
3. `rule:tooling/a-diagnostic-code-carries-its-card` puts a plain card beside every `Code::new`, which
   `nvs agent show <code>` prints, and a terminal rendering of diagnostics names that command once.
4. Existing features, keys and codes are brought up to this by goal `core-class-cards`, the goal that
   already drains the class cards. The Help check is off in `tools/data/dossier-policy.toml` until
   that goal turns it on, so the goals ahead of it are not failed by a proof they could not yet meet.
   A new code lands with its card from the day the card field exists, and old codes drain from a
   "still owing" list, as the class cards do.

## Consequences

### 5. What it costs

- **Memory:** the code cards are static strings in the binary, per process and never per request:
  a few hundred bytes per code, on the order of 100 KB over today's codes. The new index entries are
  derived at the call and kept nowhere.
- **Latency:** nothing on the request path. `nvs agent find` does more work per call, which is a
  command-line lookup.
- **Usability:** a user or an agent who knows a name, a key, a flag or an error code gets an answer
  from the binary that runs their program.
- **Simplicity:** one more proof per feature and one card per new code, for contributors. The
  language surface does not change.
