# ADR 0217 — a test describes a TLS session with `Core\Test::tlsSession`, and an answer the table serves may report it

- **Scope:** how a Novis program holds a non-null `Core\Http\TlsInfo` without a network: a new
  member `Core\Test::tlsSession`, and a `tls` option on `Core\Test::answerHttp`. It does not change
  what a real handshake reports, what `verified()` means, or the answer table's all-or-nothing switch.
- **Depends on:** [0180](0180.md) for `Core\Http\TlsInfo` and the answer table.
- **Validated by:** `tests/conformance/core/http-response-tls-reports-the-session-a-test-described.nvst`,
  and `crates/nvs-host/src/tls.rs`'s `a_described_session_reads_back_what_was_written`,
  `every_default_suite_is_one_this_build_negotiates` and
  `a_description_the_session_cannot_hold_is_refused`.

> **In short:** `Core\Test::tlsSession({version?, cipher?, verified?, subject?, issuer?, expiry?})`
> returns a `Core\Http\TlsInfo` over a real two-certificate chain — a leaf for `subject`, signed by a
> CA certificate for `issuer` — issued on the spot. `Core\Test::answerHttp`'s new `tls` option takes
> one, and every reply that answer serves reports it through `Core\Http\Response::tls()`. Every option
> has a default: a verified TLS 1.3 session over `TLS_AES_128_GCM_SHA256`, subject `CN=example.com`,
> issuer `CN=Novis Test CA`, expiring 90 days after the test's clock. A `tls` session on an `http://`
> URL is a `LogicError`.

## Context

### 1. Seven members no Novis program could reach

`Core\Http\Response::tls()` returns `null` for a reply the answer table served, because nothing was
negotiated. `Core\Test::serverUrl` is `http` only and no Core member serves TLS. So without a network,
no Novis program could hold a `Core\Http\TlsInfo`, and `version`, `cipher`, `verified`, `peerChain`,
`subject`, `issuer` and `expiry` could have no example, bench or attack
(`rule:testing/feature-proofs`). The conformance case for `tls()` had a branch over all seven that
compiled and never ran. A test of a program that audits its outbound sessions — the case `verified()`
exists for — could not be written at all.

## Options considered

### 2. Where the session comes from

1. **A test describes it, and the table carries it.** Chosen.
2. **`[skip]` the Novis proofs** and keep Rust tests only. Rejected: seven public members with no example
   a reader can learn from, and the audit test above still cannot be written.
3. **A local TLS test server** beside `Core\Test::serverUrl`, so a real handshake runs. Rejected for
   now: a certificate and trust setup, and far more code than the gap needs. It stays open as its own
   decision.

### 3. How a test writes the session

An options bag cannot nest: an option's type is never a bag or a shape, because a bag flattens to one
ABI argument per option (`crates/nvs-stdlib/src/registry.rs`, `CoreOption::ty` and `CoreTy::Shape`).
So `answerHttp($url, 200, {tls: {subject: …}})` would need a compiler change. The fields go to a
member of their own, `Core\Test::tlsSession`, whose trailing bag is ordinary, and `answerHttp` takes
the `Core\Http\TlsInfo` it returns. Seven flat `tls*` options on `answerHttp` were the other form;
they would take that member from three options to ten.

### 4. Where the certificate comes from

`subject`, `issuer` and `expiry` parse the leaf with `nvs_host::tls::leaf`, so the session carries a
real certificate. It is issued from the fields with `rcgen`, which moves from a dev-dependency into the
shipped binary. A PEM the test pastes in was the other form, and it puts a block of base64 in every
example. One certificate compiled into the binary could not show three different uses of `subject`.

## Decision

### 5. `Core\Test::tlsSession`

`Core\Test::tlsSession({version?, cipher?, verified?, subject?, issuer?, expiry?}): Core\Http\TlsInfo`.

- `version` is `TLSv1.3` or `TLSv1.2`, and `TLSv1.3` by default.
- `cipher` is a suite this build negotiates over that version, under the IANA name `cipher()` returns.
  The default is `TLS_AES_128_GCM_SHA256` for TLS 1.3 and `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256`
  for TLS 1.2, the AES-128-GCM suite each version uses with the ECDSA key the leaf has.
- `verified` is what `verified()` returns, `true` by default.
- `subject` and `issuer` are written the way `subject()` and `issuer()` return them: `KEY=value` pairs
  separated by commas, with the keys `CN`, `O`, `OU`, `C`, `ST` and `L`, each at most once. The
  defaults are `CN=example.com` and `CN=Novis Test CA`.
- `expiry` is the leaf's `notAfter`, in whole seconds, between 1950 and the end of 9999. The default is
  90 days after `Core\Time::now()`, so a `#[Test(at: …)]` gets the same value every run.

The chain is two certificates, leaf first: the leaf, and the self-signed CA certificate for `issuer`
that signed it, because a real server sends its leaf and an intermediate and a `peerChain()` example
should show that order. Both keys are fresh P-256 keys. Anything outside those bounds is a `LogicError`
naming the field.

### 6. `answerHttp`'s `tls` option

`tls: Core\Http\TlsInfo`, `null` by default. The table keeps a copy of the session as plain data
(`nvs_runtime::AnsweredTls`), and every reply the row serves builds its own `Core\Http\TlsInfo` from
it. A row with a session on a URL that starts with `http://` is a `LogicError` when it is registered:
a reply over plain `http` has no session to report. A prefix row whose URL names no scheme is not
checked.

### 7. Why it is safe outside a test

Neither member refuses a call outside a test, for the reason `answerHttp` already gives: nothing
trusts what they build. The CA is not an anchor anywhere and nothing verifies the chain. A
`Core\Http\TlsInfo` from `tlsSession` is one the program built for itself, and a reply that reports it
came from the program's own answer table, which has already taken the program off the network. No
request input reaches `rcgen`.

## Consequences

- **Memory:** one copy of the chain, about 1 KB, per registered answer that names a session, for the
  life of the test's context; and a fresh `Core\Http\TlsInfo` per reply that answer serves, released
  with the reply. Nothing outside a test.
- **Latency:** `tlsSession` generates two P-256 keys and makes two signatures per call, under a
  millisecond. A request path never calls it.
- **Binary size:** `rcgen` is linked into the shipped binary. It adds no crypto of its own: it signs
  with the `ring` provider `rustls` already ships.
- **Surface:** one member on `Core\Test` and one option on `answerHttp`. `tlsSession` owes its own
  feature proofs.

## Verification

The conformance case reads all seven `Core\Http\TlsInfo` members from Novis through a faked reply, and
checks the defaults, the `http://` refusal and three refused descriptions. The `nvs-host` tests read
the chain back through the same `leaf` parser a peer's certificate goes through, and prove that both
default suites are ones this build negotiates.
