# ADR 0205 — A connection idle between requests closes the moment it sees the drain

- **Scope:** what the drain does with an HTTP/1.1 connection that has answered its last request and
  is waiting for the next one. What it does with a request in flight, and with a WebSocket a program
  is speaking on, stays [0186](0186.md) § 3's.
- **Depends on:** [0186](0186.md).
- **Validated by:** `crates/nvs-server/src/serve.rs`'s
  `an_idle_kept_alive_connection_is_closed_when_the_drain_begins`, with both the keep-alive wait and
  the drain period set far past what the case is allowed to take.

> **In short:** a kept-alive connection with no request on it was given the whole drain period,
> and a stop after one browser request took the full `drain_timeout` with nothing to finish. An
> idle connection now closes the moment it sees the drain, with the same clean close the keep-alive
> wait ends in. A request that is moving keeps the whole period, so a stop is bounded by the requests
> in flight and never by the connections that happen to be open.

## Context

### 1. A stop took the whole drain period for one idle connection

[0186](0186.md) § 3 made the drain wake every parked wait, so a stop no longer composed the drain
period with `keepalive_timeout`. What the woken connection did next was arm a deadline of "the
moment it saw the drain, plus the period": `nvs_server::io`'s idle phase was bounded by the same
period as a request in flight. One request from a browser leaves the connection open and idle, and
a browser keeps one or two more it never sends a request on, so Ctrl-C on a server that had served
a single page waited the whole of `drain_timeout`, `"30s"` with nothing configured, before exiting.
Nothing was finishing during that wait.

### 2. An idle kept-alive connection may be closed at any moment

HTTP/1.1 keep-alive is a hint and not a promise: a client is required to retry an idempotent request
that fails because the server closed an idle connection, and every browser and HTTP library does.
The period exists so a request that is moving reaches its end and the peer sees a finished response
followed by a clean close. A connection between requests has no response to finish, so the period
buys it nothing, and the servers a proxy sits in front of already close their idle connections at
the start of a graceful stop.

## Decision

### 3. The connection loop asks `hyper` to close an idle connection the moment it sees the drain

`nvs_server::serve`'s drive reads the adapter's phase and the drain bit on every poll of the
connection future. The first poll that finds the keep-alive phase under a begun drain calls
`hyper`'s `graceful_shutdown` on the connection, once. `hyper` closes a connection that is idle on
that poll, and on one still writing a response it disables keep-alive and closes after the
response. The wake [0186](0186.md) § 3 registered is what makes a connection already parked in
that phase re-poll at once; a drain that has begun before the connection reached the phase is read
on the first idle poll.

The question is put to `hyper` rather than answered from the phase because the phase is an
over-approximation: the adapter reads any read attempted during the response phase as the start of
the keep-alive wait, and `hyper` reads during a streaming body to detect the peer's end of stream.
A deadline set from the phase alone cut an event stream short at the first such read. `hyper`
alone knows whether a response is in flight, so the close is its to take. The adapter's own bound
on the keep-alive wait, the moment the drain was seen plus the period, stays as the backstop behind
that call. The head, body and write phases are unchanged, and so is `nvs_server::socket`, whose
WebSocket is a working connection a program is speaking on.

### 4. A case that sends a second request on one connection ends the loop from the client

`serve_on_this_core`'s tail begins its drain the moment `keep_serving` breaks, before the last
connection it accepted has run, so a case that broke after one accept had every request on that
connection served under a drain. That was invisible while an idle connection was given the period;
now it is the close between the two requests. Those cases end the loop from the client instead:
one more connection, made once the last answer is in and dropped unread, un-parks the accept and
a `keep_serving` that breaks on the second connection ends the loop.

## Consequences

- A stop after serving one request exits as soon as the accept loops and workers have ended, rather
  than a drain period later.
- A stop's bound is now the requests in flight plus the write of their responses; an idle
  connection contributes nothing to it.
- The response that was moving when the drain began is still written to its end, and the peer
  sees it complete before the close.
- What it spends: one `bool` per connection and one atomic load per poll of the connection
  future, which the adapter's idle poll already paid.

## Alternatives rejected

- **Shorten the default drain period.** It bounds a request that is working, and a shorter one
  cuts a slow response short on every restart to fix a wait that had nothing to do with responses.
- **Close the idle connection from the accept loop.** The socket belongs to the connection's own
  task, and a close reached in from outside is the reset
  `rule:concurrency/a-drain-closes-a-connection-cleanly` exists to prevent.
- **Write `Connection: close` on the last response instead.** It covers only a response written
  after the drain began; the connection that had already answered, and the ones a browser opened
  and never used, would still wait.

## Verification

- `crates/nvs-server/src/serve.rs`'s `an_idle_kept_alive_connection_is_closed_when_the_drain_begins`:
  keep-alive and drain both set to thirty seconds, the request answered, the close seen by the
  client within a few seconds.
- `crates/nvs-cli/src/serve.rs`'s `a_terminating_signal_drains_serve_and_every_connection_closes_cleanly`:
  end to end from the signal seam, the kept-alive connection ends in a clean close and never a
  reset.
