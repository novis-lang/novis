# ADR 0127 — The end of a script is observable: `Core\Script::onExit` runs at every non-fatal ending

- **Scope:** the end-of-script hook queue — what registers a hook, the three endings that fire it, the
  two terminations that never do, its ordering against `rule:errors/escalation-ladder`'s
  ladder and native teardown, and the report each hook receives. Not in scope: what runs after a `FATAL`
  ([0020](0020.md) §§ 1–2 own the two `Core\Fatal` hooks), post-response work
  ([0072](0072.md) § 6 owns `afterResponse`), and graceful drain
  (`Core\Signal`, [0051](0051.md)).

> **In short:** `Core\Script::onExit(callable $hook)` registers hooks that run FIFO, once, as the **last
> user code of the script** — at a normal end, at `exit`, and at an uncaught throw — each receiving a
> readonly `Script\ExitReport` saying which ending it was. A `FATAL` and a cancellation run **none of
> them**: the first stays `rule:errors/escalation-ladder`'s reserved-budget ladder, the
> second stays `rule:concurrency/cancellation-runs-no-user-code`'s no-user-code rule. Hooks
> observe an ending and never steer one: reason and status are fixed before the first hook runs, and
> nothing a hook does changes them. This is PHP's `register_shutdown_function` for every ending that is
> not a fatal — the one PHP use it does not cover is exactly the one `Core\Fatal` already does.

## Context

- PHP's `register_shutdown_function` fires on a normal end, on `exit`, on an uncaught exception and on
  most fatals. Novis deliberately split those jobs — `afterResponse` for post-response work
  ([0072](0072.md) § 6), the `Core\Fatal` hooks for failure observation
  ([0020](0020.md) §§ 1–2) — and swept the function itself into
  [0063](0063.md)'s removal table, attributed to
  [0028](0028.md).
- That attribution over-reached. 0028's argument is about `__destruct`: the per-object teardown walk,
  resurrection, order-dependence between destructors. A flat, request-local queue of closures run at one
  well-defined moment has none of those properties, so reopening this overturns nothing 0028 decided.
- The split left one ending no user code can see at all: **`exit` runs no `finally`**
  ([docs/adr/README.md](../adr/README.md) § *Decisions taken at project start* — checked against PHP, which
  skips `finally` on `exit` too). A root `try/finally` covers a normal end and an uncaught throw, but a
  CLI program that must flush a buffer, write a summary line or release an external resource *whatever
  the ending* had no home for that code, and wrapping every entry file in a `try/finally` is the wrong
  price for the endings it does cover.

## Decision

### 1. The surface

```php
Core\Script::onExit(callable $hook): void

enum Script\ExitReason { Normal, ExitCall, UncaughtThrow }

// handed to each hook, which may also declare no parameter at all
Script\ExitReport::reason(): Script\ExitReason
Script\ExitReport::status(): int
Script\ExitReport::error(): ?Throwable
```

Three accessors and not three properties, because a `Core`-owned instance has no property a program
can reach — `rule:core-api/shape-rules`'s shape, stated at
`nvs_stdlib::registry::CoreTy::Instance` and already spelled this way by `Core\RateLimit\Decision`
and `Core\Http\Response`. Readonly is then structural: there is no member that writes a slot and no
constructor a program may reach, so the only thing that builds a report is the ending itself.

Registration is request-local and runs nothing; hooks run FIFO in registration order. There is no cap
beyond the request's own memory budget: a registration is an ordinary value on the request heap, and the
hooks and their captures stay live until the end of the script — per request, O(registrations), the
spend this sentence states as `rule:programs/memory-priority` requires. `ExitCall` is spelled
with the suffix so the case never shares a spelling with the `exit` keyword. `status` is the status the
process will exit with; `error` is the real, live `Throwable` for `UncaughtThrow` — the same object
[0020](0020.md) § 2's handler gets, for the same reason — and `null` otherwise.

### 2. The three endings that fire it

| ending | `reason` | `status` | `error` |
|---|---|---|---|
| the last top-level statement ran | `Normal` | `0` | `null` |
| `exit;`, `exit($n);`, `exit("msg");` | `ExitCall` | `0`, `$n`, `0` | `null` |
| an uncaught `THROWN` reached the root | `UncaughtThrow` | `1` | the `Throwable` |

The queue runs once, at most once per script, and drains until empty.

### 3. The two terminations that never fire it

- **A `FATAL`.** A resource-limit breach stopped the request *for exceeding its budget*; running an
  unbounded queue of arbitrary hooks after that point is either an unenforceable cap or a reserved slice
  sized for work that cannot be sized — the exact reasoning behind
  [0020](0020.md) § 1's single handler on a single reserved slice. The one
  observer of a `FATAL` stays `Core\Fatal::onLimit`. This is the deliberate divergence from PHP, whose
  shutdown functions do fire on most fatals; a migrator moves that one use to `onLimit`.
- **A cancellation.** [0072](0072.md) § 5's rule — a cancelled task
  runs no user code, no `catch`, no `finally`, no registered handler — extends to this queue unchanged,
  and for the same reason: every producer of a cancellation (a sibling threw, the deadline expired, the
  parent died, the client disconnected at a safepoint) means the request is already failing or already
  gone. Process death is the same answer for free.

### 4. Where in the ending it runs

On the throw path: the unwind's `finally` blocks (innermost first, as always), then
[0020](0020.md) § 2's `onUncaughtThrow`, then this queue, then native teardown —
the failure hooks run first so a misbehaving queue cannot starve the failure report, and a faulting
tier-2 handler changes nothing here: the queue runs either way. On the other two endings there is no
ladder step: the last statement (or the `exit`), the queue, teardown. Under every hook the heap is fully
alive and output goes wherever the script's output was already going. On the request path the queue is
ordinary request code and delays the end of the response by what it costs — work that should not delay
the response is [0072](0072.md) § 6's `afterResponse`, unchanged. The
four mechanisms route by one line each: `finally` is scoped cleanup, `afterResponse` is post-response
work, `Core\Fatal` observes a failure the request cannot survive, `onExit` is the end of the script.

### 5. Hooks observe an ending; they never steer one

The report — reason and status — is fixed before the first hook runs, and nothing a hook does changes
it; anything else rebuilds `set_exception_handler`, which the ladder replaced. A hook that throws is
abandoned where it stands ([0020](0020.md) § 1's rule for a faulting handler),
its `Throwable` is written to `Core\Log` with the request's trace id rather than swallowed
([0072](0072.md) § 4's rule for a second throw), and the queue
continues. `exit` inside a hook throws `RuntimeError` at the call site — the alternative hands any hook
a way to suppress every hook behind it. A hook may register another hook; it joins the tail of the same
drain. A limit breach *inside* a hook is a `FATAL` like any other: the ladder takes over and the rest of
the queue never runs, consistent with § 3.

## Consequences

**Positive**

- The one ending no user code could observe — `exit` — is observable, without reopening the `exit`
  ABI decision: the queue runs before the status propagates, and `finally` still does not.
- CLI programs get one honest home for "always at the end" work instead of a root `try/finally` that
  cannot see `exit`.
- `nvs convert` gains a mechanical target for the non-fatal majority of `register_shutdown_function`
  uses; the fatal-observing minority maps to `Core\Fatal::onLimit`
  ([0063](0063.md)'s table updated by this ADR).
- The `reason`/`error` report replaces PHP's `error_get_last()`-in-shutdown idiom with a typed argument.

**Negative**

- A fourth "run code later" mechanism to learn. Bounded by § 4's one-line router, but real.
- Hooks pin their captures until the end of the script — per request and attributable, but a large
  capture registered early is held for the whole request.
- The firing set is narrower than PHP's (no fatals, no cancellation, § 3) — a migrator who assumed
  "no matter what" must learn the two exceptions.
- `ExitReason` is a closed public enum: a future termination kind that should fire the queue is a new
  case, which is an API change and a new ADR, not a quiet addition.

## Alternatives rejected

- **PHP's full shape, firing on fatals too.** Guts § 3's first bullet;
  [0020](0020.md)'s reserved-slice design exists precisely because arbitrary
  user code after a limit breach is how a cap stops being one.
- **A bare `array<string>` report, matching `onLimit`'s shape.** That shape is priced for a handler
  running on a reserved slice after a memory `FATAL`, where allocating a typed object is what you
  cannot afford. Here the ordinary budget applies, and an `array<string>` cannot carry the live
  `Throwable`, which is half the report's value.
- **Letting hooks set the status or swallow the error.** Rebuilds `set_exception_handler`; § 5.
- **Doing nothing — a root `try/finally`.** Covers two of the three endings, never `exit`, and taxes
  every CLI entry file for the coverage it does provide.

## Revisiting

If a future termination kind arrives that user code should observe — M7's graceful drain deciding a
request gets a last word, or the in-flight CLI cycle collector growing an end-of-run report — it is a
new `ExitReason` case on this queue, decided by its own ADR; a second queue is the wrong answer.
