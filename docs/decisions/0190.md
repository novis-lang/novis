# ADR 0190 — A `type` alias is a member of a class, interface or enum body, reached as `Owner::Name` from anywhere and as a bare `Name` inside its owner

- **Scope:** the second place a `type` alias may be declared — a class, interface or enum body — its
  key, the two spellings that reach it, how far it reaches, and the refusals that bound it. It does
  not reopen what an alias *is*: transparency, erasure and the bare-class exclusion are
  [ADR 0015](0015.md) § 5's and stay exactly as written.
- **Depends on:** [0015](0015.md) § 5 (the alias itself, and its file scope), [0011](0011.md) (every
  callable is a method and every constant a class constant), [0036](0036.md) (the shape type an
  owner-scoped alias most often names), [0007](0007.md) (types are declared and checked).
- **Validated by:** `tests/conformance/lang/a-class-scoped-type-alias-agrees-with-the-file-scope-form.nvst`
  and the four `tests/conformance/reject/a-class-scoped-type-alias-*.nvst` cases.

> **In short:** `type Name = TypeExpr;` is accepted in a class, an interface and an enum body as well
> as at file scope. It takes no visibility modifier, because there is no runtime name to restrict; it
> is reached as `Owner::Name` from anywhere and as a bare `Name` inside the owner's own body, and by
> no third spelling; and it is **not** inherited, because a subclass reaching an ancestor's alias
> would be a second name for one type. Everything else about an alias is unchanged — it is still
> transparent, still erased before codegen, and still may not name one bare class.

## Context

### 1. The owner existed everywhere except on the one name that wanted it

[ADR 0011](0011.md) settled that this language has no free functions and no free constants: a name
that means something to a program hangs off a class. [ADR 0015](0015.md) § 5 then introduced the one
name that does not — the `type` alias — and put it at file and namespace scope, explicitly "not
inside a class". That was the right call for what the alias was being argued *against* at the time:
§§ 1–3 of that record reject every mechanism that creates a second **runtime-observable** name, and
the alias earned its place by creating none. Where it should be *written* was not the question being
answered.

The gap shows up as soon as an alias describes one class's payload, which is the common case:

```php
type OrderMeta = {total: decimal, note?: string};   // file scope

final class Order {
    public function meta(): OrderMeta { … }
}
```

The owner is in the name, spelled by hand, because there is nowhere else to put it. A reader has to
trust the prefix; a second class wanting its own `Meta` picks `InvoiceMeta`; and `nvs meta --json`
lists both flat, beside aliases that genuinely belong to the file. Every other member of `Order` —
its constants, its methods, its properties — is namespaced by its owner for free, and the one member
that is erased before codegen is the one that has to carry the owner as a spelling convention.

### 2. Why the erasure is what makes the second site cheap rather than what forbids it

An alias has **zero runtime footprint** — [ADR 0015](0015.md) § 5's own words. Nothing downstream of
the checker sees the name: not codegen, not the value layout, not `Core\Reflect::typeOf`, not an
isolate crossing. That is the property `rule:statements/nothing-gets-a-second-name` is satisfied by,
and it is also what makes a class body a *cheap* place to declare one. There is no slot to allocate,
no vtable entry, no descriptor to widen, no field on a running class. Adding the member costs one
arm on `ClassMemberKind` and one entry in the checker's alias table, and the compiled artifact is
byte-identical to the one the file-scope spelling produces.

## Options considered

### 3. Four shapes, and what each one commits the language to

- **Leave it at file scope.** Zero work, and the hand-prefixed name stays. Rejected: the cost is paid
  by every program, forever, to avoid a member arm.
- **A class member with visibility, like a class constant.** `private type Meta = …`. Symmetric with
  the neighbouring member, and wrong for the reason § 5 gives.
- **A class member with no modifier, lexically scoped.** Reachable wherever the owner's name is;
  `Owner::Name` from outside, bare `Name` inside. What this record decides.
- **A class member inherited through the class graph**, like a class constant, so `Sub::Name`
  resolves an ancestor's declaration. Rejected in § 6.

## Decision

### 4. One member, in all three bodies, by the same routine

A class, interface and enum body each accept `type Name = TypeExpr;` wherever they accept `const`,
parsed by the routine the file-scope form already uses, with a `///` run attaching to it as it does
to any member. One rule for every body that has a class-shaped name is simpler than one rule plus two
refusals, and nothing about the member differs between the three: an interface's alias is not a
contract an implementor must satisfy, and an enum's alias has nothing to do with its cases.

The declaration is keyed by the owner's `QName` **plus** the member name, never by a synthetic
namespace path. `Ns\Order\Meta` is also the spelling of a class `Meta` in namespace `Ns\Order`, and
the two must not collide in one table.

### 5. No visibility, ever

A class-scoped alias takes no modifier and has no access rule. Writing one in front of it is a
refusal, not a default.

Visibility is a rule about reaching a **runtime** name: `private` means a call site or a property
fetch is refused because the object it would touch is not yours to touch. An alias has no runtime
name to reach. A `private type` would therefore be a compile-time-only reachability rule invented for
a name that is gone before the program exists — a whole second access system, enforced in the
checker, over an identifier nothing can observe.

It would also not do what the modifier appears to promise. An alias is transparent in both
directions: `Order::Meta` and `{total: decimal, note?: string}` are one type. A `private` alias
therefore hides the *name* and not the *type* — the shape it expands to is still writable by anyone
who can write the expansion, which is anyone at all. The encapsulation would be a spelling
restriction wearing an access modifier's clothes, which is exactly the kind of second meaning for a
familiar keyword this language declines elsewhere.

### 6. Lexical scope, and no inheritance

An alias is reached by the owner that **declares** it. `Owner::Name` resolves from anywhere the
owner's name resolves; a bare `Name` inside the owner's own body is the short form. `Sub::Name`,
where only an ancestor of `Sub` declares `Name`, is refused and the diagnostic names the spelling
that does resolve.

A class constant is inherited because it is a real entry on a real class that a subclass genuinely
has. An alias is not an entry on anything. Inheriting it would mean `Sub::Name`, `Sub2::Name` and
`Base::Name` are three spellings of one type, none of which the reader can resolve without walking
the hierarchy — a second, third and fourth name for a type that already has one, which is the precise
thing `rule:statements/nothing-gets-a-second-name` closes. The refusal costs a program one qualified
name and buys the reader a name that says where to look.

### 7. Two spellings and no third

`Owner::Name` and, inside the owner's body, a bare `Name`. `self::Name` and `static::Name` in type
position are not spellings of this member and stay refused as they are today.

`self` and `static` exist to defer a choice to the running receiver, and `static` in particular means
*the class this was called on*. An alias is resolved before there is a receiver, so `static::Name`
could only ever mean "the lexical class", which is what the bare `Name` already says — and a
late-bound type name is a different feature, not a spelling of this one. Accepting `self::Name`
because it happens to be decidable would make `static::Name` look like the obvious next step while
being unimplementable, which is worse than refusing both.

### 8. What `Owner::Name` in type position means, in order

An `Owner::Name` in type position is tried as an alias, then an enum case, then a class constant. A
name that would be two of those at once is refused **at the declaration**, so no program that
compiles depends on the order. The order exists for one reason: when nothing resolves, the
diagnostic can say which three things were looked for.

## Diagnostics

Each is an existing code doing its existing job at a new site; the member introduces no new band.

| Written | Refused as |
|---|---|
| A modifier run or an attribute group in front of a body's `type` | `E0133` |
| `type` in a method body, a block or a closure body | `E0233` |
| A body's alias sharing a name with a class constant or an enum case | `E0304` at the later declaration |
| A body's alias naming one bare class-shaped atom | `E0307`, as at file scope |
| `Sub::Name` where only an ancestor declares `Name` | `E0405`, naming the owner that does |

## Consequences

- **Per request: nothing.** The alias is erased before codegen exactly as the file-scope form is, so
  a running program has no table, no lookup and no bytes attributable to it. An isolate crossing, a
  `Core\Reflect::typeOf` and a `Core\Debug::dump` see the expansion and never the name.
- **At compile time: one alias-table entry per declaration**, keyed by the owner's `QName` and the
  member name — the same entry the file-scope form already pays for, differing only in its key. The
  cycle check and the bare-class check run over it unchanged.
- **For the developer:** an owner-scoped shape stops carrying its owner in its spelling, and the
  tooling follows it for free — the outline nests it, `nvs meta --json` nests it under its owner, and
  go-to-definition in type position lands on the declaration.
- **On the priority ordering ([ADR 0004](0004.md)):** this buys simplicity of the language surface,
  priority 4, and spends nothing above it. Security, semantics and the request path are untouched
  because nothing about the member survives the checker.
- **The file-scope form is untouched** — its rule, its tests and its `nvs meta` emission do not
  change; `rule:types/type-alias` gains the second site and loses nothing.

## Alternatives rejected

- **Visibility modifiers on the member** — § 5. A second access system over an erased identifier,
  hiding a name while the type it names stays writable by anyone.
- **Inheritance through the class graph** — § 6. Buys a shorter spelling and costs one type as many
  names as it has subclasses.
- **A `self::`/`static::` spelling** — § 7. `static::` cannot mean anything here, and accepting
  `self::` alone advertises it.
- **A class-scoped *parametric* alias** (`type Rows<T> = …`) — out of scope for the same reason the
  file-scope form defers it: user-defined generics are not designed, and an alias is not the vehicle
  for smuggling that decision in early.
- **An owner-scoped alias that is a distinct type from its expansion** — that is a newtype, which
  [ADR 0015](0015.md) § 5 already declined as a different feature. Transparency is not negotiable
  here: `Order::Meta` and the shape it names are one type in both directions.

## Revisiting

User-defined generics are the one thing that reopens this. When they land, `type Rows<T> = …` is a
question about the *declaration*, not about the scope — a parametric alias would be accepted at both
sites or neither, and nothing in §§ 4–8 has to move for it.
