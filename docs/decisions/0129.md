# ADR 0129 — `Core\Password::verify` reads a PHP-stored bcrypt hash, and `hash` never writes one

- **Scope:** the read roster of `Core\Password::verify` and `::needsRehash` — which stored shapes they
  accept, what a bcrypt hash answers, the bcrypt cost ceiling, and what still throws. Not in scope: the
  write side's algorithm and parameters, whose home stays `crates/nvs-stdlib/src/password.rs`'s module
  doc; the class's placement in `Core` ([0082](0082.md) § 2 by
  [0051](0051.md) § 3's tests); what a `secret` may reach
  ([0033](0033.md)).
- **Depends on:** [0082](0082.md) — the decision that `Core\Password` exists
  and what its three members are.

> **In short:** `verify` and `needsRehash` read **exactly two stored shapes**: the Argon2id PHC string
> `hash` writes, and PHP's stored bcrypt hash (`$2y$`, `$2a$`, `$2b$`) — because `PASSWORD_DEFAULT` has
> been bcrypt since PHP 5.5 and never became Argon2, so the user table of almost every migrating PHP
> application is a bcrypt column. A bcrypt hash verifies; `needsRehash` answers `true` for **every** one
> of them; and `hash` still writes only Argon2id — so the login-time upgrade loop the reference doc
> already teaches (`verify`, then `needsRehash`, then `hash`) migrates the table one login at a time,
> and there is still no algorithm argument anywhere on the class. Everything outside the roster keeps
> throwing `LogicError`, and a stored bcrypt cost past 17 is refused before any work, for
> `MAX_M_COST`'s reason.

## Context

- As first landed, `verify` and `needsRehash` read one shape: the Argon2id PHC string `hash` writes. A
  stored value outside that shape throws `LogicError` rather than answering `false` — a storage layer
  handing back the wrong column must not read as every user mistyping at once
  ([0063](0063.md)'s failure-throws, argued in the module doc). That refusal is
  right for garbage; the question here is only what counts as readable.
- PHP's `password_hash` has defaulted to bcrypt (`$2y$`) since it appeared in 5.5, and still does in
  8.4. Argon2 arrived in 7.2/7.3 as opt-in constants behind a compile-time flag and was never promoted
  to `PASSWORD_DEFAULT`. The migrating application with an Argon2 column is the minority case; the
  bcrypt column is the population.
- Without a read path, that population's choices are catching `LogicError` around every `verify` —
  which launders exactly the storage-bug signal the throw exists to raise — or a hand-built dual-column
  scheme. Both push complexity onto every migrating application to keep one algorithm out of one module.
- A stored hash is not invertible, so no offline tool can convert the column. Only a presented password
  can be rehashed, which is why the login-time loop is *the* migration path and the read roster is what
  makes it reachable.
- [docs/plan/m8.md](../plan/m8.md) already names `bcrypt` among this milestone's crates; this ADR is
  the decision that was missing under that word.

## Decision

### 1. The read roster is exactly two shapes

`verify` accepts the Argon2id PHC string `hash` writes, and a bcrypt hash under the `$2y$`, `$2a$` or
`$2b$` tag — one algorithm under three prefixes, verified identically. `$2x$` is **refused**: it exists
to be bug-compatible with `crypt_blowfish`'s sign-extension overflow, and verifying it means
reimplementing the bug. The roster grows only by amending this section, never by accepting what a parser
happens to read.

The dependency is a pure-Rust bcrypt crate with a constant-time comparison, picked under
[0051](0051.md) § 4's pre-authorization. What it spends
([0004](0004.md) asks for the number): ~4 KiB, transiently, per `verify` of a
legacy row, on the calling task — O(in-flight logins), and shrinking as § 3 upgrades the table.

### 2. The write side is unchanged

`hash` writes Argon2id and nothing else, and no member gains an algorithm argument. Novis never
*produces* a bcrypt hash; it only stops refusing to read one. The write-side parameters and their
reasons stay where they are, in the module doc.

### 3. `needsRehash` answers `true` for every bcrypt hash

The landed rule is *weaker, not different*, and a different algorithm is weaker by that rule's own
terms — so `needsRehash` reads a bcrypt hash (rather than throwing at a non-PHC string) and always
answers `true`. With § 1 that completes the migration: `verify` proves the password, `needsRehash` says
the row has fallen behind, `hash` rewrites it under Argon2id, and the bcrypt column converges to empty
without a flag, a tool or a second code path.

### 4. The cost ceiling is 17

A bcrypt hash carries its cost, and cost is the base-2 log of the round count — a CPU-time lever where
Argon2's `m` was a memory one, and the same one `UPDATE` away. `verify` refuses a stored cost above
**17** before doing any work, as a `RuntimeError` in `MAX_M_COST`'s shape. Seventeen is far above the
10–13 real PHP deployments write and far below 31's minutes of CPU, so it costs no real table anything
and closes the denial of service.

### 5. Truncation is bcrypt's, not ours

bcrypt hashes at most 72 bytes of the password and stops at a NUL. `verify` replicates that because it
must accept exactly the passwords PHP accepted against the same row — it is the algorithm, not a
choice — and it is one more reason § 3 marks every such row for rehash under an algorithm without the
edge.

### 6. What still throws

A stored value outside § 1's roster — garbage, `$2x$`, a PHC string naming any other algorithm — throws
`LogicError` from `verify` exactly as before, and the message still never quotes the bytes
([0033](0033.md)). The roster has two entries instead of one;
the property that a wrong column wakes an operator is unchanged. This section is now the home of that
refusal's boundary; the module doc states the mechanism and points here.

## Consequences

- A PHP application's existing user table verifies on day one of running under Novis, and rewrites
  itself to Argon2id one successful login at a time. No API surface is added.
- The cost is a second parse path beside the PHC one, one new dependency owing the usual
  `[workspace.dependencies]` comment, `cargo deny check` and notice regeneration, and a read roster that
  is now two entries rather than one.
- `password_verify`'s remaining divergences get their register rows, owned here: Novis throws for a
  stored value it cannot read where PHP answers `false`, and `needsRehash` measures *weaker* where PHP
  compares for difference (`docs/divergences.md`).
- `docs/reference/core/Password.md` gains the migration paragraph, and the module doc's refusal section
  is rewritten to defer to § 6 — in the slice that lands this, not before.

## Alternatives rejected

- **An algorithm argument, or a `PASSWORD_BCRYPT` write path.** Reopens the copied-call-site problem
  the class exists to close, and no new hash should ever be bcrypt.
- **Answering `false` for an unreadable stored value**, as PHP does. Hides the storage bug behind the
  login screen; rejected once by [0063](0063.md) and not reopened by widening the
  roster.
- **Reading every algorithm the RustCrypto tree can verify.** Roster creep: each entry is a parser, an
  attack surface and a forever-promise, and two shapes cover the actual migrating population. A third
  shape earns its place the way bcrypt did — by being what a real population's column holds.
- **An offline conversion tool.** Impossible without the passwords; see Context.

## Verification

The slice that lands this owes: a unit test that a PHP-written `$2y$` hash verifies and its wrong
password answers `false`; one that `needsRehash` answers `true` for every bcrypt tag in § 1's roster;
one that a stored cost past 17 is refused before any work; one that `$2x$` and a foreign PHC algorithm
still throw; and a conformance case walking the § 3 upgrade loop end to end. The landed refusal case
`tests/conformance/core/password-refuses-a-stored-value-that-is-not-a-hash-it-wrote.nvst` must pass
unchanged — nothing it pins is loosened by this ADR.
