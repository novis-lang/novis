# ADR 0242 — A `.novis/completion` folder anywhere in the workspace holds JSON files of values the editor offers at the string parameters they name, and nothing in them is run

- **Scope:** The `.novis` folder as a project's place for data its tools read, the `completion` kind
  inside it, the format of a completion file, and how the language server finds, reloads, checks and
  offers one, with the VS Code client's part (the file watcher and a JSON schema). Any other kind of
  content under `.novis`, and any reader other than the language server, are left to the record that
  adds one.
- **Depends on:** [0108](0108.md) (its § 2, the terms on which a value enters a completion list, which
  this record widens), [0240](0240.md) (a string argument mapped to its parameter through
  `crate::arguments`, and `'` and `"` as trigger characters answered only inside a string the editor
  completes).

> **In short:** every folder named `.novis` in the workspace, `vendor/` included, may hold a
> `completion/` folder, and every `.json` file under it is a completion file. A file declares named
> sets of values and attaches a set, or values written inline, to a parameter of a method, named
> `App\Ui\Icon::render` and `name`. Inside a string argument at that parameter the editor offers the
> values, each with everything a completion item can show: label, two label details, icon, popup
> title, Markdown documentation, deprecation, sort and filter text, preselection. Nothing in the file
> is run, and an item can change only the string the cursor is in: no editor command, no edit
> elsewhere, no command link. The server finds the files once at start, asks the client to watch
> them, and reloads a file whose modification time or size changed. A file that is not valid JSON or
> has an unknown field contributes nothing and carries a warning; an entry whose method or parameter
> does not exist carries a warning on its own. This overturns the part of
> `rule:ide/completion-offers-only-what-the-compiler-derived` that refused an `ide.json`-style file.

## Context

A string parameter often takes one of a set of values the program cannot see while it compiles: the
modules a deployment has, the names in an icon set, the keys of a dataset kept outside the
repository. `rule:ide/completion-offers-only-what-the-compiler-derived` offered a value only where the
compiler derived it, and refused "an `ide.json`-style patch file" by name as a second, unchecked
description of the program's shape. For these values there is no first description to be second to:
the compiler never holds them, so the refusal left the developer typing them from memory. PhpStorm
answers the same need with `.phpstorm.meta.php`, a file it parses and does not run.

## Options considered

### 1. A helper written in Novis, run when completion is requested

The user's first form of the idea. It would reach any source, but it runs code from the workspace on
a keystroke: opening a cloned repository would run whatever its helper does, a request would wait on
a JIT compile and on whatever the helper reads, and the same position could answer differently from
one keystroke to the next.

### 2. The helper run on demand, its result kept in a file the editor reads

Running the helper by command removes those three costs: code runs only when a person asks, and
completion reads a file. It still needs a Novis command and a helper contract.

### 3. Files only, written by anything

The user's choice. Novis defines the file and nothing that writes it, so a Novis script, a Python
script, a CI job or a person can produce one. It is the smallest of the three, runs nothing inside the
editor, and keeps option 2 open as a script any project can write.

## Decision

### 1. `.novis` is a project's folder for tool data, and `completion/` is its first kind

A folder named `.novis` may appear anywhere in the workspace, as many times as a project needs. It is
not tied to the editor: it is where a project keeps data its tools read. Each kind of data is a
subfolder with its own format, so a later kind never shares a file with this one. This record decides
one kind, `.novis/completion/`, whose every `.json` file, in any subfolder of it, is a completion
file. Any other file there is ignored, so a README can sit beside the data.

The name follows the dot-folder convention of `.vscode` and `.idea` for data that is not source. It is
written `novis` and not `nvs` because `.nvs` is the source file extension.

### 2. The server finds the files once, and the client watches them

At start the server walks each workspace root for `.novis` folders. The walk enters `vendor/`, so a
library can ship completion values for its own parameters, and it skips `.git`, `target`,
`node_modules` and every other dot-folder. It reads no source and lists directories only. It is not
`crate::index`'s walk, which skips `vendor/` and every dot-folder (`crates/nvs-lsp/src/index.rs:603`).

The server then registers a watcher for `**/.novis/completion/**/*.json` through
`client/registerCapability`, when the client supports dynamic registration of
`workspace/didChangeWatchedFiles`. On an event it compares the file's modification time and size with
the ones it loaded, and reloads only a file where either changed, since a client reports changes that
are not. A created or deleted file is added or dropped the same way. A client without dynamic
registration gets the files found at start.

### 3. A completion file is named sets and the parameters they attach to

```json
{
  "sets": {
    "icons": [
      "home",
      {
        "value": "arrow-left",
        "label": "Arrow left",
        "labelDetail": " navigation",
        "labelDescription": "outline",
        "kind": "constant",
        "title": "arrow-left",
        "documentation": "An arrow that points **left**.",
        "deprecated": false,
        "sortText": "a",
        "filterText": "arrow left",
        "preselect": false
      }
    ]
  },
  "parameters": [
    { "method": "App\\Ui\\Icon::render", "parameter": "name", "set": "icons" },
    { "method": "App\\Module::load", "parameter": "module", "values": ["blog", "shop"] }
  ]
}
```

- **A value** is a string, or an object whose one required field is `value`, the text the item
  inserts. Every other field is optional and is one field of an LSP `CompletionItem`: `label`
  (`label`, the value when absent), `labelDetail` and `labelDescription` (`labelDetails.detail` and
  `.description`), `kind` (the icon, one of the protocol's kind names in camelCase, `value` when
  absent), `title` (`detail`, the popup's heading), `documentation` (Markdown, the popup's body),
  `deprecated` (the `Deprecated` tag), `sortText`, `filterText` and `preselect`.
- **A set** is a name and a list of values. A set name is one namespace across every completion file
  in the workspace, so a generated file can define a set and a hand-written one attach it.
- **An attachment** names a `method` as `Class::method` with the class's whole name, a `parameter` by
  its name without the `$`, and gives `set`, `values`, or both. Novis has no free functions, and a
  constructor is `Class::constructor` (`rule:classes/constructor-is-a-method-named-constructor`).
- **The top-level fields are `$schema`, `sets` and `parameters`**, and the set is closed at every
  level, as `nvs.toml`'s is. `$schema` is read by the editor's own JSON support and ignored by the
  server.

### 4. An attachment reaches the declaration the checker resolved

Inside a string argument, `crate::arguments` already finds the call and the parameter the argument
binds to ([0240](0240.md) § 8). The checker's `ResolvedCall` names the class that declares the method,
the method and the parameter names (`crates/nvs-types/src/expr_table.rs:102`), and that triple is the
key an attachment is looked up by. A call through a subclass to an inherited method finds the
attachment written for the declaring class. An override is a declaration of its own and needs its own
attachment. A parameter a `#[Core\Path]` or class-name mark already completes is offered both lists.

### 5. Several sources for one parameter are merged

Every attachment for one parameter contributes, in path order of the files that declare them, and
within a file in written order. Two values with the same `value` are one item, and the first one
read is kept. Two sets with the same name are merged the same way. Nothing here is a conflict, so
nothing here is reported.

### 6. An item changes only the string the cursor is in

An item's one edit replaces the whole text of the string literal, as a whole name does
([0240](0240.md) § 7), with `value` escaped for that literal's quote style, so the literal's value is
`value` exactly. Three fields of a `CompletionItem` are not offered, and an unknown-field warning
names them like any other: `command`, which would let a cloned repository run an editor command when
an item is accepted; `additionalTextEdits`, which edits outside the string; and `insertTextFormat`
as a snippet, which is meaningless inside a string. `documentation` is sent as untrusted Markdown, so
a `command:` link in it is not followed. A relative image or link in it is resolved against the
completion file's own folder and sent as a `file:` URI, so an icon set can show its icon. Whether VS
Code renders an image in the completion popup is not checked; the goal that implements this checks it
first, and the field is kept either way, because the text renders.

### 7. Completion files are data, whoever reads them

Nothing in a completion file is run, by the language server or by any later reader of `.novis`. The
server reads the files and makes no network request: a URL in `documentation` is fetched, if at all,
by the client that renders it. The rule `rule:ide/completion-offers-only-what-the-compiler-derived`
keeps its no-network sentence and every refusal except the file, and names this as the one source of
values the compiler does not derive.

### 8. `'` and `"` open the list at such a parameter

`continues_a_trigger` (`crates/nvs-lsp/src/completion.rs:415`) answers `'` and `"` only inside a
string the editor completes. A string argument at a parameter some completion file names is one, so
typing the opening quote there opens the list.

## Diagnostics

The server publishes diagnostics on the completion file's own URI, as warnings in the `W1xxx` band.
The goal that implements this claims the numbers, one per kind:

- **The file is not valid JSON, or a field is unknown or of the wrong type.** The whole file
  contributes nothing until it is fixed, so a value is never offered from a file that is half
  understood. The message names the field and the fields that are allowed.
- **An attachment names a method the class does not declare, or a parameter the method does not
  have**, for a class the workspace index declares. That attachment contributes nothing; the rest of
  the file does.
- **An attachment names a class the workspace index does not declare.** An information-level hint,
  not a warning, because the class may come from `vendor/`, which the index does not read.
- **An attachment's parameter is not a string**, so no string argument can reach it.
- **An attachment names a set no file defines.**

A completion file under `vendor/` gets no diagnostics: it is a library's to fix. No diagnostic checks a
string literal in a program against the values, because the data can change after the file is
written.

## Consequences

What this spends: one walk of the directory tree when the server starts, listing directories and
reading no file outside `.novis/completion/`. Every value of every completion file, kept in the
server for its lifetime, in proportion to what the files hold. One `stat` per changed file per watcher
event. One hash lookup per completion request inside a string argument. Nothing at run time, and
nothing in the language: a program compiles the same with or without the files.

The VS Code extension contributes a `jsonValidation` entry for `**/.novis/completion/**/*.json` with a
schema it ships, so a person writing a file by hand gets the editor's own JSON completion and
validation for it. The server's warnings stay the authority: the schema cannot know which methods
exist.

The guard test `crates/nvs-lsp/tests/completion.rs` keeps refusing `read_dir` and `std::fs` in a
completion source. The walk and the reads live in a module of their own, outside the guarded set, and
the completion arm that offers the values reads its loaded table, a row the guard names like the
others.

## Alternatives rejected

- **A helper run on each completion request** (option 1). It runs workspace code when a folder is
  opened, and puts a compile and the helper's own reads on a keystroke.
- **A `nvs` command that runs the helper** (option 2). A file any program can write already does
  this, and a command would fix one way of writing it.
- **A list of files in `nvs.toml`.** `nvs.toml` configures a program that runs, and these files serve
  the editor. A folder found by name needs no configuration to add a file.
- **One file per project.** Several generated sources would have to be merged by hand into it.
- **A fixed file name such as `novis-ide-meta.json` found anywhere.** A subfolder per kind leaves
  `.novis` open to later kinds, and a file name would claim the whole folder for completion.
- **An attribute in the source naming a set, `#[Completion('icons')]`.** It needs a change to the
  code, and a library's parameters could not be given values by the project that uses them.
- **Checking string literals in a program against the values.** The values describe data outside the
  program and may be out of date; a check would turn a stale file into a false error.
- **A whole file rejected for one missing method.** A rename in the program would silence every set
  in the file until the file is regenerated.
