# ADR 0118 — A capability is checked at the door to the effect, and declared in one table

- **Scope:** where a capability check runs, what it is checked against, where the declaration that a
  member needs one lives, and what proves the set of checked members is closed. It does **not** decide
  the roster of capability names or their `nvs.toml` spelling — that is
  [0064](0064.md) § 2a's `[capabilities]` block, typed in
  `crates/nvs-config/src/tree.rs`; it does not decide limit enforcement, which is a `FATAL` and
  [0020](0020.md)'s; and it does not decide how a child isolate derives its
  grants from its parent's, which is [0006](0006.md) § 5's.
- **Depends on:** [0078](0078.md) § 1, without whose immutable
  per-request snapshot there is nothing a check could read that two checks in one request would agree
  about.
- **Validated by:** `crates/nvs-stdlib/tests/capability.rs`

> **In short:** a capability question is a *grant* plus a *scope*, asked once of the request's own
> snapshot. The check runs at the **door to the effect** — the one function in `nvs_runtime` through
> which a `Core` member reaches the operating system — so a member cannot route around it by omission,
> because the API it must call to do anything at all *is* the check. What a member needs is declared in
> one table, `nvs_stdlib::registry::CAPABILITIES`, keyed by class and member name: never consulted at
> run time, read by `nvs meta`, by a security review that wants the whole answer on one screen, and by
> the closure test that proves the table and the doors agree. A member that needs no capability pays
> nothing — no lookup, no branch, no field.

## Context

Capabilities are named all over this repository and enforced nowhere. [0006](0006.md) § 5
grants `script.spawn`, [0024](0024.md) assumes a sink is reachable
only under one, [0051](0051.md) sorts the standard library partly by which ones a
tier may hold, [0103](0103.md) § 6 makes the file that grants them
unwritable by anyone else, and [0104](0104.md) § 3 lets an
`[[app]]` block widen one. Not one of them says where the question is *asked*. That gap is what this ADR
closes, and it is the only thing about capabilities still undecided.

Two facts about the tree as it stands shape the answer, and both are worth stating because they will
stop being true:

- **No `Core` member reaches the operating system today.** `crates/nvs-stdlib/src` contains no `std::fs`,
  no `std::net`, no `std::process`. The whole capability-bearing surface is ahead of us, which means the
  door can be made the *only* door before there is anything to migrate. A design that has to retrofit a
  check onto forty existing call sites is a different and much worse design, and we are not obliged to
  pick it.
- **The registry is 346 rows across 39 modules.** Anything stated per member costs 346 edits and is
  thereafter maintained by whoever remembers it. That is the constraint § 3 answers.

## Decision

### 1. A capability question is a grant and a scope, asked of the request's own snapshot

At the point of a call the question has exactly two parts:

- the **grant** — is this capability present at all in the effective configuration, and
- the **scope** — does *this argument* fall inside what was granted: a path under a granted root, a host
  in a granted list, a binary in a granted set.

Both are answered against `Ctx::config()`, which is [0078](0078.md)
§ 1's snapshot: cloned once before the program runs, immutable for the request's whole life. Nothing on
the request path may re-read the configuration tree, so two checks in one request cannot disagree, and a
`nvs ctl reload` between a program's first syscall and its second cannot widen or narrow what that
program is allowed to do halfway through. A capability grant is a `Reload` directive
([0078](0078.md) § 2) and this is what makes that safe.

`nvs_config::Capabilities::allows(cap, scope) -> bool` is the whole of the decision procedure and it is
pure: a snapshot, a capability, an argument, a `bool`. It takes no `Ctx`, throws nothing, and is
therefore testable without a compiler in front of it.

### 2. The check sits at the door, and the door is the only way out of the process

The check is **not** in the member's body as a line the author remembers to write, **not** at the call
site in emitted code, and **not** in a dispatcher. It is inside the function that performs the effect:

```rust
// nvs-runtime
pub fn open_read(ctx: &Ctx, path: &Path) -> Result<File, Fault>  // requires Cap::FsRead
pub fn connect(ctx: &Ctx, host: &str, port: u16) -> Result<Stream, Fault>  // Cap::NetConnect
```

A `Core` member cannot open a file without calling one of these, because **`nvs-stdlib` may not name
the spellings that perform an effect** — `std::fs`, `std::net`'s three socket types,
`std::process::Command` and `std::env`'s readers and writers.
`nvs_stdlib_reaches_the_os_only_through_the_gate` reads the crate's own sources and fails on one. So
"the author forgot the check" is not a failure mode that exists: forgetting it means calling
`std::fs::read` directly, and that does not get past the test.

The list is of *spellings*, not of modules, and the difference is load-bearing in both directions.
`std::net::IpAddr` is a parser — `Core\Validate::isIp` uses it and touches no socket — and
`std::process::abort` is the bottom of [0020](0020.md)'s ladder rather than a
way out to the operating system. Banning their modules wholesale would ban two members that need no
capability, and the exemption it would then need is exactly the kind of allowlist § 7 refuses.

This is the property the ADR is for. Every other placement leaves the check *beside* the effect, where
omitting it is a silent hole that reviews are expected to catch; this one puts it *in* the effect, where
omitting it means not performing the effect.

### 3. The declaration is one table, not a field on 346 rows

What each member needs is declared once, in `registry.rs`:

```rust
pub const CAPABILITIES: &[(&str, &str, Option<Cap>)] = &[
    ("Core\\IO", "read", Some(Cap::FsRead)),
    ("Core\\IO", "write", Some(Cap::FsWrite)),
    ("Core\\Cache", "local", None),   // reaches nothing, and says so — § 7
    // …
];
```

**This table is never read at run time.** It is audit data: `nvs meta --json` renders it, the reference
documentation prints it beside a member's card ([0117](0117.md)),
and § 7's closure test reads it. Enforcement is § 2's doors and does not consult it, so the table cannot
be the thing an attacker edits to gain a permission.

A field on `CoreMethod` was the obvious shape and is rejected for two reasons, in this order. The first
is that **"what can this runtime do to my machine" should be one screen of one file.** Spread across 41
class literals in 39 modules it is 39 greps and a judgement about whether you found them all, which is
precisely the question a security review is trying not to have to make. The second is cost: 346 rows
would each carry a `caps: &[]` that is empty for the overwhelming majority, and a field that is empty on
330 rows documents nothing while being maintained everywhere.

The locality the table gives up — a member's row and its capability in different files — is bought back
mechanically rather than by care: `every_capability_entry_names_a_member` fails on an entry naming a
class or member that does not exist, and § 7's test fails on a member that needs an entry and has none.

### 4. Path scope is canonicalise-then-prefix, and a path that does not exist yet is its deepest existing ancestor

Path-bearing capabilities resolve by the comparison
[0104](0104.md) § 1 already wrote and
`crates/nvs-config/src/app.rs` already implements: **canonicalise both sides, then compare whole
components with `Path::starts_with`.** `/srv/data/../etc/passwd` does not reach a root of `/srv/data`,
a symlink planted under a granted root does not carry the root's grant to its target, and
`/srv/database` is not under `/srv/data`. There is one implementation of this rule in the tree and
adding a second is how one of the three callers ends up accepting a symlink.

The granted roots are canonicalised **once, when the snapshot is built**, exactly as an `[[app]]`
block's key is: a root that is still spelled the way the operator typed it is a comparison against the
wrong thing, and doing it per call would put a `realpath` on the grant side of every check.

One case § 1's rule does not cover on its own: **a write to a file that does not exist yet cannot be
canonicalised**, because `std::fs::canonicalize` resolves an existing path. Creating it first to find
out whether creating it is allowed is obviously wrong. So the argument path canonicalises its **deepest
existing ancestor** and re-appends the remaining components, with the remainder refused outright if it
contains `..` — an unresolvable `..` is the one component that could still escape after the ancestor is
pinned, and there is no legitimate spelling of a new file's path that needs one.

### 5. A denial is a `RuntimeError` that names the capability, never a `FATAL`

A denied capability throws, and a program may catch it and degrade. It is not a
[0020](0020.md) escalation: a limit breach is a `FATAL` because the request has
already consumed something it cannot give back and the runtime can no longer reason about its state,
whereas a capability denial is known *before* any work is done and leaves nothing behind. A cache that
falls back to recomputing when `fs.write` is not granted is a reasonable program, and making the refusal
uncatchable would forbid it.

The class is `RuntimeError` — "the world said no", where the world is the operator — and no new class is
added to [01-core-library.md](../spec/01-core-library.md) § 10's tree. The message names the capability
in its configuration spelling and, for a scoped one, the argument that fell outside the grant:

```
RuntimeError: Core\IO::write needs the capability `fs.write` for /var/tmp/x, which is not granted
```

Naming the capability rather than the operation is deliberate: the reader of that message is usually the
operator, and `fs.write` is the string they will add to `nvs.toml`.

### 6. What it costs

**A member that needs no capability pays nothing at all** — no table lookup, no branch, no field on its
row, no code emitted at its call sites. That is the direct consequence of § 2 and § 3: the check lives
inside a function such a member never calls, and the declaration is data no execution path reads.

A member that *does* need one pays, on top of a syscall: an enum-indexed field read on the snapshot it
already holds, and for a scoped capability one canonicalisation of the argument plus a component-wise
prefix compare per granted root. The canonicalisation is one `realpath`, which is on the order of a
microsecond and is dwarfed by the `open` it precedes — and every member that reaches this check is by
construction about to make a syscall, so **the check is never on a hot path**. This is the whole
latency argument (`AGENTS.md`'s priority 3), and it holds because of *where* the check is rather than
because of how it is written.

### 7. How the closure test knows a member needs one

`every_capability_bearing_member_declares_its_capability` (this goal's item 16) reads the registry, not
the bodies. A class is **capability-bearing** if any of its members has an entry in § 3's table; for
such a class, **every member owes exactly one entry**, and a member that genuinely needs no capability
— `Core\IO::basename` manipulates a string and touches no disk — declares that by entering the table
with **no capability rather than none**, which is why § 3's third column is an *optional* capability.

**There is no allowlist, which is the point.** A member that is hard to classify is a member whose
capability has not been thought about, and the answer is to think about it, not to exempt it — so the
one move this design forbids is the one an exception list makes cheapest. The test is a claim about the
*set*, and a set with a growable exception list makes no claim; a set whose every member carries a row
makes a total one. Declaring "nothing" costs what declaring `fs.read` costs, is reviewed in the same
table beside its reason, and grants nothing — no row grants anything, per § 3.

This replaced a frozen one-entry allowlist beside the test, and what broke it was the second honest
entry rather than a dishonest one: `Core\Cache::local` and `Core\RateLimit::shed` are siblings of doors
(`shared()`, `consume`) whose own state is a map in the calling core's thread, and both were classified
before they were written. A list frozen at one had no room for the second, and unfreezing it would have
traded a real claim for a convention nobody could enforce.

The second half of the closure claim is § 2's `nvs_stdlib_reaches_the_os_only_through_the_gate`. The two
tests fail on different mistakes and neither subsumes the other: the first catches a member that reaches
the OS through a door but is not declared as doing so, the second catches a member that reaches it
without a door at all.

## Consequences

- The capability surface of the language is auditable from one file and one test, and neither is on the
  request path.
- Every future `Core` member that touches the operating system is written against `nvs-runtime`'s doors
  rather than against `std`. That is friction, and it is the point: the door is where the check, the
  path rule and the diagnostic already are, so a member that goes through it inherits all three.
- `nvs-stdlib` gains a dependency on `nvs-config` for the `Cap` enum. The enum is the one place a
  capability *name* maps to the field of `Capabilities` that grants it, so a new capability is one
  variant and one arm rather than a string compared in several modules.
- A member needing a capability the configuration cannot express is now a visible failure at the door
  rather than an unnoticed one — there is no `Cap` variant to pass.

## Alternatives rejected

- **A check emitted at every call site by `nvs-codegen`, driven by the row.** Unforgeable for a lowered
  call, and it costs a branch and a snapshot read at every call site rather than one inside the effect.
  It also does not cover a member reached any way other than a lowered call, and it would have to
  marshal the scoped argument — the path — into the check at every site. Strictly more machinery for
  strictly less coverage.
- **A guard emitted by `nvs_helper!` before every member body.** Every member does go through that
  macro, but the macro cannot see the row, so it would have to look the member up by symbol on every
  `Core` call — a table lookup on `Core\Str::repeat` to learn that it needs nothing. Priority 3 refuses
  it.
- **The check written by hand as the first line of each body.** This is the shape the closure test would
  have to prove by reading Rust source for a call, which is a test about text rather than about data.
  § 2's inversion — the check inside the only door — makes the same guarantee with no test at all.
- **A dedicated `SecurityError` in the § 10 tree.** It would let a program catch a denial specifically,
  which is a real benefit; it costs a class in the spec's exception tree, a `ThrownClass` variant and
  its four cross-references, and it invites `catch (SecurityError)` as a way to make a policy refusal
  look handled. `RuntimeError` with the capability in the message is enough for the program that wants
  to degrade. Revisit if a real program needs to distinguish a denial from an I/O failure
  programmatically.

## Verification

- `an_ungranted_capability_throws_naming_the_capability` — a member called under a snapshot that does
  not grant its capability throws, and the message carries the capability's configuration spelling.
- `a_path_reaching_a_granted_root_through_dotdot_or_a_symlink_does_not_match` — § 4, on both spellings,
  and the neighbouring case that a sibling directory sharing a name prefix does not match either.
- `every_capability_entry_names_a_member` and
  `every_capability_bearing_member_declares_its_capability` — § 3 and § 7's two directions.
- `nvs_stdlib_reaches_the_os_only_through_the_gate` — § 2's constructive half.
- `examples/capability.nvs`, frozen in `docs/agent/loop-goal.toml`: a granted read succeeds, an
  ungranted `fs.write` and an ungranted `script.spawn` are refused by name.
