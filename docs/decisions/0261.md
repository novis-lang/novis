# ADR 0261 — An enum case in a tagged value carries an enum tag of its own, one per backing type, over its backing integer's payload

- **Scope:** the runtime tag an enum case takes once it is materialized into a 16-byte value, and which
  readers of a tagged value see it. What an enum costs where its static type is known is
  [0010](0010.md)'s and is unchanged.
- **Depends on:** [0010](0010.md), [0035](0035.md), [0150](0150.md).
- **Validated by:** `tests/conformance/enum/a-case-backed-by-zero-in-a-mixed-is-truthy-and-not-an-int.nvst`
  and `tests/conformance/core/arr-a-callback-enum-parameter-checks-the-enum-tag.nvst`.

> **In short:** the tag [0010](0010.md) reserved for an enum is spent, as two tags: `EnumInt` (8) for an
> `int`-backed enum and `EnumUint` (9) for a `uint`-backed one. The payload is the backing integer, as
> before. A condition, a type test, a closure parameter's check and a declared slot's write check read
> the enum tag. Every reader that decodes a payload reads a case as its backing integer, as before.

## Context

[0010](0010.md) made an enum case its backing integer and reserved a tag for it without spending it, so
a case put into a `mixed` took the `Int` or `Uint` tag. [0035](0035.md) makes every case truthy, and a
case backed by `0` that passed through an `array<mixed>` or an erased parameter was falsy there: one
value, two answers in a condition. `$value is int` was `true` for a case, and `$value is Rank` was `true`
for any integer equal to one of its cases. The user decided that the reserved tag is spent.

## Decision

### 1. Two tags, one per backing type

`nvs_runtime::Tag` gains `EnumInt = 8` and `EnumUint = 9`, the two discriminants the roster had left
open. The payload is the case's `i64` or `u64`, exactly as `Int`'s or `Uint`'s is. One tag per backing
keeps the payload's signedness with the value, so nothing reads a `uint` case above `i64::MAX` as a
negative number, and no padding byte has to be written. The tag does not name the enum: two enums with
one backing are not told apart in a `mixed`.

`nvs_codegen::ty::tag_of` and `nvs_ir::lower::param_tag_nibble` answer the enum tags for
`Ty::Enum`, so every place compiled code writes or tests a tag follows from those two functions. A
statically typed enum still costs nothing: the tag is written only where a case is materialized into a
tagged value.

### 2. Who sees the enum tag

`Value::exact_tag` returns the tag as written. `Value::tag` returns the tag a payload is read as, which
is `Int` for `EnumInt` and `Uint` for `EnumUint`, and `as_int`/`as_uint` accept a case. So the readers
that only decode a value — printing, conversion, comparison, JSON, a database row, a record, a message
across an isolate — read a case as its backing integer with no change. The readers that ask which type a
value is read `exact_tag`:

- `value_truthy`, so a case is always truthy ([0035](0035.md));
- the compiled type test `InstKind::TagIs`, so `$value is int` is `false` for a case and `$value is Rank`
  is `false` for a plain integer ([0150](0150.md));
- a closure parameter's check, so an enum parameter accepts a case of either enum with its backing and
  throws `LogicError` for an `int`, and an `int` or `float` parameter throws for a case;
- a declared property slot's write check through an erased receiver;
- an `array<T>` element-tag walk.

`===` between two tagged values reads `Value::tag`, as does the hash beside it, so a case in a `mixed`
is identical there to an integer of the same value. That keeps the two agreeing, and no rule asks
for more.

## Consequences

A ported `if ($status)` whose case reached a `mixed` takes the branch PHP takes. `$any as Rank` still
converts an integer to a case, because the conversion reads the payload. A callback typed with an enum
parameter now refuses an `int` argument, which it used to accept unchecked. `Core\Reflect`'s type kind
still reports a case in a `mixed` as `int` or `uint`.

## Alternatives rejected

- **One enum tag with the signedness in a padding byte.** Every tag write would have to write the pad,
  and every reader would need a second byte to read the payload.
- **The enum's identity in the padding bytes.** It tells two enums apart in a `mixed`, which no rule asks
  for, and it costs a store on every materialization.
- **`Value::tag` returning the enum tags.** Every reader of a payload would need a new arm, a few hundred
  of them, for a value they all read as its integer.
