# ADR 0244 — An attack that ends early names the step and the ending it stops with, and stopping anywhere else fails it

- **Scope:** What `// hostile: ends-early` declares, how the proof runner checks it, and what an
  attack that ends early prints. Which endings count as a pass at all is unchanged.
- **Depends on:** [0134](0134.md) (the hostile-case contract).
- **Validated by:** `tools/nv/test/hostile-ending.test.ts`.

> **In short:** the marker becomes `// hostile: ends-early <step> <ending>`. The step is the number
> of the file's last step. The ending is the class the runtime's error report names for an uncaught
> throw, `FATAL` for a stop the runtime reports as one (every limit), and `exit` for an `exit` with a
> non-zero status. The declared step prints `step <N>` on a line of its own as its first statement.
> The case passes only when that line was printed and the program then stopped with the ending it
> names. Stopping before the step, stopping with another ending, running to the last line and a
> marker with no step or no ending all fail it, and the failure names both what was declared and
> what happened.

## Context

The contract already says that what cannot be caught is the file's last step and that the case
declares its ending. The runner checked only half of that: under `ends-early` it accepted any
non-zero exit, from any step, for any reason. An attack written to reach a memory limit in step 4
that threw in step 2 passed, and steps 3 and 4 were never delivered. That is the failure the
contract exists to catch, one marker away from being caught.

## Investigation

What the CLI prints for each way a program stops, read off a run of each:

- **An uncaught throw** prints the error report (`rule:errors/log-write`), whose `class` field names
  the class and whose frames name the file and line of every call, the outermost in the script
  itself (`crates/nvs-runtime/src/floor.rs:125`).
- **A `FATAL`** prints `FATAL: ` and a message, and nothing else
  (`crates/nvs-cli/src/main.rs:3068`). It has no class and no frames, by design: no backtrace is
  taken on the path that stops a program at a limit. Every limit stops a program this way
  (`rule:errors/on-limit`).
- **`exit`** prints nothing and leaves its status as the process status.

So a line is available for one ending of the three, and most attacks that end early end at a limit.

## Decision

### 1. The marker names the step and the ending

`// hostile: ends-early <step> <ending>`, both required. The step is the number its step comment
carries (`// 4.` or `// Step 4:`); a file with one attack is step `1`. It must be the file's last
step, because only the last step may end the program. The ending is one of:

| The program stops with | The ending written |
|---|---|
| an uncaught throw | its class, as the report's `class` names it: `RuntimeError` |
| a `FATAL` (any limit) | `FATAL` |
| `exit` with a non-zero status | `exit` |

The goal that asked for this assumed a limit has a class of its own. It does not, and the name
written is the word the runtime prints. Giving a `FATAL` a class would change what every operator
reads for the sake of a test runner.

### 2. The step prints that it started

The declared step's first statement is `echo "step <N>\n";`. That line is how the runner knows the
program reached the step, whatever the ending: a `FATAL` and `exit` name no line, and one rule for
every ending is simpler for an author than one for throws and another for the rest. Where the report
does name a line, the runner maps the outermost frame in the attack file to the step comment above
it, and its failure message names that step.

### 3. The verdicts

| What happened | Verdict |
|---|---|
| `step <N>` printed, then the declared ending | pass |
| `step <N>` never printed | fails: *stopped before step N*, naming the step the report points at when there is one, and the ending |
| `step <N>` printed, another ending | fails, naming both endings |
| ran to the last line (status `0`) | fails, as before |
| the marker has no step or no ending, or its step is not the last | fails, before the program is judged |

The message names the declared and the reached together: `stopped at step 2 with RuntimeError,
declares step 4 with FATAL`.

### 4. Tradeoffs

Performance and memory: nothing; no program a user runs changes. Usability for the author: two
tokens on the marker and one `echo` in the last step. Simplicity: one more line of convention, and in
exchange the marker states a fact the runner checks rather than a hope.

## Consequences

- Every attack that declares `ends-early` gains its step, its ending and the `echo`, each read off a
  run of it. An attack that stops before its last step is fixed so the step runs. Moving the marker
  to the step it stops in is softening it, and `tests/hostile/README.md` refuses that.
- The `echo` is backward compatible with the old runner, so the attacks can gain it before the
  runner starts to require it.

## Alternatives rejected

- **The report's line alone.** It finds the step for a throw, and a throw is the ending an attack
  should not have. A `FATAL` has no frames, so the endings that matter most would go unchecked.
- **A class for each limit** (`MemoryLimitError`). No such class exists, and none should exist only so
  that a marker can name it.
- **Freezing the last line of output.** That is the frozen output the contract refuses.

## Revisiting

If a `FATAL` report ever names the limit it stopped at with a stable word, the ending names that word
instead of `FATAL`, so that a memory attack stopped by its time limit fails too.

## Verification

`tools/nv/test/hostile-ending.test.ts` pins the verdicts in § 3 and reads every attack under
`tests/hostile/`, failing on an `ends-early` without a step and an ending.
