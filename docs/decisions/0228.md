# ADR 0228 — a timing check warns at a soft bound and fails only at a hard bound an order of magnitude further, and a count is the check that fails at once

- **Scope:** how a test that asserts a wall-clock figure is judged: the guards in
  `benches/abi-probe/tests/perf_guards.rs` and the latency check in `crates/nvs-lsp/tests/latency.rs`. It
  does not reopen [0026](0026.md)'s two mechanisms, it moves no job between [0143](0143.md)'s lanes, and
  the historical dashboard and the member perf ledger stay as they are.
- **Depends on:** [0026](0026.md) (a wall clock is not comparable across machines), [0191](0191.md)
  (counts that read the same on any machine are the headline of the member perf ledger).
- **Validated by:** `judge` in `benches/abi-probe/tests/perf_guards.rs` and `judge` in
  `crates/nvs-lsp/tests/latency.rs`, and the runs under *Verification*.

> **In short:** a test that asserts a timing holds it against two bounds. Past the **soft bound** the test
> passes and prints a warning that reaches the CI log, the run's annotations and the step summary. Past
> the **hard bound**, ten times further out, the figure is measured again, and the test fails only when
> the third attempt is past it too. Where ten times would pass the change of kind the check exists to
> catch, the hard bound sits just short of that change. Every attempt is labelled steady or noisy from a
> fixed loop timed before and after it. A deterministic count has one bound and fails at once, and a check
> whose question a count can answer is a count. The price: a slowdown between the two bounds no longer
> fails CI.

## Context

A timing guard failed on a shared CI runner, and no change to the code it measures was behind the
failure.

[0026](0026.md) keeps the per-PR guards on the wall clock because a guard compares two timings taken in
one run on one machine. That holds for the comparison. It does not hold for the bound. A bound is a number
chosen on one machine and enforced on every other, several guards assert a time in nanoseconds with no
second timing to divide it by, and load on a machine moves a figure inside one run. A single bound is then
either loose enough to pass the change of kind the guard exists for, or tight enough to fail with no
change behind it.

## Decision

The decision is the project owner's, taken after that failure.

### 1. A timing check has a soft bound and a hard bound

The **soft bound** is where the figure stays on an ordinary machine. A figure past it fails nothing. The
test prints a warning, and the warning is written straight to the process's standard output, because
libtest holds back what a passing test prints through `println!`. On GitHub Actions the line is a
`::warning` workflow command, which lists it among the run's annotations, and a line is appended to the
file `GITHUB_STEP_SUMMARY` names. Elsewhere it is a plain line.

The **hard bound** is ten times the soft one. Ten times is not a rule where it would pass the change of
kind the check exists to catch: a guard whose ratio is near one, or whose whole claim is a factor smaller
than ten, has its hard bound just short of the figure that change reaches.

### 2. A figure past the hard bound is measured again

The check measures up to three times, and only the last attempt is judged. A burst of load that lands on
one attempt passes on the next. A change of kind is past the bound on every attempt, so it still fails.

### 3. Every attempt is timed between two readings of a yardstick

The yardstick is a fixed scalar loop that does the same work on every run. It is timed before and after
each attempt. When the two readings differ by more than 25% of the faster one, the attempt's printed
figure says `noisy`, and otherwise `steady`. Every printed time also gives its ratio to the yardstick.
Neither the label nor the ratio is judged: they are what a reader of a warning has for telling a busy
machine from a slower program.

### 4. A count has one bound, and a check that can be a count is one

Allocations, emitted calls and executed statements read the same on any machine, however loaded. A count
therefore has a single bound and no second attempt, and it fails the moment it is missed. Where a guard's
question can be asked as a count, the check that fails is the count, and a timing beside it is a sanity
bound. [0191](0191.md) makes the same choice for the member perf ledger, whose counts are the columns a
report diffs and whose clock is compared only with its own machine.

### 5. A timing is compared only with a timing from the same machine

No claim is made from two timings taken on two machines. A warning is answered by measuring the commit
before it on the machine that warned.

## Consequences

- **What it loosens.** A slowdown that lands between the soft and the hard bound no longer fails CI. It
  shows as a warning, and catching it is the job of a same-machine comparison and of the counts.
- **What no count sees.** A slowdown with no count behind it, such as a layout that misses the cache more
  often or a slower instruction sequence, shows only as a warning until it reaches the hard bound.
- **Performance and memory.** Nothing a program or the server runs changes, because all of this is test
  code. It spends no memory per request or per task. A test run pays two yardstick readings per attempt,
  and up to two further attempts when a figure is past its hard bound.
- **Usability.** A red timing check means a change of kind and no longer a busy runner, so a contributor
  who sees one has something to fix. A warning fails nothing, so it is seen only by somebody who reads the
  run's annotations or its step summary.
- **Simplicity.** Every timing check states two numbers where it stated one, and the judgement is one
  helper per test binary. `latency.rs` carries its own copy of it, because one test binary cannot call
  another's helper, so a change to how a timing is judged is made in both files. The language and its
  surface are untouched.

## Verification

`crates/nvs-lsp/tests/latency.rs` was run three ways through `cargo test --test latency`, with no
`--nocapture`, and its bounds were restored afterwards:

| Bounds | Environment | What the run showed |
|---|---|---|
| soft bound under the measured figure, hard bound over it | none set | both tests passed, and a `warning:` line stood above each test's `ok` |
| the same | `GITHUB_ACTIONS` and `GITHUB_STEP_SUMMARY` set | the line was a `::warning` command, and the summary file gained one line per check |
| hard bound under the measured figure | none set | each test measured three times and failed on the third |

`perf_guards.rs` holds each of its timing guards to the same judgement through its own `judge`, and its
counts keep their single bound.
