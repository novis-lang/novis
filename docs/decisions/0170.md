# ADR 0170 — on SQLite the claim's mutual exclusion is the immediate transaction, and the claim carries no locking clause because there is nothing left for one to do

- **Scope:** what arbitrates a claim on the one backend with a single writer, and where the primitive
  that provides it sits. It does not touch the claim's shape on the other dialects, which is
  [0084](0084.md)'s, and it decides nothing about how many workers an operator runs.
- **Depends on:** [0084](0084.md) for the claim, the visibility timeout and the at-least-once
  guarantee that rests on them; [0067](0067.md) for the drivers being an enum whose entry points
  `match` once.
- **Validated by:** `crates/nvs-db/src/sqlite.rs`'s own cases for the primitive and
  `crates/nvs-stdlib/tests/queue_sqlite.rs` for the claim, both named in *Verification*.

> **In short:** `rule:concurrency/claiming-is-one-statement` already names SQLite's claim as an
> immediate transaction. What it does not yet say — and what a later contributor will read the other
> dialects and try to correct — is that on this backend the mutual exclusion **is** that transaction.
> SQLite has one writer, so inside an immediate transaction no second connection is writing at all
> and two workers cannot come back with one row; `for update skip locked` buys exactly that on a
> backend that has row locks and concurrent writers to need them from. So `CLAIM_SQLITE` carries no
> locking clause, cannot be given one, and the reason is not that SQLite lacks the spelling. The
> transaction is *immediate* rather than deferred because the read-then-write pair would otherwise
> ask to upgrade a shared lock, which SQLite refuses without honouring the busy timeout, and
> `SqliteConn::begin_immediate` is its own entry point rather than a sixth `Isolation` case because
> what it asks is *when* a lock is taken and not how much of the world the transaction sees.

## Context

- [0084](0084.md) makes a claim one act the database arbitrates: the worker selects the oldest due
  job in its queues and marks it in the same moment, and the runtime writes no lease protocol, no
  heartbeat and no coordinator. `rule:concurrency/claiming-is-one-statement` is that rule, and it
  names the mechanism per dialect — `for update skip locked` on PostgreSQL and MySQL, `readpast` on
  SQL Server, an immediate transaction on SQLite.
- On the two dialects that cannot express the claim as one statement, `queue.rs`'s `Split` runs it as
  a pair inside a transaction: the `select` names the row, the `update` keys on the id it named. That
  is a settled trade and this record does not re-open it.
- **The tension this record exists to settle is that SQLite's claim looks under-specified beside its
  neighbours.** Read down the dialect arms, `CLAIM_POSTGRES` and `CLAIM_MYSQL` each carry a locking
  clause and `CLAIM_SQLITE` carries none, so the shape of the code says *something is missing here*
  while the truth is the opposite: the exclusion is stronger, and it is provided one level up, by the
  transaction the pair runs inside. A sentence in a statement comment is not enough for that, because
  the correction — "add `skip locked` for parity" — is one a reader reaches for from the shape alone
  and is refused by a fact about the database rather than by taste.

## Investigation

- SQLite's writer is exclusive for the whole database, not for a row or a table. Two connections may
  read concurrently; the second to want the write lock waits, and `set_busy_timeout` bounds that wait.
  There is therefore no state in which two workers hold write locks over one jobs table at once, and
  no row for a `skip locked` to skip past.
- **A deferred transaction does not have that property when the claim needs it.** `BEGIN` opens a
  deferred transaction, which takes no lock until its first statement; a claim reads and then writes,
  so it holds a shared lock and asks to upgrade it — and SQLite answers an upgrade it cannot grant
  with `SQLITE_BUSY` *without honouring the busy timeout*, because backing a reader off a lock it
  already holds would break that reader's own snapshot. `SqliteConn::begin_immediate`'s doc comment
  in `crates/nvs-db/src/sqlite.rs` owns that reasoning at the point the primitive is defined.
- **It reproduces on two connections and never on one**, which is why the failure is worth a record
  rather than a comment: a single-connection test of a deferred claim passes, and the pair only
  breaks under the concurrency the claim exists to survive.
- `Isolation`, the enum `Core\Db::transaction` takes, is the SQL standard's levels. None of them
  means "take the write lock now": SQLite's isolation is serializable under either spelling, so an
  `Isolation::Immediate` would be a sixth case that answers a different question from the other five.

## Options considered

1. **A deferred transaction plus a retry loop around `SQLITE_BUSY`.** Keeps one `begin`, and pays for
   it with a busy-error path the timeout was supposed to have already covered, on the hot path of
   every claim.
2. **A sixth `Isolation` case.** One entry point, and it puts a lock-acquisition question in an enum
   about visibility, where four other drivers must then answer it with an error.
3. **A lease table or an advisory lock of the runtime's own.** Restores symmetry with `skip locked`
   by writing the coordinator [0084](0084.md) refuses to write.
4. **An immediate transaction through its own entry point, and no locking clause in the statement.**
   Chosen.

## Decision

### 1. SQLite's claim is `CLAIM_SQLITE`'s pair inside an immediate transaction

The claim is the `Split` the other two-statement dialect already runs — a `select` that names the
oldest due job in the queue, an `update` keyed by the id it named — and every `Split` the SQLite side
runs is inside a transaction that began with `BEGIN IMMEDIATE`. A statement that stands alone does
not need the transaction; a pair always does.

### 2. The exclusion is the single writer, so there is no locking clause and none can be added

`CLAIM_SQLITE` carries no `for update skip locked` and no equivalent. The reason is not that SQLite
lacks the syntax — it is that inside the immediate transaction no second connection is writing at
all, so the guarantee the clause buys elsewhere is already held. A worker that arrives second waits
for the write lock, and when it proceeds the row the first one took is no longer due, so it comes
back with nothing rather than with the same job. **This is the sentence a later contributor will try
to correct toward `skip locked`, and it is the reason this record has a number.**

### 3. `begin_immediate` is its own entry point, not a sixth `Isolation`

`SqliteConn::begin_immediate` sits beside `begin` on the driver: it refuses any depth above zero,
because an immediate transaction is an outermost one and a `SAVEPOINT` holds whatever lock the
transaction around it took — which makes the one thing the caller asked for the one thing a nested
level cannot give. It moves the depth only after a command SQLite accepted, so a refused `BEGIN
IMMEDIATE` leaves a connection that is still in no transaction.

### 4. Nothing on the language surface moves

`Core\Db::transaction` opens the deferred transaction it always has, for every caller that does not
ask, and there is no new option, key or enum case a program can name. The immediate transaction is a
driver-internal primitive the queue's own statements use, and the only place it is reachable from is
the runtime's worker.

## Consequences

- **Throughput against a SQLite queue is bounded by the database's single writer**, and that is a
  property of the database rather than a defect of the queue. Workers above one serialize on the
  write lock and wait out the busy timeout instead of proceeding in parallel, so `[queue] workers`
  buys throughput there only up to the point one writer allows. The queue adds no lock, no shard and
  no second file to work around it; what it owes is a sentence where an operator reads `workers`.
- **The claim costs one transaction's worth of round trips where PostgreSQL costs one statement.**
  That is `Split`'s existing trade, already paid on MySQL and MariaDB, and here the round trips are
  function calls into a file rather than messages over a socket, so it is the cheaper end of that
  trade rather than a new one.
- **What this spends**, per `rule:programs/memory-priority`: nothing per job on the request path, and
  no allocation the queue was not already making. A transaction is a depth counter the connection
  already carries.
- The visibility timeout and the at-least-once guarantee are unchanged: a worker that dies inside the
  immediate transaction leaves the transaction unfinished, the row pending, and the job claimable by
  the next worker, exactly as `rule:concurrency/delivery-is-at-least-once` describes.

## Alternatives rejected

- **A locking clause for parity with the other arms.** `skip locked` is a syntax error on SQLite, and
  fixing the syntax would not be the point: there is nothing for it to do. Parity of *shape* between
  dialect arms is not a goal — parity of *guarantee* is, and that is what this arrangement has.
- **A single `update … where id = (select …) returning …` claim.** It is a real alternative to the
  pair and it is refused here because the rule names the immediate transaction; moving to it is an
  edit to `rule:concurrency/claiming-is-one-statement` through a record whose `changes:` block names
  that rule, not a change a dialect arm makes on its own.
- **A build option that unlocks a wider SQLite grammar or a concurrent-write mode.** A queue statement
  that parses only under a non-default `libsqlite3-sys` build is a statement that stops parsing the
  day the dependency moves.
- **A lease table, an advisory lock or a coordinator process.** [0084](0084.md) refuses these for every
  backend, and the backend where contention is settled by the database itself is the last place to
  make an exception.

## Revisiting

The trigger is a SQLite the runtime links against in which two writers can proceed at once. § 2 rests
on the single writer and on nothing else, so a mode that admits concurrent writers to one database
makes the paragraph false rather than dated, and the claim would then need what the other dialects
have. Nothing else here moves with it: § 3's entry point is right either way, because taking the
write lock up front is still not an isolation level.

## Verification

- `crates/nvs-db/src/sqlite.rs` holds the primitive's cases, over two connections to one database:
  `an_immediate_transaction_holds_the_write_lock_before_its_first_statement_runs`,
  `core_db_transaction_still_opens_the_same_deferred_transaction_it_always_did`,
  `an_immediate_transaction_asked_for_inside_an_open_one_is_refused` and
  `a_refused_immediate_begin_leaves_the_connection_in_no_transaction`.
- `crates/nvs-stdlib/tests/queue_sqlite.rs` holds the claim itself, against the schema
  `nvs queue migrate` applies and never a copy of it:
  `two_connections_claiming_one_sqlite_file_never_come_back_with_the_same_job` is § 2 asserted
  directly — the second connection answers nothing rather than the same job —
  `a_sqlite_claim_reads_the_attempt_it_is_about_to_have_and_not_the_one_before` pins what the pair's
  two halves agree on, and `a_sqlite_claim_takes_a_job_whose_visibility_window_has_passed` pins the
  visibility cutoff on both sides.
- Both run on the default `python tools/verify.py` legs: an in-memory database needs no container, so
  nothing here is behind the five-driver matrix gate.
