# ADR 0128 — A PDF page is a decode source of the image component

- **Scope:** admitting PDF to the image component's format roster as a decode-only source — the `open`
  options that select a page and a scale, what `info` reports without rasterising, how the pixel cap
  prices a page, what is refused rather than approximated, and the engine. Not in scope: PDF
  *generation* ([0121](0121.md)); text extraction,
  page manipulation and forms, which stay in the third-party channel (§ 5); the sandbox contract
  ([0003](0003.md)); the builder's plan/terminal shape and the component's entry points
  ([0120](0120.md) §§ 2–3, which gain
  options here but no new member); scheduling — the second wave has no milestone, deliberately, like
  the roster it joins.
- **Depends on:** [0120](0120.md) —
  the pipeline, roster and cap this ADR extends; [0003](0003.md) — the sandbox that
  makes shipping a PDF interpreter admissible at all.

> **In short:** an uploaded PDF becomes an image the way an uploaded SVG does — `Image::open($bytes,
> {page: 3, dpi: 150})` rasterises one page into the ordinary pipeline, and
> `Image::info($bytes)->frames` is the page count, read from the page tree without allocating a pixel.
> The job this replaces is PHP's ImageMagick-delegating-to-Ghostscript pair: an installed, unsandboxed
> interpreter with an RCE history long enough that ImageMagick's stock `policy.xml` ships with the PDF
> coder disabled. The engine is **hayro**, a pure-Rust PDF interpreter from the same ecosystem as
> [0121](0121.md)'s writer, running inside the
> sandbox where a parser this large belongs. The selected page's box at the requested dpi is priced
> against `[image] max_pixels` before any buffer exists; an encrypted document, a page out of range and
> an embedded object the engine recognises but cannot decode all **throw** rather than rendering
> approximately, and equal input gives byte-equal output. Decode only: rasterising is how a PDF becomes
> a thumbnail, a preview or a validated upload — text extraction and page manipulation are different
> jobs and stay third-party, and generation stays 0121's.

## Context

- **The userland job, and what PHP does today.** "Thumbnail this uploaded PDF" and "how many pages is
  it" are as routine as the jobs [0120](0120.md)'s
  Context lists, and PHP answers both with ImageMagick delegating to an installed Ghostscript: an
  operational dependency outside the package manager, a process per page, and a security record —
  `-dSAFER` bypasses, pipe-device RCEs — bad enough that ImageMagick's own default policy disables the
  PDF coder and every hardening guide repeats the advice. The genre's standing answer is a
  PostScript-descended interpreter running unsandboxed on the host.
- **[0051](0051.md) § 2's tests, applied.** Rasterisation is a pure
  `bytes → bytes` transform holding no cross-request state (tests 1–3: no). Test 5: **emphatically** —
  a PDF embeds fonts (Type 1, CFF, TrueType), images (JPEG, JBIG2, JPX, CCITT) and content streams,
  a strictly larger hostile-bytes case than any format already on the roster. Test 6: yes — the
  alternative is every deployment wiring its own Ghostscript.
- **An engine now exists, which it did not when 0120 was written.** hayro is a pure-Rust PDF
  interpreter and rasteriser from the author of `krilla` — the writer 0121 already picked — tested
  against 1400+ PDFs scraped from the PDFBox and pdf.js regression suites, and the most complete
  implementation in Rust. It is young: performance is not yet a focus, and fidelity gaps remain
  (knockout groups, non-embedded CID fonts). § 4 names what the building wave must verify before
  linking it.
- **0120 already built the seam.** SVG's second-wave admission is the exact template: a vector source
  whose declared canvas is priced against the pixel cap, rasterised because that is the safe way to
  display hostile input, with no external reference ever resolved.

## Decision

### 1. Placement: a decode-only format of `nvs/image`, second wave

PDF joins [0120](0120.md) § 5's
roster **decode only**, in the second wave beside SVG. It is not a member of `nvs/pdf`: a writer and an
interpreter share no code, and a raster produced there would recross the boundary to enter the image
pipeline that is the whole point of loading one. No new entry point is added — the plan/terminal shape
and § 3's closed set are unchanged; `Format` gains a `Pdf` case.

### 2. One page per `open`, pages counted by `info`, the page priced by the cap

`open` gains two options meaningful for a paged source: **`page`** (1-based, default `1`) and
**`dpi`** (default `150`). A call rasterises exactly that page; a document's pages become images by
iterating, one `open` per page, so cost stays proportional to what was asked for. The pixel price is
the page box scaled to the requested dpi — `ceil(width_pt × dpi / 72) × ceil(height_pt × dpi / 72)` —
counted against `[image] max_pixels` before any buffer is allocated, exactly § 6's header read. A
`page` beyond the document throws a `RuntimeError` naming the page count.

`info` parses the xref and page tree and never a content stream: `format` is `Format::Pdf`, `frames`
is the **page count**, and `width`/`height` are the first page's box in whole points. Counting pages
is therefore one header-only call with no pixel allocated.

Rasterising is a pure function of the bytes and the options — no clock, no I/O, no system fonts — so
equal input gives byte-equal output, the same testability rule
[0121](0121.md) § 5 and
[0123](0123.md) already hold.

### 3. Refusals: encryption, and a detectable omission throws

An encrypted document throws `ParseError` naming the encryption; there is no password option, and
decrypting stays in the third-party channel. An embedded object the engine recognises but cannot
decode throws naming the object rather than rendering a blank region — the rule
[0095](0095.md) states and
[0121](0121.md) § 2 applies to a missing asset:
a generated image must be deterministic, not approximately right. An external reference never
resolves, because nothing in the guest can resolve one; JavaScript, launch actions and embedded files
are inert by construction, since rasterising reads a page's appearance and never executes an action.

### 4. The engine: hayro, in the sandbox, with the standard fonts swallowed

The interpreter is **hayro**, pure Rust, compiled into the `.nvsx` beside the codecs. Substitutes for
the PDF standard-14 fonts are embedded in the component's data section so an unembedded-font document
renders out of the box — the precedent [0051](0051.md) § 3 set with CLDR and
[0121](0121.md) repeated with its default fonts.
Two prerequisites are owed by the building wave before the crate is linked, recorded here so
scheduling inherits them: it builds for the component's `wasm32` target, and its dependency tree
passes [deny.toml](../../deny.toml). hayro is young, and an *approximated* supported construct — as
opposed to § 3's detectable omission — is a silent fidelity miss; the Consequences own that surface.

**What it spends**, per request that opens a PDF: the encoded document and one page's raster at at
most the pixel cap — 96 MB worst case at 24 MP RGBA8 — inside the extension's existing `StoreLimits`,
nothing outliving the request. Per binary: the interpreter and the font substitutes grow the `.nvsx`
by single-digit megabytes. CPU is the request's epoch deadline; per-page wall-clock is unmeasured
until the building wave commits numbers, and bulk rasterisation belongs in `Core\Queue` — the line
[0120](0120.md) § 5 draws for AVIF.

### 5. What is not admitted

Text extraction, page splitting and merging, form filling, signing and password decryption are
different jobs over the same bytes: the third-party channel's, not this roster's. Generation is
[0121](0121.md)'s. The fidelity escape hatch for
a document hayro renders wrong is an installed Ghostscript or `pdftoppm` under `process.exec` via
[0044](0044.md) — the shape 0121 § 6 already blessed — and is never
made first-party.

## Consequences

- **The two userland questions become one call each**: `Image::info($bytes)->frames` counts pages with
  no pixel allocated, and a thumbnail of page 1 is the ordinary
  `open → resize → format → encode` pipeline. Upload validation gets "is it a well-formed PDF, how
  many pages, how big" the way it already gets those answers for images.
- **The Ghostscript class is absent, not mitigated**: there is no host interpreter, no delegate policy
  to configure, and the hostile-bytes surface that remains is contained by the sandbox's memory cap
  and epoch deadline like every other decoder's.
- **A cost this ADR does not hide:** hayro is the tier's youngest engine against the format with the
  deepest legacy, and "rasterises wrong in `Novis\Image`, fine in Ghostscript" is a standing ticket
  category. § 3 converts the detectable half into a named throw; the approximated half stays silent
  until the engine matures.
- **No new C in the build.** The second wave's growth is pure Rust; libwebp remains the roster's one
  C library.

## Alternatives rejected

- **A `rasterize` entry on `nvs/pdf`.** Keeps "PDF" in one package, but the writer and an interpreter
  share nothing, and every raster would recross the boundary as bytes to reach `resize`. Rejected on
  the cost model that shaped 0120.
- **pdfium or MuPDF compiled to wasm.** Mature fidelity today. Rejected: pdfium is a large C++ build
  no other component needs a toolchain for, MuPDF is AGPL and outside deny.toml, and
  [0051](0051.md) § 4's pure-Rust-first test now has a candidate that passes it.
- **Leave the category to the third-party channel.** The honest competitor, as it was for 0121.
  Rejected for the same pairing: a universal job and a security class — the host-Ghostscript shell-out
  — that first-party ownership of one sandboxed spelling removes.
- **Render a blank region where an embedded object cannot be decoded.** Ghostscript-compatible
  lenience, and more documents "work". Rejected by
  [0095](0095.md): a silently incomplete raster is a repair.

## Revisiting

If the building wave's benchmark puts hayro far from practical for a text-heavy page, or either § 4
prerequisite fails, the fallback is pdfium compiled to wasm under
[0051](0051.md) § 4's second question — never an unsandboxed host dependency,
and never Tier 2. §§ 1–3 are written against the interface, so a swapped engine changes no rule here,
the same clause [0121](0121.md)'s Revisiting
carries.

## Verification

Owed by the wave that builds the second roster, in the component's fixtures, each asserting inside the
guest:

- A 100-page fixture answers `info` with `frames: 100` and `Format::Pdf`, with no pixel buffer
  allocated and one host-to-guest call, counted.
- A page box that exceeds `max_pixels` at the requested `dpi` is refused as a `RuntimeError` before
  allocation, and the same bytes pass at a lower `dpi`; `{page: 7}` of a three-page fixture throws
  naming the count of 3.
- An encrypted fixture throws `ParseError` naming the encryption; a fixture embedding an object the
  engine cannot decode throws naming it (§ 3), never rendering a gap.
- A fixture carrying an external reference, a JavaScript action and an embedded file rasterises with
  nothing resolved and nothing executed, and no network or filesystem access is observable.
- The same page rasterised twice is byte-equal (§ 2).
- A bomb corpus — recursive form XObjects, an xref loop, a stream-length lie, a deflate bomb — ends
  each case in a throw or a contained trap under the epoch deadline, never a hang.
- The benchmark: one text page and one image-heavy page, guest against the same crate native, numbers
  committed beside M9's resize figures.
