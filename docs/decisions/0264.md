# ADR 0264 — A write door opens the path it checked one level at a time from a handle, following no link

- **Scope:** how the `fs.write` doors open the path after the grant check. The copy and rename doors
  come under the same walk; they need a relative copy and a relative rename, and are built after the
  others. Every read door is left as it is and is not decided here.
- **Depends on:** [0118](0118.md), [0104](0104.md).
- **Validated by:** `crates/nvs-runtime/src/beneath.rs`'s tests, which plant a link and a junction where a
  folder was.

> **In short:** `capability::create`, `capability::write`, `capability::create_dir` and the writing
> modes of `capability::open` resolve the path once, ask the grant about that resolved path as written, and open it from the root one level at a
> time, each level relative to the handle above and never through a link. A link planted after the
> check fails the write. A link that was there before the call means what it always meant.

## Context

The grant check resolves a path — canonicalising its deepest existing ancestor — and compares the
result against the granted roots. The doors then opened the original path by name, which resolves it a
second time. A folder replaced by a link between the two resolutions is followed, and the write lands
wherever the link points, outside the grant. `Core\Zip::extract` made this easy to reach: the archive
picks the names, and the extraction creates many files in a folder another process may be writing to.

## Investigation

The extraction already compared each folder's resolution against the destination, one level at a time.
That narrowed the window to the moment between the last comparison and the file's create, and did
nothing for the plain `Core\IO` doors. Linux has `openat2` with `RESOLVE_BENEATH`, and no other
platform Novis runs on has an equivalent. Every platform has a relative open: `openat` on Unix, and
`NtCreateFile` with a root handle on Windows.

## Options considered

1. A handle-relative walk for `Core\Zip::extract` alone.
2. The same walk under every write door that creates or replaces.
3. Keep the window, and state it as a bound in the module doc.

## Decision

Option 2, by the user's answer at the end of goal `goal-closeout`. The check and the open now use one
resolved path. The grant is asked about that path as written (`Capabilities::allows_resolved`), because
a second resolution inside the check could see a different path than the one the walk opens. The walk
starts at the root and opens each component with `O_NOFOLLOW` (Unix) or `FILE_OPEN_REPARSE_POINT` and a
name-surrogate test (Windows). Missing folders are created by the same walk with `mkdirat` or
`FILE_OPEN_IF`. An overwrite on Windows opens the existing file without emptying it, refuses a link, and
then sets its length to zero, so a link is never emptied.

## Diagnostics

No new diagnostic. A link met on the walk fails the call with the door's `IOError`, whose message says
a folder in the path was replaced by a link.

## Consequences

- One open per level of the path, which is what the operating system's own lookup costs, plus one
  attribute read per level on Windows. No memory is held past the call: every handle but the deepest is
  closed as soon as the next one is open.
- `nvs-runtime` carries two platform halves of about a hundred lines each, and the `Wdk_Foundation` and
  `Wdk_Storage_FileSystem` features of `windows-sys`, which add no crate.
- A path whose resolved form passes through a folder the process may search but not list still works on
  Linux, where a level is opened `O_PATH`. Elsewhere such a folder fails the walk.

## Alternatives rejected

- **`openat2` with `RESOLVE_BENEATH` on Linux.** It would be a third platform half for one kernel, and
  the walk already gives the same guarantee there.
- **Anchoring the walk at the granted root rather than at the filesystem root.** It would refuse a link
  inside a granted tree that points to another place in the same tree, which writes allow today.

## Revisiting

If a volume mount point inside a granted tree has to be written through on Windows: its reparse tag is
a name surrogate, so the walk refuses it unless canonicalisation spells the path through its volume.

## Verification

`crates/nvs-runtime/src/beneath.rs`'s tests create folders and files, refuse an exclusive create of a
name already there, and plant a directory link and a file link where the walk will meet them. On
Windows the directory link is a junction when the account may not create a symbolic link.
