# ADR 0258 — Two operator mixes whose grouping a reader misreads warn, and a fix-all applies only the parentheses that keep the meaning

- **Scope:** a compiler warning for a closed list of operator mixes, the help and fix two existing errors carry for
  the same misreading, and which suggestions an editor's fix-all may apply. Novis's precedence table is
  unchanged, and so is every program's behaviour.
- **Depends on:** [0040](0040.md), [0039](0039.md).
- **Validated by:** `crates/nvs-types/tests/misread_grouping.rs`,
  `tests/lsp/actions/a-misread-coalesce-offers-both-groupings.lspt`, and
  `a_fix_all_applies_the_grouping_that_keeps_the_meaning_and_never_the_alternative` in
  `crates/nvs-lsp/tests/actions.rs`.

> **In short:** `W1022` warns at a `??` whose right operand is a bare arithmetic or `.` expression
> (`$n ?? 0 + 10`) and at a `?:`, long or short, whose condition is a bare arithmetic, `.` or `??`
> expression (`"n=" . $ok ? "x" : "y"`), and nowhere else. It carries two edits: parentheses around
> what the code does now, which a fix-all may apply, and the grouping the author most likely meant,
> which is marked as an alternative and offered only as a quick fix. `E0105` and `E0706` gain a help
> line and a fix for the same kind of misreading.

## Context

Novis keeps PHP's precedence table (`rule:expressions/catch-expression-precedence` places `catch` in
it), and two of its rows are read wrong often enough to be bugs in practice. `??` binds looser than
every arithmetic operator and `.`, so `$n ?? 0 + 10` is `$n ?? (0 + 10)`: with `$n = 5` it gives `5`
where the author expected `15`. The ternary binds looser still, and a condition accepts any type and
tests its truthiness (`rule:expressions/truthy-positions`), so `"n=" . $ok ? "x" : "y"` tests the
non-empty string `"n=…"` and always gives `"x"`. Neither is a type error, so nothing reported them.

Two errors meet the same misreading from the other side. `"test" == $x && $foo = $bar ?? null`
assigns to `"test" == $x && $foo` in Novis, because PHP's grammar special-cases a variable on the
right of a binary operator followed by `=` and Novis's does not; the parse also produced a second,
type-mismatch error about a target nobody wrote. `$flags & 4 == 4` is `$flags & (4 == 4)`, refused
by `E0706` with a help line about converting the operand, which is not the mistake.

## Options considered

### 1. An error

Refusing the shapes is a language change: every warned shape is valid code with one meaning, and
refusing it breaks programs that meant exactly that meaning. Rejected.

### 2. An LSP-only hint

A hint in the editor alone is never seen by `nvs check` or by CI, and the server would carry a
second copy of a syntactic check the compiler can make once. Rejected.

### 3. A compiler warning over a closed list

Chosen. `&&` beside `||`, `-2 ** 2` and nested ternaries were considered and left out: the first is
common, deliberate and well understood, the second is pinned by the reference's own table, and the
third already groups to the right as documented.

## Decision

### 1. The warning and its list

`W1022` is raised by the parser (`crates/nvs-syntax/src/parser/grouping.rs`), which sees each written
operator once with its source text at hand. It covers a `??` whose right operand is a bare `+ - * / %
** .` expression, and a `?:` whose condition is a bare one of those or a `??`. A parenthesized operand
is an `ExprKind::Paren` node, so it never warns. The list is closed: a warning on valid code is worth
its noise only where the misreading is common.

### 2. Two edits, and which one a fix-all may apply

The first edit puts parentheses around what the code does now. It changes nothing, so it is an
ordinary safe suggestion and `source.fixAll.nvs` may apply it on save. The second is the grouping the
author most likely meant: the `??` or `?` taking the operand nearest it, through the operators the
warning covers. It changes behaviour, and it is one of two choices, so it is marked with the new
`Suggestion::alternative` field. The language server leaves an alternative out of a fix-all and keeps
it as a quick fix (`crates/nvs-lsp/src/actions.rs`), and `nvs check --json` carries the field beside
`safe`. A field was chosen over a per-code rule in the server, so the diagnostic says what it is and
no consumer keeps a list of codes.

`safe` was not reused for this. The legacy cast's fix is unsafe and still composes with
format-on-save (`rule:ide/narrowing-is-a-diff-never-a-save-time-fix`), so filtering a fix-all on
`safe` would have changed an existing behaviour.

### 3. The two errors

`E0105` on a binary target whose rightmost operand can be assigned to names the parentheses PHP adds
and offers them, and the parse is recovered as that grouping, so the checker reports no second error.
`E0706` over a bare comparison replaces its general help with one about precedence and offers
`($flags & 4) == 4`. Each fix is the only grouping of its line that compiles, so neither is an
alternative.

## Diagnostics

`W1022` (warning), new: "`??` is applied last, so its default is the whole `+` expression" and "the
`?` tests the whole `.` expression", each with a help line and two suggestions. `E0105` and `E0706`
keep their codes and messages and gain a help line and one suggestion in the shapes above.

## Consequences

Zero runtime cost: the grammar and the compiled program are unchanged. At compile time the parser
does one `match` per `??`, per `?:` and per invalid assignment target, and allocates only when it
warns. No memory is held past the diagnostic. The repository's own `.nvs` programs and test cases
already parenthesize these shapes, so none of them warns.

## Verification

`crates/nvs-types/tests/misread_grouping.rs` pins every warned shape, both edits and their
`alternative` flags, the shapes that stay silent, and the two errors. The `.lspt` case freezes the two
quick fixes, and the `nvs-lsp` test holds that a fix-all applies only the first.
