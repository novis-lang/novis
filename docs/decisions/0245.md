# ADR 0245 — A scheduled script, a log handler and a queued job's script start at the file that names them

- **Scope:** Which file `[[schedule]] script`, `[log] handler` and `Core\Queue::push`'s script name
  when they are relative, what a queue row stores, and what `nvs_runtime::script::resolve` does with a
  relative path. The `script.spawn` grant they are checked against is unchanged.
- **Depends on:** [0241](0241.md) (a relative path literal resolves from the file that wrote it),
  [0103](0103.md) (a relative configuration path resolves against its file).
- **Validated by:** the Stage 3 checks of goal `path-literals-follow-up`: `nvs-config`'s
  `a_schedule_script_resolves_against_the_folder_of_its_file`, `nvs-types`'
  `queue_push_script_literal_resolves_from_the_file_that_wrote_it`, `nvs-stdlib`'s
  `a_pushed_job_stores_an_absolute_script_path` and `nvs-cli`'s
  `a_schedule_script_beside_the_configuration_runs_from_any_working_directory`.

> **In short:** `[[schedule]] script` and `[log] handler` join the path-valued directives. A relative
> value resolves while the configuration is read, against the folder of the file that wrote it, and
> the tree holds the absolute path from then on, so the boot log and `nvs config dump` print it.
> `Core\Queue::push`'s script is a path parameter: a relative literal starts at the file that wrote
> the call, a relative path built at run time throws at the push, and the row stores the absolute
> path. `script::resolve` reads no working directory for any caller: a relative path reaching it is
> refused with the error `Core`'s doors give. A job already queued with a relative script is not
> rewritten; it fails when a worker takes it.

## Context

[0241](0241.md) made every path a program passes to a `Core` door absolute before the door is
reached, and named the four places that still hand `script::resolve` a path no source file wrote:
a queue worker, a `[[schedule]]` entry, a `[log] handler` and the name typed after `nvs run`. The
first three stayed relative. `script::resolve` checks the grant with the path as written, and the
resolver it calls opens that path, so a relative one names a file in the process's working
directory. Under `nvs serve` that is wherever the server was started, and under a service manager it
is a system folder.

## Investigation

The boot check for a schedule already joins `script` to the folder of its file before it asks the
`script.spawn` grant (`nvs_config::schedule`). The value it checks is then thrown away: the tree
keeps the relative text, and each fire passes that text to `script::resolve`. So the boot check and
the fire can name two different files. `[log] handler` has no boot check, and the escalation ladder
passes its text to `script::resolve` unchanged.

`Core\Queue::push` takes its script as `CoreTy::Text(Qual::Sink)`. The text goes into the row as
written, and a worker started in another folder resolves it against its own working directory.

Every other path-valued directive is rewritten in place while the configuration is read: `[db.<name>]
path` and an `[[app]]` key replace the written text with the joined one, in the typed configuration
and in the table `nvs config dump` prints.

## Decision

### 1. The two directives resolve while the configuration is read

`[[schedule]] script` and `[log] handler` are path-valued directives under
`rule:config/a-relative-path-resolves-against-the-file-it-is-written-in`. A relative value is joined
to the folder of the file that wrote it, in the same pass that joins `[db.<name>] path`, and the
joined path replaces the written one in the typed configuration and in the table. A directive in an
`[[include]]`d file starts at that file. The schedule's boot check reads the value it already holds.

### 2. `Core\Queue::push`'s script is a path parameter

The registry marks it `CoreTy::Path(Qual::Sink)`. It stays a sink, so a `tainted` script is still
refused. A relative literal is joined to the folder of the file that wrote the call while compiling,
under `rule:programs/relative-paths-resolve-from-their-file`. A relative path built at run time
throws at the push, with the `RuntimeError` every `Core` door gives, before anything is written. The
row stores the absolute path, so a worker started in any folder runs the same script.

### 3. `script::resolve` refuses a relative path

With every caller handing it an absolute path, `script::resolve` asks the same question the doors
ask, before the grant: a path that does not start at a root is refused with the door's message. That
makes a relative path reaching it a defect upstream that is reported, and never a file looked up in
the working directory.

### 4. A job already queued is not rewritten

A row written before this decision can hold a relative script. It is left as it is. When a worker
takes it, `script::resolve` refuses it, and the job fails with that error on the path any job whose
script does not resolve already takes. Rewriting
the rows would need a folder to join them to, and the only one available is the worker's working
directory, which is the guess this decision removes.

### 5. Tradeoffs

- **Performance:** nothing on the request path. Two directives are joined once per configuration
  read instead of resolved per fire; a push literal is joined while compiling.
- **Memory:** nothing.
- **Usability:** a scheduled script, a log handler and a queued job run the same file whichever
  folder the server or the worker was started in. A queued row written before this change with a
  relative script fails once, with an error that names it.
- **Simplicity:** one place fewer reads the working directory, and `script::resolve` has one rule for
  every caller instead of a carve-out for three of them.

## Consequences

The tests that wrote a scheduled script or a handler relative to the working directory write it
beside their configuration, or name it absolute. `nvs_runtime::capability::relative`'s doc no longer
names three callers that skip it.

## Alternatives rejected

- **Resolve at fire time against the origin.** The origin map would have to travel with the
  published tree to every fire, and the boot log would still print the relative text.
- **Rewrite stored relative rows against the worker's folder.** That is the working-directory guess
  this decision removes, made once and then stored.

## Verification

The four tests named under *Validated by*, and the `nvs-cli` pair starts the program in a working
directory that is not the configuration's folder.
