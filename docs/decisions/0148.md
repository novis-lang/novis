# ADR 0148 — A request reads its memory as three numbers on `Core\Budget`, and the runtime records the peak rather than waiting to be asked

- **Scope:** where a request's memory figures live, what they are called, and how the high-water mark
  reaches an operator who never wrote a line to ask for it. Not in scope: what the counter measures,
  which [0005](0005.md) settled and
  `crates/nvs-runtime/src/budget.rs` implements; whether a memory budget is per request or per
  isolate tree, which is `rule:security/isolate-budget-is-the-trees`' to
  settle and which this inherits rather than decides; and the `Core\Net` socket surface, which is the
  one ADR loop goal `net-os-signal` was already authorised to open.
- **Depends on:** [0005](0005.md), whose `[limits] memory` is the ceiling all
  three numbers are read against; [0051](0051.md), whose roster placed the
  figure on `Core\Os`; [0076](0076.md), whose default series this adds a tenth
  row to; [0127](0127.md), whose `Script\ExitReport` gains a fourth accessor;
  and [0067](0067.md), whose `slow_query` threshold is the shape the warning
  copies rather than reinvents.
- **Validated by:** `crates/nvs-stdlib/tests/migration-members-outstanding.txt`, whose keys move from
  `Core\Os::memoryUsage` to the three on `Core\Budget` and stay owed until loop goal `net-os-signal` strikes them;
  and `benches/abi-probe`, which is where the claim that the high-water update is free has to survive
  measurement rather than assertion.

> **In short:** `memory_get_peak_usage` was dropped on the reasoning that a peak is only meaningful
> against a request's budget and the limit report already carries one when a ceiling is breached.
> That reasoning holds for the breach and fails everywhere else, and it fails **because Novis
> releases memory well**. PHP's Zend allocator keeps its chunks, so a reading taken at the end of a
> script approximates the high-water mark by accident; Novis refcounts and releases deterministically,
> so held bytes fall back toward the baseline and a request that spent most of its life at 96% of the
> ceiling reports a comfortable number at exit. The better memory behaviour is what destroys the
> evidence. So the peak is restored — as a **recorded** number, not one a program has to think to ask
> for — and the surface it lands on is rebuilt around it: `Core\Budget::memoryHeld`, `memoryPeak` and
> `memoryLimit`, three numbers on one class, with the process's resident bytes staying on `Core\Os`
> where a host fact belongs. The peak reaches an operator three ways with no application code:
> `Script\ExitReport::memoryPeak`, a `nvs_request_memory_peak_bytes` histogram, and a
> `[limits] memory_high_water` threshold that writes one `Warn`.

## Context

### 1. What was decided before, and the half of it that was right

[0051](0051.md) placed a single member, `Core\Os::memoryUsage`, as the answer to
`memory_get_usage`, and `docs/spec/02-php-migration.md` dropped both of its relatives with reasons:

- `memory_get_peak_usage` — *"`Core\Os::memoryUsage` is the current figure; a peak is only meaningful
  against the request's budget, which `rule:errors/escalation-ladder`'s limit report already carries
  when one is breached"*.
- `memory_reset_peak_usage` — *"nothing tracks a resettable peak — a budget is per request and dies
  with it"*.

The second is still right and this record does not disturb it. The first is right about the breach
and wrong about everything short of it, and the gap between those two is where a production incident
lives.

### 2. Deterministic release is what makes a current-usage reading misleading

`rule:security/arena-is-an-ownership-root` releases memory when the last
reference dies, with no collector and nothing deferred. That is a better property than PHP's in every
way this repository ranks things, and it has one consequence nobody costed: **the current figure
stops being a proxy for the peak.**

In PHP, `memory_get_usage(true)` reports what the Zend memory manager has taken from the OS in 2 MB
chunks, and the manager holds those chunks after the arrays inside them die. A reading at the end of
a script is therefore sticky, and an operator who logs it is accidentally logging something close to
the high-water mark. In Novis the same reading falls back to the baseline as soon as the values die.
A request that decoded a 90 MB payload, transformed it, and returned a 2 KB summary reports the 2 KB.
Two requests, one at 30% of its ceiling throughout and one that touched 96% in the middle, are
indistinguishable at exit — and the second is the one that will take the process down under load.

So the member that survived the drop is, on its own, **actively misleading in Novis in a way it is
not in PHP**, which inverts the argument that dropped the other two.

### 3. The ceiling cannot be sized from data

`[limits] memory` is a number an operator has to pick, and `[limits.hard] memory` bounds how far an
application may widen it (`rule:config/three-changeability-classes`). Today
the only feedback on either number is the `FATAL` that arrives when the first one is wrong — a
breach, at production traffic, after the fact. There is no reading from which a ceiling could be
chosen before it is breached, because the one available reading is taken at the moment it says least.

### 4. The class is wrong, and it reproduces PHP's own ambiguity in a new place

PHP's memory functions confuse people on the axis of *which accounting* — `memory_get_usage()` and
`memory_get_usage(true)` return different numbers, and the ceiling is enforced against the one the
default call does not return.

`Core\Os::memoryUsage` avoids that and lands on a second axis: **whose memory**. `Core\Os` holds
`pid`, `hostname`, `cpuCount` and `loadAverage`, every one of them a fact about the host or the
process. A member sitting among them that returns *this request's* held bytes will be read as process
memory by anyone who has not read this record, and the word `usage` does not distinguish "currently
occupied" from "consumed cumulatively" — which is precisely the distinction PHP got wrong.

## Investigation

### 5. The counter exists, in every build, and is already load-bearing

`crates/nvs-runtime/src/budget.rs` keeps a signed thread-local balance and
`Ctx::memory_used` reads a request's share as the difference from the balance when its `Ctx` was
made. It is compiled into every build — not a `cfg(test)` facility — because
`rule:errors/on-limit`'s cap is unenforceable without it, and its module doc
gives the reason the counter sits in the allocator rather than at the members that allocate: *"a
guard written per call site is a guard the next call site forgets, which is the shape of PHP's own
history"*.

Nothing anywhere keeps a maximum of it. A grep for `peak` across `docs/rules/` and `docs/spec/` finds
the word only in prose about arena sizing and upload buffers.

### 6. A high-water mark is close to free on that path

`budget::add` already branches on `bytes > 0` and, inside that branch, updates two further
thread-local cells that exist in every build. A peak update is one more `Cell` read, a comparison
against a value the function has just computed, and a store that is almost never taken once a
request's working set has stabilised. It sits inside an existing branch on a path that already pays
for three thread-local accesses, and the branch it adds is monotone and therefore well predicted.

That is an argument for expecting the cost to be small, not a measurement, and § 14 is where it has
to survive one.

### 7. Three places already exist that could carry the number without being asked

- `rule:observability/script-on-exit`'s hook runs as the last user code at
  every non-fatal ending, and its `Script\ExitReport` is already the readonly carrier for facts about
  how a script ended.
- `rule:observability/default-series` already seeds a `nvs_memory_bytes`
  gauge the moment an exporter is configured, and already carries a histogram —
  `nvs_request_duration_seconds` — for the one other per-request quantity whose distribution matters.
- `rule:observability/a-slow-query-is-logged-past-a-threshold` is a worked
  precedent for an operator-set threshold that writes to `Core\Log`, down to the details that are
  easy to get wrong: unwritten is off, off is silent, and a written `0` is a threshold everything
  passes rather than a second spelling of off.

None of the three needs a new mechanism. Each needs one row.

### 8. Nothing is built yet, so the naming is free to fix

`rule:core-api/tier-roster` records `Core\Os` as *designed, not shipped*: it
has no module in `crates/nvs-stdlib`, and `Core\Os::memoryUsage` is an owed key in
`crates/nvs-stdlib/tests/migration-members-outstanding.txt` against loop goal `net-os-signal`, which is thirteen
goals out from the live one. Renaming and rehoming costs a handful of documentation rows and no code,
no migration and no deprecation. It will not be free later.

## Options considered

### 9. Where the peak comes from

1. **Sample it.** A timer or a safepoint reads `memory_used` periodically and keeps the maximum.
   Rejected: a sampled peak misses exactly the short spike that a deterministic-release runtime makes
   invisible, so it is least accurate where it is most needed.
2. **Keep it in the allocator, per thread, rebased per `Ctx`.** Exact by construction, since every
   allocation passes through one function, and § 6 prices it.
3. **Have the program record it.** A member the application calls at points it chooses. Rejected as
   the *only* mechanism for the reason § 2 gives — the request nobody instrumented is the one that
   matters — though it is kept as one of the three readings, because a program that wants to bound a
   section still needs to be able to ask.

Option 2, with option 3 alongside it as a member rather than as the mechanism.

### 10. Where the numbers live

1. **Keep everything on `Core\Os`, add `memoryPeak`.** Smallest edit, keeps the roster closed.
   Rejected: it leaves per-request figures among host facts, § 4, and keeps the word `usage`.
2. **Rename in place on `Core\Os`.** Fixes the vague word, not the class.
3. **A `Core\Budget` class holding the three request figures, with `Core\Os` keeping only host facts
   and gaining `residentBytes` for the process.** One more roster row; in exchange, neither name can
   be mistaken for the other, and the question "how much memory does this *process* use" gets a real
   answer instead of a member that looks like one.

Option 3.

## Decision

### 11. Three numbers, one class, and the ceiling among them

```php
Core\Budget::memoryHeld():  int   // bytes this request holds right now
Core\Budget::memoryPeak():  int   // the high-water mark of that, for this request
Core\Budget::memoryLimit(): int   // the ceiling both are measured against
```

`held` rather than `used`, because the runtime already says *held*: the breach a request gets is
rendered *"the request exceeded its memory limit — N bytes held against a ceiling of M"*, and a
member whose name disagrees with the error text about the same quantity is a second vocabulary to
learn. `used` is the word that carries PHP's ambiguity between "occupied now" and "consumed in
total"; `held` carries neither reading but the intended one.

`memoryLimit` is not padding and is not derivable at the call site. Without it a peak is a number
with no scale, and the ceiling is otherwise reachable only as `Core\Config::get('limits.memory')` —
a string with a suffix, which every call site would then parse. With it, the question this record
exists to answer is one expression:

```php
if (Core\Budget::memoryPeak() * 10 > Core\Budget::memoryLimit() * 9) { … }
```

An uncapped request — `[limits.hard] memory = false`, which
`rule:config/three-changeability-classes` allows and which gives literal PHP
behaviour — answers `0` from `memoryLimit`, matching `Ctx::over_memory_limit`'s existing reading of
zero as "no ceiling" rather than inventing a second spelling for it.

### 12. `Core\Os` keeps the host, and answers the process question honestly

`Core\Os` loses `memoryUsage` and gains `residentBytes(): int` — the process's resident set, which is
what `getrusage`'s `ru_maxrss` answers and what someone reaching for "how much memory are we using"
usually means. The split is the whole point: two questions that were being answered by one
ambiguously-named member become two members whose names cannot be confused, on the two classes whose
subjects they actually belong to.

`memory_get_usage`'s migration row therefore points at `Core\Budget::memoryHeld`, not at `Core\Os`.

### 13. `memory_reset_peak_usage` stays dropped, with a better reason

Its original reason — nothing tracks a resettable peak — stops being true here, so the row keeps its
outcome and changes its argument. **The peak is evidence, and a program that could reset it could
hide it.** § 14's three readings all exist so that an operator learns about a near-miss the
application did not report; a member that lets the application set the number back to the current
figure is a member that lets it set the number back to a comfortable one. PHP added the reset for
sectioned profiling, and sectioned profiling is what `Core\Debug`'s probes
([0018](0018.md)) are for.

### 14. The peak is reported three ways, none of which the application has to opt into

1. **`Script\ExitReport::memoryPeak(): int`** — a fourth accessor on the readonly report
   `rule:observability/script-on-exit`'s hook already receives, so a
   one-line `onExit` logs the peak at every non-fatal ending. It carries no cost for a script that
   registers no hook. It never fires on a `FATAL` or a cancellation
   (`rule:observability/a-fatal-and-a-cancellation-run-no-exit-hook`), which
   needs no compensating mechanism: a breach is precisely the case where
   `rule:errors/on-limit`'s report already names both numbers.
2. **`nvs_request_memory_peak_bytes`**, a histogram, seeded with the other default series the moment
   an exporter is configured. A gauge cannot answer "what fraction of requests came within 10% of the
   ceiling" and a histogram can, which is why `nvs_request_duration_seconds` is already one. It is
   read from the counter § 5 describes and adds no probe site, so
   `rule:observability/the-runtime-exports-what-it-already-measures` holds
   for it as written.
3. **`[limits] memory_high_water`**, a fraction of the effective ceiling; a request whose peak
   crosses it writes one `Warn` to `Core\Log` at the end of the request, naming the peak, the ceiling
   and the route. Unwritten is off and off is silent. It is a fraction rather than a size so that it
   keeps meaning the same thing under an `[app.limits]` block that narrows the ceiling
   (`rule:config/an-app-block-may-widen-bounded-by-the-global-ceiling`), and
   a value outside `0.0..=1.0` is refused at boot by the same typed-value path in `crates/nvs-config`
   that refuses a malformed size, so this introduces no diagnostic of its own.

One record per request and only past a threshold nobody wrote by default: this is the mechanism that
turns "nobody noticed" into "it said so", and it is the reason the other two are not enough on their
own.

### 15. What the peak is a peak *of* is inherited, not decided here

The counter is a thread-local balance read as a per-request difference, and `budget.rs`'s own header
says that reading is exact for the one request a thread runs at a time and defers to
`rule:security/isolate-shares-nothing` for when a core runs several. The
high-water mark inherits that boundary exactly and settles nothing new about it. The one mechanical
requirement it adds is stated in
`rule:observability/a-memory-peak-is-recorded-not-asked-for`: a nested
`Ctx` saves the enclosing high-water mark on creation and restores the larger of the two on drop, so
an isolate cannot erase the peak of the request that spawned it.

## Consequences

- **What this spends**, per `rule:programs/memory-priority`: one `isize` per
  thread and one per `Ctx` — the saved enclosing mark of § 15. Nothing per process, nothing that
  grows with requests served, and nothing that outlives a request. On the request path, one
  thread-local read and a predicted branch inside a branch that already exists.
- **One more roster row.** `Core\Budget` is a new Tier 0 entry, which
  `rule:core-api/tier-roster` requires be placed rather than left pending;
  three members is the whole class and it is not a home for anything else that happens to be a
  number.
- **`Core\Os` shrinks and sharpens.** It answers host and process questions only, which is what its
  name has always claimed.
- **A tenth default series.** `rule:observability/default-series`' opening
  count changes with it, and the series is seeded ahead of
  `rule:observability/past-max-series-a-new-series-is-refused`'s bound like
  the other nine.
- **The migration table gains a member row and loses a drop.** `memory_get_peak_usage` becomes
  `member` → `Core\Budget::memoryPeak`; `memory_get_usage` re-points from `Core\Os::memoryUsage` to
  `Core\Budget::memoryHeld`; `gc_status`'s row, which cites `Core\Os::memoryUsage` for a request's
  held bytes, re-points with it.
- **A program can be wrong about its own peak on purpose.** Nothing stops an application from never
  calling any of the three, which is why § 14 exists and why none of its three readings is a member.

## Alternatives rejected

- **A `$real_usage`-style boolean, in any spelling.** Two accountings behind one member is the exact
  shape `rule:core-api/no-mode-strings` refuses and the exact shape that
  makes PHP's version hard to reason about. Where two numbers are genuinely different questions they
  get two members on the two classes that own them, § 12.
- **`memoryHeadroom()` as a fourth member.** `memoryLimit() - memoryHeld()` at the call site, and a
  member per arithmetic is how a three-member class becomes a nine-member one.
- **Warning at a fixed fraction with no directive.** A threshold nobody can move is a threshold that
  is wrong for someone, and `slow_query` already established that the operator writes it.
- **Warning as a size rather than a fraction.** A size stops meaning the same thing the moment an
  `[app.limits]` block narrows the ceiling, and would have to be re-derived per application block.
- **Making the peak resettable so a program can bound a section.** § 13.
- **Leaving all of this to `Core\Debug`'s profiler.** A profiler answers "where did this go" for a
  developer who is already looking. The whole problem is the request nobody was looking at.

## Revisiting

Revisit § 15 when `rule:security/isolate-shares-nothing` sharpens the
per-request memory boundary for a core running several isolates: the peak follows whatever that
resolves to, and the save/restore of § 15 is the part that would change shape. Revisit § 14's third
reading if the `Warn` proves too noisy at production traffic — the fix is the threshold's default,
which is *unwritten*, and not the mechanism.

## Verification

- `crates/nvs-stdlib/tests/migration-members-outstanding.txt` carries `Core\Budget::memoryHeld`,
  `Core\Budget::memoryPeak`, `Core\Budget::memoryLimit` and `Core\Os::residentBytes` against loop
  goal `net-os-signal`, and no longer carries `Core\Os::memoryUsage`.
  `every_outstanding_key_names_an_owner` in `crates/nvs-stdlib/tests/spec_registry_coverage.rs` holds
  that against the chain, and the file only shrinks.
- `python tools/check-migration.py` audits the three rewritten rows against
  `docs/spec/01-core-library.md`'s roster, which is what keeps a `member` row from naming a spelling
  nothing backs.
- The high-water arithmetic is held by a conformance case that allocates a known-size buffer, drops
  it, and reads a peak that is above the drop and a held figure that is below it — the one assertion
  that would fail if the peak were re-derived from the current balance.
- A nested-isolate case asserts the parent's peak survives a child that allocated less than it did,
  which is § 15's save/restore and the failure mode a naive rebase produces.
- The cost claim of § 6 is measured in `benches/abi-probe` rather than asserted, and a guard there
  that moves when the high-water update lands is a finding about this decision, never a threshold to
  raise.
