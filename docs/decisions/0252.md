# ADR 0252 — `var` infers an array literal whose elements all have one type, and refuses every other with the type to write

- **Scope:** A bare array literal under `var` — a local's initializer and a `var` value binding's
  `foreach` subject — and the one function in `nvs-types` that types it. Every other position with
  no target keeps `array<mixed>`, and a written `array<T>` is accepted everywhere it was.
- **Depends on:** [0037](0037.md) (`var` takes a local's type from its initializer),
  [0251](0251.md) (a `foreach` binding may write `var`),
  [0114](0114.md) (the synthesis, designed for the editor),
  [0007](0007.md) (an array literal is checked against its target).
- **Validated by:** the Stage 2 checks of goal `var-array-literal`: the named tests in
  `crates/nvs-types/tests/locals.rs` and the two `.nvst` cases named under *Verification*.

> **In short:** `var $ids = [1, 2, 3];` declares an `array<int>`. An array literal under `var` is
> `array<T>` when every element has the same type `T`, where an element's type is exactly what
> `var` gives that element alone. Every other literal is still `E0414`: elements of two types, an
> empty literal at any depth, and an element that could not be typed. The help line names the
> declaration to write — the union of the element types, `?T` when the second is `null`, and
> `array<T>` with `T` left open for an empty literal. No common supertype is computed, and a
> qualifier is part of the type, so `var` can neither drop one nor invent one.

## Context

### 1. The most common array declaration repeated its elements' type

`array<int> $ids = [1, 2, 3];` was the only way to write it, because 0037 refused every bare
literal under `var`: a literal is checked against a target, and `var` gives it none. The refusal
was right for a literal whose elements disagree, since the type there is a choice somebody has to
make. For a literal whose elements all say `int`, the written `array<int>` repeated what the
elements already state.

### 2. The function that could answer was designed and not built

0114 designed a synthesis — the type an array literal would have if typed bottom-up — for one
editor action, and kept every compile path away from it, so that a union answer could never be
attached to a binding unseen. That reason holds for a union. It does not hold for a literal whose
elements share one type, where the answer is the type the author would write anyway.

## Decision

### 3. One type, or refused

An array literal under `var` is `array<T>` when every element has the same interned type `T`, and
otherwise it is refused. An element's type is what `var $e = <element>;` gives it alone, so `1` is
`int`, a string literal is `string`, an enum case is its enum, a call is its return type and a
`mixed` value is `mixed`. No widening rule is added: `[1, 2.5]` is two types, as `[$user, $admin]`
is when `Admin` extends `User`. A qualifier is part of the type, so `[$tainted, "plain"]` is two
types.

- A **nested literal** is inferred by the same rule first, so `[[1], [2, 3]]` is
  `array<array<int>>` and `[[1], ["a"]]` is two types.
- A **spread** contributes its source's element type. A source that is not an array is the
  spread's own `E0484`, and the literal is then not inferred.
- **Keys** are checked as they are everywhere and take no part in `T`.
- An **empty literal** is refused wherever it stands under `var`, nested included.
  `array<never>` is never inferred for a binding.

On success the binding is declared at `array<T>`, and each element is recorded at `T` exactly as
a written `array<T>` target records it, so the two spellings lower the same.

### 4. The refusal names what to write

The code stays `E0414`, since every refused case is the one mistake of a literal `var` cannot
type. The message says which case it is, and the help line is the written declaration: the
canonical union for elements of two or more types, which reads `?int` for an `int` beside a
`null`, and `array<T>` for an empty literal. An element that reported its own error adds no
second diagnostic. Under a `foreach` value binding the help names a typed local to iterate, as
0251 did.

### 5. The synthesis has two callers and no third

The function lives beside `check_array_literal` in `nvs-types`, as 0114 placed it. `var`'s arm
and the `foreach` subject under a `var` value binding call it, and no other position does: an
`echo` argument or a bare expression statement still types a literal as `array<mixed>`. A guard
test counts the callers. The editor action 0114 designed still answers with a union where this
refuses, because there the answer is text a person reads and approves.

## Consequences

- Performance: nothing. The type is fixed at compile time, and the literal lowers as the written
  one does.
- Memory: nothing, per request or per task.
- Usability: the most common array declaration no longer repeats its element type. A literal whose
  elements disagree is still a type somebody writes down, and the help line writes most of it.
- Simplicity: one more place a type is not visible in the source. The inlay hint shows it in an
  editor, and nothing shows it in a diff. A later write of a new element type is an error that has
  to be read back to the `var` line.

## Alternatives rejected

- **A common supertype.** It would give `[$user, $admin]` the type `array<User>`, a choice the
  author did not make, and a `[1, "a"]` the union nobody wrote. The rule is the user's: one type,
  or the author writes it.
- **Inferring the union.** A union attached to a binding unseen is 0114's objection, and it stands.
- **A new code per refused case.** One mistake gets one code; the message names the case.
- **`array<never>` for `var $x = [];`.** The binding could then hold nothing, and the first append
  would be the error.
