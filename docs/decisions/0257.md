# ADR 0257 — `nvs check` on a file a program autoloads or requires checks it through that program's `autoload` map

- **Scope:** what `nvs check <file>` resolves a file's names through when the file declares no `autoload` of
  its own, which tree it searches for the program that lends one, and when it searches at all. Which
  program lends, and what a borrowed declaration may report, are [0198](0198.md)'s and unchanged.
- **Depends on:** [0198](0198.md), [0061](0061.md).
- **Validated by:** `crates/nvs-cli/tests/check_borrow.rs`, the language server's `crates/nvs-lsp/tests/autoload.rs`,
  and the run under *Verification*.

> **In short:** `nvs check app/User.nvs` on a class file a program autoloads used to report every
> autoloaded name in it as undeclared, while `nvs check` on the program was clean. Now, when a checked
> file declares no map of its own and names a type nothing declares, the command searches the `.nvs`
> files under the project root in path order for the first program that lends to the file, by
> 0198's test, and checks the file again with that program's declarations behind its own. A file that
> declares a map, or names nothing undeclared, is checked once, as before.

## Context

0198 made the language server lend a program's map to the files it autoloads or requires, and said
in § 5 that `nvs check` does not borrow, because it is handed the file a program starts from. That
stopped being true of how the command is used. A coding agent is told to run `nvs check` on the file
it just edited, and `nvs agent init` installs that instruction ([0256](0256.md)). The file an agent edits
is most often a class file under an `autoload` root, so the command it was told to trust reported
`E0303` and `E0306` on a program that builds clean. A false error there sends the agent to fix code that
is correct.

## Decision

### 1. One test of who lends, in `nvs-hir`

What a lender is and which files it lends to moves from `nvs-lsp`'s `document.rs` to
`nvs_hir::lenders`: `Lender::walk` builds one, `Lender::lends_to` is 0198's three-way test, and
`sources` is the tree walk with its skip list. The server keeps what is its own — the session's lender
list, the resurvey on edit and the open buffers overlaid on the walk — and calls into that module, so
the editor and the command cannot disagree about which program lends.

### 2. The command searches only when the first walk needs a map

`nvs check` walks the file as today. It searches for a lender only when all three hold:

- the walk found no `autoload` declaration of the file's own program, so the file is not a lender, and
  a lender never borrows;
- the walk reported `E0303` or `E0306`, the two diagnostics a borrowed map can change;
- a lender under the survey root lends to the file.

Then the file is walked again, from a fresh source map, with the lender's declarations passed to
`resolve_program_linted` as borrowed, and the second walk's diagnostics are the ones reported. A file
that no lender reaches keeps the first walk's diagnostics. A program's entry point pays nothing new.

### 3. The survey root is the project root

The root is the directory of the first `--config` path that is a file, and otherwise the working
directory, which is where the `nvs.toml` that applies is found. `target`, `vendor` and dot-directories
are skipped, as under the server's `nvs.check.scope = workspace`. The files are walked in path order
and the search stops at the first lender that lends, which is the server's "first in entry-path order"
without walking the lenders after it.

### 4. Output does not change

The text and `--json` renderings keep their formats. A borrowed declaration reports nothing, so a
diagnostic in the output is always about a file the check read for the checked file.

## Consequences

- **Performance:** nothing for a file that declares a map or names nothing undeclared. For a class file
  that does, one read of each `.nvs` file under the root, one name-resolution walk per file that holds
  `autoload` or `require` up to the lender, and a second walk of the class file. Nothing is on a request
  path of the runtime.
- **Memory:** the first lender's resolved map, for the length of one command. Nothing per request.
- **Usability:** `nvs check` on a class file agrees with `nvs check` on its program and with the editor.
  Run from a directory that is not the project, the command finds no lender and reports what it
  reported before.
- **Simplicity:** one implementation of the lending test for two callers. The command gains one
  parameter on its front end and a second walk on one path.

## Alternatives rejected

- **Surveying before the first walk.** It costs a tree read on every check of every file, including
  the programs that need nothing.
- **Searching upwards from the checked file for a lender.** A shared framework tree is reached by a
  program outside its own directories, and the server, which surveys the workspace, would then
  disagree with the command.

## Verification

`crates/nvs-cli/tests/check_borrow.rs` holds the five cases: a class file checks clean in both
renderings, a real mistake in it is still reported, a file no program lends to is unchanged, the first
program by entry path lends, and a file with its own `autoload` never borrows.

On a generated project of 2,000 class files and 84,000 lines, with one entry that autoloads all of
them, the release binary checked the entry in 0.34–0.40 s, as before. A class file that names an
autoloaded class took 0.45–0.46 s, nearly all of it the lender's walk; it reported `E0303` before. A
class file that names nothing undeclared took 0.01 s and searched nothing.
