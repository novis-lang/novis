# ADR 0266 — `Core\Html::later` runs a slow part of a page as a child of the request, and a slotted route sends the page before that part is ready

- **Scope:** the method `Core\Html::later`, its placeholder and its per-request token, how a normal
  route assembles the page, the route field `slotted` and `Core\Response::slotted()`, the wire format
  of a slotted response, what a failed slot and a limit breach show, and when after-response work runs
  once a response can outlive its frame. The polyfill's own text and its CSP hashes are named here and
  may get a record of their own; flushing before the main script ends, a slot in `<head>` and
  declarative shadow DOM are not decided here.
- **Depends on:** [0072](0072.md), [0006](0006.md), [0024](0024.md), [0169](0169.md),
  [0265](0265.md), [0004](0004.md).
- **Validated by:** the `later` cases under `tests/conformance/core/` and the slotted-delivery tests in
  `crates/nvs-server/src/serve.rs`, as each stage of goal `html-later` lands them.

> **In short:** `Core\Html::later(fn, {placeholder?, error?, deadline?}): Markup` starts `fn` at once
> as a task whose parent is the request, not the call, and returns a placeholder carrying a 96-bit
> per-request token. On a normal route the page is sent once every `later` task has ended, with each
> placeholder replaced by its task's output in one pass. On a route declared `slotted: true`, or one
> that called `Core\Response::slotted()`, the page goes out as soon as the main script ends and each
> output follows in the same response as a `<template for>` fill, with a small inline polyfill.
> `later` has no limit of its own; a failed slot shows `error` and the page keeps its status; a
> `later` closure cannot change the response head. After-response work runs once the response is
> complete: the frame has returned and every `later` task has ended.

## Context

Every response is buffered whole, so a page's first byte waits for its slowest query.
`Core\Response::stream` is the only early byte, and it gives up `echo` and its escaping
(`rule:security/response-body-is-one-typed-member`). Out-of-order streaming exists elsewhere only
inside frameworks that run JavaScript on both ends. The user asked for it as one `Core` method and
one route field, with no change to how a page is written.

## Options considered

1. **Markup: declarative shadow DOM**, which needs no script in any current browser. Rejected by the
   user: the content would sit in a shadow root that the page's CSS does not reach and
   `document.getElementById` does not find.
2. **Markup: `<template for>` with `<?start>`/`<?end>` placeholders**, the HTML standard's
   declarative partial update, plus an inline polyfill until browsers ship it — chosen by the user.
3. **Delivery chosen by the call site** (a `later` that streams and one that does not). Rejected: a
   component would then depend on the route that includes it. The route decides, and the component
   is written once.
4. **A carrier slot on `Markup` for the placeholder.** Rejected: the token in the bytes is enough to
   find it, and `+`, `Core\Html::join` and partials carry it with no change.

## Decision

### 1. The method

`Core\Html::later(callable(): void|Core\Html\Markup $fn, {placeholder?: Core\Html\Markup, error?: Core\Html\Markup, deadline?: Core\Time\Duration}): Core\Html\Markup`.
The task's output is what `fn` echoes, followed by the `Markup` it returns, if any; its `echo` is the
request's escaping sink (`rule:core-classes/html-auto-escape`). `placeholder` defaults to empty,
`error` to a plain fragment the reference names, and `deadline` has no default.

### 2. The task's parent is the request

The task starts at the call and runs concurrently with the main script and every other `later` task.
Its parent is the request, so `later` returns with its child running; the guarantee of
`rule:concurrency/nothing-is-still-running-when-a-call-returns` holds one level up: the response does
not end while one runs. It is charged to the request tree like any task
(`rule:security/isolate-budget-is-the-trees`). A `later` inside a `later` closure is the request's
child too, and its placeholder is part of its parent's output.

### 3. The placeholder and the token

`later` returns `<?start name="nvs-<token>-<n>">` + `placeholder` + `<?end>` as `Markup`. `<token>` is
96 random bits drawn once per request and written as 16 base64url characters; `<n>` counts the
request's `later` calls from 1. A visitor's string is escaped before it reaches the sink and an author
cannot know the token, so nothing but `later` can name a slot. A placeholder that is in no body when
the main script ends is cancelled then, with one `Warn` naming the call's file and line. A placeholder
written twice throws `LogicError` at the second write.

### 4. A normal route

When the main script and every `later` task have ended, each placeholder, `<?start` to `<?end>`
inclusive, is replaced by its task's output in one pass over the body, nested placeholders included.

### 5. A slotted route

`#[Core\Route(…, slotted: true)]` turns it on before the first line runs, and
`Core\Response::slotted()` turns it on at run time; after the main script ends, or inside a `later`
closure, that call throws `LogicError`. A slotted request that never calls `later` is sent whole. The
head and the shell, placeholders in place, go out as the first chunk when the main script ends, and
nothing before. Each fill is `<template for="nvs-<token>-<n>">` + output + `</template>` +
`<script>_nvs()</script>`, written in finishing order. The polyfill `<script>` is written once, just
before the first fill. A shell ending in `</body></html>` has those bytes held back until after the
last fill. The response is chunked, has no `Content-Length`, carries `X-Accel-Buffering: no`, and
holds its admission place until its last fill. When the client goes, `rule:http-server/a-request-outlives-a-client-that-goes-away`
applies to the `later` tasks as to the main script.

### 6. The polyfill

Novis's own, minified, with its `sha256` beside it. It defines `_nvs()`, which fills a placeholder only
when its marker and its `<template for>` are both still in the page and then removes both, so it never
fills a slot a native browser already filled. No MutationObserver: every fill is followed by the same
trigger. When the response's CSP limits scripts, the two hashes are added to it. A test holds the
polyfill to 1 KB and a slot's wire overhead to 120 bytes, and a real Chromium, with and without native
`<template for>`, runs it.

### 7. Failure and limits

A task that throws or passes its own `deadline` fills its slot with `error`; the throw is logged with
the request, the status stays what the main script set, and the other slots go on, on both kinds of
route. `later` has no limit of its own: a breach of the request's `wall_time`, `cpu_time` or `memory`
fails the request as it does today. On a slotted route the head is already out, so every unfilled slot
gets `error`, the held-back end is written and the response ends.

### 8. The head is closed to a `later` closure

Inside one, `Core\Response::setStatus`, `setHeader`, `redirect`, every body method, a cookie write and
`Core\Session::regenerate` throw `LogicError` on both kinds of route, and a call the checker sees in
the closure's own body is a compile error. Reading the request and the session is allowed.

### 9. Outside an HTML response

In a request whose body is not HTML, or outside an HTTP request, `later` runs `fn` in place and returns
its output, so a component still works there.

### 10. After-response work

The trigger of `rule:concurrency/after-response-outlives-the-connection` becomes the response being
complete: the request frame has returned and every `later` task has ended. With no `later` call that
is the frame returning, as before.

### 11. What is spent

- **Performance:** nothing for a request that never calls `later`. One pass over the body to assemble.
  On a slotted route the first byte goes out when the main script ends and the last when the slowest
  slot ends.
- **Memory:** each `later` task's output is held until it is sent, and a slotted shell from the end of
  the main script until it is written — per request, O(in-flight), under the request's `memory` cap.
- **Usability:** an early first byte with no change to how a page is written.
- **Simplicity:** one method with three options, one route field, one call. The developer never writes
  streaming markup, and a browser without JavaScript shows the placeholders.

## Consequences

The markup, the route field with the runtime call, the error fragment keeping the status, concurrency
on a normal route and `later` having no limit of its own are the user's calls. The option names, the
`void|Markup` return, cancelling an unwritten placeholder, `LogicError` for a second write, the
per-call `deadline` with no default, the polyfill being Novis's own with its CSP hashes, holding back
`</body></html>`, sending nothing before the main script ends, and after-response work waiting for the
last fill are calls made with this decision and open to the user's review.

## Alternatives rejected

- **Flushing the shell before the main script ends.** The status and headers would be fixed before
  the script that sets them has finished; it is a possible later decision.
- **A limit of `later`'s own** (a slot count, a per-slot memory share). A page with `later` is bounded
  exactly as the same page without it, and a second set of limits is something every developer must
  learn.
- **A slot in `<head>`.** The head is sent first, so a `<title>` cannot be filled later.
