# ADR 0223 — the HTML parse holds at most 512 open elements and closes the current one to make room, and every check it makes grows no faster than the document

- **Scope:** how `Core\Html::parse` and `Core\Html::sanitize` bound the time one document can cost:
  a cap on the stack of open elements, and three checks rewritten without changing their answer. It
  carries the `html5ever` changes as a patched copy under `vendor/html5ever`. It does not change the
  memory limit, which already bounds a tree's size, or `DEPTH_CEILING`, which bounds the walks over a
  finished tree.
- **Depends on:** [0122](0122.md) for the parse and its never-fails contract, [0121](0121.md) for the
  PDF renderer that shares it.
- **Validated by:** `crates/nvs-stdlib/src/html.rs`'s
  `every_walk_over_the_stack_of_open_elements_is_bounded_by_the_cap`,
  `a_start_tag_at_the_cap_closes_the_current_element_and_becomes_its_sibling` and
  `the_cap_closes_tables_templates_selects_and_foreign_content_without_failing`, and the attacks under
  `tests/hostile/core/Html/`.

> **In short:** the stack of open elements holds at most 512 elements. A start tag that arrives with
> 512 open first closes the current element with an end tag for its own name, and the new element
> becomes its sibling — WebKit's rule, at the depth Chromium, Firefox and WebKit all use. The cap is a
> constant. Duplicate attribute names are found with a hash set once a tag has ten attributes, and an
> active formatting element carries a fingerprint of its attributes, so neither check grows with the
> square of a document. `html5ever` offers none of this, so the workspace builds a patched copy of the
> 0.39.0 release.

## Context

### 1. A small body held a core until its CPU limit ended it

A request can hand `Core\Html::parse` or `Core\Html::sanitize` any text. Two gap records named the
shapes that cost time in the square of their size: `<div>` nested a hundred thousand deep, and one tag
with a hundred thousand attributes. Each attack under `tests/hostile/core/Html/` that showed them ran
to the ten-second timeout. The node-by-node memory limit stops a tree that is too large, and does
nothing about time. A parse that holds a core for seconds is a request-isolation problem under
AGENTS.md's first priority, not a speed problem.

## Investigation

### 2. Where the time goes

Timed on a release build, `nvs run`, at 10k, 25k, 50k and 100k:

| Shape | 10k | 25k | 50k | 100k |
|---|---|---|---|---|
| `<div>` × n | 0.29 s | 1.43 s | 5.37 s | 24.9 s |
| one tag with n attributes | 0.14 s | 0.49 s | 2.26 s | 11.0 s |
| `<span>` × n, then `</x>` × n | 0.62 s | 3.58 s | 13.8 s | 65 s |
| `<b a=i>` × n, each value different | 3.39 s | 21.4 s | 111 s | — |
| `<html><html` and n attributes | 0.37 s | 1.21 s | 5.61 s | 23.2 s |
| `<table>`, then `x<i></i>` × n | 0.10 s | 0.36 s | 1.33 s | 6.45 s |

The last four were found while measuring the first two; no gap named them. A probe driving
`html5ever` 0.39.0 with a sink that does nothing separated its cost from the `Sink` in
`crates/nvs-stdlib/src/html.rs`:

- **The stack of open elements.** `<div>` × 100,000 took 15.5 s in the probe and read 10¹⁰ element
  names. `TreeBuilder::in_scope` walks the stack from the top until it meets a scope boundary, and every
  `<div>` asks whether a `p` is in button scope. The "any other end tag" rule, the `template` search
  and the adoption agency's searches walk the same stack. A document of nested elements with no
  boundary makes each walk as long as the document.
- **Duplicate attributes.** The tokenizer alone took 10.2 s for 100,000 attributes. `finish_attribute`
  compares each new name with every earlier name on the tag.
- **Noah's Ark.** `create_formatting_element_for` compares a new formatting element with every entry
  of the active formatting elements back to the last marker, and each comparison,
  `Tag::equiv_modulo_attr_order`, copies and sorts both attribute lists.
- **The `Sink`.** `add_attrs_if_missing` scanned the element's attributes for each new one, and
  `locate` searched a parent's children from the front for every node foster parenting inserts
  before an open table.

### 3. Upstream and the browsers

No `html5ever` release fixes either path: 0.40.1 has the same `in_scope` and the same scan. The
project's issues about linear searches of the stacks and O(n) time on hostile input are open, and a
pull request that indexed element names to stack positions was closed unmerged.

The browsers, read from their source:

- **Chromium** caps tree depth at 512 (`kMaximumHTMLParserDOMTreeDepth`): past it, a node is attached
  to the current node's parent. Its stack still grows, and the `p` check reads a cached bit. It finds
  duplicate attributes with a hash set from 10 attributes (`kMinimumNumAttributesToDedupWithHash`),
  and caps no attribute count.
- **Firefox** appends anything past stack position 511 to the element at that position, without
  popping.
- **WebKit** caps depth at 512 by default, and at the cap it pops the current element and attaches
  the new one to its parent, so its stack never grows past the cap.
- **WHATWG** places no limit, and expects that "practical concerns will likely force user agents to
  impose nesting depth constraints".

`Sink`'s own `fill` already flattens a finished tree past `DEPTH_CEILING`, which is the Chromium and
Firefox shape. That shape does not bound the stack, so it does not bound the time.

## Options considered

### 4. Close the current element at the cap (WebKit)

Every walk over the stack is bounded by the cap, so every token's cost is. Every element and
attribute of the document arrives. Nesting past the cap becomes siblings, and an end tag for an
element the cap closed is ignored or closes an open ancestor of the same name, as in WebKit.

### 5. Keep the stack and index it

Chromium's cached bit covers only the `p` check; the end-tag walk and the others would each need an
index kept correct under every push, pop, insertion and removal the adoption agency makes. That is
the largest change to `html5ever` of the four, and upstream closed the one attempt at it.

### 6. Drop start tags past the cap

The smallest change: text past the cap arrives, but the elements and their attributes do not, links
included.

### 7. Stop at the cap

Throwing breaks `rule:core-classes/html-parsing`'s never-fails half, and truncating drops content.

## Decision

### 8. The cap

`html5ever`'s `TreeBuilderOpts` gains `max_open_elements`, and `Core\Html`'s parse sets it to
`OPEN_ELEMENTS_CAP`, 512. Before a start tag is processed, while the stack holds that many elements,
the tree builder processes an end tag for the current element's name. The builder only ever sees a
token stream a document could have held, so every invariant its rules keep between tokens still
holds: a `table`, `template` or `select` closed this way resets the insertion mode as its own end
tag always does. If a rule ignores that end tag and the stack does not shrink, the start tag is
dropped.

The cap is a constant. It is what bounds the work each token costs, so a setting could only buy the
square-time path back, and a configuration key, its help and its proofs would be spent on a number no
document a person writes comes near.

### 9. The three checks

- The tokenizer scans for a duplicate name while a tag has fewer than ten attributes and uses a hash
  set of them from ten on. The first value of a repeated name is kept, as before.
- Each active formatting entry carries a fingerprint: an order-independent sum of hashes of its name
  and attributes, keyed at random for each parse so a document cannot be written to collide. The full
  comparison runs only when the fingerprints match.
- `Sink` keeps a set of names for each element `add_attrs_if_missing` has added to, and `locate`
  searches from the last child.

None of them changes what the parse produces.

### 10. The patched crate

`vendor/html5ever` is the published 0.39.0 with these changes, each site marked `// Novis:`, and the
workspace's `[patch.crates-io]` builds it in place of the registry's. `vendor/` is excluded from the
workspace, so this repository's lints and formatter do not run over it. No change is offered upstream.

## Consequences

- A document deeper than 512 elements parses to a different tree than before: the elements past the
  cap are siblings rather than nested. Before, the tree was flattened only past 1024.
- Every shape in § 2 now takes time in proportion to its length: at 100,000, from 0.12 s to 0.41 s on
  a release build.
- The PDF renderer parses through the same code and holds the same cap, so it lays out what WebKit
  would.
- The member perf ledger's clock for `Core\Html::parse` and `Core\Html::sanitize` moved inside its
  own spread, and each parse holds a few more bytes: an empty map in `Sink` and a random key.
- Upgrading `html5ever` now means carrying the patch forward onto the new release.

## Alternatives rejected

- **Upgrading `html5ever`:** no release changes either path.
- **Tracking the stack from the `Sink`:** several of the builder's pops never reach the sink, and the
  one public view of the stack, `trace_handles`, costs a walk per call.
- **Capping a tag's attributes:** no browser does, and the hash set makes a cap unnecessary.

## Verification

- `every_walk_over_the_stack_of_open_elements_is_bounded_by_the_cap` counts the element names the
  builder reads per tag over six deep shapes and holds it under four times the cap. With the cap
  switched off, nested `div`s read 20,005 names per tag against that bound of 2,048.
- The attacks under `tests/hostile/core/Html/parse/` and `sanitize/` finish in under two seconds each
  on the proof profile, and none is marked as a gap.
