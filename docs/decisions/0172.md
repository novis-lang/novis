# ADR 0172 — An editor reads the CLI's own documents: `nvs check --json` at version 1, the test report at version 2 with every record located, and a Test Explorer that is those two projected

- **Scope:** the two machine-readable surfaces the editor layer consumes — `nvs check --json` and
  `nvs test`'s JSON report, including the discovery document `--list` writes — and the shape of the
  VS Code Test Explorer that reads the second. It settles what each document carries and what its
  version number means. It says nothing about coverage, which has no data source to wire, and
  nothing about when the client lands, which is
  `rule:ide/every-feature-is-staged-behind-its-dependency`'s question.
- **Depends on:** [0079](0079.md), [0108](0108.md), [0040](0040.md), [0099](0099.md).
- **Validated by:** `tests/conformance/lang/a-test-run-reports-a-versioned-json-document.nvst`,
  `tests/conformance/lang/a-test-run-lists-what-it-declares-without-running-it.nvst`, and the named
  tests in `crates/nvs-cli/src/runner.rs` and `crates/nvs-cli/tests/check.rs`.

> **In short:** every machine surface the editor layer needs is a document the CLI already writes or
> grows a key on, and each one is versioned exactly once. `nvs check --json` is `schemaVersion: 1`.
> The test report goes to `schemaVersion: 2`, where every record carries the file, line and column
> its `#[Test]` method is declared at, and `nvs test --list` writes a document of the same version
> whose records sit under `listed` and carry no verdict, because nothing ran. The Test Explorer is a
> projection of those two: `--list` fills the tree, `--format=json --filter` runs a selection, and
> the client computes nothing the documents do not already say.

## Context

The editor layer needs three answers the language server cannot give: which tests a workspace
declares, where each one is written, and how a run of them came out. A language server answers
questions about a *document at a cursor*; a test tree is a question about a *program*, and the thing
that already compiles a program and holds its `#[Test]` table is the CLI.

Two of the three had no surface at all. `rule:testing/report-formats` version 1 named a test by
`class` and `method`, which is enough to print a line and not enough to open a file: nothing below
the compiler can recover which file declared a class. And nothing discovered tests without running
them — the only way to learn what a program declares was to run it, which is exactly what an editor
populating a tree must not do.

The third, `nvs check --json`, landed under [0108](0108.md) with its schema described as frozen but
its version number never written down as a decision.

## Decision

### 1. Each document is versioned once, at its root

`nvs check --json` is `schemaVersion: 1`, and `nvs test --format=json` is now `schemaVersion: 2`.
The number is at the root of the document and covers the whole of it. A consumer reads that key
first and knows what every other key means, which is the entire contract a version buys and the one
[0099](0099.md) already set for `nvs ast --json`.

### 2. A `#[Test]` row carries where it was declared, and the report prints it

`nvs_types::testing::TestCase` gains the span of the method's own name — the span every refusal
about that test already points at. It was held in a side table the checker threw away, and it is the
one fact about a test that nothing downstream can recompute: a class label and a method name say
nothing about which file the two were written in.

Every record of the version 2 report therefore carries `file`, `line` and `column`, one-based,
counting `char`s in a column exactly as the `--> path:line:col` header does and as
`nvs check --json` does. One function writes those three keys for both documents this report has, so
a location cannot come to be spelled two ways. They are present on every record or `null` on every
record; a record silently missing its location is the one shape a consumer would have to guess about.

The JUnit XML and the plaintext report are **byte-identical** to what they were. JUnit has no version
to raise and every element it has is about how a test came out, so a location added there would be a
schema change nobody could announce.

### 3. Discovery is `nvs test --list`, and its document is a `listed` array

`--list` answers from the checked program's test table without compiling, installing or calling
anything: a program whose tests fail, hang or `exit` lists exactly as a passing one does. Under the
human format it prints one `Class::method  file:line` per test; under `--format json` it writes a
`schemaVersion: 2` document whose `listed` array holds one `{class, method, file, line, column}` per
*call* — a `#[TestWith]` row is listed under the label the report would give it, so a listing and a
run can be matched record for record.

**The array is named `listed`, and there is no `summary`.** The two alternatives were a `summary` of
zeros — which reads as a run in which nothing passed, a statement about an execution that did not
happen — and a `tests` array whose records merely omit `verdict`, which would make every consumer of
the run document branch on a key's *absence* to find out which document it was handed. The key that
carries the data is what says which document this is.

`--list` excludes `--update`, which rewrites what a run produced, `--format junit`, and a `.nvst`
tree, which is discovered by walking a directory. Each is refused rather than ignored, which is what
`nvs test`'s other flag combinations already do.

### 4. The Test Explorer is those two documents, projected

The client discovers with `--list`, runs a selection with `--format=json --filter`, and maps records
to `TestItem`s by `class` and `method`. It computes nothing: the tree's labels, the file each item
opens at and the verdict each run produces are all read out of a document. Coverage is not wired,
because `nvs test --coverage` does not exist yet and a `FileCoverage` fed from nothing is a lie; when
the exporters land, the explorer feeds VS Code's own coverage model and still draws no UI of its own
(`rule:ide/the-extension-builds-no-ui-the-editor-already-has`).

This is the same shape the AST panel already has
(`rule:ide/the-ast-panel-shells-out-to-the-cli`): a view that shells out to the binary and renders
what it says, rather than a second implementation of the compiler's tables inside a client.

## Consequences

The compiler holds one `Span` per test row for the life of a compile — twelve bytes on a table that
only exists for a program that declares tests — and a run holds one resolved path, line and column
per reported case. That is the memory this spends, and it buys the two features that cannot exist
without it.

A CI job reading the report sees three new keys and a version it can assert. A job that pinned
`schemaVersion: 1` breaks loudly, which is what the number is for; one that reads keys by name does
not.

The client is smaller than it would otherwise be. Every question it could have answered by scanning
a workspace for classes, or by parsing the human report back into records, is answered by a document
instead — and `rule:ide/one-grammar-one-tree`'s reason applies here too: a client that re-derives
what the compiler knows is a second implementation that can disagree with the first.

## Alternatives rejected

**A second document for discovery, with its own version.** Two schemas to freeze, two consumers to
write, and a location spelled twice. The version number exists so one document can grow; growing it
is what it is for.

**Reconstructing the location in the client**, by asking the language server for the symbol or by
scanning the workspace for the class. That is the reconstruction
`rule:ide/every-feature-is-staged-behind-its-dependency` refuses on principle and the goal this
record closes refuses by name: a client feature whose CLI surface is missing is the CLI's problem.

**Listing by running with everything skipped.** A `skip` is a verdict, which means a run happened,
which means fixtures were built and a program was compiled and installed. Discovery that pays for a
run is the cost the feature exists to avoid.

**Making the plaintext report carry the location too.** It is the format a person reads, the
`problemMatcher` of `rule:ide/tasks-carry-a-problem-matcher` reads its diagnostics rather than its
test lines, and a path on every line is noise for the reader it is written for.

## Verification

The conformance case `a-test-run-reports-a-versioned-json-document.nvst` pins the version 2 document
whole, including the line each of its five tests is declared at, and
`a-test-run-lists-what-it-declares-without-running-it.nvst` pins the listing of a program whose first
test would echo and fail if it ran. In `crates/nvs-cli/src/runner.rs`,
`every_json_test_record_carries_its_declaring_file_and_line` asserts each record's line against the
fixture's own text rather than a number written in the test,
`the_schema_version_is_two_and_junit_and_human_are_byte_identical` asserts the JUnit document carries
no location attribute, and `the_listing_mode_discovers_without_executing` takes a listing without
ever calling `compile` — which is what makes "without executing" checkable rather than asserted.
