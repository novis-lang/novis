# ADR 0164 — An encoder ends a cycle at the first repeat, by identity, and never by exhausting a depth cap

- **Scope:** what every encoder that walks a program's own value graph does when it reaches a value it
  is already inside. It does not decide what the *record* renderings answer — [0092](0092.md) settled
  that and this record leaves it exactly as it stands — and it does not move any depth cap, which
  stays as the bound on structure that is legal but deep.
- **Depends on:** [0023](0023.md), [0006](0006.md) and [0024](0024.md), whose graph copy is the walk
  that already holds this property for the two carriers it owns; [0092](0092.md), whose record model
  resolves a repeat to an identity so a diagnostic rendering can link or reference it.
- **Validated by:** the conformance cases the rule below names, landed by the goal that carries it.
  Nothing holds this record on its own today, which is why the rule it creates is `designed`.

> **In short:** an encoder walking a value graph carries the identity of the objects it is currently
> inside, and the first value it meets twice ends the walk there — refused, naming the property chain
> that closed the cycle. `Core\Json::encode` today carries a depth counter and no identity at all, so
> a self-referencing object walks a thousand levels and is then reported as *nesting*, which points
> the reader at a structure that does not exist. The answer is deliberately **not** the `$cycle`
> reference the record renderings emit: that output is our own diagnostic format, and this output is
> somebody else's contract.

## Context

- `rule:classes/graph-copy` already holds cycle-safety for the two carriers it owns — the isolate
  boundary and `Core\Serialize` — and its closing argument is that one walk serving both is what
  stops two implementations that agree today from drifting apart. Nothing states the same property
  for the encoders a program calls directly.
- `rule:errors/record-transformations` holds it for the other half, and resolves a repeat to an
  identity rather than a `*RECURSION*` marker, precisely so the HTML rendering can link the repeat
  and the JSON rendering can emit a reference.
- Between those two sits every encoder a program reaches for itself. `Core\Json::encode` is the one
  that exists; `Core\Xml` is scheduled and not yet built, so a rule written now binds it as it is
  written rather than being retrofitted afterwards.

## Investigation

- **`Core\Json::encode` cannot hang or overflow, and this record does not claim otherwise.**
  `Encodable` carries a depth, a child is constructed at `depth + 1`, and both walk arms check it
  against `DEPTH_CEILING` before descending — `crates/nvs-stdlib/src/json.rs`, `serialize_object` and
  `serialize_array`. The ceiling is `1024`.
- **There is no identity anywhere in the encoder.** No ancestor stack, no seen-set, nothing that
  could tell a repeat from a deep nest.
- **So a cycle is reported as nesting.** `$user->company->owner === $user` walks to the ceiling and
  then throws `a value nested past 1024 levels has no JSON encoding`, a `ThrownClass::Logic`. The
  developer is sent looking for a deep structure that does not exist, which is the worst direction
  for a diagnosis to point — the same argument [0092](0092.md) makes for the debug dump landing in
  the log rather than in a body.
- **It also does the work first.** A thousand levels of walking and allocation are spent before the
  refusal, where the first repeat is reachable at the depth the cycle actually closes at.
- **PHP is not the divergence people expect.** `json_encode` *does* detect recursion, sets
  `JSON_ERROR_RECURSION` and returns `false`. What it does not do is say where. The divergence here
  is the report, not the detection: a throw carrying the property chain, against a `false` and a
  separate call to ask why.
- **Other walkers.** `Core\Serialize` runs the graph copy and is already covered.
  `crates/nvs-stdlib/src/csv.rs`, `uri.rs` and `encoding.rs` each walk a value and are owed an audit
  rather than an assumption; whether any of them can reach an object graph at all is what that audit
  answers.

## Options considered

1. **Leave the depth cap alone.** It is memory-safe and bounded, and that is the whole of its
   defence. It misdiagnoses every cycle and pays a thousand levels of work to do it.
2. **Detect a repeat and emit a reference**, the way the record renderings emit `{"$cycle":3}`.
3. **Detect a repeat and refuse, naming the path that closed it.**

Option 3 is taken.

## Decision

### 1. The walk carries the ancestors it is inside, and refuses the first repeat

An encoder walking a value graph carries the identity of the objects **on the path from the root to
the value it is encoding**, and refuses when the value it is about to descend into is already on that
path. The refusal happens where the cycle closes, not where a counter runs out.

### 2. Ancestors, and deliberately not everything already seen

The set is the ancestor chain, never a global seen-set, because the two answer different questions.
A value reached twice by two different paths — one object held by two properties — is **shared, not
cyclic**, and it is perfectly encodable: JSON has no way to express sharing, so the encoder writes it
out twice, which is the correct and only possible answer. A global seen-set would refuse that legal
document. Only a repeat *on the current path* is a cycle.

This is the one place where an encoder's answer must differ from the record renderings', which assign
an identity to every object precisely so that sharing and cycles both survive into the rendering.

### 3. The refusal names the path

The thrown message carries the property chain that closed the cycle — `User::$company->$owner` —
rather than a count. That is the whole point of detecting at the first repeat: the encoder is standing
exactly where the answer is, and a message that says only "there is a cycle" throws away what it
already knows.

### 4. A user-facing encoder never invents a marker in the document

`Core\Json::encode`'s output is consumed by third parties. Emitting `{"$cycle":3}` would put a
Novis-specific key into a document written against a published contract — the exact objection
[0092](0092.md) already raises about a JSON body: a served shape must not disagree with the contract
in the one environment where clients are written against it. A record rendering may emit a reference
because the consumer of a record rendering is our own tooling. An encoder a program calls to produce
somebody else's payload may not.

The consequence is accepted and is the right one: **a cyclic graph has no JSON encoding, and the
program is told so.**

### 5. The depth cap stays exactly where it is

Cycle detection does not replace the cap and the cap does not replace cycle detection. A legal
acyclic structure can still be deeper than any encoder should walk, and the cap is what bounds that.
After this record the two failures are distinguishable, which is all that was wrong.

## Consequences

- **Cost is bounded by depth, not by node count.** The ancestor chain is at most as deep as the walk,
  which the existing cap already bounds; a linear scan of it is bounded by the same number. Nothing
  here is proportional to the size of the document.
- **A shared substructure still encodes**, and still duplicates, exactly as it does today.
- **A cycle now costs the depth it closes at** rather than a thousand levels.
- **`Core\Xml` inherits the rule as it is written**, which is the reason for taking this record before
  that encoder exists rather than after.
- What a program can express is unchanged: a cyclic graph had no JSON encoding before this record and
  has none after it. Only the diagnosis moves.

## Alternatives rejected

- **`{"$cycle": N}` in the encoded document** — § 4. It is the right answer for a record rendering
  and the wrong one for a payload, and having one encoder that sometimes emits a foreign key is worse
  than having two encoders whose audiences are stated.
- **A global seen-set** — § 2. It buys nothing and refuses legal documents that contain shared
  substructure, which is common in any object graph with a repeated reference.
- **Raising or removing the depth cap** — the cap is not what is wrong; the cap is the only reason
  the failure is currently safe. Removing it trades a bad diagnosis for a stack overflow.
- **Detecting only in `Core\Json`** — the rule exists because the next encoder is not built yet. A fix
  applied to one file is the "two implementations that agree today" failure `rule:classes/graph-copy`
  already names.

## Verification

The rule names its conformance cases: a self-referencing object refused with the path in the message,
a shared-but-acyclic graph encoded rather than refused, and a legal deep document still bounded by the
cap it was always bounded by. The audit of `csv.rs`, `uri.rs` and `encoding.rs` is the goal's, and
reports what it found rather than assuming the answer.
