# ADR 0130 — Usage telemetry is opt-in, counts only operator actions, and a serving process never uploads

- **Scope:** how the project measures that Novis is actually used — the two consents, the counter
  schema, when a payload may leave the machine and from which process shapes, `nvs update-check`'s
  output contract, the endpoint's configurability, and when this is implemented. Not in scope: package
  updating — `nvs update` is [0081](0081.md)'s resolver
  and this ADR's version check is deliberately spelled `update-check` so the two never collide; the
  server's response headers and proxy contract ([0097](0097.md));
  a Novis *application's* metrics and tracing ([0076](0076.md)); user code's
  outbound-request policy ([0058](0058.md)), which governs the language, not
  the tool.

> **In short:** adoption is measured by **two independent opt-ins, both off by default**: usage
> telemetry (`nvs telemetry on`) and the update check. Telemetry separates **recording** from
> **uploading**: any `nvs` invocation increments local counters drawn from a closed schema — the
> subcommand that ran, never its arguments and never anything derived from request traffic — and the
> finished previous week's aggregate is uploaded **at most weekly**, riding the next short-lived
> user-initiated command, commonly the update check. A process serving traffic records and **never
> uploads**. An upload gets 3 seconds, cannot fail the carrying command, and says plainly what it did.
> `nvs telemetry show` prints the exact pending payload; the endpoint is configurable so tests prove
> all of it against a local listener. Implementation waits until the parity chain's six goals are done.

## Context

- PHP's `X-Powered-By` header (`expose_php`) is the best-known way a runtime advertises itself, and it
  measures nothing by itself: only third-party crawls (W3Techs, Netcraft, Shodan) turn it into counts,
  it discloses a version to attackers — every hardening guide's first line is `expose_php = Off` — and
  the people it exposes are a site's visitors and operators, who never consented. As a measurement
  channel it is both passive and hostile to priority 1
  ([0004](0004.md)'s ordering), so it is the shape to avoid, not copy.
- The population worth measuring is developers and operators *running* `nvs` — most of them running it
  as an HTTP server. Since `nvs serve` is itself a CLI invocation, the honest boundary is not "CLI
  versus server" but **operator actions versus traffic**, and **local writes versus network uploads**.
- The user's constraints, fixed before this design: disabled by default, and 100% clear what is
  collected, when, and where. The nearest prior art meeting both is Go's transparent-telemetry design:
  opt-in, local-first counters, weekly aggregated uploads, schema and collected data both public.
- Download and pull counts need no runtime code and keep working for hosts that never opt in; they are
  the floor this design sits on, not something it replaces.

## Decision

### 1. Two consents, both off by default, independent

Usage telemetry is switched by `nvs telemetry on|off|status`; the update check runs only when invoked
(`nvs update-check`, interactively or from the operator's own cron). Neither switch ever implies the
other: enabling update checks must never silently enable usage reporting, and vice versa. One TCP
connection may carry both — § 3 — only when both are on. Consent and counters live in plain files
under the user's nvs data directory, inspectable with any editor; `nvs telemetry off` stops recording,
and `nvs telemetry reset` (or deleting the directory) wipes everything held locally.

### 2. Recording is local and the counter set is closed

Any `nvs` invocation may increment counters in the local file — a write, never a connection. A counter
is `invocation.<subcommand>` where `<subcommand>` comes from the binary's own compiled-in command
table, plus exactly one fallback, `invocation.unknown`. **The literal argv never becomes a counter
name**: a typo, a path, or a misparse increments `invocation.unknown` and nothing else, so arbitrary
user input cannot leak into the schema and every counter that can ever exist is enumerable from the
binary that wrote it. Beside the counters the payload carries only: a schema version, the `nvs`
version, coarse `os` and `arch`, and the ISO week being reported. No machine ID, no per-event
timestamps, no arguments, no paths, no environment.

**Nothing derived from traffic is ever counted.** `nvs serve` incrementing `invocation.serve` at
startup records the operator's action; request counts, routes, headers or anything else the internet
sent belong to the site's visitors and are permanently out of schema. The counter file is provably a
function of what the operator did.

### 3. An upload rides a short-lived invocation, at most weekly

Only the **previous, finished week's** aggregate is ever sent — never a live stream — at most once a
week, at a randomized point inside the eligible window. The upload is carried by the next short-lived
user-initiated invocation that notices "telemetry is on and a finished week is unsent"; `nvs
update-check` is the natural carrier (an ops team cronning it on production boxes is exactly the
user-initiated short-lived process this rule wants), and `nvs telemetry upload` exists for schedulers
that want only that. There is no daemon, no timer, and no background process. **A process that has
bound a socket records and never uploads**: the auditable claim is that `nvs serve` makes zero
outbound telemetry connections. An empty week is not sent, and a week bucket in the future is never
sent.

### 4. A failed upload never fails the command

The upload has a **3-second budget** end to end; when it expires or the connection fails, the attempt
is abandoned, the counters are kept for the next carrier, the output says exactly that — e.g.
`telemetry: could not send (timeout after 3s); kept for next time` — and the carrying command's work
and exit status are untouched. No retry inside the same invocation.

### 5. `nvs update-check` states the whole picture

Its output always carries: whether telemetry is on or off, the local version, and the latest released
version. With telemetry on it adds: when the last upload happened, when the next one is eligible, and
the lifetime totals — how many uploads, how many bytes sent — both maintained locally and never
themselves uploaded. `--json` emits one JSON document with stable, schema-versioned field names for
the user's own automation; the default human output **streams** as it works, one line per step, so
the user sees exactly where it is when something is slow, and follows
[0086](0086.md)'s terminal conventions. The exit status is 0 whether or
not an update exists and whether or not a telemetry send succeeded; automation reads the JSON.

### 6. The endpoint is configuration

The update-check and telemetry URLs have compiled-in defaults, overridable by environment variable
(`NVS_UPDATE_URL`, `NVS_TELEMETRY_URL`). That is what makes § 3 and § 4 testable: the test suite runs
every claim — the weekly gate, the timeout, the never-uploads-from-serve rule — against a local
listener, and CI never touches the real host.

### 7. The design is falsifiable, and both sides are published

`nvs telemetry show` prints the exact payload the next upload would send, before anything is sent.
The reference's tools chapter documents both consents, the complete counter list, and both endpoints'
contracts **when this ships** — [docs/reference/README.md](../reference/README.md) documents only
what ships — and that chapter, not this file, is then the user-facing statement of what is collected.
The service side's contract is published with it: aggregates only, no IP retention, and the
aggregated data itself public, so anyone can see exactly what the project sees.

### 8. Implementation waits for the parity chain

Nothing in `crates/` changes while the six goals of
[docs/agent/goals/](../agent/goals/) are running; the implementing slices are
scheduled after goal `server` reaches its acceptance, alongside the other post-chain work the plan names.
Until then this ADR is the design's only home and the reference says nothing of it.

## Consequences

- The question "how many people actively run Novis, and as what" becomes answerable from three
  layered signals — downloads, update checks, and opted-in counters — without a byte leaving any
  machine whose operator did not ask for it, and without the serving runtime gaining an outbound call.
- What it spends ([0004](0004.md) asks for the number): a few KiB in one local
  counter file per user, one buffered append per invocation — for `nvs serve`, once at startup, before
  the listener binds — and nothing on the request path.
- The undercount is accepted and stated: opt-in telemetry famously reports a few percent of the real
  population, and a deployed server whose operator never runs another command records forever and
  uploads never. Cronned `nvs update-check` on ops boxes, and download counts, are the correction.
- `update-check` beside [0081](0081.md)'s `nvs update` is
  a naming cost paid deliberately: the resolver keeps the short verb it already owns.

## Alternatives rejected

- **An `X-Powered-By`-style header as measurement.** Passive — only someone else's crawl counts it —
  and a version disclosure on every response, spent against priority 1 for data the project never
  receives. If an advertise-yourself header is ever wanted it is a separate decision on
  [0097](0097.md)'s surface, off by default, and still not
  measurement.
- **Opt-out telemetry** (the .NET CLI, Homebrew). Bigger numbers, wrong default for a runtime whose
  first priority is that operators can trust it; also simply outside this decision's fixed constraint.
- **A background daemon or timer that phones home.** The exact shape people distrust even when opted
  in, and a second long-lived process to secure. Uploads are carried, never initiated by a resident
  process.
- **Uploading from the serving process** — even just once at startup. It breaks the one-sentence
  auditable claim (`nvs serve` makes zero outbound telemetry calls) that § 3 exists to keep.
- **Counter names from argv.** One typo'd invocation turns "we collect command names" into a lie;
  the closed set with a single `unknown` bucket is the whole difference between a schema and a log.
- **Counting anything from request traffic.** The visitors never consented; out of schema permanently,
  not merely off by default.

## Verification

The slices that land this — after § 8's gate — owe, all against § 6's local listener: a test that a
`serve` process under load opens no outbound telemetry connection while still incrementing
`invocation.serve`; that an unknown subcommand increments only `invocation.unknown`; that an
unreachable endpoint costs at most 3 seconds, leaves the counters intact, exits 0, and says what
happened; that a second upload inside the same week is refused locally; that `nvs telemetry show`'s
bytes equal what the listener then receives; that enabling the update check alone uploads nothing and
enabling telemetry alone checks no version; and that `update-check --json` carries every § 5 field
under stable names while the human output streams. The reference chapter and the published schema
land in the same slices, not before.
