# ADR 0226 — a check runs only when the change reaches what its green runs were observed to use, and the pipeline builds, runs and records on one instrumented debug build

- **Scope:** how the acceptance sweep, `bun nv verify`, `bun nv affected` and `bun nv proofs` choose
  what to start, what they record, and which `nvs` they run. It does not change what a check asks, how
  a check is judged, the plan's shape or the floor gate's cadence.
- **Depends on:** [0222](0222.md) for the floor as a view over the walked goals, [0224](0224.md) for
  `tools/nv-scan` reading Rust with `syn`, and [0225](0225.md) for the graduated floor checks.
- **Validated by:** `tools/nv/test/select-store.test.ts`, `select-items.test.ts`,
  `select-extract.test.ts`, `select-query.test.ts`, `select-record.test.ts` and
  `select-checks.test.ts`, and `crates/nvs-cli/tests/footprint.rs`.

> **In short:** every run of a check's smallest part, an **atom** (one `.nvst` case, one proof program,
> one Rust test binary, one `bun nv` command, one tools test file, one other plan check), records what
> it was observed to use: the Rust items that ran, from LLVM coverage, and the `Core` classes, cards,
> files, directories and paths it looked up, from a log the binaries write. A sweep turns the change
> since the last recorded tree into keys and looks the atoms up in a reverse index. Only those start.
> The sweep, verify, affected and proofs share one engine (`tools/nv/select/`) and one store
> (`.cache/select.sqlite`). The pipeline's one debug build is `covws`, which instruments the
> workspace's own crates. Proof programs are judged on the uninstrumented `target/proof` build and
> recorded in a second run on `covws`.

## Context

Every check was keyed on a **prediction** of what it reads (`tools/nv/keys/`), made at crate
granularity and then narrowed by exceptions: tiers of a Rust file's tokens, partitions of the tree,
lists of wide binaries and card readers. An edit to one function body of
`crates/nvs-stdlib/src/process.rs` re-ran about 4,600 case runs and 125 test binaries. Five fixes to
the keys in one day each moved the over-selection somewhere else. And the sweep computed a key for
each of 486 checks to learn which were current, so many checks were started only to find they were.

Three stores answered the same question in different shapes: the sweep's memo, verify's green caches
and the proofs memo, plus the reads logs of `bun nv` commands, proof groups and test binaries.

## Investigation

A spike under `.agent-tmp/spike/` measured the observed alternative over every case tree.

1. **Coverage maps to items.** 0 of 18,270 repository functions were unmapped. Closures, generics
   and inlined functions map to their items, and the JIT's Rust helpers show up. The 1,002
   `nvs_helper!` wrappers map to the macro in `crates/nvs-runtime/src/abi.rs`.
2. **Instrumenting only the workspace crates is enough.** A `RUSTC_WORKSPACE_WRAPPER` that adds
   `-C instrument-coverage` to workspace crates compiled for an explicit `--target` gives the same
   footprints as instrumenting everything. The build is 320 crates and 2.3 GB, `nvs.exe` is 79 MB, a
   one-body edit to `process.rs` rebuilds 6 crates, and a run's overhead is in the noise. Each
   process writes about 2.9 MB of raw profile.
3. **The selection is small where it should be and total where it should be.** A `Handle::wait` body
   edit selects 15 cases; `Math` `gcd` 17; `CoreMethod::positional` and `Lexer::new` every one of
   the 6,099 programs, since every program runs them.
4. **What coverage cannot see.** Consts, statics, types, traits and `macro_rules!` never appear in a
   profile. A registry row is reached by lookup, not by name: a name-reference fallback made `CLASSES`
   select everything, and it missed compile-only cases under `tests/conformance/reject/` that depend
   on a row and run none of its functions. A warm compile cache skips the code generator, so its
   functions go missing from a footprint.
5. **Seeding costs.** Every case tree is 6,107 cases, 9,039 processes, 25.3 GB of raw profile written
   and deleted as it was read, and 18,078 extraction launches. The compact footprint set was 1.7 MB
   gzipped.
6. **Instrumented optimized code is too slow to judge on.** Over all 699 attacks, the instrumented
   proof build against the uninstrumented one is median 1.7x, p90 3.5x and at most 16–23x, and one
   attack went over its own time limit (2.0 s to 11.9 s, of 10 s). Recording itself cost nothing
   measurable.

## Options considered

1. Refine the static keys again: finer tiers, more partitions, more exception lists.
2. A static call graph from `syn`: follow calls from each program's entry points.
3. Observed footprints: record what each atom ran and read, and select from the change through a
   reverse index.

## Decision

Option 3.

### 1. An atom's footprint is what its green runs were observed to use

A footprint is a set of keys with the digest each had when the atom ran. `fn:<file>#<item>` comes from
coverage, mapped by line to the innermost `syn` item (`tools/nv-scan --items`). `class:`, `card:`,
`file:`, `dir:`, `exists:`, `tree:` and `named:` come from the log `nvs` and the test binaries write
under `NVS_FOOTPRINT_LOG`, and from `nvs_repo` in the Rust tests. `mod:` and `file:` for a `bun nv`
process come from the `NV_READS_LOG` shim. `def:` is the atom's own definition, computed. A change to a
global file (the toolchain, `Cargo.lock`, the root manifests, `.cargo/config.toml`) selects every atom.
`tools/nv/select/keys.ts` is the key table.

An atom's footprint is the union of its green runs since its definition last changed, pruned of items
that no longer exist, so a nondeterministic path is kept once it has been seen. Footprints are stored
per platform.

### 2. Selection starts from the change, never from the check list

The change since the recorded tree is read from git, untracked files included. A Rust file is compared
item by item on docs-stripped token digests, so a doc-comment edit is no change. What coverage cannot
see is closed over the reference graph until a function is reached: a const, static, type or table
moves every item that names it; a `macro_rules!` moves every item that invokes it; a class table's
changed row moves that row's `class:` key; a card moves only `card:` keys. A build script's inputs are
what cargo recorded as its `rerun-if-changed` paths, and a generated file's bytes are folded into the
item that includes it. The atoms run are those never recorded on this platform, last red, owed or
diverged, those whose definition changed, and those indexed under a changed key. Nothing else starts.

### 3. One engine and one store

The sweep (`tools/nv/driver/accept.ts`), `bun nv verify`, `bun nv affected` and `bun nv proofs` all ask
`tools/nv/select/`. A plan check is a named group of atoms plus its pass condition
(`tools/nv/select/checks.ts`), so a check runs only its selected cases, programs or binaries. A verify
step that runs no code is selected by the files it reads. The store is `bun:sqlite` in
`.cache/select.sqlite`, beside the index and never inside it, since the index deletes its own file when
its layout changes. It replaces the JSON memos and reads logs.

Every run records. A run advances the recorded tree for what went green: a red atom stays selected as
`red`, and an atom the change reached that the run did not start is `owed` until a run of it is green.
`bun nv select --seed` records from nothing, for a new platform or a lost store.

### 4. `covws` is the pipeline's one debug build

`tools/covwrap` is the wrapper, and `tools/nv/lib/covws.ts` builds `target/covws` with an explicit host
`--target`, so dependencies, build scripts and proc-macros stay uninstrumented. Every debug `nvs` and
test binary the sweep, verify, `bun nv try` and `bun nv reference` run is this build. `target/debug` is
what a person builds by hand, and the pipeline never needs it. A recorded run starts with an empty
compile cache, so the code generator's functions are seen.

### 5. Proof programs are judged uninstrumented and recorded on `covws`

A proof program's verdict is taken on the uninstrumented `target/proof` build, as before. Each selected
program then runs a second time on the `covws` debug `nvs` with only a generous hang timeout, and that
run is never a verdict. If its outcome differs from the judged run's, the footprint may be cut short:
the atom is marked diverged, always runs, and `bun nv select --stats` lists it. An item compiled only
under `cfg(not(debug_assertions))` that changes counts as a change to its debug twin, and one with no
twin selects every proof program (`profile:optimized`).

### 6. What stays predicted, and the safety net

The heavy checks build what no recorded run builds: the release profile, fuzz, TSan, the database
matrix and the two Linux legs. They keep the floor gate's cadence and are keyed on their observed reads
plus every item and directory of the crates they build (`heavyKeys`). That is the one prediction left,
and it is named as one. A check with `memoize = false` is never answered from the store. Anything that
cannot be attributed widens: an unparseable file selects every atom that ran any of its code, an
unmapped function gives `fn:<file>#*` or `*`, and an unreadable record depends on everything.

A full run of every atom, recording, on the floor gate's cadence is the safety net: an atom red there
that no selective run started since its last green is a selection miss, reported as a red.

## Consequences

- An edit selects what ran the code it changed. The acceptance sweep prints nothing for a check the
  change did not reach.
- `tools/nv/keys/` keeps only `scan.ts` (the perf ledger's `impl_hash` and the item scan), `graph.ts`
  (CI's lane closure) and `escape.ts` (the wide-binary list for tests that leave their package). The
  tiers as keys, the partitions, `nv why`, `nv impact`, the impact probes and verify `--keys` are
  deleted.
- **What it costs.** The `covws` build replaces the pipeline's `target/debug`, at about the same size.
  Each recorded atom costs two extra launches of `llvm-profdata`, plus one `llvm-cov export` per
  object and build, cached. Each selected proof program runs twice. A new platform or a lost store pays
  one seed of every atom.
- **What it spends on disk**, on the development machine and never on a request: the store is about
  180 MB for 6,025 atoms, and the coverage-map cache under `.cache/select/covmap/` about 370 MB. Both
  are per machine, git-ignored, and grow with the number of atoms and builds, not with the number of
  runs. Raw profiles are deleted as each atom is read.
- A Rust test binary is one atom: libtest runs it in one process, so its footprint is the union of its
  tests, and a test added to a package moves that package's `tests:` key.

## Alternatives rejected

- **Refining the static keys.** Each refinement over the last day moved the over-selection rather than
  removing it, and every narrowing was a claim someone had to prove and remember. A prediction at crate
  granularity cannot tell a function body a program runs from one it does not.
- **A static call graph.** Dynamic dispatch, the registry's lookup by name, JIT-compiled code calling
  Rust helpers through `no_mangle` symbols and closures passed across crates all hide the edges that
  matter. The graph would be unsound exactly where the runtime is interesting.
- **Judging proof programs on an instrumented optimized build.** Investigation item 6: a 1.7x median
  and a 23x worst case change what an attack's time limit means, and one attack fails its limit only
  under instrumentation. Recording on a second debug run costs no build and leaves the verdict where
  it was.

## Revisiting

If the full run finds selection misses that trace to one kind of input, that kind gets a key of its
own or widens. If the extraction launches become a measurable share of a sweep, a reader of
`__llvm_covfun` and the raw profile replaces them.

## Verification

The store, the item diff and closure, extraction, the query, recording and the check groups have their
own test files, named above. `crates/nvs-cli/tests/footprint.rs` holds the footprint log's lines. Before
the merge, a mutation run applies one change at a time (a function body, a registry row, a card, a
struct field, a `macro_rules!` body, a table const, an `include_str!` target, a data file a case reads,
a new file in a listed directory, `nvs.toml`, a tools module), runs the selection and the full suite,
and requires every atom that went red to have been selected.
