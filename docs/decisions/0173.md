# ADR 0173 — format-on-save runs `nvs fmt`, then the editor's own HTML formatter over each markup chunk, starting at the Novis block's indentation

- **Scope:** what a format request in an editor does to a `.nvs` file with inline HTML in it, and the
  one layout rule `nvs fmt` gains so the two halves meet. It changes nothing else `nvs fmt` does, and it
  does not decide how the PhpStorm client formats markup.
- **Depends on:** [0039](0039.md) for `nvs fmt`, [0108](0108.md) for the template region,
  [0169](0169.md) for the markup literal.
- **Validated by** goal `template-format`'s acceptance list, and goal `fmt`'s for the `?>` rule.

> **In short:** [0108](0108.md) gave the markup half of a `.nvs` file the editor's HTML services and
> refused it the editor's HTML formatter, and `nvs fmt` never touches markup — so markup was formatted
> by nothing. Format-on-save is now three steps in one order: `nvs fmt` over the whole file,
> `nvs/regions` over the result, and the editor's own HTML formatter over each markup chunk, starting at
> the indentation of the `?>` line that opened it. `nvs fmt` gains one rule: a `?>` that begins its line
> sits at the depth of the block it is in. Markup therefore indents from where the Novis code is, and a
> file does not jump left and right between the two. The pass is on by default, and
> `nvs.template.format` turns it off.

## Context

- `nvs fmt` leaves inline HTML byte-identical (`rule:tooling/fmt-novis-constructs`), and
  [0108](0108.md) registered no formatting provider over the markup, so a developer writing a page got
  completion and hover in the markup and no layout at all.
- A template interleaves the two modes. The layout developers keep by hand is that markup starts at the
  indentation of the Novis code around it and nests from there — the shape, not a conformance case:

  ```nvs
      public function render(): void
      {
          ?>
          <div class="box">
              <img src="<?= $src ?>" alt=""/>
          </div>
          <?nvs
          foreach ($rows as $row) {
              ?>
              <p>row</p>
              <?nvs
          }
      }
  ```

  Neither formatter produces that alone. `nvs fmt` does not touch markup, and an HTML formatter over the
  whole document does not see a Novis block, so the `<p>` inside the loop would sit at its siblings'
  column rather than the loop's.

## Decision

### 1. The order

A format request in the editor runs three steps, and the result is one edit:

1. `nvs fmt --stdin` over the whole buffer. A file `nvs fmt` refuses is left as written, and nothing
   below runs.
2. `nvs/regions` over the text step 1 produced, which the request now carries (§ 4).
3. The editor's HTML formatter over each chunk (§ 2), at the chunk's base (§ 3).

Nothing in step 3 is Novis's code: it is the editor's own formatter, reached the way the services
already are, and the client decides only where a chunk starts and at what column — both read off text
whose boundaries the server reported.

### 2. A chunk

A chunk is the markup between a `?>` that ends its line and the `<?nvs` (or the end of the file) that
reopens code, together with every `<?= … ?>` hole inside it: a hole is part of its line, not a boundary.
The markup before a file's first open tag is a chunk whose base is column zero.

A hole's bytes are Novis's and are never edited. The formatter is shown a stand-in of the same length,
and a chunk whose formatting would change a byte of a hole is left as written — the safe direction, since
an unformatted chunk is a layout complaint and an edited hole is a changed program.

### 3. The base

A chunk's lines start at the indentation of the line holding the `?>` that opened it, and the line
holding the `<?nvs` that closes it starts there too. Nesting inside the chunk is the HTML formatter's,
one unit per level, and the unit is `nvs fmt`'s four spaces rather than the editor's tab setting, so a
chunk and the code around it agree on what a level is.

`nvs fmt` is what puts that `?>` where it belongs: a `?>` that begins its line is indented to the depth
of the block it is in. It never moves a `?>` onto or off a line (`rule:tooling/fmt-never-reflows`), and
the whitespace before a `?>` is code, so the move changes nothing the program prints.

### 4. `nvs/regions` takes the text it is asked about

The request carries an optional `text`. Given one, the answer is the regions of that text; without one it
is the open buffer's, as before. Step 2 needs the regions of a text the buffer does not hold yet, and the
two alternatives are both refused elsewhere: the client lexing it is the second lexer
[0108](0108.md) put the list on the server to prevent, and `nvs fmt` printing regions would be a flag
that is not an I/O mode (`rule:tooling/fmt-is-one-canonical-style`). The answer's shape is unchanged —
a range and a language.

### 5. On by default, and its own setting

`nvs.template.format`, default `true`; `false` makes format-on-save exactly `nvs fmt`. It is separate
from `nvs.template.services`, so a developer can keep the completion and refuse the formatter, or the
reverse.

### 6. What stops being canonical

`nvs fmt --check` still passes over a file this pass formatted, because `nvs fmt` never touches markup.
What stops holding is that format-on-save *is* `nvs fmt`. The markup's layout reads the user's
`html.format.*` settings, so two developers with different settings can reformat each other's markup,
CI cannot check it, and the PhpStorm client's HTML formatter will not write VS Code's bytes. Novis bytes
stay canonical and identical in every editor; markup bytes are the editor's.

## Consequences

- **Priority 2.** Inline HTML is printed byte for byte — `lower_inline_html` in
  `crates/nvs-ir/src/lower/expr.rs` emits the run's text as one constant string — so re-indenting markup
  changes what a program prints. A browser renders the same page, except inside `<pre>`, `<textarea>` and
  `white-space: pre`, which VS Code's HTML formatter is believed to leave alone by default (not checked
  here). A CLI program or a `text/plain` response that prints through inline HTML prints different
  whitespace. That is why the pass is the editor's and never `nvs fmt`'s: a Novis formatter that changed
  program output would not be a formatter. A developer whose markup whitespace is output turns it off.
- **Priorities 3 and 5.** Nothing on the request path. Per format request: one `nvs fmt` process, one
  regions round trip and one HTML format per chunk, all in the editor process, and nothing held by the
  server.
- **Priority 4.** The client grows its most intricate code — chunks, stand-ins, the base column, refusing
  an edit that reaches a hole — all of it over text and none of it language logic.
  `rule:ide/one-server-two-thin-clients` now says formatting of Novis has one implementation and markup's
  is the editor's.
- M10's *Verify* line narrows from format-on-save matching `nvs fmt --check` byte for byte to the Novis
  bytes matching it.
- The rule id `ide/a-template-region-gets-services-but-no-second-formatter` names the half this record
  removes. Goal `template-format` renames it together with its citations.

## Alternatives rejected

- **Off by default.** Keeps every file's bytes canonical and was the recommendation put to the owner, who
  chose on: markup is where a web application is written, and a formatter that skips it is one
  developers replace with nothing. The setting keeps the other answer one click away.
- **Markup formatting inside `nvs fmt`.** Canonical, checkable in CI and identical in every editor — but
  an HTML formatter to build and own, every change to it a diff across every template, and a Novis
  formatter that re-indents markup changes program output.
- **One HTML format over the whole joined document**, the virtual document the services are already
  shown (`editors/vscode/src/template.ts`, `virtual`). It nests markup by HTML depth alone, so a chunk
  inside a `foreach` sits at its siblings' column — the jump this record exists to remove.

## Revisiting

If markup whitespace that is program output turns out to be common — CLI programs writing through inline
HTML — the default flips to off. That is `nvs.template.format`'s default and nothing else.

## Verification

- Goal `fmt`: a `?>` that begins its line sits at its block's depth, and inline HTML and a markup
  literal's body are byte-identical after `nvs fmt`.
- Goal `template-format`: `nvs/regions` answers for a text it is given. In the headless tier, with the
  HTML formatter injected: a chunk starts at its `?>` line's indentation, a chunk inside a loop body is one
  level deeper than the loop, the closing `<?nvs` sits at the chunk's base, no byte of a hole is edited, no
  byte outside a region changes, and `false` leaves format-on-save as `nvs fmt`. The editor's real HTML
  formatter is proven by the host run (`rule:ide/headless-gates-the-loop-the-host-run-gates-the-milestone`).
