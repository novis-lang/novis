# ADR 0084 — A background job is a durable row, enqueued in your transaction and run as an isolate

- **Scope:** `Core\Queue` — what a job is, where it is stored, how it is claimed by a fleet, its delivery
  guarantee, retries and dead-lettering, which process runs one, and what a payload may carry. Not in scope:
  the `Web\Job` ergonomics that sit on top ([0082](0082.md) § 3), and any
  external broker, which § 8 places outside the runtime.
- **Depends on:** [0067](0067.md) — the queue has no storage engine of its own.

> **In short:** a job is **a row in a table in a database `Core\Db` already talks to**. That single choice
> buys the property every other design gives up: **`Core\Queue::push` inside a `Core\Db` transaction commits
> with it**, so a job and the row that justified it are atomic — no "the order saved but the confirmation
> email never queued", which is the most common correctness bug in background work and one an external
> broker cannot fix. A job **names a script file** and runs as a **root isolate**, the same shape
> `spawn script` ([0006](0006.md)) and a connection upgrade
> ([0083](0083.md)) already use, with its own budget and grants.
> Delivery is **at-least-once** — stated plainly rather than implied — with a visibility timeout, bounded
> attempts, exponential backoff with jitter, and a dead-letter row that is never silently discarded.
> Claiming is a `SKIP LOCKED`-shaped query, so **a fleet of instances is safe by construction** with no
> lease protocol of our own. A payload **refuses `secret`**, because a durable row is an output.

## Context

- **Neither existing mechanism covers this.** `rule:config/scheduled-work-is-a-config-block` fires work by
  *time*, from operator-owned config. `rule:concurrency/one-scheduler`'s
  `afterResponse` runs work after a response but inside the request tree, bounded and in-memory: if the
  process dies, the work is gone. Neither answers *enqueue this now, run it durably later, retry it if it
  fails* — which is what an email, an export, a webhook delivery, a thumbnail and a third-party sync all
  are.
- **The strongest available correctness argument favours the database.** In every queue architecture built
  on an external broker, the enqueue and the business write are two systems, so they cannot commit
  together. Every team then rediscovers the outbox pattern — write the job to your database inside the
  transaction, relay it to the broker afterwards — which is to say they rediscover that the database was
  the right queue. Starting there removes the failure mode instead of documenting it.
- **Novis's shared-nothing model makes the storage question sharper, not softer.**
  `rule:concurrency/cross-request-state-is-explicit`'s cross-request store is explicitly lossy — "it must
  always be correct to find nothing there" — which is right for a cache and disqualifying for a job
  somebody is waiting on. A runtime-owned on-disk log would make a job local to one machine's disk, which
  breaks the moment a deployment has two instances.
- **The ceiling is known and acceptable.** A database-backed queue does thousands of jobs per second, not
  millions. `rule:programs/audience`'s audience is nowhere near that, and § 8
  keeps the seam open for the day someone is.
- **The runtime already knows how to run a detached unit of work.** `spawn script` gives an isolate with a
  budget, grants, an argument and an artifact-cached compiled unit; [0073](0073.md)
  already fires one from a ticker. A job is that, triggered by a row instead of a clock.

## Decision

### 1. The surface

```php
Core\Queue::push(string $script, {
    args?:        mixed,          // copied by 0023's graph copy; refuses `secret`
    queue?:       string,         // named queue, default "default"
    runAt?:       Instant,        // earliest execution; default now
    maxAttempts?: uint,           // default from config, always finite
    backoff?:     Duration,       // base for exponential backoff with jitter
    key?:         string,         // dedupe: at most one pending job per key
    limits?:      {…},            // 0005's budget for the job's isolate
    grants?:      {…},            // narrowed from the enqueuing context, never widened
}): Queue\Id
```

`Core\Queue::cancel(Queue\Id): bool`, `::status(Queue\Id): Queue\State` and
`::stats(string $queue): Queue\Stats` complete the roster. Everything follows
[0063](0063.md): subject first, one trailing options shape, nothing mutates,
failure throws, absence is `?T`.

**`Queue\State` is `Pending`, `Claimed`, `Succeeded`, `Dead`, `Cancelled`**, and there is no `Failed`: § 6
retries a failed attempt, so a job between attempts is `Pending` with its backoff still to elapse, and the
question "did it fail" is a question about `Dead`. **`cancel` answers a `bool` because it is a race it can
lose** — § 4 lets a worker claim a pending job at any moment, so a late cancel finds the work already
running, and that is the ordinary outcome rather than an unlucky one. It changes the job's state rather than
deleting the row, so a caller that cancels and then asks `status` gets `Cancelled` instead of a refusal.

**`Queue\Stats` is a class whose four counters are members** — `pending()`, `claimed()`,
`attempts()` and § 6's dead-letter depth as `deadLettered()`. A record returned by value would read
better and is not available: a `Core`-owned instance has no property a program can reach, so
`$stats->pending` would resolve to nothing at all, and a shape returned by value is a spelling the
signature registry has not got. `stats` is also the one member of the four asked about a *queue*
rather than about a job, because what § 6 asks to be watched is a population; it reads all four out
of one statement, so they describe one instant rather than four.

**A job names a file**, not a class or a closure — the third construct to take that shape after
`spawn script` and `Core\Socket::upgrade`. A payload crossing into it is a value copied by
[0023](0023.md), never a reference, and it is decoded on the other
side into declared types through [0071](0071.md)'s codecs.

### 2. Storage is a table, in a connection the operator names

```toml
[queue]
connection   = "main"        # a [db.<name>] block; may be the application's own
workers      = 4             # per instance; 0 makes this instance enqueue-only
max_attempts = 5
visibility   = 5m
```

- **The runtime owns the schema, and owns it as a value.** One jobs table and one dead-letter table,
  expressed as a [0145](0145.md) `Core\Db\Schema`
  and converged by `nvs queue migrate`, an explicit operator command. That is one description of the two
  tables rather than one per dialect, which is what makes the next bullet's "all five" hold: a
  hand-written DDL list per backend is one chance to drift per backend, and the backend nobody wrote is
  indistinguishable from one nobody supports. DDL is an injection sink and a privileged act
  ([0024](0024.md)); the runtime never issues it implicitly at boot or
  from a request, and applying the plan takes 0067 § 3's `db.schema` like any other DDL.
- **It may be the application's own database, and that is the recommended configuration**, because § 3's
  transactional enqueue requires it. A separate queue database is permitted and silently gives up that
  property — the documentation must say so at the point where the option is offered.
- **All five [0067](0067.md) backends are supported**, with per-backend claiming (§ 4) and one
  contract.

### 3. The property that decides the design: enqueue commits with your write

```php
Core\Db::connect("main")->transaction(fn (Db\Transaction $tx) {
    var $orderId = $tx->execute("insert into orders …", […]);
    Core\Queue::push('jobs/send-receipt.nvs', {args: {orderId: $orderId}});
    // both commit, or neither does
});
```

`push` inside a transaction on the queue's own connection enlists in that transaction. If the transaction
rolls back, the job was never enqueued; if it commits, the job is durable. **There is no window in which one
exists without the other**, and no outbox to write.

Outside a transaction, `push` is its own committed statement. `push` on a *different* connection than the
queue's is not transactional and the compiler cannot know that — so the runtime records it and
`Core\Queue::stats` reports non-transactional enqueues, rather than the property silently not holding.

### 4. Claiming, and why a fleet needs no protocol of ours

A worker claims with a single statement that atomically selects and marks the oldest due job in its queues:
`FOR UPDATE SKIP LOCKED` on PostgreSQL and MySQL, `READPAST` on SQL Server, and an immediate transaction on
SQLite, whose single-writer model makes the contention question moot. In every case the database provides
the mutual exclusion, so **two instances of a fleet cannot claim the same job** and Novis writes no lease
protocol, no heartbeat and no coordinator. `rule:config/scheduled-work-is-a-config-block`'s fleet lease exists
for the same reason and this reuses its reasoning rather than a second mechanism.

A claimed job carries a **visibility timeout**: if the worker dies, the claim expires and the job becomes
claimable again. That is what makes delivery at-least-once and it is why § 6 is a rule rather than advice.

### 5. Running a job

- A job runs as a **root isolate** — its own arena, its own budget, its own grants narrowed from those
  recorded at enqueue, sharing only compiled code. It is the same `Isolate` M5 builds; there is no second
  execution path.
- **A payload refuses `secret`.** A durable row is an output, and
  [0033](0033.md) refuses output. A job that needs a credential
  reads it from configuration at run time, which is where credentials live anyway.
- **A payload's qualifiers are recorded with it and restored on decode.** A `tainted` value enqueued comes
  back `tainted`, so the analysis survives the round trip instead of being laundered by a database. The
  queue table is trusted exactly as far as the rest of the application's database is — an attacker who can
  write to it has already won — and saying that here is better than returning everything `tainted` and
  training every job to launder reflexively.
- **Which process runs jobs is configuration.** `[queue] workers` runs them inside `nvs serve`, on the same
  binary and the same cores; `nvs work --queue=…` runs a dedicated worker process for fleets that separate
  them. Both drive the identical isolate.
- **A job holds the compiled unit it started with**, exactly as a request and a connection do
  ([0017](0017.md)).

### 6. Failure is bounded, and nothing is discarded silently

- **At-least-once, stated plainly.** A job may run twice — the worker died after the work and before the
  acknowledgement, or the visibility timeout expired under load. Idempotency is the application's
  obligation, and `key` gives dedupe at *enqueue* time only.
- **Attempts are finite with nothing configured**, per [0074](0074.md)'s
  no-unbounded-wait posture. Backoff is exponential with jitter and a cap.
- **A job exhausting its attempts moves to the dead-letter table**, with its payload, every attempt's error
  and its timing. It is never deleted by the runtime. `Core\Queue::stats` reports dead-letter depth, and
  [0076](0076.md) exports it as a default series — an unwatched dead-letter table is
  the classic way a queue silently loses work.
- **A job exceeding its memory, CPU or time budget is a failed attempt**, reported as that rather than as an
  out-of-memory, and retried like any other failure. A fatal error follows
  `rule:errors/escalation-ladder`'s ladder with the job as the unit torn down.

### 7. Queued work and scheduled work are different, and here is the difference

| | `[[schedule]]` ([0073](0073.md)) | `Core\Queue` (this ADR) |
|---|---|---|
| Triggered by | a clock, from root-owned config | a program calling `push` |
| Declared by | the operator | the application |
| Durable | no — a missed tick is missed | yes — a row, until it succeeds or dead-letters |
| Retried | no | yes, bounded |
| Carries data | no | a payload |
| For | "every night at 03:00" | "because this request happened" |

A scheduled entry may of course `push`; that is the intended way to enqueue a nightly batch's worth of work.

### 8. No broker, and the seam that stays open

There is no Redis, NATS, SQS or AMQP backend, and no pluggable driver interface in v1. Adding one would mean
specifying and testing N backends, and — decisively — **transactional enqueue would stop being guaranteed**,
which is the whole reason for the design. The seam that stays open is the storage layer's internal boundary,
not a public interface: if a user genuinely outgrows a database-backed queue, the honest answer is that they
have outgrown what this ADR promises, and a broker-backed `Core\Queue` would be a new ADR that states which
guarantee it drops.

## Consequences

- **The queue's throughput is a database's throughput.** Thousands of jobs per second, bounded by write
  contention on one table. That is the ceiling, it is documented, and it is far above the target audience's
  need.
- **The queue adds write load to the application's primary database**, which is a real operational cost and
  the reason `[queue] connection` exists — while pointing it elsewhere gives up § 3.
- **`nvs queue migrate` is an operator step**, so a deployment has one more thing to get right. The
  alternative — implicit DDL from a running server — is worse in every way that matters here.
- **At-least-once forces idempotency onto application authors.** Exactly-once is not on offer from any
  honest system, and stating the guarantee in the ADR and the API documentation is the only real mitigation.
- **A job is a file, which makes it a compiled unit** — cached, hot-reloadable, traceable and coverable with
  no special case. The same payoff [0083](0083.md) gets from the same
  choice.
- **Three constructs now share one shape** — `spawn script`, a connection upgrade and a job all name an
  entry and take `with`-style options. The first two also accept a static method
  ([0006](0006.md)); a job does not, and the reason is the row: its target is
  stored as data and claimed by any host in the fleet, possibly after a redeploy, and a string in a table
  can hold a path but not a method reference. That consistency is worth more than any of the three individually,
  and a fourth thing that runs code should take the same shape or explain why not.

## Alternatives rejected

- **A pluggable driver interface from day one**, with a database driver and Redis/NATS alongside. More
  future-proof and better for high-throughput users. Rejected because it makes transactional enqueue a
  property of one driver rather than of the API, which is exactly the guarantee worth having, and because it
  multiplies the surface to specify and test at a scale nobody has yet asked for.
- **A runtime-owned durable log on disk.** Fastest, no external dependency, and it fits shared-nothing
  neatly. Rejected because it ties a job to one machine's disk — a second instance cannot see it, a
  rescheduled container loses it — and because durability would become ours to prove rather than the
  database's to provide.
- **`Core\Cache` as the store** ([0059](0059.md)). Rejected outright: that
  ADR requires it to be correct to find nothing there.
- **A job as a class implementing an interface**, discovered by
  [0061](0061.md)'s enumeration. Better ergonomics, and it is
  what `Web\Job` will provide on top. Rejected as the *Core* shape because a file is what the isolate
  machinery already takes, and because a class would need a rule for reconstructing an instance from a
  payload that [0071](0071.md) already gives for plain data.
- **Exactly-once delivery.** Rejected as undeliverable. Systems that claim it are describing at-least-once
  plus deduplication, which is what `key` provides at enqueue and what an idempotent job provides at
  execution.

## Revisiting

- **If a user is genuinely bounded by database write throughput**, § 8 is what changes, and the new ADR must
  state which guarantee the broker-backed path gives up.
- **If non-transactional enqueues turn out to be common in practice** — visible in `Core\Queue::stats` —
  that argues for making `push` on a foreign connection a compile-time warning, which needs the checker to
  know the queue's connection name at compile time.
- **If `key` dedupe proves insufficient** and applications ask for execution-time idempotency keys, that is
  a real gap and a candidate addition — not a change to the at-least-once guarantee.

## Verification

- **Transactional enqueue:** a transaction that pushes a job and then rolls back leaves no row in the jobs
  table; one that commits leaves exactly one. Asserted on every backend that supports it, and the SQLite
  single-writer path asserted separately.
- **Fleet safety:** N worker processes against one queue of M jobs run each job at least once and — absent
  an induced worker death — exactly once, asserted per backend with a counter table.
- **Visibility:** a worker killed mid-job leaves the job claimable again after the visibility timeout, and
  the second attempt sees `attempt == 2`.
- **Bounds:** a job that always fails lands in the dead-letter table after exactly `max_attempts`, with each
  attempt's error recorded, and is never deleted; backoff intervals grow and are capped.
- **Isolation:** a job isolate cannot see the enqueuing request's heap, statics or session; the state-bleed
  suite gains jobs as a parameterisation, as [0083](0083.md) does for
  connections.
- **Qualifiers:** pushing a `secret` fails to compile; a `tainted` payload field arrives `tainted` and fails
  to compile at a sink without laundering — both fixtures that would not compile if the rule were wrong.
- **Budgets:** a job exceeding its memory or CPU budget is recorded as a budget failure, retried, and never
  reported as an out-of-memory.
- **Observability:** queue depth, oldest-job age, failure rate and dead-letter depth appear as default
  series ([0076](0076.md)); a job appears in the timeline with the same event kinds
  [0041](0041.md) already emits for a spawn.
- **No implicit DDL:** a server started against a database with no queue tables refuses to run workers and
  names `nvs queue migrate`, rather than creating them.
