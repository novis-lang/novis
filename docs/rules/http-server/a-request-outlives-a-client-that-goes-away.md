A request whose client goes away runs to its end, under every limit it already has, and its response is thrown away; a method listed in `[limits] cancel_on_disconnect` is cancelled at the drop instead.

The case it answers: a request hangs on something slow and the user closes the tab. On a server that gives each request a worker process, that request holds the whole process until its time limit, and a handful of them empties the pool for every user at once — the cost that pushes such servers towards cancelling.

**Completion is the default for every method.** A user who refreshes, navigates away or submits twice abandons a request, so a disconnect is the everyday case; cancelling there stops a script between two writes that share no transaction, and leaves half-written data its author never planned for. The cost that argues for cancelling does not exist here: a request waiting on readiness is a parked coroutine (`rule:http-server/a-core-is-never-blocked-on-a-syscall`) costing a pooled stack rather than a worker, and its CPU, memory and output limits still bound it. **A detached request keeps its admission place until it ends** (`rule:http-server/admission-is-arithmetic-not-a-number`) — giving it back at the drop would let a client open, disconnect and repeat until a core runs unbounded work. Every write it makes to the response, buffered or streamed, succeeds at once and its bytes are discarded; nothing throws because the client left, and a streamed write does not park on a gone socket. A send timeout counts as the client having gone. A read of the request body after the drop fails as any failed read does. `Core\Sse` and a WebSocket are upgraded connections, not requests, and are outside this rule.

**The one bound it adds.** A request with a `wall_time` has that one limit, connected or not. A request without one — the default — is cancelled once `[limits] disconnect_grace` (default `30s`, finite, no unbounded spelling, `rule:http-server/an-unsafe-or-unbounded-default-is-a-defect`) has passed since the disconnect. `wall_time` is a `Runtime` key, so the deadline follows it: from the drop on, a request has exactly one of the two bounds and never neither. A graceful drain waits for a detached request as for an attached one, up to `drain_timeout`.

**A listed method is cancelled at the drop**: the connection lives on the reactor, so its drop is delivered like any other readiness, and the server cancels the request tree — `rule:concurrency/cancellation-runs-no-user-code`'s cancellation, delivered at the next safepoint, running native teardown and no user code, with a task inside a driver statement drained under `rule:concurrency/nothing-is-still-running-when-a-call-returns`. A request past its grace is cancelled the same way. Both keys are `System` keys a request cannot change, matched by exact, case-sensitive method name, and may be written in `[app.limits]` for one application. The method is the switch because it says whether stopping is safe: a `GET` or `HEAD` that writes nothing can stop, and a `POST` should not. `cancel_on_disconnect` defaults to `[]`; a name that is not an HTTP token, or a name listed twice, is refused at load naming the key, and any token is allowed, so a custom method can be listed. `disconnect_grace` refuses `false` and `0` as `[server]`'s waits do, and has no `[limits.hard]` ceiling because no request may set it. There is no runtime switch and no method that tells a script its client has gone.

After the response is on the wire, the connection's end means nothing to the request — the tree outlives it for exactly the work `rule:concurrency/after-response-outlives-the-connection` admits, which a detached request reaches as an attached one does.

- **Memory:** a detached request keeps its heap until it ends, reaches its `wall_time` or, with none, `disconnect_grace`: per request, O(in-flight), and under its own `memory` cap. A request whose client stays pays nothing.

**Declined:**

- **Cancellation at the drop as the default.** The everyday disconnect breaks data, and every application would need the same one line to turn it off.
- **Completion for every request with no opt-out.** A deployment serving expensive read-only searches loses nothing by stopping them, and wants the capacity back.
- **A switch per route or per request.** A route table is not a configuration concept, and a per-request switch is a runtime method this rule does not add.
- **A `Core` method like PHP's `ignore_user_abort()`.** Completion would be something each script must remember, which is the wrong default for the everyday case.
- **Giving the admission place back at the drop.** A disconnect loop becomes unbounded work on one core.
- **A grace on every detached request, `wall_time` or not.** One request would have two limits, and a long job would be cut short because its client left.
