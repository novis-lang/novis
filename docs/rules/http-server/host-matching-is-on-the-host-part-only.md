An absent `Host` on HTTP/1.1 is a `400`. A mount's `host` is compared against the host part only: the port is stripped, the value is ASCII-lowercased and one trailing dot is removed — three equivalences the relevant specifications define, so this is the *accept verbatim* branch of `rule:errors/ambiguous-input-refused` rather than a repair. Non-ASCII in `Host` is refused, and so are two `Host` lines; punycode matches literally. `Host: A.EXAMPLE.COM:8080.` matches the mount declared for `a.example.com`. The mount table holds a declared host in ASCII lower case for the same reason, so `host = "A.example.com"` and `host = "a.example.com"` are one key to the duplicate check and to an explicit mount's override, exactly as they are one name to a request.

The refusal is the door's, ahead of every mount and of the health probe (`nvs_server::mount::host_is_refused`, answered in `nvs serve`'s handler). The mount table refuses the same host again: a caller that skipped the door still matches no mount on it, and never falls through to the mounts that declare no host — which is what reading it as no host at all would do, handing the request to a tenant it did not name. HTTP/1.0 may leave `Host` out and reaches those host-less mounts.

**A target that carries its own authority names the host**, as RFC 9112 § 3.2.2 says: a target in absolute form (`GET http://a.example.com/`), and HTTP/2's `:authority`. A `Host` line beside it that names another host is a `400`, because a proxy that routed by one and this table by the other would choose different tenants. Both are folded as above before they are compared, so a port or a case difference is the same host.

A deployment that declares only host mounts gets a `404` for an unknown host, with no allowlist directive to remember — the failure Django had to add `ALLOWED_HOSTS` for. The forwarded walk never reaches this value: what a trusted proxy may assert is the client address and the scheme, and neither is read here.

The proxy note is on the reverse-proxy page of the website: nginx's `proxy_pass` sends `Host: $proxy_host` unless told otherwise, so a host-mounted deployment must set `proxy_set_header Host $host;` or every request arrives with the wrong name and lands on the fallback — silently.
