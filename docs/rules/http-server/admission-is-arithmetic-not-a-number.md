Admission counts the memory requests actually hold, because a memory limit is the most one request may hold and not what each request takes. A request is admitted while fewer than `max_in_flight` requests are in flight and the memory every core holds now, plus the per-request cap, fits under the memory budget less the engine's own reserve, so each admitted request has room to reach its own ceiling.

**What is counted.** Each core publishes its thread's live balance, plus the bytes it holds for cross-request stores, into one gauge of its own, and admission sums the gauges with relaxed loads. A core publishes when its balance has moved a mebibyte since its last publish, and at a request's start and end, so the allocation path gains one compare and no atomic, and the sum is stale by at most a mebibyte per core. A per-core sum is exact where a sum of per-request readings is not: one core runs several requests interleaved, and each request's reading includes the others' bytes. A child placed on another core is charged to that core's balance, so the sum counts it.

**A connection between requests is not counted.** An idle keep-alive connection keeps `hyper`'s buffers and the head of its next request, and enough of them would refuse every request while no request held anything. So once a connection's place goes back, what its tree holds above the balance its last request started at leaves the core's gauge at each of its parks, and the next request on it counts those bytes again. A tree with after-response work still running is counted whole, because that work is a request's. What an idle connection holds is bounded by `hyper`'s buffer size, and how many connections are open is the proxy's (`rule:http-server/two-deployments-and-nothing-a-proxy-owns`); no cap on open connections is added.

**The conditions.** The per-request cap is `[limits.hard] memory` where it is written, else `[limits] memory`, else the 128 MiB default (`rule:config/no-configuration-file-is-a-complete-configuration`), and the largest any mounted entry reaches. With `false` on the side that wins there is no cap, and a request is admitted while what the cores hold is under the room. A host that answers no budget leaves no memory condition, and `max_in_flight` alone bounds admission. The budget prefers a container's limit to the host's. With no request in flight a request is always admitted, so a server never refuses everything by arithmetic. The refusal is a fixed `503` with `Retry-After` and no body, taken before a mount is selected (`rule:http-server/max-in-flight-refuses-before-allocating`). A reload sets all three numbers from the snapshot it publishes, because the per-request cap is a `Reload` directive; requests already admitted keep their places.

**Growing past the room after admission.** Two requests admitted against the same headroom can both grow into it. The same room is the process's memory limit: when a core's publish takes the sum past it and a request is running on that core, that request is stopped with the memory error, through the same poll its own ceiling uses, and the message says the server's memory is full. Work with no request running is never stopped by it, because the engine's own bytes are what the reserve is for. This is the out-of-memory killer's job done one request at a time, with the process and every other request still running, which is tier A of `rule:http-server/a-requests-blast-radius-is-bounded-at-four-tiers` kept closed.

- **Memory:** one cache-line-padded gauge and five thread-local cells per core, and three words per request tree for what an idle connection sets aside.

**Declined:**
- **Dividing the budget by the per-request cap to get a count.** It assumed every request holds its whole cap, so a large host admitted only the budget over the cap and answered `503` to the rest while each waiting request held a few kilobytes. The cap bounds one request; the gauges bound the process.
- **Logging a clamp when `max_in_flight` exceeded the divided count.** With no division there is nothing to clamp, and `max_in_flight` and the memory condition are separate conditions that cannot disagree.
- **Summing each request's own reading.** One core runs several requests interleaved and nothing swaps the thread's balance per task, so each reading includes its neighbours' bytes and the sum counts them twice.
- **Charging each turn to a request or to a connection by a running sum.** A block allocated on one kind of turn and freed on the other moves the sum and never comes back, so it drifts with requests served. A tree's own excess over its base is dropped when the next request starts, so nothing outlives one request.
- **An atomic add per allocation.** It puts a shared read-modify-write on the allocation path to buy a freshness nothing needs: the stop at the limit covers the mebibyte of staleness.
