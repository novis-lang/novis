`nvs serve` binds every entry of `[server] listen` before it accepts anything, and then starts one worker per core, each holding its own handle on every one of those listeners — so a connection is accepted by whichever core reaches it first, rather than by one core that hands it on.

**`[server] workers` bounds the count, and the default is what the machine answers.** With the key left out the fan-out is [`std::thread::available_parallelism`](https://doc.rust-lang.org/std/thread/fn.available_parallelism.html), so a deployment moved onto a bigger box scales without a directive being edited, and a host that answers nothing at all is one core. A written count is the bound in **both** directions: it is neither raised to the machine's parallelism nor clamped down to it, because a core count a heuristic chose is one the file cannot state, and an operator who sized a container against its CPU quota has already answered the question. `0` is refused under `E0636` — every listener is accepted on by a worker, so a count of zero binds the addresses the tree names and then answers nobody on any of them, which is `rule:http-server/the-server-block-is-boot-class`'s empty `listen` array reached from the other end. There is no `auto` spelling: leaving the key out is what asks for the machine's own answer.

**What the cores share is compiled program text and the memory cache tier, and nothing else.** Every mounted entry is compiled before the first socket is bound (one that does not compile is kept and fails its own requests, `rule:http-server/a-mount-table-expands-at-boot`), published once behind an `Arc` that every core reads, so the compile count is one per distinct source rather than one per core — `rule:security/isolate-shares-nothing`'s "shares immutable compiled code", and the same single publisher an edit revalidates through (`rule:config/an-edit-reaches-the-next-request-without-a-restart`). Beside it stands the one mutable thing: the map behind `Core\Cache::memory()`, created before the first core accepts, read and written by every one of them, sharded behind locks and bounded by `[cache.memory] max_size` (`rule:concurrency/the-memory-tier-is-one-store-per-process`). Everything else a core holds is its own: its scheduler, its run queue, its accept loop and the backoff that loop applies (`rule:http-server/the-accept-loop-backs-off`), which is what `rule:http-server/admission-is-arithmetic-not-a-number`'s relaxed in-flight counter and `rule:http-server/a-wedged-core-is-detected-by-its-deadline`'s per-worker watchdog are already written against.

**A listener the server cannot bind is refused once, before any core starts.** The classification of a `listen` entry belongs to the configuration and not to a core (`rule:http-server/a-unix-socket-listener`), so one deployment mistake is one refusal — a fan-out that bound as it started would report the same wrong entry once per core and would leave a process half-listening while it did.

**Each core accepts on its own handle, so no connection passes through a thread every other connection also passes through.** The kernel picks which blocked acceptor a connection wakes: there is no handoff, no shared queue and no accepting core to become the bottleneck the fan-out exists to remove. A request stays on the core that accepted it.

- **Memory:** one scheduler, one accept loop and one listener handle per listener per core, all paid at process start and O(cores) rather than O(requests served). The shared compiled unit holds strictly less than a compiled unit per core would, so the fleet's compiled-code footprint does not grow with the core count.

**Declined:**
- **One acceptor handing connections to N request workers.** The acceptor is one thread paying a syscall and a handoff per connection, which moves the bottleneck rather than removing it.
- **One process per core, as php-fpm runs.** N processes compile every source N times, hold N caches and split one memory budget N ways; the built-in server is one process with one budget and one compiled unit.
- **A compiled-unit cache per core.** It costs N compiles of the same file, and "compile exactly once" would mean something different at four cores than at one.
- **Clamping `workers` to the machine's parallelism.** The count is already bounded by the file, a container's CPU quota is in general invisible from inside the process, and a directive silently overridden is a value the file cannot state.
- **An `auto` value for `workers`.** A second way to write the default is a second thing to explain; leaving the key out already asks the machine.
- **Reading the core count from the environment.** The configuration is the one place a deployment is stated, and a second input for one number would be the first exception.
