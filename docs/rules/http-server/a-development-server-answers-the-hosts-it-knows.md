**In development, a request from a loopback address must name a host this server knows in `Host`:** `localhost`, a name under `.localhost`, a loopback address, a host a `[[server.mount]]` lists, or an entry of `[server] development_hosts`. Any other host reaches no mount and is answered `421 Misdirected Request` before step 1 of `rule:http-server/a-request-resolves-in-five-steps`. Only the health probe still answers at its path. That closes DNS rebinding, where a web page makes its own name resolve to `127.0.0.1` and the browser sends that name to a server on this machine.

**Who is asked.** The peer is the socket peer, whatever `X-Forwarded-For` says the client is. A loopback peer is asked even when it is a trusted proxy that forwards another address, because a local proxy serves a browser on this machine whatever it writes in that header. A request from another machine is not asked, so a development server on `0.0.0.0` still answers its network address. A request over a Unix socket is not asked. Production never asks: the mode is `[mode] default` as the tree states it, so a reload that flips the mode turns the guard on or off for the next request.

**`[server] development_hosts`** lists the extra hosts, for a local proxy that sends its own name. Each entry is a host name or an IP address, an IPv6 one in brackets, compared exactly with the folded `Host`: ASCII lower case, no trailing `.`, no port. An entry with a scheme, a port, a wildcard, a path or a space is `E0663` at boot and at reload, because an entry that can never equal a `Host` is a proxy an operator believes is let in. The key is checked in production too, so a tree a reload flips to development cannot carry one. It is `System` and reloads with the `[server]` block.

**The refusal says what to do.** The `421` has a one-line `text/plain` body that names `[server] development_hosts` and the host to add, so the person at the browser can fix the setup. The host is the one the request sent, so a rebinding page learns nothing from the body. Its access line is a `Warn`, written whatever `[log] access` says, with a `host` field and a message that names the key. The `Warn` is written once per host per minute, so a page that retries cannot fill the log, and a repeat is an ordinary access line. A control character in the host is written escaped in the body and the message. `421` and not the table's `404`, because a `404` looks exactly like a mount that does not exist and the server looks broken behind a proxy that works.

- **Memory:** the list, once per configuration tree, and one copy of the refused host and its body per refused request, freed with its response. The hosts warned in the last minute, at most 64 per process. Nothing per accepted request.

**Declined:**

- **A wildcard or suffix entry.** One entry would let in every name under a domain the operator does not control the DNS of, which is the rebinding the guard exists to close. A proxy sends a fixed list of names.
- **Turning the guard off with a switch.** A list states what is let in; a switch lets in every page on the web.
- **Trusting any host a trusted proxy sends.** A local proxy with a catch-all server block forwards a rebinding page's host as readily as its own.
- **The table's `404`.** It is indistinguishable from a missing mount, so a correct proxy setup reads as a broken server.
- **A bodiless `421`.** The person at the browser saw an empty page and had to find the log line. The body names only the host the request sent and a key name, which a rebinding page already knows.
- **Asking the client address after the forwarded walk.** A local proxy listed in `trusted_proxies` forwards a rebinding page's request with the browser's address, so the guard never saw it.
