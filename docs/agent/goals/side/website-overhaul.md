# Side goal — the website is four areas a newcomer can follow, and cannot go stale

When this goal is green, the website's top navigation is **Guides · Syntax · Reference · In-Depth**,
then an **Install** button and **Sponsoring**. "Docs", "Why Novis?", the rulebook, the decision list,
the claims and the prev/next buttons are gone. Every page reads in plain, simple English. Every code
block on the site is a real file that CI runs. Every handwritten page names the features it explains,
so a change to one of those features cannot land without that page being reviewed in the same session.

## Why a side goal

Nothing on the chain waits for it, and it opens almost no file a chain goal opens: `website/`, a new
`tools/nv/cmd/site.ts`, one gate in `tools/nv/cmd/session.ts`, `apps/notes/`, one CI step and one
section of `AGENTS.md`. It is a large, mostly prose job that a run can do alone. The user asked for it
to run as one side goal that merges into `main` when it is done, with no review stop in between
(2026-10-03).

## Stage 2 — the structure and the stale guard (the keystone)

**Does:** Builds the four-area site skeleton, removes what is retired, and makes staleness a checked
failure, not something a person has to notice.

File set: `AGENTS.md`, `website/astro.config.ts`, `website/src/components/{Header,Footer}.astro`,
`website/package.json`, `website/scripts/`, `tools/nv/cmd/site.ts` (new), `tools/nv/main.ts`,
`tools/nv/renderers/index.ts`, `tools/nv/cmd/session.ts`, `.github/workflows/{ci,pages}.yml`.

- **The plain-English rule is widened first**, so everything written after it follows it.
  `AGENTS.md` § *Text an end user reads* now covers **everything a user sees**: every website page,
  every `about.md`, every comment in a published `.nvs`, CLI `--help` text and diagnostic messages.
  The internal docs that only agents read (rules, decisions, goals, AGENTS.md itself) stay out of it.
  The section's opening says this scope, and the rest of the section stays as it is. Existing CLI help
  and diagnostics are not swept by this goal. The rule applies to what is written from now on.
- **Navigation.** The top nav is Guides, Syntax, Reference, In-Depth, then Install (styled as a
  button), then Sponsoring. Each of the four areas shows its subtitle in smaller text on a second
  line, without brackets: Guides — "Examples, how to use"; Syntax — "How to write Novis";
  Reference — "Classes and functions"; In-Depth — "Decisions, ideas". Each area has its own sidebar.
  URLs: `/guides/`, `/syntax/`, `/reference/`, `/in-depth/`, `/install/`.
- **Removed:** the rulebook pages and `rules.json`, `decisions.mdx` + `DecisionSummary` +
  `decisions.json`, `why-novis.mdx` + `WhyClaims` + `src/content/claims/`, the `docs/` tree as a URL
  space, `site-index.mdx` if nothing links it, and `<Pagination/>` from the footer. Their generators go
  too: `websiteRules` leaves both renderer lists, `nv decisions --render` stops writing website JSON,
  and `sync:decisions` leaves `package.json`. `docs/decisions.md` and `nv decisions --check` stay,
  because they serve the repo and not the site. **No redirects:** the site was never public, so no
  old URL needs to keep working, and a removed page simply stops existing.
- **Examples are read in place.** The site reads `docs/examples/**` directly at build time (an Astro
  content loader, or a Vite glob with `server.fs.allow` widened to the repo root). The mirror
  directory, `sync-examples.mjs` and its `.gitignore` line are deleted. A CI Pages build then shows
  every example without a sync step.
- **Snippets.** A handwritten page has **no inline Novis code fence**. Every code block is a
  `<Snippet src="…"/>` that includes `website/snippets/<area>/<page>/NN-slug.nvs` and shows its sibling
  `.out` as the result. Snippets follow the same comment rule as examples. Shell commands
  (`nvs serve`, `git clone`) are not Novis code and stay as ordinary fences.
- **The stale guard: `bun nv site`.** One tool, module doc as its home:
  - Every handwritten page's front matter has `covers:`, a list of feature ids from the proofs roster
    (`Core\Str::length`, `lang/statements/match`, `config/server-dispatch`, …). A page that explains
    no specific feature (a manifesto page) writes `covers: []`.
  - `website/site.lock.json` stores, per page, a hash of each covered feature: its registry card or
    reference section, its `about.md` and its examples. `bun nv site --stamp <page>` writes the
    current hashes after a person or agent has reread the page against the feature.
  - `bun nv site --stale` lists **broken** ids (a covered feature no longer exists), **stale** pages
    (a covered feature's hash changed since the stamp) and **uncovered** features (a `lang/` or
    `types/` feature that no Syntax page covers).
  - `bun nv site --check [part]` runs one or all parts and prints `site <part>: ok` per part that
    passes. A failing part lists its problems and exits non-zero. Parts: `structure`, `snippets`,
    `stale`, `reference`, `syntax`, `guides`, `in-depth`, `apps`, `prose`. Each stage below says what
    its part asserts. `structure` asserts the nav order above, no `<Pagination/>`, no removed page,
    and no redirect entry in the Astro config. `snippets` runs every snippet through `nvs` and diffs it against `.out`, and
    fails on any inline Novis fence in a handwritten page. `stale` fails on any broken id or stale
    page. `prose` applies the three countable bounds that `bun nv proofs --comments` applies (lines
    in a block, words in a sentence, a dash joining two sentences) to the prose of every handwritten
    page. Passing it says nothing about plainness, as for comments.
  - `bun nv site --build` runs the Astro build and prints `site: built` on success.
- **The wrap gate.** `nv session --wrap` refuses while `bun nv site --stale` reports a broken id or a
  stale page whose feature this slice changed. The session that changes a feature rereads the pages
  that cover it, fixes them and re-stamps them, in the same way it owes feature proofs. CI runs
  `bun nv site --check` in the job that already has a built `nvs` (the one that runs
  `bun nv proofs --verify`, `ci.yml:293`). `pages.yml` stays build-only.
- **Tests** for `site.ts` live beside the other `tools/nv` tests: a renamed id is broken, a changed
  `about.md` makes its page stale, a re-stamp clears it, and a `lang/` feature with no covering page is
  uncovered.

## Stage 3 — Reference, generated and complete

**Does:** Makes Reference a generated lookup of every Core class, every configuration key and every
CLI command, with its examples, and with no empty heading anywhere.

File set: `website/src/pages/reference/` (or a content loader), `website/src/components/Method*.astro`,
`website/src/lib/core.ts`, `tools/nv/renderers/website-core.ts`, `docs/examples/**/about.md`.

- **Generated, never edited by hand.** One dynamic route renders every member from `core.json` plus
  the feature's `about.md` and examples. The 325 per-member `.mdx` files are deleted. The handwritten
  prose on the 11 non-draft pages moves into that member's `about.md` (or its registry card, for
  errors) before its `.mdx` goes, so nothing written is lost.
- **Three sub-areas** in the sidebar: Core classes (by class, then member), Configuration (one page
  per `nvs.toml` block, keys from `docs/examples/config/` and `docs/reference/tools/20-config.md`),
  CLI commands (one page per command, from `docs/examples/tools/` and `docs/reference/tools/10-cli.md`).
- **Every example is shown.** All of a feature's examples appear with their output, nested classes
  included (`Time-Date/at` is `Core\Time\Date::at`). The lookup goes through the proofs roster's
  feature id, never through a path split by hand.
- **A heading with nothing under it is not rendered.** That covers Errors, Return value, Parameters,
  Related, Changelog and Examples. The string "Not documented yet" appears nowhere in the built site.
- **Related.** `about.md` may end with one line `related: Core\Bytes::length, Core\Str::graphemes`.
  The generator removes that line from the prose, renders the list as links, and fails the build on an
  id that does not exist. A member without the line shows no Related section. The goal writes
  `related:` lines where a reader would clearly want the link (siblings with a real difference to
  explain, like `Str::length` and `Bytes::length`). It does not write one for every member.
- **`--check reference`** asserts: every Core, config and CLI feature in the roster has a page; the
  built site contains no "Not documented yet"; every feature with examples shows all of them; every
  `related:` id resolves; and `core.json` is current against the binary when one is built.

## Stage 4 — Syntax

**Does:** Explains how to write Novis, from the first line to the special syntax, with a runnable
example and a best practice on every page.

File set: `website/src/content/docs/syntax/**`, `website/snippets/syntax/**`, read against
`docs/reference/lang/*.md` and `docs/examples/{lang,types}/`.

- **The outline the user approved (2026-10-03):** Start here · Basics (files and statements, comments
  and doc comments, variables and `var`, constants) · Values and types (numbers, strings and
  interpolation, bool and null, arrays and `array<T>`, nullable `?T`, union types, enums, converting
  with `as`, type tests with `is`) · Operators (arithmetic, comparison, `??` and `??=`, string
  operators, precedence) · Control flow (if, match, loops and foreach, break and continue) · Functions
  (declaring, parameters and defaults, named arguments, `inout`, closures and callables, generics) ·
  Classes and objects (classes, properties, interfaces, static, attributes) · Errors (throw and catch,
  error types, checked returns) · Programs and files (namespaces and `use`, require, paths, entry
  points for CLI and web) · Special syntax (html literals, routes and mounts, tests in code). The
  outline is a draft of headings. A heading Novis does not have is dropped, and every `lang/` chapter
  the outline misses (concurrency, for one) gets a page, so `--check syntax` reports 0 uncovered.
- **Every page** shows the short, convenient way first, then the longer, more flexible way where one
  exists, under "Use this when…". It ends with a short **Do / Don't** list. Every page has at least one
  snippet.
- **PHP is named on "Start here" only**: Novis's syntax is inspired by PHP, so much of it will look
  familiar, and the page lists what is new or different. No other Syntax page mentions PHP.
- **`--check syntax`** asserts: every `lang/` and `types/` feature in the roster is covered by at least
  one Syntax page; every Syntax page has `covers:`, at least one snippet, and a Do / Don't section.

## Stage 5 — Install and Guides

**Does:** Gives a newcomer the reasons to pick Novis, a path from install to a running app, and the
habits that make Novis code fit together.

File set: `website/src/content/docs/{install,guides}/**`, `website/snippets/guides/**`, `apps/notes/`.

- **Install** (`/install/`): install on each platform (from `docs/reference/tools/15-install.md`),
  Hello world, the editor extension, and a "next: the Tour" link.
- **Guides**, in this sidebar order:
  1. **Why people pick Novis** — the standout features: a curated list of what Novis does better than
     other languages or that no other language does (security, language design, simplicity,
     performance). One short page each, with a snippet and a link into Syntax or Reference. The run
     drafts 10–14 candidates from the retired claims, the In-Depth concepts and the feature proofs.
     The user curates the final list when the goal lands.
  2. **A Tour of Novis** — about 10 short steps from Hello world to a running web app, each step
     building on the last.
  3. **Simple programs** — complete one-file programs a user would really write (a CLI tool that reads
     a CSV and prints a report, a JSON API in one file, a file watcher, a small scraper, a form handler,
     a scheduled job). At least six. Each is one snippet with its output and a short walk-through.
  4. **How to use Novis** — how the pieces fit together: project layout, configuration, request
     handling, errors, tainted input, limits. Best practices, and a Do / Don't list on each page.
  5. **Cookbook** — short task pages: read a JSON body, validate a form, page through database rows,
     upload a file, call an HTTP API, schedule a job, send a signed URL. At least ten. One task, one
     snippet, one result.
  6. **Testing your app** — `nvs test`, test doubles, coverage reports, testing a route without a
     server.
  7. **Going to production** — run as a service on Linux and Windows, Docker, behind a reverse proxy,
     TLS, limits, logs, and a short security checklist.
  8. **Example apps** — one for now: **Notes**. The app lives in `apps/notes/`: SQLite,
     server-rendered HTML with html literals, a small JSON API, form validation, and tests. Its page
     shows the commands to get it running (a sparse `git clone` of `apps/notes`, `cd`, `nvs serve`,
     `nvs test`), what each file does, and how to start a new app from it.
- **`--check guides`** asserts the eight sections exist, each has at least one page, every Simple
  program and Cookbook page has a snippet, and the counts above are met. **`--check apps`** runs
  `nvs test` over every app under `apps/` and boots each with `nvs serve` long enough to get a `200`
  from `/`.

- **Home page** rewritten: a short hero, one runnable snippet, the 4–6 strongest standout features
  (each linking to its Guides page), four cards for the four areas, and the Install button. The old
  claims are removed.
- **`--check in-depth`** asserts the eight sections exist and each has a page. **`structure`** now also
  asserts that no page links to a URL the site does not build.
- **The whole site is then read once against `AGENTS.md` § *Text an end user reads*** by a subagent
  that did not write it. Every page it flags is rewritten from what it means to say, never trimmed until

## Standing decisions

These are the user's calls, made on 2026-10-03, unless marked as mine. No session re-decides one.

- **Four areas, in learning order:** Guides, Syntax, Reference, In-Depth, with subtitles on a second
  smaller line. "Docs" and "Why Novis?" are removed.
- **Install is its own top-nav button**, not a Guides section. Release notes go to the footer and to
  In-Depth's "What changed".
- **Staleness is a wrap gate, like feature proofs.** A removed or renamed id and a broken snippet fail
  CI. A changed feature makes the session that changed it review and re-stamp the pages that cover it.
- **Reference is generated, never edited by hand**, and covers Core classes, Configuration and CLI
  commands. `types/` and `lang/` feed Syntax.
- **Related links are explicit**, one `related:` line in `about.md`, checked at build. No automatic
  fallback.
- **No heading without content.** Every "Not documented yet" goes.
- **Syntax uses the outline above.** PHP is named once, on "Start here".
- **Guides gets the user's four kinds plus four more**: Cookbook, A Tour of Novis, Going to production,
  Testing your app.
- **The first example app is Notes**, in `apps/notes/` in this repo, tested in CI. It is fetched with
  `git clone`. The user declined an `nvs new <template>` command.
- **In-Depth is organised by reader question.**
- **The home page is rewritten.**
- **The plain-English rule covers everything a user sees**, and internal docs stay out of it.
- **No review stop.** The run goes straight to `SIDE GOAL GREEN`, and the user reviews everything,
  including the standout-feature list, before it lands.
- **No redirects for removed URLs.** The site was never public, so nothing outside links to it.
- **Mine, 2026-10-03:** examples are read in place, not mirrored; snippets live under
  `website/snippets/`; `covers:` uses the proofs roster's feature ids; one `site.ts` with parts in
  place of several tools.
- **ADR slot: one.** The website's structure and its stale guard are one decision record, written by
  the stage-2 session. Take the next free number right before writing it, because the chain run takes
  numbers too.
- **The tradeoffs, stated once.** Runtime performance and memory: none, because nothing here touches
  `nvs`. The site build grows to roughly 1,200 Reference pages, which costs build time in CI's Pages
  job. Developers using Novis get a site they can follow and code that is known to run. Contributors
  get one more wrap gate: a change to a feature costs a reread of the pages that cover it. That cost is
  the point.
- **Every comment in a new `.nvs` snippet, every new or changed `about.md` and every website page
  follows `AGENTS.md` § *Text an end user reads* at the first write.**
