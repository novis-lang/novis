<Lead>
  An isolated script is another file you run as a **job**. It gets its own memory, its own variables
  and only the permissions you give it. If it crashes, loops forever, or eats all its memory, that
  job ends — and your code carries on at the next line.
</Lead>

## Quick start

Run a file. Wait for it. Check whether it worked.

```nvs
<?nvs
$job = spawn script 'jobs/report.nvs';

$result = await $job;

if ($result->ok) {
    echo "the report is ready";
} else {
    echo "the report failed: " . $result->error->message;
}
```

Two things happened here that are worth naming straight away.

The job ran **inside this same process** — nothing was started, no other program
was launched. And the job could not see a single one of your variables. It began
with an empty world.

The file it ran is an ordinary Novis script. It reads what it was given and
answers with `return`:

```nvs
<?nvs
use Core\Script;

mixed $month = Script::args()['month'];

return ['rows' => Reports::build($month)];
```

<Aside type="note" title="This syntax is not final">
Novis is pre-alpha. The behaviour on this page is decided; the exact spelling of
`spawn script … with(…)` is still being pinned down. If it changes, this page
changes with it.
</Aside>

## Giving the job something to work with

A job that starts with nothing needs to be handed what it needs. Four things can
be passed at the spawn site, and none of them are required:

```nvs
<?nvs
$job = spawn script 'jobs/report.nvs' with(
    args:   ['month' => 7],                     // values, copied in
    limits: ['memory' => '256M', 'cpu_time' => '10s'],
    grants: ['fs.read' => '/srv/www/data'],     // narrowing only
    output: 'capture',                          // or 'inherit'
);
```

- **`args`** are ordinary values. They are copied into the job, so the job
  cannot change yours.
- **`limits`** are a ceiling for this job. They can only make things *tighter*
  than what the request already has.
- **`grants`** are permissions. They can only ever *remove* permissions the
  caller already had — never add.
- **`output`** decides what happens to anything the job prints. See
  [Output](#output) below.

## What the job can and cannot see

This is the whole mental model, and it is worth reading once properly.

| | Shared with the caller? |
|---|---|
| Compiled machine code | **Yes** — it cannot be modified, so sharing it is safe. Ten thousand jobs running one file compile it once. |
| The resource budget | **Yes**, deliberately. See [Budgets](#budgets-belong-to-the-request-not-the-job). |
| Memory, variables, objects | No. Its own, released completely when it ends. |
| Globals, class statics, constants defined at run time | No. Fresh. |
| Request, server and session state | No — and reaching for them inside a job **throws**, rather than quietly handing back the caller's data or an empty result. |
| Anything printed | No. Captured separately by default. |
| Open files, sockets, database connections | No, and they cannot be passed in. |
| Configuration | Derived, not shared: the job gets a copy of the caller's settings, which the spawn may tighten. |
| Loaded files and autoloading | No. It resolves its own. |
| Cancellation | Linked: the job is a child, so it dies when its parent does. |

The row people trip on is the last-but-four. **You cannot hand a job an open
database connection or an open file.** Pass what identifies the thing instead —
a connection string, a path, a credential reference — and let the job open its
own.

That is not a limitation to work around. It is the point: a job that cannot
inherit your handles cannot use them.

## When the job fails

A failure in the job is **data on the result**, never an exception thrown into
your code. Your `await` always returns; it is the result that says what happened.

| What happened in the job | What you get |
|---|---|
| It returned a value | `ok` is `true`, `value` holds a copy of it |
| It threw and nothing caught it | `ok` is `false`, `error` carries the class name, message, code and rendered trace — as copied data, not the exception object |
| It ran out of memory, CPU or time | `ok` is `false`, `error->limit` names the setting it hit |
| It hit a contained runtime fault | `ok` is `false`, and your code keeps running |
| The caller was cancelled or timed out | The job is stopped, its memory released, nothing left behind |

If you would rather have the exception, ask for it explicitly:

```nvs
<?nvs
$rows = (await spawn script 'jobs/report.nvs')->valueOrThrow();
```

The error that raises names the job, not the line you wrote — because your line
never ran the job's code.

## In depth

Everything below is the complete behaviour. You do not need it to use the
feature, and you will want it the first time something surprises you.

### Permission to run code is its own permission

Being allowed to *read* a file is not permission to *run* it. Spawning requires
a separate grant naming the directories code may be executed from:

```toml
[capabilities]
script.spawn = ["/srv/www/jobs", "/srv/www/app/tasks"]
```

The path you spawn is resolved to its real location and then checked against
those roots — so `../../etc/something` cannot escape by construction, rather
than by somebody writing a validation function correctly.

A computed path is allowed, because a queue worker needs one. It can still only
ever land inside a root the operator wrote down.

A job's permissions are the caller's permissions, optionally narrowed. Nothing
widens. A request that has already given up network access cannot get it back
by spawning a job.

### Budgets belong to the request, not the job

A request and everything it spawns are **one tree**, and every limit is counted
against the root of that tree.

A job does not get a fresh allowance on top of yours. It spends yours. So a
request that spawns fifty jobs does not get fifty times the memory ceiling — it
gets one ceiling, to divide among fifty.

That has three consequences worth stating plainly:

- The worst case for the whole process is unchanged by jobs: in-flight requests
  multiplied by the hard limit, exactly as it was before.
- `limits:` at the spawn site is a **sub-cap**. It can be tighter than what
  remains. It cannot be wider.
- Child tasks count against the root's task limit, child output against the
  root's output limit, child CPU against the root's CPU time. A runaway that
  spawns jobs that spawn jobs is bounded by arithmetic, not by a heuristic — and
  nesting has its own ceiling (`max_script_depth`, eight by default) so that
  runaway recursion is diagnosed as recursion instead of as a memory failure.

**What a job costs while it runs:** one 64 KiB task stack, committed lazily,
plus its own memory arena held to its peak until the job ends. Concurrent jobs
each hold their own, so a tree's peak is the sum across the jobs alive at once —
under the root's cap, per the paragraph above.

When a job ends, its arena is released whole. Nothing is retained. A long-running
command-line program gains a way to reclaim a leaky job's memory that it did not
have before.

### How values cross the boundary

Arguments going in and the result coming out are **deep-copied**, or moved when
nothing else refers to them. These are the same rules used when sending values
to another CPU core, deliberately: two boundaries with two sets of rules would
be two things to learn and two things to keep correct.

- The copy follows the **object graph**, not a tree. Shared structure stays
  shared, and cycles terminate — so a value that refers to itself crosses
  instead of hanging.
- **Three kinds of value cannot cross at all**: closures, by-reference (`inout`)
  bindings, and objects holding a live handle such as an open file or socket. A
  closure captures a heap and a scope; an `inout` binding is an alias; a handle
  is owned by this process. None of the three means anything in another memory
  space.
- An object whose class the receiving side cannot find is **refused, with a
  diagnostic naming the class**. It is not degraded into a placeholder object
  that fails later, somewhere further from the cause.

### Output

By default, anything the job prints is **captured** and handed back on the
result, charged against the request's output limit.

`output: 'inherit'` appends it to the caller's output instead, at the moment the
result is awaited — which keeps the ordering predictable when several jobs run
at once.

Capture is the default because the alternative silently mixes another script's
bytes into a response you are responsible for.

A job's output carries the same kind as the caller's output stream — page markup
under a web request, terminal text on the command line — so a caller can re-emit
a captured result without escaping it a second time.

### It is the same machinery that serves a request

There is one isolation implementation, not two. **An inbound HTTP request is
itself the root job of its own tree.** The server path and the `spawn script`
path are the same code.

That is worth knowing for two reasons. It is why jobs are cheap: nothing extra
was built for them. And it is why the isolation is trustworthy: it is the same
boundary that already separates one visitor's request from another's, exercised
on every request your server handles.

### Where it sits among the other spawn forms

`spawn script` is one of three, and they compose rather than compete:

| Form | Runs where | Sees the caller's memory |
|---|---|---|
| `spawn` | This core | Yes — same heap |
| `spawn worker` | Another core | No — values are copied |
| `spawn script` | This core, or another with `on: 'worker'` | No — fresh heap, fresh globals |

All three are awaited the same way and all three die with their parent.
