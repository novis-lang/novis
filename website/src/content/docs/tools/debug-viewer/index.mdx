The debug viewer is a page in your browser. It shows the requests that your server recorded. For each
request, you see its status, its duration, its queries and its log lines. You also see the values it
dumped: the values it printed for debugging with `Core\Debug::dump`. Other pages show
totals for each route and for each query.

`nvs debug` serves the viewer. It also reads the recorded requests into one database,
`debug/index.sqlite` in the data folder. This is a SQLite database, which is one file.

## Start the viewer

Turn on recording in `nvs.toml`:

```toml
[debug]
store = true
```

Then start your server with `nvs serve` in development mode. `nvs serve` starts `nvs debug` for you, and stops it when the
server stops. With this setting, `nvs run` and `nvs test` are recorded too.

`nvs debug` prints a link to the viewer. Open the viewer with this link. The link contains a token,
which is a long random text. The viewer opens only in a browser that has the token. Another user
account on the same computer does not have it.

`nvs debug link` prints the same link again, and it starts nothing:

```sh
nvs debug link
```

With `--json`, it prints one JSON object with four fields:

- `url`: the link to the viewer.
- `embed`: the link that an editor shows inside its own window.
- `running`: `true` when `nvs debug` runs.
- `recording`: `true` when `[debug] store` is on.

The address is `127.0.0.1:8137`. `[debug] listen` or the `--listen` option sets another address.

A production server never starts `nvs debug`. On a production host, you run `nvs debug` yourself.
Then it shows the requests that the production server recorded.

## The viewer's window

A list on the left names the pages: **Requests**, **Runs**, **Routes**, **Queries**, **Errors**,
**Logs**, **Mail** and **Stream**. **Settings** is at the bottom of this list. **Errors** shows a number. It
is the number of exceptions that were thrown after you opened the viewer. In a narrow window, the
list shows only its icons.

The bar at the top has the search box, the live state and the theme button. The live state shows
the text **Live** when `nvs serve` started `nvs debug`. It shows **Recording stopped** when `nvs debug` runs
without a server. The theme button changes between the system's theme, dark and light.

Press `Ctrl+K` (`Cmd+K` on macOS) to open a list of every page and action. Type a few letters to
find one. Press `?` to see every key.

Every `file:line` in the viewer is a link. It opens the file in your editor. Choose the editor on
the **Settings** page. In VS Code, the Novis extension can show the viewer in an editor tab. Read
[The debug viewer in the editor](/tools/editor/#the-debug-viewer-in-the-editor).

## The request list

The first page lists the requests, newest first. Each row has the method, the route, the status,
the duration, the number of queries and dumps, and the exception the request threw. A dump is a
value that the request printed with `Core\Debug::dump`. The route is the path of its
`#[Core\Route]`, such as `/notes/{id}`.

<Shot src="tools/debug-viewer/requests.shot" alt="The request list with 9 requests. The newest, POST /polls with status 303, has 12 queries and a 5× badge. The pane on the right shows its timeline." />

A bar in each row shows how the request's time was split. Each colour is one kind of work: queries,
HTTP calls, the cache, the session, files, garbage collection and processes. Garbage collection is
the time Novis spends to free memory that the program no longer uses. The gray part of the bar shows
the time that your own code ran. A badge such as `5×` means that one query ran five times at the
same line of your code.

The filters above the list choose the method, the status, the route, a minimum duration, and
whether the request threw an exception. A status filter can be one code, such as `404`, or a class,
such as `5xx`. The filters are part of the page's link. Press `s` to save the filters under a name.

Three boxes above the list show the last five minutes. They show the number of requests, the median
duration (p50) and the share of requests that failed. The median is the middle value: half of the
requests were faster, and half were slower.

New rows appear at the top while you watch. To pause the list, press `p` or scroll down. While
it is paused, the rows on the page do not move. A number shows how many new rows arrived.

Press `j` and `k` to move the selection. A panel beside the list shows the selected request's
events. Press `Enter` to open the request.

## A request's page

When you open a request, you see its method, path, status, duration and route. You also see its
trace id and span id. The trace id is a unique id that Novis gives each request. The span id is the
id of this request's own part of the work.

You also see the handler: the method in your code that
the route called. Boxes show the duration and the number of queries, dumps and log lines. Below
them, a bar shows how the time was split.

Two more boxes show the memory and the sizes. **Memory peak** is the most memory the request used.
Beside it is the memory limit, which `[limits] memory` in `nvs.toml` sets. The bar under the
memory peak turns orange at 75% of the limit, and red at 90%.

**Response size** is the number of bytes in the response body. It also shows how many bytes of the
request body your program read. A streamed response is sent in parts while your program runs. The
viewer shows no size for it.

The tabs below show one part of the request each. The tab is part of the page's link, such as
`?tab=queries`.

| Tab | What it shows |
|---|---|
| **Timeline** | every event of the request on one time axis: queries, HTTP calls, cache, files, processes and dumps |
| **Request** | the method, the path, the query, the headers and the body that your server received |
| **Response** | the status, the headers and the body that your server sent |
| **Queries** | each query, grouped by the line that ran it, with how often it ran there |
| **Cache** | each cache key, with its calls, hits and misses |
| **Dumps** | each value that `Core\Debug::dump` wrote |
| **Logs** | the request's log lines |
| **Coverage** | which lines of your code ran, when the server ran with `[debug] mode = ["coverage"]` |
| **Exception** | the exception and its stack, when the request threw one |

Each event on the timeline shows its result after its name:

- A cache read shows **Hit** or **Miss**, and the store: `memory` or `redis`.
- An HTTP call shows its status code and the bytes it sent and received.
- A file read or write shows its number of bytes.
- A process shows the name of its program and its exit code.
- Sent mail shows the number of recipients. The timeline shows no address and no text.
- A job pushed to the queue shows its script, its queue and its delay.

The **Exception** tab shows the stack: every function that was running when the exception was
thrown, the innermost first. The functions of your own code are in bold text. The functions of
`Core` are in gray text. An exception can have a `previous` exception: the exception that caused
it. The tab shows the previous exception below the first one, with its own stack. The stack never
contains the values of arguments, because a value can be a secret.

<Shot src="tools/debug-viewer/timeline.shot" alt="The page of a GET request to / with status 200. Its timeline shows two queries, and the bar splits the time between the database and your code." />

The **Request** and **Response** tabs show the headers as a table. A JSON body is shown as a tree,
and any other body as text. An HTML body is shown as text too, so it never runs in the viewer.

<Shot src="tools/debug-viewer/request-tabs.shot" alt="The Response tab of GET /api/notes with status 200. It lists the response headers, and the JSON body is a list of two notes." />

**Copy as curl** copies a `curl` command that sends the same request. Some headers, such as
`Authorization`, are removed when a request is recorded. In the command, such a header has the
value `[redacted]`.

## From your page to the viewer

In development, `[debug] inline` adds the output of `Core\Debug::dump` to the end of an HTML page.
When `[debug] store` is also on, this output starts with one more line. It shows how many queries
the request ran, and it has a link. The link opens this request in the viewer.

## Runs

The **Runs** page lists work that is not a request, newest first:

- a job of a `[[schedule]]` block in `nvs.toml`,
- a job that a worker took from the queue,
- a run of `nvs run` or `nvs test`.

Each row shows the kind, the name, the outcome, the duration, the memory peak, and the number of
queries and dumps. The outcome is **OK**, **Failed** or **Cancelled**. A run that threw an exception
shows its class and the line that threw it. The filters above the list choose the kind, the
outcome, a minimum duration and a minimum memory peak.

<Shot src="tools/debug-viewer/runs.shot" alt="The Runs page with two scheduled jobs. import-orders is OK and ran 5 queries. send-receipts failed with a RuntimeError." />

Press `Enter` to open a run. A run's page has the same boxes and tabs as a request's page. It has no
**Request**, **Response** and **Coverage** tabs, because a run has no HTTP request.

<Shot src="tools/debug-viewer/run.shot" alt="The page of the failed job send-receipts at its Exception tab. The RuntimeError says The mail server did not answer, and the stack lists three functions with their file and line." />

## Mail

The **Mail** page lists the mail of each `[mail.<name>]` block with `capture = true`. Such a block
keeps each message and sends nothing. The page needs `[debug] store = true`. A block that really
sends mail is not on this page.

Open a message to see its headers, its text and its attachments. The HTML is shown in two forms.
**As written** is the HTML your program wrote. **As sent** is the HTML after its CSS is copied into
the elements. Scripts do not run in this preview, and nothing loads from the network.

The page also lists the CSS rules that stay in a `<style>` element, and the rules that match no
element. A note appears when the HTML is larger than 102 KB, because Gmail cuts such a message.

## Routes

The **Routes** page has one row for each method and route. Each row shows the number of requests
and the number of errors. It also shows two durations, p50 and p95. Half of the route's requests
were faster than p50. 95 of every 100 requests were faster than p95, so p95 shows the slow
requests. The row also shows the average number of queries, and when the route last ran.

Click a column's name to sort by it. Click a row to see the route's
requests.

<Shot src="tools/debug-viewer/routes.shot" alt="The Routes page with five routes, such as GET /polls/{id} and POST /polls. Each row shows its requests, errors, p50, p95 and queries." />

## Queries

The **Queries** page has one row for each line of your code that ran a query. Each row shows the
query, how often it ran, its total and its longest time, and how many requests ran it. A badge
such as `3×` shows that one request ran the query three times at that line. Such a query is often
inside a loop. One query that reads all the rows can often replace it.

<Shot src="tools/debug-viewer/queries.shot" alt="The Queries page with three queries. The query select ? * 3 as price ran 90 times in 3 requests and has a 3× badge." />

## Search

The search box searches the requests, the dumps, the log lines, the queries and the exceptions.
Press `/` to go to the search box. The results are grouped by request, newest first.

<Shot src="tools/debug-viewer/search.shot" alt="The results for the word notes. They are grouped by request, and each group lists the request and its queries." />

Press `s` to save a search as a filter. You can also paste a trace id into the search box. Each
response from your server has a `traceresponse` header, which contains the request's trace id. You
can paste the value of this header too. The viewer then opens that request.

## Exceptions

The exceptions page has one row for each exception class and the line that threw it. Each row has a
count, and the dates when the exception was first and last seen.

<Shot src="tools/debug-viewer/exceptions.shot" alt="The exceptions page with one row: RuntimeError with the message There is no such invoice. It was thrown 3 times." />

Here, three requests were for an invoice that does not exist. Each one threw the same
`RuntimeError` on the same line. The page shows them as one row with the count `3`.

## Compare two requests

Press `c` to compare a request with the previous request to the same route. To compare any two
requests, press `m` to select one. The next request you open is compared with it.

<Shot src="tools/debug-viewer/compare.shot" alt="Two GET requests side by side. The first has status 500 and the second has status 404. The page says that 6 rows differ." />

The page shows the two requests side by side and highlights each row that differs. It compares the
request's path, query, headers and body. It also compares the response's status, headers and body.
Then it compares the queries, the dumps and the log lines.

## Send a request again

Press `r` to replay a request. The viewer sends the recorded request to your development server
again. Replay works only when `nvs serve` started `nvs debug`.

<Shot src="tools/debug-viewer/replay.shot" alt="A dialog with the question Send this request again? It says that GET /api/notes/1 is sent to the server, and it has the buttons Cancel and Send." />

Your code runs again for this request. If it sends an email, the email is sent again. If it writes
rows to the database, the rows are written again. So the viewer first shows a dialog. The request is
sent only when you click **Send**.

## Make a test from a request

Press `t` to make a test from a request. The test sends the same request to your program with
`Core\Test::request`. It checks that the response is the same.

<Shot src="tools/debug-viewer/to-test.shot" alt="A test made from a GET request to /api/notes. It checks that the status is 200, the content type is application/json and the JSON body is an empty list." />

The test checks the status, the `Content-Type` header, the `Location` header of a redirect, and the
body. A JSON body is compared as data, so spaces in it do not matter. The **Copy** button copies the
test. Save it in your project and run it with `nvs test .`.

`nvs debug to-test` prints the same test in a terminal. Give it the trace id that the viewer shows.
`--write <file>` writes the test to a new file. When no recorded request has that trace id, the
command prints an error:

<Terminal src="tools/debug-viewer/unknown-trace.term" />

Some headers, such as `Authorization`, are removed when a request is recorded. In the test, such a
header has the value `'redacted'`. Replace it with a credential that your tests may use.

## Settings and lost records

The **Settings** page has the theme, the editor that a `file:line` opens, and your saved filters.
Your program can run in a container. There, its files can have other paths than on your
computer, and a `file:line` link does not open. A path mapping fixes this. It replaces the start of each recorded
path, such as `/app`, with the folder on your computer. A button at the bottom deletes every
recorded request.

Your server saves each request as records: one for the request, and one for each query, dump and
log line. These records wait in a folder until `nvs debug` reads them. The folder has a size limit,
`[debug] spool_max`. When the folder is full, Novis deletes the oldest files, and their records are
lost.

A record is also lost when `nvs debug` cannot read it. Then the live state turns orange and shows the number of
lost records. Click it to see each count on the **Settings** page.

<Shot src="tools/debug-viewer/lost.shot" alt="The settings page at Lost records. It says that 5 records were dropped. The top bar shows an orange state with the text 5 lost." />
