This page compares Novis with PHP, Bun and Go. Each language runs the same small web programs. One
command measures all four on one machine, and anybody can run it.

The page has four parts:

- **Speed and memory**: how many requests each server answers, and how much memory it uses.
- **More than one CPU core**: how each server uses more cores.
- **When something goes wrong**: what happens to requests during a deploy, or when one request runs
  away.
- **Features**: a table of things a web server needs, and which server has each one.

## How the test works

Each language runs as a web server in its own container. The same nginx server is in front of each
one. nginx handles TLS, so every request is sent over HTTPS. Each server gets the same number of CPU
cores, and only one server runs at a time.

- Novis runs with `nvs serve`.
- PHP runs with PHP-FPM, with opcache turned on.
- Bun runs with `Bun.serve`.
- Go runs with the `net/http` package.

Each server runs with its default settings. When a setting is needed for a test, the page says which
one. When a server stops, Docker starts it again. Servers in production run the same way.

Each program is written the way the documentation of its language shows. Before a test is timed, the
four servers must return the same answer for the same request. A server that returns a different
answer gets no number.

### How to read the charts

The absolute numbers depend on the machine. A faster machine gives bigger numbers for all four. The
result is the relation between the four servers.

The number in the circle before a bar is the server's place, and place 1 is the best result. The
coloured bars are the best results. The margin of error is about 3%. Two results closer than that
get the same place, and the next place is skipped.

Every number is the middle result of several runs. Each speed test runs 5 times, and the runs take
turns between the four servers. The tests in "When something goes wrong" run 3 times each. A slow
moment on the machine then affects all four servers in the same way.

Novis's bars have a border, so you can find them quickly.

## Speed and memory

Each server has two bars in each test. The first bar is requests per second, and the fastest server
has the full bar. The second bar is peak memory, and the server that used the most memory has the
full bar. The best results are the most requests and the least memory.

<CaseCharts />

`p99` is the time within which 99 of 100 requests were answered. Peak memory is the most memory the
server's container used during the test. Memory matters as much as speed when you pay for a server,
because less memory per server means more servers on one machine.

When servers in different languages reach about the same speed, the language is probably not the
limit. The limit is then the rest of the setup: the nginx proxy, HTTPS and the network between the
containers.

## More than one CPU core

A server can use more than one CPU core in two ways. It can answer many requests at the same time,
each on its own core. Or one request can split its own work into parts that run at the same time.

### Scaling with more cores

This test checks if a server gets faster when it has more CPU cores. Each request runs a loop that
takes about one millisecond of CPU time. The test runs each server with one core and then with four
cores.

Each bar shows how many times more requests per second the server answers with four cores than with
one. With four cores, four times is the most possible, and that is the full bar. The line under the bar has the requests per
second.

The loop only does arithmetic. So the requests per second show how fast each language runs a loop,
and not how fast it handles a request. The tests in "Speed and memory" measure that.

The HTML page test is not used here. Some servers answer it so fast that nginx becomes the limit
with four cores. The test would then measure nginx and not the server.

<CoreCharts chart="many-requests" />

All four servers use the cores. Novis, PHP and Go do it with no extra code. One Bun process runs your
code on one core. So the Bun program starts one Bun process for each core itself.

### One request in four parts

Each request runs the same loop in four parts. The test times one part alone, and then all four
parts on four cores. Each language has two bars: the time for one part, and the time for all four
parts. A shorter bar is faster, and the coloured bar is the fastest time for four parts. Only the
time for four parts has a place. When the four parts run at the same time, both bars are about the
same length.

<CoreCharts chart="one-request" />

The three languages split the work in different ways:

- In Novis, each part is a script with its own memory. It gets a copy of its arguments and cannot
  change the request's variables. Together, the parts must stay under the request's memory and CPU
  limits.
- In Bun, each part is a `Worker` with its own memory. Values are copied between them.
- In Go, each part is a goroutine. All parts share the same memory, so one part can change a value
  that another part reads.

PHP is not in this chart. PHP-FPM runs one request on one core, and PHP has no built-in way to split
it. Novis needs no setting for this. A program may start the scripts in its own app folder. A
script in another folder needs that folder in `[capabilities.script] spawn`.

## When something goes wrong

These tests send steady requests to each server while something goes wrong. The charts show what
happened to those requests.

### Deploying a new version

The four servers take a new version of a program in two different ways:

- **Live deploy:** Novis and PHP. You copy the new source files to the server, and the next request
  uses them. There is no build, no restart and no reload.
- **Build and restart:** Bun and Go. The server loads new code only when it restarts. Go also needs
  a new build first.

Each chart shows the two groups in separate boxes, and the place counts inside each box.

Each test puts a new version of a program on a running server. Requests arrive the whole time, and
the test checks every page it gets back. A failed request is a request that gets an error instead of
the page. A mixed page is built partly from old files and partly from new files. Each bar is every
request a server got during the test. The number at the end is the share of complete pages.

#### A small deploy

The new version is 200 source files. They are copied over the old files, one after another, which
takes about 2 seconds.

<FaultCharts chart="deploy" />

Novis waits until no file has changed for 1 second. Then it switches to the whole new program at
once. In this test, it used the new version 1.2 seconds after the copy, and every page was
complete. PHP had no failed request, but 47% of its pages mixed old and new files. PHP checks each
file on its own, so during the copy some files are new and others are still old. Bun and Go need a
restart, and some requests failed during each restart.

#### A big deploy

The new version is 2,000 source files, copied the same way. This takes about 20 seconds.

<FaultCharts chart="deploy-big" />

Novis used the new version 3.5 seconds after the copy, and every page was complete. PHP mixed old
and new files in 90% of its pages. The copy took longer on PHP's server, because the copy and PHP's
workers share the one CPU core. Bun and Go failed requests during the restart, as in the small
deploy.

#### Switching to a new release

Many teams deploy a new version this way. The new version is copied to its own folder first. When it
is complete, a link named `current` is switched from the old folder to the new one. The server reads
the program through that link. For PHP, nginx uses `$realpath_root`, as the PHP deploy tools
recommend.

<FaultCharts chart="deploy-switch" />

Novis and PHP had no failed request and no mixed page. For PHP, switching a link is the safe way to
deploy. Novis is also safe when you copy the new files over the old ones. Bun and Go still need a
restart.

### Runaway requests

A runaway request is a request that never ends, or one that uses more and more memory. Each test
sends steady requests to the server for 15 seconds, and one runaway request together with them.
The test checks three things:

- Did the server stop the runaway request?
- Did the server keep running?
- Did any of the other requests fail?

Each bar is all the other requests. The green part was answered, and the red part failed. The line
under the bar says what happened to the runaway request. It also says how fast the other requests
were answered, compared with the same test without a runaway request. A server that stopped the
runaway request and kept running gets a better place than one that did not.

By default, Novis and PHP stop a request at 128 MB of memory or 30 seconds of CPU time. In Novis,
these limits are in the `[limits]` table. In PHP, they are `memory_limit` and `max_execution_time`.
Bun and Go have no limit for one request.

#### A request that uses too much memory

<FaultCharts chart="memory" />

Novis and PHP stopped the runaway request, and every other request was answered. Bun and Go have no
memory limit for one request. The container's memory limit stopped the whole server, so the open
requests failed. Docker then started the server again.

#### A request that never ends

<FaultCharts chart="loop" />

Each server has one CPU core in this test. Novis stopped the runaway request after 30 seconds of CPU
time. Until then, Novis gave the core to the other requests every 10 ms, so every other request was
answered. PHP and Go also share the core between their requests. Bun and Go never stopped the runaway request. On Bun, the
runaway request kept the core, and some other requests failed.

## Features

Each row tests one thing a web server needs. A small program for each language tries it, and the
result comes from what the server did. A result says what happened in that test. It is not a
promise for every program. Each result is one of five values:

- **Built in**: the server does it with no setting and no extra code.
- **On by default**: a setting does it, and this setting is on when you install the server. You do
  not need to change anything. The cell names the setting, which you can also use to turn it off.
- **One setting**: the server does it after you change one setting. The cell names the setting.
- **Your code**: you must write the code yourself, or add a library.
- **No**: the server does not do it.

Most Novis settings that are off by default are off for security. A Novis program gets only the
access that you give it. The details on this page say why a setting is off, for every language
where the reason is known.

Click a result to see the four programs for that row. Click **See details** to read more about a
row on this page. The table shows every result, also the rows where another language does better
than Novis.

### Escaped text

In Novis, every string you print in a request is escaped. To write HTML tags, you use an `html`
template, and the values in it are still escaped. To print raw HTML, the program must use
`Core\Html\Markup`, so it can only happen when you choose it. In Go, `html/template` escapes, but
`fmt.Fprintf` writes the same text unescaped.

### Outside data

Outside data is every value that comes from outside the program. Examples are the request, the
session, environment variables and command line arguments. A reply from another server and values
read from a database are outside data too. Novis calls these values tainted. A tainted value in an
SQL string is a compile error, so the program never runs with it.

### One visitor, two requests

One visitor sends two requests with the same session cookie. The slow request changes a value in
the session and then works for 2 seconds. The fast request starts 200 ms later and only reads the
session. The chart shows how long the fast request waited for its answer. Bun and Go have no
sessions without a library, so they are not in the chart.

<SessionChart />

PHP locks the session file while a request has the session open. The lock stays until that request
ends, so the fast request waits for the slow one. A PHP program can avoid this in two ways.
`session_start(['read_and_close' => true])` reads the session and closes it at once.
`session_write_close()` saves the session and releases the lock before the slow work starts.

Novis reads the session once when the request starts. It writes the session once when the request
ends, and only if it changed. No request waits for another one. This has a cost. Two requests of
one visitor can change the session at the same time. Then the session from the request that ends
last is kept, and the change of the other request is lost.

### Many waiting requests

PHP-FPM answers each request in its own worker process. By default, it starts at most 5 workers.
The PHP configuration file says that this default is for a server with few resources. This test
sets `pm.max_children` high enough for 1000 requests at the same time.

### Edited files

Novis checks for edited source files while it runs. No setting turns this check off. PHP checks for
edited files by default, with `opcache.validate_timestamps`. Every test on this page runs PHP with
this check on. Both servers use their default and check every 2 seconds.

Bun shows an edit only when it runs with `bun --hot`. Go compiles the program, so you must build and
start it again.

## Run it yourself

You need [Bun](https://bun.sh) and [Docker](https://www.docker.com). Clone the Novis repository and
run this command in it:

```sh
bun nv bench-compare
```

The command builds each server, runs each test and prints the results. It takes several minutes. To
run the feature table, add `--scenarios`. To check that everything works with a short run, add
`--smoke`.
