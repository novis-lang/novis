Mail comes back after you send it. A bounce says that a message could not be delivered. A reply
comes from a person. Your program reads these messages in two ways:

- `Core\Imap` reads a mailbox on a mail server. IMAP is the protocol that mail programs use to
  read a mailbox.
- `Core\Mail\Message::parse` reads one message that a mail provider posts to your webhook. A webhook
  is a request that a mail provider sends to your server when something happens.

Both ways give you a `Core\Mail\Message`. [Sending mail](/guides/how-to-use/sending-mail/) shows how
to send the messages.

## The settings block

An `[imap.<name>]` block describes one mailbox. You choose the name. This block is named `inbox`:

```toml
[imap.inbox]
host = "imap.example.com"
port = 993                                   # the default
tls = "implicit"                             # encrypted from the first byte, the default
user = "bounces@example.com"
password_file = "/run/secrets/imap-inbox"    # the file contains the password

[capabilities.imap]
connect = ["inbox"]                          # the blocks this program may open
```

The `[capabilities.imap]` block allows the program to open the block. Without it, `Core\Imap::open`
throws a `RuntimeError`. Your code gives only the name of the block. So a program cannot read
another mailbox.

- `tls` is `implicit` or `starttls`. With `starttls`, the connection starts without encryption and
  is encrypted before the sign-in. There is no `none`, so a password is never sent unencrypted.
- `tls_ca_file` is a PEM file with the certificate of your own certificate authority. It works as
  in a `[mail.<name>]` block.
- `auth = "xoauth2"` signs in with an OAuth token instead of a password. The keys
  `oauth_token_url`, `oauth_client_id`, `oauth_client_secret`, `oauth_scope` and
  `oauth_refresh_token` work as in a `[mail.<name>]` block.
- `timeout` is how long one command to the server may take. The default is `30s`.

Read every key in [Reference: configuration](/reference/config/the-blocks-the-binary-accepts/).

## Reading a mailbox

`Core\Imap::open` connects to the server and signs in. `folder` opens one folder, such as `INBOX`.
`search` returns the UID of each message that matches. A UID is the number the server gives each
message in a folder. `fetch` reads the message with that UID:

<Snippet src="guides/how-to-use/receiving-mail/read-inbox.nvs" />

`search` takes these options, and each one makes the list shorter:

- `unseen: true` finds only the messages that are not read yet.
- `since` and `before` take a date. They find the messages received on that day or later, or
  before that day.
- `from` and `subject` take a text. They find the messages whose `From` header or subject contains it.
- `limit` returns at most that many UIDs.

The connection is closed when the request or the script ends. A script that checks the mailbox
every few minutes can run as a [scheduled job](/guides/simple-programs/scheduled-job/).

## Reading a message from a webhook

`parse` takes a `string` or `bytes`. It never throws. A header that the message does not have is
`null` or an empty list. The other sections of this page explain `kind()`, `answers()`,
`bounceTag()` and `report()`.

## What kind of message it is

`kind()` returns a `Core\Mail\Message::Kind`. It is one of these:

- `Bounce`: a delivery report that says at least one recipient failed.
- `Delay`: a delivery report that says the delivery is late, and no recipient failed.
- `Complaint`: a report that a recipient marked your message as spam.
- `AutoReply`: a message that a program wrote, such as an out-of-office reply.
- `Reply`: a reply from a person to an earlier message.
- `Other`: any other message, such as a new question.

Novis reads the kind from the standard headers and report formats. It never guesses from the
subject or the sender. A bounce that does not contain a standard delivery report has the kind `Other`.

## Matching a message to the mail you sent

`answers()` returns the message id of the message that this one is about. For a bounce, a delay or
a complaint, it comes from the copy of your message inside the report. For any other message, it
comes from the `In-Reply-To` header, or else from the last id in `References`. `Core\Mail::send`
returns this id when you send the message. Save it, so you can find the message later. With it, you
can find the order or the user that the message is about.

A bounce does not always contain a copy of your message. The `bounceTag` option of `send` helps
here. It adds a tag to the bounce address. With `return_path = "bounces@example.com"` in the
`[mail.<name>]` block and the tag `order-42`, a bounce goes to `bounces+order-42@example.com`.
`bounceTag()` reads that tag from the address the bounce was delivered to. In the webhook snippet
above, it returns `order-1042`.

## The delivery report

A bounce and a delay contain a delivery report. `report()` returns it. For a message that is not
a delivery report, the result is `null`. The report is a `Core\Mail\Report`.
`Core\Mail\Report::recipients()` returns one `Core\Mail\ReportRecipient` for each address:

- `address()` is the address of the recipient.
- `action()` is what happened to the message for this recipient. It is one of these:
  - `Failed`: the message could not be delivered.
  - `Delayed`: the message is not delivered yet. The server tries again.
  - `Delivered`: the message was delivered.
  - `Relayed`: the message was passed to a server that sends no report.
  - `Expanded`: the message was delivered to a mailing list. The list sends it to its members.
- `status()` is the status code, such as `5.1.1`. It is an empty string when the report has no code of three numbers.
- `isPermanent()` is `true` when the status code starts with `5`. Mail to this address will not
  arrive later, so do not send to it again.
- `diagnostic()` is the message of the mail server, or `null`.

In the webhook snippet above, `anna@example.org` failed with `5.1.1`, so `isPermanent()` is `true`.
The delivery to `bo@example.org` is late, and the status `4.4.1` is not permanent.

## Moving, marking and deleting messages

A `Core\Imap\Folder` changes messages on the server:

- `move($uid, $folder)` moves the message to another folder. There it has a new UID.
- `markSeen($uid)` marks the message as read, and `markUnseen($uid)` marks it as not read.
- `flag($uid, $flag)` adds a flag, and `unflag` removes it. A flag is a mark the server keeps on a
  message, such as `\Seen` or `\Flagged`.
- `delete($uid)` deletes this one message. Other messages stay.

`flag` does not accept `\Deleted`. Call `delete` to delete a message. This program sorts the new
messages of a folder by their kind:

## Testing

A test should not read or change a real mailbox. For tests, the block reads a folder on your disk
instead of a server. Write `directory` in the block, and no other key:

```toml
[imap.inbox]
directory = "mail"

[capabilities.imap]
connect = ["inbox"]

[capabilities.fs]
read = ["mail"]
write = ["mail"]
```

Each folder inside `mail` is a mail folder, such as `mail/INBOX`. Each message is a file named
`<uid>.eml`, such as `mail/INBOX/4.eml`. A `.eml` file is one whole message, headers first. The
flags of a message are in a `<uid>.flags` file beside it, one flag on each line.

The program needs `fs.read` for the folder. It also needs `fs.write` to move, mark or delete a
message. Both go in the `[capabilities.fs]` block, as above. Each change is made to the files on
disk. So the test in the snippet above undoes its changes at the end.

The examples on this page read the `.eml` files in this folder. Their output comes from those files.

## Do and don't

- Do keep the password in a file, and name it with `password_file`.
- Do grant `[capabilities.imap] connect` only the blocks the program uses.
- Do store the message id that `send` returns, and match it with `answers()`.
- Do stop sending to an address when `isPermanent()` is `true`.
- Don't put a received HTML body on a page without `Core\Html::sanitize`.
- Don't test against a real mailbox. Use a `directory` block.
