This guide builds an extension from an empty folder. The extension shows code in color. It uses the
Rust library [`syntect`](https://crates.io/crates/syntect) for the work. Novis does not include a
syntax highlighter, so an extension is the way to add one. At the end, a web page uses the extension
to show Markdown with colored code blocks.

The extension has two classes:

- `Example\Highlight\Highlighter` is written in Rust. It has two methods: `tokens` splits code into
  tokens, such as keywords and strings, and `languages` returns the languages it knows.
- `Example\Highlight\Code` is written in Novis. It calls `Highlighter` and writes the tokens as HTML.
  It is packed into the same file as the Rust code.

[`Core\Markdown::toHtml`](/reference/core/markdown/tohtml/) converts Markdown to HTML. Its `code`
parameter is a function that writes the HTML of each code block. The web page passes `Code::toHtml`
there.

The finished project is in the Novis repository, in the folder `website/guides/highlight-extension`.
The [last section](#get-the-finished-project) shows how to download it.

## What you need

- Novis. See [Install](/install/).
- Rust, installed with [rustup](https://rustup.rs/).
- The Rust target `wasm32-wasip2`. It compiles Rust to WebAssembly:

```sh skip="installs a Rust target with rustup"
rustup target add wasm32-wasip2
```

## Step 1: Create the project

`nvs ext new` writes a small extension that works. Start from it:

```sh
nvs ext new --lang rust highlight
cd highlight
```

The folder `highlight` now has these files:

| File | What it is |
|---|---|
| `Cargo.toml` | The Rust package. |
| `src/lib.rs` | The Rust code of the extension. |
| `wit/greeting.wit` | The functions of the extension, written in WIT. |
| `wit/deps/` | What every extension can use. Do not change these files. |
| `nvsx.toml` | The manifest: the class name and the Novis signature of each method. |
| `tests/GreetingTest.nvs` | A Novis test for the extension. |

The template is the class `Example\Greeting` with one method, `hello`. You can build and test it
now to check that your tools work:

```sh skip="builds with cargo, which bun nv ext-templates --example runs"
cargo build --release --target wasm32-wasip2
nvs ext build
nvs ext test
```

Then delete `wit/greeting.wit`, `tests/GreetingTest.nvs` and the file `greeting.nvsx` that
`nvs ext build` wrote. The next steps add the files of the highlighter.

## Step 2: Describe the functions in WIT

WIT is the language that WebAssembly components use to describe their functions. Novis reads it to
know what the extension exports. Create `wit/highlight.wit`:

<ExtensionFile path="wit/highlight.wit" />

A few things to know about this file:

- A name in WIT uses dashes. A function `to-html` is `to_html` in Rust and `toHtml` in Novis.
- Every function returns a `result`: the value, or an `error`. Novis throws an exception for an
  error. You can see which one in [Errors](#errors).
- The `world` at the end includes `nvs:ext/extension`. That is what every Novis extension can use.

Each WIT type has one Novis type:

| WIT | Novis |
|---|---|
| `bool`, `s64`, `u64`, `f64` | `bool`, `int`, `uint`, `float` |
| `string` | `string` |
| `borrow<bytes>` as a parameter, `bytes` as a result | `bytes` |
| `list<T>` | `array<T>` |
| `record` | an anonymous object, such as `{ text: string, kind: string }` |
| `option<T>` | `?T` |
| `enum` | an enum |

A WIT `bytes` is a byte string that Novis keeps. The extension reads it with `read()`. It builds a
result with `append()`. A WIT file that uses `bytes` needs the line
`use nvs:ext/types@1.0.0.{error, bytes};`. A `list<u8>` for a Novis `bytes` does not load.

`tokens` returns `option<list<token>>`. In Novis, that is `?array<{ text: string, kind: string }>`.
The result is `null` when the extension has no grammar for the language.

## Step 3: Add the library

Open `Cargo.toml`. Change the package name to `highlight`, and add `syntect` under
`[dependencies]`:

<ExtensionFile path="Cargo.toml" />

`syntect` uses the grammars of the text editor Sublime Text, and it includes grammars for many
languages. Its default regex library is written in C. The feature `regex-fancy` uses a regex library
written in Rust, which builds for WebAssembly with no other tools.

`crate-type = ["cdylib"]` makes Cargo write one `.wasm` file. The `[workspace]` table at the end
makes the project build alone, also inside another Cargo workspace.

## Step 4: Write the Rust code

Replace `src/lib.rs`:

<ExtensionFile path="src/lib.rs" />

The macro `wit_bindgen::generate!` reads the WIT files and writes the Rust types for them. The trait
`Guest` has one method for each function in the WIT file. `Token` is the WIT record as a Rust
struct.

A grammar gives each piece of code a list of scopes, such as `keyword.control.rust`. `kind_of` turns
those scopes into one short kind, such as `keyword`. The list of kinds is fixed, so the Novis class
knows every kind it can get.

`SYNTAXES` loads the grammars at the first call. Later calls in the same request use them again.

This extension uses only strings. A function with a `bytes` parameter or result uses two helpers.
They are in the template's `src/lib.rs` from Step 1.

`read_all` reads a `bytes` parameter into a `Vec<u8>`. `bytes_from` returns a `Vec<u8>` as a new
`Bytes`. In Rust, `Bytes` is `nvs::ext::types::Bytes`. The template's `reverse` uses both:

```rust copy="crates/nvs-cli/templates/ext/rust/src/lib.rs"
fn reverse(data: &Bytes) -> Result<Bytes, Error> {
    let mut bytes = read_all(data);
    bytes.reverse();
    Ok(bytes_from(&bytes))
}
```

If the Rust code panics, the program gets an `ExtensionError`. The request goes on. The next call to
the extension gets a new copy of it.

## Step 5: Write the manifest

Replace `nvsx.toml`:

<ExtensionFile path="nvsx.toml" />

| Key | What it is |
|---|---|
| `class` | The Novis name of the class. |
| `interface` | The WIT interface the class calls: the package, then the interface name. |
| `module` | The `.wasm` file that Cargo writes. |
| `source` | A folder of Novis files to pack with the extension. Step 6 adds one. |
| `[[methods]]` | One table for each function. `signature` is written in Novis. `help` is a short description. |

The Novis signature and the WIT function must match. If they do not match, `nvs ext build` stops
with an error that names the method.

## Step 6: Add a Novis class

An extension can contain Novis classes beside its Rust code. They must be in the namespace of the
manifest's class, here `Example\Highlight`. A program can use them with no `autoload` line. Create
`nvs/Code.nvs`:

<ExtensionFile path="nvs/Code.nvs" />

`Code::toHtml` builds the HTML with `html` templates. A template escapes each value in it, so the
code is shown as text. `<script>` in the code is shown as the text `<script>`. The result is a
`Core\Html\Markup` value, so a page writes it as HTML.

Each token gets a class, such as `hl-keyword`, and `Code::styles` gives each class a color. A
template escapes a value in an attribute for HTML, but not for CSS. So the colors are in the style
sheet, and the tokens have only class names.

The parameters are `tainted string`, so a method accepts text from a form. When an argument to an
extension is `tainted`, every string in the result is `tainted` too. The template escapes them.

## Step 7: Build the extension

```sh skip="builds with cargo, which bun nv ext-templates --example runs"
cargo build --release --target wasm32-wasip2
nvs ext build
```

`cargo build` writes `target/wasm32-wasip2/release/highlight.wasm`. `nvs ext build` packs it with
the manifest and the Novis files into one file, `highlighter.nvsx`. It names the file after the last
part of the class name. Then it loads the file and checks it, and prints the path and the `sha256` of
the file.

Run both commands again after each change to the Rust code, the manifest or the Novis files.

Create `tests/HighlightTest.nvs`:

```sh
nvs ext test
```

The tests need no `nvs.toml`. If `highlighter.nvsx` is older than a file it is built from,
`nvs ext test` stops and tells you to build it again.

## Step 9: Use the extension in a web page

Create `demo/index.nvs`. It is a page with a form. You write Markdown in the box, and the page shows
it as HTML. Each code block that names a language is shown in color:

<ExtensionFile path="demo/index.nvs" />

`Core\Markdown::toHtml` calls the `code` function for each code block that names a language after
its opening backticks. If the function returns `null`, the block is written as plain text. `Code::toHtml`
returns `null` for a language it has no grammar for.

A program can use an extension only when the configuration file `nvs.toml` lists it.
`nvs ext pin` prints the entry for a file:

```sh
cd demo
nvs ext pin ../highlighter.nvsx
```

```toml
[[extension]]
path   = "/home/you/highlight/highlighter.nvsx"
sha256 = "a09d75a3a0dbc8e46980ebc716f5955705e0ed92c18249cbba4fe070c5b0cf81"
```

Save the entry as `demo/nvs.toml`. Your path and your `sha256` are different. Then start the
server:

```sh
nvs serve index.nvs
```

Open `http://127.0.0.1:8000/` and click **Show**. Try some code that looks like HTML, too:

````md skip="text the reader types into the demo page"
```html
<script>alert(1)</script>
```
````

The page shows the `<script>` tag in color, as text. It does not run.

Each build writes a new `highlighter.nvsx` with a new `sha256`. A file whose `sha256` is not the one
in `nvs.toml` does not load. So after each build, run `nvs ext pin` again and replace the entry.

## Errors

The Rust code can fail in three ways. Each one gives the program something different:

| What happens in Rust | What the program gets |
|---|---|
| A function returns `Err(Error::Invalid(message))` | a `LogicError` with the message |
| A function returns `Err(Error::Parse(message))` | a `ParseError` with the message |
| A function returns `Err(Error::Runtime(message))` | a `RuntimeError` with the message |
| The code panics | an `ExtensionError` |
| The code uses more time or memory than the request may use | the request stops, as for any limit |

`tokens` returns `Error::Runtime` if a grammar cannot read a line. The template's `hello` from step 1
shows another error: an empty name returns `Error::Invalid`.

## Files and the network

This extension needs no files and no network. An extension that needs them asks in its manifest,
with a `[requests]` table. The person who runs the server then allows them in the `[[extension]]`
entry. The extension gets only what both allow. See
[the `[[extension]]` entry](/reference/config/extension/).

Pass a large file on disk to the extension as a path. Do not pass its content as `bytes`. The
extension asks for its folder with `read` in the `[requests]` table. The `[[extension]]` entry
allows that folder with `grants = { read = [...] }`. Then the extension reads the file itself.

## Get the finished project

Download only the folder `website/guides/highlight-extension` of the Novis repository. A sparse clone
(a clone that checks out only the folders you name) does this:

```sh skip="clones the repository with git"
git clone --depth 1 --filter=blob:none --sparse https://github.com/novis-lang/novis.git
cd novis
git sparse-checkout set website/guides/highlight-extension
cd website/guides/highlight-extension
```

Then build and test it, as in steps 7 and 8.
